物理行号 ctid，就是这条记录的磁盘地址

ctid = (blockNum, itemid/lpNum)：第一维定位数据块，第二维定位块内的 line pointer；它本身也可以直接当查询条件用。

01
两级坐标，一次乘法 + 一次偏移
blockNum 定块，lpNum 定块内第几条记录。
02
索引里 key 存值、value 存 ctid
命中索引后按 ctid 回表，读取 heap 中对应的 tuple。
03
ctid 支持等值与范围查询
见右侧 SQL；范围条件可用来做块级扫描。
04
VM 也用 ctid 的 blockNum
判断该块是否全部可见，决定要不要回表（Index Only Scan）。
select * from table where ctid = '(1,9)';
select ctid,* from tbl; -- (0,1) = 0 号块第 1 条 select * from table where ctid = '(1,9)'; select * from table where ctid >= '(0,1)' and ctid < '(11,0)';
回表时访问 ctid 指向的 heap tuple；是否需要回表（Index Only Scan），也要用 ctid 里的 blockNum 去查 VM 对应 bit。

SECTION 02 · 更新
更新不是覆盖，是打标 + 新写一条
Postgres heap 表的 live tuple 和 dead tuple 都存放在同一个数据文件中：更新时对老记录打标，同时往数据文件里写入一条新记录。因此更新会导致 ctid 变化，而索引 value 里存的正是 ctid。
01
老记录被打标为 dead tuple，新记录写到数据文件中，物理行号随之改变。
02
如果每次更新都要改所有索引，UPDATE 会带来巨大的索引写 IO 放大。
03
PG 的答案是 HOT-update：让索引里那个旧 lp 依然能找到新的 live tuple。

HOT-update 用 block 内的 lp 链条，绕开索引更新

dead tuple 的 lp 本来指向自己的 offset；HOT-update 后该 lp 改指向 live tuple 的 lp，索引里存的旧 lp 依然能找到新记录。

01
核心是 block 内的 lp 链条
dead lp → live lp → live tuple，链路不出块。
02
条件一：索引 key 没有更新
索引项本身无需变化。
03
条件二：新旧 tuple 在同一个 block 内
否则链条跨块，HOT 不成立。
04
用 fillfactor 为 HOT 预留空间
建表时决定每个 block 保留多少空间；非索引字段更新频繁的表收益最明显。
create table tbl (...) with (fillfactor = 80);

SECTION 03 · 垃圾回收
dead tuple 不会自己消失
dead tuple 与 live tuple 混合存放在同一个数据文件中。不及时清理，数据文件就会膨胀：占用更多空间与内存，性能随之下降。但「能不能回收」由事务快照说了算，不是由 vacuum 自己说了算。
01
哪些 tuple version 还可能被老事务用到？看 xid snapshot 里 oldest xid 之后的版本都不能回收。
02
长事务、逻辑复制槽、开启了 hot_standby_feedback 的备库，都可能把这条边界往后拖。
03
所以常见现象是：长事务开启后发生大量更新，被大量更新的表必然膨胀。

为什么只能回收文件末尾的空闲 block？

因为 blockNum 就是地址：中间的块一回收，后面所有块的位置都会前移，索引里存的 ctid 就全错了。

(10,9)
→
(11,9)
如果 block 8 的物理空间被回收，索引 value 里存的 (10,9) 实际访问到的会是 (11,9)。
而回收最后一个数据文件末尾的完全空闲 block 不存在这个问题 —— 它后面已经没有 block 了。

数据库筑基课  /  TRADE-OFFS  ·  NO.18
2024-09-19 · digoal

写得快、整行读得快，代价是怕膨胀、不适合 OLAP

行存把所有字段放在一条 tuple 里，也把 dead 与 live 放在同一个文件里 —— 优势和劣势其实是同一件事的两面。

优势 & 适合场景

  • 写入快：不需要考虑写入位置。
  • 整行读取快：以 tuple 为最小粒度、以 block 组织存储，一次定位一条记录的所有字段，适合经常访问一条记录中多个字段的业务。
  • OLTP 为主的业务场景。
  • 时序热数据：append only + timescaledb 插件 / 分区表 + BRIN 块级索引，适合高速写入与小范围检索聚合。
  • 冷热分离：配合 parquet 列存 + 对象存储压缩历史数据，配合 duckdb 插件高速分析。

劣势 & 不适合场景

  • 怕膨胀：dead / live tuple 混存，不适合「高频更新 + 长事务」混合业务；非要用建议高级 SSD + 监控与处理预案。
  • 单行不能超过 block size：不适合超级大宽表业务。
  • 压缩率低：以行为单位组织存储，存储历史数据成本较高。
  • OLAP 弱：访问少量字段并做大量记录计算时无法使用 CPU 批处理能力，性能相比列存较差。
