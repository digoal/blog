01 · What is Parquet
01 · What

不是「数据文件」，是自解析的存储格式

Apache Parquet 是开源的列式数据文件格式，为高效存储与检索而设计；提供高性能压缩与编码方案批量处理复杂数据，并被众多编程语言与分析工具支持。

01 / COLUMN

按列组织

同列同类型、连续存放，只需读取目标列；配合 CPU 批量指令做向量化处理。

02 / NESTED

原生嵌套

从一开始就考虑 JSON、list、map、dictionary 等复杂嵌套结构，而非先拍平。

03 / CODEC

可插拔编码

压缩方案可按列指定；编码由 enum 声明，未来新增编码无需改动文件协议。

04 / SELF-DESC

自描述 + 索引

thrift 元数据写在文件尾；内置 column index、bloom data，可按条件跳过 page。

再次提醒：不要本能地把 Parquet 当成 text / CSV。它有 head、row group、column chunk、page、footer（meta + column index 的 min/max bound 与 page offset、bloom data），因此能高效存储与检索——而且封装协议还能升级，未来可能有更高效的组织形式。
设计立场
与计算框架、数据模型、编程语言无关，可与任意项目集成 —— 这是它成为 Hadoop 生态列式存储事实标准的前提。
今天的位置
Apache 官方生态涵盖 parquet-java、Arrow C++/Go/Rust、ClickHouse、cuDF、Impala、DuckDB、fastparquet 等实现，各实现对特性的支持程度并不一致。

WHY NESTED MATTERS

为什么嵌套格式是关键

嵌套格式能自然描述互联网与科学计算领域的数据。「原生」支持嵌套，减少了把这些大规模数据规则化、重新组合的代价 —— 这正是它优于「简单拍平命名空间」的地方。

FUTURE-PROOF

协议里预留了哪些扩展点

  • 文件版本：FileMetaData 带 version，lib 按版本解释文件
  • 编码：由 enum 指定，后续可继续添加
  • 页面类型：可新增 page type，不认识的可以安全跳过

可以理解为：meta 里编入了「密语」，reader 据此找到对应的编解码 / 压缩 / 加密 lib。

02 · Row vs Column
02 · Why

行存读整行，列存只读需要的列

一张 A / B / C 三字段的表，两种物理排布决定了查询时到底要碰多少数据。

QUERY

SELECT A, SUM(C) FROM t;

只需提取 A、C 两列 —— 列存下是两段连续 IO；行存下则必须把每一整行都读进来再丢弃 B 列。

WHY IT COMPOUNDS

收益会叠加

同列同类型 → 更好的编码与压缩比 → 更省空间与内存；连续同列值 → CPU 批量指令 → 大批量处理更快；再叠加页级索引 → 连不需要的 page 都不读。

结论：行存适合「整行读取」，列存适合「只读取部分列的统计分析」。这也是 OLAP 场景把列式存储作为主流选择的原因。

02 · Trade-off
02 · Trade-off

优势来自列式，劣势也来自列式

同一份物理排布，在 OLAP 下是加速，在 OLTP 下就是代价。

ADVANTAGES / 适合

OLAP · 数据湖 · 分析型产品

  • 只访问目标列，减少内存与 IO
  • 同列连续，可结合 CPU 批量指令提升处理速度
  • 同列同类型，压缩编码选择更多 → 更高压缩比、更省空间
  • 内置 column index / bloom data，按 where 条件高效过滤
  • 典型落地：DuckDB；云数据库 + OSS 对象存储的冷热分离

对象存储已支持 offset 等文件访问接口，才能与 Parquet 索引配合。

LIMITS / 不适合

OLTP · 高频小事务

  • 需要读一条记录的多数字段时，按列分开存储反而要访问更多 page
  • 不支持物理更新 / 删除，有这类需求必须重整数据
  • 不适合小数据量高频写入：压缩比下降、footer 每次刷新造成空间浪费
  • 不适合高并发小事务查询：没有单点精准索引 / secondary index
一句话：分析型批量读 = 主场；点查、更新、小事务 = 客场。

03 · Configuration

行组、块、页：三个尺寸的权衡

大块换顺序 IO，小块换细粒度读取；没有万能值，只有与访问模式匹配的值。

ROW GROUP SIZE
512M–1G

更大 → 更大的列块、更大的顺序 IO；代价 → 需要更大的写缓存，且可能要读整个行组。

建议让一个行组完整适配一个 HDFS Block。

HDFS BLOCK SIZE
1GB

较优读取配置：行组 1GB / HDFS 块 1GB / 每个 HDFS 文件对应 1 个块。

块大小需随行组大小相应放大。

DATA PAGE SIZE
8KB

更小 → 更细粒度的读取（如单行查找）；更大 → 更少的 page header 开销与解析开销。

数据页应视为不可分割。

为什么索引能生效：读取时先从文件尾拿到元数据与 column index / bloom data，算出满足条件的 page offset，再按 offset 精确访问 —— 这也是对象存储必须支持 offset 接口的原因。
写入侧的反面：小数据量高频写入会反复刷新文件尾的 foot 信息，压缩比下降、空间浪费，因此不适合拿 Parquet 当事务型写入层。

04 · Page index
04 · Page Index

文件尾的页级导航

每个 Column Chunk 都可创建 ColumnIndex / OffsetIndex（可选）；OffsetIndex 可单独存在，ColumnIndex 必须与它一同创建。

COLUMN INDEX · 每个 page 的统计

null_pages[] · min_values[] · max_values[]
boundary_order · null_counts[]
repetition_level_histograms[] · definition_level_histograms[]

min/max 可以是更紧凑的边界值（如用 "B" / "C" 代替长字符串），但必须是该逻辑类型下的合法值；排序列只存页间边界元素，空间最省。

OFFSET INDEX · 每个 page 的位置

PageLocation { offset, compressed_page_size, first_row_index }

page_locations 按 offset 递增；有 OffsetIndex 时，page 必须从行边界开始（repetition_level = 0）。ColumnIndex 的第 i 项对应 OffsetIndex.page_locations[i]。

设计目标：排序列单行查找精确到目标数据页；范围扫描只读确切数据页；非排序列上的高选择性谓词，让其他检索列也只读匹配行所在页；全行组扫描不产生额外解码开销。
SORTED COLUMN

什么算「排序列」

在该 column chunk 内 logical value 物理有序：page2 的值 ≥ page1（ASCENDING）或反之（DESCENDING），由 BoundaryOrder 标注；UNORDERED 则不能二分。

04 · Bloom filter
04 · Bloom Filter

SBBF：用几个 bit 换掉整页扫描

订单号、昵称、手机号这类高基数字段，边界交叉严重时 min/max 与字典都失效 —— 这时用 Split Block Bloom Filter。

HOW IT WORKS

给 N 个 data page 一块固定大小的 bitset（SBBF），每个 block 256 bits = 8 个 32-bit word。block_insert(value' hash) 把映射位置的 bit 置 1；block_check(value' hash) 检查这些位是否全为 1。

false → 一定不存在，可安全跳过；true → 可能存在（假 true）。

BITS PER DISTINCT VALUE → 假 TRUE 概率

26.4 bit
0.01 %

0.001 %
算一笔空间账：100 万条记录 / 10 万唯一值，要把假 true 压在 0.1% 内 → 16.9 × 100000 = 169 万 bits ≈ 6601 个 256-bit blocks。

04 · Pushdown

同一条查询，数据分布决定 IO

min/max 边界清晰时，BRIN 式过滤效果极好；边界交叉时，所有 page 都要被访问。

# 边界清晰 · 交叉少
data page 1: [1, 10]
data page 2: [20, 100]   ← where id = 90
data page 3: [101, 200]
data page 4: [201, 1000]
data page 5: [1001, 2000]

where id = 90            → 只读 page 2
where id > 90 and id < 200 → 读 page 2, 3
FILTERING WORKS
# 边界不清晰 · 交叉多
data page 1: [1, 100]
data page 2: [2, 110]
data page 3: [5, 100]
data page 4: [90, 200]
data page 5: [50, 150]

where id = 90 → 5 个 page 全都要访问
FILTERING DEGRADES
SOLUTION

高基数 + 未排序 → Bloom filter data

N 个 data page 对应一个 SBBF，col = ? 时只要 block_check 返回 false 就能跳过这些 page。要注意 bit conflict 带来的假 true，以及 bloom 无法过滤 <> / NOT IN。

DICTIONARY PUSHDOWN · 4 个前提

想靠字典跳页，缺一不可

  • column index 先筛出满足范围条件的 page
  • dictionary page 内确实没有目标值
  • 该 data page 的值全部已字典化（没有原始值）
  • reader 能获知「这个 page 是否只含字典值」—— 原文分析 parquet.thrift 后指出 column index 里暂无此信息，扩展它会更好

05 · Nested schema
05 · Nested

用 repeated + group 表达复杂类型

Parquet 用类似 Protobuf 的协议描述 schema：最上层是 message，内含若干 field，每个 field 有重复性、类型、名称三个属性。

message AddressBook {
  required string owner;
  repeated string ownerPhoneNumbers;
  repeated group contacts {
    required string name;
    optional string phoneNumber;
  }
}
REQUIRED

有且只有一次

OPTIONAL

0 或 1 次

REPEATED

0 或多次

模型非常简洁：Map / List / Set 都可以用 repeated fields + groups 表达，无需单独定义这些类型；叶子结点才是原子类型字段，扁平结构只是嵌套结构的一个特例。
TREE → COLUMNS

叶子结点 = 一列

把 schema 中的 field 组织成树，每个叶子（原子类型）对应一个物理列；嵌套字段以点分路径命名。列存连续存储一个字段的值，以获得高效编码压缩与快速读取。

数据库筑基课列存之 Parquet
05 · Shredding
05 · Repetition & Definition

列拆开了，结构怎么找回来

只存 field 值无法表达记录结构：不知道值在哪一级重复，也不知道路径上有多少字段被显式定义。

Dremel 的目标：任意一个 field 的恢复都不依赖其它 field，并且能对任意 field 子集按原始嵌套格式重建 —— 这是「只投影几列」还能还原嵌套记录的前提。
REPETITION LEVEL · r

「在路径的哪一级重复了」

数字代表重复节点的层级：根为 0，下一层为 1……r = 0 代表新记录的开始。required / optional 字段不需要 r，只有可重复字段需要。例：Code 在 r1 中依次是 en-us(0), en(2), en-gb(1)。

计算方法：当前 value 路径与上一个 value 路径做 bitAnd → 相同 repeated 节点数。

DEFINITION LEVEL · d

「路径上有多少可选字段被定义」

用来区分「值为 null」与「路径上根本没定义」，以及 null 到底停在第几层。d < max 即隐含该字段值为 null，null 值不实际存储。只有 optional / repeated 需要 d。例：Backward 路径上 Links 被显式定义 → d = 1。

d = 0 隐含 r 也为 0；required 字段必然被定义，可省下位数。

05 · SHREDDING15 / 19PAR1
数据库筑基课列存之 Parquet
05 · Assembly
05 · Striping & Assembly

两条 level，无损重建记录

以 AddressBook 的 contacts.phoneNumber 投影为例：两条记录，最终只存 3 组 (R, D, Value)。

BIT WIDTH

每个 level 用几个 bit？

取决于 schema 完全展开后的 max definition / repetition level：路径最长为 7，则每个 r/d 用 3 bit 就够。同一个 page 内所有 value 的 r/d 用 RLE 编码，进一步省空间。

RDValue重组时怎么读
02"555 987 6543"新记录；D 已达最大值，值被定义并插入，从根重建到第 2 层。
11nullcontacts 列表在第 1 层新增一项；contacts 已定义但 phoneNumber 没有 → 创建一个空 contacts。
00null新记录；contacts 本身为 null → 只有一个空 AddressBook。
为什么填 NULL

从上往下扫描时，若端节点值缺失、但从顶节点到端节点的完整路径上仍有上层 field 有值，就要为缺失节点填 NULL，否则重建时会把「第 3 个 Name」误认成「第 2 个」。

HISTOGRAMS

每个 data page 的 repetition / definition level histogram 存在 column index 里，记录每一级各有多少条记录 —— 可用于估算内存、推断 null 数量与 list 最大长度。

隐含信息也是信息：Code 是 required，一旦它未定义，就隐含其上级 Language 也一定未定义；d < 路径中 optional + repeated 的数量，则该值必为 null。

schema 是一棵单根树，按深度优先遍历摊平成 list；第一个元素是 root。column_orders 缺失时，min/max 的语义是未定义的。

3 类 PAGE TYPE

data page / index page / dictionary page，位于文件中的不同位置。

EXTENSIBILITY

版本号、encoding enum、可安全跳过的 page type —— 让新编码、新压缩、新逻辑类型编解码能被「未来」加入。

READ PATH · 自解析怎么用

先读末尾 4 字节得到 metadata length → 读 FileMetaData 中的 schema 与 row_groups → 按谓词定位 Column Chunk → 借索引跳页 → 顺序读取命中的 page。

为什么元数据放在文件尾：数据可以依序一次性写入；元数据与数据分离后，未来还能把 column chunk 拆成多个文件，或用独立的 metadata file 表达多个 row group 文件的信息。

06 · Engineering
06 · Engineering

一个数据页的完整生命周期

精简物理类型 + 逻辑类型扩展；按列指定压缩；可选加密；以及损坏时到底会丢多少。

01 / TYPES & ENCODING

8 种物理类型，逻辑类型在上层

BOOLEAN · INT32 · INT64 · INT96 · FLOAT · DOUBLE · BYTE_ARRAY · FIXED_LEN_BYTE_ARRAY

逻辑类型（如 strings → 带 UTF8 标识的 byte array）在物理类型之上封装；levels 用 RLE / bit-packing，值可用字典、Delta 等编码。

02 / COMPRESSION

按列指定，面向未来

SNAPPY · GZIP · BROTLI · ZSTD · LZ4_RAW · LZ4 (deprecated)

dictionary page 必须放在 column chunk 第一位，且一个 chunk 最多一个 —— distinct 极多时只能部分字典编码，此时改由 bloom filter 兜底过滤。

03 / ENCRYPTION

加密不牺牲列式能力

客户端加解密，存储服务器看不到明文、元数据或密钥；认证加密防篡改；不同列与页脚可用不同密钥；支持部分加密（只加密敏感列）、两种元数据保护模式，并尽量降低加密开销。

04 / CORRUPTION & RECOVERY

损坏半径是分层的

文件元数据坏 → 整个文件丢失；列元数据坏 → 该列块丢失；page header 坏 → 该列块剩余页面丢失；页内数据坏 → 只丢这一页。较小的行组更能抗损坏。每写完一个 row group 就增量合并 meta 并 fsync，可从前一个 row group 的 meta 恢复历史数据。

07 · Takeaway
07 · Takeaway

带走五句话

以及一页的延伸阅读。

01

它是格式，不是文本。自带 schema、编码、压缩、索引与文件尾元数据，读取从文件末尾开始。

02

列式是收益也是边界。OLAP 批量少列读取是主场；点查、更新、高频小事务是客场。

03

少读数据靠三层过滤。min/max 走范围、bloom 走高基数等值、字典走低基数；三者都有失效条件。

04

嵌套靠 R/D levels 无损重建。r 记「在哪一级重复」，d 记「定义到第几层」，null 不必真存。

05

协议留了未来。版本号、encoding enum、可扩展 page type 与 thrift 元数据，让新算法无需重造格式。
