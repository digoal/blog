Agenda / 本节路线

从一个「无序」的假设说起六步，把 CLUSTER 的原理、实测和边界讲清楚。

01 / WHY
heap 为什么无序
FSM 找空位就插，写入快、无热点；ctid 按块号 + 行指针寻址。
02 / WHAT
CLUSTER 做了什么
按索引顺序把 heap 的行重写一遍，一次性动作。
03 / HOW
为什么能省 IO
区间扫描时，回表访问的块从分散变相邻。
04 / PROOF

05 / COST
代价与边界
排他锁、磁盘空间、一次性；哪些表坚决不要碰。

01 / Background

无序，是 heap 的主动选择写入优先的存储结构，代价留给查询侧。

01

插入时靠 FSM 找到空闲空间够用的块就写，不挑位置。

02

换来的是 插入快：不用选目标 page、不用分裂、不用改 page link，并发写相邻 value 也不会撞热点页。

03

更新产生的新版本 tuple，可能落进另一个 block；顺序进一步被打乱。

04

寻址靠 ctid = (数据块ID, 块内 line point)，与业务顺序毫无关系。

· 无序换写入吞吐，代价是同批记录散落各处
HEAP BLOCK · 块内结构示意（悬停每个 line pointer）
同一个块里混着不同 uid、不同轨迹的记录；物理位置 ≠ 业务顺序。
02 / Definition

按索引顺序，把 heap 重排一遍CLUSTER 不是一种表类型，而是一次重写动作。

cluster 是针对 heap 表 重新排序存储 的行为：按某个索引值的顺序，把行重新写入 heap blocks。
STEP 01

先有索引

例如 (uid, tid)，索引键的顺序就是重排的依据。

STEP 02

按序读出

按索引顺序扫描全表，或顺序扫描后排序。

STEP 03

重写存储

生成按序排列的新副本，并重建表上的索引。

-- 用已有索引重排整张表CLUSTER tbl USING tbl_uid_tid_idx;-- 之后可用同一索引再次整理CLUSTER tbl;
⚠ ONE-TIME · 一次性操作
系统会记住这张表是按哪个索引 cluster 的，但不会帮后续写入维持顺序。想保持，只能定期再执行一次。
来源：PostgreSQL 官方文档 SQL-CLUSTER · 悬停各步骤查看细节
03 / Mechanism

索引没变，变的是回表的距离省的不是索引扫描，是 heap fetch 要碰的数据块数量。

BEFORE · 随机回表
01 索引扫描：拿到一批 ctid
02 ctid 散布在 90 个不同的 block
03 逐块回表取字段 / 判可见性
90 blocks
随机 IO · 大量离散块
AFTER · 连续回表
01 索引扫描：同样拿到一批 ctid
02 ctid 集中在连续的 4 个 block
03 顺序读少量块即可取完全部行
4 blocks
连续 IO · 访问量骤降
尤其当一次查询要访问很多行、且这些行原本散落在大量块里时，收益最明显。

一次通勤，360 个点落在 360 个块越是被「同时写入」打散的数据，越需要 CLUSTER。

即使有 (userid, traceid) 索引，回表时仍要跑遍这些块。

典型受益场景

共享单车 轨迹回放查询
时序数据按某个传感器做 时间范围聚合
一次性取回某索引区间内 成百上千行

共同特征

按有序字段做 范围读取，且数据相对静态（例如历史轨迹整理）。

相关实践：index include 覆盖索引、IoT 车联网实时轨迹、索引组织表 —— 用空间/写入换查询 IO。

05 / Trade-offs

天下没有免费的排序以下六条来自官方文档与本篇实践，上线前逐条确认。

01 一次性操作
后续 INSERT / UPDATE 不会按索引顺序摆放新行。
想维持顺序，只能定期重新 CLUSTER；系统只记住「用哪个索引」，不负责维护。
02 ACCESS EXCLUSIVE 锁
执行期间读写全部被阻塞，直到完成。
必须在维护窗口操作；大表要考虑停服时长，或改用在线重排工具。
03 额外磁盘空间
需要创建表与索引的临时副本。
至少等于「表 + 索引」大小；若走顺序扫描 + 排序，峰值约为 2× 表 + 索引。
04 记得 ANALYZE
优化器会记录表的顺序统计信息。
重排后建议 ANALYZE，否则优化器可能依据旧统计选出错的计划。
05 fillfactor 只帮一半
降低填充率可让 UPDATE 的新版本留在原块。
它缓解更新导致的漂移，但对全新 INSERT 完全无解。
06 不适合高频写入
顺序很快被新数据打乱，收益随时间衰减。
适合历史轨迹整理、归档表等读多写少的相对静态数据。
悬停每张卡片展开细节 · 结论：CLUSTER 适合「相对静态的数据」，例如历史轨迹的整理。
05 / Decision

把它当「整理动作」，不是「存储结构」先判断写入模式，再决定要不要 CLUSTER。

适合

按索引区间 / 同一索引值取回多行
数据相对静态、读多写少
回表块数明显偏多，且可以接受维护窗口

不适合

INSERT / UPDATE 频繁的业务表
单行点查为主，或结果集只需少量行
7×24 无停服窗口、或磁盘余量不足

换个思路：不重排，也能少回表

01include 覆盖索引：把要返回的字段塞进索引，走 index only scan，连 heap 都不用碰。
02批量写入：同一轨迹的记录一次批量插入，写入时就是密集块。
03大字段建模：整条轨迹存进 array / jsonb，一行搞定一次查询。
04结构性方案：索引组织表、HBase 式有序存储，或定期 recluster 脚本。

06 / Open Questions

讲完了，留下四个问题悬停卡片翻面，看思考方向。

Q1 / 持久有序
如何维持频繁变更 / 插入的表记录存储的永久顺序？
悬停翻面 →
思考方向
CLUSTER 是快照式整理，做不到。需要存储层本身有序（索引组织表、LSM 类结构），或接受定期重排的成本。
写入时维持顺序 = 把代价从查询转移到写入
Q2 / 物理连续
如果能维持顺序，如何保证底层 block 物理连续？
悬停翻面 →
思考方向
index page 是由 link 串起来的逻辑有序，物理 page 并不连续，只能起到「聚集存储」的作用；真正的顺序 IO 还要看文件系统与存储介质。
逻辑有序 ≠ 物理连续
Q3 / 业务改进
同一个轨迹的记录批量插入，能否确保写进密集的数据块？
悬停翻面 →
思考方向
单事务批量写同一批点时，FSM 倾向于把它们放进相近的块；这相当于在写入侧就完成「预聚集」，不依赖事后整理。
写入模式，往往比事后优化更划算
Q4 / 建模改进
把一条轨迹存进 array / jsonb 大字段呢？
悬停翻面 →
思考方向
一行 = 一条轨迹，回表从几百个块降到 1 个；代价是单个点难以独立检索、更新，且大字段会走 TOAST。适合「整条取、整条写」的场景。
用查询灵活性换 IO

Takeaway / Q&A

排序的是数据，
省下的是 IO。

heap 用无序换写入吞吐；CLUSTER 用一次重写，把成百上千次离散回表收拢成几个连续块。
它是一次整理，不是一劳永逸的结构 —— 用在对的数据和对的时机上。
