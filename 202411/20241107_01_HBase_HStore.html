01 · 是什么
THE STORE / 全篇的核心命题

一个列簇，一个 HStore

HStore 是 HBase 存放列簇数据的组件。每个 HStore 包含 1 个 memstore 和 0 到多个 StoreFile（HFile），文件数随写入不断增长；达到阈值后由 compaction 收缩旧版本、压缩存储。
为什么需要垃圾回收？
HBase 用 type(put/delete) 表达插入与删除、用 ts 表达版本。删除不是抹掉数据，而是追加一条标记；旧版本与删除标记要靠 compaction 才能真正清掉。
column family→HStore→memstore→HFile(s)
SOURCE · APACHE HBASE JAVADOC
「A Store holds a column family in a Region. It's a memstore and a set of zero or more StoreFiles, which stretch backwards over time.」
官方文档同时点明：Store 最重要的服务之一，是文件越过阈值后的 compaction；日志与锁由 HRegion 层负责，Store 只管 StoreFile 集合。

02 · 怎么存
SORT ORDER / 全篇最值得停一页的地方

为什么是 ts desc：读到的第一条就是最新值

HFile 与 memstore 内，数据一律按下面这个键排序；同一条记录的多个版本因此被挨着放，且最新的排在最前。
rowkey字典序
cf列簇
qualifier列限定符
typeput / delete
ts desc版本倒序
三个连带结果
① 精确查 rowkey 时，顺序扫描到第一个匹配 cell 就能拿到当前版本；
② 同一 rowkey 的所有列簇 / 列 / 版本天然聚在一起，整行读取只需少量块；
③ 删除只是追加一条 type=delete 的更新，旧数据仍在文件里。
示意 · 同一 cell 的三个版本

name = huitailang
← 先读到

type = delete
删除标记
ts = t1
name = xiyangyang
旧版本
于是必须有 compaction
版本与删除标记会一直堆积；达到阈值时合并 StoreFile、收缩旧版本，才真正释放空间。想再往下挖，扩展阅读里指向 LSM-Tree。

GLOSSARY II / 存储与服务

另外七个词，把物理链路说清楚

region server存储服务器
regionrowkey 范围分片
hstore列簇的物理存储单元

三层归属一句话
RS 管 HLog 与 BlockCache；Region 按 rowkey 范围切分；只有 Store 才持有 memstore 与 HFile。写故障恢复靠 RS 层日志，读缓存也在 RS 层，都不属于某个列簇。

READ PATH / 客户端首次读写

先问 ZooKeeper，再问 META，最后才问数据

STEP 01
ZooKeeper
客户端从 ZooKeeper 获取 META 表所在的 Region Server
STEP 02
META 表
查到目标 rowkey 所在的 Region Server，并缓存 META 位置与路由信息
STEP 03
目标 Region Server
直接从该 RS 上获取数据；再次读取走缓存，不再查 META
缓存什么时候失效？ Region 发生移动时缓存失效，客户端重新查询 ZooKeeper 并更新缓存。META 是保存所有 Region 位置的特殊表，它自己的位置存在 ZooKeeper 上。

04 · 擅长什么
STRUCTURE / 列簇是「可调节」的存储形态

同一张表，换个列簇设计就换了一种存储

1 个列簇 · 含全部列
2 个列簇 · 按关联分组
每列一个列簇
↑ 点选三种 schema，观察物理文件如何变化（默认已展示第一种）
PHYSICAL · 1 个 HStore → 1 组 HFile
HFile #1nameaddragesex
HFile #2nameaddragesex
一行的所有列相邻存放 → 取一行只需读少量块
≈ 行式存储
一个列簇装下所有列，HBase 把同列簇数据存在一起，取一整行非常高效；但如果查询只要其中一列，仍要读出包含无用列的块，内存里再挑选。
代价：无法跳过无关列，也不好利用同类型数据的批量计算与高压缩。
PHYSICAL · 2 个 HStore → 2 组 HFile
cf:basenameaddr
cf:basenameaddr
cf:profileagesex
按访问相关性切分：常一起读的列放同簇
真正的「行列混合」
这是列簇式存储最有价值的状态：把关联性强、常一起访问的列归到一个列簇，不同访问模式的数据落进不同 StoreFile。既能整簇连续读，也能避开无关列簇的 IO。
设计含义：列簇划分不是命名习惯，而是 IO 边界的决策。原文也提到另一个行列混存代表 zedstore。
PHYSICAL · 每列 1 个 HStore → 每列 1 组 HFile
cf:namename
cf:addraddr
cf:ageage
cf:sexsex
≈ 列式存储
每个列簇只含一列，只查少数列时连续读出目标列即可，同列同类型还带来高压缩与 CPU 批量计算能力。
代价：取一整行需要多次 IO 读多个 Store 再合并；且 HBase 中列簇过多会放大 memstore / flush / compaction 的管理成本。
行式存储
取一行高效；只查指定列会读入大量无用列
列式存储
查少数列高效、易压缩、可用批量指令；取一行需多次 IO
列簇式
两者之间，靠列簇数量在行存与列存之间连续滑动

04 · 擅长什么
STRENGTHS / 结构特点决定场景

rowkey 自己控制、有序、密集 存储

01
容量巨大
单表可支持千亿行、百万列，容量达 TB 甚至 PB 级。
02
线性扩展
加 Region Server 扩计算，加 DataNode 扩存储。
03
稀疏性
允许大量列值为空且不占任何存储空间，可上百万列。
04
多版本
一个 KV 可同时保留多个版本，按 ts 倒序读取。
05
TTL 过期
设置过期时间后自动清理，不需要业务写程序删除。
06
写与点读
主要擅长 OLTP：写性能强劲，随机单点读与小范围扫描有保障。
时序 / 物联网
一次捞取一辆车的全部轨迹、一个传感器一天的记录：rowkey 设计得一致时，这些记录密集存放在少量数据块内，读取非常高效。
与 PostgreSQL 的对照
PG heap 表下同类场景的优化思路，是把分散在多个 block 的记录聚到一起以减少 IO（覆盖索引 / 聚簇）；而 HBase 天然就是这样。大范围扫描则交给 MapReduce API 并行处理。

05 · 边界在哪
LIMITS / 三处需要外部组件补位

它不擅长的，恰好是关系型数据库的日常

能力缺口
为什么
常见补位
01
复杂聚合
HBase 本身不支持 Join、GroupBy 等复杂聚合运算。
小规模 OLTP 聚合用 Phoenix；大规模 OLAP 聚合用 Spark。
02
二级索引
原生没有实现二级索引，因此不支持二级索引查找；只能靠 rowkey 与扫描。
用 Phoenix 提供的二级索引，或由其他组件异步构建。
03
跨行事务
原生不支持全局跨行事务，只有单行事务模型。
用 Phoenix 的全局事务模型组件弥补。
据此判断「不适合」：以多表 Join、任意条件组合查询、跨行强一致事务为主的业务，不该把 HBase 当主存储硬上；而写入密集、按 rowkey 访问、能接受最终一致与宽表模型的场景，才对得上它的结构优势。

05 · 边界在哪
EXTENSION / 原文的扩展问题

rowkey 不是主键，是存储布局本身

01
贴合业务 / 组合设计
容易按业务需求构造 rowkey；把查询频率高的条件组合成 rowkey 或其前缀。
02
唯一性
每行 rowkey 建议唯一。同一行应包含该 rowkey 下所有列簇、限定符、type 与全部版本。
03
散列，避开热点
HStore 内 rowkey 按字典序存储；有序（如时间戳）会让一个时间窗全写进同一 region / 同一 RS。
04
长度越短越好
满足业务需求的前提下尽量短，节省空间 —— rowkey 会随每个 cell 重复存储。
热点示意 · 顺序 rowkey vs 散列 rowkey
时间戳前缀（顺序）
同一时间窗集中写入 → 单 RS 瓶颈
散列前缀（打散）
写入分散到多个 region → 吞吐上来
digoal · 2024-11-07
代价：散列会牺牲按时间前缀的范围扫描，需按查询权衡
