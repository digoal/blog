01一、索引原理 / 背景WHY ANN

为什么要一张「图」？精确检索撑不住高维

RAG / 语义搜索把文本变成几百到几千维的浮点向量。要找最相近的 K 条，精确 KNN 必须与每一条向量算距离 —— 数据量一大，这条路就走不通了。

01 / 困境

精确 KNN

与全表每条向量算一次距离。召回率 100%，代价是 O(N · d) 的时间和 I/O。

02 / 失效

高维没有全序

一维排序无法保持高维邻近性，B-tree 类结构失效。要换一种组织数据的方式：用邻接关系表达「谁跟谁近」。

03 / 出路

ANN：以图换速

把向量变成节点、把相近关系变成边。搜索变成在图上「走路」，而不是把表扫一遍。

本文的分析入口

以 pgvector 的 hnsw 索引接口为例：它支持并行构建、动态维护与灵活参数配置，能在查询性能与结果质量（召回率）之间取得平衡。

时间复杂度
O(log N)搜索　逐层下降，每层只做局部贪心
O(M log N)插入　M 为连接数
O(N M log N)构建　相当于 N 次插入
空间复杂度
O(N M)底层规模　节点会出现在多个图层，实际占用更大；构建时需足够内存容纳整张图。

16八、DEMO / 一条可复制的完整链路SQL

从建扩展，到带过滤的向量查询

原文示例 · 9 步
-- 1 创建扩展
CREATE EXTENSION vector;
-- 2 建表（384 维）
CREATE TABLE documents (
  id SERIAL PRIMARY KEY, title TEXT,
  content TEXT, embedding vector(384),
  category_id INTEGER,
  created_at TIMESTAMP DEFAULT NOW());
-- 3 插入 1 万条测试数据
INSERT INTO documents
  (title, content, embedding, category_id)
SELECT 'Document ' || i,
  'Content for document ' || i,
  ARRAY(SELECT random()
    FROM generate_series(1,384))::vector(384),
  (i % 10) + 1
FROM generate_series(1, 10000) i;
-- 4 内存与并行参数
SET maintenance_work_mem = '2GB';
SET max_parallel_maintenance_workers = 4;
-- 5 创建 HNSW 索引
CREATE INDEX CONCURRENTLY idx_documents_embedding
ON documents USING hnsw
  (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
-- 6 为过滤列建索引
CREATE INDEX idx_documents_category
  ON documents (category_id);
-- 7 查询参数
SET hnsw.ef_search = 100;
SET hnsw.iterative_scan = relaxed_order;
-- 8 带过滤的向量相似性查询
SELECT id, title,
  embedding <=> '[0.1, 0.2, ...]' AS distance
FROM documents
WHERE category_id = 5
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 10;
-- 9 监控查询性能
EXPLAIN ANALYZE
SELECT id, title FROM documents
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 5;
要点：ORDER BY + LIMIT 才会走索引；CONCURRENTLY 避免阻塞写入；ef_search / iterative_scan 是会话级可调参数。
