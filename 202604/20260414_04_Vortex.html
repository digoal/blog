02 PARQUET 的痛点 / BLOCK-COMPRESSED

先解压，再过滤：代价与命中行数无关

01

定位到目标 Page

通过 column index / bloom filter 找到页

这一步本身很快，Parquet 的元数据设计并不弱。
02

解压整个 Page

Snappy / GZIP 整页还原

整页粒度的固定开销：即使最终只命中 1 行，也要把整页还原出来。这是设计约束，不是实现缺陷。
03

解码数据

还原为引擎可处理的内存表示

解码后的数据还要占内存带宽，宽表尤其明显。
04

执行过滤、聚合

此时才知道哪些行真正需要

过滤发生在最后：CPU 已经为大量最终被丢弃的数据付过解压与解码的代价。
+ 悬停任一步骤 · 查看这一步的代价
「想在快递箱里找一把钥匙，必须先把整箱胶带撕开、解压、再翻找。」
Parquet 是 Google Dremel 的开源实现，也是大数据生态的事实标准。它的局限与生俱来：Page 内使用块压缩，引擎必须先解压 Page 才能做过滤、解码等操作。

DuckDB 官方博客在介绍 Vortex 时，也把这一点列为 Parquet 最典型的设计约束。
定位→解压整页→解码→过滤

04 黑科技之一 / LIGHTWEIGHT ENCODINGS

编码布局已知，计算就能不解压直接做

Vortex 为不同数据类型选择不同编码；每个编码都可以特化自己的计算函数，让过滤在编码域完成。

01 / FLOATING POINT

ALP

Adaptive Lossless Floating-Point

面向浮点数列。缩放为整数后可直接在编码域做比较、聚合，兼顾无损与有损模式。

+ 悬停 · 实现细节
按指数把浮点缩放成整数再做 bit-packing；异常值由 Patches 单独记录。比较与聚合在整数编码域即可完成。
02 / STRINGS

FSST

Fast Static Symbol Table

面向字符串列。从样本学习高频字节符号表，类似字典编码但更紧凑、更高效。

+ 悬停 · 实现细节
仿射兼容的符号表编码。过滤可先作用于很小的符号表（类似先过滤字典），命中后再处理原串，避免全量解压。
03 / INTEGERS

FastLanes

Bit-Packed Integers

面向整数列。针对顺序与随机整数的高效位打包编码，高度数据并行。

+ 悬停 · 实现细节
起源于 CWI（与 DuckDB 同源），是延迟物化的主要驱动力之一；向量化解码友好，也让数据能高效拷贝到 GPU。
共同点：编码布局是文件自描述的一部分，因此计算函数能直接在压缩数据上运行。Vortex 还支持动态加载第三方编码，甚至把 WebAssembly 解码器写进文件。　来源：DuckDB 官方博客 2026-01-23 / Vortex 仓库

01 / DISK

+ 实现细节

+ 实现细节

目标：从对象存储直送加速卡

+ 实现细节

04 / VRAM

写入 GPU 显存

压缩态直接落地，不经过 CPU 中转

+ 实现细节
少一次 CPU–GPU 搬运，是 ML 管道最贵的一段。
05 / DECODE

原位解压

在 GPU 上就地解码

+ 实现细节
解压延迟到进入 CPU / GPU 的那一刻。
06 / COMPUTE

进入计算

此刻才物化为可用值

+ 实现细节

1.4.2 LTS 起成为核心扩展

由 SpiralDB 团队构建，DuckLabs 合作纳入核心扩展。

这意味着安装体验、版本管理与 Parquet 等内置格式一致，而非社区实验插件。

写入：自动选编码

按列的数据特征选择 ALP / FSST / FastLanes 等编码。

压缩策略基于采样与统计信息，编码可级联；上层不需要感知物理布局。

读取：自动下推过滤

过滤表达式在压缩域执行，只还原命中行。

这就是为什么带 WHERE 的点查最能体现差异；纯全表扫描的差距会小得多。

09 场景判断 / WHEN TO USE

该用，与不该用

✓ 适合 VORTEX

+

交互式分析 / 即席查询

随机访问快、延迟低；过滤下推减少 I/O 与内存消耗，冷启动表现更一致。
+

ML 训练数据准备

多种编码覆盖音频、文本、图像、向量等模态；目标是把压缩数据高效送进 GPU。
+

实时数仓 / 批流一体

统一 API 同时支持批与流，写入性能好；注意生态与事务语义仍需上层表格式补齐。
+

数据湖冷热分离

与 Arrow 零拷贝互通，避免序列化开销，跨引擎交换数据更便宜。
+

高频随机点查

最能放大轻量编码优势的场景；但 100× 级别属项目方基准，需按自有数据形状复核。

✕ 暂不适合 VORTEX

+

强类型嵌套数据

Vortex 的嵌套 Layout 支持仍在演进，成熟度暂不如 Parquet。
+

已有成熟 Parquet 生态

Parquet 几乎被所有引擎读取；迁移收益不明确时，保持现状更稳。
+

追求极致压缩率

Vortex 偏向计算效率，压缩率略逊于 zstd-Parquet；存储成本优先时需重新算账。
+

强依赖 Hive / Presto

这些引擎尚未支持 Vortex；先确认查询引擎与 catalog 能否读取，再谈迁移。
+

需要 ACID / 时间旅行

Vortex 是文件格式而非表格式；事务、快照与 catalog 仍需 Iceberg / Delta / Hudi 这一类上层语义。
判断顺序：查询特征（OLAP / 点查）→ 介质是否支持随机访问 → 计算效率与压缩率谁优先。　+ 悬停任一行查看判断依据

11 边界 / ASSUMPTIONS & LIMITS

结论成立，是有前提的

下面三条前提任一不成立，或右侧任一条件命中，都请回到自己的负载重新评估。

三个前提 / PRECONDITIONS
01

查询是分析型（OLAP）

而非高频单行点查的事务负载

Vortex 优化的是扫描 + 过滤下推 + 批量解码；单行事务写入不是它的目标场景。
02

介质支持随机访问

本地 SSD、对象存储等

随机访问优势依赖按 Chunk 定位的能力；纯顺序流式的介质会抹平差异。
03

计算效率 > 极致压缩

愿意用少量空间换时间与稳定性

TPC-H 实测体积多约 12%；若存储预算是硬约束，收益需要重新计算。
重新评估 / RECONSIDER WHEN
A

数据写入远多于读取

→ LSM Tree 系：RockDB、PolarDB XEngine

写多读少时，列式编码带来的读取收益无法摊薄写入与合并成本。
B

需要强一致性事务写入

→ PostgreSQL / PolarDB 原生表

文件格式本身不提供事务、快照与 catalog；那是表格式与数据库的职责。
C

已有成熟 Parquet 管道

→ 迁移收益不明确时不动

先用同一份数据做 A/B；生态兼容成本往往比查询耗时更决定成败。

12 动手验证 / VALIDATE ON YOUR DATA

5 步，用你自己的数据做决定

对比典型查询耗时

点查 / 高选择性过滤最能放大差异；纯全表扫描的差距通常小得多。每查询多次运行并关闭连接，抑制缓存影响。

对比存储体积

达到阈值再考虑迁移

随机访问耗时 Vortex < Parquet 的 1/10
