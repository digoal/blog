01 / 药引子

为什么 Parquet 们不够用了？

过去十年，Parquet 凭出色的压缩率和分析性能成为数据湖事实标准。大模型时代，一个新的痛点正在爆发：随机访问。

训练现场
从数亿张图片中
随机抽样 1 万张
做小批次训练
顺序扫描 ✓ 擅长 随机读 ✗ 痛点
每次读一条记录，都要重新走一遍「定位 → 解压」的流程。
Parquet 的一次随机读，要经历三步
STEP 01
读文件末尾元数据
先知道数据在哪
→
STEP 02

粗粒度分区
→
STEP 03
解压对应 Page
为一行，付一页
100×
随机读相比顺序扫描，性能可能下降 100 倍以上
AI 工作负载还同时要：列存压缩与向量化计算、原生向量相似搜索、ACID 与时间旅行、Schema Evolution 不重写全表。
这不是 Parquet 的缺陷——它面向批量扫描分析设计，随机读取从来不是它的目标。问题出在：AI 把访问模式换了。

02 / 反常识判断

真正值钱的不是「更好的 Parquet」，
而是「随机读和批量扫描一样快」这个组合。

AI 时代对一份列存的五个诉求
列存压缩 + 向量化计算 高速随机访问 · 100× 原生向量相似搜索 ACID + 时间旅行 Schema Evolution 不重写
Lance 的核心赌注
用更细粒度的 MiniBlock（~4KB） 替代 Parquet 的 Page（8KB–1MB）， 让随机读一条记录只需解码极少数块，而批量扫描仍保持接近 Parquet 的吞吐量。
代价是压缩率与元数据开销；收益是把「点查」从批处理的副作用，变成一等公民。

06 / 全篇核心

一条随机读，究竟要解码多少？

把鼠标移到右侧任意一格，看两侧为「取这一行」各自付出的解码范围。（默认第 42 行；这是探索，不是隐藏信息。）

Parquet · Page
8KB – 1MB
目标行所在的整个 Page 都要解压
需解码的整页真正想要的那一行
Lance · MiniBlock
~4KB
只解码目标行所在的一个块
需解码的 MiniBlock真正想要的那一行
24 : 4
示意：本次需解码的单元数
核心原理：MiniBlock ~4KB 粒度 + 列投影裁剪 + 无需解压完整 Page 即定位目标行。
代价：每个 MiniBlock 需要独立元信息，元数据开销略高，因此 Lance 用中低压缩率换随机读性能（该判断的 2026 年更新见 P19）。

07 / 编码

编码没有发明新东西，取舍才是新东西

Lance 借鉴了列存的成熟编码技术，但每一处选择都偏向「解压快」而非「压得小」。

设计哲学：Parquet 追求高压缩率，Lance 更倾向于「解压开销最小化」。 为什么？ 随机读一条记录后往往立即喂给 GPU/CPU，解压延迟直接影响端到端 throughput。

08 / 向量检索

把 ANN 索引放进格式内部

向量索引的核心三要素，Lance 均有对应实现——索引不是外挂系统，而是同一套存储里的一类文件。

01 · 聚类
IVF
k-means 划分向量空间，搜索时只扫描相关聚类
降低搜索计算量
02 · 子索引
FLAT / HNSW
FLAT 精确无近似；HNSW 分层图，O(log N) 高召回低延迟
决定召回与延迟
03 · 量化
PQ / SQ / RQ
分段量化 / 标量量化 / 随机旋转二元量化
决定内存与压缩
常用组合
IVF_PQIVF_HNSW_SQIVF_SQ IVF_RQIVF_FLAT
索引存哪儿
向量索引本身作为普通 Lance 文件存在 _indices/，在 Manifest 中被引用——索引与表数据天然一体化管理，跟着版本走。

10 / 演化

加一列，要不要重写整张表？

这是 AI 训练管线里的高频动作：embedding 重算、新增特征、派生字段。

传统路径 · 全表重写
ABC+D
rewrite all files
新列与既有列的物理布局耦合 → 重写 / 回填，成本随数据量线性增长
Lance 路径 · 追加
ABC+D
append DataFile only
Fragment 独立加列 → 只写新列数据，旧 Fragment 原封不动
工程基础
Fragment 是水平分区单元，每个 Fragment 只包含部分行与部分列——不是所有列都存在每个 Fragment 里。 这条结构性质同时带来两个收益：随机读的列投影成本更低，以及新增列可以就地追加。

14 / 选型

把优点和代价摆在同一页上

优势

它强在哪

  • 随机读比 Parquet 快 100×，批量扫描吞吐仍接近 Parquet
  • 原生向量索引（IVF / HNSW / PQ / SQ / RQ），无需独立向量库即可 ANN
  • ACID 事务 + 时间旅行，版本管理原生内置
  • Schema Evolution 高效，加列不重写全表
  • Rust 实现；Arrow 生态零拷贝，无序列化开销
适合场景

什么时候该考虑它

  • AI 训练数据管理（随机采样、增量写入）
  • 多模态 RAG（向量 + 文本 + 图片统一存储）
  • 向量数据库场景，同时想要结构化数据与事务能力
  • 数据湖中随机读取比 Parquet 更吃紧的部分
  • 需要频繁 Schema Evolution 的 ETL pipeline
劣势 †

要付什么代价

  • 压缩率不如 Parquet（细粒度 MiniBlock + 更轻量压缩的取舍）†
  • 生态相比 Parquet 年轻，应用工具链还在成熟中
  • 缺少 Iceberg / Delta Lake 那样成熟的表格式治理体系
  • 面向磁盘随机访问优化；纯内存场景 Arrow 仍是首选
不适合场景

什么时候别用它

  • 极致压缩率优先的冷存储（Parquet / ORC 更合适）†
  • 已有成熟 Iceberg / Delta Lake 治理体系，迁移成本划不来
  • 小文件高频写入，细粒度 MiniBlock 未必有优势

16 / 追问

三个最常被追问的问题

结论直接写在卡片上；悬停可看完整推导。

Q1
MiniBlock 与 Parquet Page
核心差异在哪？
粒度。Page 是 8KB–1MB 的粗粒度解码单元，MiniBlock 是 ~4KB。随机读一行，前者要解压整页，后者只解码极少数块。
代价：元数据开销更高 → 用压缩率换点查性能。
悬停看完整推导 →
Q2
Lance 的向量索引
和 pgvector 的 HNSW？
算法无本质差异，归属不同。pgvector 是 PG 内置索引、随表管理，擅长 SQL 联表；Lance 是独立索引文件、与表数据同格式管理，适合非 PG 环境。
区别在「索引归谁管」，不在「用什么算法」。
悬停看完整推导 →
Q3
Lance vs
Delta Lake / Iceberg？
不在同一层级。Iceberg / Delta 是「表格式」，管理一群 Parquet 文件；Lance 是「存储格式」本身，且把版本语义内嵌进来。
Iceberg 管理 Parquet，Lance 自己就是格式 + 版本管理。
