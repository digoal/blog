列存之 ORC

不是把数据按列放起来，
而是把类型、编码、压缩、统计与跳读，
一起固化进文件格式。

digoal2026 / 04 / 16PostgreSQL · DuckDB · 列存
01先说结论

ORC 的价值，不在「按列放」，
而在把五个能力写进文件

普通列存解决「只读需要的列」；ORC 进一步解决下面这些：

01 / PROJECTION只读需要的列按列切分的 streams
02 / SKIP只读可能命中的 stripemin / max 统计
03 / ENCODING按类型选择编码不做二进制 blob
04 / SELF-DESCRIBING文件自描述降低外部元数据依赖
05 / ECOSYSTEM生态里高效流转Hive · Spark · Trino
一句话：ORC 是面向大规模分析扫描的「带类型语义、带索引统计、带压缩编码策略」的列式文件格式。　适合 OLAP、数据湖、归档分析、批量扫描；不适合高频单行 OLTP 与随机小事务。
02药引子 · 为什么只有行存不够

「查出来」三个字，成本完全不同

一张 200 字段的日志表，查询只关心 4 列
SELECT app_id, count(*), avg(latency)
FROM logs
WHERE log_time >= now() - interval '1 day'
  AND status = 500
GROUP BY app_id;

行存的天然问题：一行里的 200 个字段往往一起被读进来。即使查询只需要 4 个字段，也可能被迫搬运大量无关数据。

200行内字段
4查询真正需要
≈50×粗略读取放大

ORC 沿着这个方向做得比较彻底：列裁剪、统计信息、谓词下推、编码压缩、批量向量化读取，组合起来才是价值。

列存的第一性原理：查询只需要哪些列，就只读取哪些列；过滤能在存储层提前判断，就不要把无关数据搬到计算层。
行存：整行搬运　·　列存：只读 4 个投影列忽略元数据与压缩差异，仅示意「读了多少」
03第一性原理

少读，比算得快更重要

「查询只需要哪些列，就只读取哪些列；
过滤能在存储层提前判断，就不要把无关数据搬到计算层。」

ORC 的加速不是玄学，落到机制就是这条链路。数据写入顺序决定了这条链路的起点是否有效。
04ORC 是什么

Optimized Row Columnar

Apache 生态里的列式文件格式，最早来自 Hive 场景。目标不是替代数据库表，而是在 Hadoop / 数据湖 / 大数据分析生态中，高效存储和扫描结构化数据。

ORC 文件是 self-describing 的：类型、编码、统计信息都在文件内，不完全依赖 Hive Metastore 才能解释内容。
类型语义 → 编码策略 → 压缩块
　　→ stripe / row group 统计 → 谓词下推
　　→ 少读 IO → 少解压 → 少计算

真正要理解 ORC，不要只记「列存」，要记住这条链路。

  • 01保留表定义里的类型信息不像早期 RCFile 那样把列当二进制 blob
  • 02使用类型相关编码dictionary / bit packing / delta / RLE
  • 03轻量编码之上叠加通用压缩zlib / Snappy / LZO / LZ4 / ZSTD
  • 04支持列投影只读当前查询需要的列
  • 05内置轻量索引与 min/max 统计用于跳过无关 row group / stripe
05ORC 文件结构

Header、Body、Tail 三段

悬停图中带 + 的区块，查看该段的内容与作用Tail 在末尾，是为了 write-once 写入模型
FOOTER / 目录stripes 列表 · 总行数
FOOTER / 语义schema 类型树 · writer
FOOTER / 统计文件级列统计 · rowIndexStride
读取前提先判断要不要读，再决定读哪里
整个 Tail 的设计都指向同一件事：把「要不要读」的判断成本，压到只读几个字节的元数据。这也是后面 stripe 统计与谓词下推能成立的前提。
06反向读取路径

先判断要不要读，再决定读哪里

写完主体数据，再把整体元数据写到文件尾部——这是 ORC 能做「跳读」的基础。

Footer 让 reader 在不解压任何数据页的前提下，就完成「哪些 stripe 值得读」的判断。
07Stripe

大块组织单位 + 元数据索引

每个 stripe 相对独立，适合大规模并行扫描行不会跨 stripe 边界
  • 01查询只需要某些列时，只读这些列对应的 streams
  • 02带过滤条件时，先看 stripe / row group 统计信息
  • 03不命中的 stripe 或 row group 直接跳过
  • 04每个 stripe 相对独立，适合大规模并行扫描
它不是 B-tree 那种精准定位索引，而是 OLAP 里更常用的 metascan / skip scan：用便宜的元数据过滤掉大量不可能命中的数据块。

与「存储级、块级、batch 级过滤与数据编排」的思路一致：不一定给所有列建重索引，但可以用块级统计减少扫描量。

08三级索引

嵌在文件里的统计与位置元数据

不是传统数据库的二级索引，而是统计 + 位置。

层级粒度作用
file level整个文件判断整个文件是否可能命中
stripe level每个 stripe判断某个 stripe 是否需要读
row levelstripe 内每 10,000 行进一步跳过 row group

列统计通常包含

value counthasNullmin / maxnumeric sum bloom filter（Hive 1.2+）
过滤条件 → SARG / Search Argument → 对比统计信息 → 跳过文件 / stripe / row group → 减少 IO 与解压
例：WHERE log_time ≥ '2026-04-01' AND log_time < '2026-04-02'。若某 stripe 的 max(log_time) 都小于下界，这个 stripe 就没有读取价值——判断只读元数据。
09跳读判定 · 互动实验

数据写入顺序，就是一种隐形索引

WHERE log_time >= '2026-04-01' AND log_time < '2026-04-02'　-- 同一条过滤条件，两组数据分布
判定只发生在元数据上：max(log_time) < 下界 或 min(log_time) ≥ 上界 → 跳过整个 stripe；区间相交 → 读取，再交给 row group 级统计继续缩小范围。
全程不需要解压任何数据页——这正是「少读 IO → 少解压 → 少计算」的第一步。
10编码与压缩 · 轻量编码

不是把一列值连续写到磁盘

ORC 根据类型和数据分布选择编码，先把值域压小，再谈通用压缩。

编码适合数据价值
Dictionary encoding低基数字符串、枚举值用字典 ID 替代重复字符串
Bit packing小范围整数用更少 bit 表示一个值
Delta encoding单调递增 / 递减序列存差值而不是存完整值
Run length encoding连续重复值存值 + 重复次数
Varint / ZigZag小整数、有符号整数减少整数编码空间
轻量编码之上，ORC 还能叠加通用压缩：NONE / ZLIB / SNAPPY / LZO / LZ4 / ZSTD。两层叠加，才是文件变小的完整原因。
11编码与压缩 · 通用压缩

不是「压缩率越高越好」

要看查询路径：你是在全表批量扫，还是经常小范围过滤、交互式查询、随机抽样？

CompressionKind（ORCv1 枚举，共 6 项）
NONE = 0 ZLIB = 1SNAPPY = 2LZO = 3LZ4 = 4ZSTD = 5 默认压缩块 256K

一个必须看清的工程取舍

块更大

压缩率通常更好
但随机跳读和解压开销可能更高

块更小

过滤和随机读取更灵活
但元数据和压缩率可能受影响

判据

省下的 IO 是否大于
多花的解压 CPU

压缩块 ← 小：过滤灵活 / 元数据多　━━━━━━━━━━━━　大：压缩率高 / 解压重 → 压缩块
工程结论：压缩块大小本质是「IO 节省」与「解压粒度」的权衡。官方把默认 256K 写进 Postscript，reader 据此分配缓冲区——连解压要预留多少内存都被显式记录在文件里。
12类型系统

格式知道类型，统计才可信

ORC 支持的标量 + 复合类型
booleantinyint / smallintint / bigintfloat / double string / char / varcharbinarydecimal timestamptimestamp with local time zonedate structlistmapunion
类型树 → writer 按类型选编码　·　reader 按类型解释统计
类型树 → 谓词下推用同一套比较语义　·　嵌套子字段裁剪
timestamp 不是一个简单字符串。官方区分不带时区 timestamp 与 timestamp with local time zone；跨时区分析把时间语义搞错，压缩和扫描再快也没用，因为结果不可信。

如果格式只把列当 bytes

  • 01很难做正确的 min/max、sum统计失去可比性
  • 02谓词下推无从判断无法安全排除数据块
  • 03时间语义与 decimal 精度会出错结果可信度问题
  • 04嵌套结构无法裁剪只能整块读取

type-aware 让 writer 按类型选编码，也让 reader 按类型解释统计信息。

13ACID 边界

数据湖语境下的 ACID

大概机制

  • 01base file + delta files
  • 02transaction list + row id
  • 03compaction 合并
适合：数据湖里批量写入、批量更新、分钟级流式提交、查询看到事务一致性。
不适合：订单系统、账户余额、库存扣减这类高频单行 OLTP；不要因为看到 ACID 就把 ORC 当 OLTP 表存储。

官方也明确说明：它可以支持一个事务更新大量行，但不是为每小时百万级小事务设计的。

ORC 的 ACID 是数据湖 / 分析系统语境下的 ACID，不是 PostgreSQL heap + WAL + MVCC 那种高并发 OLTP 路线。
14PostgreSQL 生态

先纠正一个常见误解

cstore_fdw 官方说法是数据布局 inspired by ORC，并不是直接使用标准 ORC 文件格式——不能理解为「PostgreSQL 直接用 ORC 文件当表」。
-- postgresql.conf
shared_preload_libraries = 'cstore_fdw'

CREATE EXTENSION cstore_fdw;
CREATE SERVER cstore_server
  FOREIGN DATA WRAPPER cstore_fdw;

CREATE FOREIGN TABLE customer_reviews (
  customer_id text, review_date date,
  review_rating integer, product_id text,
  product_title text
) SERVER cstore_server
OPTIONS (
  compression 'pglz',
  stripe_row_count '150000',
  block_row_count '10000');

COPY customer_reviews FROM '/data/...csv' WITH CSV;
ANALYZE customer_reviews;
参数含义 / 取舍
filename数据文件位置
compressionnone / pglz
stripe_row_count默认 150000 行
block_row_count默认 10000 行

价值：列投影、压缩、skip indexes（row group / block 的 min/max）、使用 PostgreSQL FDW API 与类型表示、支持 optimizer 统计信息。

限制：支持 COPY 与 INSERT INTO … SELECT；不支持 DELETE、UPDATE、单行 insert。官方 README 已提示现代化列存能力进入 Citus columnar table access method。

学习 ORC 思想可以看它；生产新系统更应评估 Citus columnar、DuckDB / Parquet / ORC、Greenplum AOCO 或数据湖表格式。

正确问题是这 7 个

01我的数据类型是什么？
02过滤列是否有局部相关性？
03全表扫描还是选择性过滤？

离开这些条件谈性能，基本都是口水仗。
16适用边界

边界比结论更值钱

适合 · 批量扫描与过滤下推

  • ✓Hive / Spark / Trino 等大数据分析生态支持成熟
  • ✓大宽表，只查少量列列裁剪收益明显
  • ✓时间序列日志、行为数据、账单流水按时间写入，min/max 跳读有效
  • ✓冷热分层、归档分析压缩和批量扫描友好
  • ✓数据湖批处理文件格式开放，可跨引擎读取

不适合 · 点查与高频更新

  • ×高频 OLTP文件格式不是事务数据库存储引擎
  • ×单行高频更新 / 删除write-once + delta / compaction 模型不合适
  • ×小文件高频写入元数据和调度成本会放大
  • ×过滤列分布随机min/max 跳读收益差
  • ×低延迟点查B-tree / LSM / 主键索引路线更合适
两栏其实只由两个变量决定：负载是批量扫描还是单行点查，以及过滤列是否具有局部相关性。前者决定该不该用列存格式，后者决定列存的跳读能力能不能真正兑现。

18选型建议

ORC 通常不是主表存储，而是分析链路的一环

OLTPPostgreSQL / PolarDB
→
管道CDC / ETL
→
存储数据湖 ORC / Parquet
→
计算Spark / Trino / DuckDB / Presto
→
消费报表 / 训练 / 归档 / 审计

想在 PostgreSQL 内部体验列存

  • 01学习历史机制：看 cstore_fdw
  • 02新项目列存表：优先看 Citus columnar access method
  • 03本地分析：DuckDB 读 ORC / Parquet 很方便
  • 04大规模湖仓：结合 Iceberg / Delta / Hudi 表格式

真正的判断标准，是这 6 个问题

数据如何写入？
查询如何过滤？
哪些列被投影？
哪些统计能跳读？
压缩省的 IO 是否大于解压 CPU？
引擎能否把谓词下推到 reader？
不是「这个格式先进不先进」，而是把这几个问题答清楚——ORC 的价值就很清楚了。
19小结

把列存的底层变量串起来

01 / IO列裁剪减少无关 IO
02 / TYPE类型语义支持正确编码和统计
03 / SKIPstripe / row group 统计支持 skip scan
04 / SIZE编码 + 压缩降低存储和传输成本
05 / TAILFooter / Postscript 让文件自描述、可跳读
06 / ACIDACID 服务于数据湖批量变更，而非 OLTP

对 OLAP 来说，性能常常不是来自「算得更快」，
而是来自「根本不读、不解压、不计算
那些不可能命中的数据」。

这也是列存、BRIN、cstore_fdw skip index、Parquet row group、ORC stripe 背后共同的第一性原理。学 ORC 的重点不是背格式字段，而是理解这个生产判断。
