01 / 药引子

只记住这行 DDL，基本等于没学会

大多数人记住的「列存」

WITH (
  appendoptimized = true,
  orientation     = column
)
DISTRIBUTED BY (order_id);
真正影响生产效果的不是语法，而是这条链路：
01 批量写入 → 02 按列落盘 → 03 每列独立压缩/编码
04 只读查询需要的列 → 05 visimap 处理删除可见性
06 vacuum / compaction 回收空间 → 07 gp_toolkit 验证效果

本文要回答的五个「为什么」

  • 为什么适合数仓大宽表？
  • 为什么不适合高频小事务？
  • 为什么 delete / update 后空间不立刻回来？
  • 为什么建索引后会多出 block directory？
  • 为什么 blocksize 不是越大越好？
视角把 AOCO 当成一个数据库内核存储模型：IO 路径、压缩编码、MVCC 元数据、垃圾回收与查询形态，是一整套互相牵制的取舍。
02 / 全景

七步链路，才是生产效果的决定因素

悬停任一步 → 底部深挖层给出它的机制与源码/工具落点。核心结论默认就在页面上。
01
批量写入
COPY / 批量 INSERT，而非单行高频插入
02
按列落盘
一行拆成每列一个 datum stream
03
列级压缩/编码
同类型、低基数、有序值更易压
04
只读需要的列
extract columns 决定打开哪些列流
05
visimap 可见性
删除不原地改，只标记不可见
06
vacuum / compaction
把 live tuple 搬进新 segment file
07
gp_toolkit 验证
压缩比、hidden tuple、段状态
主结论语法只是入口；写入 → 落盘 → 压缩 → 裁剪 → 可见性 → 回收 → 观测，任意一环没设计好，列存都不会自动变快。
03 / 结论先行
「核心价值不是『列存』两个字，而是把 MPP 数仓里的大表扫描成本，
从按行搬运，改成按列、按块、按压缩单元搬运。」

适合 · 用 AOCO

  • 明细事实表、日志表、事件表、宽表、历史流水表
  • 批量导入、批量追加，少量更新删除
  • 查询只访问少数列，或对少数列聚合
  • 列值局部重复、有序、低基数，适合压缩
  • 分区表，按时间 / 租户 / 业务域做冷热分层

不适合 · 别优先 AOCO

  • 高频单行 INSERT
  • 高频 UPDATE / DELETE
  • 大量点查、强随机访问
  • 每次都读绝大多数字段的小窄表
  • 低延迟 OLTP 事务表
一句话AOCO 是给 OLAP 大表准备的「列式段文件 + MVCC 元数据层 + 压缩编码 + 辅助目录」方案，不是 OLTP heap 的平替。
04 / 第一性原理

查询只要 5 列，为什么要搬 10 列？

订单明细宽表 · 10 列

SELECT tenant_id, category_id, sum(pay_amount)
FROM dwd_order_detail
WHERE order_time >= date '2026-04-01'
  AND order_time <  date '2026-04-02'
  AND status = 1
GROUP BY tenant_id, category_id;
行存的问题：即使只需要 5 列，也容易把同一行里的大量无关字段一起搬进 IO、解压、CPU cache、executor。
两层代价削减MPP 分布：多 segment 并行扫　＋　AOCO 列存：每个 segment 内只扫需要的列
当前：行存 · 整行搬运（10 / 10 列）
tenant_id
category_id
pay_amount
order_time
status
order_id
user_id
province
sku_id
ext_json
本次查询需要的 5 列无关字段悬停任一列查看说明
列存第一性原理：
查询只需要哪些列，存储层就尽量只搬运哪些列；列值类型相同、分布相近，就给压缩和编码创造条件。
05 / 创建表

Greenplum 7 的两种常见写法

传统 storage option

CREATE TABLE fact_sales (
  sale_id    bigint,
  sale_time  timestamp,
  shop_id    int,
  amount     numeric(18,2),
  status     int
)
WITH (
  appendoptimized = true,
  orientation     = column
)
DISTRIBUTED BY (sale_id);
列式存储必须是 append-optimized 表；heap 只能是行式。

Table access method

CREATE TABLE fact_sales (
  sale_id    bigint,
  sale_time  timestamp,
  shop_id    int,
  amount     numeric(18,2),
  status     int
)
USING ao_column
DISTRIBUTED BY (sale_id);
\d+ 中显示 Access method: ao_column；可用 ALTER TABLE ... SET ACCESS METHOD 切换。
别被名字骗了appendoptimized 是 legacy appendonly 的 thin alias，catalog 仍按 appendonly 记录和展示；看到 appendonly=true 不要误解为「不能 update/delete」。
06 / 列级压缩

不是「全表一个算法打天下」，而是按列看

压缩类型适合场景级别 / 备注
zstd通用压缩，压缩率与速度平衡1–19
zlib通用压缩，兼容性好1–9
RLE_TYPE连续重复值、排序后低变化列列级 1–6，AOCO 特有
none已压缩数据 / 不值得压的列省 CPU
列级 ENCODING 可指定 compresstype / compresslevel / blocksize；与 WITH 冲突时以 ENCODING 为准。
  • 时间列按时间写入 → delta / RLE 类思路更易受益
  • 状态、枚举、租户、类别等低基数字段 → 测试 RLE_TYPE
  • 大 text / json 重复度不高 → 更像通用压缩问题，测 zstd / zlib

按列编码的示例

CREATE TABLE fact_event (
  event_id    bigint,
  event_time  timestamp
    ENCODING (compresstype=zstd, compresslevel=3),
  tenant_id   int
    ENCODING (compresstype=rle_type, compresslevel=5),
  event_type  int
    ENCODING (compresstype=rle_type, compresslevel=5),
  payload     text
    ENCODING (compresstype=zstd, compresslevel=1)
)
WITH (appendoptimized=true, orientation=column)
DISTRIBUTED BY (event_id);
低基数列用 RLE，大文本用低级别 zstd —— 压缩决策跟着列值分布走。
07 / 生产目标
压缩率不是唯一目标。
scan latency、CPU、内存、并发才是生产目标。
8192 – 2097152blocksize 字节范围
× 8192必须是 8192 的倍数
32768默认值
partition × columnbuffer 维护粒度

大 block 的两面

  • 大 block 通常有利于压缩率
  • 但会占更多内存：block size 决定存储层缓冲
  • Greenplum 对列存表按 partition、按 column 维护 buffer
  • 「分区很多 + 列很多 + blocksize 很大」会把内存压力放大

调优时同时盯住四个量

A压缩率 / 磁盘尺寸 —— 只是一个因素
B压缩与解压的 CPU 开销 —— segment 要有余量
C扫描延迟 —— 压缩越好，随机访问越难
D并发下的内存 —— 分区数 × 列数 × blocksize
官方建议：在你的硬件与查询形态上做对比测试，不要照搬别人的级别。
08 / 物理模型

一张 AOCO 表，背后是一组辅助表 + 每列的段文件

用户表 rel
├── pg_appendonly 记录 AO 辅助表 OID
├── pg_aoseg.pg_aoseg_xxx segment file 元数据
├── pg_aoseg.pg_aovisimap_xxx 删除/更新可见性覆盖层
├── pg_aoseg.pg_aoblkdir_xxx block directory，随机定位
└── data files 每列、每 segment 的物理数据文件
源码要点：用户视角可 update / delete；物理 segment files 是 append-only，不做 in-place overwrite；AOCS 与 AO row 相似，但额外需要跟踪「哪个 segment file 对应哪个 column」。
钥匙「为什么 delete 后空间没回来」「为什么索引 scan 多一层跳转」「为什么 vacuum 会移动 tuple」——都能从这几张辅助表解释。

catalog 里的字段

CATALOG(pg_appendonly,6105,AppendOnlyRelationId)
{
    Oid   relid;
    Oid   segrelid;
    Oid   blkdirrelid;
    Oid   visimaprelid;
    int16 version;
} FormData_pg_appendonly;

-- pg_aoseg   segno, eof, tupcount,
             varblockcount, eofuncompressed,
             modcount, formatversion, state
-- pg_aovisimap  segno, firstrownum, visimap
-- pg_aoblkdir   segno, columngroupno,
             firstrownum, minipage
对应头文件：pg_appendonly.h / aosegfiles.h / aovisimap.h / aoblkdir.h

一行进来，拆成 N 个 datum stream

INPUT一行 values
›

›
aocs_insert_values逐列 put 到 ds[i]
›
datumstreamwrite_block写块 + 维护 block directory
›
AOTupleId(segfile#, row#)

源码片段 · 按列写入循环

for (i = 0; i < RelationGetNumberOfAttributes(rel); ++i)
{
    Datum datum = d[i];
    int err = datumstreamwrite_put(
                  idesc->ds[i], datum, null[i], &toFree1);
    ...
    datumstreamwrite_block(idesc->ds[i],
                  &idesc->blockDirectory, i);
}

AOTupleIdInit(aoTupleId, idesc->cur_segno,
              idesc->lastSequence);
src/backend/access/aocs/aocsam.c · aocs_insert_values()

这段代码说明三件事

  • 每列一个 datum stream：一行拆到多个列流
  • block 满了或遇到大对象时写块，同时维护 block directory
  • 每行仍需逻辑 tuple id：AOTupleId
兼容桥AOTupleId 把 (segfile#, row#) 映射成系统其它部分可当作 heap TID 处理的结构——让完全不同的物理布局接得上 PostgreSQL 执行器与索引接口。
10 / 扫描路径

列存 scan 的自然单位，是「本次查询需要的列集合」

table AM 扩展了 extract columns 入口

.scan_begin_extractcolumns =
    aoco_beginscan_extractcolumns,
.scan_begin_extractcolumns_bm =
    aoco_beginscan_extractcolumns_bm,
行存 scan 的自然单位是一行；列存 scan 的自然单位是本次查询需要的列。只有被投影或过滤需要的列，才值得打开和读取。
收益公式少读列 + 批量扫描 + 压缩友好 + MPP 并行　≠　所有查询都神奇变快

反例 · 点查 + 全列

SELECT *
FROM fact_event
WHERE event_id = 123;
  • 要读很多列，列裁剪几乎失效
  • 随机定位依赖 block directory / 索引，多一层间接访问
  • 压缩块可能要解压后才能取少量值
  • AOCO 本身不是为高频点查设计
源码注释：AO_COLUMN 表不支持 parallel SeqScan；Greenplum 的并行主要来自 MPP segments，而不是 PostgreSQL 单节点 parallel seq scan。
11 / 删除与更新

为什么 DELETE 之后，磁盘空间没有马上下降？

第一次用 AOCO 的困惑

DELETE FROM fact_event
WHERE event_time < date '2025-01-01';

-- df 一看：空间没变？

调用链

aoco_tuple_delete()
  ↳ aocs_delete()
    ↳ AppendOnlyVisimapDelete_Hide()
aocsam_handler.c · aocsam.c · appendonly_visimap*.c

答案在物理层

  • AOCO 物理文件 append-only，删除不原地改旧 block
  • 只在 visibility map 里标记 tuple 不可见
  • UPDATE = 隐藏旧 tuple + 追加写新 tuple
  • 于是产生 hidden tuples，维护要盯着它们

回归测试怎么验证

SELECT * FROM gp_toolkit.
  __gp_aovisimap_hidden_info(
    'fact_event'::regclass);
-- delete → 观察 → vacuum full → 再观察
一句话逻辑删除发生，物理回收要靠后面的 vacuum / compaction。
12 / 空间回收

不是就地清页面，而是把活着的 tuple 搬一次家

01读旧 segment file
›
02跳过 visimap 标记的 dead tuples
›
03live tuples 写入新 segment file
›
04旧 segment 标记 / 回收

为什么必须这样

物理文件不能原地删除旧 tuple，所以 vacuum 的基本模式不是 heap 那种就地清理页面。源码把它类比成 heap 的 VACUUM FULL：被移动的 tuple 会产生新的 index entries。

观察阈值

SET gp_appendonly_compaction_threshold=10;
SELECT * FROM gp_toolkit.
  __gp_aovisimap_compaction_info(
    'fact_event'::regclass);
src/test/regress/sql/uaocs_compaction/threshold.sql

四条生产建议

  • 大批量 delete 后别只看 count(*)，要看 hidden tuple 与 aoseg 状态
  • 按时间淘汰的数据，优先 DROP / TRUNCATE PARTITION，少做大范围 delete
  • 必须 delete / update 的 AOCO 表，规划 vacuum / compaction 窗口
  • delete / update 频繁的表，重新评估是否该用 heap 或 AO row
13 / 随机定位

索引要 TID，varblock 流却没有 block number + offset

LOGICALAOTupleId(segfile#, row#)
›
CATALOGpg_aoblkdir
segno / columngroupno / firstrownum / minipage
›
PHYSICALsegment file offset / minipage
›
BLOCK找到包含该 row 的 block

为什么需要它

  • AOCO 物理文件是 append-only varblock 流，不像 heap 天然有 block + offset
  • PostgreSQL / Greenplum 的索引却需要 TID 定位 tuple
  • 解决办法：用 block directory 做一层映射
  • 第一次在 AO 表上 CREATE INDEX 时才按需创建

由此带来的取舍

  • 没索引：AOCO 最自然的路径是批量顺序扫描
  • 有索引：能点到 block，但比 heap 多一层 indirection
  • 低选择率点查：AOCO + index ≠ OLTP heap + btree
源码口径顺序扫描从头到尾读 blocks；index scan 需要一份 map，找到给定 TID 所在 block 的物理 segment file 和 offset。

15 / 架构评审

不是所有大表都该 AOCO

场景推荐
小维表，频繁 update / deleteheap
大事实表，批量导入，多列一起读取AO row 或 AOCO 测试对比
大宽表，查询只扫少数列AOCO
时间序列 / 日志，按时间批量写入和聚合AOCO + 时间分区
低基数字段很多，重复值多AOCO + RLE_TYPE 测试
高频单行写入heap 或重新设计写入链路
高频 delete 历史数据分区表，用 drop / truncate partition 代替 delete
需要大量点查heap + index，或单独服务化存储
更简单一点批量写、批量读、少列读、少改动 → AOCO　　｜　　频繁小写、频繁更新、点查为主 → 不要优先 AOCO
16 / 动手验证

100 万行，把列压缩 / hidden tuple / vacuum 串起来

最小 POC

CREATE TABLE aoco_lab (
  id         bigint,
  tenant_id  int  ENCODING(compresstype=rle_type, compresslevel=5),
  event_day  date ENCODING(compresstype=rle_type, compresslevel=5),
  amount     numeric(18,2) ENCODING(compresstype=zstd, compresslevel=3),
  payload    text ENCODING(compresstype=zstd, compresslevel=1)
) WITH (appendoptimized=true, orientation=column) DISTRIBUTED BY (id);

INSERT INTO aoco_lab
SELECT i, (i%10)::int, date '2026-04-01' + ((i%30)::int),
       (random()*1000)::numeric(18,2),
       repeat('payload-',10) || (i%100)::text
FROM generate_series(1,1000000) s(i);

SELECT * FROM gp_toolkit.get_column_size('aoco_lab'::regclass);
DELETE FROM aoco_lab WHERE event_day < date '2026-04-10';
SELECT * FROM gp_toolkit.__gp_aovisimap_hidden_info('aoco_lab'::regclass);
VACUUM aoco_lab;
SELECT * FROM gp_toolkit.__gp_aovisimap_compaction_info('aoco_lab'::regclass);

四个验收点

  • tenant_id / event_day 这类重复有序字段，应比随机字段更容易压缩
  • delete 后 hidden tuple 应增加
  • vacuum / compaction 后，segment 状态与 hidden tuple 信息应变化
  • 若 SELECT * 与只查少数列差异不明显，说明没吃到列裁剪收益
实验设计意图低基数列 + 随机大文本放在同一张表里，压缩比的对比才会明显；删除 + vacuum 串起来，才能看见 MVCC 元数据层的存在。

18 / 小结

数据库选型和调优，最怕只记参数

AOCO 的本质，是在 MPP 数据库内部实现的一套列式 append-optimized 存储：
列裁剪减少 IO
列级压缩减少存储与扫描
元数据层aoseg / visimap / blkdir
把 AOCO 用在「批量追加、批量分析、少列访问、压缩友好」的表上；把频繁小事务、点查、更新删除压力留给更合适的存储模型。
带走这一句appendoptimized=true, orientation=column 只是入口；能不能用好，要看你是否理解它背后的 IO、压缩、MVCC 元数据、vacuum/compaction 和查询形态。
