01 问题 / BACKGROUND

上线之后，搜索不再是「找得到」

一开始只把全文检索理解成「能不能用索引找到包含关键词的行」；真正上线后，问题变成了下面四件事。
01
按相关度排序
不能只是过滤，要回答「谁更相关」
GIN 的 posting 里没有词位置，排名要回表取 tsvector 再算。
02
短语搜索要快
例如 postgres <-> index 相邻词匹配
短语判断依赖词位置信息，不在索引里就需要更多 recheck。
03
按业务字段排序
时间 / 价格 / 距离，别先扫出一堆候选再回表
GIN 只给 TID，排序字段必须从 heap 里逐行取出来。
04
LIMIT 20 尽快返回
只想看第一页，不想算完所有候选
候选集要先全部产生并排序，Top-N 的延迟被全集拖住。
ONE LINE
四个问题的共同点：索引不止要过滤，还得携带排序 / 排名所需的信息。

01 问题 / GIN BASELINE

GIN 很会「找到」，不擅长「排好」

GIN LOGICAL MODEL
lexeme / key
→ posting list · posting tree
→ heap TID
擅长回答：「哪些行包含这些 key」。posting 做得很轻，因此写入快、空间省。

BUT BUSINESS ASKS
这些行里谁更相关？
这些词是否相邻？
离某个时间点最近的是谁？
三个代价 / 如果索引里只有 TID
01
回表多
候选行越多，为了取 tsvector 位置、时间戳或排序字段而访问的 heap 越多。
02
Top-N 慢
即使只要前 N 条，也可能先产生大量候选再排序。
03
短语搜索弱
短语匹配依赖词位置信息，不在索引里就要更多 recheck。
执行器拿到 TID 后，还要访问 heap → 取位置 / 时间戳 → 计算排名 → 排序。
链条的每一段，都是延迟。

01 问题 / THE TRADE-OFF

把 posting 做重：换来了什么，又付了什么

得到 / 读侧
+更快的 ranking：位置信息在索引里，索引扫描后不必额外 heap scan官方 README：Faster ranking
+更快的短语搜索：短语同样需要位置信息Faster phrase search
+按 timestamp 排序：附加信息与 lexeme 一起存Faster ordering by timestamp
+depth-first search：立即返回第一批结果为 LIMIT / Top-N 服务
付出 / 写侧与空间
−索引条目更大，空间成本高于只存 TID 的倒排每个 item 多 addInfoIsNull + addInfo
−build / insert 更慢：要写入并维护附加信息官方明确说明慢于 GIN
−generic WAL records：日志成本与实现路径不同不是 GIN 的 WAL 路径
−类型限制：pass-by-reference 附加信息用于 ordering 有限制initRumState() 会拒绝该组合
BOTTOM LINE
不是「谁更先进」，而是索引组织目标不同：GIN 把 posting 做轻，RUM 把 posting 做重。

02 定义 / WHAT IT IS

它是 PostgreSQL 的一个索引 AM 扩展

可以理解为「带 additional information 的倒排索引」，不是一个独立的全文检索引擎。

ambulkdelete   = rumbulkdelete

typedef struct RumItem {
    ItemPointerData iptr;      /* heap TID */
    bool            addInfoIsNull;
    Datum           addInfo;     /* 多出来的 */
} RumItem;

同一个 key，posting 有两种形态

03 原理 / WHERE addInfo COMES FROM

addInfo 从哪来？两条路

① OPERATOR CLASS 自己生成
rum_tsvector_ops：存词位置
CREATE OPERATOR CLASS rum_tsvector_ops DEFAULT FOR TYPE tsvector USING rum AS OPERATOR 1 @@ (tsvector, tsquery), OPERATOR 2 <=> (...) FOR ORDER BY float_ops, FUNCTION 2 rum_extract_tsvector(...), FUNCTION 8 rum_tsquery_distance(...), FUNCTION 10 rum_ts_join_pos(...), STORAGE text;
配置 tsvector 词位置信息；rum_tsquery_distance() 用于 <=> 排名距离计算。定义见 rum_init.sql。
② 从同一 HEAP TUPLE 的另一列 ATTACH
把业务列挂到 tsvector 的 posting 上
CREATE INDEX tsts_idx ON tsts USING rum (t rum_tsvector_addon_ops, d) WITH (attach = 'd', to = 't');
注意
initRumState() 要求 attach 与 to 同时存在；源码也会拒绝 order_by_attach 用在 pass-by-reference 列上。
03 原理 / FOUR CODE PATHS

四条源码路径，解释它的性能性格

Buildsrc/ruminsert.c · rumbuild()
  1. 初始化 meta / root page
  2. IndexBuildHeapScan() 扫 heap
  3. 每 tuple → rumHeapTupleBulkInsert()
  4. rumExtractEntries() 提取 key + addInfo
  5. BuildAccumulator 红黑树按 key 聚合
  6. 达到 maintenance_work_mem 就 flush
  7. 更新 metapage + generic WAL
要同时保持 TID 与 addInfo 的组合
Insertsrc/ruminsert.c · ruminsert()
  1. 初始化 RumState
  2. 有 attach 列则取 outerAddInfo
  3. 逐索引属性 rumHeapTupleInsert()
  4. 提取 key，构造 RumItem{iptr, addInfo}
  5. 逐 key 调 rumEntryInsert()
  6. 已有 tree → 插入；list 放不下 → 转 tree
  7. 新 key → fresh leaf tuple
没有 pending list 的批量缓冲路径
Searchsrc/rumget.c
  1. rumgetbitmap() 填 TIDBitmap
  2. rumgettuple() 产有序结果
  3. scanGetItem() 分派 Fast / Full / regular
  4. 不能按自然序时放入 rum_tuplesort
  5. keyGetOrdering() 调 orderingFn 算 order by 值
  6. 把结果交还 executor
order by 信息在索引内 → 少回表
Vacuumsrc/rumvacuum.c
  1. rumbulkdelete() 从 entry tree 左端叶子页开始
  2. 逐页清理 entry page
  3. 记录待处理的 posting tree root
  4. rumVacuumPostingTree() 删无效 TID
  5. cleanup 统计页数 / entries 并更新 metapage
  6. PageIsNew 与 RUM_DELETED 页记入 FSM
死 TID 清理仍依赖 VACUUM
ENGINEERING IMPLICATION
写入慢不是「实现不够快」，而是维护的信息量更多，且没有 GIN pending list 的批量缓冲。
03 原理 / SEARCH & TOP-N

两个取数接口，决定 Top-N 的命运

rumgetbitmap() → Bitmap Heap Scan
把匹配 TID 加入 TIDBitmap，交给上层回表。过滤快，但排序信息不参与推进。
rumgettuple() → Index Scan（有序）
可产生有序结果，适合带 ORDER BY <=> LIMIT 的 Index Scan；不能按自然顺序返回时才走 rum_tuplesort。
价值点：order by 所需信息在索引里，执行器不必为排序字段或词位置频繁回表。
depth-first search / 官方称可立即返回第一批结果
仍需 MVCC 可见性检查与必要 recheck —— 不等于 index-only scan。

RUM · GIN · GiST / B-tree

04 权衡 / HOW TO JUDGE

怎么判断 RUM 值不值得：四个维度

01 / 回表减少
索引扫描阶段就能算距离
排序 / ranking 需要的信息已在 posting 的 addInfo 中，不必先回 heap 取。
02 / 短语更直接
位置信息不再完全依赖 heap
短语搜索与 ranking 不必从 heap 里的 tsvector 位置重新计算。
03 / Top-N 延迟更低
LIMIT 有机会更早返回
索引能按 distance / order 推进时，不必算完整批候选。
04 / 写入与空间变贵
每个 item 都多带一份信息
posting 更大，写路径更长，容量规划要同步算进去。

05 实操 / DEMO 01

全文检索，按相关度排序

CREATE EXTENSION rum; -- 表 + tsvector 更新触发器 CREATE TABLE test_rum(t text, a tsvector); CREATE TRIGGER tsvectorupdate BEFORE UPDATE OR INSERT ON test_rum FOR EACH ROW EXECUTE PROCEDURE tsvector_update_trigger('a', 'pg_catalog.english', 't'); INSERT INTO test_rum(t) VALUES ('The situation is most beautiful'), ('It is a beautiful'), ('It looks like a beautiful place'); -- 关键：opclass 选 rum_tsvector_ops CREATE INDEX rumidx ON test_rum USING rum (a rum_tsvector_ops); EXPLAIN (COSTS OFF) SELECT t, a <=> to_tsquery('english','beautiful | place') AS distance FROM test_rum WHERE a @@ to_tsquery('english','beautiful | place') ORDER BY a <=> to_tsquery('english','beautiful | place');

05 实操 / DEMO 02

全文过滤用 ts，排序用 created_at

CREATE TABLE docs ( id bigserial PRIMARY KEY, body text NOT NULL, ts tsvector GENERATED ALWAYS AS (to_tsvector('english', body)) STORED, created_at timestamp NOT NULL ); INSERT INTO docs(body, created_at) VALUES ('postgres rum index supports phrase search', '2026-04-21 10:00:00'), ('postgres gin index supports inverted search', '2026-04-20 10:00:00'), ('rum can attach timestamp for ordering', '2026-04-21 12:00:00'); -- 把 created_at 挂到 ts 的每个 posting 上 CREATE INDEX docs_rum_idx ON docs USING rum (ts rum_tsvector_addon_ops, created_at) WITH (attach = 'created_at', to = 'ts'); EXPLAIN (COSTS OFF) SELECT id, created_at, created_at <=> timestamp '2026-04-21 11:00:00' AS distance FROM docs WHERE ts @@ to_tsquery('english', 'postgres | rum') ORDER BY created_at <=> timestamp '2026-04-21 11:00:00' LIMIT 5;

06 决策 / BEST PRACTICES

三种角色，各自该盯什么

数据库架构师
DBA
业务开发者
01把 RUM 定位为「搜索体验优化索引」，不要默认替代所有 GIN。
02需求包含「全文过滤 + 相关度排序 / 短语 / 业务时间 Top-N」时，才把 RUM 纳入候选。
03只是 WHERE tags @> ... / WHERE tsv @@ q 且无复杂排序，先用 GIN 做基线。
04设计索引时明确主问题：相关度、短语、时间排序还是数组相似度 —— 不同 opclass 的 addInfo 不一样。
05写多读少系统，先评估 WAL、索引大小、insert / update TPS，再决定是否上线。
01用 EXPLAIN (ANALYZE, BUFFERS) 对比 GIN / RUM，不要只看 planner 选了哪个索引。
02重点观察：heap blocks hit/read、sort 节点是否消失、Top-N 延迟、索引大小、WAL 量、vacuum 时间。
03更新频繁的全文列关注索引膨胀：RUM 仍存 heap TID，死元组清理依赖 VACUUM。
04生产启用前确认扩展版本、PostgreSQL 版本和升级路径（README：12+ 可直接构建，9.6–11 需额外处理 tidbitmap 源文件）。
05不要在 pass-by-reference attach 字段上启用不受支持的 ordering 形态。
01SQL 要写成索引能理解的形态：WHERE t @@ q ORDER BY t <=> q LIMIT n 或 attached_col 版本。
02不要把 <=> 当普通相似度函数到处套：它是 opclass 暴露给 ORDER BY 的距离语义，通常越小越靠前。
03对搜索框 query 做规范化：语言配置、停用词、前缀搜索、短语操作符都会影响召回与 recheck。
04结果质量用业务样本评估：RUM 让 ranking 更快，不等于默认 ranking 符合产品排序目标。
05复杂多字段打分、个性化排序仍要 SQL 层或业务层完成，RUM 只承担召回与部分排序。

06 决策 / WHEN & WHEN NOT

一条分界线：需求里有没有「排序 / 排名 / 短语」

适合 / USE RUM
✓文档、帖子、商品、工单、日志全文检索，且要求相关度排序
✓搜索结果常带 LIMIT，用户只看第一页，Top-N 延迟敏感
✓短语 / 近邻词搜索多，词位置信息对判断很重要
✓「全文过滤 + 时间 / 价格 / 业务字段距离排序」的组合查询
✓读多写少或读写比适中，愿意用更大索引换查询体验
不适合 / STAY WITH GIN
×高频 insert / update / delete，且搜索排序要求不强
×只做简单包含过滤，GIN 已经满足 SLA
×对扩展依赖敏感，必须只用 PostgreSQL core 功能
×attach 字段是复杂 varlena / pass-by-reference，且希望用于不受支持的 ordering
×排序规则高度业务化：多字段、多阶段打分、个性化排序
决策提示
RUM 是「用写入与空间，换排序 / 排名 / 短语能力」的交易。没有这些需求，交易就不成立。
06 决策 / SEVEN PITFALLS

上线前，先绕开这七个坑

01
当成 GIN 的无脑升级版
→ 没有排序 / 排名需求，就别换
RUM 用写入和空间换排序能力。没有排名 / 短语 / 附加字段排序需求时，GIN 往往更合适。
02
只看查询快，不看写入慢
→ 压测写入 TPS、WAL、autovacuum
官方明确说明 build / insert 慢于 GIN。上线前必须压测写入、更新、WAL 与 autovacuum。
03
attach / to 理解反了
→ 过滤走 t，排序才用 d
WITH (attach='d', to='t') 是把 d 附着到 t 的 posting 上：过滤走 t，排序可以用 d。
04
以为索引排序 = 业务排序
→ 复杂打分仍在 SQL / 业务层
<=> 是 opclass 定义的 distance。会员等级、库存、点击率、新鲜度混合排序仍需额外打分。
05
忽略 recheck 和 MVCC
→ 有 addInfo 也不是 index-only scan
返回 TID 后仍要过可见性检查与必要 recheck；索引里有 addInfo 不等于 index-only scan。
06
用错 opclass
→ hash_ops 不支持前缀搜索
rum_tsvector_hash_ops 存 lexeme hash，不支持 prefix search；rum_tsvector_ops 才支持。先确认查询语义。
07
版本与部署路径没锁定
→ 升级 / 主从 / 备份都要带上扩展
RUM 是扩展不是 core。大版本升级、主从、备份恢复、镜像构建都要包含扩展安装与版本验证。

TAKEAWAY / 带走什么

三句话，和留给你的五个问题

01
差别只有一个字段
posting item 从 iptr 变成 (iptr, addInfo)，其余仍是 PostgreSQL 的索引 AM 框架。
02
读侧的收益是「少回表」
排名、短语、附加字段排序、Top-N 提前返回，都源于排序所需信息已在索引里。
03
写侧的代价是「信息更多」
更大的索引、更慢的 build / insert、generic WAL、没有 pending list 缓冲。
别把它当升级版，把它当一次有明确前提的交易。
