03PROBLEM / 背景与痛点

最基础的问题：数据放哪里，怎么找回来？

如果从零设计存储层，最直觉的方案是「所有记录顺序追加进一个大文件」——然后会撞上四堵墙。

01 / 查

查一条记录要扫全表

没有位置信息，SELECT 变成线性扫描，性能灾难。

02 / 删

删除留下空洞

文件不会自己收缩，磁盘空间被白白占住。

03 / 改

更新要移动数据

行长度变了就得搬家，写放大，索引跟着失效。

04 / 并发

写入争抢同一位置

所有会话都往文件尾部挤，形成单点热点。

heap 的答案 / 两条链路
WRITE
写入请求→FSM 找空闲 Block→空闲位写入→更新 FSM

不排序、不搬家，找一个放得下的位置直接写。

READ
读取请求→ctid 直接寻址→读 Block 中对应记录

物理行号就是地址，不需要遍历。

无序存储的代价：UPDATE 不原地修改，旧版本变成 dead tuple 与 live tuple 混存；不及时清理就越写越胖。这就是 vacuum 存在的理由。

06ADDRESSING / ctid 物理行号

ctid = (3, 9)：两个数字定位一行

悬停或点击任一 lp[i]：观察 line pointer 如何指向真实行数据。

当前寻址
(3, 9)

第 3 号数据块中，第 9 条 line pointer 所指向的记录。

SQL 里直接用 ctid
SELECT ctid, * FROM tbl WHERE ctid = '(0,1)';
SELECT ctid, * FROM tbl
 WHERE ctid >= '(0,1)' AND ctid < '(11,0)';

为什么 lp 不移动？官方定义：line pointer 一旦分配，直到被回收前索引号长期不变——行数据可以在页内挪动，索引里存的 ctid 却不用改。

07FREE SPACE MAP / 空闲空间管理

FSM：停车场的「剩余车位显示牌」

要写入一行，先要快速找到一个放得下它的 Block —— FSM 用一棵二叉树把「最大值查询」变成 O(log n)。

搜索过程
根值 8 ≥ 6，说明「一定存在」满足条件的 Block。点击左侧按钮，看路径如何被点亮。
精度与代价

每个叶节点只用 1 个字节，把 8 KB 切成 256 档 → 每档约 32 字节。省空间，但不精确；写入后必须回写更新 FSM。

用插件亲眼看到
CREATE EXTENSION pg_freespacemap;
SELECT * FROM pg_freespace('tbl') LIMIT 10;
-- blkno, avail（字节）
08VISIBILITY MAP / 可见性图

VM：每个 Block 只花 2 个 bit，省下大量回表

悬停小方块：查看该 Block 的两个标志位。

在 EXPLAIN 里验证

Index Only Scan 的输出里 Heap Fetches: 0 表示完全没回表；这个数字开始增长，通常意味着相关 Block 的 all-visible 位被更新清掉了，等 vacuum 重新置位。

INDEX ONLY SCAN / 有无 VM 的差别
没有 all-visible
索引条目→回表读 heap→逐行判断可见性→返回

索引里拿到 ctid，仍必须访问 heap 页确认这行对当前快照是否可见。

有 all-visible
索引条目→查 VM 位→直接返回

整页都可见，无需回表 —— 大范围扫描时省下的随机 IO 非常可观。

维护成本：一旦某个 tuple 被更新/删除，对应 Block 的 all-visible 位就要清掉；vacuum 再把它重新置上。

09WRITE PATH / 写入流程

一条 INSERT 落地，经过谁的手

为什么是这个顺序

① FSM 先回答「写哪儿」

不扫描整表，只按树找满足行大小的位置；找不到就新分配 Block。

② Buffer 里改，不是直接改磁盘

页被 pin 住后，lp 与 tuple 在内存中同时相向生长。

③ WAL 先落，安全才有保障

日志记录变更，崩溃后可重放；这也是写入链路里不可省的一步。

④ 回写 FSM，再返回 ctid

剩余空间变了，下一次写入才能拿到正确的判断依据。

一句话：heap 的写入几乎没有排序成本，快就快在「找空位 + 直接放」。

10MVCC / 多版本与死元组

UPDATE 不是覆盖：live 与 dead 会同时住在页里

点击时间轴，观察 lp 与 tuple 状态变化 →
谁会挡住 vacuum
只有「所有活跃事务都不再需要」的旧版本才能回收。t1 时只有一条 live tuple，没有垃圾。

长事务 backend_xmin

一个老快照钉住 xid 水位，之后产生的 dead tuple 全部无法回收。

复制槽 xmin / catalog_xmin

下游没消费完，主库就得替它留着旧版本。

SELECT pid, backend_xmin, state, query
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL;

HOT Update：让索引「原地不动」

切换对比 →

01

12VACUUM / 清理与空间复用

Vacuum：把 dead tuple 变回「可复用空间」

AUTOVACUUM 关键参数
参数默认作用
autovacuum_vacuum_threshold50触发的最少 dead tuple 数
autovacuum_vacuum_scale_factor0.2触发的 dead tuple 占比
autovacuum_vacuum_cost_delay2ms每次 sleep 时长（IO 限速）
autovacuum_vacuum_cost_limit200sleep 前的 IO 消耗上限
autovacuum_max_workers3并发 worker 数

VACUUM ≠ VACUUM FULL

VACUUM 在线、不锁表，空间只标记复用（末尾全空 Block 除外）；VACUUM FULL 重建整表、彻底缩小文件，但要锁表阻塞业务。生产环境优先 pg_repack。

ALTER TABLE hot_table SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_vacuum_threshold = 100,
  autovacuum_vacuum_cost_delay = 0  -- NVMe 不限速
);

三个值得带走的问题

① 为什么 vacuum 只能回收文件末尾的完全空闲 Block？

② 长事务为什么导致膨胀

一个老快照把 backend_xmin 钉住，此后产生的 dead tuple 谁都不能收，直到它结束。

SET statement_timeout = '30min';
SET idle_in_transaction_session_timeout = '5min';
③ 本质取舍 / 每个设计选择都在交换
设计选择获得的放弃的
无序存储（FSM 找空位）写入极快、无热点范围查询 IO 多（需 cluster 辅助）
MVCC 多版本共存读写不阻塞、快照隔离需要 vacuum，有膨胀风险
行存（整行为一体）整行读取一次寻址只读少列时 IO 浪费

一句话：heap 是「为 OLTP 写入性能极度优化，牺牲了 OLAP 分析性能与空间利用率」的设计。

14FIT / 优势与不适合场景

什么时候用 heap，什么时候换引擎

FITS WELL

优势与适合场景

01

OLTP 高频小事务

按行存储，全行读取效率高 · 电商订单、用户账户

02

随机读写

ctid 直接寻址，O(1) 定位 · 用户信息更新

03

时序热数据写入

append-only + FSM 快速找位置 · IoT 传感器数据

04

需要整行大多数字段

一行物理上在一起，一次 IO 取全行 · 报表导出

05

中等数据量 HTAP

配合并行查询，兼顾写入与分析 · SaaS 多租户

NOT A FIT

劣势与替代方案

01

高频 UPDATE + 长事务

dead tuple 堆积、膨胀严重 → zheap / 分区表

02

只读少数列的大规模扫描

读整行只用几列，IO 浪费 → Parquet 列存

03

超宽表（单行 > 8KB）

受 blocksize 限制 → TOAST + 适当拆表

04

历史数据归档 / 高压缩

行存压缩比低 → Parquet + 对象存储

05

时序历史数据 OLAP

列存更高效 → DuckDB + Parquet

判断口诀

写多、点查多、要整行 → heap；少列大扫描、归档压缩 → 列存。

16HANDS-ON / 实操与最佳实践

上手：用插件把内部结构「翻出来」

CREATE EXTENSION IF NOT EXISTS pageinspect;
CREATE EXTENSION IF NOT EXISTS pg_freespacemap;

CREATE TABLE heap_demo (
  id BIGSERIAL, name TEXT, score FLOAT, payload JSONB
) WITH (fillfactor = 80);

INSERT INTO heap_demo (name, score, payload)
SELECT 'user_' || g, random()*100,
       jsonb_build_object('level', (g % 10)+1)
FROM generate_series(1, 10000) g;

-- 1 物理文件路径  2 ctid  3 页内结构  4 FSM
SELECT pg_relation_filepath('heap_demo');
SELECT ctid, id, name FROM heap_demo LIMIT 5;
SELECT lp, lp_flags, t_xmin, t_xmax, t_ctid, t_data
  FROM heap_page_items(get_raw_page('heap_demo', 0)) LIMIT 5;
SELECT blkno, avail FROM pg_freespace('heap_demo') LIMIT 10;
-- 只在 id 上有索引；name / score 无索引
CREATE TABLE hot_test (
  id INT PRIMARY KEY, name TEXT, score INT
) WITH (fillfactor = 70);

INSERT INTO hot_test
SELECT g, 'user_'||g, g FROM generate_series(1,1000) g;

SELECT ctid, id, name FROM hot_test WHERE id = 1;  -- (0,1)
UPDATE hot_test SET score = 999 WHERE id = 1;
SELECT ctid, id, name, score FROM hot_test WHERE id = 1;
-- HOT 成功：(0,XX)，Block 号仍为 0

SELECT n_tup_upd, n_tup_hot_upd,
  round(n_tup_hot_upd::numeric / nullif(n_tup_upd,0)*100, 2) AS hot_ratio
FROM pg_stat_user_tables WHERE relname = 'hot_test';
-- 表膨胀：dead tuple 占比 + 最近 vacuum 时间
SELECT schemaname, tablename,
  pg_size_pretty(pg_total_relation_size(schemaname||'.'||tablename)) AS total_size,
  n_dead_tup, n_live_tup,
  round(n_dead_tup::numeric /
        nullif(n_live_tup + n_dead_tup, 0) * 100, 2) AS dead_ratio,
  last_vacuum, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 20;

-- 找出阻碍 vacuum 的长事务
SELECT pid, age(backend_xmin) AS xmin_age, state, left(query, 100)
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL ORDER BY age(backend_xmin) DESC;

VACUUM VERBOSE ANALYZE heap_demo;
观察要点
ctid 从 (0,1) 开始连续增长；heap_page_items 能直接看到 t_xmin / t_xmax / t_ctid，把前面讲的多版本机制坐实。
时序场景的配置反例

几乎不更新的写入型表，fillfactor = 100 更省空间；按时间分区 + BRIN 索引，冷热分离、索引极小。

CREATE TABLE iot_metrics (...)
  WITH (fillfactor = 100)
  PARTITION BY RANGE (ts);
CREATE INDEX ON iot_metrics_2024_01
  USING brin (ts);

18FAQ / 常见问题

五个最常被问到的问题

Q1

fillfactor 设多少合适？

−

频繁 UPDATE 非索引列的表，70–80 是常见选择；append-only 时序表和几乎不更新的历史表用 100 更省空间。预留空间是给 HOT update 用的，不更新就别白留。

Q2

vacuum 和 vacuum full 的区别？

+

VACUUM 在线，只回收 dead tuple 空间供复用，一般不缩小文件（末尾全空 Block 除外）；VACUUM FULL 重建整表、彻底缩小，但锁表阻塞业务。生产环境优先考虑 pg_repack。

Q3

为什么 UPDATE 一行后，表文件反而变大了？

+

heap 的 UPDATE 是「写新版本 + 标记旧版本为 dead」。HOT 条件不满足时，新旧版本都占空间，还可能新增索引条目；直到 vacuum 清理后，空间才被标记为可复用（文件不一定变小）。

Q4

TOAST 是什么？什么时候用到？

+

行（含变长字段）超过 toast_tuple_target（默认约 2KB）时，大字段被移到独立 TOAST 表：Extended 先压缩、还大就搬走；External 不压缩直接搬走。heap 里只留一个 18 字节指针，可用 SET STORAGE 调整。

Q5

如何判断一张表是否严重膨胀？

+

经验阈值：dead tuple 占比 > 20%，或实际大小达到理论大小 2 倍以上。可用 pgstattuple('your_table') 精确诊断，重点看 dead_tuple_percent。
