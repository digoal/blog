01 / 问题

一个反复出现的工程问题

数据库需要一个随时可插入、可删除、可按顺序扫描的数据集合。两条老路各有代价。

方案 A

平衡树 / 红黑树

能做这件事，但旋转、重平衡、并发修改、内存管理都不便宜；一次插入可能牵动整条祖先路径。

方案 B

普通有序链表

插入只改局部指针，简单可靠；但定位一个 key 只能线性查找，范围扫描的起点也难以快速确定。

第三种选择 · 跳表　保留链表的局部拼接特性，用随机层高制造「高速通道」，让查找、插入、删除在期望意义上接近 O(log N) —— 不通过旋转维持严格平衡，而是在插入节点时随机决定它出现在多少层。
William Pugh, Skip Lists: A Probabilistic Alternative to Balanced Trees — 把它定位为平衡树的一个概率替代方案。
01 / 现场

数据库里的四个现场

抽象地说，跳表解决的是「动态有序字典」：插入 key、删除 key、找第一个 ≥ 目标 key 的节点、从某处开始顺序扫描。

排行榜 / 延迟队列

按 score 或时间排序，还要频繁更新单个成员、按区间取结果。

动态更新 + 范围

LSM MemTable

写入先进入内存有序结构，刷盘时按 key 顺序生成 SSTable。

追加写友好

范围查询

先快速定位下界，再沿底层链表连续扫描，跳转成本极低。

seek + scan

并发读写

插入只改局部指针，比树旋转更容易拆出单写多读或无阻塞读路径。

读路径易无锁
它牺牲了什么：严格的最坏情况保证，以及缓存连续性。B+Tree 的节点是「页」，适合磁盘与 SSD 的块访问；跳表是指针结构，更适合内存。把跳表原样放到磁盘页上通常不是最自然的选择。
02 / 结构

一组从稀疏到密集的有序链表

最底层包含所有节点；越往上层节点越少。查找时从最高层出发，能向右走就向右走，走过头之前下沉一层。

L0 · 底层

全量有序链表，范围扫描沿它连续读出。

L1 — L3 · 上层

稀疏索引 = 「高速通道」，一次跨过多个底层节点。

节点塔

同一个 key 出现在多层，各层各有自己的 forward 指针（图中竖虚线相连）。

鼠标悬停任意节点，可查看它的层高。　图示说明：为便于阅读按约 p ≈ 1/2 的稀疏度绘制；Redis 与 LevelDB 生产实现使用 p = 1/4（详见下一页）。图中层高是随机的，并非严格 2:1。
02 / 层高

层高从哪来：几何分布

插入节点时随机决定它出现在多少层：所有节点都有第 1 层，约 p 的有第 2 层，约 p² 的有第 3 层……

切换概率 p：
每节点平均指针数　1/(1−p)
1.33
个 forward 指针 / 节点
生产实现的常量
Redis　ZSKIPLIST_P = 0.25，MAXLEVEL = 32
LevelDB　kBranching = 4（即 1/4），kMaxHeight = 12
两者只是常量命名不同，升层概率一致。
最高层期望 ≈ log1/p N

p 越小，指针越省、层数越少；横向移动略增，但常数更优。

Pugh 原文用 p = 1/2 解释算法；工程上 Redis / LevelDB 都取 1/4 —— 减小 p 会增大运行时间波动，但能降低每节点指针开销。
03 / 查找

查找：寻找第一个 ≥ 目标 key 的节点search(55)

# 从 header 开始，按层从高到低
search(target):
  x = header
  for level = max_level - 1 downto 0:
    while x.forward[level] != NIL
      and x.forward[level].key < target:
      x = x.forward[level]
  return x.forward[0]  # 第一个 ≥ target
单步演示 · 点击按钮推进
LevelDB 的 FindGreaterOrEqual 正是这个形状：逐层记录前驱并下降，到第 0 层返回候选节点。
路径：高层大步快进 → 逐层下沉 → 底层定位下界。朱红为已走过的查找路径，深绿为返回结果。
03 / 插入

插入：随机层高 + update[] 前驱数组

先查找插入位置，把每层的前驱保存到 update[]；再随机生成新节点层高，把它挂到这些前驱之后。

蓝虚线框 = update[] 记录的各层前驱；朱红虚线框 = 新节点 58（随机层高 = 2）
只改 L0 / L1 两层前驱指针 —— 无旋转、无回溯，其余节点层高不变
局部放大示意：为突出「每层前驱不同」，L1 仅画出部分索引节点；节点间距已放大。
示例：插入 key = 58，随机层高 = 2

图中蓝色虚线框是 update[] 记录的前驱（L1 = 37、L0 = 52），朱红虚线框是新节点 58 —— 每层前驱可以不同。

为什么简单
  • 01没有旋转，没有递归回溯
  • 02修改范围就是新节点参与的那些层
  • 03其余节点的层高完全不变
两条实现分叉

Redis 还要维护 span 与 backward；删除时把 span 调整回去。
LevelDB 不删除单个节点：删除语义由内部 key 的 deletion marker 表达，内存交给 Arena 在 MemTable 结束时整体释放。

Redis 的 zslInsertNode / zslUnlinkNode 负责 forward、span 的维护；LevelDB 的 SkipList::Insert 只做发布。
03 / 复杂度

期望对数，不是绝对最坏

层数期望约 log1/p N，每层横向移动期望为常数，因此查找期望 O(log N)。

⚠ 别把期望复杂度说成最坏复杂度
跳表是概率平衡：有坏的最坏情况，但随机层高让固定输入序列无法稳定制造退化结构。高概率足够好 ≠ 硬实时最坏情况保证。
工程上还要设 MaxLevel，防止极端层高无限增长
Redis
32
4³² = 2⁶⁴
注释：足以覆盖 2⁶⁴ 元素
LevelDB
12
4¹² ≈ 1.68×10⁷
贴近 MemTable 规模

差异不是「谁更先进」，而是数据结构上限与 workload 生命周期不同：MemTable 写满即冻结刷盘，不需要无限膨胀。

Pugh 同时提醒：设置上限低于理论值不影响正确性，只让顶层链表变长。

05 / Redis ①

为有序集合组合两种索引

Redis sorted set 在大对象编码下使用「哈希表 + 跳表」双结构：元素同时加入两者，各管一半命令表面。

官方源码 src/t_zset.c 文件头写明：哈希表用于成员到节点的定位，跳表用于按 score 的有序视图；元素少时用 listpack 更省内存。
05 / Redis ②

不是教科书跳表照搬

它围绕 sorted set 的命令表面做过增强 —— 其中 span 是支持 rank 系列命令的关键代价。

ZRANK 不必逐个遍历底层节点：查找时把经过的 span 累加，即为目标节点的排名，复杂度 O(log N)。
01
允许重复 score

相同 score 再按成员字典序比较，不是插入顺序。

02
level-1 backward 指针

支持 ZREVRANGE 等反向遍历。

03
每层的 span

记录该层 forward 跨过的底层节点数，支撑 ZRANK / ZCOUNT 类按排名定位。

04
节点中嵌入 SDS

减少成员字符串的重复分配。

ZRANGE 复杂度 O(log N + M)，M 为返回元素数；添加元素需 O(log N) 的有序结构维护。

05 / LevelDB ①

MemTable：有序的写缓冲

每个 log file 的最近更新都有一份内存结构 MemTable；log 达到阈值后旧 MemTable 冻结，后台写成 SSTable。

源码里 MemTable::Table 就是 SkipList<const char*, KeyComparator>；MemTable::Add 把 internal key 与 value 编码进 Arena 的连续 buffer，再插入跳表。读操作需要同时查询 MemTable 与 SSTable。
05 / LevelDB ②

单写、多读、节点不删除

线程安全注释非常明确：写入需要外部同步；读者只要求跳表不被销毁，除此之外不需要内部锁。

支柱 01

写者外部同步

同一时刻只有一个写者，插入无需处理写写竞争。

支柱 02

读者完全无锁

节点 next_[] 是原子指针；读 next 用 acquire load。

支柱 03

不删节点 + Arena

key 一旦链接即不可变；内存随 MemTable 整体释放。

发布顺序是全部要点（skiplist.h · Insert 节选）
// 写侧：外部同步
x = NewNode(key, height)
for i = 0 .. height-1:
  // 先 relaxed 填好 x 自己的 next
  x->NoBarrier_SetNext(i,
      prev[i]->NoBarrier_Next(i))
  // 再 release 发布：让前驱指向 x
  prev[i]->SetNext(i, x)

// 读侧：无锁
node = prev->Next(i)   // acquire
不变量：读者一旦在某层看到新节点，它在更低层也已经接好 —— 「每层都是下一层的子列表」始终成立。
对比 Redis：Redis 必须真实删除节点，因此要维护 forward、backward、span 与 dict 的一致性；并发删除涉及逻辑删除、物理摘链、内存回收与 ABA 风险。

  • 02相同 score 的成员按字典序排列（alice 在 bob 前）
  • 03rank 查询依赖跳表 span 的维护
LevelDB 侧

编译并运行 skiplist_test，重点看并发测试：单写线程持续插入，多读线程随机 seek / next，要求读者不漏掉迭代器创建时已存在的数据。

07 / 实践

三类角色，各自该记住什么

面向数据库架构师
  • 01把跳表放在内存路径优先考虑：MemTable、排行榜、调度队列、临时有序结构，而不是直接替代磁盘 B+Tree。
  • 02明确是否需要 rank。需要按排名跳转，普通跳表不够，要像 Redis 一样维护 span。
  • 03删除策略要先定：LevelDB 用「不单独删除 + tombstone + 整体释放」规避复杂删除；Redis 必须维护多套指针的一致性。
面向 DBA
  • 01大 sorted set 不只是一个集合，还包含 dict + skiplist 两套结构；容量评估要算成员字符串、指针、span、dict entry。
  • 02避免深分页滥用，改用「记住上次 score / member 作为游标」的 seek-after 模式。
  • 03监控对象编码：小 zset 用 listpack 更省内存，阈值调小会换来更早的有序能力与更高内存成本。
面向业务开发者
  • 01sorted set 适合「分数变化 + 范围查询 + 排名查询」：排行榜、延迟任务、滑动窗口索引。
  • 02相同 score 的排序不是插入顺序，而是成员字典序；需要稳定时间顺序时把时间或唯一序列编码进 score / member。
  • 03不要把每个过滤维度都建成巨大 sorted set 后频繁交并集，先估算集合规模与交集代价。
共同的前提：先判断数据在哪一层（内存 / 外存）、需要哪些查询能力，再选结构 —— 而不是先选结构再迁就查询。
08 / 边界

适合与不适合

场景是否适合原因
内存排行榜、延迟队列、时间窗口索引适合需要动态插入、更新、按 score 范围扫描；Redis zset 的双结构正好匹配。
LSM MemTable适合写入在内存排序，冻结后顺序刷盘；节点生命周期和 Arena 可以绑定。
磁盘主索引通常不适合指针跳转多、页局部性弱；B+Tree 更适合块设备和 buffer pool。
纯等值查找缓存不优先哈希表更直接，跳表的顺序维护会成为额外成本。
需要严格最坏情况延迟上界谨慎跳表是概率平衡；高概率足够好不等于硬实时最坏情况保证。
向量 ANN 检索不是同一问题HNSW 借鉴「随机层级 + 上层粗导航」，但底层是近邻图，不是有序链表。
一句话判断：要「有序 + 动态 + 在内存里」→ 跳表很有竞争力；要「块 IO / 严格最坏延迟 / 纯等值」→ 另有更合适的结构。
09 / 常见坑

六个容易踩的坑

坑 01

期望 ≠ 最坏

把「期望 O(log N)」说成红黑树那种严格最坏 O(log N)。

坑 02

忽略随机数质量

层高分布影响高度与指针数；Redis / LevelDB 都把最大层高写死并做结构校验与测试覆盖。

坑 03

忘记 rank 要额外维护

只有 forward 指针无法高效回答「第 k 个元素是谁」；span 是为 rank 付出的空间与维护成本。

坑 04

低估并发删除

插入只发布新节点相对容易；删除牵涉逻辑删除、物理摘链、内存回收与 ABA 风险，不能简单套用非阻塞链表结论。

坑 05

Redis 深分页

大 offset 仍需跳过大量元素，应改用「记住上次 score / member」的游标模式。

坑 06

把 HNSW 当普通跳表

HNSW 同样用随机最高层与分层导航，但解决近似最近邻，不提供有序字典语义与严格 score 范围查询。

Harris 的非阻塞链表论文围绕线性化插入 / 删除与 CAS 设计展开，是理解并发跳表删除难点的基础资料，但不能直接套用到带多层索引的跳表。
