01 / 问题意识Motivation

OLAP 的 CPU 时间，去哪了？

heap 行存非常适合 OLTP；但大批量过滤、表达式计算、聚合是另一种负载。

PostgreSQL 每行一个 tuple。执行器每拿到一行，都要把列值从 tuple 里解出来，再逐行执行表达式与聚合。这个模型通用、事务语义清楚、单行更新便宜 —— 代价则出现在扫描型查询里。

01tuple deform：解包一行，取到目标列
02表达式解释执行：递归求值计划树节点
03函数调用：每个运算都要走一次函数约定
04pull 模型：叶子节点反复保存 / 恢复上下文
05MVCC：每行可见性判断与元组头开销
不改 executor、不改 heap page，
能不能先验证「向量化」这条路的收益？
一行数据的旅程 · 每行重复一次
官方 docs 佐证：TPC-H Q6 中 tuple deform 约占 40% 总执行时间。来源：Postgres Pro Enterprise vops 文档「Motivation」。
01 / 问题意识Three Costs

行存模型在 OLAP 上的三个放大

通用性换来的每行固定成本，在只读少量列、却要扫上百万行的场景里极难摊薄。
01读取

列读取放大

查询只需要 4 个列，但 heap tuple 仍按行整体读出；宽表尤其吃亏。

代价：I/O 与解包时间与表宽成正比，而非与查询宽度成正比。
02CPU

CPU 调用放大

同一个表达式对每一行重复走解释执行与函数调用路径；解释执行约为原生代码的十分之一量级。

代价：调用开销远大于运算本身，尤其在高成本谓词上。
03可见性

可见性与解包放大

每行都有 MVCC 头和 tuple deform 成本；读多写少的分析场景没有写入收益来抵消。

代价：只为事务一致性付账，却拿不到对应收益。
02 / 结构定义WOS → ROS

把 64 行同列值，塞进一个字段

业务上仍是一张普通表；物理上每个字段已经变成一个小向量。一次函数调用最多处理 64 个值。
代价 / TRADE-OFFS 源表与投影两份数据 投影需要批量刷新 单行实时写入 → 大量未满瓦片 优化器无法理解 tile 内选择性
02 / 结构定义Definition

VOPS 是什么，不是什么

它的「vector」指分析执行中的批量标量处理，不是向量数据库里的 embedding。
定义 / DEFINITION
VOPS 是一种通过 PostgreSQL 扩展类型实现的微型列向量投影：一个 tile 类型值保存同一列最多 64 个标量值，并配套位图记录 NULL、空槽和过滤结果；算子、聚合、unnest 和 FDW 都围绕这 64 个槽位工作。
TILE_SIZE 64null_maskempty_mask filter_maskvector aggregateFDWparse hook
×

不是 Parquet 那样的独立文件格式

数据仍存在普通 PostgreSQL heap 行里，只是字段类型被替换成扩展类型。

×

不是 DuckDB / HyPer 那样的向量化执行器

executor、planner 与 SQL 类型系统保持原样，收益来自扩展函数内部的循环。

×

不是 pgvector 的相似搜索

不解决 embedding ANN 检索；这里的向量是一批同列标量值。

VECTOR 的真实含义
少函数调用 + tile 内批处理
逐行　price × discount → 每行一次解释 + 一次函数调用，重复 64 次
tile　一次 tile 函数进入 → 内部循环 64 个槽位，返回一批结果
成本 ÷ 64

为什么恰好是 64？

① 位图刚好装得下：一个 64 位整数正好表示每个槽位的 NULL / EMPTY / 过滤状态；vops_bool 的 payload 本身就是一个 64 位位图。

② cache 放得下：tile 太大会让复杂表达式的多个操作数与中间结果挤不进 CPU cache。

空间直觉

vops_int4 / vops_float4 = 16 + 64×4 = 272 字节；vops_int8 / float8 = 528 字节。

　predicate, sort)

为什么必须批量刷新？

单行插入会让大多数 tile 只有 1 个有效槽：既浪费空间，也失去「摊薄函数调用成本」的意义。

混合投影的关键：投影表同时含标量列与 tile 列时，源码会在标量列值变化时提前切断当前 tile —— 这是按标量分组列聚合的基础。

末尾瓦片：不满 64 行时由 empty_mask 标出未填槽位，聚合与展开都会跳过它们。

03 / 核心原理Vector Aggregate

聚合有两条路径

支持 sum / avg / min / max / count / 方差 / 标准差 / wavg；分组时选哪条路，结果差别很大。
路径 A · 大聚合（直接对 tile 列）
select sum(l_extendedprice * l_discount) as revenue from vops_lineitem where filter( betwixt(l_shipdate, '1996-01-01', '1997-01-01') & betwixt(l_discount, 0.08, 0.1) & (l_quantity < 24) );

聚合函数拿到的是一个 tile，而不是一行；内部循环 64 个槽位、按 filter_mask 跳过不命中位置，一次函数调用产出一批中间值。

sumavgmin / maxcountvariancewavg
路径 B · 分组聚合的两种做法

① map / reduce

能工作，但不自然

把分组 key 与多个同类型聚合表达式交给 VOPS 的 hash table，再用 reduce() 展开结果。

SQL 不自然；聚合表达式类型受 variadic array 限制（必须同类型）。

② 混合投影

README：Q1 通常更快 ★

低基数分组列保留为普通标量列，度量列做成 tile：PostgreSQL 负责 GROUP BY，VOPS 负责每组内部的 tile 聚合。

各司其职：标量语义交给优化器，批处理能力交给扩展。

04 / 定位与效果Comparison

关键不是「谁更快」，而是边界不同

VOPS 保留了 PostgreSQL 内的扩展可试验性，也因此受 executor、planner、heap 与类型系统约束。
维度VOPS 瓦片投影PostgreSQL heap 行表CStore FDW 类列存DuckDB / HyPer 类引擎
主要目标在 PG 内用扩展类型验证向量化 OLAP通用 OLTP 与事务一致性列式读取、压缩、分析扫描从执行器到存储都按向量批量设计
存储单位heap 行里的 tile 字段，每字段 ≤ 64 值一行一个 tuple外部列式分片 / stripecolumn / vector / chunk

读取代价少函数调用、少 tuple deform，仍在 PG executor 内逐行解包与表达式执行只读需要列，压缩收益更强原生批处理，算子融合更充分
事务 / MVCC一致性由刷新策略保证原生 MVCC依 FDW / 外部存储实现通常不是 PG heap MVCC
SQL 兼容tile SQL 有特殊函数；FDW / parse hook 改善最高取决于 FDW 能力系统自身 SQL 方言
适合场景读多写少、批量刷新、过滤聚合、教学验证OLTP、混合负载、频繁更新大宽表列裁剪与压缩分析专业 OLAP、嵌入式分析

一句话结论
真正的向量化数据库，需要从存储、执行、优化器、统计信息到内存管理一起设计；VOPS 是用最小代码量把这条链路压缩成一个可观察的实验 —— 它的价值在机制教学，不在生产替代。

05 / 上手实践Best Practice

三种角色，同一条底线

把 VOPS 当成「读优化投影」，而不是主表。
数据库架构师
先确认业务能否接受刷新延迟，再决定投影维度。
  • 分组列低基数且常出现在 GROUP BY → 优先保留为标量列
  • 度量列与时间过滤列 → 适合做成 tile 列
  • 把源表与投影的一致性责任写进架构约定，而不是默认信任
主表仍是 heap；投影只是读优化副本。
DBA
不要逐行维护投影，用批量窗口刷新保证 tile 填充率。
  • 按时间 / 批次刷新：predicate 限制增量，sort 让同组数据集中
  • 启用自动投影替换前，明确投影滞后风险
  • vops.auto_substitute_projections 默认关闭，正是为避免结果与源表不一致
刷新窗口，就是一致性契约。
业务开发者
写直接 VOPS SQL 时，留意特殊函数与运算符。
  • filter()、betwixt()、& | ! 的语义与优先级不同于标准 SQL
  • 字符串字面量常需显式转换，例如 '1998-12-01'::date
  • 想写普通 SQL，请让 DBA 封装 FDW 或投影替换，但仍需知道哪些能下推
知道哪些谓词能下推，比会写 filter() 更重要。
共同纲领
读多写少 + 批量刷新 + 无 join 的过滤聚合 —— 这才是 tile 能摊薄成本的地方。

05 / 上手实践Pitfalls

八个常见坑

大多数问题不是性能问题，而是把「微型列向量投影」误当成了别的东西。
01 / CONCEPT

把 VOPS 当 pgvector

它不是向量相似搜索扩展，不能解决 embedding ANN 检索问题。

规避 · 先确认需求是批量标量聚合，而非相似度检索
02 / INIT

第一次查询未改写

缺 shared_preload_libraries 或 vops_initialize() 时 parse hook 加载太晚；官方文档指出首次查询可能返回错误结果。

规避 · 预加载 vops，或显式调用 vops_initialize()
03 / SYNC

投影不自动同步

create_projection() 只生成刷新函数，不保证源表与投影强一致。

规避 · 按批次调用生成的 PNAME_refresh()
04 / FILL

tile 填充率太低

单行维护让 64 槽只有少数有效值，空间与性能同时变差。

规避 · 批量窗口刷新，禁止逐行维护投影
05 / SQL

布尔运算符优先级

直接 VOPS SQL 用 & | !，优先级不同于 AND OR NOT，复杂条件要加括号。

规避 · 复杂条件一律加括号，或改用改写后的标准 SQL
06 / INDEX

索引只能粗过滤

first() / last() / low() / high() 只定位候选 tile，精确条件必须复查。

规避 · 候选 tile 内仍执行 filter() 逐槽复查

分组聚合类型限制

06 / 收束Takeaways

带走三句话，留下五个问题

机制的收益与它的边界，往往来自同一个设计决定。
三句话 / TAKEAWAYS
01

一次函数调用处理 64 个值，是把「解释 / 调用成本」摊薄的最小可观察实验。

02

filter_mask 把行级选择性藏进扩展内部 —— 收益与优化器盲区同源。

03

它是读优化投影而非主表：一致性靠刷新策略，不靠 MVCC。

五个扩展问题 / OPEN QUESTIONS
Q1　executor 原生支持 vector batch 后，filter_mask 还需要藏在全局变量里吗？
Q2　tile size 改成 128 / 1024，位图、cache、tuple 大小与 page 局部性怎么变？
Q3　投影一致性更接近物化视图、列存副本，还是 LSM 的 memtable / segment？
Q4　为什么让 PostgreSQL 做 GROUP BY 反而比 reduce(map(...)) 更自然？
Q5　要变成生产级列存，还缺统计信息、压缩、MVCC、WAL、自动刷新还是代价模型？
