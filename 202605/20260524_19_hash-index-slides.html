01 背景 / THE TRADE-OFF

一句话：用顺序能力换等值定位速度

业务里大量访问是 id = ?、token = ?、device_id = ?、session_key = ?。B+Tree 也能做等值查找，但它为顺序、范围、排序和页分裂维护了更多结构。

✓ 它解决的问题
  • 动态集合里的等值定位：给定 key，快速判断在哪个桶，再在桶内确认目标项。
  • 理论等值查找接近 O(1)，桶定位路径短。
  • 适合高基数字段，且查询只关心「是否等于」。
✕ 它不解决的问题
  • 按 key 排序、ORDER BY、MIN/MAX。
  • 范围扫描、「找大于某个 key 的第一条记录」、分页。
  • 前缀匹配、最近邻、模糊匹配。
诱人也危险：hash 不保序；碰撞必须处理；扩容可能造成停顿或写放大；磁盘页与持久内存还会把「桶分裂、overflow、WAL、flush、恢复」变成真正的工程成本。

02 它解决什么问题 / THREE PLACES

同一个 hash，落在三个完全不同的位置

hash 不是一个「索引类型」，而是一种可以放在不同层的手段。看清楚它在哪一层，才不会用错。

把 hash 索引拆成四层

理解一个 hash 索引，不是只看「hash 怎么算」，而是看这四层各自做了什么、以及每一层带来的工程代价。

1
hash functionHASH CODE

常见：32-bit hash code；不保序，不能反推原值
2
bucket addressing桶定位
用 hash code 算出应该去哪个桶
常见：目录、mask、取模、多 hash 函数
3
collision handling冲突处理
一个桶里可能有多个 key，如何共存与查找

05 核心原理 / STATIC HASH

静态 hash 很便宜，直到 N 要变

最朴素的 hash table 是固定桶数：bucket = hash(key) % N。问题不在「hash 怎么算」，而在「桶怎么增长」。

扩容前 · N = 4
h % 4
扩容后 · N = 8
同一个 key，桶号变了
k3 · k4桶号不变 k1 k2 k5 k6 k7 k8需要搬迁 6 / 8 个 key 换桶
把鼠标放到任意 key 上，可以在两个桶数组和右侧表格中同时追踪它的位置。
逐 key 可核验
keyhh%4h%8迁移
为什么这件事很贵
N 一变，大量 key 的桶号都会改变，整表 rehash 很贵。内存里可以接受一次性搬迁；磁盘索引和在线数据库通常不能接受长时间停顿。
数据库课程里最重要的不是「hash 怎么算」，而是「桶怎么增长」。

06 核心原理 / DYNAMIC HASHING · 1

Extendible Hashing：用目录换局部分裂

Fagin · Nievergelt · Pippenger · Strong，ACM TODS 1979。directory 保存 hash 前缀到 bucket 的映射；每个 bucket 有 local depth，directory 有 global depth。

点击分步查看结构变化
DIRECTORY · GLOBAL DEPTH = 2
BUCKETS · LOCAL DEPTH
定位路径清晰
  • 先用 hash 前缀查 directory，再读 bucket。
  • 论文强调唯一键定位最多两次页访问这一类目标。
  • 桶满时只分裂相关 bucket。
DIRECTORY · GLOBAL DEPTH = 2（不变）
BUCKETS · A 分裂为 A0 / A1
局部分裂，目录不翻倍
  • A 的 local depth 1 < global depth 2，可以直接分裂。
  • 00 → A0，01 → A1，两者 local depth 升到 2。
  • 只有 A 里的 key 需要搬迁，B、C 完全不动。
DIRECTORY · GLOBAL DEPTH = 3（翻倍）
BUCKETS · C 分裂为 C0 / C1
代价出现在这里
  • C 的 local depth 已等于 global depth，必须先把 directory 翻倍。
  • 其它桶由两个目录项共享，本身不分裂。
  • directory 可能变大，且它自己也要被并发和恢复机制保护。
判断规则：bucket 的 local depth < global depth → 只分裂该桶；local depth == global depth → 先把 directory 翻倍，再分裂该桶。

07 核心原理 / DYNAMIC HASHING · 2

Linear Hashing：不要目录，按线性顺序分裂

Witold Litwin，VLDB 1980。地址空间动态增长、保持负载稳定，同时避免一次性全表 rehash。

split pointer 逐个推进，而非整表重排
核心机制：维护当前轮次和 split pointer，每次扩容只新增一个桶、按线性顺序分裂一个旧桶，不靠全局目录翻倍。
代价：overflow page、bitmap free space、split-cleanup、WAL 和并发锁顺序等复杂性。
PG 属于这个家族：README 明确可增量扩展，新 bucket 添加时只需 split 一个已有 bucket。

08 核心原理 / SOURCE CODE

PostgreSQL 的三行：mask 决定桶号

_hash_hashkey2bucket() 的核心逻辑只有三步，对应 meta page 上的三个控制字段。

/* src/backend/access/hash/ · _hash_hashkey2bucket() */ bucket = hashkey & highmask; if (bucket > maxbucket) bucket = bucket & lowmask;
hashm_maxbuckethashm_highmaskhashm_lowmask
为什么这样写
先用高位 mask 算出「如果已扩到 2 的幂次」时的桶号；若这个桶号超过了当前实际存在的 maxbucket，说明该桶还没被创建，用低位 mask 折回已有桶。于是每新增一个桶，只有落到新桶号的那部分 tuple 需要搬走。
避免了全局目录，但引入 overflow page、bitmap free space、split-cleanup、WAL 与并发锁顺序复杂性。

Bloom filter 的 KeyMayMatch() 只回答「可能存在 / 一定不存在」；block cache 的 HandleTable 用 hash + 链表定位缓存块。两者都在减少无效读和定位缓存，不承担主数据定位。
常见坑：把 Bloom filter 当索引。它是读路径过滤器，可 false positive，不能单独返回数据。
主数据路径为什么仍然有序
LSM 需要范围扫描和 compaction，因此主数据路径必须保持有序。LevelDB 把 hash 放在「过滤无效读」和「定位缓存块」这两层，恰好是它不要求顺序的地方。

13 横向对照 / GROWTH STRATEGIES

四条扩容路线，各自让了什么步

图 3 重绘：它们都在解决同一个问题 —— 避免「一次性全表 rehash」，或者干脆把 hash 放对层。

Extendible Hashing
用目录换局部分裂
局部：只分裂满的桶；local depth == global depth 时 directory 翻倍。
代价：目录变大，且目录本身要被并发与恢复机制保护。
Linear Hashing / PG
mask + 线性分裂
无全局目录：维护轮次与 split pointer，逐个桶推进，保持负载稳定。
代价：overflow page、bitmap free space、split-cleanup、WAL、锁顺序。
Redis dict
双表渐进 rehash
把停顿摊薄：搬迁成本分摊到每次普通读写，适配单线程事件循环。
代价：内存里同时存在两张表；多线程内核需重新设计锁与可见性。
LevelDB
hash 不在有序主路径
放对层：filter 随 SSTable 构建，cache 用 resize；主路径保留有序结构。
代价：Bloom 是概率判断，不精确；filter 不原地删，cache 靠 evict。
共同点：都在避免「一次性全表 rehash」或避免让 hash 承担它做不到的顺序职责。区别只在 —— 谁来记扩容元数据、谁承担搬迁成本。

14 前沿 / PERSISTENT MEMORY

持久内存：写放大成为第一约束

在 PM / NVM 上，问题换了维度：不再只看查找次数，而是每次更新需要多少 cache line flush、fence、日志或 CoW。

一次结构修改要穿过的层
传统磁盘 hash 关心页访问与 WAL；PM hash 还要把每次结构修改压缩到少量可证明的持久写。
WORT / WOART · FAST 2017
failure-atomic write 是核心约束
论文讨论 radix tree 在 persistent memory 上为何要以失败原子写为核心约束；写放大小于结构复杂度本身更关键。
HMEH / OP-HMEH · JSA 2022
目录放 DRAM，bucket 放 NVM
radix-tree-assisted dynamic hashing：把 bucket 放在 NVM、目录放 DRAM，用持久 radix tree 支撑崩溃后的目录恢复。
Dash · PVLDB 2020
真实 Optane DCPMM 上的可扩展方案
把 extendible hashing 与 linear hashing 适配为可扩展、动态增长、可即时恢复的 PM hash 方案，并报告高负载因子与恢复时间目标。
未来的 hash 索引不只是「桶更多、冲突更少」：在 PM / NVM / RDMA / 分布式 KV 场景里，扩容元数据、桶迁移、恢复路径和并发协议，往往比单次 hash 计算更重要。

17 实操 DEMO / RUN IT YOURSELF

最小验证脚本：重点比较计划与 buffer

诚实声明：本文未在本机启动 PostgreSQL 实例执行，因此不提供伪造输出。请在自己的环境里运行下面脚本。
CREATE TABLE hash_demo ( id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, uid text NOT NULL, payload text, created_at timestamptz DEFAULT now() ); INSERT INTO hash_demo(uid, payload) SELECT md5(i::text), repeat('x', 80) FROM generate_series(1, 1000000) AS s(i); CREATE INDEX hash_demo_uid_btree_idx ON hash_demo(uid); CREATE INDEX hash_demo_uid_hash_idx ON hash_demo USING hash(uid); ANALYZE hash_demo; -- 等值查询：观察 planner 选择哪个索引，以及 heap 访问量 EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM hash_demo WHERE uid = md5('424242'); -- 范围查询：hash index 不适用，B-tree 才有顺序能力 EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM hash_demo WHERE uid >= 'a' AND uid < 'b'; -- 查看 index 大小 SELECT relname, pg_size_pretty(pg_relation_size(oid)) AS size FROM pg_class WHERE relname IN ('hash_demo_uid_btree_idx', 'hash_demo_uid_hash_idx');
验证时不要只看耗时

  • Buffers: shared hit/read 是否降低
  • 返回行数是否很小
  • 插入和更新后的 index 膨胀是否可接受
  • REINDEX、VACUUM、备份恢复窗口是否符合运维约束

18 最佳实践 / BY ROLE

落地：三种角色各自该做什么

同一条结论，对不同角色意味着完全不同的动作。

A
数据库架构师
把 hash index 作为「等值专用索引」评估，不要作为默认索引。
建模阶段先问：未来是否需要范围、排序、前缀、分页、唯一性、外键辅助访问？只要答案可能是「需要」，B-tree 往往更稳。
选型建模默认索引
B
DBA
重点监控 index size、idx_scan、idx_tup_read、idx_tup_fetch、VACUUM 状态和写入延迟。
删除大量数据后若 hash index 明显膨胀，单靠 VACUUM 不会减少 bucket 数，需要考虑 REINDEX CONCURRENTLY。
监控膨胀REINDEX
C
业务开发者
不要因为「hash 是 O(1)」就盲建。
低基数字段如 status、type、gender 不适合；长文本等值查询可以测试 hash index，但要和 B-tree、表达式索引、规范化字段 一起比较。
基数长文本对比测试
决策顺序：先问「未来要不要顺序能力」→ 再看字段选择性与 key 宽度 → 最后用 EXPLAIN (ANALYZE, BUFFERS) 与长期 idx_scan 决定是否保留。

19 适用边界 / DECISION GUIDE

一边是等值，一边是顺序

✓ 适合
高基数字段的等值查询
key 分布分散，桶内冲突少
查询只关心是否等于某个 key
完全不需要顺序
key 很宽，且能接受回表重检
hash code 存储可显著缩小索引项
内存字典、缓存、过滤器
不承担范围扫描的结构
✕ 不适合
范围、排序、ORDER BY、MIN/MAX、前缀
hash 不保序，能力边界之外
需要唯一性约束的主索引路径
PostgreSQL hash index 不能替代 unique B-tree
低选择性字段
命中行太多时瓶颈不在索引定位
删除/更新极多且无法安排 REINDEX
bucket 数只增不减
需要稳定最坏情况延迟
且无法控制碰撞或扩容时机
一句话：凡是 B-tree 能表达的顺序需求，都不要指望 hash；只有把需求收敛到「高基数 + 纯等值」，才轮到 hash 上场。

20 常见坑 / PITFALLS

六个最常见的误解

1
当成 B-tree 的更快版本
这是错误模型：hash index 没有顺序，不支持范围。
2
忽略重检成本
只存 hash code、不存原始 key；碰撞和 MVCC 可见性最终还要回到 heap。
3
忽略扩容和 overflow
桶链过长会把一次查找变成多个页访问；split 时还会产生 WAL 和锁竞争。
4
删除后期待自动缩小
overflow page 可复用，但 bucket 数不缩，只能 REINDEX 缩小。
5
把 Bloom filter 当索引
它是读路径过滤器，可以 false positive，不能单独返回数据。
6
只谈平均 O(1)
工程系统真正关心 tail latency、恢复路径、并发、缓存局部性、写放大和可观测性。
共同点：这六个坑，都是把 hash 的「平均情况」误当成了「工程约束」—— 能力边界、重检成本、扩容代价与恢复路径，一个都不能省。

21 收尾 / TAKEAWAYS

带走这三句话

01
hash 牺牲顺序，
换等值定位速度。
它不解决范围、排序、前缀。
02
真正难的不是 hash 怎么算，
是桶怎么增长、怎么恢复。
还有写放大与并发协议。
03
选不选它，看 workload 和
EXPLAIN (ANALYZE, BUFFERS)。
不看 O(1) 的口号。
延伸思考 · 5 个开放问题
  • 改成 extendible hashing，怎样保护 directory 的并发和 WAL 恢复？
  • Redis 渐进 rehash 为何适合单线程事件循环？换成多线程内核会新增哪些锁与可见性问题？
  • Cuckoo 查找路径短但插入可能搬迁多个元素，它适合磁盘页索引吗？
  • Hopscotch 改善 cache locality 但要求邻域内移动元素，适合 PM 吗？flush/fence 会放大到哪里？
  • 同时有 B-tree 和 hash index，怎样用 pg_stat_user_indexes 证明它值得保留？
这些问题没有唯一答案 —— 答案取决于你愿意牺牲顺序、精确性，还是牺牲写放大与恢复复杂度。
