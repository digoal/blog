背景 / 问题定义

一个工程矛盾，三条技术路线

AGE 解决的是「在 PostgreSQL 内部承载属性图」，不是「把 PostgreSQL 改造成原生图存储引擎」。

想业务要表达关系

人、设备、账号、交易、权限、知识实体之间的关系，用属性图（vertex / edge / label / properties）建模最自然。

不想团队不愿迁移整套体系

事务、权限、备份、SQL 生态、扩展生态、运维体系，全部迁到一套新的图数据库代价太高。

路线 A

纯关系模型

自建 vertex / edge / vertex_property / edge_property 表，用 SQL join 与递归 CTE 查询。

  • 优：透明、可控
  • 缺：大量图语义要手写
路线 B

独立图数据库

Neo4j、JanusGraph、TigerGraph 等，图模型与遍历能力完整。

  • 优：原生图能力
  • 缺：多一套事务/备份/权限/同步
路线 C · AGE

关系-图混合

在关系库里增加图类型、图 catalog、图查询语言与索引；继承 AgensGraph 思路，以 PostgreSQL extension 落地。

  • 优：接入成本低、复用 PG 能力
核心改写 图对象管理 → PostgreSQL 对象管理：建 graph → 建 schema + catalog 行；建 label → 建物理表 + sequence；插顶点/边 → 插 heap tuple + 维护索引；属性用 agtype 保存。 有代价
代价：邻接关系不是 compressed adjacency list，label 不是轻量 tag 而是 relation；多跳路径、属性过滤、统计信息与索引选择都受 PostgreSQL 表结构和优化器约束。

二、它是什么

五层映射：图对象全部落到 PostgreSQL 对象

图查询语言看到的是 label；存储层看到的是 catalog 行、schema、普通表、sequence 和索引。

默认父表

建 graph 后自动创建 _ag_label_vertex 与 _ag_label_edge，作为后续顶点/边 label 的父表。

catalog 记录物理指针

ag_label.relation 保存物理表 OID，ag_label.seq_name 保存生成 graphid 的 sequence 名称。

两种视角

Cypher 看到 label 与属性；PostgreSQL 优化器看到 relation、attribute、operator class、统计信息与可用索引。

官方文档确认：每个 graph 生成一个 namespace，其下先建两张默认父表；create_vlabel 再生成 graph."Person" 这样的物理表。

三、核心原理 · 1 / 7

ag_graph 与 ag_label 是图对象的根

扩展 SQL sql/age_main.sql 创建两张核心 catalog 表；label 编号是存储格式的一部分，不只是属性里的名字。

sql/age_main.sql · 核心 catalog 定义（节选）
CREATE TABLE ag_graph (
  graphid   oid NOT NULL,
  name      name NOT NULL,
  namespace regnamespace NOT NULL
);
CREATE TABLE ag_label (
  name     name NOT NULL,
  graph    oid NOT NULL,
  id       label_id,
  kind     label_kind,
  relation regclass NOT NULL,
  seq_name name NOT NULL,
  CONSTRAINT fk_graph_oid
    FOREIGN KEY(graph)
    REFERENCES ag_graph(graphid)
);
label_id 是 1..65535 的 domain；label_kind 只能是 'v' 或 'e'。

三、核心原理 · 3 / 7

graphid：64 位里塞进 label 与局部序号

typedef int64 graphid；INTERNALLENGTH = 8、PASSEDBYVALUE、STORAGE = plain。不是 UUID，也不是全局 sequence 直接生成的 bigint。

动手算一个 graphid　互动演示

用 64 位整数计算，并回读验证两个位段：gid >> 48 与 gid & mask。

工程含义

  • 一个 ID 同时携带「属于哪个 label」与「该 label 内第几个 entry」。
  • B-tree 排序先受高位 label_id 影响，同一 label 的实体天然聚在一个区间。
  • label 上限被固定在 16 bit；比较与索引复用 64 位整数语义。
比较运算符 =, <>, <, >, <=, >= + 默认 B-tree opclass graphid_ops + hash opclass graphid_ops_hash（高低部分异或得 32 位整数）。
来源：附件 §三-3；Apache AGE DeepWiki / graphid.h（已核对 16+48 位与取值范围）
三、核心原理 · 4 / 7

默认索引只解决「身份」与「边端点」

属性过滤不是自动魔法：默认 B-tree 让点查和一跳邻接有基础路径，其余要靠 GIN、表达式索引或拆列。

区分父表与子 label：默认顶点父表和普通顶点 label 都在 id 上建 unique B-tree；默认边父表列定义含 id graphid PRIMARY KEY；普通边 label 显式在 start_id / end_id 上建非唯一 B-tree，该路径没有额外为子 edge label 的 id 调用 create_index_on_column()。执行层 entity_exists() 也优先找 id 上可用的 B-tree，没有才 fallback 到 heap scan。
属性查询要自己补路：properties @> ... 或键存在查询需另建 GIN / 表达式索引；强约束、高频过滤字段拆成关系列往往更稳。

三、核心原理 · 5 / 7

agtype：JSON-like 外观，自定义二进制容器

顶层是 PostgreSQL varlena datum，不是简单文本 JSON；还扩展出 AGE 自己的顶点 / 边 / 路径类型。

每个子项由 agtentry 描述；AGE 为 vertex / edge 定义了固定字段位置，可直接访问字段而不必每次做一般对象查找。

扩展类型 不只是 JSON 的 6 种值

AGTV_VERTEX、AGTV_EDGE、AGTV_PATH 是 AGE 扩展出来的图值类型。

固定字段顺序 · vertex

id , label , properties

固定字段顺序 · edge

id , label , end_id , start_id , properties

为什么要看二进制布局：它决定了属性能否被索引、统计信息能否描述属性分布，以及 GIN 抽取 token 时能看到什么。

三、核心原理 · 7 / 7

Cypher 最终要落到 PostgreSQL 的关系访问

执行器构造 tuple slot，调用 table_tuple_insert()、ExecInsertIndexTuples()、table_tuple_update() 等原生路径。

关键挑战不是语法翻译本身，而是下面 5 个问题

① label 选择性

估算是否准确，决定扫哪张表。

② 端点过滤

start_id/end_id 能否尽早发生。

③ 属性过滤

GIN、表达式索引、顺序扫描之间怎么选。

④ 多跳扩展

是否造成路径组合爆炸。

⑤ 统计信息

能否描述 agtype 内部属性分布。

这与「Translating Cypher to SQL inside Relational Database Engines」「Cost-Based Query Optimization for Relational-Graph Hybrid Systems」等论文面对的是同一类问题：图 pattern 被拆成表扫描、索引扫描、连接、过滤和投影。

五、效果如何

不要把 AGE 理解成「装了 extension，图查询就天然快」

效果取决于访问路径是否能被 PostgreSQL 高效执行；收益与代价来自同一个设计选择。

收益 复用了 PostgreSQL 的整套底座

1事务、权限、备份、WAL、MVCC、SQL、扩展生态全部复用。
2graph / label / properties 能与普通关系表一起查询、管理和迁移。
3graphid 是 8 字节 pass-by-value，适合 B-tree 等值、排序和 join key。
4start_id / end_id 默认有 B-tree，一跳邻接查询有基础索引路径。
5agtype 可以用 GIN 做属性包含和键存在过滤。

代价 物理模型仍然是关系表

1每个 label 一张物理表，relation、catalog、统计信息与 DDL 成本上升。
2边查询本质是按 start_id / end_id 扫边表，不是邻接链表跳转。
3agtype 的灵活性削弱列统计、约束与类型检查。
4GIN 需要 recheck，写入、更新与 VACUUM 成本不可忽略。
5多跳路径快速放大中间结果，必须控制 label、方向、深度与过滤。
判断方法：把「图查询」翻译成「访问路径」——看它落到哪张 label 表、哪个索引、过滤能否尽早发生、中间结果有多大。

SET search_path = ag_catalog, "$user", public;

SELECT create_graph('age_foundation');
SELECT create_vlabel('age_foundation', 'Person');
SELECT create_elabel('age_foundation', 'Knows');

SELECT * FROM cypher('age_foundation', $$
  CREATE (:Person {name: 'Alice', city: 'Hangzhou'}),
         (:Person {name: 'Bob', city: 'Shanghai'})
$$) AS (v agtype);

SELECT * FROM cypher('age_foundation', $$
  MATCH (a:Person), (b:Person)
  WHERE a.name = 'Alice' AND b.name = 'Bob'
  CREATE (a)-[:Knows {since: 2026}]->(b)
$$) AS (e agtype);
SELECT graphid, name, namespace
FROM ag_catalog.ag_graph
WHERE name = 'age_foundation';

SELECT name, graph, id, kind, relation, seq_name
FROM ag_catalog.ag_label
WHERE graph = (
  SELECT graphid FROM ag_catalog.ag_graph
  WHERE name = 'age_foundation'
)
ORDER BY id;

-- 重点：一个 graph 对应一个 namespace，
-- 每个 label 对应 relation + seq_name
SELECT n.nspname AS schema_name,
       c.relname AS table_name,
       a.attnum, a.attname,
       format_type(a.atttypid, a.atttypmod) AS data_type
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
JOIN pg_attribute a ON a.attrelid = c.oid
WHERE n.nspname = 'age_foundation'
  AND c.relkind = 'r'
  AND a.attnum > 0
  AND NOT a.attisdropped
ORDER BY c.relname, a.attnum;

SELECT tablename, indexname, indexdef
FROM pg_indexes
WHERE schemaname = 'age_foundation'
ORDER BY tablename, indexname;
CREATE INDEX person_properties_gin_idx
ON age_foundation."Person"
USING gin (properties);

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM age_foundation."Person"
WHERE properties @> '{"city": "Hangzhou"}'::agtype;

七、最佳实践

索引设计要从访问路径反推，而不是从「属性很多」反推

先问查询主要问什么：身份、邻接、属性、路径还是分析；再决定用默认索引、GIN、表达式索引或关系化。

七、最佳实践 · 分角色清单

架构师 / DBA / 开发者，各自守住哪条线

同一套物理结构，不同角色的动作完全不同；把职责分开，才能避免「出了问题没人看得见」。

架构师

  • 把 graph 当成 PostgreSQL schema 级对象规划：graph 数量、label 数量、权限边界、备份恢复、迁移策略提前定。
  • 不要把所有实体塞进一个大 label，也不要把每个业务细分都建成独立 label；label 应对应稳定、查询路径明显不同的实体/关系类型。
  • 对强约束、强统计、强 join 字段，优先考虑关系列或旁路关系表。

DBA

  • 定期检查 ag_catalog.ag_label、pg_class、pg_indexes，确认 label 表与索引数量没有失控。
  • 对大 label 表执行 ANALYZE，尤其是批量导入后；没有统计信息，优化器很难选对 join 和 scan。
  • 监控 GIN 索引体积、pending list、VACUUM 压力和 recheck 比例。
  • 大量删除后关注表与索引膨胀：空间回收仍依赖 VACUUM、REINDEX、CLUSTER 或重写。

业务开发者

  • 先限定 label、方向和深度：优先 MATCH (a:Person)-[:Knows]->(b:Person)，少写无界 MATCH (a)-[r]->(b)。
  • 不要默认相信 n.name = 'Alice' 一定有索引；确认它落到哪张表、哪个表达式、哪个 operator。
  • 高频路径保留可观测 SQL：用 EXPLAIN、catalog 查询和 pg_stat_user_indexes 证明索引有价值。
  • 对多跳查询设置业务上限。
三者的共同前提：AGE 的底层就是 PostgreSQL 的表和索引。任何性能问题，最终都要回到 relation、index、stats 与 EXPLAIN 上定位。

八、适合与不适合场景

把 workload 放在一条刻度上看

AGE 的舒适区在 PostgreSQL 生态内的中等规模、浅层图查询；越往深度遍历与全图分析走，边界越明显。

适合

  • 已以 PostgreSQL 为核心系统，希望补充图查询能力。
  • 图规模中等，主要一跳、两跳查询，且能用 label、方向、属性过滤收窄候选集。
  • 需要 SQL + Cypher 混合分析：关系主数据、JSON 属性、向量检索、时序数据与图关系共存于 PG。
  • 希望复用 PostgreSQL 权限、事务、备份、审计、扩展生态。

不适合

  • 深度路径遍历、全图算法、实时推荐图、超大规模动态图分析是主 workload。
  • label 与属性极度动态，relation 数量、索引数量与统计信息无法管理。
  • 每次都要在 agtype 深层属性上做复杂过滤，却不愿拆列或设计表达式索引。
  • 需要图引擎级邻接压缩、路径缓存、分布式图计算或专用 traversal optimizer。
判断落点：查询深度、候选集能否收窄、属性是否需要强 schema、是否还要 PG 生态之外的图能力。

九、常见坑

8 个高频误用（点击卡片查看解释）

绝大多数坑都不是「AGE 的 bug」，而是把关系-图混合模型误当成了别的模型。

坑 1

当成黑盒图数据库

性能问题要回到 relation / index / stats

坑 2

label 设计过细

每加一个就多表、序列、catalog 行、索引

坑 3

label 设计过粗

大表查询严重依赖 properties 过滤

坑 4

把 GIN 当精确匹配

token 过滤，复杂结构仍需 recheck

坑 5

忽略边的方向

有向边应明确方向，避免两边都扫

坑 6

把灵活属性当强 schema

约束 / join / 排序 / 范围应考虑关系化

坑 7

批量导入后不 ANALYZE

优化器估不准 label 表与属性选择性

坑 8

只看查询延迟

每个新索引都增加写入与维护成本

这 8 条对应同一条主线：图查询的代价，由 PostgreSQL 的物理对象与执行计划决定。

5 个扩展问题

  • 更强的多跳 cost model，统计信息应记在 label 级、edge 级，还是 (start_label, edge_label, end_label) 级？
  • graphid 高 16 bit 是 label id，对跨 label 排序、范围扫描和分区有什么影响？
  • 属性从低频过滤变成核心业务字段时，何时从 agtype 迁移成普通列？
  • PostgreSQL inheritance 表达 label 层次，在权限、统计、约束与查询继承语义上有哪些运维风险？
  • GIN 对 agtype 设置 recheck 的原因是什么？能否设计更结构化的 opclass 减少 recheck？
