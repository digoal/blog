01 它解决什么问题

三种传统做法，各有各的代价

「存储结构」不只是一张表怎么落盘，还包括数据离开数据库以后，如何继续被正确、低成本、可演进地读取。

PAIN 01

JSON 太松

字段名重复写入，数值类型不够明确；schema 演进多靠应用约定，坏数据容易进入链路深处才暴露。

PAIN 02

纯二进制太硬

自定义协议可以很快，但跨语言、调试、兼容、长期维护都会变成隐性成本。

PAIN 03

列式文件不适合所有阶段

Parquet/ORC 适合分析扫描，但事件流、行级交换、RPC 和小批量 append 不是它们的强项。

AVRO 把问题转化为 ↓
STEP 1 · 逻辑层
先用 JSON schema 定义记录结构
{"type":"record","fields":[…]}
→
STEP 2 · 编码层
用 schema 指导二进制编码
字段名 / 类型 / 分隔符都不写入
→
STEP 3 · 文件层
写进对象容器文件 OCF
writer schema + codec + block 边界
代价同样明确：Avro 不是天然适合任意字段投影的列式格式；二进制 payload 离开 schema 不能正确解释；schema 注册、兼容策略与治理流程必须成为数据平台的一部分。

02 它是什么

三个层次：schema → binary → OCF

把逻辑契约、字节编码和文件容器分开看，就不会把 Avro 误当成「压缩版 JSON」。

LOGIC
逻辑层

schema · 用 JSON 表达

支持 primitive、record、enum、array、map、union、fixed 与 logical type。字段 default 主要服务于读取旧数据时的 schema resolution，不代表写入时可以省略字段。

ENCODING
编码层

binary encoding · 按声明顺序

记录字段按 schema 声明顺序深度优先写入；字段名、类型名、分隔符都不进入二进制 payload。

FILE
文件层

Object Container File · OCF

自描述文件格式：header 带 writer schema，记录按 block 组织，适合写成可切分、可压缩、可追加读取的文件。

它不是什么
✕  不是「压缩版 JSON」
✕  不是列式存储
✕  不替代数据库事务存储
✕  schema 是 JSON，数据编码不是

03 编码规则

九条规则，理解「行式但并不粗糙」

schema 已经知道字段顺序和类型，字节流就不必重复写这些信息。

null · 0 字节

不写任何内容，只靠 schema 知道这里有个 null。

boolean · 1 字节

单字节表示 true / false。

int / long · 变长 zig-zag

小整数占用更少字节；64 → 80 01，-64 → 7f。

float / double

按 IEEE 754 bit 表示后用 little-endian 写入。

bytes / string

先写长度，再写原始字节；string 字节为 UTF-8。

record · 顺序串接

按字段声明顺序，深度优先逐个编码。

enum · 零基序号

写 symbol 在 schema 中的序号，不写字符串。

union · 序号 + 值

先写分支序号，再写该分支的值。

array / map · block

用 block 表示，负 count 后可跟 block size，允许跳过整段集合内容。

但它仍然不是列式：行内用 schema 消除了字段名重复、用变长整数降低常见小整数成本、用集合 block 支持跳过；如果只查宽记录中的 2 个字段，通用 Avro OCF 不能像 Parquet 一样只读取这 2 列的 page。

03 CODEC · BLOCK SIZE

压缩的是 block，不是每条记录

规范要求实现必须支持 null 和 deflate；拖动右侧滑块，观察 block 大小如何同时改变四件事。

必需的 CODEC
nulldeflate

可选：bzip2 · snappy · xz · zstandard。本地 Java CodecFactory 默认注册了全部六种。

粒度带来的三个结果
① block 内重复模式更多 → 压缩比更好
② 读取一条记录，通常要先解压整个 block
③ block 大小影响延迟、内存峰值、切分粒度与恢复边界

04 效果如何

别把 Avro 的效果只理解成「压缩率」

收益分五层，代价同样具体 —— 架构决策要一起算。

收益 · 5 层
01
编码体积 不重复写字段名，整数用变长 zig-zag
02
解析成本 不做通用 JSON token 解析，按 schema 走确定路径
03
契约治理 writer/reader schema、canonical form、fingerprint、resolution
04
文件切分 block size、object count、sync marker 支持跳过与损坏检测
05
跨语言 多语言实现共同遵循同一数据文件格式
代价 · 5 条
01
列裁剪弱 block data 是完整记录，不是按列分 page
02
schema 是硬依赖 没有 writer schema，payload 很难安全解读
03
延迟放大 只取少量记录也可能要解压整个 block
04
压缩与切分要平衡 大 block 压缩率好，小 block 延迟与切分好
05
演进不是随意改 缺 default、类型不匹配、union 不兼容都是读时错误
评价方法论（Viotti & Kinderkhedia）：比较序列化格式要区分 schema-driven 与 schema-less，并把数据形状、冗余度、压缩、可复现实验条件放进评价模型 —— 不应只拿「Avro 比 JSON 快多少」的孤立数字做架构决策。

05 实操 DEMO

用 Python 写一个最小 OCF，再读回来

点「运行」，逐行打印本地 Apache Avro Python 源码实验的真实输出。（下方为节选关键行）

demo.py · PYTHONPATH=avro/lang/py
import io, json, avro.schema
from avro.datafile import DataFileWriter, DataFileReader, SYNC_SIZE
from avro.io import DatumWriter, DatumReader
schema = avro.schema.parse(json.dumps({
  "type":"record", "name":"event", "fields":[
    {"name":"id","type":"long"}, {"name":"user","type":"string"},
    {"name":"amount","type":"double"}]}))
buf = io.BytesIO()
w = DataFileWriter(buf, DatumWriter(), schema, codec="null")
w.append({"id":1,"user":"alice","amount":12.5})
w.append({"id":2,"user":"bob","amount":7.0}); w.flush()
raw = buf.getvalue(); print("bytes", len(raw))
print("magic_hex", raw[:4].hex())
print("magic_ascii", raw[:3].decode(), raw[3]); print("sync_size", SYNC_SIZE)
buf.seek(0); r = DataFileReader(buf, DatumReader())
print("codec", r.codec); print("schema_name", avro.schema.parse(r.schema).name)
print("records", list(r))

06 最佳实践

不同角色，关注点完全不同

把 Avro 放进正确的一层，比调参数重要得多。

数据库架构师

把它放在数据契约层

业务事件、CDC、实时计算中间层、跨语言交换适合 Avro；面向 BI 的宽表明细与聚合扫描优先评估 Parquet/ORC；湖仓表级快照、分区演进和 ACID 提交交给 Iceberg / Delta / Hudi。

DBA / 数据平台工程师

治理 schema lifecycle

建立 schema registry 或等价流程并强制兼容检查；新增字段给 default；禁止无评审地改 union 分支、字段类型和语义；把 block 大小、压缩比、读取延迟、任务切分数作为观测指标。

业务开发者

别把 Avro 当动态 JSON 用

字段名、类型、默认值、nullable 写法都属于接口契约。nullable 显式写成 ["null","string"]，并注意 default 必须匹配 union 的第一个可用分支；写入前校验，读取时保留 writer schema。

数据湖使用者

分层落地，各司其职

Avro 适合 landing zone / streaming bronze 层的行事件；进入大规模 ad hoc 分析层后通常转为 Parquet/ORC，并由 Iceberg / Delta / Hudi 管理表元数据、快照、分区和演进。

一句话：Avro 是「序列化 + 文件格式」，不是「压缩格式」，也不是「表格式」；把它放在数据契约层看，选型就不会错位。

06 场景边界

什么时候用，什么时候别用

判断的关键词是：行事件、写入频繁、schema 需要长期演进 —— 而不是「所有数据都该换成 Avro」。

✓ 适合
✓Kafka、Pulsar、Flink、Spark Streaming 中的结构化事件
✓需要长期 schema evolution 的日志、CDC、业务事实流
✓Hadoop / Spark 可按文件切分读取的批量行式数据
✓多语言系统之间共享同一数据契约
✓写入频繁、读取模式还不固定的原始明细层
✕ 不适合
✕大宽表 OLAP：只读少数列，高度依赖列裁剪、统计跳过与向量化扫描
✕没有 schema 治理流程、字段经常随意变动的团队
✕需要人直接阅读和手工编辑的配置或调试文件
✕单条低延迟 RPC 已全面使用 gRPC / Protobuf 的服务边界
✕需要表级事务、快照隔离、分区演进和元数据管理的湖仓表

06 常见坑

八个最容易踩的坑

前四个最常导致「历史数据读不出来」，其中第 1 条最严重。

01
只保存 binary，不保存 writer schema 最严重
离开 writer schema，二进制 payload 不能可靠读取
02
把 default 当成写入时可选
default 用于读取缺失字段；写入仍要按 writer schema 编码
03
随意调整 union
写的是分支序号 + 值；分支匹配失败直接报错
04
以为 Avro 自动适合分析查询
OCF 是行式 block 文件，宽表列裁剪不是强项
05
block 设置只看压缩比
sync interval 还影响内存、延迟、split 粒度与失败恢复
06
忽略 codec 兼容
规范只要求 null / deflate；跨平台前确认消费者支持
07
把 schema evolution 当代码重构
改名、改类型、删枚举、改默认值都要先跑兼容验证
08
把 Iceberg 和 Avro 当同层替代
Iceberg 管表与元数据，可以管理 Avro 数据文件
共同根因：把「schema 是硬依赖」这件事忘了。只要把 schema 注册、兼容验证和 writer schema 留存做成平台能力，前四个坑基本可以系统性消除。

07 扩展问题

带走三个问题

这些问题的答案，决定了你的数据平台把 schema 放在哪一层。

Q1

writer schema 应该放在哪里？

一条事件在 Kafka 保留 30 天、在湖仓保留 3 年 —— 放消息里、注册中心里，还是 OCF 文件头里？三种方案的故障边界分别是什么？

Q2

「按名称匹配」与「按声明顺序写入」矛盾吗？

一个说的是编码时的字节布局，一个说的是 resolution 时的字段映射 —— 中间靠 writer schema 连接。

Q3

int → string 为什么不允许自动兼容？

规范把兼容边界划在「语义不变的类型提升」上。它保护的到底是历史数据，还是下游的计算语义？
