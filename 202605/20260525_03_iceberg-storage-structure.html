01 — 背景

同样是 Parquet，为什么“目录 + 文件”
会很快变成不可控资产

Parquet 只回答“一个文件内部怎么编码”。真正的表还要回答：哪些文件属于当前版本、并发怎么写、分区规则变了怎么办、删一行要不要重写。

01
表状态不能靠目录推断
Hive 风格分区把物理布局暴露给用户：查询要知道 dt=…，写入端要正确造目录。规则一变，新旧目录共存，查询、迁移、权限、清理同时变复杂。
02
并发不能靠“最后写入 wins”
分析、流式、回填任务同时写表。没有快照和原子提交，读者看到半成品，写者互相覆盖对方新增的文件。
03
优化器不能扫全量文件清单
对象存储上 list 很贵，千万级文件更不能逐个打开读 footer。规划需要一层更轻的索引，先靠分区摘要、min/max、null count 跳过文件。
04
演进不能每次重写全表
schema、partition spec、sort order、delete 方式都会变。每次演进都迁一张新表，成本与风险都太高。
目录即真相 · 失控
⇄
代价互换：你获得 ACID-like 表语义与多引擎互操作，但必须维护 metadata tree、小文件、snapshot 保留、delete files、manifest 布局、catalog 一致性。

02 — 一句话原理

把“表”从文件集合，变成一棵带事务语义的树

Iceberg 不是文件格式，而是 open table format。行数据仍写在 Parquet / ORC / Avro 里，另有自己的表元数据定义“哪些文件在当前版本有效、怎么裁剪和合并读取”。

不可变
data file 写完不改。删除不是原地修改行，而是另写一份 delete file 作为补丁。
可版本化
每次提交产生新 metadata.json 与新 snapshot，父子链接成链，历史版本天然存在。
单点提交
catalog 里只有一个指针是“活”的。它换成谁，读者就看到哪个版本——这就是事务边界。

schema 与 partition spec 都用 ID 管，不用名字和位置

数据演进里最怕两件事：名字被复用、位置被移动。两者都会让旧文件在新 schema 下被“合理地”错误解释——而且不会报错。

✔ 语义被锚住
删除列不改变其他列的 id；新增列在旧文件里读作 null。旧数据不必重写，也不会被错误解释。
同一思路延伸到 spec id：每份 manifest 记住自己属于哪一代 partition spec，规划时按 spec 分别推导过滤条件。

04 — 核心原理 · 物理数据独立性

一句 SQL 投影到三代分区规则上

分区值由 Iceberg 根据业务列与 transform 生成。查询只写业务列，规划器按每个 manifest 的 spec id 分别推导隐藏分区谓词——旧数据保留旧 spec，新数据用新 spec。

SELECT*FROMevents WHERE event_time >= TIMESTAMP '2026-05-26 09:00:00' AND user_id = 104 没有 dt= · 没有 bucket= · 没有目录名
spec 0spec 1spec 2
→
当前表里三代 spec 的 manifest 同时存在；规划器按每份 manifest 的 spec id 分别推导，最后合并成一个 FileScanTask 列表。旧文件不必重写。
同一个谓词，三代 spec 各自算出自己的命中集合。代价是规划器必须同时理解多个 spec，manifest 也必须按 spec 保存对应的 partition struct。

04 — 核心原理 · 图 4 提交隔离

四个步骤，一个 compare-and-swap

写者把所有物理文件先写好，最后只做一件事：如果 catalog 里的指针还是我的 base，就换成我的；否则失败、重读、重试。

两个写者都基于同一个 base 开始。谁先提交，谁赢；另一个不会覆盖，而是基于新版本重建。

05 — 横向对比

都是“湖上建表”，边界完全不同

同样先用元数据少读数据，差别在于：谁拥有这套结构、开放到什么程度、优化闭环能做多深。

行级删除position / equality delete，v3 DV通常重写文件或外部约定deletion vectors / rewriteMOR / COW 多种路径内部微分区维护
事务边界catalog 指针原子替换弱，依赖引擎约定事务日志提交timeline commit专有服务托管
主要代价metadata 与维护策略必须治理演进、并发、清理困难协议与实现绑定度较高模型复杂，读写路径多专有系统，物理控制权低
与 Snowflake 的共同点： 两者都在做“先用元数据少读数据”。Snowflake 用微分区 min/max、distinct、重叠深度；Iceberg 用 manifest / file metrics。
边界差异： Iceberg 把结构开放给多引擎，优化深度取决于引擎实现与表维护质量；Snowflake 把存储、统计、优化器和执行器收在一个托管系统里，闭环更强，但互操作边界不同。

07 — 适合与不适合

它是一张分析表，不是一个数据库

判断标准只有一条：你的读写形态是否落在这条轴的分析端。

✓ 适合
PB 级或长期增长的分析型事实表，主要 append，偶尔 merge / update / delete。
多引擎共用一份数据：Spark 写，Trino / DuckDB / Snowflake / Databricks 读。
需要 time travel、rollback、增量读、审计与跨版本调试。
分区规则会随规模演进：从 day 到 hour，从单时间维度到时间 + bucket。
对象存储为主、存算分离，想避开目录 list 与 metastore 分区爆炸。
✕ 不适合
高频单行 OLTP 更新、强二级索引、低延迟点查为主的业务。
数据量很小、文件数有限、单引擎脚本就能跑完的临时数据集。
没有 catalog 治理、没有维护任务、没有文件大小控制，只想“换个表格式”。
强依赖某专有数仓自动优化，且不需要开放的文件级互操作。
所有查询都是全表扫描、没有 selective predicate——裁剪收益有限。

08 — 常见坑

八个把表搞坏、或把表搞慢的习惯

前四个破坏正确性，后四个只破坏性能——后者更隐蔽，因为你不会收到报错。

01
把 Iceberg 当目录格式手动移动、删除、改名 data file 会破坏 metadata 引用。变更必须走 Iceberg API 或引擎命令。
02
只压 data file，不管 manifests小文件合并后若 manifest 与查询路径错位，规划一样慢。
03
delete files 长期不合并equality delete 写得方便，读时要和大量文件合并过滤。
04
orphan cleanup retention 拍得太短官方维护文档提醒：可能把仍在写入中的文件误判为孤儿，直接破坏表。
05
snapshot 保留策略拍脑袋太短伤 rollback / time travel / 长查询，太长堆 metadata 与旧引用。
06
跨引擎版本不一致v2/v3/v4 特性、DV、branch/tag 成熟度不同，要按最弱的读写方设计。
07
高基数分区制造碎片分区不是越细越好，查询可能还没读数据就耗在规划上。
08
迷信格式本身带来性能Iceberg 只提供结构与 metadata；快不快取决于文件大小、排序、统计完整度、引擎裁剪与维护动作。

它把“文件集合”

Iceberg 给你的是结构与协议；快不快，取决于你怎么治理这棵树。
