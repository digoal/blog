00 · 核心结论

不重新发明存储引擎，而是补一层「文件版本定义」

Delta Lake 自己定义的既不是数据格式，也不是执行引擎，而是表根目录下的事务日志协议。每个 commit 声明这一版 add / remove 了哪些逻辑文件，读者重放日志就得到一份一致的快照。

① 物理对象（不可变）
part-00000.snappy.parquet
part-00001.snappy.parquet
part-00002.snappy.parquet
写者只新增文件，从不原地改写旧文件。目录里可能有几十万个对象。
② 事务日志（只追加）
v10  + add f_a
v11  − remove f_b  + add f_c
v12  + add f_d
一个版本 = 一个 JSON 文件，内容是一组原子动作。
③ 可见快照 v12
f_a   f_c   f_d
f_b 已 remove：物理还在，但不再属于当前表版本。
同一条结论的另一面：快照的代价也很明确 —— 必须维护事务日志、checkpoint、文件统计、小文件、tombstone、VACUUM 保留期与协议兼容性。收益不是白拿的。

01 · 为什么需要

纯 Parquet 数据湖的四个坏味道

对象存储便宜、容量大、存算分离，但它本质更接近 key-value 对象存储：目录 listing 贵、跨对象原子更新弱。把文件堆在一起，就得到四个结构性毛病。

01
表状态靠目录推断，不便宜也不可靠

表可能有百万到十亿级对象。查询前先递归 LIST，再逐个读 Parquet footer 找 min/max，规划阶段的成本可能超过真正扫描。

Delta 重放日志得到文件集合，不依赖 listing 推断。
02
多文件更新不是原子的

一次 overwrite / merge / delete 要新增一批、删除一批文件。任务中途失败会留下半成品，读者可能看到混合状态。

Delta 一个版本一个 commit，可见性只发生在提交点。
03
并发写入缺少清晰的冲突边界

流式写入、批量回填、手工修数、OPTIMIZE 可能同时发生。没有日志时，系统判断不出两个写者是否动了同一批数据。

Delta MVCC + 乐观并发：抢版本号，冲突再检查语义。
04
维护动作会被误认为业务变化

小文件压缩、Z-Order 重排只改变布局，却让下游流式读者以为表里多了一批新业务记录。

Delta 用 dataChange=false 显式标记纯布局变化。

于是问题被转回一个数据库老问题：如何维护一条可串行化的表版本历史，并让读者在任何时刻只读取某一个一致快照。

02 · 定位

它定义的是协议，不是文件格式

Delta Lake 是 open table format / storage framework，不是 Parquet 的替代品。真实行列数据仍然写成 Parquet；Delta 自己定义的是日志协议、动作模型、快照重放规则与维护语义。

引擎 / 计算层 通过协议读写

SparkTrinoFlinkDuckDBKernel API

Delta 协议层 Delta 自己定义的部分

protocol metaData add / remove checkpoint snapshot

存储层 仍然是开放的

Parquet 文件 S3 / OSS / ADLS / GCS / HDFS
Parquet 负责「单文件内部」
列式编码、row group、page、压缩
footer 里的 min / max 统计
Delta 负责「跨文件表语义」
schema、分区、当前文件集合
事务版本、删除标记（DV）、文件级统计
checkpoint、VACUUM、OPTIMIZE 维护语义

因此判断一张表「有哪些文件」，应该看 snapshot，而不是看目录。

03 · 提交

一个版本 = 一个原子动作集合

文件名 = 20 位补零版本号。写入 = 创建下一个文件，而不是修改旧文件。
_delta_log/00000000000000000000.json
_delta_log/00000000000000000001.json
_delta_log/00000000000000000002.json
每个 commit 里通常出现的 action：protocol、metaData、add、remove，另有 txn（幂等写入）与 commitInfo（审计指标）。
并发写者抢的，就是「同一个版本号」这一个文件。

protocol

读写协议版本与表特性；最新值生效，旧客户端必须拒绝读写。

metaData

schema、分区列、配置；最新值生效。

add

新增一个逻辑文件：路径、分区值、统计、dataChange。

remove

移除逻辑文件，并作为 tombstone 保留到过期。

04 · 快照

读者只看一个稳定版本：日志重放得到 snapshot

Delta 协议把某个版本的表状态称为 snapshot：包含 protocol、metadata、当前有效文件集合、未过期 tombstone 与应用事务集合。它是不可变的 —— 读者拿到之后，写者的新提交不会改变它。

_last_checkpoint
指向近端 checkpoint
checkpoint @ v10
一次读全量状态
v11.json
增量动作
v12.json
增量动作
Snapshot v12
可扫描的文件集合
构造 snapshot 的五步
1找到目标版本之前最新的完整 checkpoint
2读取 checkpoint 中已经消解过的表状态
3读取 checkpoint 之后到目标版本之间的 JSON commit
4按 action reconciliation 规则合并
5得到可扫描的 AddFile 集合与未过期 RemoveFile tombstone
重放时的归并规则（很像日志归并）
·最新 protocol 生效；最新 metaData 生效
·同一个 appId 的最新 txn 生效
·同一个逻辑文件，保留最新的 add 或 remove 引用
·查询路径只返回有效 add；remove 主要服务 VACUUM 和并发旧读者

没有 checkpoint 时，读者要从 0 号日志一路重放；有了 checkpoint，只需「一次全量 + 少量增量」。下一件事：checkpoint 本身也是存储结构。

04 · checkpoint

Checkpoint 把日志状态物化成 Parquet

它不是缓存小优化，而是存储结构的一部分：把历史 commit 的重放结果落成一个文件，让新读者不必从 0 号日志开始，也让更老的 JSON 日志具备被清理的条件。

无 checkpoint：重放 v0 → v12

13 个 JSON commit 的顺序读取与合并

有 checkpoint：1 次全量 + 2 次增量
checkpoint v10

构造成本与版本号增长解耦

注意指针不是真相。_last_checkpoint 只是加速定位的指针，表状态仍由 checkpoint + 后续 commit 共同决定。
三种形态
1classic —— 单个 parquet 文件，最常用。
2multi-part —— 已不推荐：无法原子创建，容易部分缺失或混合覆盖。
3V2 / UUID 命名 —— 可用 sidecar files 改善可扩展性。
它包含什么

protocol、metadata、当前仍有效的 add files、未过期 remove files、txn、domain metadata。因此它可以是「已完成重放的快照」。

维护语义

降低新读者构造 snapshot 的成本；让元数据清理可以删掉更老的 JSON 日志；也让 LIST 日志目录这件事退化成一次指针读取。

05 · 并发

先写数据，再抢下一个版本号

Delta 的写路径是典型的乐观并发控制（OCC）：写者先在对象存储里把新文件写完，最后才尝试创建下一个版本的 commit 文件。版本号被占用，就检查冲突再重试。

读者 R 持有 v10 snapshot 写者提交了 v11 也不影响：R 全程只读 v10 的文件集合，不阻塞、不重试

提交实现中 doCommitRetryIteratively 在 FileAlreadyExistsException 或可重试冲突时进入冲突检查；最终由 commit coordinator 或文件系统 commit 写出目标版本。

事务中的读取必须通过 transaction 对象完成 —— 否则并发冲突检测覆盖不到这些读。这就是「盲 append 冲突概率低、MERGE/DELETE 冲突概率高」的由来。

它依赖的三个存储前提
atomic visibility · 提交文件要么可见要么不可见
mutual exclusion · 同一版本号只能有一个赢家
consistent listing · 列出的对象不会漏
不满足时由 LogStore / commit coordinator 补齐语义
06 · 动作模型

AddFile / RemoveFile：Delta 的文件级 MVCC 记录

不要把它想成「文件列表」，而是「文件级版本记录」：一个逻辑文件的最新一次 add 或 remove 决定它在当前版本里可见与否。

同一个逻辑文件（path）：日志里最新的一条 add 或 remove，决定它在当前版本里可见与否。这是一个「文件级」的版本记录，不是物理去留。
AddFile
path — 相对表根或绝对路径
partitionValues — 分区列值
size / modificationTime
dataChange — 是否业务数据变化
stats — numRecords / min / max / nullCount
deletionVector — 可选 DV 描述符
baseRowId / defaultRowCommitVersion
clusteringProvider — 聚簇表相关

stats 是 data skipping 的依据；deletionVector 让删除不必重写整个文件。两者都把成本转移到了写入端。

RemoveFile
path — 被移除的逻辑文件
deletionTimestamp
dataChange — 是否业务删除
extendedFileMetadata
partitionValues / size / stats / tags
deletionVector

remove 不是物理删除：它只是一条 tombstone，保留到过期，服务旧快照读者与 VACUUM 判定。

VACUUM 默认保留 7 天，是 MVCC 的安全窗口。把旧文件删得太早，旧 snapshot、time travel、慢查询就会读不到它们 —— 这是策略问题，不是清理参数问题。
Deletion Vector 的取舍：降低删除写放大（不重写整个文件），代价是读取更复杂、统计维护更难。

为什么只统计前 32 列

默认 delta.dataSkippingNumIndexedCols = 32。长字符串等类型收集统计有成本，应按查询模式取舍。

统计范围高度重叠时，跳过率会明显下降 —— 这正是下一节 Z-Order 要解决的问题。
08 · 布局维护

重写文件来改善布局：bin-packing 与 Z-Order

两者都不原地改旧 Parquet：读候选文件 → 写新文件 → 提交一组 add 与 remove。区别在于一个治「文件太多」，一个治「min/max 太宽」。

① OPTIMIZE · bin-packing

10 · 效果

收益来自五个机制，不是一个神奇开关

01正确性读者只读一个 snapshot，写者通过下一版 commit 建立原子可见性，避免「半写入表」。依赖存储前提
02元数据规划checkpoint 与 _last_checkpoint 降低 snapshot 构造成本，避免全量 listing 日志目录。多一份物化文件
03读取data skipping 在 Parquet 扫描前跳过不相关文件，效果取决于统计与布局。数据散落则失效
04写入与维护append 只加文件；OPTIMIZE 合并小文件；Z-Order 改善多维谓词裁剪。写放大 / 算力
05时间旅行与审计日志保留版本历史，可按版本或时间读旧 snapshot，也能查看 operation 与 metrics。保留策略要匹配
两个必须避免的误解
不是行存数据库

没有二级索引时，点查仍是「文件级跳过 + Parquet 扫描」。不要拿它替代 OLTP 主键查询。

ACID 只到单表

它是单表事务日志语义。跨表事务、全局约束、复杂锁管理不是默认强项。

单表事务 文件级 MVCC 无内建二级索引
「正确」和「快」是两件事：前者靠协议，后者靠统计与布局。
11 · 最佳实践

三类角色，各自的抓手

维护语义是全表共享的，但职责要分清：架构师定边界，运维守物理文件与日志，开发者管谓词和写入方式。

架构师
把它当文件级 MVCC 表格式，不是把对象存储伪装成 OLTP
高并发表先设计分区边界、批次大小、冲突域
明确 time travel SLA：要回溯 30 天，就别用 7 天 VACUUM
多引擎场景先确认 protocol 版本与表特性兼容性
DBA / 数据平台运维
监控日志大小、commit 频率、文件数、平均文件大小、tombstone 与 VACUUM
不要手工删目录里的 Parquet 或日志文件
小文件严重就排 OPTIMIZE / 自动压缩，把算力与写放大纳入调度窗口
对常用过滤列确认 stats 覆盖
业务开发者
写入走 Delta API / SQL，不要绕过日志直接塞 Parquet
谓词用分区列与高选择性列，别包在难下推或非确定性函数里
MERGE / UPDATE / DELETE 控制匹配范围，否则扩大冲突域与重写量
理解 dataChange=false，别把重排当业务新增
贯穿三类角色的一条线：表状态从 snapshot 看，物理文件交给 VACUUM 管，布局交给 OPTIMIZE 管，统计交给写入端管。
12 · 场景判断

适合什么，不适合什么

同一个技术，边界清楚了才好用。选型失败通常不是因为它不好，而是拿它去解决错的问题。

适合
✓大规模 append-heavy 分析表：日志、事件、交易流水、埋点、宽表
✓批流统一、时间旅行、审计历史与一致快照的湖仓场景
✓对象存储上多作业并发写，但事务边界主要是单表
✓过滤列稳定，可借分区与 data skipping 少读大量文件
✓要开放 Parquet，同时想避开半写入、脏读、小文件失控
不适合
✕低延迟单行点查、高频短事务 OLTP
✕复杂跨表事务与强外键约束场景
✕毫秒级更新可见性、极高 QPS 主键写入
✕不愿维护 checkpoint、VACUUM、OPTIMIZE、统计与协议兼容的简单文件交换
✕查询条件高度随机、统计范围高度重叠、每次都接近全表扫描的小数据集

最后一条尤其容易被忽略：维护层的成本是固定的，数据量小的时候，它可能比收益更重。

13 · 常见坑

七个高频踩坑

下面这些坑几乎都源自同一个误解：把 Delta 表当成一个普通目录来管理。

01  把表目录当普通目录管理

手工删除 Parquet 或日志文件会直接破坏 snapshot。要用 DELETE、VACUUM、OPTIMIZE 和表维护命令。

02  VACUUM 保留期小于回溯窗口

只要有 time travel、审计、慢查询或下游延迟消费，7 天默认值就可能不够。

03  小文件堆积后只怪查询引擎

它同时拖慢日志重放、任务调度、对象存储访问和 Parquet 扫描。先看文件大小分布与 commit 模式。

04  Z-Order 选错列

应选常出现在谓词中、选择性高、且有统计的列。列越多，局部性收益通常越分散。

05  把 partition 当索引用

高基数分区会制造大量小目录和小文件。分区适合粗粒度裁剪，不适合照搬 OLTP 主键。

06  忽视协议版本

Deletion vectors、column mapping、clustering、row tracking 都可能抬高协议要求；旧客户端读不了是协议保护。

07  只看当前 Parquet 文件，不看日志动作

旧文件、孤儿文件、被 remove 但未 VACUUM 的文件都可能物理存在。表状态要从 snapshot 看，不能从目录看。

14 · 收尾

记住一句话：日志定义可见性，落盘定义数据本身
