01 问题

“目录 + Parquet”只回答了一半问题

Parquet 回答的是“一个文件内部如何列式编码、压缩、存统计”。但业务表还要回答另一组数据库问题——这组问题，数据湖的目录结构本身答不了。

01更新没有落点

Hive 表只知道“有个分区目录”，不知道 order_id=123 在哪个 Parquet 文件里。想改一行，只能整片重写或全表扫描。

缺少：索引

02没有版本边界

对象存储 listing 贵、跨对象无原子性。写者先落地数据文件再写元数据，读者直接扫目录就会读到未提交文件、旧版本文件。

缺少：timeline

03失败无法回滚

作业写一半挂掉，半成品文件没人认领。没有事务状态，就分不清“写完了”和“写了一半”，也无法重试与清理。

缺少：事务语义

04没有维护机制

log 会涨、小文件会堆、旧版本占空间、列统计每次从头推导。没有内建表服务，只能靠一堆外部脚本硬拼。

缺少：表服务
关键差别 “文件存在” ≠ “表里有这条数据”。可见性（visibility）必须由表自己发布，而不是由对象存储的目录瞬态决定。
02 答案

Hudi 的答案，可以浓缩成一句话

数据按 file group / file slice 组织，表状态由 .hoodie timeline 发布；更新先通过索引定位 record key 所在 file group，再选择 COW 重写 base file 或 MOR 追加 log file。

为什么是 file group

record key 定位的粒度不是行、也不是文件，而是“一组会长大的文件”。更新只碰目标组。

为什么是 timeline

唯一的事实来源。表有哪些版本、谁写完了、从哪读到哪，全部由 instant 状态决定。

代价是什么

概念多：timeline、file group、slice、索引、metadata table、compaction、cleaning，缺一不可。

03 定义

它是表格式，不是文件格式

Apache Hudi 是 open data lakehouse platform / table format。它不替代 Parquet、ORC、Avro、HFile，而是在这些文件格式之上定义表目录、timeline、file group、索引、读写语义与表服务。

物理布局 · 你在 find 里会看到
/table_base_path表根目录 — Hudi 表的物理边界，一切都在它下面
.hoodie/元数据目录 — hoodie.properties、timeline、metadata table、aux / temp / schema
dt=2026-05-25/数据分区 — 按分区列组织；非分区表可以没有这一层
fg-a-001_…parquet数据文件 — 文件名里编码了 fileId、写入 instant、写 token

记住这张地图：目录里只有“文件”，没有“表”。表是 .hoodie 里的元数据对这批文件的一次解释。

逻辑概念 · 你必须理解的四件事
file grouppartition + fileId。更新、索引、compaction、读合并的基本逻辑单元
file slicebaseInstantTime + base file + log files。同一组在某个 instant 下的一个版本
timeline instantcommit / deltacommit / compaction … 发布状态变化，提供快照隔离与恢复边界
metadata table.hoodie/metadata。内部 Hudi MOR 表，存文件列表、列统计、Bloom、record index

源码入口：HoodieTableMetaClient · HoodieTimeline · HoodieFileGroup · FileSlice · HoodieLogFile · HoodieFileGroupReader

04 存储布局

一张图看懂：timeline × file group

读图 纵轴是 timeline instant（时间），横轴是不同的 file group（空间）。读者要的是一个交点：在每个 file group 上，找到最新的、已完成的那一个 file slice。把鼠标移到任意文件块上可查看说明。
05 两种表类型

COW 与 MOR：不是谁更高级，是把同一笔成本放在不同阶段

COW 在写入时同步偿还重写成本，读路径简单；MOR 写入时先记账，读时或 compaction 时再偿还合并成本。

选型 读多写少、对查询延迟敏感 → 优先 COW；高频 upsert/delete、CDC 入湖、要准实时新鲜度 → 优先 MOR，并把 compaction 当成必须运维的日常。
06 timeline

一次写入的一生：requested → inflight → completed

Hudi 的事务边界不是“文件已经写到对象存储”这个物理事实，而是 timeline 上这个 action 是否 completed。

对照 Delta Lake 的 _delta_log 也靠日志决定可见性。但 Hudi timeline 不是简单的文件增删清单：它同时承载写入动作、表服务动作、增量查询边界、恢复语义和表类型的状态转换。
07 timeline action

timeline 上到底有哪些 action

写入、表服务、schema 变化都会记录成 action；每个 action 有 requested instant、completed instant、state 和 type。表维护不是外部脚本，而是 timeline 上的正规动作。

action 谁产生 作用 对读者的影响
commitCOW 写入作业一批记录写入完成，产生新 base file 与新 slice可见新 slice；旧 slice 仍可 time travel
deltacommitMOR 写入作业一批变更写入 log file（不动 base file）snapshot 立即可见（要合并 log）；RO 查询看不到
compaction表服务（同步 / 异步）把 log 合并进新的 base file，slice 前进一代RO 查询的新鲜度提升；读放大下降
clean表服务按保留策略删除不再需要的旧 file slice超出保留窗口的版本不能再 time travel
replacecommitclustering / 批量重写原子地把一组 file group 替换成另一组查询需要规划的文件更少
clustering表服务重排小文件、优化文件布局（最终落成 replacecommit）同上：更少小文件、更稳的查询计划
indexing表服务维护 record index 等索引分区写入 upsert/delete 的定位更快

写入类：commit / deltacommit —— 决定“表里现在有什么”。

维护类：compaction / clean / clustering / indexing —— 决定“表好不好用”。

共同点：都要经过 requested → inflight → completed，都可重试、可回滚、可观测。

08 并发

MVCC：读者固定快照，写者和表服务发布新版本

Hudi 通过把 commit 原子发布到 timeline 来保证 atomic writes，并在 writer / reader / table services 之间提供 snapshot isolation；多 writer 场景再叠加 OCC、NBCC 等并发模式。

09 增量层

MOR 的增量层：log file 与 log block

log file 不是随便追加的 JSON。文件名本身就是元数据，内部是一串有类型的 block；读取时按 record key 与 ordering / preCombine 规则合并出最终记录。

10 可见性

file system view：把“文件清单”变成可见性索引

读者不会递归目录后把所有文件丢给引擎。HoodieTableFileSystemView 在给定 visible active timeline 下构造 partition → file groups 映射，并跟踪各种 pending 状态。

本质 这层非常像数据库里的“可见性索引”：把对象存储上的文件名、timeline 状态、在途表服务合起来，回答一个问题 —— 对这次查询来说，每个 file group 应该读哪个 slice？
11 读路径

三种查询的差别，只在三个位置

选哪些 instant、选哪些 slice、是否合并 log —— 选完这三件事，读到的数据就定了。点击任一查询类型查看它的路径。

12 元数据

metadata table：把对象存储的成本前置成内部索引

对象存储上最贵的动作之一，是海量目录 listing 和逐个打开文件 footer。Hudi 把这两件事在写入维护阶段做掉，读的时候只查自己的元数据表。

悬停 把鼠标移到任意索引分区上，看它到底替谁省了成本。
13 可观测性

每次写入，都留下一份文件级账本

commit metadata 记录每个分区的 write stats。这让 timeline 不只是可见性日志，也是排查“表为什么变慢”的入口。

HoodieCommitMetadata.avsc（结构示意）
HoodieCommitMetadata ├─ partitionToWriteStats │ └─ "dt=2026-05-25" : [ HoodieWriteStat ] │ ├─ fileId "fg-a-001" │ ├─ path "..._001.parquet" │ ├─ prevCommit "002" │ ├─ numWrites / numDeletes / numUpdateWrites │ ├─ totalWriteBytes / fileSizeInBytes │ ├─ totalLogFiles / totalLogRecords │ ├─ baseFile / logFiles │ └─ minEventTime / maxEventTime └─ // 每个 commit 都可审计、可回放
表变慢时，先看这五件事
  • 这次 commit 写了哪些 file group，是否集中在少数热点
  • log file 是否在积累：totalLogFiles 与 totalLogRecords 的趋势
  • compaction 是否追上：base file 的 prevCommit 是不是很旧
  • clean 是否回收：旧 slice 是否还占着空间
  • 写入是否异常：单次 commit 的文件数、字节数是否突然放大

只数文件数是不够的。同一张表，1000 个 10MB 小文件和 10 个 1GB 文件，文件数一样好看，规划成本差一个数量级。

prevCommit = "002"

这个 slice 的 base 还停在 002 —— compaction 落后了，下一次 snapshot 读要合并更多 log。

totalLogFiles = 3

同一个 base 上挂了 3 个 log —— 读放大在涨，该看 compaction backlog 了。

numUpdateWrites = 1

只改了 1 行，却重写了整块 base —— 这就是 COW 的写放大，也是选 MOR 的理由。

14 横向对比

四个系统，四种设计取舍

重点不是排出高低，而是让架构选择回到 workload：谁把“记录级变更”当一等公民，谁把“开放元数据树”当核心。

论文 CIDR 2023《Analyzing and Comparing Lakehouse Storage Systems》把 Delta、Hudi、Iceberg 放在同一类：都在低成本数据湖存储之上补事务、索引和 DBMS 管理能力 —— 但取舍不同。
15 效果

收益从哪来，代价又落在谁身上

Hudi 不是“免费的更快”。它把复杂度换成了可控的阶段：写放大转移到 compaction，规划成本转移到 metadata table。

四个方向的收益
1降低更新写放大COW 只重写目标 file group 而不是整表 / 整分区；MOR 把同步重写变成追加 log，交给 compaction 收口。
2快照隔离与增量边界读者按 completed instant 构造快照，增量消费者按 begin/end instant 取变化，比“按分区时间扫目录”更接近数据库语义。
3降低规划成本files / column_stats / partition_stats / bloom / record_index 把 listing 与 footer 读取换成内部元数据查询。
4维护动作事务化compaction、clean、clustering、indexing 都通过 timeline 留痕，可重试、可回滚、可观测。
六笔明码标价的代价
  • COW 写放大：频繁小更新会反复重写 base file
  • MOR 读放大：snapshot 要合并 log，compaction 落后就直接变慢
  • 索引自身开销：metadata table / record index 要写、要维护、要监控一致性
  • 并发更复杂：多 writer 必须配锁、并发模式、failed writes 清理策略
  • 小文件要治理：小文件放大 metadata、规划与执行开销，得靠 clustering / 合理批量
  • 排障门槛高：概念多，比 Hive 目录表和很多 Iceberg 读多场景更难调
本文不引用任何通用性能数字。湖表性能强依赖数据分布、文件大小、分区、索引类型、引擎、对象存储与 compaction 策略 —— 只用自己的 workload 验证才作数。
16 实操

动手：用三个动作看见存储结构

目标不是压测，而是观察 .hoodie、timeline、base file、log file 以及 compaction 前后的变化。

1建一张 MOR 表
CREATE TABLE hudi_orders ( order_id STRING, user_id STRING, amount DECIMAL(18,2), status STRING, ts BIGINT, dt STRING ) USING hudi PARTITIONED BY (dt) OPTIONS ( type = 'mor', primaryKey = 'order_id', preCombineField = 'ts' ) LOCATION 'file:///tmp/hudi_orders';
看：
· 根目录下有 .hoodie
· .hoodie 里有 hoodie.properties
· 分区目录出现 base file
2执行一次 MERGE（更新 o1）
MERGE INTO hudi_orders t USING ( SELECT 'o1' AS order_id, 'u1' AS user_id, 15.00 AS amount, 'paid' AS status, 2000 AS ts, '2026-05-25' AS dt ) s ON t.order_id = s.order_id WHEN MATCHED THEN UPDATE SET * WHEN NOT MATCHED THEN INSERT *;
看：
· 更新后出现 .log 文件
· timeline 多一个 deltacommit
· snapshot 读到 paid，RO 取决于 compaction
3对照查询类型
find /tmp/hudi_orders \ -maxdepth 4 -type f | sort # 应该能看到 .hoodie/hoodie.properties .hoodie/<instant>.deltacommit dt=2026-05-25/ fg-a-001_<t>.parquet .fg-a-001_<t>.log.1_... # 再用两种读法对照 val snap = spark.read.format("hudi") .option("hoodie.datasource.query.type", "snapshot") # 合并 log .load(basePath) val ro = spark.read.format("hudi") .option("hoodie.datasource.query.type", "read_optimized") # 只读 base
看：
snapshot → 合并 log，最新
read_optimized → 只读 base，可能滞后
incremental → 按 instant 区间取变化
前提 本文未在本地启动 Spark / Hudi，以上 SQL 未实际执行。请在已配置 Hudi Spark bundle 与 HoodieSparkSessionExtension 的 Spark SQL 环境中运行。
17 最佳实践

三类角色，三张检查清单

Hudi 的复杂度不会消失，只会转移。把它分配到正确的角色上，就不至于变成“很多文件但没人知道哪些该读”。

数据库架构师
  • 先按 workload 选表类型：读多更新少、要低延迟 → COW；高频 upsert、CDC、要新鲜度 → MOR
  • 把 record key 当主键设计：索引、upsert、file group 稳定性都依赖它，别用不稳定字段
  • 分区不只看查询写法：还要看更新分布，避免热分区倾斜或跨大量旧分区更新
  • 把表服务纳入架构：compaction、clean、clustering、metadata table、indexing 都要有人管
  • 先确认版本矩阵：表版本、bundle 版本、Spark/Flink/Trino 支持、并发模式
DBA / 数据平台运维
  • 盯 timeline：commit / deltacommit 是否持续完成，有没有长期 inflight / requested
  • 盯 log 积累：每组 log 数量、总大小、compaction backlog、RO 滞后
  • 盯 metadata table：files index 是否启用，stats / record_index 是否按预期维护，它自己是否 compaction
  • 慎配 clean 保留：太短伤慢查询 / time travel / 增量消费；太长占空间又拖规划
  • 多 writer 显式设计锁：不要默认“对象存储最终会一致”
业务开发者
  • 写清 primaryKey 与 preCombineField：明确定义同 key 多条变更的胜出规则
  • 别把表目录当 Parquet 目录读：除非你确定只要某些 base file，且清单合法
  • 按新鲜度选查询：要新 → snapshot；要快可滞后 → read optimized；下游 ETL → incremental
  • MERGE 前先小表实验：观察 .hoodie 与文件变化，理解会碰哪些 file group
  • SLA 写清两件事：数据新鲜度 + 查询延迟，否则 compaction 无法调参
18 边界

什么时候该用它，什么时候别用

判断标准应该是 workload 与团队能力，而不是“哪个更流行”。

适合 Hudi
  • MySQL / PostgreSQL / Oracle / NoSQL 的 CDC 入湖，需要 upsert / delete 与准实时分析
  • 订单、交易、库存、画像、风控、广告等会持续修正的事实表
  • 下游 ETL 希望按 timeline 增量消费，而不是每天全表重算
  • 同一张表要同时支持 snapshot / incremental / CDC / time travel / RO 查询
  • 团队愿意投入运维：治理 compaction、clean、metadata table 与索引
要谨慎 / 不适合
  • 纯 append、低频查询、几乎没有更新的小表 —— 普通 Parquet 或 Iceberg/Delta 更简单
  • 需要亚秒级 OLTP 点查 / 事务：它是湖表格式，不是关系库或 KV 存储
  • 团队不愿维护 timeline / compaction / clean / 索引，却用 MOR 扛高频更新
  • 多引擎混用但版本治理能力弱：读写语义依赖客户端理解 timeline 与表版本
  • 查询主要是开放多引擎批量扫描，几乎没有记录级变更诉求 —— Iceberg 往往更自然
反模式 最贵的坑不是选错表类型，而是选了 MOR 却不运维 compaction：写入一直很快，直到某天 snapshot 查询开始合并几百个 log。
19 总结

记住这四个词，剩下的都是细节

1file group —— 单元更新、索引、compaction、读合并，全部围绕“一组会长大的文件”进行。
2timeline —— 事实可见性、增量边界、恢复语义，都从 completed instant 来，而不是从目录瞬态来。
3索引 —— 定位record key → file group，让 upsert / delete 不必全表扫。
4表服务 —— 运维compaction / clean / clustering / indexing 都是 timeline 上的正规动作，不是外部脚本。
选型一句话
● 记录级变更多、要 CDC / 增量 → Hudi
● 开放多引擎批量读、长期演进 → Iceberg
● Spark / Databricks 为家 → Delta
● 纯 append 的小表 → 普通 Parquet 就够
留给你的三个问题
  • 95% append + 5% 跨 90 天旧分区更新，你选 COW 还是 MOR？索引和 compaction 怎么配？
  • Hudi 的 file group 与 LSM tree 的 level / run，有哪些相似与不同？
  • 同一个数据湖里，判断“这张表该给 Hudi 还是 Iceberg”的标准，是生态偏好还是 workload？
