02 定义

一句话说清它是什么

PostgreSQL large object 是一个由系统表承载、由 OID 标识、按小页切片、通过类文件 API 访问、受事务与权限控制的大值存储结构。
pg_largeobject_metadata OID LOBLKSIZE = 2 KB open / read / write / seek MVCC · WAL · ACL
它解决了什么
事务内对流式 / 随机访问大值的问题。数据页在数据库里，跟着提交、回滚、WAL、备份恢复一起走。
它把什么交给了你
引用治理、孤儿对象、备份策略、系统表膨胀、权限，以及应用侧 API 的正确用法。

02 结构

三层模型：逻辑层、元数据层、数据层

业务表里看到的只是一个数字。真正的对象存在两张系统表里，各管一件事。

一个 large object 的"存在"不取决于 pg_largeobject 里有没有数据页，而取决于 pg_largeobject_metadata 里有没有这个 OID。 所以 LO 可以没有任何数据页 —— 那就是一个 0 字节的对象。

02 结构

pg_largeobject：只有三列的系统表

整个 large object 的数据模型，可以压缩成三个字段加一个主键。

列类型含义

官方文档和源码都说同一句话：每一行保存从 pageno × LOBLKSIZE 开始的一页数据。页号不是地址，是索引键 —— 正因为它是索引键，页可以缺、可以短，也可以按任意顺序写入。

03 原理

为什么是 2 KB，而不是 8 KB

LOBLKSIZE 是这套结构的"扇区大小"，当前源码里定义为 BLCKSZ / 4。

LOBLKSIZE = BLCKSZ / 4 = 8192 / 4 = 2048 字节 / 页 改动它需要 initdb

① 少浪费

更新单个 page tuple 时，页越大，重写浪费的空间越多。2 KB 让一次局部修改的代价维持在很小的量级。

② 够大，能触发压缩尝试

源码注释的动机之一：这个尺寸足够大，使得 tuple toaster 愿意尝试内联压缩。

③ 2 的幂，贴合客户端习惯

应用侧本来就习惯按 2 的幂分块读写；页边界与分块边界对齐，可以少做跨界拼接。

④ 它是一个"格式常量"

改变它意味着已存在的页布局全部失效，所以只能通过 initdb 重建集簇，而不是一个 GUC。

记住这个数字，后面所有的读写、截断、空间放大都从它推导：一个 large object 的"磁盘页"是 2 KB，不是 PostgreSQL 的 8 KB block。 8 KB 是堆页/索引页的单位，2 KB 是 LO 逻辑页的单位 —— 两者不同层级。

03 原理 · 创建

先有 metadata，后有数据页

创建 large object 只做一件事：在元数据表里插入一行。此刻对象大小就是 0。

源码注释写得很直白：创建新 large object 时先插入 metadata，不插入数据页，因此对象以 0 字节大小存在。 这条不变量决定了后面所有行为 —— 包括"空对象"和"稀疏对象"都是合法的。

03 原理 · 布局

页号可以缺失：一个数据库内的稀疏文件

pageno 不要求连续，页也不必写满。没写过的区域不占任何数据页，但读起来是零。

这个行为和 Unix 稀疏文件（sparse file）非常像：缺失区间读出来是零，写进去才物化。 于是"随机写一个大文件的一小段"不会把整个文件写一遍 —— 这是 LO 相对 bytea 的核心竞争力。

03 原理 · 读

inv_read：从 offset 算页号，缺页补零

一次随机读，四步走完。注意第二步：除法取整之后，剩下的余数就是页内偏移。

对照 Unix：pageno 像文件块号，offset % LOBLKSIZE 像块内偏移。 只改一行，却要读回整页再写回 —— 这也是为什么一页不能太大。

03 原理 · 写

inv_write：旧页 update，新页 insert

写路径比读路径多一个分支判断 —— 目标页是否已经存在。两个分支都要处理"洞"。

注意"洞"在两个分支里的表现形式不同：update 分支是旧数据尾部与写入位置之间的空隙，insert 分支是从页首到写入偏移之间的空隙。 两者都必须补零，否则一次局部写会改变对象的语义内容。

03 原理 · 截断

truncate 两个方向，和"大小"的真相

缩短要删尾页，扩展要造一个"逻辑结尾"。而对象大小，从来不是 count(*) × 2048。

缩短：改页 + 删尾

扩展：制造逻辑结尾

inv_getsize( )
反向扫描该 loid 的最后一页 →
last_pageno × 2048 + last_page_len
这是最容易被误解的一点：LO 的大小是一次"反向找最后一页"的探查结果，不是行数乘法。 页缺失、末页短于 2048、扩展截断只留一个标记页 —— 都让"行数 × 2048"这个直觉失效。

03 原理 · 会话

descriptor 不是 fd，是事务内的一张凭据

API 长得像 Unix 文件接口，但 lo_open 返回的东西只在当前事务里有效。

字段作用
idlarge object OID
snapshot读写使用的快照
subid打开 descriptor 的子事务
offset当前 seek 指针
flags是否以读 / 写模式打开
结构体名：LargeObjectDesc， 定义在 storage/large_object.h。 服务端 be-fsstubs.c 用一个 cookies[] 数组保存这些指针， 数组下标就是 SQL 里看到的那个"描述符编号"。
一个事务内的生命周期
BEGIN 事务开始
lo_open( ) → cookies 里占一格
lo_read / lo_write → 用快照和 offset 工作
lo_close( ) → 释放这一格
COMMIT / ABORT AtEOXact_LargeObject( ) 兜底清理

03 原理 · 快照

只读打开和写打开，看到的不是同一个世界

descriptor 里带着快照。用哪种模式打开，决定你能看见谁提交的数据。

原文的表述是：只读打开绑定打开时的活动快照；写打开历史上允许同时读取，读取会反映其他已提交事务和当前事务写入的内容 —— 行为上类似 ordinary SQL 在 READ COMMITTED 下的可见性。而写入、truncate、create、unlink 都会阻止只读事务做出修改。

03 原理 · 生命周期

两条生命周期，一条会被忘记

LO 是数据库对象，业务行只是应用层的引用。删除业务行，不会有任何东西自动发生。

OID 引用不是外键。业务表里的 raster_oid oid 只是一个数字，数据库不会因为它被删除就回收对象。 这是 large object 最常见的工程坑，也是选型时必须提前回答的问题。

05 效果

收益和成本，来自同一套机制

固定页号 + 索引定位带来了随机访问，也带来了 tuple 级开销。这不是取舍，是同一枚硬币。

收益 · 随机访问

pageno = offset / LOBLKSIZE，经 btree(loid, pageno) 直达目标页。适合按 offset 读写。

收益 · 稀疏存储

没写过的页不占 pg_largeobject 行，读时补零。大文件局部写不必整份重写。

收益 · 流式接口

libpq 提供 lo_read / lo_write / lo_lseek64 / lo_tell64，客户端可以分块传输。

收益 · 事务保护

数据页在库内，随提交、回滚、WAL、备份恢复一起管理。这是外部存储给不了的。

同一套机制的另一面

成本 · 空间放大

每个约 2 KB 的数据页都是一条系统表 tuple：tuple header、line pointer、索引项、visibility 信息全都要钱。

成本 · 写放大

更新一页 = 一次 tuple update，产生 MVCC 旧版本与 WAL。频繁覆盖写要靠 autovacuum 回收。

成本 · 集中热点

所有对象的数据都在 pg_largeobject。对象一多，系统表就变成运维重点。

成本 · 清理外包

OID 引用不是外键。业务删除不会释放 LO，清理责任被完整地推给了应用或 DBA。

所以 large object 的性能优势不是"比文件系统快"，而是"在数据库事务边界内，提供比整值字段更适合局部访问的大对象接口"。

06 实操

DEMO：创建、写入、读片段

一段能跑完的最小闭环。注意三点：全部在事务内、写打开用了两个标志位或运算、读的时候先 seek。

BEGIN; -- 业务表 image_store(id, title, raster_oid oid) -- 1. 建 0 字节对象，OID 存进业务表 WITH n AS (SELECT lo_create(0) AS oid) INSERT INTO image_store(title, raster_oid) SELECT 'demo', oid FROM n; -- 2. 写打开，写入 14 字节 WITH o AS (SELECT lo_open(raster_oid, x'20000'::int | x'40000'::int) AS fd FROM image_store WHERE title = 'demo') SELECT lowrite(fd, decode('48656c6c6f20504f535447524553','hex')); -- 3. seek 到 6，读 8 字节 → POSTGRES WITH o AS (SELECT lo_open(raster_oid, x'40000'::int) AS fd FROM image_store WHERE title = 'demo'), s AS (SELECT lo_lseek(fd, 6, 0), fd FROM o) SELECT loread(fd, 8) FROM s; COMMIT;

两个标志位

x'40000' = INV_READ
x'20000' = INV_WRITE
这是回归测试的写法。C 应用应 #include "libpq/libpq-fs.h" 直接用符号常量。

返回值可以自检

lowrite → 14（Hello POSTGRES）
loread(6, 8) → POSTGRES
有确定结果，才好判断读写路径是否按预期落页。

整段必须在一个事务里

descriptor 随事务存活；拆成多条自动提交语句，fd 立刻失效。

DEMO：看物理页、安全删除、兜底清理

诊断 · 页是怎么分布的（只读）
SELECT loid, pageno, length(data) AS bytes FROM pg_largeobject WHERE loid = (SELECT raster_oid FROM image_store WHERE title='demo') ORDER BY pageno;
只用于学习和诊断。应用不应绕过 API 直接改 pg_largeobject。
删除 · 显式配对
BEGIN; WITH victim AS ( DELETE FROM image_store WHERE id = 1 RETURNING raster_oid) SELECT lo_unlink(raster_oid) FROM victim; COMMIT;
约定 · 用 lo domain + 触发器托管
CREATE EXTENSION lo; CREATE TABLE image_with_lo ( id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, title text NOT NULL, raster lo NOT NULL); -- lo domain CREATE TRIGGER image_with_lo_cleanup BEFORE UPDATE OR DELETE ON image_with_lo FOR EACH ROW EXECUTE FUNCTION lo_manage(raster);
前提：每个 large object 只有一个业务引用。共享对象被触发器误删，是这个方案最常见的事故。
兜底 · 扫描孤儿对象
# 先看，不动手 vacuumlo --dry-run --verbose mydb # 低峰期，分批清理 vacuumlo --limit=1000 mydb
vacuumlo 的工作方式：把所有 LO OID 放进临时表，扫遍库里 oid / lo 类型的列， 去掉仍被引用的，剩下的就是孤儿。注意它识别不了 domain over oid 这类自定义包装 —— 所以它是兜底工具，不是替代建模。

07 最佳实践

三个角色，三份不同的清单

同一个 large object，架构师关心建模，DBA 关心膨胀与备份，开发者关心 API 用法。

数据库架构师

默认用 bytea/text + TOAST 处理中小型字段；只在超 1 GB、必须流式或局部访问、或已有客户端 LO API 依赖时才选 LO。
业务表存 OID 时，把"谁负责删除 LO"写进模型，不要留给事后巡检。
同一 LO 可能被多行共享时，不要用 lo_manage 自动删除；改用引用计数表、唯一引用约束或应用层生命周期协议。
超大静态媒体优先对象存储，PG 里只放 metadata、URL/key、hash、状态机和一致性补偿记录。

DBA

监控 pg_largeobject 与 metadata 的大小、dead tuple、autovacuum、WAL 量和备份耗时。
备份前确认 pg_dump 策略是否包含 LO。带 schema/table 过滤时要注意：LO 属于非 schema 对象，需理解 --large-objects / --no-large-objects 的影响。
定期 vacuumlo --dry-run 评估孤儿风险，再安排低峰清理。
高频覆盖写的库要盯 pg_largeobject 膨胀；必要时拆分业务、改对象存储，或改成追加式对象版本。

业务开发者

所有 descriptor 都放在事务里使用，不要把 fd 存到事务外复用。
客户端分块传输，不要一次性把超大对象读进应用内存。
用 lo_import/lo_export 时区分客户端 libpq 函数与服务端 SQL 函数 —— 服务端函数读写的是服务器文件系统，权限风险更高。
删除业务记录时同步 lo_unlink()，并为失败场景设计补偿任务。

07 避坑

七个坑，按踩到的频率排序

01 把 OID 当外键

OID 引用不会级联删除 LO。需要显式 lo_unlink()、lo_manage 或后台清理。

02 忘记事务

descriptor 只在事务内有效。自动提交环境里拆开的 open / read / close 很容易出错。

03 误用服务端 import / export

SQL 函数读写服务器文件系统，与 libpq 客户端函数的文件位置完全不同。别把 DBA 的机器当成应用容器。

04 忽略权限

9.0 之后 LO 有 owner 和 ACL，读写分别需要 SELECT / UPDATE。

05 直接改系统表

可以查 pg_largeobject 学习布局，但不应该直接写它 —— 绕过了 API、校验和可见性规则。

06 把 LO 当免费空间

每个 LO page 都是一条系统表 tuple，会产生索引、WAL、MVCC 和 vacuum 成本。

07 备份过滤误判

只 dump 某个 schema 或 table 时，large object 的包含规则要单独确认 —— 恢复出的"完整备份"可能一个附件都没有。

07 边界

什么该用，什么别用

适合

医学影像、工程图、模型文件等单对象可能超过 1 GB，且需要按 offset 读取片段。
应用已经在用 libpq / JDBC / ODBC 的 large object 流式接口，迁移成本高。
需要把大对象写入和业务 metadata 变更放在同一个 PostgreSQL 事务里。
需要在数据库权限体系内控制对象读写，而不是维护一套独立的对象存储 ACL。

不适合

Web 图片、视频、下载文件这类以 CDN 分发为主的静态媒体。
对象生命周期没人负责，只是"先把文件塞进数据库"。
频繁小范围覆盖写且对象数量巨大，导致 pg_largeobject 长期膨胀。
只需要保存几十 KB 到几十 MB、并且主要整体读写 —— 此时 bytea / TOAST 更简单。
一句话总结：large object 是中间方案，不是所有二进制文件的默认归宿。它赢在"事务 + 局部访问"，输在"分发热点 + 引用治理"。
