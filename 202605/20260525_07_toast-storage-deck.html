01 它解决什么问题

一行不能跨页，但业务要存远超 8 KB 的值

PostgreSQL 使用固定页面大小（常见 8 kB），并且不允许物理元组跨多个页面。这是 heap 表访问方法的硬约束，也是 TOAST 存在的唯一理由：既不能加宽页面，也不能让行跨页，只能把"大值"从行里搬出去。

1物理边界

单行太宽，页面放不下。页面大小编译期固定，改动代价极高。

2缓存效率

扫描主表时拖着大字段，buffer / CPU / 排序内存被浪费。

3压缩时机

文本可压，图片、视频、加密数据再压只是白烧 CPU。

4读路径

只查 id, status 时，正文、附件不该被搬进内存。

关键
TOAST 的工程取舍是四次交换：用小指针换紧凑主表，用压缩 CPU 换空间和 IO，用表外 chunk IO 换主表扫描效率，用透明机制换开发复杂度 —— 同时把 chunk 膨胀、VACUUM、OID 分配、读放大留给运维。
02 它是什么

TOAST 不是"自动压缩开关"，而是大字段搬运机制

TOAST 是 PostgreSQL heap 表访问方法围绕 varlena 类型实现的一套大字段搬运机制：用 varlena 头部编码、列级 storage 策略、独立 TOAST 表、chunk 唯一索引、压缩方法 和 detoast 读路径，把"行不能跨页"转化为"主表行保存小指针，大值在表外按 chunk 管理"。

边界
它是行存储的延伸，不是对象存储：不解决"所有文件都该进库"、"JSON 可以无限膨胀"、"SELECT * 没代价"这三个建模问题。
03 结构总览

四个层次，从"类型允许吗"一路问到"指针指向哪"

缺任何一层都拼不出完整图像：类型决定能不能 TOAST，列策略决定允许怎么做，TOAST 表存 chunk，指针负责把两者连起来。

读法
自上而下是约束的逐层放松：类型层管"有没有必要"，列层管"允不允许"，表层管"数据落在哪"，指针层管"怎么找回来"。
04 第一层

一切从长度字开始：2 个 bit 换来四种形态

TOAST 并不发明新的存储格式，它只是重新解释 varlena 开头的长度字。因此所有 C 层函数在处理输入前必须先 detoast —— 拿到的可能根本不是"4 字节长度 + 内容"。

实践
任何 C 层函数拿到 datum 后都必须先 PG_DETOAST_DATUM：把前 4 个字节当长度直接读，读到的是被重新解释过的位，结果是垃圾或崩溃。
05 边界的来历

1 GB 不是拍脑袋：32 − 2 = 30 bit

长度字总共 32 bit，被两个形态标志位吃掉 2 bit，剩下的只能表示 2³⁰−1 ≈ 1 GB。这是单个 varlena datum 的逻辑大小上限，不是 TOAST 表的上限，也不是表的上限。

红线
单值接近 1 GB 的设计基本等于选错了地方：要么拆成多行分片，要么换 large object / 对象存储 —— 继续加列只会把 TOAST 表变成第二个文件系统。
06 第二层

四种列策略，本质是两个开关的组合

"允许压缩吗"和"允许搬出主表吗"，两个开关只有四种组合。理解了这张图，EXTENDED / EXTERNAL / MAIN / PLAIN 就不用背了。

选型
拿不准就用 EXTENDED；值本身已压缩、或主要做切片读 → EXTERNAL；确认"绝不能外置"才用 MAIN；PLAIN 基本只属于定长类型。
07 触发条件

触发看的是整行宽度，不是某个字段多大

TOAST 管理代码只在"待存储的行"宽于 TOAST_TUPLE_THRESHOLD（通常约 2 kB）时才启动，然后压缩或外置，直到行宽降到 TOAST_TUPLE_TARGET（也约 2 kB，可用 toast_tuple_target 按表调整）以下，或者再无收益。

误解
"字段超过 2 kB 就一定外置"是错的。短 text 完全可能整条内联；判断顺序是整行宽度 → 列策略 → 压缩收益 → 是否真需要外置。
08 核心流程

行太宽？按优先级四轮让路

heap_toast_insert_or_update() 不是一个阈值判断，而是一串带优先级的动作：先压缩，再外置，最后才动 MAIN 列。

点击任意一轮查看该步之后的行宽
09 写路径

一个 datum 怎么变成 N 行 chunk

toast_save_datum() 做七件事，其中两件是成本大头：切片写行 和 逐行写索引。一次大字段写入，写放大就发生在这里。

1
打开 va_toastrelid 指向的 TOAST 表，以及它的唯一索引
2
算出外部存储大小、原始大小、压缩方法，写进 va_extinfo / va_rawsize
3
为这个值取一个未被占用的 OID → va_valueid（在 TOAST 表索引上查重）
4
按 TOAST_MAX_CHUNK_SIZE 循环切片，从 seq 0 开始编号
5
每片写一行 (chunk_id, chunk_seq, chunk_data)
6
每一行都插一条 TOAST 表索引项（不是一批一次）
7
返回 18 B 的 on-disk 指针，替换主表 tuple 里的原始大值
10 物理布局

为什么 chunk 恰好是约 2 KB

顺序反了：不是先定 chunk 大小再凑页面，而是先定"一页放 4 个 chunk 元组"，再倒推出 chunk 能有多大 —— TOAST_TUPLES_PER_PAGE = 4。

代价
写 6.4 kB 的值 ≈ 写 4 行 + 4 条索引项 + WAL。所以"大字段 UPDATE 慢"往往不是磁盘慢，而是行数与索引项翻了几倍。
11 压缩

压缩是"有机会才用"，不是必用

toast_compress_datum() 先看输入是否够大、再比较压缩后是否真的更小；没有收益就保留原值。所以对已压缩数据设 EXTENDED，只会白烧 CPU。

什么时候该主动关掉压缩（设 EXTERNAL）
  • 已经是压缩格式：jpeg、png、zip、pdf、加密块 —— 再压只花 CPU
  • 高熵数据：哈希、向量、随机 ID、加密载荷
  • 超大文本主要做切片读：substr() 只要一小段时不压缩更划算
  • 写入 CPU 是瓶颈：宁可多占空间，也别在写路径上反复压
注意
SET COMPRESSION 与 SET STORAGE 一样，只影响后续写入；想让旧值生效必须 UPDATE 或重写表。
边界
两个"放弃"条件：输入太小，压了不划算；压缩后没更小，保留原值。所以"设了 EXTENDED 就一定压缩"是错的。
12 读路径

读的时候，header 决定走哪条路

大多数 SQL 用户感受不到 TOAST，因为类型函数、输出函数和执行器会在需要时 detoast。但"需要时"这三个字，就是成本发生的位置。

结论
读放大只发生在真正需要大字段内容的那一刻。所以 SELECT id, status 和 SELECT * 在宽表上的成本可以差一个数量级。
13 切片读取

同一句 substr()，两条完全不同的路

未压缩的外置值可以只取需要的 chunk；压缩值必须先拿到足够的压缩数据才能解压出目标片段。这就是 EXTERNAL "更快但更占空间"的全部原因。

读放大不是"读整行"，而是"为了 50 个字节，读了多少 chunk"
14 生命周期

TOAST 在 MVCC 里，但有自己的chunk 生命周期

它不是一个"外部对象存储"：写入、可见性、回收都跟主表在同一套事务与 WAL 体系里，只是多了一层 chunk 的创建与清理。

15 运维边界

每个外置值要一个 OID，而 OID 会回绕

正常的 toast_save_datum() 会用 GetNewOidWithIndex() 在 TOAST 表索引上验证候选 OID 是否已存在。当单个 TOAST 表占用了大量连续 OID，新值就可能反复撞车。

示意：一个高 churn 的 TOAST 表
为什么不能"换个 OID 就行"
OID 是全局 32-bit 计数器，会回绕；旧 OID 可能在回绕后被重新分配。所以每次分配都必须在 TOAST 表索引上验证唯一性 —— 这就是冲突探测的来源，也是"单表 OID 区间太长就会变慢"的道理。
典型症状
  • 只有涉及大字段的 INSERT / UPDATE 偶发变慢
  • 等待事件里出现 OidGenLock、buffer 相关等待
  • 日志出现持续"搜索未使用 OID"类信息
四个条件叠加才会发生
  • 单表有极大量外置大字段值
  • 宽表多个 TOASTed 列，每行可能消耗多个 value OID
  • 高 churn：频繁插入、更新、删除大字段
  • 长期没有分区、归档、冷热拆分或表重建
治理方向（不是"关掉 TOAST"）
  • 分区 / 拆表，把单个 TOAST 表拆成多个对象
  • 归档历史、写入新表迁移
  • 避免无意义的大字段更新
16 横向对比

同样是"存大东西"，语义完全不同

对比时最容易犯的错是把它们当同类替代品。TOAST 是行存储的透明扩展，large object 是数据库内的大对象 API，对象存储则不在事务里。

五条 SQL，把 TOAST 从"听说"变成"看见"

下面是最小可验证脚本。重点不是某个固定数字，而是看这五个现象是否出现：TOAST 表是否被创建、chunk_id 是否从 NULL 变成 OID、TOAST 大小是否增长、两种查询的 buffer 是否不同、EXTERNAL 下压缩是否为空。

① 建表、强制 EXTERNAL、写入大值

② 看 chunk、看读放大

18 常见坑

六个坑，五个都不是 TOAST 本身的错

TOAST 的失败案例里，绝大多数是建模问题和查询习惯问题，只有 OID 争用属于真正的机制边界。

1只看主表大小

pg_relation_size() 只算主表 fork。宽表要用 pg_total_relation_size()，差额往往就是 TOAST 表加索引。

→ 应对：容量口径统一用 total，监控也用它

2以为 SET STORAGE 立即生效

它只改变后续写入的策略。旧值要按新策略存，必须 UPDATE、重写表或迁移分区。

→ 应对：改策略前先规划一次受控重写

3压缩字段做 substr 仍慢

压缩值要先取足压缩数据再解压。超大文本主要切片读时，EXTERNAL 可能比 EXTENDED 更合适。

→ 应对：按"读的模式"选策略，不按习惯选

4宽表列表页用 SELECT *

只要标题、状态、时间，却把正文、附件、JSON 全选出来 —— 等于主动触发 detoast 和网络传输。

→ 应对：接口层按字段白名单取列

5大 JSON 小改也放大

JSON 是一个 varlena 值。改一个属性也要落一个新值和新 chunk。高频局部修改应拆字段或换建模。

→ 应对：高频改的字段拆成独立列

6忽略 TOAST OID 压力

极高 churn 的宽表会在 value OID 分配上变慢。治理靠清理、归档、写新表、分区，不是调参数。

→ 应对：先看等待事件，再动结构

19 最佳实践

三类角色，三种不同的动作

同一条 TOAST 机制，架构师关心建模边界，DBA 关心可观测性与治理，开发者关心查询和写入习惯。

面向架构师
  • 别当无限列宽：单值约 1 GB，单表还有 OID、VACUUM、索引与膨胀边界
  • 访问分层：常过滤/排序/join 的列留主表；很少读的大字段可同表，也可拆 1:1 扩展表
  • 高 churn 表优先分区：把一张 TOAST 表拆成多个独立对象，降低容量与 OID 压力
  • 文件分发类内容不进 TOAST：元数据在库、内容在对象存储，用 outbox / 状态机保证跨系统一致
  • 先算访问模式：谁读、读几列、多久改一次大字段 —— 这三点决定要不要拆表
面向 DBA
  • 总成本用 pg_total_relation_size()，它含 TOAST 与索引
  • 定期识别 TOAST 大户（见下方 SQL）
  • 大字段偶发慢先确认是否只发生在触发 TOAST 的语句上，再结合等待事件与 chunk_id 数量判断
  • 别手工操作 pg_toast 表：那是内部实现细节
SELECT n.nspname, c.relname, c.reltoastrelid::regclass AS toast, pg_size_pretty( pg_relation_size(c.reltoastrelid)) AS toast_size FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace WHERE c.relkind IN ('r','m') AND c.reltoastrelid <> 0 ORDER BY pg_relation_size(c.reltoastrelid) DESC LIMIT 20;
面向业务开发者
  • 宽表别写 SELECT *：列表页、分页接口、后台任务最容易被它拖垮
  • 别频繁重写大 JSON：改一个属性也要落新值、新 chunk
  • 已压缩二进制设 EXTERNAL：少烧 CPU，还改善切片读
  • 别用 TOAST 字段模拟文件：需要随机写就用 large object、对象存储或分片表
  • 算上表达式索引与触发器：里面调用 detoast 的函数会把成本带进写路径
  • 批量写要控事务大小：一个事务塞太多大字段，WAL 与 chunk 写入一起放大
20 选型

什么时候该用它，什么时候别硬用

适合 TOAST
  • 行语义上天然包含一个中等大小的大字段：文章正文、JSON 配置、消息内容、扩展属性
  • 大字段多数时候不参与过滤、排序、join，只在详情页或后台读取
  • 数据可压缩性好：长文本、重复结构 JSON、日志、XML
  • 需要数据库事务一致性，且对象大小在单值上限以内
  • 大字段更新频率不高，或主要改的是非大字段列
不适合 TOAST
  • 大文件、视频、图片原图、模型权重：需要 CDN 分发或对象生命周期治理
  • 需要对大值做频繁局部随机写，希望像文件一样 seek / write
  • 单表高频插入更新多个大字段，长期积累数十亿级 TOASTed value
  • 查询经常对大 JSON 做深层解析、表达式索引、全文转换，反复 detoast
  • 已压缩或随机数据却仍用默认压缩策略，CPU 换不到空间
✕ 图片 base64 塞进 text 列
体积先涨约 33%，每行都被撑大，还失去 CDN 分发能力
✕ 用 jsonb 存整篇文档并频繁改
每次改动都是新值 + 新 chunk，膨胀落在三处
✕ 列表页 SELECT * 拉正文
读放大 × 网络放大，通常比 TOAST 本身更致命
一句话
字段语义属于这一行 → 用 TOAST；内容需要分发与生命周期治理 → 对象存储；需要随机读写 → large object 或重新建模为多行分片表。
21 收尾

带走五句话

1
页面固定、元组不跨页这是根因。TOAST 不是优化项，是这套设计下的必然产物。
2
主表留 18 B 指针，大值按约 2 KB 切成 chunkTOAST 表 3 列 + 一个唯一索引，靠 (chunk_id, chunk_seq) 重组。
3
触发看整行宽度，不看单列约 2 kB 阈值，四轮优先级：先压 EXTENDED，再外置，最后才动 MAIN。
4
读放大发生在 detoast 那一刻SELECT * 是最贵的习惯；未压缩 EXTERNAL 对切片读最友好。
5
透明 ≠ 无成本chunk 膨胀、VACUUM、OID 分配、单表容量边界，都是这套透明机制留给你的运维债。
