02 背景

慢不是因为找不到，而是找到太多、回表太早

宽事实表 + 临时组合过滤 —— 这是 bitmap 索引唯一真正主场的场景。

典型负载
一张 几十亿行的宽事实表，用户按 region · status · channel · is_vip · event_type 做 临时组合过滤，每次组合都不一样。
一句话结论：如果每个条件都能先变成一串位，用 CPU 的 AND / OR 在索引层就把候选行收缩，再按页回表，随机 I/O 会少很多 —— 这就是 bitmap 索引存在的全部理由。

05 它是什么

三层看它：逻辑是映射，物理是页，执行是集合运算

同一个机制换三个抽象层级描述，才既讲得清原理，又落得到源码。

01

逻辑层

LOGICAL
key value → bitmap vector
  • 每个 distinct key value 一条位向量，互不干扰
  • 第 N 位 = 第 N 个逻辑位置的行是否含该值
  • 查询就是位向量的 AND / OR
02

物理层

PHYSICAL
vector → HRL words → pages
  • 向量切成压缩字，写入 bitmap pages
  • distinct key 的入口放在 LOV 页
  • 压缩用 HRL：64 位 Hybrid Run-Length
03

执行层

EXECUTION
bitmap → TID → heap pages
  • BitmapIndexScan 产生命中集合
  • BitmapAnd / BitmapOr 合并
  • BitmapHeapScan 按页回表并 recheck
三层对不上的地方，就是性能问题的来源：逻辑层看是「一个值一条向量」，物理层看是「一堆页和压缩字」，执行层看是「TID 与 recheck」。

06 物理结构

它不是一张裸 bitmap，而是「小目录 + 辅助查找 + 压缩页链」

源码：gpdb-archive/src/backend/access/bitmap/

为什么需要辅助 btree：如果只有 LOV 页，查一个 key 就得把所有 LOV item 扫一遍；基数越高，这一步越像全表扫描。辅助 heap + btree 把它变成一次等值查找。

07 关键设计

不存 TID 列表，而是把 (block, offset) 压成一个位置编号

这是「一位一行」能成立的根本前提：行必须能被映射到一个稳定的整数序号。

为什么非要压成位置
如果索引里直接存 TID 列表，一条向量就退化成「一堆行号」，多条件组合又得重新求交。换成位置之后， 一条向量是一段连续的位区间：压缩、按位运算、批量解码同时成立。
代价：位置是「稀疏」的
即使某页完全没有任何命中，它的区间也要占位（一串 0）。空间取决于总页数 × 页内槽位，不只是命中行数 —— 这正是 HRL 压缩存在的理由。

09 压缩的边界

同一列、同一基数，数据顺序不同，压缩率天差地别

位向量里的 run 从哪来？来自「相同值的行在 TID 空间里连成片」。

所以，装载顺序是索引设计的一部分
批量装载天然按时间/分区顺序写入时，如果过滤列与写入顺序相关（时间、批次），run 容易形成。 而完全随机的分布键、随机生成的维度值，会让 HRL 几乎失效。
更新会主动破坏 run
改中间一个 bit，可能把一个 fill word 拆成 2~3 个新 word，甚至让页溢出。 在频繁 DML 的列上建 bitmap index，本质是用查询收益换维护债。

10 写入路径

追加很便宜，改中间的 bit 很贵 —— 四种情况，四种代价

这一页解释了「为什么 bitmap index 不适合高更新表」的全部物理原因。

选择左侧任一情况，观察它对 LOV item 和 bitmap 页链的影响。
结论：追加式写入是「改元数据 + 写尾页」；中间改 bit 是「拆 word + 溢出页 + 碎片」。这就是它对更新敏感的全部原因。

12 一个容易忽略的分叉

内存不够时，执行期位图会退化成「一页一位」

注意：这是执行期中间结构的行为，不是 bitmap index 自身的属性。

对使用者的意义
候选行非常多时，bitmap 路径可能因为 lossy + recheck 比想象中慢。看到 Rows Removed by Index Recheck 就该警觉。
别把两件事混起来
「索引里的向量是有损的吗」和「执行期的位图是有损的吗」是两个问题。前者 GPDB 实现为无损，后者受内存约束。

13 横向对比

比的不是「谁更快」，而是各自在优化哪个瓶颈

B-tree 优化有序查找；BRIN / 分区优化粗粒度跳过；bitmap 优化多条件集合运算；Roaring 优化压缩整数集合的随机访问。

维度 Greenplum bitmap index B-tree index BRIN / 分区裁剪 Roaring bitmap
主要目标 多条件分析过滤，先做集合运算再回表 高选择性点查、范围查、排序相关访问 大范围跳过数据块或分区 内存/文件中的压缩整数集合
数据组织 每个 distinct key 一条压缩位向量，LOV 定位 有序 key 到 TID 的树 page range 摘要或分区元数据 32 位空间按高 16 位分 container
写入代价 改中间 bit 可能拆 word、页溢出、碎片化 单行维护成熟，最适合 OLTP 维护摘要 / 元数据，通常较轻 取决于实现，多用于内存集合
读取代价 多谓词快速 AND/OR，回表前收缩候选 单索引过滤好；多索引组合仍要走执行期 bitmap 粗粒度过滤，可能大量 recheck 交并差很快，随机访问优于 RLE

事务 / MVCC 不适合频繁 DML，文档建议少更新 通用事务场景的首选 适合大表扫描裁剪 不是通用数据库二级索引协议
适合场景 数仓、ad hoc 多维过滤、低到中基数 唯一键、高基数、强选择性条件 时间序列、天然分区、大块有序数据 搜索 / OLAP 引擎的 doc id 集合

14 效果评估

收益来自三处，代价也是实打实的四条

评估时别只看「查询快了」，要同时看「写入慢了多少、索引大了多少」。

收益 · 三个来源
① 回表前消减候选行
多个条件先在位图层 AND/OR，需要访问的数据页数量直接下降。
验证：EXPLAIN 里候选行是否明显小于各条件之和
② 顺序化 heap 访问
BitmapHeapScan 把候选 TID 按 page 聚合，缓解普通 index scan 的随机 I/O。
验证：计划里是否出现 Bitmap Heap Scan
③ 压缩降低索引尺寸
HRL 对长 run 很有效；数据按过滤列（或与其相关的列）聚集时，效果最明显。
验证：对比索引体积与 distinct 值数量的关系
代价 · 四条
① 空间与 distinct 值数强相关
官方经验边界：约 100 ~ 100000 个 distinct value 表现较好，超过后效率下降。
边界参考：100 ~ 100000 个 distinct 值
② 写入 / 更新放大
中间 bit 更新可能拆分压缩字，甚至插入 overflow page。
边界参考：DML 比例高的列不要建
③ 唯一列与极低基数列都不合适
唯一列让每条向量极稀疏；极低基数列过滤不掉足够多的行。
边界参考：唯一列 / 命中过半的列
④ 收益依赖组合谓词
单列选择性差时，bitmap 只是在回表前确认「几乎全表都要读」。
边界参考：单列过滤收益有限

16 实操 DEMO

最小实验：三列 bitmap index + 一个三条件查询

语法参考 GPDB 文档与回归测试 bitmap_index.sql；本文未启动集群，因此不提供任何 EXPLAIN ANALYZE 输出。

SET enable_bitmapscan = on;
SET optimizer_enable_bitmapscan = on;

CREATE TABLE bm_sales (
  id bigint, region text, status text,
  channel text, amount numeric
) DISTRIBUTED BY (id);

-- 100 万行：4 个 region / 3 个 status / 3 个 channel
INSERT INTO bm_sales
SELECT g,
  CASE g%4 WHEN 0 THEN 'CN' WHEN 1 THEN 'US' WHEN 2 THEN 'EU' ELSE 'APAC' END,
  CASE g%3 WHEN 0 THEN 'paid' WHEN 1 THEN 'trial' ELSE 'cancel' END,
  CASE g%5 WHEN 0 THEN 'app' WHEN 1 THEN 'web' ELSE 'partner' END,
  (g%1000)::numeric
FROM generate_series(1,1000000) AS g;
ANALYZE bm_sales;

CREATE INDEX bm_sales_region_idx ON bm_sales
  USING bitmap (region);
CREATE INDEX bm_sales_status_idx ON bm_sales
  USING bitmap (status);
CREATE INDEX bm_sales_channel_idx ON bm_sales
  USING bitmap (channel);

EXPLAIN SELECT count(*) FROM bm_sales
WHERE region='CN' AND status='paid'
  AND channel IN ('app','web');
预期计划形态（示意） 不是实测输出
四个观察点：① 计划底部出现 Bitmap Index Scan；② 多条件出现 BitmapAnd / BitmapOr；③ 上层是 Bitmap Heap Scan；④ 关掉 bitmapscan 后计划应切换路径。
想看物理页：pageinspect 提供 bm_metap() / bm_lov_page_items() / bm_bitmap_page_items()。

17 最佳实践

同一个索引，三种角色关注点完全不同

架构师定位置，DBA 盯维护，开发者负责让谓词可被索引。

◆

架构师

WHERE TO PLACE
决定「建在哪、建几个」—— 这一步错了，后面全是补丁。
  • 建在事实表的常用组合过滤维度上，不是把所有低基数列都建一遍。
  • 分区表先评估分区裁剪是否已足够；若要建索引，索引列应不同于分区列。
  • 批量装载优先「先装载、ANALYZE、再建索引」；大批量装载前可先删索引，装完重建。
自检：这个维度是不是真的经常出现在 WHERE 里？
◆

DBA

KEEP IT HEALTHY
索引是「活的」：会碎、会过期、会误导优化器。
  • 重点监控写 / 更新 / 删除比例：DML 一频繁，维护成本就可能吞掉查询收益。
  • 维护统计信息：选择性估错会导致「该顺扫时走索引，该组合时却顺扫」。
  • 大量 UPDATE / DELETE 后考虑重建；VACUUM FULL 场景会通过 REINDEX 处理 bitmap index。
自检：这张表的 UPDATE / DELETE 占比是多少？
◆

业务开发者

MAKE PREDICATES INDEXABLE
索引再好，也救不了写坏的 SQL。
  • 让谓词「裸」着出现在 WHERE 里；把列包进复杂函数会让索引失效，除非显式建表达式索引。
  • 不要为一种低基数过滤强行要 bitmap：gender='M' 命中半张表时，瓶颈仍是读表。
  • 给关键报表保存 EXPLAIN 基线，看的是「是否先组合位图、候选是否真的减少」。
自检：这条 SQL 的谓词能被索引直接用上吗？
三者的共同判断标准只有一句：这条查询的候选集合，能不能在回表之前被显著收缩？能，才谈得上收益。

18 常见坑

这五个坑，几乎每个团队都会踩一个

它们都不在原理层面，而在于「把不同层的东西当成同一层」。

01
把 Bitmap Index Scan 和 bitmap index 混为一谈

计划里的 Bitmap Index Scan 不代表底层是持久 bitmap index —— B-tree 也能产出执行期位图。

02
只看列基数，不看组合选择性

bitmap index 的强项是组合多个条件。单列或组合后仍返回大量行，回表成本一分都不会少。

03
更新后不关注碎片与重建

middle insert / update 会导致 vector fragmentation。在频繁更新的列上建它，等于用查询收益换维护债。

04
把经验阈值当绝对规则

100 ~ 100000 只是文档给出的建议区间；真实效果还取决于行数、压缩、数据聚集、列相关性、segment 分布与查询模式。

05
忽略分布键与数据倾斜

Greenplum 是 MPP 系统，索引在每个 segment 上独立工作。分布键导致热点 segment 时，单机局部索引再快也会被整体并行度拖住。

20 一页纸

记住四句话，就记住了 bitmap 索引

如果只能带走一页，就带这一页。

01 · 它做什么
把「按值找行」变成「按值找一串位」，让多个谓词在回表之前就完成集合运算。
02 · 它怎么存
向量被切成 HRL 压缩字写进 bitmap 页链；distinct 值入口放在 LOV 页，再由辅助 heap + btree 加速定位。
03 · 它赢在哪
候选行在回表前被收缩 + 回表按页顺序化 + 压缩降低索引尺寸。三个收益都指向少读页。
04 · 它输在哪
追加便宜、改中间 bit 昂贵；唯一列与极低基数列都不合适；压缩效果高度依赖数据顺序。
适合
读多写少 多条件 ad hoc 批量装载 中低基数 数仓 / DSS
不适合
OLTP 高并发 DML 唯一列 / UUID 命中过半的表 乱序写入 主键点查
一句话
bitmap 索引不是「更快的 B-tree」，它是把冲突提前：用写入的灵活性，换读取时更少的页。
