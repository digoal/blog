01背景

表大了以后，问题变得很朴素

我们想把「从 N 行里找几行」变成「沿少量页面跳转，定位到一小段有序数据」。

点查
WHERE id = ?

主键 / 唯一键，期望 3–4 次页访问就够

组合条件
user_id = ? AND
created_at BETWEEN ? AND ?

等值 + 范围，复合键一起服务才不浪费

排序分页
ORDER BY created_at
LIMIT 20

要么索引本身有序，要么额外排序

全表扫描的代价
1 亿行、每行 200B ≈ 20GB；全扫 = 把 250 万个 8KB 页 全读一遍。
B-tree 想做的事
只读 3–4 个索引页 + 少量数据页，把随机 IO 压到常数级。

02它解决什么问题

把节点做宽，树就变浅了

二叉树在内存里很好理解；放到磁盘或缓冲池里，每访问一个节点都可能变成一次页访问。

理论出处
Bayer & McCreight, 1972：检索/插入/删除的页访问随 logk(I) 增长
为什么普及
Comer 1979：顺序访问、范围查找、增量维护、空间利用率四者兼顾
代价一：写入不纯追加
页满要 split，删除要清理或合并，随机写制造尾延迟
代价二：只擅长一维
多维组合条件不如 bitmap / GIN / R-tree / zone map

04它是什么

内部页只负责导航，叶子层才是有序数据

数据库里常说的 B-tree 索引，大多接近 B+tree：真正可返回的数据或行定位信息集中在叶子层。

page / block
树节点的物理载体：PG 8KB，InnoDB 16KB，SQLite 512B–64KB
fanout
一个内部页能指向多少子页；key 越短、压缩越好，扇出越高
separator
内部页的导航 key（pivot），决定走向哪个 child
leaf tuple
叶子页里的实际索引项；三种库放的内容差别很大
split
页放不下时搬走一半记录，并把新页入口插进父页
merge / purge
删除后的空间维护：vacuum / purge / balance，名字不同

05先看物理载体

教材画「key 数组 + 指针数组」，源码先面对页格式

同样是 B-tree，三种引擎的页内组织完全不同 —— 这决定了页内查找方式、碎片形态和清理成本。

三个细节值得记住：PostgreSQL 页尾 special area 放 BTPageOpaqueData（left/right link、level）； InnoDB 用 infimum/supremum 伪记录把页内记录串成有序单链，再用 page directory 做稀疏索引加速二分； SQLite 的 cell pointer array 有序、但 cell content 在页内可以物理乱序 —— 这正是它做页内碎片整理的前提。

页内二分靠什么

PG 靠 linp 有序偏移，InnoDB 靠稀疏 page directory 槽，SQLite 靠有序 cell pointer array。

special area 为什么在页尾

left/right link 与 level 放在固定偏移，读页时不用先解析变长 tuple。

碎片从哪来

定长页装变长记录：删掉中间一条就留下空洞，只能靠页内整理或重建回收。

07核心原理 · 写入

先局部改，页满再向上传播

均摊复杂度很好，但线上感受到的是尾延迟：页分裂、父页传播、日志刷写、二级索引维护叠在一起。

填充率（PostgreSQL 的 fillfactor、InnoDB 的 MERGE_THRESHOLD）本质是拿空间换分裂频率：留白越多，splits 越少，但树更胖、范围扫描要读更多页 —— 没有免费的选择。

08核心原理 · 并发

读线程怎么在并发 split 中不走错

Lehman-Yao 的办法很克制：每个页存一个 high key 当上界，再用 right link 串成链，让查找能在页级别自我纠正。

点「播放」看一次「落到旧页 → 沿 right link 修正」的完整过程。

注意边界：right link 解决的是「读路径的自我纠正」，它不能替代 WAL 与恢复协议 —— 崩溃后页面的结构一致性，仍然由日志和 ARIES/IM 这类恢复算法保证。

09核心原理 · 删除

逻辑删除很快，物理回收很慢

B-tree 删除不能只看「把 key 从 leaf 删掉」：还有事务可见性、并发扫描、崩溃恢复和页复用安全。

阶段PostgreSQL nbtreeMySQL InnoDBSQLite btree
删除动作 索引项不立即物理移除，先由 heap 的 xmax 决定可见性 记录打 delete-mark，索引项保留；二级索引同样要维护 cell 直接从页里移除并整理；页过空触发 balance
物理回收 VACUUM、simple deletion、bottom-up deletion、page deletion；重复 key 可压成 posting list purge 线程在没人再需要旧版本时物理移除记录 freelist 复用空闲页，auto-vacuum 收缩文件
谁触发 autovacuum；被长事务、复制槽拖住 后台 purge；受 history list length 影响 事务提交后的 balance 与 checkpoint
要小心 索引膨胀；膨胀后「重建」不是第一反应，先查来源 二级索引只存主键，可能需要回聚簇索引确认状态 大 payload 的 overflow 页、频繁 rebalance
共同点一：删除都便宜

三者的删除路径都是「标记 + 快速改页」，不做大范围搬移。

共同点二：清理都滞后

物理回收交给后台任务，所以「删了表没变小」是正常现象。

共同点三：长事务是公敌

一个长事务能让 vacuum / purge 全部停摆，索引随之膨胀。

10三种工程实现

同样是 B-tree，叶子层的语义完全不同

这一层差异，直接决定了「回表」到底有多贵、二级索引有多大、MVCC 在哪里判断。

PG

索引只是跳板：命中后必须回 heap，候选行越多回表越疼。

InnoDB

主键即物理顺序：主键选错，整张表的写入形态都会变形。

SQLite

rowid 稳定，所以索引可以放心存 rowid 而不存页号。

11横向对比

重点不是排名，是「嵌进事务之后的样子」

B-tree 是一个抽象族；存储引擎把它嵌进事务、日志、页缓存和执行器之后，才形成真实行为。

维度 PostgreSQL nbtree MySQL InnoDB SQLite btree Bw-tree / FAST+FAIR
主要目标 通用二级索引，配合 heap MVCC 表即聚簇索引，二级索引回主键 单文件页式存储；table / index 都是 btree 面向多核、闪存、持久内存重新设计
叶子内容 key + heap TID；重复 key 可压成 posting list 聚簇叶 = 整行；二级叶 = 二级 key + 主键 table 叶 = rowid + 行；index 叶 = key + rowid delta record、mapping table、cache-line aware 布局
并发 split high key + right link（B-link）；页面读锁适配共享 buffer tree latch + page latch；普通 B-tree，不是 B-link 单机嵌入式模型，Pager 统一管锁与事务 CAS 原子改指针、delta 链、持久化 flush 顺序
与 MVCC 可见性主要回 heap 判断 聚簇记录含事务信息；二级索引可能要回聚簇确认 没有 PostgreSQL/InnoDB 式多版本行链 取决于系统设计
删除清理 VACUUM / simple & bottom-up deletion / page deletion delete-mark 后 purge，二级索引一并维护 cell 删除、freelist、balance、auto-vacuum 针对 latch、日志、PM 写放大做优化
最适合 通用 OLTP/OLAP 混合、范围查询、排序 主键访问强、行按主键聚簇、覆盖二级索引 嵌入式、单文件、轻量事务 高并发内存/闪存索引、专用引擎与研究
主要风险 索引膨胀、回表可见性成本、长事务阻塞清理 随机主键页分裂、长主键放大二级索引 大 payload overflow、频繁 page rebalance 实现复杂，恢复协议与内存回收更难

同一份抽象结构，被嵌进不同的日志、锁、MVCC 与缓存体系之后，长出完全不同的行为 —— 所以「B-tree 快不快」这个问题本身没有答案，只有「在这个引擎里、这类负载下快不快」。

12效果如何

四处收益，五笔代价

收益写在文档里，代价写在 P99 里。两边都得看。

+ 收益
树高低
高 fanout 把随机页访问控制在 3–4 层，和 N 几乎无关
天然有序
等值、范围、前缀、排序、merge join 输入全部覆盖
增量维护
不必重建索引，insert / update / delete 都可局部维护
缓存友好潜力
root 与上层 internal 常驻缓存，热点 leaf 复用率高
− 代价
写放大　一次行写入可能维护多个 B-tree；split 还要改父页与 WAL/redo
空间放大　二级索引复制 key 与行定位；InnoDB 长主键进入所有二级索引
回表代价　PG 需访问 heap；InnoDB 未覆盖时回聚簇索引
清理滞后　MVCC 系统不能随便物理删除旧版本与旧索引项
宽 key 降扇出　长字符串、列太多、包含列滥用 → 树更高更胖

13选型

B-tree 只擅长「有序一维键空间」

把不合适的问题硬塞进 B-tree，通常不会报错，只会慢慢变慢。

最适合

高选择性等值、时间/价格区间、分页游标、外键与唯一约束、InnoDB 主键路径

勉强可用

低基数列单独建索引（除非组成有效复合键）、写极重的追加型时序表（考虑 LSM / 分区）

不要硬塞

非前缀模糊匹配、多维范围相交、超宽 JSON/text 当长复合 key

替代思路

表达式索引、前缀索引、hash、倒排、规范化建模，往往比「加一个索引」更省

14实操 DEMO

用同一张表，看三种引擎的不同答案

示例用于验证语义与执行计划形态；本文未启动实例执行，因此不提供伪造的 EXPLAIN ANALYZE 输出。

点击切换 · 同一张 bt_demo 表 
-- 业务表：租户 + 状态 + 时间，典型多条件查询
CREATE TABLE bt_demo (
    id bigserial PRIMARY KEY,
    tenant_id int NOT NULL,
    status text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    payload text
);

-- 复合 B-tree：等值过滤 + 排序方向一起服务
CREATE INDEX bt_demo_tenant_created_idx
    ON bt_demo (tenant_id, created_at DESC);
-- 重复值多的列：观察 deduplication 的影响
CREATE INDEX bt_demo_status_idx
    ON bt_demo (status) WITH (deduplicate_items = on);

ANALYZE bt_demo;

EXPLAIN
SELECT id, created_at FROM bt_demo
 WHERE tenant_id = 42
 ORDER BY created_at DESC
 LIMIT 20;
-- 主键即聚簇索引：表本身按 id 有序存放
CREATE TABLE bt_demo (
    id BIGINT NOT NULL,
    tenant_id INT NOT NULL,
    status VARCHAR(16) NOT NULL,
    created_at DATETIME NOT NULL,
    payload VARCHAR(100),
    PRIMARY KEY (id),
    KEY idx_tenant_created (tenant_id, created_at),
    KEY idx_status (status)
) ENGINE=InnoDB;

-- 1) 覆盖访问：选择的列都在二级索引 + 主键里
EXPLAIN SELECT id, created_at FROM bt_demo
 WHERE tenant_id = 42 ORDER BY created_at LIMIT 20;
-- 2) 需要 payload：二级索引没覆盖，回聚簇索引
EXPLAIN SELECT payload FROM bt_demo WHERE status = 'paid' LIMIT 20;

-- rowid 表：INTEGER PRIMARY KEY 就是 rowid 别名
CREATE TABLE bt_demo (
    id INTEGER PRIMARY KEY,
    tenant_id INTEGER NOT NULL,
    status TEXT NOT NULL,
    created_at TEXT NOT NULL,
    payload TEXT
);

-- 普通索引是独立的 index btree，叶子存 key + rowid
CREATE INDEX bt_demo_tenant_created_idx
    ON bt_demo (tenant_id, created_at);
EXPLAIN QUERY PLAN
SELECT id, created_at FROM bt_demo
 WHERE tenant_id = 42 ORDER BY created_at LIMIT 20;

-- 文件页粒度：观察 page_size / page_count
PRAGMA page_size;
PRAGMA page_count;
该看什么
  • (tenant_id, created_at DESC) 同时服务等值过滤与排序方向，省掉 Sort 节点。
  • status 重复值多，适合用 pg_relation_size() 对比 dedup 开/关的索引尺寸。
  • 收益依赖版本、数据分布与页内空间状态，别把「开 dedup 一定更快」当结论。
该看什么
  • 查询 1 选择的列都在二级索引 + 主键里，可能变成 覆盖访问，完全不回表。
  • 查询 2 要 payload，二级索引没覆盖，必须用主键回聚簇索引取整行。
  • 这就是「索引命中 ≠ 查询快」：命中后还有多少行要回表，才是关键变量。
该看什么
  • rowid 表以 rowid 为 table btree 的 key，普通索引是独立的 index btree。
  • EXPLAIN QUERY PLAN 验证是否走索引；PRAGMA 看文件页粒度。
  • TEXT 存时间时，字符串的字典序必须与时间序一致才能用索引排序。

15最佳实践

同一个索引，三种角色的不同责任

架构师决定「要不要建」，DBA 盯「有没有坏」，开发者负责「别把它用废」。

数据库架构师

决定「要不要建」

先定主访问路径

InnoDB 主键决定聚簇顺序；随机 UUID = 随机写 + 页分裂 + 缓存抖动

控制 key 宽度

宽 key 降低 fanout，还放大二级索引与 WAL/redo 体积

按 workload 选结构

一维范围与排序用 B-tree；多维、全文、数组别硬塞

显式决定填充率

批量导入或高并发随机插入的表，用 fillfactor 留白

DBA

盯「有没有坏」

盯膨胀与清理延迟

PG 看 autovacuum / 长事务；InnoDB 看 history list length

重建不是第一反应

先查膨胀来源：长事务、更新模式、填充率，还是索引不匹配

让统计信息跟上

基数、相关性、直方图、页成本 —— 估错就会选错索引

用同一把尺子对比

前后都记录索引用量、尺寸、命中率、P99，别凭感觉

业务开发者

负责「别把它用废」

匹配左前缀与排序方向

(tenant_id, created_at) 服务等值 + 排序，不等价于任意组合

覆盖索引要克制

塞太多列会让 leaf tuple 变宽，反而降低缓存效率

关注被更新的列

高频更新列在多个索引里 = 每次更新多次 B-tree 删插

别在索引列上套函数

隐式转换与函数包裹会让普通 B-tree 直接失效

判断顺序 先看查询形态（一维还是多维）→ 再看选择性（能过滤掉多少行）→ 最后看维护成本（写放大与清理延迟）—— 顺序反了，就会做出「加了索引反而更慢」的决定。

16常见坑

八个坑，踩过的人都在这里

这些坑的共同点：不会报错，只会悄悄变慢。

01
把 B-tree 当万能索引

B-tree 是有序一维结构，不擅长所有检索问题。

怎么避　多维用 GiST、包含用 GIN、粗过滤用 BRIN、低基数组合用 bitmap。

02
忽视回表成本

候选行太多、回表随机、可见性检查多，都可能慢。

怎么避　用覆盖索引或更窄的候选集；EXPLAIN 要看回表行数，而不是只看「走了索引」。

03
随机主键导致聚簇写抖动

InnoDB 里主键选择会改变整张表的物理组织。

怎么避　用有序 UUID、雪花 ID 或自增键；接受代价就要同时监控页分裂。

04
长事务阻塞清理

VACUUM 与 purge 被拖住，索引膨胀随之而来。

怎么避　盯 longest transaction / history list length，把长事务拆小、别开着事务等网络。

05
复合索引列序随意

列顺序要服务等值 / 范围 / 排序与选择性，不是把 WHERE 里的列堆进去。

怎么避　等值列在前、范围列在后；排序列方向要和索引声明一致。

06
统计信息陈旧

优化器不知道真实分布，可能放弃好索引，或选中坏索引。

怎么避　调 autovacuum / analyze 频率，复杂相关性用 extended statistics。

07
只看平均延迟

页 split、WAL 刷写、后台清理争用，都体现在 P99 / P999。

怎么避　用分位延迟和等待事件定位，不要用均值判断「快不快」。

08
误解唯一索引成本

唯一约束要做冲突检查，并发插入相同 key 还需额外同步。

怎么避　确认业务真的需要唯一性；高冲突场景可考虑普通索引 + 业务侧校验。

一句话 索引命中只说明「找到了入口」，不说明「代价可接受」—— 判断标准永远是要回表多少行、这些页在不在缓存里。

17总结

四句话，带走 B-tree

结构决定了成本的形状；实现决定了成本的数字。

01
用扇出换深度

一页装几百个 key，亿级数据也只有 3–4 层。真正的成本是「页在不在缓存」，不是比较次数。

02
叶子层才是语义所在

PG 存 TID、InnoDB 聚簇存整行、二级存主键、SQLite 存 rowid。回表成本从这里长出来。

03
写入的痛点在传播

split 从叶子传到 root，叠加 WAL/redo 与多个二级索引；B-link 让读操作能自我纠正，不用等父页。

04
它只擅长一维有序

多维用 GiST、包含用 GIN、粗过滤用 BRIN、低基数组合用 bitmap。选错结构，加索引只会更慢。

留给自己五个问题

Q1　PG 叶子直接存行而不是 TID，会改变哪些 MVCC 与 VACUUM 设计？

Q2　InnoDB 二级索引为什么存主键？存物理页号 + 槽位会遇到什么维护问题？

Q3　key 从 8B 变 200B，fanout、树高、buffer 命中率、WAL 量如何变化？

Q4　right link 已能解决 split 并发，为什么还需要 WAL 与恢复协议？

Q5　持久内存场景下，为什么「改页后写日志」被 Bw-tree / FAST+FAIR 重新审视？

Levandoski et al., The Bw-Tree, ICDE 2013
