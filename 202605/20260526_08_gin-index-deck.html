共同点 谓词问的都是「这一行里，有没有某个元素」，而不是「这一行整体等于/大于某个值」。
尴尬 1

→ 于是这类谓词只能靠扫描后再过滤

→ 回表次数随行数线性增长

02 · 关键一步/倒排模型

把映射翻过来：从 行 → 值 到 key → 行集合

左 表 · 写 入 侧

一行里有多少个元素，就产生多少个 key —— 这是写放大的来源。

右 表 · 查 询 侧

一个 key 覆盖多少行，决定这个 key 的选择性。

中 间 那 一 步

写入走 extractValue()，查询走 extractQuery()，两者都由 opclass 提供。

03 · 它是什么/核心抽象

三层抽象：item · key · posting

Generalized 这个名字的由来：索引访问方法本身不理解 JSONB、数组、全文各自的语义，语义全部由 opclass 注入 —— 这就是下一节的分工。
一句话 索引里不存 item 本身，只存从 item 抽出来的 key，外加每个 key 的 TID 集合。所以它天生只能回答「包含」，不能回答「等于整行」。

05 · 核心原理/语义边界

GIN 只管框架，语义全部交给 opclass

同一套 GIN 框架，不同的 opclass 行为差别很大
array_ops jsonb_ops　支持 @> ? ?| ?& @? @@ jsonb_path_ops　更小，但不支持 ? 系列 tsvector_ops pg_trgm　候选过滤，不是搜索引擎
推论 GIN 只负责并发、WAL、页面、posting 集合与扫描框架；「从值里抽什么 key、哪些 operator 能用、要不要 recheck」由 opclass 决定。所以谈 GIN 性能，先说清 opclass。

06 · 核心原理/两种叶子项

同样是 B-tree 叶子，装的却是完全不同的东西

为什么不能 index scan

GIN 索引项只保存原值的一部分，无法重构完整 indexed value，因此通常也不支持 index-only scan。

为什么必须是 bitmap

main index 与 pending list 可能给出重复 TID，bitmap 天然去重，这也是 GIN 不实现 amgettuple 的原因之一。

为什么没有排序

TID 的物理顺序 ≠ 业务顺序；ORDER BY 相关度 必须另想办法。

08 · 压缩/差值 + varbyte

TID 天生有序，所以能只存「差多少」

为 什 么 值 得 压

posting 是 GIN 体积的大头。TID 密集时，6 字节/项能压到 1–2 字节/项。

代 价 是 什 么

只能顺序解压，不能随机定位某个 TID；更新要重编码整段。

对 查 询 的 影 响

扫描是流式的；真正贵的是候选太大导致的 recheck，而不是解压本身。

09 · 写入路径/fastupdate

写入慢的根因：一行进来，可能变成很多次索引插入

工程边界 fastupdate 降低的是前台单次写入成本，不是让维护成本消失：它被推迟到 cleanup，而且查询必须额外线性扫一遍 pending list。阈值太大 → 单次 cleanup 更痛；阈值太小 → 频繁付合并成本。
数据库筑基课 · GIN 索引结构10 / 19
10 · 查询路径/先 pending，再 main

查询返回的不是有序行，是一张 TIDBitmap

为什么顺序不能反
如果先扫 main index，之后并发的 cleanup 把 pending entry 合并进主结构 —— 这些条目就被漏掉了（扫过的那段不会再回来看）。
先扫 pending 则最坏情况只是同一个 TID 被置位两次，bitmap 天然幂等。
代价 pending 越大 → 每次查询多扫的页越多　·　候选集越大 → recheck 越重　·　work_mem 不够 → bitmap lossy，整页回表
数据库筑基课 · GIN 索引结构11 / 19
11 · 并发与回收/边界在哪里

entry tree 从不删 key，posting tree 才回收页

VACUUM 会做
  • 遍历 entry tree 叶子
  • 清理 posting list 中已死的 TID
  • posting tree 页清空后调用 ginScanPostingTreeToDelete() 删空页
  • 把 pending list 合并进主结构
VACUUM 不会做
  • 不从 entry tree 删除 key tuple
  • 不立刻复用被删掉的页 —— 先打 xid 标记
  • 不替你做容量规划

打 xid 标记是为了避免并发 reader 顺着旧的 downlink / rightlink 走进一个已被复用的页面。

所以 GIN 的「膨胀」不只是死 TID：它还包括 entry key 的永久生命周期、posting tree 空页回收、pending list 周期性合并三个层面。长期高频更新的表，必须把这三件事写进容量与 autovacuum 设计。
监控　pgstatginindex() 的 pending pages / tuples
回收　定期 gin_clean_pending_list()，并放过长事务
容量　把 key 生命周期与 posting tree 空页计入增长模型

12 · 横向对比/四种访问方法

不是「哪个索引更快」，是「哪个查询语义更贴」

维度 GIN B-tree GiST BRIN
主要目标 复合值内部 key 的包含、成员、全文 标量等值、范围、排序 可扩展搜索树：空间、相似、签名 大表块范围摘要
基本映射 key → TID 集合 value → TID predicate → 候选 block range → 摘要
最强场景 jsonb @> · 数组 @> / && · tsvector @@ · trigram 候选 主键、外键、时间范围、排序分页 地理空间、范围重叠、近邻 时间序列、追加写、物理顺序相关
写入代价 高：一行多 key，可延迟 中：一行一个索引项 中到高，依 opclass 低：按块摘要
查询输出 TIDBitmap，通常 Bitmap Heap Scan index scan / index-only scan 候选集，常需 recheck 候选块，常需 recheck
空间成本 取决于 key 数、重复度、posting 压缩与 pending 取决于 key 宽度与行数 取决于签名与树结构 通常很小
典型风险 pending 过大、热词低选择性、更新放大 随机写 split、膨胀、宽 key false positive、opclass 语义复杂 物理相关性差时过滤很弱
选型口诀 标量找 B-tree；复合值里找元素找 GIN；空间近邻找 GiST；超大追加表跳块找 BRIN。四者不是竞争关系，同一张表可以同时有它们。

13 · 效果/收益与代价

收益来自四处，代价也同样具体

GAIN 收益：把工作提前到写入阶段
把行内解释提前到写入阶段

查询时不再逐行解析 JSONB / 数组 / tsvector，只做 key 查找与集合运算。

相同 key 只存一次

一个热词或 JSON key 对应一组 TID，数据重复度越高越省空间。

集合运算下推到 TID 层

多个 key 先求交、并，再统一回表，回表次数可控。

fastupdate 摊平小批量写

持续低频写入的 OLTP 场景很受用，前台延迟稳定。

COST 代价：每一项都写在结构里
写放大

一行抽出多少 key，就可能有多少索引 entry 需要维护。

读路径受 pending list 影响

pending list 越大，查询越要多做一遍线性扫描。

热 key 低选择性

posting 很大、回表很多，收益反转成负担。

不能承担排序需求

GIN 不是按结果顺序返回的访问路径，相关度排序要另设计。

通常不能 index-only scan

索引项只保存原值的一部分，无法重构完整 indexed value。

评估强依赖 workload

查询语义、更新强度、存储约束共同决定，没有通用答案。

15 · 实操/最小验证脚本

先跑 EXPLAIN (ANALYZE, BUFFERS)，再谈结论

6.1　JSONB CONTAINMENT
CREATE TABLE gin_doc_demo (
  id   bigserial PRIMARY KEY,
  jdoc jsonb NOT NULL);

INSERT INTO gin_doc_demo (jdoc)
SELECT jsonb_build_object(
  'tenant', g % 100,
  'status', CASE g % 5 WHEN 0
     THEN 'paid' ELSE 'active' END,
  'tags', jsonb_build_array('postgres'))
FROM generate_series(1,200000) g;

CREATE INDEX gin_doc_demo_jdoc_idx
  ON gin_doc_demo USING gin (jdoc);
ANALYZE gin_doc_demo;

EXPLAIN
SELECT id FROM gin_doc_demo
WHERE jdoc @> '{"tenant":42,"status":"paid"}';
变体：jsonb_path_ops

只做 containment / jsonpath 时，可以建第二个索引对比体积与耗时；但它不支持 ? 系列，别把两者混用。

6.2　数组包含 / 交叠
CREATE INDEX gin_array_demo_tags_idx
  ON gin_array_demo USING gin (tags);

EXPLAIN SELECT id FROM gin_array_demo
WHERE tags @> ARRAY['postgres','bucket_42'];

EXPLAIN SELECT id FROM gin_array_demo
WHERE tags && ARRAY['jsonb','fts'];

-- value = ANY(tags) 不是同一个 operator
-- 想当然认为它走 GIN，是常见误判
6.3　pending list 观测
SELECT * FROM pgstatginindex(
  'gin_doc_demo_jdoc_idx'::regclass);

SELECT gin_clean_pending_list(
  'gin_doc_demo_jdoc_idx'::regclass);

ALTER INDEX gin_doc_demo_jdoc_idx
  SET (fastupdate = off, 
       gin_pending_list_limit = '64MB');

16 · 最佳实践/三个角色，三套动作

同一个 GIN，架构师 / DBA / 开发各看一面

ARCHITECT
数据库架构师
先建模，再选 GIN

JSONB 里已是高频过滤、排序、关联条件的字段，应提升为普通列并用 B-tree，而不是让一个大 JSONB 包打天下。

按 operator 选 opclass

jsonb_ops 覆盖面广；jsonb_path_ops 更窄但通常更紧凑；pg_trgm 的 GIN 只是候选过滤。

拆分热路径

tenant_id 走 B-tree、JSONB 走 GIN，让 planner 做 bitmap combine；或把租户条件放进分区与局部索引。

DBA
运维
盯住 pending list

用 pgstatginindex() 看 pending pages / tuples；配合 pg_stat_user_indexes 看扫描频率与命中收益。

调 autovacuum，不只调阈值

增大 gin_pending_list_limit 减少 cleanup 次数，但会放大单次 cleanup 与查询扫描 pending 的成本。

批量导入优先后建索引

大批量插入先 drop GIN、导入后重建；maintenance_work_mem 对 GIN build 很敏感。

DEVELOPER
业务开发者
表达式必须对上

建在 to_tsvector('english', body) 上，就只稳定支持同样配置的同一个表达式。

别直查低选择性热词

停用词、极高频词、几乎每行都有的 key —— GIN 会退化成「大量候选 TID 生成器」。

不要期待 GIN 排序

相关度排序、时间排序、深翻页另设计：先收窄候选，再结合 B-tree，或交给专门搜索系统。

17 · 常见坑/六个高频误判

坑几乎都来自「以为 GIN 懂语义」

01 以为 jsonb GIN 支持所有写法

jdoc @> …、jdoc ? …、jdoc -> 'tags' ? 'x' 是三个不同表达式。最后一个用不上 jdoc 上的 GIN。

→ 给表达式单独建索引：USING gin ((jdoc -> 'tags'))

02 jsonb_path_ops 选错

它常常更小更快，但不支持 ?、?|、?&；它也不为「不含值的结构」建索引项。

→ 大量查 key 存在性时，默认 jsonb_ops 更稳。

03 pending list 变成尾延迟来源

写入高峰后查询突然变慢 —— 别只看「索引在不在」，要看 pending pages / tuples、autovacuum 是否及时、是否有长事务。

→ 先查 pending，再怀疑索引没建对。

04 热词让 GIN 退化成大候选扫描

GIN 找 key 很快，但 key 命中大部分行时，后面的 bitmap 与 heap recheck 才是真正成本。

→ 处理停用词、改写查询、给结果集设上限。

05 把 GIN 当复合 B-tree 用

多列 GIN 是在 composite (attnum, key) 上建一棵 entry tree，不提供列顺序的排序能力。

→ 排序分页仍要 (a,b) B-tree 或分区裁剪。

06 忽略 VACUUM 与 bloat

GIN 不从 entry tree 删 key；VACUUM 清的是 posting 中的死 TID 和 posting tree 空页。长期更新表必须把维护纳入容量设计。

→ 把 key 生命周期与空页回收写进运维手册。

18 · 收束/带走的四句话

GIN 把「包含」变成一次集合运算，代价写在结构里

01

GIN 索引的是 从 item 抽出的 key，不是 item 本身；所以它回答「包含」，不回答「等于整行」。

02

结构就四件：metapage + entry tree + posting(list / tree) + pending list；冷热 key 走两条不同的 posting 路径。

03

查询产出的是 TIDBitmap：必须先 pending、再 main，最后统一回表做可见性与 recheck。

04

写放大的代价是真的：一行多 key → 多次索引维护；fastupdate 只是把成本挪到未来。

所 以 ， 正 确 的 问 法 不 是 「 加 不 加 GIN 」
而是：这个 operator 有 opclass 吗？抽出的 key 有选择性吗？更新与 cleanup 扛得住吗？recheck 之后剩下的结果集够小吗？
