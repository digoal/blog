01 / 背景　·　MOTIVATION

查询条件不再是「线性有序标量」

共同点：要判断的是「一个对象是否可能满足某个领域谓词」，而不是 = / < / > 的全序比较。

图 2　一维全序 vs 多维谓词B-tree 的路径 vs GiST 的路径
业务里反复出现的五类问题
  • 01找出和某个多边形相交的地块
  • 02找出距当前位置最近的 10 个门店
  • 03判断两个时间区间 / 区域 / 网段是否重叠
  • 04排班、价格有效期、空间资源的「不允许重叠」约束
  • 05轨迹数据同时按空间范围 + 时间范围过滤
根本矛盾

B-tree 可扩展比较函数，但能力仍围绕全序关系

GiST（Generalized Search Tree）解决的是另一个层次的问题：把「搜索树的数据库工程部分」和「数据类型的搜索语义」拆开。

定位

经典论文把它定义为支持可扩展查询与数据类型的索引结构，可把 B+-tree、R-tree、RD-tree 统一进一套搜索树框架；PostgreSQL 文档称它是「实现任意索引方案的基础模板」。

本页要点不是「B-tree 慢」，而是「全序关系表达不了这些谓词」。
02 / 它解决什么问题　·　THE TRADE-OFF

两个极端之间，切一刀

没有 GiST 时，扩展作者只能二选一；GiST 把「数据库工程」与「领域语义」拆成两半。

极端 A　·　工程成本极高

每种类型写一个完整访问方法

页格式、锁、WAL、崩溃恢复、并发分裂、VACUUM、优化器接口，全部自己实现一遍。

极端 B　·　语义被迫变窄

压成普通标量后交给 B-tree

实现简单，但空间相交、区间重叠、最近邻这类谓词很难自然表达。

GiST 的折中　·　分工

core 管树，opclass 管语义

通用树结构、页面、WAL、锁、搜索、插入、构建、VACUUM 由 GiST core 负责；key、query 与领域谓词由 operator class 解释。

图 3　一条清晰的接口边界PostgreSQL 源码：gist.c / gist_private.h / gist.sgml

代价必须一起讲：GiST 通常保存「可剪枝的摘要」或「子树谓词」，很多查询只能先得到候选，再回表或复查真实值。摘要太粗、数据高度重叠、第一列选择性很差时，GiST 会扫描很多候选，性能可能不如预期。

本页要点opclass 作者不写锁和 WAL，但必须认真设计摘要、距离下界、split 策略与 recheck 语义。
03 / 它是什么　·　STRUCTURE

内部页存「子树谓词」，叶子页存「key + TID」

平衡树；但内部项不是 B-tree 的排序边界，而是「这个子树可能包含什么」。

04 / 核心原理 3.1　·　PREDICATE TREE

B-tree 靠全序定位，GiST 靠 consistent 剪枝

叶子项是 (key, TID)，内部项是 (predicate, child page)；predicate 不必是范围，也不必可排序。

图 5　同样一棵平衡树，两种「内部 key」的含义左：唯一路径　/　右：多条路径

不变量

父 predicate 不能排除任何「可能命中」的 child，否则会漏查。

判据

内部页 consistent=false 时，整个子树都不必访问。

结果

consistent=true 只表示「可能」，精确答案交给 recheck / 真实值。

本页要点GiST 的通用性来自「谓词」这个抽象；*High-Performance Extensible Indexing* 把它概括为：通用算法 + 领域函数。

08 / 核心原理 3.4　·　KNN

ORDER BY geom <-> point LIMIT 10 为什么能走索引

不是因为 GiST「懂几何距离」，而是 PostGIS opclass 提供了可用于优先队列的距离下界。

图 9　内部节点 distance 的正确含义，以及一个错误示范反例已被虚线框隔离，不是本讲主张

前提

opclass 提供 ordering operator 与 distance support function。

硬要求

内部节点的 distance 必须是子树里任意真实对象到 query 的距离下界。

收尾

叶子 box 距离只是真距离的下界 → recheck=true，用真实 geometry 修正排序。

本页要点下界保证「不漏掉更近的」；recheck 保证「返回的顺序是真的」。

10 / 核心原理 3.6　·　CONCURRENCY

搜索只锁一页，也不能漏掉刚分裂出来的右兄弟

页分裂不是瞬间完成的逻辑动作：先分裂子页，再补父页 downlink。这个窗口里并发扫描必须仍不漏查。

rightlink

页分裂后，左页指向右兄弟；新页在父 downlink 到位前也可达。

F_FOLLOW_RIGHT

标记「右页还没有父 downlink」，扫描看到就追右链。

VACUUM 的克制

当前实现只删除空叶子页，不删内部页最后一个 child；回收是 best-effort。

本页要点F_DELETED / F_HAS_GARBAGE 与 deleted page 的 deleteXid 一起，保证旧扫描仍可安全完成。
11 / 核心原理 3.7　·　BUILD

CREATE INDEX 不是只有「一条条插」

gistbuild.c 先检查每个 key column 是否提供 GIST_SORTSUPPORT_PROC；都有就走 GIST_SORTED_BUILD。

图 12　构建策略的决策分叉官方文档：sorted method 通常是最优先选择
方式 1　·　最简单

逐条插入

每个 tuple 走一遍 penalty / picksplit。大索引 + 随机输入容易产生大量随机 IO。

无额外临时空间
方式 2　·　减少随机 IO

buffering build

给部分内部节点挂 buffer，先把 tuple 推到 buffer，再批量向下 flush；插入顺序更接近广度优先。

需要临时空间 · 可能影响树质量
方式 3　·　通常最优

sorted build

所有列都有 sortsupport 时，先按保持局部性的顺序排序输入，再自底向上构建页，类似 B-tree 构建。

文档：usually the best, used by default

DBA 视角：大表建 GiST 要关注 CREATE INDEX CONCURRENTLY、维护窗口、临时空间与 IO；没有 sortsupport 时，CREATE INDEX 会逐 tuple 用 penalty / picksplit 插入，明显更慢（官方文档原文）。

本页要点构建方式由 opclass 能力决定，不是由用户随手选；树质量又反过来影响后续查询的剪枝率。

14 / 效果如何　·　EVIDENCE

三类收益是真的，论文数字不能照搬

工程上评价 GiST，要看四个指标；论文里的加速比，必须连实验条件一起读。

三类收益

① 减少扩展索引的工程成本

1995 年论文把 B+-tree / R-tree 的通用部分抽象出来；1999 年论文进一步强调 core 封装了搜索、更新、并发控制与恢复。

② 复杂谓词上的有效剪枝

PostGIS 用 R-tree-over-GiST 存 bbox，先过滤不可能的几何对象再精确计算；大于几千行的空间表，建 GiST 空间索引通常是基本动作。

③ 最近邻与复合谓词

distance 支持 KNN；多列 GiST 可用任意列子集，但第一列最影响扫描范围（官方 indexes-multicolumn.html）。

论文数字 · 连同实验条件一起读

约 14% – 40% CPU 时间：*High-Performance Extensible Indexing* 在 Informix IDS/UDO 架构里比较 GiST-based R-tree 与 built-in R-tree，部分插入 / 搜索操作因 UDF 调用更少而省 CPU。不能等同于「PG GiST 比所有空间索引快」。

1490 ms → 31.38 ms（约 47.5×）：复合 GiST 时空查询论文，1000 万条合成数据的某个实验查询。依赖数据分布、查询、硬件、opclass 与统计信息。

最高一个数量级：MGiST / MSP-GiST 把复杂对象拆成多个 index entries，针对轨迹的点 / 范围 / KNN 查询。研究原型，不是当前 PG/PostGIS 主线默认行为。

图 14　评价一个 GiST 索引，看这四个指标「候选多、命中少」就是摘要或写法出了问题
本页要点论文回答机制是否成立；生产系统要回答「在我的数据分布下，剪枝率与复查成本是否可接受」。
15 / 实操 DEMO 6.1 – 6.2　·　SQL

两条最典型的 GiST 查询

SQL 语法按 PostgreSQL/PostGIS 文档与本地源码中的 opclass 名称编写；当前工作区只有源码，没有运行中的实例与测试数据，示例未执行。

1PostGIS 2D 空间过滤
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE poi (
  id bigserial PRIMARY KEY,
  name text NOT NULL,
  geom geometry(Point, 4326) NOT NULL
);

CREATE INDEX poi_geom_gist_idx
  ON poi USING gist (geom);

EXPLAIN
SELECT id, name FROM poi
WHERE geom && ST_MakeEnvelope(
        120.0, 30.0, 121.0, 31.0, 4326)
  AND ST_Intersects(geom, ST_MakeEnvelope(
        120.0, 30.0, 121.0, 31.0, 4326));
读法：geom && envelope 是 bounding box 过滤，适合触发 GiST；ST_Intersects 是精确语义。计划可能是 Index Scan，也可能是 Bitmap Index Scan + Bitmap Heap Scan，取决于统计信息与成本估算。
2KNN 最近邻
EXPLAIN
SELECT id, name
FROM poi
ORDER BY geom <-> ST_SetSRID(
    ST_MakePoint(120.5, 30.5), 4326)
LIMIT 10;
依赖：PostGIS gist_geometry_ops_2d 的 ordering operator <-> 与 gserialized_gist_distance_2d()。叶子 box 距离不等于真实 geometry 距离，源码在 <-> 叶子场景设置 recheck = true。
图 15　两种扫描的输出方式gistget.c

提醒：geometry 的 <-> 在经纬度坐标下不是米制地球距离；需要米制距离时评估 geography、投影坐标系或二阶段排序。

本页要点索引条件要写成 opclass 能识别的 operator；被函数包住的复杂表达式，可能需要表达式索引。
16 / 实操 DEMO 6.3 – 6.4　·　SQL

把「空间 + 时间」和「不允许重叠」交给同一棵树

复合 GiST 与 EXCLUDE 约束，是 GiST Predicate 模型最直观的两个落地场景。

3空间 + 时间复合 GiST
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE vehicle_ping (
  vehicle_id bigint NOT NULL,
  ts timestamptz NOT NULL,
  geom geometry(Point, 4326) NOT NULL,
  valid_at tstzrange GENERATED ALWAYS AS
    (tstzrange(ts, ts, '[]')) STORED
);

CREATE INDEX vehicle_ping_geom_time_gist_idx
  ON vehicle_ping USING gist (geom, valid_at);

EXPLAIN
SELECT vehicle_id, ts FROM vehicle_ping
WHERE geom && ST_MakeEnvelope(
      120.0, 30.0, 121.0, 31.0, 4326)
  AND valid_at && tstzrange(
      '2026-05-26 10:00+08',
      '2026-05-26 11:00+08', '[)');
注意列顺序：若空间范围很大而时间条件很窄，要比较 (geom, valid_at)、(valid_at, geom)、分区 + B-tree/GiST 组合，不能假定一个复合 GiST 永远最好。
4排他约束 / temporal uniqueness
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_booking (
  room_id int NOT NULL,
  during tstzrange NOT NULL,
  EXCLUDE USING gist (
    room_id WITH =,
    during WITH &&
  )
);
读法：同一 room_id 下，during 区间不允许重叠。btree_gist 为标量列提供 GiST opclass；range 类型自身有 GiST 支持。官方文档中 temporal primary key / unique 的 WITHOUT OVERLAPS 底层也是 GiST 思路。
图 16　同一个 EXCLUDE 里的两种谓词标量相等 + 区间重叠

边界：btree_gist 的价值是让标量列参与 GiST 复合索引或排他约束，不是替代普通 B-tree；它通常不会超过标准 B-tree，也不能像 B-tree 那样 enforce uniqueness。

本页要点复合索引的第一列低基数时，后续列很难挽救大量扫描——这是 PostgreSQL 文档明写的限制。
17 / 最佳实践　·　PLAYBOOK

架构师选模型，DBA 看代价，开发者写对谓词

同一个 GiST 索引，三类角色关心的是三件不同的事。

面向数据库架构师
  • 01按谓词模型选索引，不按名字选：空间相交 / 范围重叠 / KNN / 排他约束优先 GiST；全文 / JSONB / 数组包含优先 GIN；纯标量范围与排序优先 B-tree。
  • 02复合 GiST 的列顺序按过滤能力与查询形态验证，第一列最影响扫描范围。
  • 03轨迹、多段线、超大 polygon 警惕单个 bbox 过粗：考虑切分对象、分区、预聚合 tile 或专门轨迹索引。
  • 04空间 + 时间方案要在复合 GiST、时间分区 + 空间 GiST、bitmap AND、BRIN 之间用指标比较。
面向 DBA
  • 01建索引后及时 ANALYZE；空间选择性估算依赖统计信息（gserialized_estimate.c 处理 2D / ND histogram）。
  • 02大表关注 CREATE INDEX CONCURRENTLY、维护窗口、临时空间与 IO；sorted build 依赖 opclass sortsupport。
  • 03监控 idx_scan / idx_tup_read / idx_tup_fetch、Rows Removed by Filter、Recheck Cond。
  • 04频繁更新时关注 VACUUM、膨胀与写放大；空叶子页删除是 best-effort，必要时评估 REINDEX CONCURRENTLY。
面向业务开发者
  • 01条件写成 opclass 能识别的 operator：&& / &&& / <-> 及可被 planner 展开的空间函数。
  • 02ST_DWithin(geom, point, r) 往往比 ST_Distance(geom, point) < r 更容易走索引，前者能形成 bbox 过滤。
  • 03坐标系要一致：geometry 距离单位取决于 SRID；geography 更适合经纬度地球距离。
  • 04低选择性、大范围扫描、返回大比例数据时，顺序扫描或 BRIN / 分区可能更便宜。
本页要点「候选很多但最终命中很少」通常说明：摘要粗、统计不准、谓词写法不利于索引，或列顺序不合适。
18 / 适合与不适合　·　DECISION

先按谓词分流，再看数据分布

GiST 很强，但它不替代 B-tree，也不擅长「命中大部分表」的查询。

✓　适合
  • 01空间对象：点线面、地理围栏、附近搜索、空间 join 的候选过滤。
  • 02范围对象：时间区间、价格有效期、IP / network 包含与重叠。
  • 03最近邻：ORDER BY <-> LIMIT n，前提是 opclass 提供正确的 distance。
  • 04排他约束：会议室、设备、价格生效区间、空间资源不允许重叠。
  • 05多维候选过滤：空间 + 时间组合，且第一列选择性足够好。
✗　不适合
  • 01纯主键 / 外键 / 唯一约束：B-tree 更直接；btree_gist 不能 enforce uniqueness。
  • 02JSONB / 数组 / 全文「包含多元素」：GIN 的倒排结构更自然。
  • 03大范围、低选择性空间查询：命中大部分表时，索引扫描 + 回表可能比顺序扫描更慢。
  • 04摘要高度重叠：大量跨全城长线、覆盖全域大 polygon，bbox 很难剪枝。
  • 05写入极频繁且查询收益不明确：要维护树与 split，收益需用计划和延迟验证。
图 17　按谓词模型分流一次选择，先问「条件是什么」
本页要点选型的判断依据是「谓词模型 + 数据分布 + 候选与复查成本」，不是索引名字。
19 / 常见坑　·　PITFALLS

索引建出来了，不代表查询就对了、就快了

八个高频误判，每一个都能对应回前面的某条原理。

坑 1　·　谓词写法

把 ST_Distance() < r 当成可索引条件

更稳妥：ST_DWithin(geom, point, r)，让 planner 有机会生成 bbox 索引条件。

坑 2　·　统计信息

忘记 ANALYZE

空间选择性估算不准时，planner 可能不用索引，也可能误用；批量导入后应 ANALYZE。

坑 3　·　列顺序

复合 GiST 列顺序凭直觉

多列 GiST 可用任意列子集，但第一列最重要；时间很窄、空间很大时试试把 range 放前面或分区。

坑 4　·　语义

把 bbox 命中当成精确空间命中

GiST 常常只是候选过滤；只写 &&，得到的就是 box overlap 语义。

坑 5　·　距离单位

KNN 距离和业务距离不一致

geometry <-> 在经纬度下不是米制地球距离；评估 geography、投影坐标系或二阶段排序。

坑 6　·　回表成本

忽视大对象 TOAST 与复查代价

大 geometry 即使命中少，精确复查也可能很重：简化几何、切片、缓存 envelope 或轻量候选表。

坑 7　·　btree_gist

认为 btree_gist 能替代 B-tree

它的价值是让标量列参与 GiST 复合索引或 EXCLUDE 约束，不是替换普通 B-tree。

坑 8　·　维护

忽略 VACUUM 与膨胀

高更新产生死项和空页；空叶子页删除是 best-effort，长期膨胀时评估 REINDEX CONCURRENTLY。

本页要点绝大多数「GiST 慢」的问题，都能归因到摘要、统计、谓词写法、列顺序或维护成本。
