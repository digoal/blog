共同点：查询过程更像「沿着分区规则排除不可能的区域」，而不是「在全序键上二分」——这正是 SP-GiST（Space-Partitioned GiST）的用武之地。
一 / 它解决什么问题

把内存里的递归分区树，做成磁盘索引

SP-GiST 解决的是 quad-tree、kd-tree、radix tree / trie 这类非平衡、递归分区树的数据库化。难点有两个。

难点一 · 内存结构 ≠ 磁盘结构

经典空间分区树最早多为内存结构：大量小节点 + 指针，树很深也没关系。磁盘里若每走一层都读一个 page，IO 成本会失控。Purdue 2001 论文明确指出 quad-tree / trie / k-D tree 可能「又瘦又长」，必须把逻辑节点合理聚集到磁盘页。

难点二 · 索引不只是算法

真正落地还要处理 page layout、WAL、锁、并发扫描、崩溃恢复、VACUUM、优化器接口、index-only scan、NULL、INCLUDE 列。每种数据类型都重写一遍访问方法，工程成本太高。

它牺牲的东西很明确：不保证树平衡；分区规则与数据分布 / 查询谓词不匹配时，可能出现深路径、低剪枝率、写入分裂成本高。它不是 B-tree 或 GiST 的通用替代品。
二 / 它是什么

两类 tuple，撑起一棵分区树

SP-GiST 是一种 index access method，也是可扩展的非平衡分区树框架；官方文档称其支持 partitioned search trees。

图 2 重绘：inner tuple 只放在 inner page，leaf tuple 只放在 leaf page。

inner tuple

分支点：包含可选 prefix 和一组 child node；每个 node 有可选 label 与 downlink。

leaf tuple

保存索引叶值、heap TID、可选 NULL bitmap、可选 INCLUDE 列。叶值不一定是原值，可以是 lossy / partial 表达。

和 GiST 的一句话差别

GiST 内部节点保存「可重叠的子树摘要」（如 R-tree bounding box）；SP-GiST 内部节点保存「分区规则下的 child nodes」，通常表示互不相交的搜索空间分区。

二 / 路径从哪来

同样是索引树，路径的来源完全不同

B-tree 靠全序关系；GiST 靠「子树是否可能命中」；SP-GiST 靠分区规则（象限、左右侧、下一字节）。

图 1 重绘：查询越贴合分区规则，剪枝越有效。
别被名字误导：GiST 是「子树摘要可能重叠」的通用平衡树；SP-GiST 是「按分区规则递归切空间」的非平衡树。两者工程模型不同。
二 / 开箱可用的 opclass

core 提供框架，opclass 决定语义

索引能不能用、怎么用，取决于列上的 operator class 支持哪些操作符与 ordering operator。

PostgreSQL 内置 7 个 SP-GiST opclass

box_opsinet_ops quad_point_opskd_point_ops poly_opsrange_ops text_ops
  • quad_point_ops 是 point 的默认 SP-GiST opclass；kd_point_ops 支持同类操作符但用不同树结构。
  • quad_point_ops / kd_point_ops / poly_ops 支持 <-> ordering operator，可做 k-NN。
  • text_ops 可索引 ^@ 前缀查询；inet_ops 处理网络地址前缀关系。

PostGIS 提供 4 个 SP-GiST opclass

spgist_geometry_ops_2d2.5+ · geometry 默认
spgist_geometry_ops_3d3D geometry
spgist_geometry_ops_nd3.0+ · N 维
spgist_geography_ops_nd3.0+ · geography 默认

2D 版本基于 BOX2DF；ND / geography 版本基于 GIDX。

最容易踩的落差：PostGIS 文档特别提醒，当前 PostGIS SP-GiST 空间索引没有 kNN 支持；这与 PostgreSQL core 中 quad_point_ops / kd_point_ops / poly_ops 的 <-> 支持不同。
依据：PostgreSQL 官方文档「Built-in Operator Classes」、PostGIS 文档 SP-GiST Indexes 小节；本文关键结论均回到源码或官方文档核对。
3.1 / 页结构

固定前三个 block，再加两类数据页

spgist_private.h 固定了 metapage / root / null root；NULL 被放进一棵独立的树。

图 2 重绘：root / null root / inner page / leaf page 的职责边界。
root page 初期可以直接堆 leaf tuple（推迟 split，用更多样本决定顶层分区）；第一次 split 后必须变成只包含一个 inner tuple。
3.1 / 设计边界

「一页之内」解释了大部分限制

leaf 链同页减少跨页 seek，但单个 inner tuple、单条 leaf 链、单个 leaf tuple 都不能无限增长。

图：一个 page 是硬天花板，分区结构必须围绕它设计。

① node 数量不能太多

SpGistInnerTupleData 用 13 bit 记录 nNodes，且整个 inner tuple 仍要放进一个 page。opclass 不应产生过多 node。

② prefix / node label 不能过大

spgFormInnerTuple() 会检查 inner tuple 大小；radix tree 的 spgtextproc.c 对最大 prefix 长度有专门限制。

③ leaf value 不能过大

除非 opclass 设置 longValuesOK 并能通过逐层 suffixing 缩短 leaf datum。text_ops 就是典型例子。

工程目标

把深逻辑路径聚集到更少 page：inner / leaf 页分离、last-used page cache、leaf 链同页、root 延迟 split。

3.2 / 合约

5 个必需函数，2 个可选函数

support proc 编号定义在 src/include/access/spgist.h；core 负责流程，opclass 只回答领域问题。

#函数作用必需
1config声明 prefix / label / leaf 类型，能否还原原值、是否支持超长值必需
2choose插入时决定匹配已有 node、增加 node，还是拆 inner tuple必需
3picksplitleaf page 放不下时，把一批 leaf tuple 分配到新 child nodes必需
4inner_consistent扫描时判断哪些 child nodes 可能满足查询必需
5leaf_consistent扫描到 leaf 判断是否满足查询，并设置 recheck必需
6compress把输入值转换成 leaf 存储值；输入类型与 leaf 类型不同时必须提供可选
7options声明 opclass 自定义参数可选

picksplit() 的输出 = 一次新分区

是否有 prefix、多少 node、每个 leaf tuple 映射到哪个 node、每个 leaf tuple 下层要保存什么 datum。

关键分工：插入时 choose() 只选一条下降路径；扫描时 inner_consistent() 可以返回多个 child node。

3.5 / 并发与回收

为什么不能随便删一个 offset？

其他 page 的 downlink 可能正指向它；四种状态共同维护 downlink 有效性与并发扫描安全。

图 4 重绘：四种状态定义在 spgist_private.h；redirect / dead / placeholder 各解决一个具体并发问题。

VACUUM 的目标不是「最干净」

而是在不破坏 downlink 与并发扫描的前提下回收空间。spgbulkdelete 顺序扫描整个索引：清理可删除 leaf tuple、把过期 redirect 转成 placeholder、移除页尾不再需要的 placeholder、更新 free space map。

inner page 的 triple parity

README 描述了一个死锁风险：不同分支的 inner tuple 可能交叉引用两个 page，两次插入各自持有父页再等子页。SP-GiST 让「子 inner tuple 尽量放在特定 block parity 的 page 上」降低交叉引用概率；条件锁失败就释放并重启。不是零成本，但避免更复杂的全局锁序。

3.6 / 内置实现

同一个框架，三种完全不同的分区规则

prefix 不一定是「字符串前缀」——它可以是中心点、切分坐标，甚至高维 centroid。

quad point

spgquadtreeproc.c：prefix 是中心点；picksplit() 默认用点集 x/y 平均值作为 centroid，把点映射到四象限。

kd point

spgkdtreeproc.c：层级 level % 2 决定按哪个维度切分；与 quad 支持同类操作符，但使用不同树结构。

text radix / trie

spgtextproc.c：prefix 是公共前缀，node label 是下一字节；longValuesOK = true，逐层 suffixing 缩短超长值。

在 quad-tree 里 prefix 是中心点，kd-tree 里是切分坐标，PostGIS 里可以是 BOX2DF / GIDX 的高维 centroid —— 抽象能力正来自「prefix 只是分区规则的状态」。

五 / 效果如何

收益来自「匹配」，不是「通用更快」

三点收益 + 一组有正反两面的实验结论；脱离 workload 谈性能没有意义。

① 降低工程成本

2001 年论文的动机：不希望每种 quad-tree / trie / kd-tree 都重写 DBMS 内核里的搜索、插入、并发与恢复。今天 opclass 写少量函数，core 处理页与事务。

② 剪枝强

text_ops ^@ 前缀、inet_ops 网络前缀、点的窗口与 KNN、PostGIS 高维 bbox 分区剪枝，都在「查询贴合分区规则」时明显受益。

③ 少读磁盘页

把深逻辑路径聚集到更少 page：inner/leaf 页分离、last-used page cache、leaf 链同页、root 延迟 split，服务「少 IO」这个核心目标。

Purdue 2006 原型实验（正向）

≈10²
SP-GiST trie 对某些正则匹配
优于 B+-tree 两个数量级以上
+300%

来源：Space-Partitioning Trees in PostgreSQL: Realization and Performance, ICDE 2006（其 PostgreSQL 原型）。

但同一篇论文也给出反例

  • B+-tree 在 prefix match 上更好。
  • R-tree 在部分 PMR quadtree 线段实验里更好。
  • B+-tree / R-tree 的插入耗时或索引大小也常有优势。
  • PostGIS「spaghetti data」注释只是说高度重叠 bbox 时尤其有益，不是无条件承诺。
结论：优势是「查询形态与分区结构匹配时很强」，不是「所有场景都更快」。真实效果还要看：是否使用 opclass 支持的 bbox 操作符、bbox 是否大量重叠、写入与分区倾斜、是否需要 KNN、统计信息是否及时。

    • 唯一约束、主键、外键支撑的标量键 → B-tree。
      • 
      
    • 全序排序分页 → B-tree。
      • 
      
    • PostGIS 最近邻 → 当前优先 GiST（SP-GiST 无 kNN）。
      • 
      
    • 查询与分区规则不匹配，例如空间数据只靠非空间属性过滤。
      • 
      
    • 数据高度倾斜且没有好的分区策略 → 可能生成深树。
      • 
      
    • 高频更新且收益不明显：split / redirect / VACUUM 成本可能抵消收益。
      • 
    
    
  
    

    



    
  
    
    
    九 / 常见坑
    
    
    最容易踩的 8 个坑
    
    
    前三条与「名字、KNN、操作符」有关，占实际误用的大多数。
    
  
    
  
    
    
    01
    把它当 GiST 升级版
    不是。两者树模型不同；PostGIS 中 GiST 更通用且支持 KNN。
    
    
    02
    忽略 PostGIS 无 kNN
    文档明确无 kNN；ORDER BY geom <-> point LIMIT n 通常看 GiST。
    
    
    03
    用错操作符
    text_ops 支持 ^@，不是所有 LIKE 写法都等价；PostGIS 支持的是 bbox operators。
    
    
    04
    只看是否 Index Scan
    有索引扫描不等于快；bbox 太粗、分区不匹配、统计信息旧都会返回大量候选。
    
    
    05
    忘记 ANALYZE
    新建索引后不更新统计信息，优化器可能继续选 seq scan。
    
    
    06
    以为 leaf datum 是原值
    可能是 lossy / partial：text 存 suffix、PostGIS 存 bbox；index-only scan 取决于 canReturnData。
    
    
    07
    自定义 opclass 让 node 过大
    inner tuple 必须放进一个 page；spgtextproc.c 对最大 prefix 长度有专门限制。
    
    
    08
    忽略 NULL 独立树
    SP-GiST 会索引 NULL，但 opclass 看不到；别在普通 support function 里找 NULL 分支。
    
  
    
  
    这些坑基本都能从「页结构 + opclass 合约 + 两阶段过滤」三条主线推导出来。

    5 个扩展问题
      
      
    • 业务对象是轨迹、单个 bbox 很粗：用 GiST、SP-GiST，还是切成多段后多 entry 索引？
      •

    Takeaway / 一页纸结论
    
    
    SP-GiST 给「递归分区」这个模型
    套上数据库工程化外壳
    
    
    不是更通用的 GiST，也不是 B-tree 的替代品。
    
    
    
      
    01
    分工
    core 管磁盘页、WAL、锁、并发、VACUUM；opclass 管如何分区、如何剪枝、是否匹配。
    
      
    02
    收益条件
    收益来自「查询贴合分区规则」；分区倾斜、谓词不匹配时会出现深路径与频繁 split。
    
      
    03
    选型红线
    PostGIS SP-GiST 当前无 kNN，KNN 优先 GiST；精确几何判断永远在第二阶段。
