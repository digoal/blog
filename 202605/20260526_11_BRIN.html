01 / 背景

一类很常见的表：持续追加，按范围查询

数据量极大，写入几乎总是追加；查询按时间、递增 ID、批次号、地理瓦片、轨迹顺序做范围过滤。

01 / 传统选择

要么读太多，要么写太贵

顺序扫描、B-tree、分区裁剪各有代价；BRIN 解决的是两者之间的中间问题。
做法好处代价索引项粒度
顺序扫描写入最便宜，完全不维护索引每次查询都要读大量无关页面无索引
B-tree精确、可排序，适合点查和窄范围每行一条索引项：索引大、随机写和维护成本高每行一条 key / TID
分区按分区元数据裁剪，管理直观粒度较粗，分区过多带来管理成本分区
BRIN索引极小、写入轻，能跳过大块无关页面过滤有损，必须回表复查；强依赖物理相关性每个 page range 一条摘要
BRIN 用「定位精度」换「写入与空间成本」：它不是更快的 B-tree，而是一种更便宜的粗过滤。
01 / 关键改写

从「找行」改成「排除页面」

BRIN 的正确性要求只有一条：不能漏掉可能命中的页面。多返回候选页面是允许的。
「不问哪几行命中，只问哪些连续页面范围不可能命中。」
02 / 它是什么

BRIN = PostgreSQL 内置的 zone map

一种索引访问方法：把 heap 表按连续物理页面切成 block range（page range），每个 range 存一个 summary tuple。
DEFINITION
用很小的索引，换取「能跳过大块无关页面」的能力；
代价是过滤有损，必须回表复查。
TRADE-OFF

有损过滤是设计，不是缺陷

摘要只能证明「不可能命中」，不能证明「一定命中」。因此 BRIN 返回的是候选页面集合，最终行由执行器复查。

01 / 空间

一条摘要换一段页面

不是每行一条索引项，而是每 pages_per_range 个 heap 页面一条摘要。索引 tuple 数约等于 ceil(heap_pages / pages_per_range)。

索引极小 → 扫描索引本身开销可忽略
02 / 前提

物理相关性

列值与 heap 物理位置越相关，每个 range 的 min/max 越窄，能排除的页面越多。数据越随机，摘要越宽，越接近顺序扫描。

时间、递增 ID、批次号、空间排序键
03 / 机制

lossy bitmap + recheck

只支持 amgetbitmap，输出单位是 heap page 而不是 row；上层 Bitmap Heap Scan 读页后复查条件。

多返回候选页是允许的；漏掉可能命中的页不允许
02 / 结构模型

不保存 (key, TID)，只保存一段页面的摘要

示意取 pages_per_range = 4；真实默认值为 128。查询能证明某个 range 不可能命中时跳过，不能证明时返回整段页面。
绿色 = 可证明不匹配，整段跳过；橙色 = 不能证明不匹配，整段 4 页进入 lossy bitmap 等待复查。
02 / opclass

summary tuple 里存什么，由 operator class 决定

官方：核心发行版支持 minmax、minmax-multi、bloom、inclusion 四类；只有 bloom 与 minmax-multi 允许指定 opclass 参数。
minmax

两个值决定一个范围

保存 range 内最小值与最大值，适合有线性排序语义的类型：时间、递增 ID、批次号。

源码 brin_minmax_opcinfo() 声明每列存 2 个值。
minmax-multi

多个小区间

保存多个 min/max 区间，适合 range 内有少量簇、整体 min/max 被离群值拉宽的情况。

values_per_range 默认 32（范围 8–256）。
bloom

位图指纹

为 range 内所有值构建 Bloom filter，主要服务等值过滤。

false_positive_rate 默认 0.01；n_distinct_per_range 默认 -0.1。
inclusion

能包含所有值的摘要

保存能包含 range 内所有值的摘要：几何外包框、range、inet 等；PostGIS BRIN 用它做空间粗过滤。

代表：box_inclusion_ops、range_inclusion_ops。
opclass 必须实现四个方法：opcInfo()、addValue()、consistent()、unionTuples()（bloom / minmax-multi 另有 options()）。BRIN 层负责并发、日志与索引结构搜索。

03 / 一致性判定

consistent()：不能证明不匹配，就不能跳过

最容易理解的是 brin_minmax.c：add_value 扩展 min/max，union 合并两个摘要，consistent 判断是否可能相交。
注意：42 落在区间内只说明「可能有」，并不说明该 range 里真的存在 42。
BRIN_MINMAX.C / 判定式

三种谓词的跳过条件

col = 42min ≤ 42 ≤ max
col > 42max > 42 就不能跳
col < 42min < 42 就不能跳
「不能跳过」≠「命中」。正确性要求只是不能漏掉可能命中的页面，多返回候选页是允许的，执行器会复查。
插入时 brin_minmax_add_value() 只在新值突破边界时更新；合并摘要时 brin_minmax_union() 扩展 min/max。

03 / 写入路径

为什么 BRIN 的写入这么轻？

建索引时按 heap 物理顺序扫描形成摘要；插入时只更新当前 range 的那一条摘要，而且多数插入连它都不用改。
brinbuild() · CREATE INDEX

按物理顺序产出 range

  • 初始化 metapage 与 revmap
  • 按 heap 物理顺序扫描整张表
  • 每走满一个 range，把累计摘要形成 BRIN tuple 并插入 regular page
  • 对空范围回填 empty range tuple，避免某些选择性查询退化成全表重扫
  • 普通串行构建禁用 syncscan：BRIN 必须按 heap block 顺序产出 range
brininsert() · INSERT

只动一个摘要

  • 由 heap TID 算出所属 range 的起始块
  • 若该 range 已有摘要：用 add_values_to_range() 尝试并入新值
  • 新值仍在旧摘要范围内 → 不更新索引
  • 摘要需要变宽：优先同页更新；放不下则建新 tuple 并更新 revmap
  • 若该 range 未摘要：插入不做任何 BRIN 更新
heapBlk = floor(origHeapBlk / pagesPerRange) × pagesPerRange　·　与 B-tree「每行插入一条索引项」不同，BRIN 的很多插入完全不改变索引内容。
03 / 正确性优先

新 range 默认未摘要；没有摘要就不能跳过任何页面

未摘要 range 的 revmap entry 是 invalid TID，查询遇到它必须把整段页面加入 bitmap——这样做保证不漏数据。
03 / 维护代价

删除极值不会让摘要自动收紧

BRIN 不保存 heap TID 列表，所以删除时无需清理索引项——这是优点；代价是不知道 min/max 该收紧到哪。源码 README：这不是正确性问题，而是优化机会。
工程含义 01

乱序 UPDATE

大量乱序更新会让 range 的 min/max 逐渐变宽，候选页比例上升。

工程含义 02

删除不收紧

删掉历史极值不会自动提升过滤能力；纯追加时间序列表通常更稳。

应对 01

重新摘要

候选页比例显著上升时，brin_desummarize_range() 后再 summarize，或直接 REINDEX。

应对 02

谨慎回填

频繁回填、修正历史时间的数据要谨慎：先按回填维度分区，或调小 pages_per_range。

04 / 横向对比

关键不是「哪个索引最快」，而是粒度不同

B-tree 的精确来自每行索引项；BRIN 的低成本来自放弃行级定位。数据湖 zone map 与 BRIN 思想相近，但粒度落在文件 / row group / stripe。

05 / 效果

收益来自跳过，成本来自「有损」

评价 BRIN 不能只看索引大小，必须同时看查询阶段付出的代价。
BENEFITS / 三份收益

① 索引很小

索引 tuple 数 ≈ ceil(heap_pages / pages_per_range)。TB 级表上不会像 B-tree 那样为每行生成索引项。

② 写入很轻

已摘要 range 上的插入，只有新值突破摘要边界才更新；未摘要 range 上的插入完全不更新 BRIN。

③ 能跳过大块页面

只要物理顺序与查询列相关，min/max 就能有效排除大量 range，扫描索引本身的开销几乎可忽略。

COSTS / 五类成本

假阳性

摘要命中不等于 tuple 命中，候选页内还要 Recheck。

未摘要范围

invalid revmap entry 被保守返回，短期影响过滤。

相关性依赖

数据越随机，min/max 越宽，越接近顺序扫描。

删除不收紧摘要

删除历史极值不会自动变窄，需重新摘要或重建。

不支持唯一性与排序输出

amcanunique / amcanorder / amcanorderbyop = false。

时间追加表：建 BRIN，看计划形态

按时间递增写入 100 万行，用 pages_per_range = 32 + autosummarize = on 建索引，再查一天窗口。
CREATE TABLE sensor_log (
  id bigint GENERATED ALWAYS AS IDENTITY,
  device_id int NOT NULL,
  created_at timestamptz NOT NULL,
  payload jsonb NOT NULL
);

INSERT INTO sensor_log (device_id, created_at, payload)
SELECT (random()*1000)::int,
       timestamptz '2026-01-01 00:00:00+00' + (g * interval '1 second'),
       jsonb_build_object('v', random())
FROM generate_series(1, 1000000) AS g;

CREATE INDEX sensor_log_created_at_brin
ON sensor_log USING brin (created_at)
WITH (pages_per_range = 32, autosummarize = on);

ANALYZE sensor_log;

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM sensor_log
WHERE created_at >= timestamptz '2026-01-10 00:00:00+00'
  AND created_at <  timestamptz '2026-01-11 00:00:00+00';
预期验证点

看计划形态，不是看固定耗时

  • 是否出现 Bitmap Index Scan on 该 BRIN 索引
  • 外层是否为 Bitmap Heap Scan
  • 是否带有 Recheck Cond
  • BUFFERS 读取是否显著少于顺序扫描
  • 把 pages_per_range 调小后，候选页是否下降
以下 SQL 未在当前环境执行：工作区只有源码与文档，没有运行中的 PostgreSQL/PostGIS 实例。语法按官方文档、本地源码与回归测试编写。
06 / DEMO ②

把 revmap 落到实物上：手工补摘要与看页面

三个维护函数 + pageinspect，可以直接验证图 2 里的 metapage 与 revmap 内容。
补全部未摘要 range
SELECT brin_summarize_new_values('sensor_log_created_at_brin');
扫描索引找出所有未摘要 page range，逐个扫表生成摘要；返回新插入的摘要条数。
只处理一个 range / 让它失效后重做
SELECT brin_summarize_range('..._brin', 0);
SELECT brin_desummarize_range('..._brin', 0);
desummarize 删除覆盖给定 block 的摘要，适合摘要已明显不代表当前数据时重做。
pageinspect 看索引页
CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT * FROM brin_metapage_info(get_raw_page('..._brin', 0));
SELECT * FROM brin_revmap_data(get_raw_page('..._brin', 1)) LIMIT 10;
把图 2 对应到查询结果
metapage (block 0)pagesPerRange
revmap (block 1..N)range → TID
invalid TID未摘要范围
这个实验能看到：索引里每个 range 到底有没有摘要、摘要元组放在哪个 TID。
官方注意：这类维护任务通常由 autovacuum 自动完成，函数只在特殊情况下手工调用；不能在 recovery 期间执行，权限限于 superuser 或索引 owner。
未摘要 range 的过滤退化是短期现象：可用 autosummarize = on 或定期 brin_summarize_new_values() 处理。
06 / DEMO ③

PostGIS：用 BRIN 做低成本空间粗筛

geometry 列上建 BRIN inclusion 索引，查询框与 range 外包框相交时返回候选页面。
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE gps_point (
  id bigint GENERATED ALWAYS AS IDENTITY,
  geom geometry(Point, 4326) NOT NULL
);

-- 生产中应尽量按空间块、瓦片、轨迹顺序或加载批次
-- 保持物理相关性，否则外包框会覆盖全域。
CREATE INDEX gps_point_geom_brin
ON gps_point USING brin (geom)
WITH (pages_per_range = 16);

EXPLAIN
SELECT id FROM gps_point
WHERE geom && ST_MakeEnvelope(120.0, 30.0, 121.0, 31.0, 4326);
观察与前提

便宜，但只做粗过滤

  • 默认使用 2D inclusion opclass，摘要类型为 BOX2DF
  • && 是「外包框相交」操作符，命中后仍需回表复查
  • PostGIS 回归测试 regress_brin_index.sql 用 enable_bitmapscan = on、enable_seqscan = off 验证 BRIN 空间索引走 bitmap scan
  • 数据按空间顺序装载时有效；随机插入全球点会让外包框失效
需要更细的空间剪枝、KNN 或排他约束时选 GiST / SP-GiST；BRIN 的价值是「比 GiST 便宜得多的粗过滤」。
06 / 最佳实践

把「分区 + 装载顺序 + 查询谓词」一起设计

最常见组合：按时间分区，每个分区内再用 BRIN 做块级跳过。
面向数据库架构师

结构与选型

  • BRIN 与分区、物理装载顺序、查询谓词一起设计
  • 只在物理相关性强的列上优先尝试：时间、递增 ID、批次号、地理排序键、append-only 状态
  • 不要用 BRIN 替代主键、唯一约束、外键支撑索引
  • BRIN 不支持唯一性，也不擅长点查
面向 DBA

验证与维护

  • 建索引后用 EXPLAIN (ANALYZE, BUFFERS) 验证候选页比例
  • 持续追加表监控未摘要范围，必要时定期 summarize
  • 数据回填多的表调小 pages_per_range 或按回填维度分区
  • 历史修正 / 删除后 recheck 升高 → desummarize + summarize 或 REINDEX
面向业务开发者

把 SQL 写对

  • 条件直接落在 BRIN 索引列：created_at >= ... AND < ...
  • 避免把列包进不可索引表达式：date(created_at) = ...
  • 需要时建表达式 BRIN 索引或改写成半开区间
  • BRIN 是粗过滤：返回少量行的点查仍用 B-tree
  • PostGIS BRIN 要保证装载顺序与空间位置相关
一句话：物理相关性是前提，半开区间谓词是入口，候选页比例是指标。
06 / 适用边界

什么时候该用，什么时候别用

判断标准始终是：数据量大不大、查询列与物理顺序是否相关、写入是否以追加为主。
✓ 适合

大、有序、追加、范围扫描

  • 百 GB 到 TB 级追加表，查询列与物理写入顺序高度相关
  • 时间范围、批次范围、递增 ID 范围扫描
  • 大表上「先粗筛再聚合」的分析查询
  • 历史冷数据：写入少、更新少、查询范围相对大
  • PostGIS 中按空间顺序装载的大对象表，需要比 GiST 更低成本的粗过滤
✕ 不适合

小、随机、点查、要唯一

  • 小表：顺序扫描成本本来就低
  • 高频点查，例如 WHERE id = ?
  • 需要唯一约束、排序输出、ORDER BY ... LIMIT
  • 查询列与 heap 物理顺序无关：随机 UUID、被打散的时间
  • 更新频繁且新值跨很大范围，摘要快速变宽
  • 删除大量极值后仍希望索引自动变精确
06 / 常见坑

踩过的坑，基本都绕不开这七条

每一条都对应前面的某条原理：有损过滤、未摘要范围、物理相关性、摘要只变宽。
① 看到用了 BRIN 就以为快看 buffers / recheck
② pages_per_range 只用默认值看 range 内键跨度
③ 忽略未摘要范围autosummarize / 定期补
④ 把 BRIN 用在随机分布列min/max 覆盖全域 = 无剪枝
⑤ 大量 UPDATE 后不复查摘要变宽，删除不收紧
⑥ PostGIS BRIN 与 GiST 混淆粗过滤 vs 搜索树 / KNN
⑦ 把函数写在列上改写成半开区间
WHERE date(created_at) = '2026-05-26' 不等同于直接范围条件，优先写成 created_at >= ... AND created_at < ...。

CLOSING / 带走三句话

BRIN 是块级摘要，不是行级索引

01

它换掉了什么

放弃逐行 (key, TID) 定位，改成每个 page range 一条摘要元组——索引极小、写入很轻。

02

它依赖什么

收益来自物理相关性；过滤是有损的，候选页必须交给 Bitmap Heap Scan 逐行 Recheck。

03

怎么验证

不要只看索引大小或「有没有用上 BRIN」；看候选页比例、lossy 块数、Recheck 丢弃行数与 buffers。

一句话：BRIN 用很小的索引换取「能跳过大块无关页面」的能力，代价是过滤有损，必须回表复查。
