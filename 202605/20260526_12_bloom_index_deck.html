01 / 背景 问题从哪里来

字段很多、组合不固定、条件大多是等值过滤

四类典型业务表，和四种传统做法各自的代价。

四类常见的宽表
1
用户画像表
city = ? · gender = ? · level = ? · tag = ?
组合经常变化
2
订单宽表
buyer_id · seller_id · status · channel · warehouse
任意组合查
3
设备资产表
型号、区域、固件版本、状态、责任人等字段都可能参与筛选
4
风控明细表
很多低到中等选择性的枚举、文本、整数列需要临时组合查询
共同点：列多、组合不可预测、谓词以等值为主。
四种传统做法的矛盾
做法好处代价
多个复合 B-tree固定查询形态最快组合多时索引数量爆炸，受 leading column 约束
每列一个 B-tree任意组合可用 BitmapAnd空间、写入、VACUUM 维护成本高
GIN / GiST适合特定复杂类型与谓词对普通多列等值宽表不是最直接模型
顺序扫描无索引写入维护成本宽表大表上延迟与 IO 不可控
N 列可能产生大量组合：为每种组合建复合索引 → 索引数量爆炸；完全顺序扫描 → 大表延迟不可控。

02 / 定义 先钉死概念

每个 heap tuple 一条 (TID, Bloom signature) 的顺序存储有损索引

contrib 扩展注册为独立索引访问方法；查询扫整个索引，把候选 TID 放进 bitmap，再回表复查。

signature

定长签名

默认 80 bit，最大 4096 bit；源码以 uint16 word 数组存储，长度按 16 bit 上取整。

col1 .. col32

每列 bit 数

默认每列 2 bit，最大 4095；官方文档暴露 col1 到 col32 参数。

false positive

误判

签名判断通过但真实列值不匹配。不会造成错结果，只会造成无用回表。

recheck

回表复查

tbm_add_tuples(..., recheck = true) 强制堆表复查真实条件。

CREATE ACCESS METHOD bloom TYPE INDEX HANDLER blhandler;　·　内置 opclass 只有 int4_ops 与 text_ops，都只需要等值操作符 + hash 函数；其他类型可按同样接口扩展。

03 / 原理 3.1 签名生成

列号参与种子：避免不同列中的相同值映射到同一 bit 序列

下方 bit 编号为教学模型在 length=64 下的示意结果，用来说明「列相关」这件事。

理想化误判估算（调参直觉，不是 PostgreSQL 成本公式）
p ≈ (1 − e−K/m)Q
m = 签名长度；K ≈ 一行所有索引列累计设置的 bit 数；Q = 查询条件累计检查的 bit 数。 length 太小或索引列太多 → 签名变满；查询列越少 → Q 越小 → 误判越容易上升。
从公式读出的三条调参直觉
1
调大 length：同样 bit 更稀疏 → 误判下降，但索引更大、扫描更慢。
2
调大某个 colN：该列查询检查更多 bit → 单列过滤更强，但行签名更容易变满。
3
目标不是「精确索引」：而是在可接受空间内减少无用 heap visit。
来源：原文 3.1 · blutils.c signValue() 源码注释 · 官方 bloom 文档

03 / 原理 IndexAmRoutine

blhandler() 的九个声明，决定了它的能力边界

不能逐条返回有序 TID，不能 index-only scan，不能唯一约束，也不能并行扫描 / 并行构建。

结论：扫描入口只有 blgetbitmap() → 计划形态只能是 Bitmap Index Scan + Bitmap Heap Scan；scan key 为 NULL 时直接返回 0（不支持搜索 NULL）。
来源：原文 3.5 · blutils.c / blhandler() · 官方 bloom 文档「Limitations」
04 / 对比 五种索引放一起看

核心差别是索引粒度：行级签名 / 行级有序键 / range 级摘要 / 倒排 key

B-tree 用精确有序入口换定位能力；bloom 用有损签名换空间和多列组合能力。

维度PostgreSQL bloom多列 B-tree 多个单列 B-tree + BitmapAndBRIN bloom opclassGIN
主要目标一个紧凑索引支持多列任意组合等值过滤固定列序的精确查找、排序、范围每列精确过滤后做 bitmap 交集每个 page range 保存 Bloom 摘要复合值、数组、JSONB、全文倒排
索引粒度每 heap tuple 一个有损签名每 heap tuple 一个有序键入口每列每 heap tuple 一个入口每 block range 一个摘要value/key 到 posting list/tree
读取路径扫完整 bloom 索引，返回 bitmap树搜索，可返回有序 TID多个 bitmap index scan 再合并扫 BRIN 摘要，返回 range bitmap查 key，再合并 posting
支持谓词仅等值等值、范围、排序相关谓词等值、范围视 opclass 而定等值摘要，仍按 range 返回取决于 opclass
误判 / 复查有误判，必须 recheck通常精确，MVCC 仍需可见性检查通常精确，bitmap heap 仍复查range 级有损，必须 recheck取决于 opclass，常见 recheck
空间成本通常小于多个 B-tree单个复合索引中等多列时较高极小可能较高
写入维护每行一条固定签名每个相关索引维护树每列索引都要维护每 range 摘要维护一行可能生成多个 key
不适合范围、排序、唯一、NULL、极高选择性点查任意组合且不满足 leading column列很多且写入重随机数据点查简单标量多列等值宽表未必划算
别混淆：contrib/bloom 是行级签名索引访问方法； src/backend/access/brin/brin_bloom.c 是 BRIN 某个 page range 的摘要类型。两者读写路径与调参目标都不同。

06 / 实操 最小验证路径

SQL 只验证三件事：只支持等值、走 bitmap scan、需要 recheck

以下为原文脚本节选（列定义与表达式略有缩排）；完整脚本见原文第六节。

CREATE EXTENSION IF NOT EXISTS bloom; CREATE TABLE tbloom_demo ( id bigserial PRIMARY KEY, c1 int, c2 int, c3 int, c4 text, payload text ); INSERT INTO tbloom_demo (c1,c2,c3,c4,payload) SELECT (random()*100000)::int, (random()*100000)::int, (random()*100000)::int, substr(md5(g::text),1,2), md5((g*17)::text) FROM generate_series(1, 1000000) AS g; ANALYZE tbloom_demo; CREATE INDEX tbloom_demo_bloom_idx ON tbloom_demo USING bloom (c1,c2,c3,c4) WITH (length=128, col1=2, col2=2, col3=2, col4=4); EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM tbloom_demo WHERE c2 = 12345 AND c4 = 'af';
预期观察点
1
计划通常应是 Bitmap Index Scan + Bitmap Heap Scan；是否选用取决于统计信息、表大小与成本参数。
2
Recheck Cond 会出现——bloom 返回的是有损候选。
3
Rows Removed by Index Recheck 越高 → 签名误判越多。
4
Heap Blocks 越少 → 排除能力越强。

07 / 实践 架构师 / DBA / 开发者

把 bloom 定位成「宽表多列等值过滤的空间折中」

不要把它当作 B-tree 替代品；评估时同时看空间、写入、recheck 与 heap 访问。

面向数据库架构师
1
定位为宽表多列等值过滤的空间折中，不是 B-tree 替代品。
2
高频、强选择性、固定列序查询优先 B-tree；组合多且每个组合频率不稳定时 bloom 才有价值。
3
范围、排序、唯一约束、外键支撑索引、IS NULL 不要选 bloom。
4
评估同时看索引总空间、写入 TPS、recheck 移除行数、heap block 访问数。
面向 DBA
1
用 CREATE EXTENSION bloom 管理；确认目标列类型有 bloom opclass，内置只有 int4 和 text。
2
从默认参数起步；列多、误判高时先调大 length，再考虑给更常用、更高选择性列增加 colN。
3
压测不要只测空缓存：优势依赖「索引更小、heap 回表更少」，缓存状态会影响结论。
4
大量删除后执行 VACUUM，让 dead TID 对应条目被清理、空页进入 FSM。
面向业务开发者
1
条件必须是 opclass 支持的等值操作，例如 c1 = ?、c4 = ?。
2
不要期待 c1 > ?、ORDER BY c1、c1 IS NULL 达到 B-tree 效果。
3
查询列越少越容易误判；一个条件命中 bloom 不一定比顺序扫描划算。
4
看到 Recheck Cond 是正常现象，不是 bug；关注 recheck 移除了多少行。

08 / 边界 选型清单

什么时候值得用，什么时候直接换索引

判断顺序：先看谓词形态，再看组合数量与列数，最后看实际 heap 访问是否明显少于顺序扫描。

适合
✓
一张表有很多可过滤列，查询组合不可预测。
✓
条件主要是等值，且可以接受 Bitmap Heap Scan 回表。
✓
不想为大量组合或大量单列维护 B-tree。
✓
查询目标是过滤候选行，不要求索引提供排序。
✓
列值分布使误判率可控，实际 heap 访问明显少于顺序扫描。
一句话：多列、任意组合、等值、可回表、少建索引。
不适合
×
需要唯一约束、主键、外键支撑索引。
×
需要范围查询、前缀查询、排序输出或 index-only scan。
×
查询大量 IS NULL（scan key 为 NULL 直接返回 0）。
×
表很小，顺序扫描已经足够快。
×
极高选择性点查有稳定列，单列 B-tree 明显更快。
×
列太多、每行设置 bit 太多、length 太短 → 签名接近全 1。
一句话：要精确、要定位、要排序、要唯一，就别用 bloom。
来源：原文「八、适合与不适合场景」
09 / 避坑 误用清单

七个最常见的误读，其中三个会直接导致错误结论

尤其注意：比较基准、opclass 限制、以及 contrib/bloom 与 BRIN bloom 的区别。

1
把 bloom 当成精确索引：只能返回候选 TID，结果正确依赖回表复查，误判越高性能越差。
2
只建一个默认参数索引就下结论：默认 length=80、每列 2 bit 只是通用起点。
3
忘记 leading column 比较基准：单个 (c1,c2,c3,c4) B-tree 对 WHERE c3 = ? 未必有效；但单列 B-tree 或合适复合 B-tree 仍可能更快。
4
忽略 operator class 限制：内置 int4 和 text；其他类型需提供等值操作符和 hash 函数。
5
用 bloom 支撑排序或唯一性：访问方法声明不支持 order、orderbyop、unique。
6
误读官方示例性能数值：那是特定数据规模、分布与查询条件下的对比，不是通用结论。
7
混淆 contrib/bloom 和 BRIN bloom：前者是行级签名访问方法，后者是 block range 摘要；读写路径与调参目标不同。
验证方法：用 EXPLAIN (ANALYZE, BUFFERS) 同时比较 bloom、单列 B-tree、合适复合 B-tree 三者的 空间 / 时间 / recheck / heap blocks，别只看单一指标。

10 / 收尾 带走什么

一句话结论 + 五个值得继续追的问题

bloom 是一个紧凑的多列等值过滤器，不是 B-tree 的替代品。

扩展问题
1
