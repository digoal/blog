P24
MOTIVATION · 01

要的不是「id = 42」，而是「最相关的前 20 条」

BM25 索引解决：按词项快速找候选文档，并按相关性取 Top-K。

业务里常见的四类搜索

  • 商品标题 / 描述 / 类目含 running shoes，按相关性取前 20。
  • 日志含多个关键词，同时按租户、时间、级别过滤。
  • 文档库既要全文匹配，又要结构化字段排序、聚合、分页。
  • 数据已在 PostgreSQL，不想再维护 ES 集群、同步链路与一致性补偿。

ParadeDB 额外要解决的集成问题

  • 写入 / 更新 / 删除对齐 PostgreSQL 事务语义。
  • 查询走 planner / executor，可用 SQL、EXPLAIN、ORM。
  • 结构化字段尽量进入索引层过滤、排序、聚合。
  • 相关性分数能通过 score(...) 返回给 SQL。
PostgreSQL 原生有 tsvector / tsquery / GIN；ParadeDB 目标不同 —— 把 Lucene 类搜索能力做成 Postgres 扩展，把相关性排序、Top-K、过滤、聚合尽量下推到索引层。

ARCHITECTURE · 02

PostgreSQL 是外壳，Tantivy 是内核

PostgreSQL 负责事务与 SQL；pg_search 负责接入与下推；Tantivy 负责倒排结构与 BM25 / Top-K 检索。

三大依赖：pgrx（Rust 扩展开发框架）· Tantivy（全文/向量检索库）· Apache DataFusion（OLAP 查询执行库）。
别混淆：BM25 倒排结构与 Block-Max WAND 来自 Tantivy；DataFusion 属于查询执行与下推框架，不在同一抽象层。
BOUNDARIES · 02

把边界画清楚，才不会问错问题

同一个 SQL 里，事务一致性、谓词下推、倒排打分分别由不同层完成。

PostgreSQL 负责

  • 表、事务、MVCC、WAL 与崩溃恢复。
  • SQL 解析、计划、执行、权限与 RLS。
  • heap 表中的数据与可见性判断依据。
  • 并行 worker 的调度与资源上限。
不负责：BM25 打分与倒排结构

pg_search 负责

  • USING bm25 索引、操作符、score()。
  • custom scan：把 SQL 谓词提取成搜索查询。
  • 过滤、排序、聚合、Top-K 尽量下推到索引层。
  • MVCC directory 等可见性接入逻辑。
不负责：底层 posting 压缩格式

Tantivy 负责

  • segment、term dictionary、posting list。
  • term frequency、position、fieldnorm。
  • BM25 评分、Top-K 检索、Block-Max WAND。
  • delete / alive bitset 与 segment merge。
不负责：PostgreSQL 事务语义

最容易产生的三个误解

  • 把 DataFusion 当成 BM25 倒排引擎 —— 它是 TableProvider / ExecutionPlan / RecordBatch 的执行框架。
  • 以为 custom scan 总会触发 —— 只有出现 ParadeDB 操作符时才会走，否则完全由原生 Postgres 执行。
  • 把 BM25 当语义检索 —— 它只算词项相关性，不理解同义词与语义相似。

SHELL · 02

让搜索成为 PostgreSQL 的一条访问路径

素材原文给出的最小建索引形式，以及按 2026 年官方文档核对后的版本差异。

-- 素材原文语法（legacy API） CREATE INDEX search_idx ON mock_items USING bm25 (id, description, category) WITH (key_field = 'id'); -- 当前官方文档（0.25+ / v2 API） CREATE INDEX search_idx ON mock_items USING paradedb (id, description, category) WITH (key_field = 'id');

索引访问方法做了什么

USING bm25 → bm25_handler() → IndexAmRoutine
  ├─ ambuild()　全量构建索引
  ├─ aminsert()　行级插入 / 更新
  └─ ambulkdelete()　VACUUM 删除路径
custom scan 会把 ParadeDB 操作符相关谓词提取成搜索查询，再转换为 Tantivy query。函数名来自 DeepWiki 源码导航。

四条硬性约束

  • key_field 必需：文档唯一标识，通常是主键或有唯一约束的列，且必须排在索引列列表第一位。
  • 同一张表只能有 一个 BM25/ParadeDB 索引。
  • 搜索、排序、过滤、聚合可能用到的列，建议都放进这一个索引。
  • 字段越多，写入、空间、merge 与 cache 压力越大，需要从搜索路径必需字段开始。

版本校订（联网核对，重要）

  • 0.25 起主访问方法由 bm25 改名为 paradedb；USING bm25 保留为兼容别名。
  • 分数函数由 paradedb.score(id) 变为 pdb.score(id)；参数是 key_field。
  • 0.26+ 起 key_field 已弃用并忽略；0.25 仍要求唯一且列在第一位。
  • 操作符：||| 任一 term、&&& 全部 term、### 短语、=== 精确 token。
本页 SQL 保留素材原语法以对应原文；实际部署请以所用版本官方文档为准。
DESIGN · 02

同样叫「索引」，要回答的问题完全不同

B-tree 只需回答「某个 key 对应哪些 TID」；BM25 索引还要回答下面五件事。

B-tree / 普通二级索引

  • 点查、范围扫描、唯一约束。
  • 结构单一，写入只维护 key 与 TID。
  • 不理解「相关性」与「分词」。

BM25 索引必须回答的五个问题

① 文本字段如何分词、归一化
记录 term frequency 与 position，支持短语与邻近查询。
② 非文本字段是否进入列式 fast field
用于过滤、排序、聚合，而不是每次都回表。
③ 哪个字段是文档唯一 key
影响索引更新、去重与分数返回。
④ 相关性分数是否需要 fieldnorm
字段长度用 1 byte 近似保存，支持 BM25 长度归一化。
⑤ 查询中哪些谓词可以下推到 custom scan
决定是索引层完成，还是取回大量候选由 Postgres 后处理。
结论：正因为一个 BM25 索引要同时承载搜索、过滤、排序、聚合的字段配置，官方文档才建议「一表一个索引、把可能用到的列都放进去」；代价是字段越多写放大越明显。
SEGMENT · 03

写入不原地改索引，而是追加不可变 segment

一个 segment 自带一整套倒排 + 列式结构；整个索引是很多个 segment-local 索引的集合。

版本差异提示

素材：每条 INSERT / UPDATE / COPY 至少产生一个 segment。当前官方文档：写入先进入 mutable segment，跨语句复用，达到 mutable_segment_rows（默认 1000 行）才冻结。属版本差异，以部署版本为准。

纯搜索引擎 vs 数据库扩展

纯引擎只需考虑 delete bitset 与 refresh；ParadeDB 还必须让 segment 服从 PostgreSQL 事务快照与可见性。这也是「搜索引擎式 segment」多出来的一层一致性约束。

SEGMENT FILES · 03

segment 不是一张「倒排表」，而是一组文件

每个文件各司其职：定位、匹配、短语、评分、删除、返回。

.term

term dictionary

term → TermInfo：doc_freq、postings byte range、positions byte range。词典小而可缓存。

.idx

postings

docid 与 term frequency，按 128 个 doc 一个 block 压缩；docid 用 sorted delta + bitpack，tf 用 bitpack，尾部用 VInt。

.pos

positions

词在字段中的位置（delta 编码），支撑短语查询与邻近查询；没有它只能判断「有没有这个词」。

.fieldnorm

字段长度

每个 doc 每个字段用 1 byte fieldnorm_id 近似保存长度，供 BM25 做长度归一化，避免长文档天然占优。

.del / alive bitset

删除标记

删除先标记、不立即物理回收；merge 重写 segment 时跳过已删除文档并重映射 docid。

.store / fast fields

返回与列式字段

store 保存展示字段；fast fields 以列式保存数值、时间、布尔等，用于过滤、排序、聚合，减少回表。

读路径总览
query term→ .term / TermInfo→ .idx posting block→ .fieldnorm 评分→ .del / MVCC 过滤→ store / fast field 返回
TermInfo 不直接保存 posting 数据，只保存 byte range —— 让 term dictionary 小而可缓存，postings 大而顺序解码。

为什么 TermInfo 只存 byte range

term dictionary 因此可以常驻内存、快速定位；真正吃 IO 的 posting 数据留在 .idx，按 range 顺序解码。这是「小词典 + 大倒排链」的经典分工。

在 ParadeDB 里多出来的一步

纯 Tantivy 只看 alive bitset；ParadeDB 还必须按 PostgreSQL 事务快照判断可见性，并用 custom scan 把结果（含 score）交回 executor。

POSTINGS · 03

128 个 doc 一个 block，压缩 + 上界信息一起写

Tantivy 源码：COMPRESSION_BLOCK_SIZE = BitPacker4x::BLOCK_LEN = 128。

压缩带来的收益

docid delta + bitpack 让 posting list 显著变小；同样的内存可以缓存更多 term 的倒排链，查询时顺序解码对 CPU 缓存也更友好。

skip 为什么关键

每个完整 block 额外保存「这个 block 最多能得多少分」所需信息（fieldnorm_id + term_freq 里 tf_factor 最大的一组）。Top-K 查询据此证明某些 block 不可能赢，从而整块跳过。

SCORING · 03

经典打分模型：idf × 词频饱和 × 长度归一化

来源 Okapi / TREC-3；Tantivy 固定参数 K1 = 1.2、B = 0.75。

公式（Tantivy / Lucene 风格）

idf = ln( 1 + (N - n + 0.5) / (n + 0.5) )
weight = idf × (k1 + 1)
score = weight × tf / ( tf + k1 × (1 - b + b × dl / avgdl) )
N = 总文档数；n = 含该 term 的文档数；tf = 词在当前文档字段中出现次数；dl = 当前字段长度；avgdl = 该字段平均长度。

五个参数分别在控制什么

N / n
稀有度：出现在越少文档里的词，idf 越高。
tf
词频：出现越多分越高。
dl / avgdl
字段长度：长文档不该因词多而占优。
k1 = 1.2
词频饱和：tf 越高，边际收益越递减。
b = 0.75
长度归一化强度：0 关闭，1 完全按长度折算。
fieldnorm
让 dl 可以 1 byte 随机访问，不用回表。
Tantivy 的 Bm25Weight 预计算 256 个长度的 tf 分量缓存，打分时按 fieldnorm_id 直接查表 —— 这是「精度换空间与速度」的典型工程取舍。

fieldnorm：1 byte 存长度

为什么不存完整 token 数？因为 BM25 只需要「大致长度」做归一化，而每个 doc 每个字段省下的空间，在亿级文档上非常可观；256 级查表还让打分变成数组下标访问。

「安全」的含义

block 上界是块内任意文档的分数上限；上界之和 ≤ 阈值即可整块跳过，不解码也不打分，不损失召回。代价：写索引多存上界信息、查询逻辑更复杂。

适合场景PostgreSQL 内强一致搜索、混合过滤排序聚合内置全文 / JSON / 数组成员查询搜索独立扩展、跨系统搜索、多租户搜索集群OLAP、查询引擎、外部数据源执行
不适合场景极高写入且不需要相关性；语义向量检索单独主导BM25、复杂搜索体验、ES 兼容能力不想维护双写与一致性链路把它当成倒排索引或 BM25 引擎
一句话定位：GIN 是 Postgres 原生倒排框架，适合很多结构化包含查询；Elasticsearch 是完整独立搜索系统；DataFusion 是查询执行框架，和 BM25 posting list 不在同一抽象层。
版本提示：当前 ParadeDB 已把索引统一为「ParadeDB index」，除倒排外还可包含列式与向量结构；本表按素材原文的 BM25 视角描述。
TRADE-OFF · 04

快在哪里，贵在哪里，是同一个设计的两面

不要在没做实验时写「比 GIN 快多少」或「毫秒级」。

五处收益

① 倒排定位
从 term 直接找到候选 docid，不逐行分词扫描。
② 压缩 posting
docid delta + bitpack 降低 IO 与缓存压力。
③ fieldnorm 快速评分
字段长度 1 byte 近似保存，BM25 不用回表算长度。
④ Block-Max WAND
Top-K 查询跳过不可能超过阈值的 block。
⑤ custom scan 下推
过滤、排序、聚合尽量在索引层完成，减少 Postgres 后处理。

五处代价

① 写放大
一行文本产生多个 term；多字段索引要写倒排、位置、fieldnorm、fast fields。
② 空间放大
除 heap 外还要保存 segment 文件、posting、positions、列式字段与删除标记。
③ merge 成本
段过多时查询要扫更多段；merge 消耗 CPU / IO 并影响写入尾延迟。
④ 可见性成本
PostgreSQL MVCC 保证结果正确，但搜索结果不能只看 delete bitset。
⑤ 评分边界
BM25 是词项相关性，不解决同义词、语义相似、跨语言理解。
正确的验证方式：固定数据集、字段配置、查询集合、Top-K 大小、并发、segment 数与 VACUUM/merge 状态，用 EXPLAIN ANALYZE 和应用侧延迟一起看。
DEMO · 05

按素材文档风格编写的验证路径

当前工作区没有运行 ParadeDB 实例，SQL 未执行 —— 示例输出不能当作实测结果。

-- 扩展与表 CREATE EXTENSION IF NOT EXISTS pg_search; CREATE TABLE mock_items ( id bigint PRIMARY KEY, description text, category text, rating int, in_stock boolean, created_at timestamptz); INSERT INTO mock_items VALUES (1, 'running shoes for trail', 'sports', 5, true, now()), (2, 'leather shoes for office', 'fashion', 4, true, now()), (3, 'running belt and bottle', 'sports', 3, false, now()); -- 一个索引覆盖搜索 / 过滤 / 排序字段 CREATE INDEX search_idx ON mock_items USING bm25 (id, description, category, rating, in_stock, created_at) WITH (key_field = 'id');
-- 基础搜索（||| = 任一 term 命中） EXPLAIN ANALYZE SELECT id, paradedb.score(id) FROM mock_items WHERE description ||| 'running shoes' ORDER BY paradedb.score(id) DESC LIMIT 5; -- 带结构化过滤 EXPLAIN ANALYZE SELECT id, description, paradedb.score(id) FROM mock_items WHERE description ||| 'running shoes' AND category = 'sports' AND in_stock = true ORDER BY paradedb.score(id) DESC LIMIT 10;

验证时看四件事

  • EXPLAIN 是否出现 ParadeDB custom scan 或 BM25 index scan。
  • 过滤、排序、聚合是否下推到索引路径，而不是先取大量候选再由 PostgreSQL 后处理。
  • LIMIT K 变化时延迟是否接近 Top-K 预期，而不是随候选集线性增长。
  • 大量写入后 segment 数、merge / VACUUM 状态是否影响查询尾延迟。
没有 ParadeDB 操作符时，查询可能完全走原生 Postgres 路径 —— 这是最常见也最容易被忽略的「索引没生效」。

版本校订

新版本请写 USING paradedb、pdb.score(id)；||| 表示 match disjunction（任一 term 命中），要求全部命中用 &&&，短语用 ###。0.26+ 起 key_field 已弃用。

示例 SQL 保留素材原语法；实际执行请以部署版本官方文档为准。
BEST PRACTICE · 05

同一套索引，三种不同的关注点

定位、运维、使用三层的判断标准并不相同。

面向数据库架构师

先定边界

  • 定位为「Postgres 内强一致全文搜索索引」，不是 B-tree、GIN、向量索引的通用替代。
  • 先明确搜索字段、过滤字段、排序字段、聚合字段；文档建议把可能用到的列都放进 BM25 索引。
  • 字段越多，写入和空间成本越高 —— 这是选型时的硬约束。
  • 语义搜索、相似图片、embedding rerank 场景，把 BM25 当召回或混合检索的一路。
面向 DBA

盯住段与可见性

  • 关注 segment 数量：应至少 ≥ 单查询可用并行 worker 数；段过多会明显拖慢搜索。
  • 关注 VACUUM、merge、长事务：删除和更新不会自动等价于物理空间马上回收。
  • 对写入高峰与查询高峰做隔离评估：merge / compaction 是真实 IO，不是免费后台任务。
  • 用 EXPLAIN ANALYZE 验证 custom scan 是否生效。
面向业务开发者

写对查询

  • key_field 选稳定唯一字段（通常是主键），不要选频繁更新或非唯一字段。
  • 明确 tokenizer：默认分词不一定适合中文、SKU、邮箱、路径、日志 token、代码片段。
  • 相关性排序要显式看 score(...)；叠加业务排序字段时注意方向与 LIMIT 语义。
  • 不要把所有字段都当全文字段：数值、时间、布尔更多用于过滤或排序。
共同原则：先用 EXPLAIN 确认路径，再用真实数据量、真实并发、真实字段配置谈性能；不要凭配置表或口号下结论。
WHEN TO USE · 05

选型的分界线：强一致 + BM25 + 混合过滤

数据主系统在 PostgreSQL、又需要相关性排序时，ParadeDB 的位置最舒服。

✅ 适合

数据主系统在 PostgreSQL
要求搜索结果与事务状态强一致，写完即可查。
需要 BM25 相关性 + 结构化处理
同时按结构化字段过滤、排序、聚合。
超出原生路径的舒适区
数据量和查询复杂度超过 ILIKE、tsvector + GIN。
不想维护双系统
不想维护外部搜索集群、CDC、双写补偿与一致性排障。

⛔ 不适合

只做主键点查 / 范围扫描 / 唯一约束
B-tree 更合适，别为索引付出 segment 维护成本。
只做 JSONB / 数组包含查询
不需要 BM25 相关性时，GIN 可能更简单。
写入极高、查询很少
BM25 索引维护可能得不偿失。
主要需求是语义相似度
应评估向量索引或混合检索。
跨库跨服务的大规模独立搜索集群
Elasticsearch / OpenSearch 仍有生态优势。
判断顺序建议：先问「要不要事务强一致」→ 再问「要不要 BM25 相关性」→ 再问「是否同时有结构化过滤 / 排序 / 聚合」→ 最后才看团队运维成本。
PITFALLS · 05

大多数「搜索不好用」不是打分模型的问题

分词、key_field、字段配置、验证方式，比调 BM25 参数更容易出错。

坑 1

把 BM25 当模糊匹配

BM25 是基于 token 的词项匹配。分词器不对，相关性再好也找不到想要的词。中文、SKU、邮箱要专门配 tokenizer。

坑 2

忽视 key_field 约束

文档唯一标识必须稳定唯一（0.25 还要求列在第一位）；不稳定会直接影响索引更新、去重和分数返回。

坑 3

字段全塞进去

索引字段越多，写入、merge、空间与 cache 压力越大。先从搜索路径必需字段开始，再按 EXPLAIN 结果补。

坑 4

只看平均延迟

segment merge、VACUUM、长事务、批量导入主要打击尾延迟，P95 / P99 比平均值更能说明问题。

坑 5

误解 DataFusion 的角色

DataFusion 是查询执行框架，不是 BM25 posting list。BM25 索引结构要看 ParadeDB + Tantivy，别在错误的仓库里找答案。

坑 6

用性能口号替代验证

必须用本地数据、真实查询、真实并发、真实字段配置测 EXPLAIN ANALYZE，而不是引用别人的基准数字。

坑 7

忽略更新模式

频繁 UPDATE 文本字段会同时制造旧文档删除标记和新 segment，merge 压力比 insert-only 大得多。

附加

忘记看执行计划

没有 ParadeDB 操作符时 custom scan 不会触发，查询完全走原生 Postgres，索引等于白建。

WRAP-UP · 06

把结构装进事务，把 Top-K 交给上界

理解 ParadeDB BM25，只需要记住下面三句话，以及它们各自的边界。

01

倒排把问题反过来

term → posting list → 候选集 → BM25 Top-K；压缩与 128 doc 分块让「大倒排链」可顺序解码，fieldnorm 让评分不必回表。

02

上界带来安全剪枝

Block-Max WAND 用 block 最大可能分数证明某些候选不可能进入 Top-K，跳过它们而不损失召回。

03

数据库约束是分水岭

事务快照、可见性、segment merge、VACUUM 与 custom scan 下推，决定了「搜索引擎式结构」在 Postgres 里真实的成本与收益。
