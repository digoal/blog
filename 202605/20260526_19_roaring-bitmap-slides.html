01 · 问题典型 workload

查询的本质：把谓词变成整数集合

在访问明细行之前，先把候选 rowid / docid 集合缩小。

01 · 问题矛盾：既要压缩，又要快

三种朴素表示，各有各的硬成本

同一个稀疏集合 {100, 1000000000}，三种结构表现截然不同。

完整 bitset
一个 bit 覆盖一个值
优点 位运算极快，两集合求交就是机器字按位与。
硬成本 空间随最大值域增长，不随实际元素数增长；2³² 空间需 2³² bit。
稀疏时浪费严重
排序数组 / posting list
uint16 / uint32 有序列表
优点 稀疏时极省空间，顺序迭代友好。
硬成本 交并差需要比较、移动和写结果；局部稠密时比固定 bitmap 更大也更慢。
稠密分片不占优
RLE / WAH / EWAH 类
压缩连续的 0 / 1 run
优点 长连续段非常省，例如 [100000, 200000] 编成一个 run。
硬成本 值随机分布时 run 膨胀；复杂交并差要处理段边界与分支。
怕随机、怕高速交集
共同问题：三者都试图为「整个值域」选定一种压缩方式。而真实数据的局部分布并不统一——同一个集合里，有的区间稀疏，有的区间稠密，有的区间连续。
图 2 · 三种朴素表示的空间/速度特性对比；Roaring 的目标是把三者优点放进同一结构。
01 · 问题核心思路

不要为整个值域选一种压缩方式

把 32 位空间切成 65 536 个局部分片，每个分片独立选择最合适的容器。

32-bit unsigned 值域 0 .. 2³²−1，共 4 294 967 296 个可能值
STEP 1
高 16 位作为目录 key
定位一个局部容器
STEP 2
低 16 位放进该容器
局部空间固定 0..65535
STEP 3
按局部形态选容器
array / bitset / run
STEP 4
运算先对齐目录 key
再走类型专用算法
代价也同样明确：结构更复杂，需要维护目录、容器类型、转换阈值、序列化格式与跨容器操作矩阵。它不是「压缩版 bitset」，而是两级、自适应、硬件友好的整数集合索引结构。

02 · 结构high 16 / low 16

两级结构：有序目录 + 自适应容器

对 32 位无符号整数，high = value >> 16，low = value & 0xFFFF。

输入整数 value = 0x0002_01F4（十进制 131 572） 一个 high-key 最多对应一个容器，容器覆盖局部 0..65535
high = 0x0002  (高 16 位)
作为顶层目录 key，定位分片
low = 0x01F4  (低 16 位 = 500)
作为容器内值，存入该分片的容器
roaring_array_t 按 high-key 有序管理的一组容器指针 不是哈希表，顶层是 size / keys / containers / typecodes
目录项（仅记录出现过元素的 key）
容器（按局部分布独立选择）
key 0x0001 稀疏分片
→
array container 排序 uint16 数组 · 2 B/元素
key 0x0002 稠密分片
→
bitset container 固定 65 536 bit = 8 KiB
key 0x0010 连续分片

Roaring 避免为整个 32 位空间分配完整 bitmap：只有出现过元素的 high-key 才有目录项，空洞的值域不占空间；每个目录项下的低 16 位再独立选择最省 / 最快的表示。

02 · 结构第一性原理

为什么 array / bitset 的分界线是 4096？

不是拍脑袋的常数，而是两条空间曲线在同一个 16-bit 分片内的交点。

一个 16-bit 分片内，两种表示的字节数
array = 2 × n bitset = 1024 × 8 = 8192 B 交点 (4096, 8192)
等式
4096 × 2 B
= 8192 B
= 1024 words × 8 B
超过这个点，bitset 不再比 array 更占空间，并且集合运算更适合走机器字位运算。
工程上还要考虑
  • array 的分配容量（capacity）与实际占用
  • lazy 运算后 cardinality 可能为未知值，需要修复
  • run 优化会再比较第三种表示的空间
  • 删除使 card ≤ 4096 时，bitset 可转回 array
图 6 · 4096 阈值来自「2 字节/元素」与「固定 8 KiB bitset」的空间平衡点；Roaring Format Spec 也以 4096 作为 array / bitset 的分界。

03 · 机制硬件友好

9 种容器组合，各自走专用算法

混合类型运算直接在压缩结构上做，不需要先解压成同一种表示。

容器类型分派矩阵（行 = A，列 = B）
A ＼ Barraybitsetrun
array排序数组交集：线性 merge / galloping / SIMD遍历 array，查 bitset 对应 bit按 run 段边界判定
bitset对称：查 bit1024 个 uint64 word 做 & | ^ &~ + SIMD popcount段展开 / 位运算配合
run按连续段边界处理按连续段边界处理两个有序 RLE 段归并
论文《SIMD Compression and the Intersection of Sorted Integers》证明排序整数数组交集可从 SIMD 受益，尤其是 posting list 场景；CRoaring 的 bitset / run 路径也包含 AVX2、AVX-512、NEON 或 runtime dispatch 实现。
CPU 友好的连续布局
  • bitset：连续 uint64_t words
  • array：连续排序 uint16_t
  • run：连续 RLE pair
相比链式对象或散列结构，更容易被 cache 与 SIMD 利用。isadetection.c 负责运行时硬件能力检测。
SIMD 不是永远更快
CRoaring README 明确提到：AVX2 代码避免浮点与乘法，以减少多核 Intel 上的 turbo 降频风险；AVX-512 只在较新硬件启用。run.c 注释也指出经验上 AVX-512 不总是快于 AVX2。

03 · 机制值域扩展

64-bit Roaring：高 48 位用 ART，低 16 位仍进容器

顶层目录可以替换实现；「容器内局部 16-bit 空间」始终是稳定核心。

roaring64_bitmap_t 的两级映射
为什么换成 ART？
32-bit Roaring 用 high 16 位目录就够了，因为最多 65 536 个容器。64-bit 空间若照搬 high-key 数组会极其稀疏；自适应基数树按字节前缀压缩路径，更适合稀疏的 48 位 key。
roaring64_bitmap_t 内部包含 art_t art、containers 指针数组，以及记录容器 index 与 typecode 的 leaf。
可替换的是顶层，不是核心
容器内「局部 16-bit 空间」是稳定核心：array / bitset / run 三种表示与 4096 阈值都不变。顶层目录只是根据值域大小换了一种索引实现。
工程上的另一种选择
对 64-bit rowid / docid，也可做 segment id + 32-bit local id 的两级拆分，常更利于局部性与序列化格式。源码：roaring64.c。
图 11 · 64 位 Roaring 的 ART 顶层与 16 位容器；Java 的 Roaring64Bitmap 同样采用 48 位 ART key + 16 位容器。

横向对比：把三种表示的优点装进同一个两级结构

关键不是谁绝对更快，而是 Roaring 能按局部分布切换。

04 · 评估收益拆解

收益可以拆成四类

空间、CPU、查询路径、生态互通——每一类都对应结构上的一个设计选择。

① 空间随「实际分片 + 局部密度」增长
不再随全局最大值增长。只落在少数 high-key 的集合只需少数容器；每个容器再按稀疏 / 稠密 / 连续选择表示。
② 集合运算利用 CPU 友好布局
bitset 是连续 uint64_t words，array 是连续排序 uint16_t，run 是连续 RLE pair；比链式对象或散列结构更容易被 cache 与 SIMD 利用。
③ 查询先组合候选集合，再访问明细行
搜索引擎、列存、OLAP 常把维度值、倒排词项、segment zone map 或权限条件映射成 rowid / docid 的 Roaring 集合，多个条件先在集合层相交或相并。
④ 序列化格式让不同语言实现互通
CRoaring README 指向 Roaring Format Spec，C/C++、Java、Go、Python 等实现可通过统一格式交换 bitmap。工业界采用：Lucene / Elasticsearch、ClickHouse、Apache Doris、StarRocks、Spark、Redpanda、Google Procella 等。

04 · 评估代价同样明确

五条代价，以及两条容易混淆的边界

Roaring 不是有损结构，也不是线程安全的共享对象。

五条代价
1
写入不是免费
单点 add / remove 可能触发 array↔bitset 转换；run 优化还需扫描与重编码。批量构建通常更友好。
2
小集合不一定值得
几十个整数用排序数组、small vector 或普通 set 可能更简单也更快。
3
极端随机分布会削弱 run 优势
连续段很少时，主要靠 array / bitset 混合，run 帮不上忙。
4
不是有损结构
与 Bloom filter 不同，没有 false positive；但也意味着不能用误判换取更小空间。
5
数据库落盘语义要额外设计
做真正索引 AM 需处理并发、MVCC、崩溃恢复、统计信息、vacuum / compaction。
边界①：并发读写
CRoaring README 说明库本身没有内置线程支持：一个线程修改 bitmap 时，其他线程查询同一对象是不安全的。需要复制、copy-on-write 或外部同步。

Roaring
精确集合 · 无 false positive · 可迭代出所有元素

04 · 评估落地位置

Roaring 在数据库里通常位于「谓词命中的集合」这一层

常见建模是 值 / 词项 → rowid / docid Roaring set，而不是替换索引访问方法。

事实表 / 列存段
rowid · status · city · tag
→
字典 / posting 入口
status=paid · city=CN
→
Roaring 集合
压缩 docid · 支持 AND / OR
→
集合交集 → 回表
先缩小候选，再访问明细行
边界：事务可见性、MVCC、锁、WAL、代价估算、回表 recheck 仍由数据库引擎负责；Roaring 只解决整数集合的表示与集合运算。
SQL 建模示意（伪代码，函数名取决于扩展 / 引擎实现）未在本机数据库执行
CREATE TABLE rb_posting (
    attr_name  text,  attr_value text,
    roaring_docids bytea,
    PRIMARY KEY (attr_name, attr_value)
);

-- 查询时：取出多个 roaring_docids，先在扩展函数中求交，再回表 docid
SELECT count(*) FROM documents d
JOIN LATERAL roaring_to_rows(
    roaring_and(
      (SELECT roaring_docids FROM rb_posting WHERE attr_name='city'   AND attr_value='CN'),
      (SELECT roaring_docids FROM rb_posting WHERE attr_name='status' AND attr_value='paid')
    )) AS hit(docid) ON hit.docid = d.docid;

06 · 决策按角色分工

三种角色，各自该盯住什么

同一套结构，架构师看建模、DBA 看维护、业务开发者看用法。

架构师建模与格式
  • 把 Roaring 放在「集合层」，而不是当成 B-tree 替代品；常见建模是 值/词项 → rowid/docid set。
  • 先按 workload 判断收益：是否大量多条件组合、能否在回表前显著缩小候选、是否读多写少。
  • 对 64-bit id，确认用 64-bit Roaring，还是 segment id + local rowid 两级拆分。
  • 落盘策略：跨语言 / 跨版本用 portable；同版本 mmap 加速才考虑 frozen。
DBA监控与维护
  • 监控容器组成：array / bitset / run 比例变化，往往比总大小更能解释性能波动。
  • 批量装载后再构建或重写 bitmap，通常比逐行维护更稳定。
  • 持续更新的 posting list 用 delta + 周期 merge，避免每事务改大对象。
  • 评估内存峰值：多路 OR / lazy union 可能暂存较多 bitset，需 repair_after_lazy()。
业务开发者用法与验证
  • 优先用在 rowid/docid、用户 id、权限 id、标签集合这类整数集合。
  • 不要把极小集合强行 Roaring 化；短数组更简单也可能更快。
  • 写查询时让集合组合发生在回表前：先相交再 join 明细。
  • 保存代表性样本做 benchmark：稀疏、稠密、连续、随机、冷热都要覆盖。

06 · 决策场景清单

适合什么，不适合什么

判断依据是瓶颈类型，而不是「这个结构听起来很先进」。

适合集合运算重、更新可控
  • 搜索引擎倒排索引中的 docid posting list
  • OLAP / 列存的 segment 内 rowid 集合、删除向量、zone / skip metadata
  • 用户画像、标签、权限系统中的大规模整数集合交并差
  • 数据分布局部性强：同一 high-key 内可能稀疏、稠密或连续
  • 读多写少或批量更新，可接受周期性 merge / optimize
不适合事务访问、有序扫描、小集合
  • 高频 OLTP 单点更新，且要求每次同步改大 bitmap
  • 集合极小，几十个整数就结束
  • 查询主要是有序范围扫描、排序、前缀匹配，而不是集合交并差
  • 需要完整索引语义，却没有实现 MVCC、锁、WAL、统计信息与 vacuum / compaction
  • 值域与分布已知很小，普通固定 bitset 更简单
一句话：Roaring 擅长「多个大整数集合的交并差，且更新可控」；把它用成万能索引，通常会把复杂度转移到事务与一致性上。

06 · 决策避坑清单

七个常见坑

大多不是 API 用错，而是把结构放错了层、或者看错了指标。

1
把 Roaring 当成数据库索引 AM
CRoaring 只负责整数集合；事务可见性、锁、恢复、统计信息与执行器接口仍归引擎。
2
只看总 cardinality，不看局部分布
相同总基数、不同分布可能得到完全不同的容器组成与性能。
3
忘记调用 run optimize
逐点插入形成的连续值不会自动变 run；部分 range API 可直接构造 run，但别假定所有写入路径都是。
4
把论文 benchmark 当成自己系统的 SLA
查询组合、CPU 指令集、编译器、冷热缓存、序列化路径都会改变结果。
5
滥用 frozen 格式
与 C 内存布局、大小端相关，不适合长期 / 跨版本 / 跨语言交换。
6
并发读写同一个 bitmap
库本身没有内置线程支持；需复制、copy-on-write 或外部同步。
7
对短生命周期小集合过度工程化
一次函数调用内存在、元素很少时，排序数组或栈上 small vector 更简单。
✓
共同的解法
先明确「集合层」与「数据库语义层」的边界，再用代表性样本验证容器组成与查询路径。

结语带走这页

一页速记：结构、代价、边界

理解一种索引结构如何把查询问题转化成集合问题，也理解它把代价转移到了哪里。

六条核心结论
1两级结构：high 16 位做有序目录 key，low 16 位进容器；只有有值的分片才分配。
2三类容器：array（稀疏 2n B）、bitset（稠密 8192 B）、run（连续 2+4r B）按局部形态自适应。
34096 阈值来自 4096×2 B = 8192 B 的空间平衡点，不是经验凑数。
4两层剪枝：目录层跳过不可能命中的分片，容器层走类型专用算法与 SIMD。
5数据库里常作为 值/词项 → rowid set 的 posting list；MVCC、WAL、代价估算仍归引擎。
6选型看 workload：集合运算重、读多写少才合适；小集合、事务索引、有序扫描不适合。
扩展问题
① Roaring 该放在执行器中间结构、索引 posting list，还是列存 segment metadata？
② 持续增量写入的 posting list：直接改主 Roaring，还是 delta + compact？何时 merge？
③ 64-bit id 用 roaring64_bitmap_t 还是 shard + 32-bit local id？
④ Top-N 排序中，先过滤候选后排序是否仍是瓶颈？能否结合 WAND / Block-Max WAND？
⑤ 如何把容器统计信息喂给优化器，估算一次交集剩多少 rowid？
