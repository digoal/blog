01 背景 · 它解决什么问题

Embedding 越多、维度越高，精确检索越贵

1 亿条 768 维 float32 向量，仅原始向量
≈ 286 GiB
1e8 × 768 × 4 B = 3.072 × 10¹¹ B — 还没算主键、元数据、索引边、缓存和副本
精确 KNN 的单次查询代价
O(N · d)
等价于「没有选择性过滤条件的全表扫描」，只是扫描对象从行变成了向量
方向 ① 减少候选数
IVF、HNSW、NSG 把搜索限制在一小部分候选上。
方向 ② 减少单向量存储
PQ、SQ、二值量化、半精度压缩原始向量。
方向 ③ 减少距离计算成本
预计算查表、SIMD、GPU、批量化、重排候选。
HNSW-PQ 组合的是 ① + ②/③：把「在所有原始向量上精确算距离」变成「沿 HNSW 图访问少量节点，并对这些节点的 PQ code 做近似距离打分」。
01 背景 · 组合定位

HNSW 负责「少看点」，PQ 负责「少存点、算轻点」

一句话定义
HNSW-PQ 是「用 HNSW 图做候选导航、用 PQ 压缩码保存向量并近似计算距离」的 ANN 索引结构。
关键在「候选生成」与「候选打分」分离：图决定看谁，PQ 决定怎么给看到的候选算分。
牺牲也很明确（5 条）
  • HNSW 图要保存邻接边，内存不会只剩 PQ code。
  • PQ code 引入量化误差，候选排序可能错。
  • HNSW 是近似图搜索，efSearch 不够时可能走不到真近邻。
  • 构建需先训练 PQ，再插入向量并维护图边。
  • 高频原地更新 / 删除 / 事务可见性不是强项，要数据库层另做 segment、delete bitmap、后台重建或版本管理。

03 核心原理 · HNSW

HNSW：上层快速接近目标区域，底层精细搜索

层级怎么来
每个点随机获得一个最高层级，概率指数衰减。HNSW::set_default_probas() 设置该分布。
为什么快
上层节点少、边跨度大，几次贪心就能接近目标区域；底层节点全、边密，负责精细搜索。
建边四步
高层贪心找入口 → 到插入层搜一批候选邻居 → 启发式裁剪避免只连同一小簇 → 写双向边，邻居满则重裁剪。
源码：HNSW::add_with_locks() 负责从高层贪心下降，逐层调用 add_links_starting_from() 建边；level 0 邻居容量 2 × M，上层 M。

播放控制
efSearch越大 → 候选访问越多
搜索步骤
HNSW 的速度来自「少访问候选」，PQ 的速度和省内存来自「每个候选只访问短 code 并查表累加」—— 二者在同一条查询链路上接力。
03 核心原理 · 容易忽略的一点

建图时用的距离，本身就是近似的

容易忽略的点
HNSW 建图不是拿原始向量精确距离选边，而是通过 IndexPQ 的距离计算器在压缩表示上比较。也就是说：图质量本身也受 PQ 量化误差影响。
构建顺序不能颠倒：先训练 PQ 码本 → 再预计算 SDC 表 → 再插入向量并维护图边。
SDC 表：什么时候用、什么时候不用
  • 建图时：code-code 距离（SDC）用于邻接边选择，依赖该表。
  • 查询时：query 保持原始 float，走 ADC 距离表，不使用 SDC 表。
  • 开销：pq_m × ksub × ksub × 4 B；pq_nbits=8, pq_m=96 时约 24 MiB。
  • 读取时可用 IO_FLAG_PQ_SKIP_SDC_TABLE 跳过；跳过后若还要继续建图，会踩到实现边界。
03 核心原理 · 图 3

查询：HNSW 负责走图，PQ 负责打分

IndexHNSW::search() 的 6 步
  • 建结果堆，准备 top-k 收集。
  • hnsw_search() 为每个 query 创建 storage_distance_computer(index->storage)。
  • set_query()：PQ 预计算 query 到各子码本 centroid 的距离表（ADC）。
  • HNSW::search() 从 entry point 开始，高层贪心下降。
  • 到 level 0 后 search_from_candidates() 扩展邻居，用 qdis(v1) 对候选 code 打分。
  • efSearch 控制候选扩展宽度，结果堆返回 top-k。
误差会叠加：图可能没走到真近邻（图近似），PQ 也可能把候选距离排错（量化误差）。二者同时影响最终召回。
速度来源拆开看：HNSW 让「被访问的候选数」变少；PQ 让「每个候选的存储与距离计算」变轻。任何一处退化，都会同时影响 recall 与延迟。

04 横向对比 · 图 4（重绘）

HNSW-PQ 位于 HNSW-Flat 与纯 PQ 之间

主要工程含义
  • Flat：准确但线性扫描，适合基线与重排。
  • HNSW-Flat：快，但原始向量和图边都占内存。
  • PQ：省内存，但距离有量化误差。
  • HNSW-PQ：图导航 + 压缩打分，两种误差叠加。
  • 写入：训练后 add，会更新图边。
  • 删除：Faiss HNSW 路径不适合高频原地删改。
参数调优要同时看召回、P99、内存和重建成本，不能只盯一个数字。
横轴为综合代价：Flat 无需训练与图维护，故偏左；HNSW-Flat 既有原始向量又有图边，故偏右。此图只表达相对关系，不代表测量结果。
05 效果如何 · 不谈脱离数据集的固定性能数字

容量预算：别只算 PQ 压缩比

粗略内存框架（故意不写成精确值）
HNSW-PQ index memory ≈ N * code_size + N * average_graph_edges * sizeof(storage_idx_t) + HNSW offsets / levels + PQ centroids + optional SDC table + allocator / vector overhead
不同实现有 id、padding、vector capacity、序列化 / 运行时结构差异。做容量规划应用目标参数真实构建样本索引，再结合进程 RSS、序列化文件大小与 recall / latency 一起评估。
查询侧成本
  • 每个 query 先算 pq_m × ksub 距离表（示例 96 × 256 = 24,576 项）。
  • 再对访问到的候选 code 逐段查表累加；efSearch 越大，候选访问与跳边越多。
  • 召回率受图质量、efSearch、量化误差、向量分布、距离度量共同影响。
  • 构建时间：PQ 训练要 k-means；HNSW add 要在图上搜索建边，efConstruction 越大越慢。
向量编码
3072 B → 96 B
d=768, pq_m=96, pq_nbits=8；编码压缩 32×。
图边
2M × 4 B
level 0 邻接表预留，storage_idx_t 为 int32。举例 M=32 时约 256 B / 向量 —— 比 code 还大。
PQ 码本
≈ 768 KiB
pq_m × 2^nbits × dsub × 4 B；nbits 增大时快速增长。
SDC 表
≈ 24 MiB
pq_m × ksub × ksub × 4 B；每子量化器 256×256×4 = 256 KiB。
最容易犯的错
只用 PQ 压缩比估内存，会系统性低估：HNSW-PQ 不是纯压缩数组，图边、层级、offset、码本、SDC 表都会吃内存。容量规划要同时算 PQ code 和 HNSW 图边。
06 实操 DEMO · Faiss Python

最小示例：HNSW8,PQ4np

  • PQ4：pq_m = 4，bit 数省略时默认 8。
  • np：关闭 polysemous training，与 factory 源码对 do_polysemous_training 的处理一致。

07 最佳实践

不同角色，关注点完全不同

架构师
定位与架构
  • 先把 HNSW-PQ 定位为「读多写少的召回索引」，不要当成支持强事务与高频更新的 B-tree。
  • 容量规划要同时算 PQ code 和 HNSW 图边；只用压缩比估内存会系统性低估。
  • 保留精确重排通道：召回 top-R 候选用原始向量或更高精度向量重排。
  • 把 delete bitmap、segment compaction、后台重建纳入架构；Faiss 的 IndexHNSW 不是数据库 MVCC 索引。
DBA
调参与运维
  • 用 recall@k 和 P99 一起调 efSearch；只看平均延迟会掩盖图搜索的尾部问题。
  • 训练 PQ 的样本要覆盖线上分布；模型升级或分布漂移后旧码本可能明显变差。
  • 监控构建峰值内存：PQ 训练、SDC 表、HNSW 构建候选都会产生额外内存。
  • 序列化 / 恢复后做一致性 smoke test，尤其关注 IO_FLAG_PQ_SKIP_SDC_TABLE 这类读取参数。
业务开发者
用法与降级
  • 不要把 ANN 返回距离当成可跨索引、跨模型、跨参数稳定比较的业务分数。
  • 写入路径接受「先进新 segment，后台建索引 / 合并」的延迟，而非每条写入立即进入全局最优图。
  • 查询参数绑定业务目标：推荐召回、RAG 召回、去重、风控相似案例，对 recall 与延迟容忍度不同。
  • 关键链路保留降级：小数据或低并发时 Flat 就够；高精度场景 ANN 召回后精排。
三者的共同底线：必须有 Flat 精确基线。没有基线，就无法判断调参究竟是变好，还是「变快但变差」。
08 适合 / 不适合

用对地方，比调好参数更重要

✓
适合
  • 百万到十亿级向量，内存预算明显不足以保存 HNSW-Flat。
  • 读多写少，允许批量构建、周期重建或 segment 合并。
  • 业务接受近似召回，可通过 efSearch、重排和离线评测控制质量。
  • 向量分布相对稳定，PQ 码本不会频繁失效。
  • 候选召回比精确排序更重要：RAG 初筛、推荐候选生成、相似图片 / 文本初召。
✕
不适合
  • 必须精确 top-k，不能接受量化误差和图近似。
  • 高频 update / delete，并要求单条变更立即对所有查询强一致可见。
  • 数据量不大，Flat 或 HNSW-Flat 已经满足成本和延迟。
  • 向量模型频繁变更，全量重编码与重建成本不可接受。
  • 业务距离阈值有强语义，不能接受 PQ 近似距离漂移。
判断顺序建议：先看数据规模与内存预算 → 再看写入 / 事务要求 → 最后看召回精度容忍度。任一不满足，就考虑 HNSW-Flat / Flat 或数据库层另做治理。
09 常见坑

8 个高频踩坑点

1
只算 PQ 压缩比，不算图边
图边、层级、offset、SDC 表都会吃内存；HNSW-PQ 不是纯压缩数组。
2
训练样本太少或不代表线上分布
PQ 码本由训练数据决定；样本偏了，距离误差会直接进入排序。
3
把 efSearch 当成固定推荐值
它是召回和延迟旋钮，随数据集、k、并发、CPU cache 行为变化。
4
忽略构建距离也是近似的
add 阶段图边选择依赖 PQ storage 的距离计算器与 SDC 表，图质量受量化误差影响。
5
误以为自动适合数据库事务更新
Faiss 是向量检索库，MVCC、删除、segment、WAL、恢复、compaction 要数据库产品自己处理。
6
没有 Flat 基线
召回率必须以精确搜索为基线，否则无法判断调参是变好还是变快但变差。
7
距离度量和向量归一化混用
L2、内积、cosine 语义不同；cosine 常通过归一化后内积实现，索引与训练数据要一致。
8
忽略序列化恢复后的辅助表
SDC 表可恢复时重建，也可用 flag 跳过；跳过后若需要 code-code 距离会踩到实现边界。
坑 1、4、8 都指向同一件事：HNSW-PQ 是「图 + 压缩码 + 辅助表」的组合系统，只盯住 code 会漏掉一半复杂度。
10 扩展 · 阅读 · 结语

把这 6 个问题带回你的系统里

扩展问题
  • 放进 PostgreSQL 扩展后，delete bitmap、VACUUM、WAL、crash recovery 应该放在哪一层？
  • RAG 场景该直接返回 top-k，还是返回 top-R 后用原始向量和 reranker 重排？
  • IVF-PQ 与 HNSW-PQ 在分布漂移、增量写入、冷热分层上的取舍有何不同？
