01 / 问题定义

Embedding 越来越大，业务却要更快、更省

只说「用 HNSW」不够：HNSW 解决「少访问多少节点」，不解决「每个节点多大」。

读图：柱子是「一个可用的向量检索服务」所需的全部工作集，不只是向量数组本身。量化只压缩最底下那一层。
1 亿条 × 768 维 × 4 B = 307,200,000,000 B
286GiB 原始向量
再加 HNSW 图边、行标识、MVCC、索引页、缓存与副本，单机内存很快不够

AHNSW 减小的是 N

不扫描全部向量，沿多层近邻图访问一批候选。访问路径问题。

BSQ / 低精度减小的是字节

每维从 float 压成低 bit，向量更短、更容易留在内存与 CPU cache。节点表示问题。

!
两者正交，可以叠加；但误差也来自两层：走图近似 + 表示误差。
01 / 成本模型

精确 KNN 的代价 = 访问多少点 × 每个点多贵

把总代价画成矩形面积：HNSW 压宽度，低精度压高度。四格图里的虚线框是「全表精确扫描」基线。

示意比例，不是 benchmark。面积 = N × d × cost_per_dimension 与 N × bytes_per_vector 的直观类比；真实收益取决于数据集、维度、图参数与缓存命中。
精确搜索的两笔账conceptual
-- 计算量：逐候选算距离
distance_work = N * d * cost_per_dimension
-- 内存带宽：逐候选读向量
memory_read   = N * bytes_per_vector
→
HNSW 把第一式的 N 变小：沿多层近邻图只访问一批候选。
SQ / 低精度把第二式的 bytes_per_vector 变小：每维从 4 字节降到 2 字节、1 字节甚至 1 bit。
01 / 别忘了这是数据库，不是纯算法库

量化只动最上面那一层

HNSW-SQ 解决的是「向量召回阶段的候选访问成本与内存工作集」，不解决所有检索问题。

1索引页空间

HNSW 节点除向量值，还要保存层级、版本、heap TID、邻接边。一个 element tuple 最多带 10 个 heap TID，邻居另存 neighbor tuple。

2执行器语义

PostgreSQL 仍要处理 MVCC 可见性、过滤条件、排序、LIMIT。近似索引的过滤在索引扫描之后应用，这是后面最重要的坑。

3维护成本

插入要更新图；删除和更新留下死 TID，靠 VACUUM / REINDEX 治理。量化降低距离计算和节点值 IO，但不消除写放大。

⚑
边界：HNSW 是近似搜索，ef_search 太小会漏真近邻；量化引入表示误差，候选距离排序可能改变；二值量化尤其激进，通常要扩大 top-R 后用原始向量重排。
02 / 全篇最重要的一页

「HNSW-SQ」在算法层 ≠ 在 pgvector 里

文章的重点不是把 SQ 泛化成营销词，而是把边界讲清楚：图结构是什么、低精度改变了什么、源码实际支持什么。

!为什么这件事必须说清

数据库索引不只是一个距离函数：它需要类型、opclass、存储格式、WAL、升级脚本、执行器集成。别的引擎有 IndexScalarQuantizer，不等于 pgvector 的 HNSW 也能用同一套容量规划。把二手 benchmark 或营销文里的「INT8 SQ」直接写进设计文档，是最常见的规划错误。

✓ 核验来源（2026-11-15）
官方 README：支持类型 vector / halfvec / bit / sparsevec，索引类型 HNSW / IVFFlat。
CHANGELOG：最新稳定版 0.8.7（2026-10-01）、0.9.0 unreleased，历次变更均无 scalar quantization / INT8 相关条目。
本地源码 hnsw.c / hnsw.h / sql/vector.sql 交叉核对。
02 / pgvector 里的四种「写法」，只有三种能跑

路径对比：精度优先 → 温和压缩 → 激进粗召回

条形长度表示单个向量 value 部分的相对大小；灰虚线条是「概念上存在、pgvector 中不存在」的严格 INT8 SQ。

路径pgvector 形态是否严格 SQ典型用途
HNSW + vectorUSING hnsw (embedding vector_l2_ops)否精度优先的质量基线，维度 ≤ 2000
HNSW + halfvecUSING hnsw ((embedding::halfvec(n)) halfvec_l2_ops)近似低精度降低向量值大小、索引更高维（≤ 4000）
HNSW + bitUSING hnsw ((binary_quantize(embedding)::bit(n)) bit_hamming_ops)二值量化超小索引做粗召回，配合原始向量重排（≤ 64000）
HNSW + INT8 SQpgvector 当前无独立类型 / opclass是（概念）需其他系统、自定义扩展或未来能力
i
读表方法：HNSW 是访问路径，低精度表示是节点值和距离函数的选择。表达式索引写入索引的是表达式结果，不是原始 embedding；heap TID 仍指向原表行，所以重排时可以回表取原始向量。
02 / 先把词统一，后面才好讲

七个术语 · 一张参数地图

建图参数决定「图长什么样」，查询参数决定「这次搜索走多远」——它们不是同一个旋钮。

HNSWHierarchical Navigable Small World，分层可导航小世界图。上层稀疏负责快速接近目标区域，底层密集负责候选扩展。
m每层邻居数量参数，pgvector 默认 16；level 0 实际使用 2 * m 的邻居容量。
ef_construction建图时动态候选列表大小，默认 64。越大图质量通常越好，构建和插入越慢。
hnsw.ef_search查询时动态候选列表大小，默认 40。越大召回通常越好，延迟和内存越高。
SQScalar Quantization，每维独立映射到低 bit 整数（如 INT8），需要 scale、zero point 或 min/max。
二值量化binary_quantize() 把每维按「是否 > 0」转成 1 bit；更激进的符号量化，不等同于 INT8 SQ。
重排先用低精度索引取 top-R，再用原始向量距离取最终 top-K；R 通常远大于 K。
∑
两个误差源要分开记：走图近似（HNSW 没走到真近邻）与 表示误差（量化改变候选距离排序）。调 ef_search 只治前者，重排只治后者。

03 / src/hnsw.h · hnswbuild.c

节点值和邻接表，是两类 index tuple

一个 HNSW 节点在磁盘上并不只是「一个向量」：它自带层级、版本、heap TID、邻接 indextids，以及页与 tuple 头开销。

关键点：表达式索引 binary_quantize(embedding)::bit(n) 写入索引的是表达式结果，不是原始 embedding；heap TID 仍指向原表行，因此两阶段重排可行。

源码里的维度闸门

HNSW_MAX_DIM = 2000；hnsw_halfvec_support → 4000，hnsw_bit_support → 64000，hnsw_sparsevec_support 检查非零元素 ≤ HNSW_MAX_NNZ = 1000。与官方 README 的 HNSW 支持维度一致。

i
注意区分：halfvec 类型本身可存到 16000 维，但 HNSW 可索引上限是 4000 维。设计表结构时两者别混。

03 / 量化索引的正确用法

召回阶段「少访问、少 IO」，重排阶段「纠正误差」

pgvector README 的二值量化示例正是这种模式：先按 Hamming 取 top-R，再按原始 embedding <=> query 排序取 top-K。

读图：top-R 里的 100 只是示例，不是最佳值。应在目标数据集上扫 R = 50 / 100 / 200 / 500，画 recall@10 与 P95 / P99 延迟曲线再定。
!
二值量化不重排，是常见坑。Hamming 距离适合快速粗召回，但不等价于原始 cosine / L2 排序；符号量化丢掉了全部幅度信息。
→
代价也要算：R 越大，回表量与精确距离计算越多。两阶段不是「免费提精度」，而是把成本从「全库扫描」挪到「候选 + 重排」。
03 / 过滤发生在索引扫描之后

WHERE 只匹配 10%，ef_search = 40 会发生什么？

近似索引不会「自动理解」过滤条件。结果不足不是 bug，是执行顺序的必然结果。

1iterative index scans

SET hnsw.iterative_scan = strict_order;（保证按距离严格有序）或 relaxed_order（允许略微乱序、召回更好）。配合 hnsw.max_scan_tuples = 20000 与 hnsw.scan_mem_multiplier 设上限。

0.8.0 起支持

2优先改数据布局

过滤列选择性强时，用分区、partial index、或「先 B-tree 缩小业务范围再向量检索」的架构。不要只把 ef_search 一路调大。

3代价是真实存在的

扫描更大比例的近似索引很贵；max_scan_tuples 是上限而非目标，且不影响首次扫描。用 EXPLAIN (ANALYZE, BUFFERS) 看实际扫描量。

03 / hnswbuild.c · hnswinsert.c · hnswvacuum.c

HNSW 不是只读结构：每一步都要维护图

低精度表示缩小单节点 value，但不能消除建图、写放大与修图成本。这决定了它更偏「读多写少」。

README 的提示：图能放进 maintenance_work_mem 时构建明显更快；放不下会出现 hnsw graph no longer fits into maintenance_work_mem notice，进入 on-disk phase 逐条插入。

A和 B-tree 插入不一样

B-tree 主要维护有序页和分裂；HNSW 插入要在图上搜索、选邻居、更新多条边。低精度能降低距离计算和节点值 IO，但 ef_construction、锁、页写入、邻居更新仍是实打实的写放大。

B删除不是「移除一个节点」

NeedsUpdated() 检查邻居是否指向 deleted 元素或 level 0 邻居不满；RepairGraphElement() 重新找邻居。所以 HNSW 的 VACUUM 可能比较慢——它要修图，不是清几个 posting list。

04 / 差别的根源：HNSW 与量化影响不同瓶颈

把「严格 INT8 SQ」和 IVFFlat 也放进来看

HNSW 影响访问候选数，量化影响每个候选的表示与距离计算，IVFFlat 换的是候选生成方式（聚类分桶）。

∑
读表的关键：「索引能否空表创建」——HNSW 三类都可以（无训练步骤），IVFFlat 不适合空表训练；「距离函数」——halfvec / vector 用 L2 / IP / cosine / L1，bit 用 Hamming / Jaccard，语义完全不同，不能直接比较分数。
04 / 压缩越激进，越要靠评测和重排兜底

没有「又小又准」的免费午餐

四个位置对应四种工程选择；虚线圈代表「概念上存在、pgvector 当前不原生提供」。

用法：先把 vector 或 halfvec 作为质量基线，再评估 bit 的粗召回 + 重排是否能达到可接受的 recall@K。没有离线评测集，就无法判断「省下来的内存」值不值。
05 / 不要只看压缩比

索引大小 = 向量值 + 一堆不会消失的东西

下面这个「粗略空间框架」用于建立直觉；真实大小请用目标数据集建索引后实测。

为什么不是精确公式：tuple 对齐、页头、ItemId、TOAST/varlena、邻居 tuple、死元组与填充都会影响真实大小。

i

SET LOCAL hnsw.ef_search = 100;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM items ORDER BY embedding <=> '[...]'::vector
LIMIT 10;
COMMIT;
③ 半精度 HNSWhalfvec_cosine_ops
CREATE INDEX items_embedding_hnsw_half_idx
ON items USING hnsw
  ((embedding::halfvec(768)) halfvec_cosine_ops)
WITH (m = 16, ef_construction = 64);

BEGIN;
SET LOCAL hnsw.ef_search = 100;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM items
ORDER BY embedding::halfvec(768) <=> '[...]'::halfvec
LIMIT 10;
COMMIT;

这一页的三个要点

基线不可省没有 exact / float32 基线，就无法知道量化损失是否可接受。
表达式要匹配建的是 embedding::halfvec(768)，查询 ORDER BY 必须用同一表达式与 halfvec_cosine_ops 对应操作符。
想保留原始排序把 halfvec 仅作候选召回，再回表按原始 vector 重排。
i
SET LOCAL 把 ef_search 的作用域限制在单个事务里，避免污染其他会话。
06 / 第三条路径 + 强过滤改法

bit 索引负责便宜地召回，原始向量负责最终排序

这里的 LIMIT 100 是 top-R，不是固定最佳值；LIMIT 10 才是最终 K。R 应由 recall / latency 曲线决定。

④ 二值量化 HNSW + 原始向量重排bit_hamming_ops
CREATE INDEX items_embedding_hnsw_bit_idx
ON items USING hnsw
  ((binary_quantize(embedding)::bit(768)) bit_hamming_ops)
WITH (m = 16, ef_construction = 64);

BEGIN;
SET LOCAL hnsw.ef_search = 200;

WITH candidates AS MATERIALIZED (
    SELECT id, embedding FROM items
    ORDER BY binary_quantize(embedding)::bit(768)
             <~> binary_quantize('[...]'::vector)
    LIMIT 100                      -- top-R
)
SELECT id FROM candidates
ORDER BY embedding <=> '[...]'::vector
LIMIT 10;                         -- 最终 top-K
COMMIT;
⑤ 带强过滤：iterative scan（0.8.0+）strict_order
BEGIN;
SET LOCAL hnsw.ef_search = 100;
SET LOCAL hnsw.iterative_scan = strict_order;
SET LOCAL hnsw.max_scan_tuples = 20000;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM items WHERE category_id = 42
ORDER BY embedding <=> '[...]'::vector LIMIT 10;
COMMIT;

R扫一组 R 再定值

试 R = 50 / 100 / 200 / 500，画 recall@10、P95 / P99 延迟、shared buffers 读写与 CPU 曲线。R 太小漏召，太大回表变贵。

!
别把 LIMIT 10 当候选数。重排模式下 R 必须大于 K；只取 10 个 Hamming 近邻再重排，等于把误差锁死。
→
过滤列选择性强时，优先考虑普通 B-tree / partial index / 分区 缩小业务范围，而不是只调大 ef_search；HNSW 不会自动理解过滤条件。以上 SQL 未在实例上执行，不提供虚构的 EXPLAIN 输出。
07 / 三类角色，同一条验证闭环

没有基线，就不要谈「量化损失可接受」

把评测做成流程，而不是一次性压测：模型、维度、归一化方式一变，旧的 recall 曲线不会自动继承。

架构师

  • 把实践定义为「halfvec 或 binary_quantize 的低精度 HNSW 召回」，设计文档里不要写「pgvector 原生 INT8 SQ」。
  • 二值量化采用两阶段：低精度 top-R 召回 + 原始向量 top-K 重排，R 由曲线决定。
  • 保留 exact / float32 基线做离线 recall@K 评估。
  • 强过滤优先考虑分区、partial index 或「先过滤后检索」架构。

DBA

  • 先批量导入、后建索引（README 明确建议）。
  • 按实例内存与并发构建数设置 maintenance_work_mem，别挤爆系统内存。
  • 用 pg_stat_progress_create_index 关注 initializing / loading tuples 阶段。
  • 大量删除更新后评估 REINDEX INDEX CONCURRENTLY 再 VACUUM；用 EXPLAIN (ANALYZE, BUFFERS) 看真实 page read / hit / 回表。

业务开发者

  • 模型 / 维度 / 归一化变了，重新评估索引与量化路径。
  • halfvec 适合「想降内存但不想大改距离语义」；binary_quantize 适合「先便宜召回再精排」。
  • ORDER BY 表达式必须和索引表达式完全一致，包括 ::halfvec(768) 与对应 Hamming 操作符。
  • 不要把 LIMIT 10 当候选数；重排模式下 R > K。
08 / 先判断能不能用，再谈怎么调

读多写少 + 有评测集 + 能重排，才最容易受益

✓适合

  • RAG、推荐、相似图片 / 文本检索等读多写少 workload
  • 向量维度高、HNSW vector 工作集太大，想用 halfvec / bit 降低索引值大小
  • 能接受近似召回，且有离线评测集衡量 recall@K
  • 可以用 top-R + 原始向量重排保障最终排序质量
  • 以初始批量构建为主，增量插入量可控

✗不适合

  • 金融风控、审计等必须精确 top-K、不能接受近似漏召
  • 高频更新 / 删除的大表，且没有重建窗口
  • 强过滤后只剩极少行，却指望 HNSW 自动返回足够结果
  • 没有原始向量可重排，却用二值量化做最终排序
  • 把其他引擎的 INT8 SQ benchmark 当成 pgvector 的容量规划依据

!八个常见坑

1 · 把 binary_quantize 当 INT8 SQ它按维度符号转 bit，没有 scale / zero point / min/max。
2 · 二值量化不重排Hamming ≠ 原始 cosine / L2 排序。
3 · 只看压缩比不看图边索引还含 element / neighbor tuple、TID、页开销、死元组。
4 · 过滤导致返回不足过滤在扫描后；用 iterative scan 或改数据布局。
5 · maintenance_work_mem 失当太小早早进入 on-disk phase；太大挤爆系统内存。
6 · 表达式不一致索引表达式与查询表达式必须逐字匹配，索引才可能被用到。
7 · 不治理索引膨胀删除涉及 heap TID 清理和图修复，观察大小 / 质量 / VACUUM 时间。
8 · 把 ef_search 当免费开关召回 ↑ 的同时延迟、内存、候选扩展一起 ↑。
FINAL / 一句话带走

HNSW 管「走哪些点」，量化管「每个点多贵」

在 pgvector 里，能落地的不是 INT8 SQ，而是 halfvec 半精度 HNSW 与 binary_quantize 表达式索引 + 原始向量重排。

结论 1

两个正交问题

HNSW 减小访问候选数 N；低精度减小每候选字节数。误差也分「走图近似」与「表示误差」两层。

结论 2

边界要写清楚

pgvector 0.8.7 / 0.9.0 unreleased 均无 INT8 SQ HNSW 类型；二手「原生量化」说法不可信。

结论 3

两阶段才稳

低精度索引取 top-R，原始向量精确距离重排取 top-K；R 由 recall / latency 曲线决定。

结论 4

运维不能省

图边、死 TID、VACUUM 修图、REINDEX 窗口都在；读多写少 + 批量构建最受益。

扩展问题（留给你的场景）

  • 最终必须用原始 cosine 排序时，top-R 如何自动调参？
  • halfvec 与 binary_quantize 的误差各来自哪里？语义文本与图像 hash 该选谁？
  • 若要给 pgvector 增加 INT8 SQ HNSW，需要新增哪些类型、opclass、距离函数与升级 SQL？
  • 强过滤下，该让 HNSW 扫更多候选，还是先用分区 / partial index 缩小向量空间？
  • Embedding 模型升级后，如何设计灰度重建与 recall 回归测试？
