主线只有一条：「少看候选」与「别漏掉真近邻」之间的权衡，贯穿全部章节。
精确 KNN 的基本代价
costexact ≈ N × distance_cost(d)
N = 行数，d = 向量维度。数据量翻倍，距离计算也大体翻倍。
现实规模

1000 万条 768 维 embedding，一次查询就要做 1000 万次距离计算。精确，但贵。

高维空间没有天然一维全序

B-tree 靠有序键定位范围；而高维向量不存在一个全局一维顺序能同时保持所有邻近关系。KD-tree、LSH、图索引、倒排文件都是 ANN 的不同答案。

数据库不只在算距离

SQL 解析、事务可见性、过滤条件、排序、连接和并发，都在同一份资源上竞争。即便有 SIMD 与并行，成本依旧随 N 线性增长。

由此得到的结论

小数据集上，全量扫描是最好的基线；进入在线高并发后，需要的是「少看候选」的近似方法，同时接受召回率不再是 100%。

ANN 共同要回答的问题：能不能少看一点，同时尽量别漏掉真近邻？　全量扫描是好基线，不是在线高并发的答案。

⑤ 精排

改写后的代价 ≈ lists 个中心点距离 + 被选中 probes 个 list 内的候选距离。收益来自候选集缩小，不是把距离计算变成零。

一句话定义：pgvector 的 ivfflat 是一个 PostgreSQL index access method，用 k-means 训练的中心点把向量划成多个倒排 list，查询时只扫描离 query 最近的若干 list，并在 list 内保存的原始向量上计算真实距离。
IVF　基础机制

用 K 个中心点把空间切成 Voronoi cells，每条向量归入最近中心点，形成一个倒排 list。查询只访问 query 最近的 T 个中心点对应的 list。

K centroidsK inverted lists少看候选
IVFFlat　pgvector 采用

list 内保存可直接计算距离的原始向量值，不是 PQ code、二进制签名或残差压缩码。候选距离是真实距离。

候选距离 = 真实距离（无量化误差）
IVF-PQ / IVFADC　另一条线

list 内保存 PQ code 或残差 PQ code，候选距离是近似距离；通常更省内存，但多一层量化误差（PQ 论文：IVF 负责少看，PQ 负责少存）。

候选距离 ≈ 近似距离（有量化误差）
为什么 pgvector 选 Flat：实现简单、list 内排序距离准确、可复用 PostgreSQL 索引接口与 WAL / VACUUM 机制；代价是索引体积比 IVF-PQ 大。

必须是按距离排序的 KNN 形态
SELECT id, embedding <-> '[3,1,2]' AS distance
FROM items
ORDER BY embedding <-> '[3,1,2]'
LIMIT 10;
✗ 没有 ORDER BY 距离，索引不生效

ivfflatcostestimate() 对没有 ORDER BY 距离算子的路径直接给无穷大成本；ivfflatgettuple() 也会在缺少 order 信息时抛错。

所以不要理解成「给向量列建了索引后，任何 WHERE 都能用」——它服务的是近邻排序，不是通用谓词加速。

距离算子：<-> L2　·　<#> 负内积　·　<=> cosine　·　<+> L1　·　<~> Hamming　·　<%> Jaccard
建索引时　CREATE INDEX
lists

中心点 / list 数量。源码默认 100，范围 1 – 32768；README 示例均显式指定。越大单 list 越小，但训练与选 list 成本更高。

center / centroid

k-means 训练出的 list 中心，保存在 list page 的 IvfflatListData 中，查询时用于粗筛。

entry page

某个 list 下保存 IndexTuple 的页面链，每个 tuple 带向量值和 heap TID。

查询时　GUC / SET
ivfflat.probes

初始扫描多少个最近 list，默认 1，上限受 list 数限制。设为 list 总数可得到精确近邻，但 planner 可能不再选索引。

ivfflat.max_probes

迭代扫描时最多扫多少个 list；若小于 probes，源码至少使用 probes。

ivfflat.iterative_scan 0.8.0+

三态：off（默认，可能少于 LIMIT）、strict_order（补足且严格按距离排序）、relaxed_order（补足但次序可略乱、更快）。

DBA 习惯：用 SET LOCAL ivfflat.probes = … 给单次查询调参，避免会话级参数影响连接池里的其他请求。

采样不足 = 质量风险

源码目标样本数是 lists × 50，且最少 10000 个样本。样本不足 lists 时会发 NOTICE，提示索引建在少量数据上、有低召回风险 —— 与 README「先有数据再建索引」一致。

举例：lists = 100 时目标样本 5000，但仍取下限 10000；空表上训练出的中心点几乎没有代表性。
并行与内存

k-means 之后可复制 centers，由 worker 并行扫表、分配、排序。若 k-means 所需内存超过 maintenance_work_mem，源码直接报错 —— 这个参数不只影响排序，也限制 k-means。

实践含义：大 lists + 高维样本的建索引任务，要提前评估训练内存，而不是等它报错。
源码锚点：src/ivfbuild.c · src/ivfkmeans.c；进度百分比列用 tuples_done / tuples_total（README）
k-means++ 初始化

让初始中心点尽量分散，避免随机初始化把多个中心堆在同一片区域。

Elkan k-means 迭代

用三角不等式跳过不必要的距离计算；最多迭代 500 次。

归一化处理

cosine / inner product operator class 会对样本和中心点做归一化。

现象一：maintenance_work_mem 不够时建索引直接报错，不是「变慢」而是失败。
现象二：cosine / 内积路径会跳过无法归一化的零向量；业务侧不要把零向量当可检索 embedding。

PostgreSQL 执行层

普通 SQL 过滤、MVCC 可见性检查、heap fetch、最终 LIMIT 行数，都由执行层共同决定。向量索引不负责非向量谓词。

MVCC snapshotWHERELIMIT k
两个源码限制

① ivfflatgettuple() 要求 MVCC snapshot：候选要放进 tuplesort，不能长期 pin 页面。
② xs_recheck / xs_recheckorderby 置为 false，表示候选距离已按索引内向量值算过；但不等于整个 top-k 精确，未扫描的 list 里可能有更近向量。

记忆点：索引保证「已扫描候选的距离算准了」，不保证「全库最近的点都被扫到了」。
过滤后置的后果

如果过滤没有参与候选生成，只在候选返回后处理，就可能出现「LIMIT 10 但过滤后不够 10 条」。这正是第二篇论文讨论的向量数据库工程硬问题。

T1 ✓T2 ✗T3 ✗T4 ✓T5 ✗ T6 ✗T7 ✗T8 ✓T9 ✗T10 ✗
② 执行层再做 MVCC 与 WHERE 过滤，只剩满足 category_id = 1 的 3 条：
T1 ✓T4 ✓T8 ✓… 后面没人补位
结果 = 3 行 < LIMIT 10　·　过滤选择性越低，缺口越大。
四条可行解法
① 提高 probes

扫更多 list，候选池更大；代价是延迟上升。

② 迭代扫描（0.8.0+）

iterative_scan = strict_order / relaxed_order，不足时自动继续扫，直到满足 LIMIT 或达到 max_probes。

③ 普通索引 / partial index

过滤字段先建 B-tree，或建 WHERE category_id = 1 的局部 ANN 索引，让候选空间先按业务边界缩小。

④ 分区

多租户、地域、分类等强过滤维度按 LIST 分区，每个分区单独建索引。

README 经验：若过滤条件只匹配少数行，先用过滤字段的普通索引做精确搜索往往比近似索引更合适。

触发重训的信号：批量导入完成、embedding 模型升级、数据分布重排、某些 list 明显变成长链。
ivfflatcostestimate() 的核心估算
ratio = min( probes / lists, 1 )
startup_cost ≈ index_total_cost × ratio

probes / lists 是优化器理解 IVFFlat 扫描规模的关键比例。probes 越接近 lists，越像全索引扫描 —— 此时「少扫」的成本优势消失。

README 提醒：把 probes 设为 list 总数可得到精确近邻，但 planner 可能不会再选择 IVFFlat 索引。
lists = 100 时，不同 probes 的扫描比例

示意比例按公式计算；不是实测性能数据。probes = lists 时 planner 常倾向顺序扫描。

核心差异不是「哪个永远更好」，而是误差来自哪里。
IVFFlat

误差 = 粗分桶后没扫描的 list 里存在更近向量。probes 越小，漏扫的 list 越多。

调参：lists / probes
HNSW

误差 = 图搜索候选扩展不充分，导航提前停在局部区域。ef_search 决定候选宽度。

调参：ef_search
IVF-PQ

误差 = 粗分桶漏扫 叠加 PQ 量化误差。更省内存，但距离本身也是近似的。

-- 观察建索引阶段（IVFFlat）
SELECT phase,
  round(100.0 * tuples_done
    / nullif(tuples_total,0),1) AS pct
FROM pg_stat_progress_create_index;

面向数据库架构师

· 把 IVFFlat 放在可接受近似召回的候选生成层，不要放在强精确排序或强一致业务规则层。

· 过滤字段先建普通 PG 索引，或做分区 / 局部索引设计。

· 多租户、分类、地域等强过滤，优先 partial index 或 partition。

· 保留精确搜索或高精度重排链路，用于 recall 评估、线上抽检和关键请求兜底。

面向 DBA

· 建索引前确认表中已有足够样本；样本数少于 lists 的 NOTICE 应视作质量风险。

· lists 从 README 经验值起步，但用业务 query 集调参。

· 用 SET LOCAL 给单次查询调参，避免污染连接池。

· 监控索引大小、VACUUM 时间、P99 与 recall；模型升级或批量导入后考虑 REINDEX CONCURRENTLY。

面向业务开发者

· SQL 必须写成 ORDER BY embedding <op> query LIMIT k。

· 不要把 ANN 距离当成跨模型、跨索引参数稳定可比的业务分数。

· 过滤越强，越要关注 probes 与迭代扫描，否则返回行数可能少于预期。

· RAG 场景：先取更大的 R，重排后再给 top-k。

RAG 推荐链路
ANN top-R 初筛› 精确向量 / reranker 重排› top-k 最终答案
R 随 recall 与 reranker 成本调整
Q1
必须精确 top-k？

是 → 用精确扫描，不要近似索引。

Q2
数据量很小？

是 → 顺序扫描已经是好答案。

Q3
内存够 HNSW 吗？

够且更看重召回/延迟 → HNSW；预算紧 → IVFFlat。

Q4
分布稳定吗？

漂移快或强过滤无法前置 → 先治理数据边界，再谈索引。

✓ 适合

· 表里已有一定规模的稳定向量数据。

· 查询以 top-k 近邻为主，业务接受近似召回。

· 写入不是极端高频，或允许周期性重建索引。

· 内存预算不适合 HNSW，但希望比精确扫描更快。

· RAG 初筛、推荐候选生成、相似图片 / 文本召回、去重候选生成。

✗ 不适合

· 必须返回精确 top-k，不能接受任何漏召回。

· 数据量很小，精确扫描已经足够快。

· 数据分布快速漂移，中心点需要频繁重训。

· 过滤极强且无法通过分区 / partial index / 普通索引先缩小范围。

· 高频 update / delete 且要求聚类持续最优；或需要 PQ 级极致压缩。

PITFALL 01

空表 / 小表先建索引

有训练步骤。数据太少中心点不可靠，后续插入只追加、不自动重训。

PITFALL 02

lists 越大越好

单 list 更小，但中心点更多、训练更重、查询要遍历更多 center，小数据集还会样本不足。

PITFALL 03

只调 lists，不调 probes

list 变多而 probes 仍为 1，查询扫描比例下降，召回可能反而变差。

PITFALL 04

probes = lists 当默认

接近全索引扫描，失去 ANN 成本优势，planner 也可能不再使用索引。

PITFALL 05

忽略过滤后置

WHERE 与 ORDER BY 同时出现时，ANN 先返回的候选不一定满足谓词，返回行数可能不足。

PITFALL 06

误以为 VACUUM 会优化聚类

VACUUM 删死 tuple、更新可插入页指针，但不重算中心点、不移动存活向量、不合并 list。

PITFALL 07

cosine 零向量

cosine 路径需要归一化，源码跳过无法归一化的零向量；业务侧应避免把零向量当 embedding。

PITFALL 08

没有精确基线

ANN 调参不能只看「快了多少」，还要看「漏了多少」。精确扫描或高精度重排是必要基线。

共同点：把 IVFFlat 当成「普通索引」来用。它是带训练、带召回代价的候选生成器。
六个扩展问题

① 过滤选择性只有 1%，该提高 probes，还是建 partial index / partition？如何用 EXPLAIN 与 recall@k 判断？

② embedding 模型从 v1 升到 v2，旧索引还能服务吗？如何设计双写、双索引和回滚？

③ 为什么 IVF-PQ 更省内存，但 pgvector 选择 IVFFlat 更符合 PostgreSQL 扩展的实现边界？

④ 某些 list 明显更长，说明分布有什么问题？调 lists、重训，还是先做业务分区？

⑤ RAG 里 LIMIT k 应等于最终返回条数，还是先取更大的 R 后重排？R 如何随 recall 与 reranker 成本调整？

⑥ probes / lists 很高时，为什么 planner 可能倾向顺序扫描？和 costestimate 的 ratio 模型有什么关系？

TAKEAWAYS　/　数据库筑基课 · 索引结构
IVFFlat 不是魔法索引，
也不是无损索引。
01 / 结构

k-means 中心点 → 倒排 list → entry page 链；list 内存原始向量，算真实距离。

02 / 权衡

probes / lists 决定少看多少；少看的代价是可能漏掉未扫描 list 里的真近邻。

03 / 边界

过滤后置、插入不重训、参数无通解 —— 用精确基线做 recall@k 验证。
