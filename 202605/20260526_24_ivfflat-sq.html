01 背景 · 事实核对

边界澄清：pgvector 里真正有什么

本地 README、SQL schema 与 ivf* 源码交叉核对后的结论，不含推测。

✓ 可直接落地

  • ivfflat access method：IVF 粗分桶的索引访问方法
  • vector / halfvec / bit 三类 IVFFlat operator class
  • binary_quantize() 表达式索引，用于二值量化召回
  • 查询后用原始向量重排，降低低精度带来的排序误差
  • iterative scan（0.8.0 起）缓解过滤后候选不足

✗ 未发现

  • ivfflat_sq_ops / ivfsq / INT8 SQ 独立访问方法
  • per-dimension scale / zero point 训练器
  • 独立于 ivfflatbuild() 的 SQ range 训练步骤
  • 把 halfvec 当作 INT8 SQ：它是 16 bit 浮点，不训练 range
  • 把 binary_quantize() 当作 SQ8：它是 1 bit 符号量化

02 它是什么

一句话定义，以及六种容易混淆的形态

IVFFlat-SQ = 用 IVF 粗分桶限制候选范围，用标量量化或低精度表示降低倒排桶内 payload 成本。

形态结构含义pgvector 原生支持
ivfflatIVF 粗分桶，list 内保存可直接算距离的 payload是
ivfflat + halfvecIVF 粗分桶，list 内保存 half precision payload是
ivfflat + bitIVF 粗分桶，list 内保存 bit payload，用 Hamming 距离是
ivfflat + binary_quantize(expr)表达式索引，把原向量转 bit 后进入 IVFFlat语法可构造，需 SQL 表达式匹配
Faiss IVF,SQ8IVF 粗分桶，list 内保存 SQ8 codeFaiss 支持，pgvector 不等价
严格 INT8 ivfflat_sq_ops类型 / opclass / 距离函数 / WAL / VACUUM 全链路实现当前未发现
SCHEMA 层
ivfflat 是 PostgreSQL index access method；vector_l2_ops / vector_ip_ops / vector_cosine_ops / halfvec_l2_ops / bit_hamming_ops 把类型与距离函数挂上去。
源码层
src/ivfutils.c 的 IvfflatTypeInfo 封装最大维度、归一化函数、item size、center 更新与求和函数。

03 3.1 严格参照

严格 IVF-SQ 长什么样：Faiss 参照结构

IndexIVFScalarQuantizer 继承 IndexIVF，内部持有 ScalarQuantizer sq，code_size 由 qtype 决定。

code_size 公式（set_derived_sizes）

QT_8bit　code_size = d
QT_6bit　code_size = ceil(d × 6 / 8)
QT_4bit　code_size = ceil(d / 2)
QT_fp16　code_size = d × 2
QT_0bit　 code_size = 0

五个不可省略的环节

  • 粗量化器训练：决定 list
  • SQ 参数训练：决定每维如何编码
  • 编码写入倒排 list：存 code 而非 float
  • 查询扫 code：解码或近似距离
  • 必要时 reconstruct / rerank

训练边界

需要训练 range：QT_8bit / QT_6bit / QT_4bit

不需要训练：QT_fp16 / QT_8bit_direct

encode_vectors() 默认先算 residual 再编码残差。

03 3.3 构建 · 可播放

构建：pgvector 只训练 IVF 中心

ivfflatbuild() 主路径五步；点下方「▶ 播放流程」逐步高亮。

ComputeCenters() 的三个关键参数

  • 目标样本数 = lists × 50
  • 最少 10000 个样本
  • 样本少于 lists 会 NOTICE：索引在少量数据上创建，会导致低召回

k-means 实现（src/ivfkmeans.c）

  • k-means++ 初始化 + Elkan k-means
  • 最多 500 次迭代
  • cosine / IP 路径对样本与中心归一化
  • 零向量跳过或拒绝，避免中心失真

为什么这件事重要

严格 IVF-SQ 有第二个训练步骤（SQ range / scale 或编码参数）。pgvector 当前没有这个步骤，因此「低精度」全部来自具体 payload 类型或表达式。

03 3.4 查询 · 可播放

查询：probes 控召回，payload 控桶内成本

src/ivfscan.c 五步；IVF 误差来自未扫描 list，低精度误差来自 payload 本身。

旋钮一：lists / probes

lists 决定桶数，probes 决定每次看多少桶。桶多但 probes 太小，召回会掉。

probes / lists 越大，召回通常越好，扫描也越贵。

旋钮二：payload 精度

误差由 halfvec 精度、bit 距离语义 或外部 SQ code 近似造成。

三者误差形态不同，不能用同一套调参方式。

旋钮三：R / K 比例

扩大 top-R 再用原始向量精排，可恢复被量化扰乱的最终 top-K。

代价是更多回表与精确距离计算。

05 效果如何

不脱离数据集谈性能数字：先看因素，再定指标

IVFFlat-SQ 类设计的收益至少由七个因素共同决定；验收要有一组可复现的指标。

七个决定收益的因素

  • 维度：越高，payload 缩小越可能降低内存带宽压力
  • list 负载均衡：center 质量差会让部分 list 过长
  • lists 与 probes：probes/lists 越大召回越好、扫描越贵
  • 低精度误差：halfvec 温和；binary_quantize 更激进；SQ8 介于两者但 pgvector 无原生实现
  • 过滤条件：后置过滤放大「候选不足」
  • R / K 比例：R 越大越可能恢复 top-K，回表越多
  • 数据漂移：新增数据只分配到旧中心，不触发重训

可操作的评估指标集

recall@K　　　= approximate_topK 与 exact_topK 的交集比例
p95_latency　 = 业务可接受延迟
index_size　　= pg_relation_size(index)
buffer_reads　= EXPLAIN (ANALYZE, BUFFERS)
rerank_rows　 = top-R 回表数量
write_cost　　= INSERT/UPDATE 延迟与 WAL
maintenance　 = VACUUM / REINDEX 周期
先跑 exact top-K 建立精确基线，再比较 approximate top-K；每个数据集、每个 embedding 模型都要单独测。

SQL DEMO：从精确基线到低精度表达式索引

以下 SQL 按 pgvector README 与 sql/vector.sql 支持的函数 / opclass 编写；本文未启动数据库、未执行，因此不提供虚构 EXPLAIN 输出。

6.1 精确基线

建表 + 10 万条 3 维向量 + exact top-K
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE items (
  id bigserial PRIMARY KEY,
  category_id int NOT NULL,
  embedding vector(3) NOT NULL
);

INSERT INTO items (category_id, embedding)
SELECT (i % 10),
  ARRAY[random(), random(), random()]::vector
FROM generate_series(1, 100000) AS s(i);

-- 精确 top-K，用于评估召回
SELECT id FROM items
ORDER BY embedding <-> '[0.2,0.4,0.6]'::vector
LIMIT 10;

6.2 IVFFlat + vector

lists = 100，probes = 10，EXPLAIN 观察 buffers
CREATE INDEX items_embedding_ivfflat_l2
ON items USING ivfflat
  (embedding vector_l2_ops) WITH (lists = 100);

SET ivfflat.probes = 10;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, embedding <-> '[0.2,0.4,0.6]'::vector AS distance
FROM items
ORDER BY embedding <-> '[0.2,0.4,0.6]'::vector
LIMIT 10;

6.3 IVFFlat + halfvec 表达式索引

查询表达式必须与索引定义一致
CREATE INDEX items_embedding_half_ivfflat_l2
ON items USING ivfflat
  ((embedding::halfvec(3)) halfvec_l2_ops)
WITH (lists = 100);

SELECT id FROM items
ORDER BY embedding::halfvec(3)
  <-> '[0.2,0.4,0.6]'::halfvec(3)
LIMIT 20;

06 实操 DEMO · 2/2

两阶段召回 + 原始向量重排，以及召回率对照

binary_quantize() 的 Hamming top-K 不能直接当最终语义相似 top-K；先取 top-R，再回到原始向量精排。

6.4 二值量化召回 + 原始向量重排

stage 1 取 100 条候选 → stage 2 用 cosine 距离选 top-10
CREATE INDEX items_embedding_bin_ivfflat_hamming
ON items USING ivfflat
  ((binary_quantize(embedding)::bit(3)) bit_hamming_ops)
WITH (lists = 100);

WITH candidates AS MATERIALIZED (
  SELECT id, embedding FROM items
  ORDER BY binary_quantize(embedding)::bit(3)
    <~> binary_quantize('[0.2,-0.4,0.6]'::vector)::bit(3)
  LIMIT 100
)
SELECT id,
  embedding <=> '[0.2,-0.4,0.6]'::vector AS cosine_distance
FROM candidates
ORDER BY embedding <=> '[0.2,-0.4,0.6]'::vector
LIMIT 10;

6.5 召回率对照查询

exact 与 approx 的 id 交集 / 10
WITH exact AS MATERIALIZED (
  SELECT id FROM items
  ORDER BY embedding
    <-> '[0.2,0.4,0.6]'::vector
  LIMIT 10
),
approx AS MATERIALIZED (
  SELECT id FROM items
  ORDER BY embedding::halfvec(3)
    <-> '[0.2,0.4,0.6]'::halfvec(3)
  LIMIT 10
)
SELECT count(*)::float / 10 AS recall_at_10
FROM exact JOIN approx USING (id);
注意：示例维度为 3，仅用于演示语法；真实业务维度常见 768 / 1536。换模型、维度、归一化方式后必须重新测召回与参数。

07 最佳实践

三类角色，各自该守住什么

架构师管边界、DBA 管可观测与维护、业务开发者管 SQL 形态与召回验证。

数据库架构师

  • 把验收拆成两层：lists/probes 的候选召回 与 低精度 payload 的排序误差，不要只看总体延迟。
  • 设计文档写清真实实现：ivfflat + halfvec / bit、binary_quantize() 表达式索引，而不是「pgvector 原生 SQ8」。
  • 强过滤 workload 优先用分区、局部索引、普通字段索引与数据布局尽早缩小候选。
  • 分布漂移明显的业务，设计 REINDEX CONCURRENTLY 或滚动重建窗口。

DBA

  • 建 IVFFlat 前先导入足够数据；样本少于 lists 有低召回风险。
  • 记录 pg_relation_size()、pg_stat_user_indexes、EXPLAIN (ANALYZE, BUFFERS)、召回率与重排行数。
  • maintenance_work_mem 影响 k-means 与构建排序，建大索引前评估内存。
  • 用 ivfflat.iterative_scan = relaxed_order 与 max_probes 缓解过滤后结果不足，同时观察延迟。
  • VACUUM 只清死 TID，不重训 center。

业务开发者

  • SQL 必须写成 ORDER BY 向量距离 LIMIT K，否则 IVFFlat 没有 KNN 语义。
  • 表达式索引要保持查询表达式一致，例如 embedding::halfvec(768) 或 binary_quantize(embedding)::bit(768)。
  • 不要把 binary_quantize() 的 Hamming top-K 直接当最终语义相似 top-K；先取 top-R 再重排。
  • 每次换 embedding 模型、维度、归一化方式，都要重新测召回与参数。

08 场景判断

什么时候该用，什么时候别用

判断依据是「业务约束」，不是「哪个索引名字听起来更先进」。

✓ 适合

01　数据已有一定规模，能先 bulk load 再建 IVFFlat
02　在线查询以近邻 top-K 为主，能接受 ANN 召回误差
03　内存 / 缓存压力明显，希望用 halfvec 或 bit 表达式降低索引 payload
04　RAG、推荐、去重等允许「两阶段召回 + 精排」
05　有能力用业务验证集持续记录 recall@K

✗ 不适合

01　必须 100% 精确 top-K，不接受任何低精度误差
02　高频更新、分布持续漂移，却没有重建窗口
03　过滤条件很强，但过滤字段没参与物理分区或普通索引设计
04　希望直接获得严格 SQ8 / 4bit 原生 pgvector 索引能力
05　只看 benchmark 延迟，不愿维护召回率与重排指标
共同前提：无论落在哪一侧，都要先跑 exact top-K 建立精确基线；没有基线，「召回率」只是一个无法验证的说法。

09 常见坑

九个最常见的坑

大部分事故不是索引选错，而是把「能力边界」和「误差来源」记混了。

PITFALL 01
当成已存在的索引类型
README / SQL / 源码未发现独立 ivfflat_sq_ops；能用的是现有类型、opclass 和表达式索引。
PITFALL 02
把 halfvec 当 INT8 SQ
halfvec 是 16 bit 浮点，不训练 per-dimension range；严格 SQ8 通常需要 range / scale。
PITFALL 03
把 binary_quantize() 当 SQ8
它是 1 bit 符号量化，空间小但排序误差更大，通常必须重排。
PITFALL 04
只调 lists，不调 probes
lists 决定桶数，probes 决定每次看多少桶；桶多但 probes 太小，召回会掉。
PITFALL 05
空表 / 小表先建索引
中心点训练质量差，README 与源码都会提示低召回风险。
PITFALL 06
忽略表达式匹配
embedding::halfvec(768) 与 embedding 不是同一个索引表达式，查询写法要匹配定义。
PITFALL 07
过滤后置导致 LIMIT 不足
向量索引先返回近邻，SQL 过滤后可能不够 K 条；需普通索引、分区、partial index 或 iterative scan 协同。
PITFALL 08
用 VACUUM 期待重训中心
VACUUM 清 dead TID，不重训 k-means center，也不重新分配旧 tuple。
PITFALL 09
没有精确基线就谈召回
每个数据集都要先跑 exact top-K，再比较 approximate top-K。

END 小结

三句话带走

从成本维度出发，落到可写出来的 SQL 与可复现的指标。

01
成本有两个独立维度
IVFFlat 减少候选数，SQ / 低精度表示减少每条候选的 payload；两者误差来源不同，必须分层验收。
02
先说清边界，再谈结构
上游 pgvector 能落地的是 ivfflat + vector / halfvec / bit 与 binary_quantize() 表达式索引；严格 INT8 SQ 是结构化讨论题，不是现成能力。
03
低精度负责召回，原始向量负责排序
top-R 召回 + 原始向量重排成 top-K；用 exact top-K 基线持续记录 recall@K、延迟、index size 与重排行数。
