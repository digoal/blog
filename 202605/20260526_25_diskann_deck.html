01 · WHY

业务想把所有东西放进同一个 PostgreSQL

embedding、原始业务行、权限条件、事务可见性和 SQL 查询放在一处；但向量维度高、数据量大
1 亿条 × 768 维 × float4
286 GiB
100,000,000 × 768 × 4 B ≈ 307.2 GB
这只算原始向量本身，还没有算：表行、索引边、WAL、缓存、VACUUM、副本。
内存图索引放不下全表扫描太慢
结论：规模上来之后，问题不是「算得快不快」，而是「能不能少算、少读、少占内存」。
01 · WHY

五类做法，各自卡在不同的地方

DiskANN 论文提出大规模 ANN 必须同时满足：高召回、低延迟、高密度（单机能装多少点）
做法优点问题
精确全表扫描结果准确、逻辑简单大数据低延迟场景不可接受
B-tree / Hash适合一维或等值条件高维距离没有天然全序键
IVF / IVFFlat聚类分桶后少扫一部分分桶边界漏召回，需调探针数（ivfflat.probes / nprobe）
HNSW内存图搜索快、召回高图与向量常驻内存成本高；更新治理复杂
DiskANN / Vamana面向 SSD 与大规模高召回，减少随机 I/O构建、压缩、重排、删除维护都有代价
PostgreSQL 还多一层：索引不能只返回向量 id，还要返回 Heap TID；执行器要处理 MVCC；CREATE INDEX / INSERT / VACUUM、opclass、GUC、planner cost 都要接上。
论文的三目标（同时满足）
高召回
近似但不能明显漏掉真正近邻
低延迟
SSD 随机读虽快，几百次仍不可接受；要压到少量 round trip
高密度
单机装下十亿级点，主要数据驻留 SSD
SSD 上真正的瓶颈是随机读次数，不是浮点运算次数。
pgvectorscale 的价值点：把 DiskANN / Vamana 类图索引落成一个真正的 PostgreSQL index access method。
02 · IDEA

DiskANN 不是「查找」，而是三次问题改写

用可导航图生成少量候选，再用压缩或完整向量距离排序

① 少看候选

从一个入口点出发，沿越来越接近 query 的边走；用候选宽度 L 控制看多少节点，而不是扫全表。

② 少占内存

把大部分图和向量放在 SSD / PostgreSQL 索引页，内存只放必要结构、缓存与压缩表示（PQ 或 SBQ）。

③ 可调准确率

用候选宽度、出边数、量化、重排在召回率、延迟、构建时间、空间成本之间调平衡。

代价也要讲清楚：它是近似索引，不保证精确 top-k；图边占空间；压缩引入距离误差；删除不是「立刻重建全图」。
关键洞察：当存储从内存换成 SSD，优化目标就从「少算距离」变成「少等磁盘」。
02 · THEORY

原始 DiskANN：Vamana 图 + SSD + PQ 缓存 + 全精度重排

NeurIPS 2019，Subramanya 等；目标是在一台 64GB RAM + 廉价 SSD 的工作站上索引十亿级点

Vamana 建图两遍

初始随机图 → 对每个点 GreedySearch 得候选 V → RobustPrune 保留 ≤ R 条边 → 加回边；论文常用 第一遍 α=1、第二遍 α=1.2。

为什么单层图

分层结构会增加 SSD 读取跳数；用 α>1 保留长边来替代「上层高速公路」，把跳数压下来。

构建也要能装下

十亿点一次性构建峰值内存很大；论文用重叠分片分别建图再合并边，在有限内存下完成。

注意：论文里的压缩是 PQ；后面会看到，PostgreSQL 侧的两个产品形态并不照抄这一套。
02 · BOUNDARY

都叫 DiskANN，侧重点完全不同

算法思想 / Azure 托管扩展 / PostgreSQL 源码实现，必须分开讲，否则参数与能力会张冠李戴

① 原始论文系统

NeurIPS 2019单机 SSD
  • 重点：SSD-resident ANN 系统设计
  • Vamana 图 + PQ 码常驻内存 + 全精度向量在 SSD
  • beam search 把随机读压到少量 round trip
  • FreshDiskANN 另讲实时插删与后台 StreamingMerge
  • 不是 PostgreSQL 索引访问方法
关键词：R / L / alpha / beam width / PQ / rerank

② Azure pg_diskann

托管扩展显式 PQ 参数
  • 重点：Azure Database for PostgreSQL 里 USING diskann
  • 构建：max_neighbors(默认 32)、l_value_ib(默认 50)、product_quantized
  • PQ：pq_param_num_chunks（建议原始维度 1/3）、pq_param_training_samples
  • 查询：diskann.l_value_is(默认 100)、diskann.iterative_search（relaxed / strict / off）
  • 文档提醒：版本/元数据升级可能要求 REINDEX
关键词：PQ chunks / iterative_search / 托管运维

③ pgvectorscale

Rust / PGRXindex AM
  • 重点：PostgreSQL AM 与 SBQ / labels / scan / vacuum 的结合
  • 默认 storage_layout = memory_optimized → SBQ
  • 构建：num_neighbors(50)、search_list_size(100)、max_alpha(1.2)
  • 查询：diskann.query_search_list_size(100)、diskann.query_rescore(50)
  • smallint[] labels 可进入图搜索；另有 plain 布局
关键词：MetaPage / Heap TID / TSVResponseIterator
最容易记错的一点：SBQ ≠ PQ。 pgvectorscale 的 memory_optimized 用 Statistical Binary Quantization（按维度统计均值/方差做位量化）；原始论文与 Azure 文档里的压缩是 Product Quantization。三者参数名、能力边界、删除维护都不一样。
本讲后续：以 pgvectorscale 源码实现为主，论文与 Azure 只作为算法来源和对照。
02 · GLOSSARY

先把 8 个术语统一，后面才不会混

左边是论文符号，右边是 pgvectorscale 里对应的参数或实现

ANNS

Approximate Nearest Neighbor Search。返回近似近邻，不保证精确 top-k，需要 recall 评估。

基础概念

Vamana

DiskANN 论文的图构建算法：GreedySearch 生成候选，RobustPrune 控制度数与边的方向多样性。

图算法

R / num_neighbors

每个节点最多保存多少出边。pgvectorscale 默认 num_neighbors = 50。

构建参数

L / search_list_size

候选宽度。构建期 search_list_size = 100；查询期 GUC diskann.query_search_list_size = 100。

构建 + 查询

α / max_alpha

RobustPrune 的剪枝松紧度。pgvectorscale 默认 max_alpha = 1.2；α 越大越容易保留长边。

剪枝强度

SBQ

Statistical Binary Quantization。按维度训练均值/可选方差，把每维压成 1 或多 bit；默认布局。

压缩

rescore / rerank

先用索引里的近似表示找候选，再读 Heap 完整向量算精确距离并重排；由 query_rescore 控制数量。

排序质量

label filtering

smallint[] labels 列随索引一起存储，用 && overlap 条件参与图搜索，而非普通 WHERE 后过滤。

过滤
源码入口：access_method/mod.rs 注册 diskann AM，把 PostgreSQL 回调连到 build / scan / vacuum / cost / options，并定义 vector_cosine_ops、vector_l2_ops、vector_ip_ops 与 smallint[] label opclass。
一句话定义：DiskANN 索引 = 用可导航邻接图生成少量候选、再用压缩或完整向量距离排序的近似 KNN 索引结构。

03 · ALGORITHM

GreedySearch 不是「找 k 个」，而是维护一个候选宽度

从 start node 出发，维护候选集合 L 与已访问集合 V，沿边逐步逼近 query

为什么这样设计

  • 少看候选：只评估最接近 query 的一小片图，避免全表 O(N·d)。
  • 可控成本：候选宽度 L 直接对应访问的节点数，是延迟的主旋钮。
  • 可流式返回：候选可以边生成边交给执行器，不必等全图搜完。
  • 召回风险：L 太小或图连通性差，容易困在局部最优而漏掉真近邻。
论文里的 beam search 会把每轮 W 个候选并行从 SSD 取回，用少量 round trip 换取高吞吐；W 过大则浪费 I/O 带宽。
下一页可以亲手调 L，看候选宽度如何改变搜索路径。
记住：K 是结果条数，L 是搜索预算；把两者混为一谈，是调参时最常见的概念错误。

03 · ALGORITHM

建图不是「每个点连最近 R 个点」这么简单

候选生成解决「看哪些点」，RobustPrune 解决「留下哪些边」

参数映射

search_list_size → 候选宽度；num_neighbors → R；max_alpha → 剪枝强度上限。

源码行为

Graph::prune_neighbors 先按距离排序候选，再逐步扩大 alpha，直到结果达到 num_neighbors 或 max_alpha 上限。

构建成本

候选越宽、边越多、alpha 越大，图质量可能更好，但构建时间、索引空间与查询访问量都会上升。

03 · ALGORITHM

RobustPrune：一条不等式决定「谁被剪掉」

α 是 Vamana 相对 NSG / HNSW 启发式选邻居多出来的那个旋钮

剪枝规则（论文形式）

对候选按 d(p, x) 升序排序；
取最近的剩余候选 p* 作为出边保留；
若 α · d(p*, p′) ≤ d(p, p′)，
则把 p′ 从候选中丢弃；
直到保留 ≤ R 条边或候选耗尽。
直觉：如果经由已保留的 p* 就能「顺路」到达 p′，那么从 p 直连 p′ 是冗余边，可以省掉。
α 增大 → 丢弃条件更难满足 → 丢弃更少、保留更多边，其中很多是长边（捷径）→ 搜索跳数下降，但度数与空间上升。
α = 1 近似相对邻域图剪枝（激进，边多为短边）；论文常用 α = 1.2；pgvectorscale 默认 max_alpha = 1.2。
论文结论：α>1 时，理想化情形下贪心搜索到目标的距离每步约按 α 收缩，收敛步数呈对数级；这也是「少走几跳」的来源。

03 · STORAGE

节点里到底存什么？两种布局，能力边界不同

Storage trait 抽象节点创建、距离计算、邻居读取、重排距离、访问候选

源码里的硬边界

  • MAX_DIMENSION = 16000；但 plain 不用 SBQ 时最多 2000 维（MAX_DIMENSION_NO_SBQ）。
  • get_meta_page 禁止 inner product 使用 plain。
  • get_meta_page 禁止 label filtering 使用 plain。
  • DEFAULT_STORAGE_TYPE_STR = "memory_optimized"。
  • 带标签节点额外保存 labels；经典 SBQ 节点保存 heap_item_pointer / bq_vector / neighbor_index_pointers。
超过 2000 维、要用内积、要用 label filtering → 都指向 memory_optimized；这不是风格选择，是实现限制。

03 · STORAGE

SBQ 不是 PQ：按维度统计，直接压成 bit

量化器先训练每个维度的均值与可选方差；1 bit 判断 v > mean[i]，多 bit 基于 z-score 分段写入

空间估算（只算压缩向量本身）

SBQ bytes ≈ ceil(num_dimensions_to_index × num_bits_per_dimension / 64) × 8

例：1536 维 × 2 bit = ceil(3072/64) × 8 = 384 字节；原始 float4[1536] 是 6144 字节，约 16× 压缩。

这不代表完整索引大小：邻居指针、page header、rkyv 序列化、labels、meta page、quantizer metadata、对齐与空洞都要另算。

6144 B → 384 B 的可视化

float4[1536] 原始向量
6144 B
SBQ 2 bit/dim 压缩向量
384 B（约 1/16）
但索引还要加上
N × R × IndexPointer + 页面开销
num_bits_per_dimension 是精度与空间的直接旋钮：默认低维 2 bit、高维 1 bit；bit 越少误差越大，越依赖 query_rescore。
再次强调：SBQ 是按维度的统计位量化，PQ 是分段子空间码本量化；二者误差特性不同，不要混用参数与经验。
源码：sbq/quantize.rs（训练与位量化）、sbq/node.rs（节点字段）、plain/node.rs（完整向量布局）。
03 · BUILD

先训练量化器，再扫描 Heap 建图

ambuild 把 reloptions、MetaPage、SBQ 训练、节点写入、图插入串成一条路径

opclass 决定距离语义

vector_cosine_ops ↔ <=>；vector_l2_ops ↔ <->；vector_ip_ops ↔ <#>。

labels 影响构建方式

带 smallint[] labels 的索引不走 parallel build，且只能用 memory_optimized。

NULL 处理

NULL 向量不进索引；NULL labels 视为空数组，label 数组中的 NULL 元素被忽略。

顺序很重要：先有量化元数据，节点里才能写 bq_vector；先有 MetaPage，scan 才能正确解释索引页。
03 · SCAN

读路径是「流式产出候选 + 可选精确重排」

VACUUM 属于另一条线；索引是 relaxed ordering，不保证严格按真实距离排序

relaxed ordering 的含义

索引流式返回近似候选，可能略微不按真实距离排序；要求严格排序时用 materialized CTE 对小候选集再排一次。

WITH r AS MATERIALIZED ( SELECT id, embedding <=> $1 AS d FROM document_embedding ORDER BY embedding <=> $1 LIMIT 50 ) SELECT * FROM r ORDER BY d LIMIT 10;

候选被过滤耗尽怎么办

普通 WHERE 是后过滤：先产出向量候选再过滤。若 tenant_id = 42 选择性很强，前 10 个候选里多数不属于该租户，就会召回不足或需要更多迭代。

三种对策：提高候选宽度 / 把常用过滤做成 smallint[] labels / 分区或多索引策略。
图 4 重绘：query_rescore 控制「读多少候选做完整向量重排」，是排序质量与 Heap 读取成本之间的旋钮。
03 · UPDATE

PostgreSQL 的 VACUUM 标记 ≠ FreshDiskANN 的 StreamingMerge

两者都叫「支持流式更新」，但机制、目标与代价完全不同

pgvectorscale：更 PostgreSQL 化

不要假设 VACUUM 会把图恢复到「全新构建」的质量：全局图优化不是免费发生的。

FreshDiskANN 论文：streaming dataset

pgvectorscale 支持的是 PostgreSQL 语义下的插入与删除标记；图质量、空间回收和重建策略仍是业务自己的运维责任。
为什么天然有张力：MVCC 让「删除」先成为版本状态，而图索引的连通性依赖边的全局结构；标记删除很容易，全局再优化很贵。

① 参数不要跨产品照抄

② 严格排序的两种做法

Azure 可以设 diskann.iterative_search = 'strict_order'；pgvectorscale 用 materialized CTE 对返回的小候选集再排序。

③ 过滤能力是分水岭

05 · COST

别搬论文数字，先算自己的两笔账

单次查询成本与索引空间成本，都能拆成可观测、可度量的组成部分

① 单次查询近似成本

≈ 图上访问的节点数 × 每节点邻居读取 / 距离计算 + query_rescore 个候选的完整向量距离 + Heap 可见性 / 回表成本 + label 或普通 WHERE 过滤成本

② 索引空间近似成本

≈ N × 节点头与 Heap TID + N × 压缩向量或完整向量 + N × num_neighbors × IndexPointer + labels / meta / quantizer metadata + page、rkyv、对齐和空洞成本
验收指标清单：recall@k（用精确扫描或离线 Faiss flat 做 ground truth）、p50/p95/p99 latency、EXPLAIN (ANALYZE, BUFFERS)、索引/表大小、缓存命中与 CPU、插入与 VACUUM 后召回是否漂移。
更可靠的理解方式：在代表性数据集与查询集上画自己的 recall–latency 曲线，而不是记一个固定参数。

06 · DEMO

六段 SQL，从建表到带标签检索

语法级示例：原文作者没有正在运行且已安装 vectorscale 的实例，因此未执行，也没有 EXPLAIN 实测输出

① 扩展与建表

CREATE EXTENSION IF NOT EXISTS vectorscale CASCADE; CREATE TABLE document_embedding ( id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, tenant_id INT NOT NULL, labels SMALLINT[], content TEXT, embedding vector(768) );

② 默认 memory_optimized 索引

CREATE INDEX document_embedding_diskann_idx ON document_embedding USING diskann (embedding vector_cosine_ops);

默认即启用 SBQ；opclass 与查询操作符必须匹配。

③ 查询（含查询期 GUC）

SET LOCAL diskann.query_search_list_size = 100; SET LOCAL diskann.query_rescore = 50; SELECT id, content, embedding <=> $1 AS distance FROM document_embedding ORDER BY embedding <=> $1 LIMIT 10;

④ 严格排序（materialized CTE）

WITH relaxed_results AS MATERIALIZED ( SELECT id, content, embedding <=> $1 AS distance FROM document_embedding ORDER BY embedding <=> $1 LIMIT 50 ) SELECT * FROM relaxed_results ORDER BY distance LIMIT 10;

⑤ label filtering

CREATE INDEX document_embedding_diskann_label_idx ON document_embedding USING diskann (embedding vector_cosine_ops, labels); SELECT id, content, embedding <=> $1 AS distance FROM document_embedding WHERE labels && ARRAY[101,205]::smallint[] ORDER BY embedding <=> $1 LIMIT 10;

⑥ 构建参数示例（勿照抄生产）

SET maintenance_work_mem = '2GB'; CREATE INDEX document_embedding_diskann_tuned_idx ON document_embedding USING diskann (embedding vector_cosine_ops) WITH ( storage_layout = memory_optimized, num_neighbors = 64, search_list_size = 150, max_alpha = 1.2, num_dimensions = 0, num_bits_per_dimension = 2 );
label 硬条件：smallint[] + && overlap + 不能用 plain；普通 tenant_id = 42 属于后过滤。上线前：记录 recall@k、p95/p99、EXPLAIN (ANALYZE, BUFFERS) 与索引大小。
07 · PRACTICE

把 DiskANN 当「召回候选层」，不是最终排序层

ANN 负责找候选，SQL 负责业务语义；这样既利用 PG 的一致性，也不把所有排序语义压进索引

为什么不要窄召回

后过滤会吃掉候选；只召回 10 个再按权限筛，往往凑不满结果。宽召回给 SQL 留足排序空间。

为什么不要把语义压进索引

权限、时间衰减、业务分经常变化，重建索引成本高；放在 SQL 层可随业务演进。

ground truth 是前提

先定义 recall@k 的精确结果来源，才有资格判断「更快」是不是牺牲了不可接受的召回。

架构判断：索引只回答「哪些向量可能相关」，业务排序回答「哪些结果应该给用户看」。
07 · PRACTICE

DBA 管住漂移，开发者写对查询

一边是索引生命周期监控，一边是「结果不够准」时的排查顺序

DBA：构建前 + 上线后

建索引前先调 maintenance_work_mem；根据表大小、labels、storage layout 判断 parallel build 是否会生效（无 labels + SBQ + 行数阈值）。
监控清单
  • pg_relation_size(index) 与增长趋势。
  • 查询 p95 / p99 与召回抽检（不只是平均延迟）。
  • 插入、删除、VACUUM 后的延迟与候选耗尽情况。
  • DEBUG1 下的 query stats：index reads、heap reads、distance comparisons、visited / candidate nodes。
  • 版本升级后的 REINDEX 要求（元数据格式可能变化）。
  • 高 churn 表：设定重建触发条件（删除比例、召回下降、索引膨胀、p99 异常）。
VACUUM 标记删除 ≠ 图全局再优化；长期 churn 需要主动重建窗口。

开发者：写出能被索引使用的查询

SELECT ... FROM ... ORDER BY embedding <=> $query LIMIT 20;
不要把向量距离藏在复杂表达式里；opclass 与操作符必须匹配：vector_cosine_ops ↔ <=>、vector_l2_ops ↔ <->、vector_ip_ops ↔ <#>。
「看起来不够准」按顺序排查
共同前提：没有精确结果样本作为 ground truth，就无法判断「快」是不是以不可接受的召回损失换来的。
08 · SCENARIO

选它，或不选它，边界要清楚

DiskANN 的价值来自「在数据库里以可接受代价近似召回」，不是万能加速器

✓ 适合

典型画像：中等写入比例的 RAG / 语义检索库，数据量从千万到亿级，要求结果能直接 JOIN 业务表并受权限约束。

✕ 不适合

若「向量只是弱信号」，真正该优化的是业务条件的选择性与索引，而不是把 ANN 参数越调越大。
决策顺序：先问是否允许近似 → 再问数据规模是否值得 → 再问更新与过滤形态 → 最后才选参数。
09 · PITFALLS

十个常见坑，按「最容易踩」排序

前四个最常在生产里造成「结果不对 / 结果变少」，后六个多属容量与运维问题

1 · 当成 B-tree

B-tree 的正确性来自有序键和比较器；DiskANN 来自近似图搜索，需要召回评估。

2 · 只看平均延迟

图搜索与回表重排都会产生尾延迟，必须看 p95 / p99。

3 · 后过滤耗尽候选

WHERE 条件在候选生成之后执行；强选择性条件会让 LIMIT 10 凑不满。

4 · 忽略 opclass

索引用 cosine 建、查询用 L2 操作符，planner 不会按预期使用同一索引语义。

5 · num_neighbors 过大

召回可能提高，但索引空间、构建时间、查询访问边数一起上涨。

6 · 忽略维度限制

plain 上限 2000 维；超过要用 memory_optimized。

7 · 忽略 label 类型

label filtering 是 smallint[]，不是任意 text / jsonb metadata。

8 · 删除后从不重建

VACUUM 只是标记删除，不是图全局再优化；长期 churn 要有重建策略。

9 · 直接套论文数字

论文数据集、硬件、召回定义、embedding 分布与你的业务完全不同。

10 · 没有 ground truth

没有精确结果样本，就无法知道「快」是否以不可接受的召回损失换来的。

还有三个实现级限制值得记住：plain 不支持内积、plain 不支持 label filtering、labels 索引不支持 parallel build；UNLOGGED 表上建索引当前也不支持。
共通根因：把「近似索引」当成「精确且自动维护的索引」，跳过召回与尾延迟的验收环节。

扩展问题

  1. 为什么 Vamana 需要 α，而 HNSW 的层级结构试图解决的是另一个问题？
  2. 强租户隔离应该用 labels、分区、每租户索引，还是召回后过滤？各自代价是什么？
  3. SBQ、PQ、SQ 的误差分别怎样影响候选生成与最终排序？
  4. query_search_list_size 与 query_rescore 同时变大时，召回提升来自「走到更好的候选」还是「把候选排准了」？
  5. PostgreSQL 的 MVCC / VACUUM 与图索引的删除维护之间，为什么天然有张力？

这些问题没有统一答案；每一个都可以用「自己的数据 + ground truth + 代价模型」做一次实验。

TAKEAWAYS

五句话带走这一讲

以及本演讲的播放、导航与快捷键

① 它改写了问题，不是消灭了代价

少看候选、少占内存、可调准确率；近似、压缩、图边、重排、删除维护都是真实成本。

② Vamana 的核心是「少量好边」

GreedySearch 定候选，RobustPrune 用 α 保留方向分散的边与长边，把 SSD 跳数压下来。

③ 三种同名形态必须分开

论文用 PQ、Azure 显式给 PQ 参数、pgvectorscale 默认 SBQ；参数名与能力边界不可混用。

④ 在 PG 里，索引只负责召回候选

Heap TID、MVCC 可见性、权限与最终排序仍归数据库与 SQL；labels 是唯一能进入图搜索的过滤形态。

⑤ 用实测曲线代替固定参数

recall@k、p95/p99、EXPLAIN (ANALYZE, BUFFERS)、索引大小与召回漂移，才是验收指标。
