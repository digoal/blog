01 / 问题

难点不在 SQL 写法，而在三类成本同时压过来

「把 embedding 放在 PostgreSQL 里，既能和关系条件一起查，又不想为 1 亿甚至 10 亿向量单独准备一套向量数据库。」

VECTOR BODY ONLY · float32
≈ 286 GiB
100,000,000 × 768 × 4 B

这还没算 PostgreSQL 行头、索引项、可见性、主键、过滤列、缓存和副本。

空间

N × dim × 每维字节数
向量本体、索引项、重排向量都要占空间。

带宽 / I/O

每次候选扫描要搬多少向量数据，决定延迟与缓存命中。

召回

少扫候选、压缩候选之后，TopK 会错多少？必须可测。

① 内存放不下、随机 I/O 扫不动

② K-means / 图构建 / 压缩训练太慢

③ WHERE tenant_id、时间、权限难与 TopK-only 融合

④ 只看近似距离不可控，全量回表重排又太慢

02 / 一句话结论

它不是 HNSW，是四件事串起来的组合索引

保留熟悉的 ORDER BY embedding <-> query LIMIT k 接口，代价藏在索引内部与数据库语义里。

分区：lists 越细 leaf 越小，但构建更贵

压缩：1-bit code 只用于估算，不替代真实距离

重排：rerank_in_table 是空间换时间（回表）

融合：prefilter 只适合严格且便宜的过滤

03 / 定义

一句话定义，以及七个必须先统一的术语

vchordrq 是 PostgreSQL 的向量索引访问方法：层级 K-means 切分空间，cell 内存 RaBitQ 压缩候选与可选重排向量，查询用误差下界剪枝，再用原向量重排。

vchordrq

RaBitQ / quantization-based 索引访问方法，本文主角。

vchordg

VectorChord 的图索引方法，HNSW-like / Vamana 风格；本文只横向对比。

lists

层级分区配置：[] 不分区；[4096] 一层叶子；[4096,262144] 两层。

probes

查询时每层探测多少 cell，形状必须和 lists 匹配。

epsilon

控制下界保守程度。越大通常越保守、候选更多、召回倾向更好、延迟更高。

residual_quantization

对残差做量化；cosine 可配合 spherical centroids，源码禁止用于 rabitq8/rabitq4。

rerank_in_table

空间换时间：打开后索引不存重排向量，精确距离改回 heap 读取。

prefilter

让向量索引在候选阶段尝试应用 PostgreSQL filter 条件。

SHAPE MATTERS

lists 与 probes 的形状必须对应

注：probes 数值仅为形状示意，实际取值需按 lists 规模与召回目标测试。
04 / 结构

它像一棵「面向 ANN 的倒排树」

上层是空间分区导航，叶子里才是候选向量列表；元信息、中心点、分支、叶列表、重排向量与空闲页各自有位置。

读法：MetaTuple → Centroid → 非叶 branch → JumpTuple → Frozen/Appendable；查询沿这条链只访问被 probes 选中的分支。关键区别：vchordrq 不是单纯的 (key, vector) 排序表。
05 / 构建

构建成本分成「分区训练」与「把表数据装进索引」

大表下 partitioning phase 通常主导构建时间与内存；这是与「建个 B-tree」完全不同的成本模型。

为什么旋转中心点？

构建对 centroid 执行 RaBitQ 的随机旋转，让后续 1-bit 量化的估算与误差界成立；这是量化前的准备动作。

并行建索引

AM_HANDLER 的 amcanbuildparallel = true 在 PostgreSQL 17/18 feature 下启用并行建索引。

外部构建

build.source = external 允许把聚类/中心点预计算放到库外，用空间与时间换构建可控性。

源码锚点：src/index/vchordrq/am/mod.rs（ambuild）· crates/vchordrq/src/build.rs（元组与页布局）· crates/rabitq/src/rotate（中心点旋转）。
06 / Index AM

它不是旁路服务，而是执行器里的一种 Index Scan

AM_HANDLER 先声明能力，amrescan / amgettuple 再按 PostgreSQL 的规则交回 CTID。

为什么必须走 MVCC

索引只负责交回 CTID，heap tuple 是否可见由数据库执行器判断。VectorChord 源码明确拒绝非 MVCC 快照扫描——向量索引不能绕过事务语义。

与 VBASE 的关系

高维 ANN 没有 B-tree 那种单调性，向量 TopK 与关系查询难融合。prefilter、CTID 返回、MVCC 限制和 recall evaluation，都是在执行框架内处理这一问题的工程路径。

常见误解：「建了向量索引，LIMIT 小就一定快」——如果过滤条件后置，索引可能要吐出很多候选，执行器才凑得够结果。
07 / 核心原理

压缩不是目的，可用于剪枝的「误差下界」才是

RaBitQ 把 D 维向量量化成 D-bit 字符串，同时给距离估算提供理论误差界，并可用 bitwise / SIMD 计算。

crates/vchordrq/src/search.rs
let lowerbound =
Distance::from_f32(rough − err × epsilon);
  • rough：压缩 code 对距离的估算
  • err：与估算误差相关的项
  • epsilon：决定下界保守程度
  • 候选按 lower bound 入堆；真正返回前再重排
同一形式同时出现在层级 cell 搜索与叶子候选扫描。

① 索引内部 1-bit RaBitQ code

rabitq::bit::code() 存 sign bits 与 CodeMetadata，服务于快速估算与误差下界；用户不直接感知。

② 用户可见 rabitq8 / rabitq4 列类型

VectorChord 1.1.0 起的低 bit 向量类型，每维 8 bit / 4 bit。省空间，但官方文档明确说明会牺牲精度和性能。

09 / 查询

查询是五级漏斗：逐层少读，最后才碰原向量

probes 控制访问多少 cell，epsilon 控制下界保守程度，io_search / io_rerank 控制读页策略，prefilter 决定是否前推过滤。

residual 分支

开启 residual 时，先计算 query 到 root centroid 的精确距离；否则走 fast path。

CTID 边界

amgettuple 只把 CTID 交回 PostgreSQL，heap tuple 是否可见仍由数据库执行器处理。

正确性来源

不是「相信压缩距离」，而是下界筛候选 + 原向量精确重排共同收敛 TopK。

源码锚点：crates/vchordrq/src/search.rs（default_search）· crates/vchordrq/src/rerank.rs（rerank_index / rerank_heap）。

11 / 重排

精确距离从哪来？两条路径，一个 space-time 取舍

reranker 按 lower bound 出队；差别在于「原向量」是索引里存着，还是回 heap 去取。

监控点

打开后重点看 heap 随机读是否成为瓶颈，可用 EXPLAIN (ANALYZE, BUFFERS) 观察。

近似集合不变

它改变的是「精确距离从哪读」，不改变分区与下界筛候选的逻辑。

源码锚点

crates/vchordrq/src/rerank.rs 在 rerank_index 与 rerank_heap 之间切换。

12 / 生命周期

它服务 ANN，但仍在 MVCC / VACUUM / 页面管理下运行

插入、更新、删除与清理都走 PostgreSQL 索引生命周期；只考虑算法、不考虑这些约束，索引在数据库里很容易失真。

INSERT

先追加可选重排向量，再沿层级树选叶子，把 code / delta / payload 写进 AppendableTuple。

UPDATE / DELETE

UPDATE 对索引通常表现为旧项删除 + 新项插入；删除由 VACUUM callback 判定 CTID 死活。

VACUUM

ambulkdelete 调 dispatch::bulkdelete()，amvacuumcleanup / maintain 整理 freepages 与统计。

FIRST, PICK A GOAL

生产调参先明确目标

  • 省钱：空间 / 内存带宽
  • 降延迟：少扫 cell、少重排
  • 提召回：更多 probes、更保守 ε
  • 缩短构建：sampling_factor / kmeans_iterations / build_threads
不要在没有 recall 样本的情况下盲目降低 ε 或 probes——那是拿准确性换延迟。
I/O 也会变：PostgreSQL 14–16 与 17+ 可用的 read / prefetch / stream 策略不同；过滤很松或表达式昂贵时，prefilter 的收益会消失甚至反噬。
15 / 实操 DEMO

最小可用索引，以及最容易踩的「形状不匹配」

以下 SQL 来自官方接口与本地测试风格，是可执行模板；本文没有在本机启动 PostgreSQL 执行，因此不给出任何伪造输出。

CREATE EXTENSION IF NOT EXISTS vchord CASCADE;

CREATE TABLE items (
    id bigserial PRIMARY KEY,
    embedding vector(3)
);

CREATE INDEX items_embedding_vchordrq_idx
ON items USING vchordrq (embedding vector_l2_ops)
WITH (options = $$
[build.internal]
lists = [1000]
build_threads = 8
$$);

SET vchordrq.probes = '10';
SET vchordrq.epsilon = 1.9;

SELECT id FROM items
ORDER BY embedding <-> '[0.3,0.2,0.1]'::vector
LIMIT 10;
opclass 名称请按所安装的扩展版本文档为准（不同版本可能写作 vector_l2_ops 或带 schema 前缀）。
SHAPE CHECK

源码会检查形状

default_search() 校验 height_of_root == 1 + probes.len()。形状不对，查询阶段直接报错，而不是悄悄变慢。

会话级 GUC 陷阱：不同索引可能用了不同层数的 lists，全局或会话级 probes 设错会「误伤」另一条查询。
16 / 实操 DEMO

两个进阶选项：residual quantization 与 rabitq8 / rabitq4

一个改的是「索引如何量化残差」，一个改的是「表列本身存什么」——别把两者混为一谈。

cosine 场景 · 残差量化

官方文档建议多数 cosine 数据集可尝试配合 spherical centroids。

CREATE INDEX items_embedding_cos_vchordrq_idx
ON items USING vchordrq
    (embedding vector_cosine_ops)
WITH (options = $$
residual_quantization = true
[build.internal]
lists = [1000]
spherical_centroids = true
build_threads = 8
$$);

SET vchordrq.probes = '10';
SELECT id FROM items
ORDER BY embedding <=> '[0.3,0.2,0.1]'::vector
LIMIT 10;
硬约束：列类型是 rabitq8 / rabitq4 时，源码在构建阶段明确拒绝开启 residual quantization。

低 bit 列类型 · rabitq8 / rabitq4

1.1.0 起提供；每维 8 bit / 4 bit，省空间但牺牲精度和性能。

CREATE TABLE items_q8 (
    id bigserial PRIMARY KEY,
    embedding rabitq8(3)
);

INSERT INTO items_q8 (embedding) VALUES
    (quantize_to_rabitq8('[0,0,0]'::vector)),
    (quantize_to_rabitq8('[1,1,1]'::vector));

CREATE INDEX items_q8_embedding_idx
ON items_q8 USING vchordrq
    (embedding rabitq8_l2_ops);

SELECT id FROM items_q8
ORDER BY embedding <->
    quantize_to_rabitq8('[0.9,0.9,1.1]'::vector)
LIMIT 10;
适用场景：空间极敏感，或一次召回大量候选后再做业务侧处理；不适合要求很高精度的 TopK 主路径。
源码细节：Rabitq8Owned 保存 dim / sum_of_x2 / norm_of_lattice / sum_of_code / sum_of_abs_x / packed_code；Rabitq4Owned 把两个 4-bit code 打包进一个 byte；extended.rs 实现多 bit code、scale 搜索与 L2 / dot / cos 估算。
17 / 召回闭环

没有 recall 基准，很容易把参数调到「快但错」

VectorChord 提供 query sampling 与 recall evaluation 相关函数和视图；生产调参建议形成固定样本集。

SET vchordrq.probes = '10';
SET vchordrq.epsilon = 1.4;

SELECT *
FROM vchordrq_evaluate_query_recall(
    query => $$SELECT ctid FROM items
       ORDER BY embedding <-> '[0.3,0.2,0.1]'
       LIMIT 10$$
);

为什么必须闭环

只看线上延迟，会把 ε / probes 一路调低到「很快但漏掉正确结果」。召回是 ANN 索引的一等公民指标，不是事后补的验收项。

embedding 模型、归一化方式、维度或距离函数变化后，旧索引的 cell 与量化误差分布不再代表新分布。

18 / 最佳实践

同一个索引，三种角色各自该盯什么

先按业务定义 TopK recall 目标，再选 lists / probes / epsilon，最后评估机器成本。

FOR ARCHITECT

数据库架构师

  • 把 vchordrq 当成可调的 ANN 索引，不是 B-tree 替代品
  • 先定 Top10 recall ≥ 0.95 一类业务目标
  • 规模是否大到 ivfflat / hnsw 成本不可接受
  • 查询是否有强过滤，能否从 prefilter 获益
  • 是否允许定期重建 / 外部构建应对分布漂移
FOR DBA

DBA

  • 建索引阶段内存与临时 I/O：sampling / build_threads
  • probes 形状与 lists 匹配，避免会话 GUC 误伤别的索引
  • VACUUM 后索引膨胀、dead tuple 与查询延迟
  • rerank_in_table=true 后 heap 随机读是否成瓶颈
  • 无 recall 样本时不要盲目降低 ε / probes
FOR DEVELOPER

业务开发者

  • SQL 保持简单：WHERE + ORDER BY + LIMIT
  • 过滤严格且便宜时，可测试 prefilter = on
  • LIMIT 小不自动等于快：过滤后置会吐更多候选
  • embedding 模型升级后重新评估召回
SELECT id, payload FROM items
WHERE tenant_id = $1
ORDER BY embedding <-> $2
LIMIT 20;
理解执行代价：写法简单不代表代价简单。WHERE 很严格且便宜时可试 SET vchordrq.prefilter = on；若过滤松或表达式昂贵，收益会消失。
19 / 场景边界

什么时候值得上，什么时候别碰

vchordrq 的复杂度是有价格的：它换来的空间与 I/O 优势，只在特定 workload 上兑现。

GOOD FIT

适合

  • 大规模文本 / 图片 / 多模态 embedding 检索，空间与内存带宽是主要瓶颈
  • PostgreSQL 内需同时处理向量相似度与关系过滤
  • 能接受 ANN，并愿意用 recall evaluation 做参数闭环
  • 数据以批量导入、周期构建或低频更新为主
  • cosine embedding 且可测试 residual quantization / spherical centroids 收益
BAD FIT

不适合

  • 小表：顺序扫描或简单 pgvector 索引已足够，复杂度不值得
  • 必须精确 TopK，不允许任何召回误差
  • 高频单行更新，且不能容忍 VACUUM / 索引维护成本
  • 每租户数据很小但租户极多、查询总是单租户强过滤：优先分区表 / 局部索引等建模
  • 对参数治理没有预算，只想「建一个索引永远不用管」
DECISION
任一环节是「否」，先看简单方案与数据建模，而不是加参数。
一句话：它是为「大规模 + 空间敏感 + 愿意做参数治理」准备的索引，不是所有向量表的默认答案。
20 / 常见坑

七个高频坑，几乎都和「把机制想简单了」有关

每一条都能在源码或官方文档里找到对应约束；踩中后通常表现为「召回掉了」或「变慢了」。

01

lists / probes 形状不匹配

[1000] 对应一层；[400,160000] 对应两层。源码检查数量，不匹配会报错。

02

把 ε 当精度百分比

ε 不是 recall，也不是误差百分比；它控制 lower bound 的保守程度，降低可能漏掉该重排的候选。

03

只看索引大小

rerank_in_table 后索引变小 ≠ 查询变快；官方文档说明会降低查询性能，prefetch 也不工作。

04

过滤条件不适合 prefilter

便宜且严格的过滤（如 id % 97 = 0）可能受益；正则、复杂函数、低选择性条件不适合。

05

量化列类型误用

rabitq8 / rabitq4 是表列层面的低 bit 类型，省空间但牺牲精度和性能，不是免费压缩。

06

忽略模型升级与分布漂移

模型、归一化、维度、距离函数变化后，旧 cell 与量化误差不再代表新分布，需重建并测 recall。

07

把论文结论直接等同于数据库实现

RaBitQ 论文给的是量化误差界与 SIMD / bitwise 路径；VectorChord 还要处理 PostgreSQL page、VACUUM、MVCC、过滤、回表和 I/O 策略。工程效果必须按数据库 workload 验证。

统一心法：任何「加速旋钮」都要配一个 recall 数字和一组 buffers / I/O 观察，否则只是在把错误藏到延迟里。
21 / 收尾

带走四句话，再带着问题回去验证

理解结构之后，真正的功夫在「按自己的 workload 测出来」。

TAKEAWAY 01

组合索引

层级 IVF + RaBitQ 下界 + 原向量重排 + PostgreSQL 语义，四件事缺一不可。

TAKEAWAY 02

下界而非压缩

RaBitQ 的价值是给出可剪枝的误差下界，不是让近似距离直接当答案。

TAKEAWAY 03

数据库约束

Index AM / CTID / MVCC / VACUUM / 过滤，决定了算法能不能在库里成立。

TAKEAWAY 04

召回闭环

先定 recall 目标，再动 probes / ε / lists；没有基准就是「快但错」。
