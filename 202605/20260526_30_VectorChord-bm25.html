01 / 背景 THE NAIVE SQL

数据已在表里，只想按相关性取前 10 条

标题、正文、日志、评论——SQL 最好还是长这样，不必先把数据搬进外部搜索系统。

SELECT · ORDER BY · LIMIT
SELECT id, passage
FROM documents
ORDER BY to_tsvector('english', passage) <&>
         to_bm25query(
           to_tsvector('english', 'PostgreSQL'),
           'documents_passage_bm25')
LIMIT 10;
没有专门索引时，数据库只能逐行分词 → 匹配 → 打分 → 排序。文档一多，瓶颈不在 BM25 公式本身。
相关性排序索引不是语义向量索引不理解「意思相近但词不同」
02 / 原理 INVERTED INDEX

把「文档 → 词」倒过来，只是第一步

点击播放，看三条文档如何逐条汇入倒排表；再看真实搜索必须付出的三个代价。

状态：等待构建
真实搜索的三个代价
  • 长 posting list：高频词一次命中大量文档
  • Top-K 阈值：只要前 10 条，没必要给所有候选完整打分
  • 数据库生命周期：更新、删除、VACUUM、MVCC 可见性都要处理
动画只是把映射关系「画出来」；索引真正要保存的是 internal token id、docid、tf、fieldnorm 和分块上界，不是字符串。
核心取舍：用 tsvector 作输入；内部 token id / docid / tf / fieldnorm；每 128 个 posting 一块保存分数上界；增量写入先落到 ptr_vectors 追加区，VACUUM 再重写为压缩倒排结构。
03 / 原理 TRADE-OFFS

四个设计取舍，对应四类明确代价

它把搜索引擎式的 Top-K 能力搬进 PostgreSQL，同时把数据库自己的生命周期约束接了下来。

prefilter 的取舍

让 WHERE 提前参与候选筛选

好处：过滤后仍有足够结果。成本：搜索阶段要做 heap fetch 和表达式求值（qual），过滤很松或表达式很重时可能反而变慢。

排序语义

它是相关性排序索引

不等于语义向量索引，也不等于完整搜索引擎。目标是把 ORDER BY … LIMIT k 变成一次索引扫描，而不是替换 PostgreSQL 执行器。

04 / 是什么 DEFINITION & ARCHITECTURE

一个自定义 Index Access Method，四层职责

PostgreSQL 上的 BM25 自定义索引访问方法：内部用压缩倒排表 + Block-WAND 上界剪枝，支撑 ORDER BY tsvector <&> bm25query LIMIT k。

返回的是 CTID：最终行可见性、回表和上层 WHERE 语义仍归数据库执行器，它不是旁路搜索服务。
四层不是四个进程；全部在同一个 PostgreSQL 后端里，通过 Index AM 回调串起来。
05 / 是什么 SOURCE MAP

六条入口，串起建、查、维护三条主路径

看源码时先认这六个文件，就能把 SQL 语法、AM 回调、倒排生成、查询剪枝、维护重写对上号。

这些路径不是彼此独立的服务：build / flush 生成结构，search 消费结构，maintain 周期性重建结构，AM 层负责把它们接进 PostgreSQL 的生命周期。
06 / 是什么 GLOSSARY

先把八个术语对齐，后面才不会串味

用户看到的是 tsvector 与分数；索引内部看到的是 token id、连续 docid、1 byte 长度桶和 heap CTID。

术语含义
bm25query复合类型，包含 query tsvector 和目标 index regclass。
summary每个 posting block 的 min/max docid、块内上界所需的 fieldnorm/tf，以及 block 指针。
append vector增量插入写入的未压缩追加区（ptr_vectors）；查询时同样参与打分。
一个容易错的细节：document_length 不是唯一 token 数，而是 term frequency 之和；Document::length() 对所有元素的 value 求和，再经 length_to_fieldnorm() 压成 1 byte。
07 / 核心原理 INDEX AM

让相关性排序成为一次索引扫描

支持 ORDER BY indexed_column operator constant 的访问方法要声明 amcanorderbyop；索引交回 CTID，可见性与回表仍归执行器。

AM_HANDLER 的四个标志
  • amcanorderbyop = true：允许 planner 把 ORDER BY 下推
  • amoptionalkey = true：允许无普通 WHERE key 的 order-by scan；既无 key 也无 orderby 时源码直接报错
  • amcanbuildparallel = false：当前 feature 下不宣称并行构建
  • amcostestimate：实现很粗，startup/total cost 置 0，按 PostgreSQL selectivity 估过滤选择率
两个硬约束：只支持 ForwardScanDirection；只支持 MVCC-compliant snapshot。它不是一个旁路搜索服务。
落地提醒：cost estimate 粗 → 生产环境必须用 EXPLAIN (ANALYZE, BUFFERS) 验证是否真的选中了 bm25 索引扫描。
08 / 核心原理 BUILD PATH

CREATE INDEX：heap tuple → 临时流 → 压缩倒排页

构建不直接往索引页里一条条塞 posting，而是先落两个临时流，外排归并后再整体 flush。

crates/bm25 · 两个很小的结构
pub struct Record(pub u32, pub [u16; 3]);
// Record(document_length, ctid_payload)

pub struct Mapping(pub [u8; WIDTH],
                    pub u32, pub u32);
// Mapping(token_id, document_id, term_frequency)
document_length = term frequency 之和，不是唯一 token 数；随后用 length_to_fieldnorm() 压成 1 byte。
09 / 核心原理 PHYSICAL LAYOUT

页面不是一条 posting list 从头写到尾

第 0 页放 MetaTuple，JumpTuple 当总目录；查询先走 token 地址树，再沿 summary / block 读 posting。

这套结构避免了把所有 posting 做成一个巨大线性数组；代价是实现复杂度上升——维护时要同时更新主目录、地址树和旧页回收链。
10 / 核心原理 TUPLES

七类 Tuple，各管一件事

从全局参数、目录、文档长度、词项入口，到分块上界、真正的 posting 数据和增量写入区。

结构关键字段作用
MetaTuplek1、b、ptr_lock、ptr_jump、seed全局参数和入口；第 0 页
JumpTuple文档数、总长度、各 tape 指针、地址树 root主目录，维护后要更新指针并回收旧页链
DocumentTuplefieldnorm、payload、deletedinternal docid → CTID 与长度归一化信息
TokenTupleid、df、token WAND 上界、wptr_summariestoken → posting summary 链入口
SummaryTuplemin/max docid、block WAND 上界、block 指针让查询先判断这个 block 值不值得解压
BlockTuple压缩 docids、压缩 term frequencies真正的 posting 数据，最多 128 条一块
VectorTuplefieldnorm、elements、payload、deleted追加区，承接增量写入
11 / 核心原理 SCORING

分数从哪来，为什么是负数

默认 k1 = 1.2、b = 0.75；idf 用 ln((N+1)/(df+0.5))；文档长度不实时算，而是查 1 byte fieldnorm 表。

用户看到的分数

<&> 返回负分

_bm25_evaluate() 最后返回 −score.to_f64()。

目的是让 PostgreSQL 默认升序 ORDER BY 把更相关的文档排在前面。

记住：分数越小越相关。想显示成正分，在展示层取负，不要改 ORDER BY 方向。
示意分数仅用于解释符号与排序方向，不是实测数据。原文明确「本文没有编造性能数字」。
12 / 核心原理 BLOCKS & COMPRESSION

每 128 个 posting 一块，先读上界再解压

flush() 按 token 读取排序后的 mappings：每块写一条 SummaryTuple（上界 + 指针）和一条 BlockTuple（压缩数据）。

为什么是 128

块是「跳过」的最小单位

块太大 → 上界偏松，跳过能力下降；块太小 → summary 变多、解压次数变多。128 是压缩率、跳过能力与解压成本之间的取舍点。

扩展问题：改成 64 或 256 会怎样？留给听众自己推。

与 Block-WAND 的关系

结构为算法服务

SummaryTuple 里保存「块内能产生最高 BM25 tf 部分的 fieldnorm / tf」，正是为了在不解压的前提下估出这个块的理论最大贡献。

结构不是通用倒排格式，而是为「少算」专门设计的。

13 / 核心原理 BLOCK-WAND · INTERACTIVE

动手跑一遍 Block-WAND

先扫追加区，再建 token cursors；token 上界 → block 上界 → 精确打分，三层决策只处理有机会进 Top-K 的块。

状态：等待播放
当前块 — 阈值 τ 5.0 解压块 0 跳过块 0 Top-K 堆 [ ]
6 个 posting block（分数为教学示意，不是实测数据）
三层决策

① token 级：tail token 上界 + 当前 token 上界 ≤ τ → 继续推进

② block 级：lead/tail cursors 的 block 上界相加 ≤ τ → 不解压，跳到下一个可能 docid

③ document 级：过线才读 fieldnorm、取 tf、精确打分，CTID 进 Top-K 堆

候选满 k 后，第 k 名分数抬高 τ，后续跳过更激进。价值：Block-WAND 不改变 BM25 语义，只减少不可能进 Top-K 的打分工作；search() 还会先扫 ptr_vectors 追加区，把未 merge 的增量文档算进来。
14 / 核心原理 DELETE & MAINTAIN

删除先打标记，空间整理交给 VACUUM cleanup

bulkdelete 不会立刻从 posting block 里物理移除数据；真正的重编号、重写和回收发生在 amvacuumcleanup()。

短期

靠 deleted 标记保证正确性

查询遇到 deleted 的 VectorTuple / DocumentTuple 就不返回无效文档；posting block 里仍留有旧数据。

长期

靠 maintain 合并与回收空间

追加区持续增长会让查询越来越依赖扫描 ptr_vectors；要监控索引体积、VACUUM 时长、P95/P99 与 heap fetch。

17 / 效果 LIMIT × PREFILTER · INTERACTIVE

改几个参数，看「过滤后结果不足」怎么发生

不开 prefilter：索引先取全局 Top-K，再由 SQL WHERE 过滤；开 prefilter：搜索阶段通过 heap fetch 判断 WHERE，继续寻找满足条件的 top-k。

当前配置下的结果

结果不足：返回 2 行

bm25.limit = 10，WHERE 只放行 20%，SQL LIMIT = 10；全局 Top-K 被过滤掉 8 条。

heap fetch：仅最终候选回表，成本较低。

调参方向：提高内部 limit / 打开 prefilter / 接受提前 heap fetch 的成本；三者与 WHERE 选择率一起看。
这是教学示意模型，用于解释「过滤后结果不足」与「prefilter 不是免费优化」，不是精确执行语义；不同发行版本对 bm25.limit 的定义可能不同，落地前按所用版本核对（见末页）。
18 / 实操 DEMO

当前接口风格的一套最小闭环

示例来自 tests/sqllogictest/indexing.slt 的当前接口风格；原文未在本机启动 PostgreSQL 执行，语法依据本地测试文件与安装 SQL 校对。

建表 · 建索引 · 查询
CREATE EXTENSION IF NOT EXISTS vchord_bm25;

CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    passage TEXT
);

CREATE INDEX documents_passage_bm25
ON documents
USING bm25 ((to_tsvector('english', passage)) bm25_ops);

SET enable_seqscan = off;
SET "bm25.limit" = 10;

SELECT id, passage,
       to_tsvector('english', passage) <&>
       to_bm25query(to_tsvector('english', 'PostgreSQL'),
                      'documents_passage_bm25') AS rank
FROM documents
ORDER BY rank
LIMIT 10;
有过滤条件时
ALTER TABLE documents
ADD COLUMN visible boolean DEFAULT true;

SET "bm25.limit" = 20;
SET "bm25.prefilter" = on;

SELECT id, passage
FROM documents
WHERE visible
ORDER BY to_tsvector('english', passage) <&>
         to_bm25query(
           to_tsvector('english', 'PostgreSQL'),
           'documents_passage_bm25')
LIMIT 10;
验证：EXPLAIN (ANALYZE, BUFFERS)
  • 是否走 documents_passage_bm25 索引扫描
  • bm25.limit 是否 ≥ 业务需要的候选数
  • 打开 bm25.prefilter 后 heap fetch 是否明显增加
19 / 最佳实践 PLAYBOOK

三类角色，各守一条主线

定位、验证、一致性：架构师别把它当 ES，DBA 盯住维护窗口，开发者守住表达式与分词的一致性。

面向数据库架构师
  • 定位为「PostgreSQL 内轻量 BM25 Top-K 能力」，不替代 Elasticsearch / ParadeDB。
  • 同时要语义召回与关键词排序时，分层组合：向量负责语义候选，BM25 负责关键词精排或反向。
  • 多租户 / 强过滤 workload 单独压测 prefilter：过滤选择率高时可能有价值；过滤很松或表达式很重时，提前 heap fetch 会拖慢。
组合方向：各管一段，不必把两种索引揉成一个。
面向 DBA
  • 建索引后用 EXPLAIN (ANALYZE, BUFFERS) 验证 planner；cost estimate 很粗，不要只看 SQL 形态。
  • 把 VACUUM 维护纳入容量与窗口规划：删除多、更新多的表会在 cleanup 阶段重写倒排。
  • 监控索引体积、VACUUM 时长、查询 P95/P99、heap fetch；关注追加区持续增长后查询是否越来越依赖扫 ptr_vectors。
  • 用 reloption 或会话级 GUC 明确设置 limit，别让业务 LIMIT 与内部 top-k 上限脱节。
面向业务开发者
  • 表达式要一致：建索引与查询都用 to_tsvector('english', passage)，否则 planner 未必能匹配索引。
  • 记住 <&> 分数越小越相关（扩展返回负 BM25 分数）。
  • 查询 tokenization 与建索引一致；README 中 pg_tokenizer 内容更像旧接口或外部配套说明，落地以安装 SQL 和测试为准。
  • 中文文本先确认 tsvector 分词方案；BM25 索引不能弥补错误分词。
20 / 场景 FIT & NON-FIT

看 workload 形状，不看「能不能装」

有明确 LIMIT k、数据已在 PostgreSQL、主要是单列 tsvector 排序、且能接受周期性维护重写——这才是它的主场。

六个最容易踩的坑

22 / 收尾 BOUNDARIES & NEXT

带着边界离开，再带着问题回来

两个版本边界、一组扩展问题，以及可以继续读的材料。

边界 A · 论文归属

RaBitQ / VBASE 不是实现依据

RaBitQ 讲高维向量量化与误差界；VBASE 讲向量相似检索和关系谓词在线融合。它们能启发「过滤与 Top-K 如何融合」，但不能直接解释 BM25 posting block。

适合放在「向量检索与关键词检索的边界对比」里。

边界 B · 版本差异

本文以本地源码为准

README / DeepWiki 仍可见 bm25vector、bm25_catalog.* 旧接口痕迹；本文依据本地 commit 14fc2a332b66 的 tsvector 体系。

外部资料补充（2026-11 检索）：vchord_bm25 1.0.0 中 bm25.limit 改为 WAND 初始批大小、扫描可继续；机制讲述以本文源码为准，落地前按所用版本核对。
