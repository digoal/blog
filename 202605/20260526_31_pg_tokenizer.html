一句话定义

PostgreSQL pgrx 扩展：用可配置 TextAnalyzer 生成 token，再用 TokenizerModel 映射为整数 token id。

它不做什么

不是内置 FTS 的包装，不输出稠密语义向量 embedding；输出的是离散的 INT[]。

它服务谁

VectorChord-bm25、RAG token、提示词压缩、业务私有词表、多语言分词。

结构依据：素材第 1–11 节；页面角标区分「测试输出」「流程示意」，避免把示意当作实测。
一 / 问题定位

第一步不是建索引，而是定义「什么算同一个可检索单元」

词元化结果会进入表、索引、触发器、查询计划和线上发布流程；这一步不稳，后面再好的索引和排序都会被拖垮。

流程定位 · 词元化在链路里的位置
三条理论线在此汇合

信息检索教材：文档先解析成 terms，再进入词典、posting list、权重与评估。
BPE（Sennrich 等，ACL 2016）：用高频子词单元组合未登录词，解决罕见词与开放词表。
LLMLingua-2（Pan 等，ACL 2024 Findings）：token 重要性与提示词压缩，涉及保真、延迟和上下文窗口的权衡。

数据库要把三条线合起来：检索看 term 统计稳定，LLM 看词表与成本，业务看版本与可复现。

一 / 问题定位

传统做法有三条路，pg_tokenizer 选第三条

差别不在「分词准不准」，而在配置、词表版本和输出落点由谁负责。

适合路线 3：同库 BM25、RAG token、业务词表、LLM 词表对齐。

三 / 核心原理 · 3.1

先定义词边界，再定义 ID 空间

源码很短，工程含义在「两层职责分离」：一个决定切成哪些 token，一个决定这些 token 对应哪些整数。

Tokenizer::tokenize() · Rust 源码
pub fn tokenize(&self, text: &str) -> Vec<u32> {
    let tokens = self.text_analyzer.apply(text);
    self.model.apply_batch(tokens)
}
TextAnalyzer 回答

「这个字符串应该切成哪些 token」
text → Vec<String>

Model 回答

「这些 token 在某词表里是哪些整数」
tokens → Vec<u32>

为什么数据库里要分两层

检索系统关心 term 的可区分性和统计稳定性；LLM 系统关心模型词表和推理成本；业务系统关心版本可控和 SQL 可复现。两层分开后，同一套清洗规则可以接不同词表，而换词表不必重写切词规则。代价是：换词表就等于换 ID 空间。

三类背景知识如何汇入这条流水线

三 / 核心原理 · 3.2

可组合，但顺序会改变结果

apply() 先按顺序执行 character filters，再用一个可选 pre tokenizer 切词，最后按顺序执行 token filters。

顺序反例 · 概念示意

停用词表内写的是小写 the，输入是 The：
先小写再停用词 → the 命中并被丢弃；先停用词再小写 → The 未命中，最终残留 the。

工程含义

配置数组的书写顺序就是发布契约。改顺序等于改词表语义，必须像 schema 变更一样走发布流程；也不要在中文链路里盲目套英文 stemmer。

来源：素材「3.2 TextAnalyzer」及图 2；顺序反例为基于大小写敏感停用词表的概念推导，非 sqllogictest 实测输出。

三 / 核心原理 · 3.3

同样的 token，不同的 ID 空间

TokenizerModel 的接口只有 apply(token) → Vec<u32> 与默认 apply_batch(tokens)；差别在词表来源和未知词处理，不在 SQL 输出形态。

builtin 通过 include_bytes! 打进扩展，wiki_tocken 用 tocken::Tokenizer。

custom 的 apply_batch() 一次查表，再按输入顺序输出找到的 ID；未命中 token 被丢弃。

结论：判断词元化是否可用，不能只看「输出是不是 INT[]」，还要看 ID 空间属于哪套词表。

来源：素材「3.3 Model」、图 3、tests/sqllogictest/tokenizer.slt；源码细节（encode_fast / include_bytes! / PRELOAD_MODELS）照素材原文。
三 / 核心原理 · 3.3

四类模型：选的是词表来源，不是输出格式

builtin / HuggingFace / Lindera / custom 的 SQL 输出都是 INT[]，差别在词表从哪来、未知词怎么处理、谁来管版本。

模型类型配置入口适合场景代价
builtinmodel = "llmlingua2" 等快速使用内置词表；和常见模型 token id 对齐词表固定，模型文件占内存
HuggingFacecreate_huggingface_model导入 tokenizers.json，复用外部模型词表配置和文件管理要严格
Linderacreate_lindera_model日文形态分析和 token id 输出配置复杂，偏日文场景
customcreate_custom_model用表内语料生成业务私有 token → id依赖触发器和 catalog 表，线上变更要管一致性
源码细节 · 打包与预加载

builtin 通过 include_bytes! / include_str! 打进扩展；PRELOAD_MODELS 默认只有 llmlingua2；tocken::Tokenizer 用于 wiki_tocken。

源码细节 · 子词拆分

tokenizers::Tokenizer 调用 encode_fast(token, false)：一个输入 token 可能被拆成多个子词 ID，所以 token 数 ≠ ID 数。

源码细节 · custom 查表

apply_batch() 用 WHERE token = ANY($1) 一次查 tokenizer_catalog."model_x"，按输入顺序输出找到的 ID；找不到的 token 被丢弃。

源码细节 · 类型转换风险

目标列不是 INT[] 时，触发器会尝试把 INT[] 转成目标列类型；这给了集成空间，也给了转换失败的风险。

来源：素材「3.3」模型对比表与源码细节四条；「3.4」目标列类型转换说明。
三 / 核心原理 · 3.4

把业务语料变成数据库内的私有词表

custom model 不是「配置一个模型」，而是在库里建一张词表、回填一次存量、再用触发器持续维护。

组合函数 SQL · 素材 6.4
SELECT tokenizer_catalog.create_custom_model_tokenizer_and_trigger(
    tokenizer_name     => 'tokenizer1',
    model_name         => 'model1',
    text_analyzer_name => 'text_analyzer1',
    table_name         => 'documents',
    source_column      => 'passage',
    target_column      => 'embedding'
);
适合

业务私有召回、词表由真实语料生长；分词、词表、触发器都在库内声明，SQL 可复现。

必须评估

写路径会变重：高并发 INSERT/UPDATE 与词表增长阶段要压测；identity id 重建后会漂移。

四 / 一致性与边界 · 3.6

为什么必须走 shared_preload_libraries

_PG_init() 会检查加载时机：扩展启动阶段要初始化 jieba 和模型预加载目录，普通后端里才加载会直接报错。

收益

模型在启动阶段就绪，首次 tokenize() 不必现场加载词表，延迟更平稳。

代价

数据库启动更慢、每个后端进程内存占用更高；词表越大越明显。

DBA 动作

确认预加载模型目录符合实例内存预算；按实例角色决定是否预加载，不要一刀切。

来源：素材「3.6 启动与预加载」；路径 pg_tokenizer/preload_models/、三个函数名与默认预加载模型 llmlingua2 均照素材原文。

四 / 一致性与边界 · 效果

收益不是「分词更快」，代价也不是「装个扩展」

真正改善的是一致性、复现性、互操作、可治理；代价集中在内存、写路径、发布流程和语义误用。

改善的四件事
01 一致性

分词配置、词表、触发器和输出列都在数据库内声明。

02 复现性

同一条 SQL、同一个 tokenizer 名称，得到同一套 token id 规则。

03 互操作

接得上 VectorChord-bm25、业务 INT[] 列、HuggingFace / LLM 词表。

04 可治理

DBA 能看到 catalog 表、模型名、触发器、预加载目录，不是应用层黑盒。

五项明确代价
01 内存

模型加载占内存，预加载影响启动与进程内存。

02 写路径

custom model 词表随写入触发器增长，写路径变重。

03 发布

缓存不完全跟随事务隔离，配置发布要有流程。

04 语义

INT[] 是 token id，不是天然向量 embedding。

05 版本

不同模型 ID 空间不可混用，同一列必须固定 tokenizer 版本。

最易踩的误用

不要把 tokenizer 输出误当语义向量。token id 是离散符号，适合 BM25 / 词表输入；语义检索要用真正的 embedding 模型输出。

来源：素材「五、效果如何？」收益 4 条与代价 5 条原文。

6.2 内联 analyzer + BERT 词表 · tokenizer.slt
SELECT tokenizer_catalog.create_tokenizer('tokenizer1', $$
model = "bert_base_uncased"
pre_tokenizer.regex = '(?u)\b\w\w+\b'
[[character_filters]]
to_lowercase = {}
[[token_filters]]
stopwords = "nltk_english"
[[token_filters]]

$$);

6.3 自定义 stopwords
SELECT tokenizer_catalog.create_stopwords(
  'stop1', $$
it
is
an
$$);

SELECT tokenizer_catalog.create_text_analyzer(
  'test_stopwords', $$
pre_tokenizer = "unicode_segmentation"
[[character_filters]]
to_lowercase = {}
[[token_filters]]
stopwords = "stop1"
$$);

SELECT tokenizer_catalog.apply_text_analyzer(
  'It is an apple.', 'test_stopwords');
-- 期望输出
{apple}

停用词表按行书写；小写化必须排在停用词过滤之前，否则大写形式不会命中。

6.3 synonym 同义词归并
SELECT tokenizer_catalog.create_synonym(
  'syn1', $$
pgsql postgres postgresql
index indices
$$);

SELECT tokenizer_catalog.create_text_analyzer(
  'test_synonym', $$
pre_tokenizer = "unicode_segmentation"
[[token_filters]]
synonym = "syn1"
$$);

SELECT tokenizer_catalog.apply_text_analyzer(
  'postgresql indices', 'test_synonym');
-- 期望输出
{pgsql,index}

每行第一个词是归并目标：postgresql → pgsql、indices → index。

6.4 custom model 自动维护
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    passage TEXT,
    embedding INT[]
);

-- 先创建 text_analyzer1（见第 9 页）
SELECT tokenizer_catalog
  .create_custom_model_tokenizer_and_trigger(
    tokenizer_name     => 'tokenizer1',
    model_name         => 'model1',
    text_analyzer_name => 'text_analyzer1',
    table_name         => 'documents',
    source_column      => 'passage',
    target_column      => 'embedding'
);

生成 tokenizer_catalog."model_model1" 词表并自动维护 embedding；把触发器写入成本纳入容量评估。

来源：素材「6.3」「6.4」；期望输出 {apple}、{pgsql,index} 与第 9 页的 12 token 输出均为测试文件给定值。
六 / 治理与决策 · 七

先按业务目标选词表来源，再决定维护边界

英文 / 多语言 LLM 场景优先 builtin 或 HuggingFace；中文搜索先解决词边界；业务私有召回用 custom model。

先选词表来源：builtin / HF / Lindera / custom 决定 ID 空间，是后续所有决策的前提。

再选维护边界：谁负责词表版本、分词规则、触发器与发布流程，必须写进运维约定。

最后固定契约：tokenizer 名称当成 schema 契约，列里存的是某个版本的 INT[]。

来源：素材「七、最佳实践」图 5 与说明；「八、适合与不适合场景」用于补充各分支关注点。
六 / 治理与决策 · 七

架构师定契约，DBA 管发布，开发者守住写路径

同一套扩展，三个角色的关注点完全不同；下面每一条都能落到具体的检查项。

面向数据库架构师
  • 把 tokenizer 名称当成 schema 契约；列里保存的是某个 tokenizer 版本的 INT[]，不要无版本替换模型。
  • 对同一业务列固定 tokenizer，不要把 BERT、LLMLingua、custom model 的 ID 混在一起。
  • 明确 INT[] 的下游语义：BM25 term id、LLM token id、私有词表 id 不是同一种东西。
  • 为 custom model 设计重建路径：新模型名 → 新目标列 → 回填 → 双写校验 → 切换读路径 → 清理旧对象。
面向 DBA
  • 通过 shared_preload_libraries 加载扩展，确认预加载模型目录符合实例内存预算。
  • 配置变更不要放在长事务里反复试错；rollback 后当前连接缓存可能仍保留对象。
  • 生产发布后检查 tokenizer_catalog.text_analyzer、.model、.tokenizer 和业务表触发器。
  • 对 custom model 源表写入做压测，尤其是高并发 INSERT/UPDATE 和词表增长阶段。
  • 升级扩展前备份 catalog 配置和 custom model 表，避免词表 id 漂移不可恢复。
面向应用开发者
  • 先写最小 SQL 测试固定输出，再把 tokenizer 接进业务写路径。
  • 不要在请求路径里动态创建 tokenizer / model；创建是 DDL / 配置发布，不是普通查询。
  • 中文不要盲目套英文 stemmer；日文优先 Lindera；英文再考虑 stopwords、stemmer、synonym。
  • 用 HuggingFace / builtin 模型时，应用层与数据库层必须使用同一份模型词表版本。
  • 使用 ngram 前，用真实语料验证短 token、中文 token、emoji 和组合字符，不要只用 ASCII 测试。
来源：素材「七、最佳实践」三栏原文，共 14 条，未增删结论。
七 / 边界与坑 · 八

边界比能力更重要：先把「不用它」的情况说清楚

如果只需要传统全文检索、或需要真正的语义向量，这套扩展就不是答案。

适合 · 五种情况
01

PostgreSQL 内要保存文本 token id，并和 BM25、RAG、提示词压缩或召回逻辑协作。

02

需要在数据库内统一管理分词、停用词、同义词、词干化和业务私有词表。

03

需要复用 HuggingFace / LLM tokenizer，让数据库输出和模型词表对齐。

04

需要中文 jieba、日文 Lindera 或 PostgreSQL dictionary 参与同一条 SQL 流水线。

05

希望 DBA 能审计 catalog、触发器与预加载目录，而不是依赖应用层黑盒。

不适合 · 五种情况
01

只需要普通 to_tsvector @@ tsquery，且不需要整数 token id。

02

不能接受 PostgreSQL 扩展预加载、模型内存占用和 pgrx 运维复杂度。

03

写入极高频，且不能为 custom model 触发器付出额外开销。

04

需要深度语义向量 embedding：pg_tokenizer 输出 token id，不输出神经网络 embedding。

05

需要跨库、跨语言统一 tokenizer 服务，且数据库不应承担 NLP 配置发布。

判断口诀

「要整数 token id、且希望它和 SQL 同库管理」→ 适合；「只要传统全文检索」或「要语义向量」→ 不适合。

来源：素材「八、适合与不适合场景」；左栏第 5 条由「五、效果如何？」可治理一条归并表述，其余照原文。
七 / 边界与坑 · 九

四个最容易在生产里出事的坑

前三个都与「ID 空间」和「状态一致性」有关，属于架构级问题，不是调优能绕开的。

坑 1 · 把 token id 当 embedding

INT[] 是离散 ID 序列，不是稠密语义向量。它可以作为 BM25 / 词表输入，但不能直接替代向量检索 embedding。

后果：语义检索召回质量失真
坑 2 · 混用不同模型输出

bert_base_uncased 的 2695 和 custom model 的 2695 没有可比性。列名、注释和约束里最好体现 tokenizer 名称或版本。

后果：同一列里两套 ID 空间互相污染
坑 3 · 事务回滚后缓存残留

docs 已说明对象缓存不完全遵守事务隔离。配置实验失败后，当前连接可能还拿得到已回滚对象。规避：显式 drop_* 或重连。

后果：catalog 与运行时状态不一致
坑 4 · custom model 词表 ID 漂移

custom model 用 identity id。重建词表后，即使 token 文本相同，ID 也可能不同。索引、缓存、下游特征都要同步重建。

后果：历史特征与新词表不再对齐
来源：素材「九、常见坑」1–4 条原文；第 14 页动画演示的正是坑 3。
七 / 边界与坑 · 九

另外四个坑：长 token、非 ASCII、源码细节、动态创建

这几条更像「上线前的回归清单」，逐条都能写成一条 sqllogictest。

坑 5 · 长 token 被切分

apply_text_analyzer_for_custom_model() 对超过 MAX_TOKEN_LENGTH = 2600 的 token 会切成多段并 warning。异常长文本、base64、URL、日志堆栈要预清洗。

坑 6 · ngram 对非 ASCII 要谨慎

当前 ngram 用 token.len() 与 token[i..j] 做字节级切片。中文、emoji、组合字符或短于 min_gram 的 token 先验证，别假设是 Unicode 字符级 n-gram。

坑 7 · drop_stopwords 源码疑点

src/token_filter/stopwords.rs 的 drop_stopwords() 写的是 DELETE FROM tokenizer_catalog.Stopwords，而表名定义是小写 stopwords。PG 未加引号标识符会折叠为小写，通常不影响；但升级前要跑完整 sqllogictest。

坑 8 · 动态创建影响连接内状态

create_* 会同时写 catalog 和对象池，适合作为发布动作，不适合在业务请求里按用户输入动态创建。创建是 DDL / 配置发布，不是普通查询。

来源：素材「九、常见坑」5–8 条原文；函数名、常量值与源码路径均照素材。

结尾 / 带走三句话

词元化是契约，不是工具函数

它决定「什么算同一个可检索单元」，也决定下游所有 ID 的语义。

01 · 两层职责

TextAnalyzer 定词边界，TokenizerModel 定 ID 空间。顺序与词表版本都要固定下来。

02 · 输出是 ID

INT[] 是离散 token id，不是 embedding；BM25 term id、LLM token id、私有词表 id 不可混用。

03 · 当 schema 发布

catalog 受事务控制、缓存不受；配置变更走发布窗口，rollback 后显式 drop_* 或重连。
