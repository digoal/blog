01 · 背景

JSON 字段不是「反范式的偏好」，是业务在变

模型变化的速度高于表结构变化的速度，四类压力最常见。

DRIVER 01
第三方接口字段每周变

全部拆成列就意味着频繁 DDL、发布与兼容处理；原始报文还需要留档。

DRIVER 02
大量稀疏属性

用户画像、设备属性、风控特征、埋点事件：属性多、每行只用得到少数几个。

DRIVER 03
一部分稳定，一部分随行业与租户变

订单、工单、审计日志：主维度稳定，扩展字段按租户、按业务线各不相同。

DRIVER 04
同一事务里保存三种形态

原始报文、解析后的核心字段、少量可检索标签，希望一次写入、原子可见。

01 · 背景

没有 JSON 类型时，代价总得有人承担

三种做法各有优点，也各自把复杂度推给了数据库、应用或发布流程。

做法优点主要问题
全部存 text写入简单，完整保留原文 数据库不校验 JSON 合法性；每次查询都要解析；索引只能依赖表达式或外部处理
EAV 属性表字段扩展灵活，不需要改表 类型、约束、查询、聚合与优化器统计都变复杂；一个宽对象被拆成大量行
全部拆成关系列类型清晰、约束完整、统计最准 字段频繁变化带来 DDL、发布、兼容和历史数据成本，模型很「硬」

01 · 命题

它解决的不是「不用建模」

而是「模型变化速度高于表结构变化速度」。

01
强约束的部分

租户、主状态、时间、外键、金额：留给普通列，让类型、约束和统计系统看得见。

02
半结构化的部分

变化快、稀疏、低频访问的扩展属性：放进 jsonb 文档。

03
需要被检索的路径

稳定热点路径提成表达式 / 生成列，或交给 GIN opclass 抽 key。

代价必须先讲清楚：jsonb 不是局部更新存储。改一个路径仍走行级 MVCC 更新、行锁、TOAST 与索引维护；官方文档提醒，大文档更新会锁住整行，文档最好代表业务上不可再独立拆分的原子 datum。
02 · 它是什么

三类类型，三种不同的「存的是什么」

官方文档 doc/src/sgml/json.sgml 把 json 与 jsonb 的差异说得很直接。

TYPE 01 · 文本层
json

存储合法 JSON 输入文本的精确副本。校验合法性，但处理函数每次执行都要重新解析。

典型用途：原始报文归档、需要保留空白 / 键顺序 / 重复键的少数场景。

TYPE 02 · 二进制层
jsonb

存储解析并规范化后的二进制 JSON 树。写入稍慢，处理更快，并支持索引。

典型用途：绝大多数业务查询、包含判断、路径提取、GIN 索引。

TYPE 03 · 路径层
jsonpath

存储解析后的 SQL/JSON path 表达式的二进制表示，供 path engine 与 SQL/JSON 函数使用。

典型用途：复杂路径过滤，@?、@@、SQL/JSON 查询函数。

选型不要只问「是不是 JSON」：要问「以后是否要按路径查、按 key/value 判断、建索引、频繁处理」。答案是「是」→ jsonb；答案是「必须逐字保真」→ json 或同时保存原文。

02 · 规范化成本

这些不是 bug，是「可比较、可索引」的代价

jsonb 的输入限制比 JSON 抽象规范更贴近 PostgreSQL 自己的类型系统。

输入 INPUT
SELECT '{"b":1, "a":2, "a":3}'::jsonb;
→
规范化
输出 OUTPUT（示意）
{"a": 3, "b": 1}
① 数字映射到 numeric

JSON number 映射为 PostgreSQL numeric；超出其表示范围会被 jsonb 拒绝。

② 更严格的 Unicode 转义

拒绝 \u0000，因为 PostgreSQL 的 text 不能表示该字符。

③ 重复 key 只保留最后值

uniqueifyJsonbObject() 对 JsonbPair 排序并去重；order 记录原始顺序以确定性地去重。

④ 不保留空白与键顺序

输出顺序可能和输入不同；对象 key 按长度 / 内容排序，便于二分查找。

审计含义：若法务或回放要求逐字保真，应同时保存 json 或 text 原文，只用 jsonb 会丢失原始报文信息。

    04 · 横向对比

    这张表的核心不是「谁更先进」，是「代价放在哪里」

    维度jsonjsonb拆成关系列EAV
    主要目标保留合法 JSON 原文半结构化数据查询和索引强类型、强约束、强统计高动态属性
    写入代价低，主要做合法性检查较高：解析、规范化、构造二进制中等，取决于列和索引数量高：一条对象可能变多行
    读取代价每次处理要解析直接遍历二进制结构最低，优化器统计最完整join / 聚合复杂
    空间语义保留空白、键顺序、重复键不保留空白/键顺序，重复键最后值生效固定列属性行膨胀
    索引支持无专用 GIN 能力GIN、B-tree、hash、表达式索引B-tree、hash、BRIN 等完整能力依赖属性表索引
    约束能力JSON 合法性合法性 + CHECK / 表达式最强复杂，需额外约束
    优化器统计对整体值有限对整体值有限，路径统计需表达式 / 生成列最好分布被拆散
    适合场景原始报文、审计归档稀疏属性、标签、事件 payload高频过滤 / 连接 / 聚合字段字段极动态且查询模式简单
    不适合场景高频路径查询高频局部更新、强事务约束字段字段变化极快复杂分析和类型安全要求高
    读法：jsonb 把解析代价前置到写入、灵活性留给文档、索引能力交给 opclass；关系列把建模代价前置到 schema，换取最完整的查询与统计能力；EAV 把 schema 变化转成数据变化，却把复杂度推给 SQL 与约束。
    05 · 效果

    机制带来的方向性收益，和同样明确的代价

    本文不制造性能数字；涉及效果只说明机制带来的方向性收益与代价。

    GAIN · 收益来自哪里
    四点机制收益
    • 不必重复解析：读取路径直接遍历 JsonbContainer，按 token 流处理。
    • key 可二分查找：getKeyJsonValueFromContainer() 按长度 / 内容比较定位 key。
    • GIN 倒排：把「文档含某 key/value」变成索引查找，ops 灵活、path_ops 更具体。
    • jsonpath 谓词可抽取：一部分路径等值条件能被 jsonb_gin.c 转成 GIN 查询项。
    COST · 代价同样明确
    五点工程代价
    • 写入更慢：输入要解析和规范化。
    • 更新更重：改一个 JSON path 仍是行级更新，相关索引也要维护。
    • 索引可能很大：jsonb_ops 抽取大量 key/value，文档越宽写放大越明显。
    • 统计不完整：不把路径提成表达式 / 生成列，选择率只能走通用估计。
    • opclass 有边界：jsonb_path_ops 不支持 key exists；空对象结构无可抽取 value。
    06 · 实操 DEMO

    一张 api_event 表，串起五步索引设计

    最小实验脚本；语法与语义参考官方文档与 src/test/regress/sql/jsonb.sql 等回归用例。

    CREATE TABLE api_event ( id bigserial PRIMARY KEY, tenant_id bigint NOT NULL, created_at timestamptz NOT NULL DEFAULT now(), payload jsonb NOT NULL ); -- ① 验证规范化：键排序、重复 key 只留最后值 SELECT '{"b":1, "a":2, "a":3}'::jsonb; -- ② 整列 GIN：支撑 payload @> '{...}' CREATE INDEX api_event_payload_gin ON api_event USING GIN (payload); -- ③ ? 作用在表达式上，需要表达式 GIN 索引 CREATE INDEX api_event_tags_gin ON api_event USING GIN ((payload -> 'tags')); -- ④ 主要做 @> 时评估 jsonb_path_ops CREATE INDEX api_event_payload_path_gin ON api_event USING GIN (payload jsonb_path_ops); -- ⑤ 稳定高频路径：表达式索引或直接提成列 CREATE INDEX api_event_status_idx ON api_event ((payload ->> 'status')); CREATE INDEX api_event_tenant_created_idx ON api_event (tenant_id, created_at DESC);
    STEP 01

    先确认规范化行为，接受「不保真」这个前提。

    STEP 02

    整列 GIN 支撑 payload @> '{"company":"Magnafone","status":"paid"}'。

    STEP 03

    payload -> 'tags' ? 'postgres' 中 ? 没直接作用在索引列上，整列索引用不上 → 表达式 GIN。

    STEP 04

    workload 以 @> 为主时换 path_ops；但它无法支持 payload ? 'company'。

    STEP 05

    status 若已稳定且高频过滤，提成普通列或生成列，配 B-tree，让统计系统看得见。

    诚实声明：原文与本稿均未启动本地 PostgreSQL 实例执行这些 SQL，因此不提供伪造输出。验证方向：数据量足够大且选择率合适时，EXPLAIN 可能出现 Bitmap Index Scan + Bitmap Heap Scan；小表走顺序扫描也正常。

    07 · 最佳实践

    同一套机制，三种角色各自该盯住什么

    FOR ARCHITECT
    数据库架构师
    • 租户、主状态、时间、外键、金额等强约束与高频 join / filter 字段放普通列。
    • 变化快、稀疏、低频访问的扩展属性放 jsonb。
    • 对稳定 JSON path 建表达式索引或生成列；不要指望整列 GIN 解决所有路径查询。
    • 对文档大小设上限：大 JSONB 更新会放大行版本、TOAST、WAL 和索引维护成本。
    FOR DBA
    DBA
    • 区分两个 opclass：需要 ? ?| ?& 用默认 jsonb_ops；主要做 @> 时评估 path_ops。
    • 观察 GIN 索引体积、写入延迟、pending list 清理与 autovacuum 压力。
    • 用 EXPLAIN (ANALYZE, BUFFERS) 验证是否真走目标索引、recheck 比例是否可接受。
    • 选择率误判明显的路径：表达式统计、生成列统计，或更明确的关系列。
    FOR DEVELOPER
    业务开发者
    • 不要把 JSONB 当「随便塞」的字段：先约定顶层结构、关键路径和类型。
    • 用 jsonb_build_object()、to_jsonb() 构造，减少手写字符串拼接。
    • -> 返回 json/jsonb，->> 返回文本；比较对象和文本时不要混淆。
    • ? 不是递归搜索；嵌套匹配用 @> 或 jsonpath。更新不同路径也会争用同一行锁。
    08 · 适用边界

    哪些场景该用，哪些坑不要踩

    SUITABLE · 适合
    • 事件、日志、审计、Webhook 原始 payload，同时抽取少量稳定列。
    • 用户画像、设备属性、商品扩展属性：字段多、稀疏、变化快。
    • 标签、配置、策略条件等按 key/value 做包含查询的文档。
    • 多租户里每个租户有少量自定义字段，主查询维度相对稳定。
    NOT SUITABLE · 不适合
    • 高频更新单个小字段，且大量事务并发更新同一业务对象。
    • 强类型、强外键、强唯一约束、复杂 join 的核心交易数据。
    • 大量按路径聚合 / 排序 / 范围过滤，却没有提成列或表达式索引。
    • 文档结构完全不受控，却要求低延迟和稳定计划。
    • 必须保留空白、键顺序、重复 key 的归档数据（此时选 json 或同时存原文）。
    PITFALLS · 八个常见坑
    把机制理解错，比不会写 SQL 更贵
    • 把 jsonb 当文档数据库替代品：它仍是行存 MVCC，不是局部原地更新。
    • 整列 GIN 建完就以为所有 JSON 查询都会变快：operator 与表达式形态必须匹配 opclass。
    • -> 'status' = '"paid"' 与 ->> 'status' = 'paid' 混写，索引设计也不同。
    • 忽略 jsonb_path_ops 不支持 ?，混合 workload 需要组合索引。
    • 在 path_ops 上查 {"a":{}} 这类空对象结构，可能慢扫描。
    • 让 JSONB 文档无限长：TOAST、WAL、vacuum、缓存命中率与复制延迟都受影响。
    • 忽略路径统计：热点路径应提成表达式或列，让统计系统看得见。
    • 应用层拼 JSON 字符串：转义、数字精度、null 语义都容易出错。
