01 · 开篇 · 封面
数组不是一张藏在行里的小表

今天我们讲一个特别小的类型：array。小到很多人觉得不用讲，写一个 text[] 不就完了吗。但我想先给一个结论，也是这一整场演说要反复回到的那句话：数组不是一张藏在主行里的小表。

业务里到处都是「一个对象有多个同类值」：商品有多个标签，用户有多个候选渠道，订单命中了好几条风控规则，指标按季度存一组数，查询参数一次传一组 ID。这些场景长得不一样，但底层是同一个建模问题。

最容易做出的动作是建一张子表。可你很快会发现，为了几个标签去 join 一张表，读写的路径变重了。PostgreSQL 给了另一个选择：把这一组值塞进一个字段。听上去很省事，问题是——省掉的那部分复杂性，并不会消失，它只是换了地方。

所以这一讲不按文档目录走，我们按因果往下挖。右边这张地层图就是路线：从最底下的存储布局开始，一层层往上看类型、读写、语义、索引、统计，最后才回到建模边界。因为只有看懂最底下那一层是「单个 datum」，上面所有收益和代价才讲得通。

02 · 01 · 问题从哪来
五个场景，其实是同一个结构

先把问题摆清楚。商品标签、候选渠道、风控命中、季度指标、查询参数——这五个场景看起来毫不相干，但把它们抽象一下，都是「一个对象，配上一组同类型、数量有限的值」。

请注意三个共同点：第一，值通常不多；第二，它们几乎总是跟着主行一起被读出来，很少单独被查、单独被改；第三，很多时候顺序或者位置本身就有含义，比如第 3 个季度、第 12 个月。这三点决定了后面所有的判断。

于是建模问题就不再是「怎么存得下」，而是屏幕最下面那一句：这些值到底是主行的属性，还是应该各自成为一行？如果你把它们当属性，array 就很顺手；如果它们其实是实体——有自己的生命周期、要被别人引用、要单独审计——那用数组就是在给自己埋雷。

先别急着下结论。我们把四条常见的路摆在一起，看看每条路到底把成本放在哪儿。

03 · 02 · 四条路，四种代价
没有免费的紧凑

四条路摆出来，一眼能看出一件事：没有哪条是免费的。子表把复杂性放在额外的表、join 和写入路径上；分隔字符串把复杂性推给应用层的转义和类型判断；JSONB 换来文档灵活性，代价是元素类型变得含糊；array 换来紧凑和原生表达力，代价是——它把一组值压成了一个字段值。

这张图里我用青绿写「你得到什么」，陶橙写「你付出什么」。请大家特别看最后一行。array 那一行的青绿很长：类型明确、下标、切片、集合操作符、聚合、GIN 索引，全是 SQL 原生能力，不用自己造轮子。可它的陶橙也很明确：整个数组是一个 datum，更新往往是列值整体变化，大数组随机访问和高频局部修改都不擅长。

这里先埋一个伏笔：官方文档自己就提醒过，数组不是集合。如果你经常要搜数组里的单个元素，那可能是设计出了问题，拆成一张一行一元素的表通常更好搜、也更能扩展。所以 array 不是「反范式万能药」，它是一个边界很清楚的工具。

接下来这一页，我们把「拿什么换」讲透。

04 · 03 · 核心命题
array 是一个 datum，不是一组行

这一页是整场演说的地基，请一定记住这句话：array 是一个 datum，不是一组行。

左边是关系模型。商品 7 有三个标签，那就是三行 tag 记录，每行有自己的主键、能挂外键、有自己的 MVCC 版本和行级统计。改一个标签，只动这一行，其他两行连碰都不碰。右边是 array 模型：三个标签挤在一个 tags 字段里。这时候数据库看到的变更是什么？不是「第 2 个标签变了」，而是「这一列的值变了」。

这一字之差，后面会一路放大：行版本以列值为单位、TOAST 以列值为单位、WAL 以列值为单位、索引维护也以列值为单位。所以底下那一排叉不是缺点清单，而是 array 主动交出去的东西——元素主键、元素外键、单元素版本、元素级统计。

你可能会说，那我加个 CHECK 约束不就行了？可以，CHECK 能控长度、维度、白名单，但它替代不了外键，因为数据库根本不认为数组里有一个「行」存在。这不是实现不够好，是模型就这样。

那为什么非得是一个 datum？光讲 SQL 语法解释不了，我们得往下钻一层，看看这个值在磁盘上到底长什么样。

05 · 04 · 地层第七阶 · 存储
磁盘上，它只是一段连续的字节

好，往下钻到最底一层。PostgreSQL 源码里 array.h 定义的 ArrayType，开头四个字段：总字节数、维度数、dataoffset、元素类型 OID。紧接着是每一维的长度、每一维的下界，然后是可选的 NULL 位图，最后才是真正的数据区。

这里有三个细节值得停一下。第一，它带着维度和下界，所以它不是一个简单的 C 数组，同一个元素类型可以有一维、二维，还可以有非 1 的下界，比如 [2:4]={10,20,30}。第二，dataoffset 为 0 就表示没有 NULL 元素，连位图都不存，紧凑到这个程度；反过来说，「某个位置是 NULL」也是值的一部分。第三，元素按 row-major 排，最后一个下标变化最快，屏幕上这六格就是 ARRAY[[10,20,30],[40,NULL,60]] 的真实线性顺序。

底下三个框是源码里的硬边界：MAXDIM 是 6；数组内部不能存 out-of-line 的 TOAST 指针，因为 TOAST 只理解整个数组 datum，根本不知道里面还有元素；数组总大小也受 MaxAllocSize 约束，防止分配路径溢出。

现在关键问题来了：如果元素是变长的，我要拿第 5 个元素，怎么定位？没有固定步长，就只能从第一个开始，一个一个读长度、往后挪。下一页我们把它变成可操作的演示。

06 · 05 · 动画演示 · 访问代价
定位第 N 个元素，要走几步

这一页请大家自己动手。上面六个格子是一行示意数组，下面有两个输入：元素类型选「定长 int4」还是「变长 text」，再选目标下标 N，然后按播放，或者单步一步一步看。

选定长的时候，你会看到只走一步就直接落到目标格。因为每个元素宽度一样，offset 就是 (N−1) × typlen，算一次就跳过去。切成变长再看：要拿第 5 个，得从第一个开始，读出它的长度、挪过去，再读第二个……一路跳过前面 4 个，才到第 5 个。这不是实现偷懒，是平面紧凑布局的必然结果——你没法既省掉每个元素的长度开销，又保留随机访问。

源码里这件事由 array_get_element() 完成：先按 ndim、dims、lbound 把多维下标折算成线性 offset，再用 array_seek 跳到数据区位置。定长元素可以直接算，变长元素就得扫。

所以记住这个画面：紧凑是磁盘的优点，却是计算的缺点。后面讲 expanded array，就是 PostgreSQL 为了化解这个矛盾专门做的内存表示。而读路径尚且如此，写路径只会更贵。

07 · 06 · 地层第五阶 · 读写
读可以定位，写通常复制

顺着上一页往下看。SQL 里的 a[2]、a[2:4]、a[3] := x，先由 arraysubs.c 接住，检查下标数量和 MAXDIM，再交给 arrayfuncs.c 里的三个函数。

读这一侧挺温和：array_get_element() 折算 offset 取元素，非法下标返回 NULL；array_get_slice() 取矩形切片，越界部分被截断，结果下界重置为 1。写这一侧就不一样了：array_set_element() 的语义是「返回修改后的新数组」。只有传入一个可读写的 expanded array，才可能原地改。还有个容易踩的边界——一维数组给现有范围外的位置赋值是允许的，中间的空洞补 NULL，但多维数组没有这个扩展行为。

这时候你可能会反驳：那我每次改一个元素都要整块重写？执行期确实有优化，就是底下深蓝和浅蓝的对照。官方存储文档讲 expanded datum 时，正是拿 array 举例：标准 varlena 紧凑适合磁盘；但变长元素找第 N 个值只能扫描前面的元素。expanded 表示会把元素拆成 Datum[] 和 isnull[]，让重复访问、PL/pgSQL 变量修改少走平面格式扫描。

但请把这句听完：一旦写回表行、写 WAL、更新索引，持久化的仍是列值变化。所以「array 字段修改」不能简化理解成永远逐字节重写整块内存，也不能理解成元素级更新。大数组高频局部修改，依然不是它的舒适区。

08 · 07 · 地层第六阶 · 输入输出
输入不是切字符串，是类型驱动的解析

值是怎么进来的？很多人以为 '{a,b,c}' 就是按逗号 split 一下。不是。arrayfuncs.c 里的 array_in() 做了六件事，左边这六条就是顺序：先读可选的维度说明，检查花括号结构，通过 get_type_io_data() 找到元素类型的输入函数、分隔符、长度和对齐信息，然后 ReadArrayStr() 去解析嵌套花括号、引号、转义、NULL 和多维 extent，再算需不需要位图、数据区多少字节，最后才构造出 ArrayType。

理解了这个顺序，右边三个细节就不是冷知识了。第一，数组文本分隔符来自元素类型的 typdelim，不是硬编码逗号——大多数内置类型用逗号，box 类型用分号。第二，'{NULL}'::text[] 里没加引号的 NULL 是真正的 SQL NULL 元素，而 '{"NULL"}'::text[] 才是字符串 NULL。第三，正因为要处理引号和转义，所以它不可能是一个简单的字符串切分。

二进制输入走 array_recv()，同样检查维度上限、元素类型、NULL 标记和元素收发函数。一句话：数组不是文本协议，是类型系统的一部分。

既然说到类型系统，下一页要给几个常见的想当然泼点冷水——你写在建表语句里的那些方括号，其实大半不生效。

09 · 08 · 类型系统的五个反直觉
写在方括号里的，多半只是注释

这一页我建议大家截图，因为踩坑率最高。第一条，integer[3] 和 integer[] 在当前实现里就是同一种类型，官方文档写得很直白：当前实现忽略任何提供的数组尺寸限制，也不执行声明的维度数。所以 text[][] 里的方括号只是给人看的注释。想真的限制？写 CHECK，比如 CHECK (cardinality(a) = 3)。

第二条，默认下标是 1，不是 0——但别以为记住 1 就万事大吉，因为值本身可以携带别的下界，'[2:4]={10,20,30}' 是完全合法的值，这时候 a[2] 才是第一个元素。应用层和数据库的下标映射必须统一约定。

第三条，多维数组要求每一层 extent 一致，它是规整矩形，不能一行 2 个、另一行 3 个。第四条，array_length(a, n) 是按维度问的，空数组返回 NULL 而不是 0；要总数得用 cardinality()，空数组它返回 0。第五条偏实现：pg_type.dat 里大量 base type 通过 array_type_oid 自动派生数组类型，执行函数靠 anyarray 这类多态伪类型复用同一套 C 代码——这也解释了为什么数组能力能覆盖几乎所有元素类型。

好，值的边界说完了。下面进入更有意思的部分：数组和数组之间，怎么比。

10 · 09 · 地层第四阶 · 集合语义
包含、重叠、比较，都不按直觉来

数组有两类操作符，别混。第一类是专用集合操作符：@> 问左边是否含有右边的每个元素，<@ 反过来，&& 问有没有交集，|| 负责连接。第二类是普通比较：=、<>、<、<=、>、>=，它们按 row-major 顺序逐元素比，用元素类型默认的 B-tree 比较函数；如果内容一样但维度信息不同，维度差异决定谁排前面。

右边那一框是重点，因为每一条都能写出 bug。重复元素不特殊处理——官方文档明确举例：ARRAY[1] 和 ARRAY[1,1] 互相包含。所以 @> 不是 multiset，你没法用它表达「这个标签至少出现两次」。NULL 元素也不能按普通等值匹配，因为 array_contain_compare() 假定比较操作符是 strict；选择率估算里甚至把 column @> '{anything, null}' 估成 0，因为包含 NULL 元素无法靠普通元素相等来满足。

还有个常见混淆：x = ANY(tags) 是标量对数组元素逐个比较，tags @> ARRAY[x] 是数组包含操作，两者的优化器和索引路径完全不同。另外千万别把数组 cast 成 text 再用 LIKE 去匹配，那等于把类型语义和索引一起绕过去了。

那么问题来了：这些「有没有」的判断，在大表上怎么才能快？

11 · 10 · 地层第三阶 · GIN 倒排
把数组拆成元素，检索才有了路径

上一页的问题是「怎么才能快」，答案就是这一页：把数组拆成元素，做倒排。内置 GIN 操作符族 array_ops 只支持四个操作符——&&、@>、<@、=，这是官方文档 Table 65.3 里列明的，不多不少。

写入时 ginarrayextract() 复制数组输入，调用 deconstruct_array() 拆成元素，每个元素变成一个 GIN key，后面挂 posting list。查询时 ginqueryarrayextract() 按操作符策略设置 searchMode：&& 默认搜索，至少一个非 NULL 元素命中即可；@> 查询数组非空时默认搜索，空数组要用 ALL 模式，因为所有数组都包含空数组；<@ 用 INCLUDE_EMPTY 并且要 recheck；= 空数组时也一样，还要 recheck。

为什么 <@ 和 = 一定要复查？因为倒排只能告诉你「候选行含有某些查询元素」，它没法证明「这个数组没有别的元素」，更没法证明维度、重复、NULL 这些整体语义完全相等。那部分得回表看真实值。

还有一条特别重要，写在最下面：MVCC 可见性不在 GIN key 里。所以真实计划通常是 Bitmap Index Scan 加 Bitmap Heap Scan，GIN 不是覆盖索引。谁要是跟你说「建了 GIN 就不用回表了」，那是对索引结构有误解。

12 · 11 · 动画演示 · 倒排与复查
谁命中，谁必须回表复查

这一页也请大家动手。左边六行是示意数据，右边是写入时生成的倒排 key。下面有两个输入：查询标签，可以直接改，比如输入 gin, cache；操作符可以选 @>、&& 或者 <@。按播放，一行一行看。

选 && 的时候，只要有一个查询元素命中，这行就变成候选；选 @>，要求查询里每个元素都在这一行的 tags 里，条件明显更严；切到 <@，语义整个翻过来，变成「这一行的所有标签是否都在查询集合里」。而下方的结论框会跟着变：前两个操作符 recheck=false，key 命中就能判定；<@ 会亮起陶橙，提示 recheck=true——必须回表确认数组里没有别的元素。

所以倒排索引擅长回答的是「哪些行出现过这些元素」，它不擅长回答「这个数组整体是什么样」。这就是 GIN 的能力边界，也是为什么 = 和 <@ 一定要复查。

不过还有个更现实的问题：就算建了 GIN，优化器也可能不走它。下一页讲决定权在谁手里。

13 · 12 · 地层第二阶 · 统计与计划
优化器不只看数组整体，也看元素分布

建了 GIN 不等于一定会走 GIN。优化器要估选择率，而估算依赖统计信息。PostgreSQL 为数组列准备了专门的 typanalyze，这一点很多人不知道。

链路是这样：array_typanalyze() 先调标准的 std_typanalyze，保留数组整体比较需要的标量统计；然后找到元素类型的等值、比较、hash 函数；在 compute_array_stats() 里采样，跳过 NULL 数组和过宽数组；用 Lossy Counting 跟踪常见元素，写进 MCELEM，再写一份 DECHIST，表示每行不同元素数的直方图。有个细节特别能体现设计的一致性：每一行内重复出现的同一元素只计一次——因为 @>、<@、&& 本来就不关心重复次数。

为什么非得统计元素？因为整数组合很少重复，但单个标签可能高度重复。只把整个数组当成一个标量，tags @> ARRAY['sql'] 的估算会很离谱。

然后是边界：arraycontsel() 只处理 Var op Const 或 Const op Var，右侧必须是常量、元素类型要对得上，统计还得可用；否则回退默认值——@> 和 <@ 是 0.005，&& 是 0.01。join 选择率函数 arraycontjoinsel() 目前还是 stub，也返回默认值。所以批量导入标签之后不 ANALYZE，计划跑偏一点都不奇怪。

到这里，从存储到计划的机制就讲完了。我们把线索收回来，回答最开始那个建模问题。

14 · 13 · 横向对比
四种结构，各守各的边界

这张表把四种结构摆在一起：SQL array、一行一元素的子表、JSONB 数组、tsvector。八个维度，我建议大家不要逐格背，只看两条主线。

第一条是元素类型与细粒度。array 强类型、同类型、下标和切片原生；子表强类型但可以多列，外键、唯一、行级约束都很强；JSONB 允许混合，代价是运行期检查；tsvector 装的是 lexeme 加位置和权重，根本不是业务值。第二条是更新的粒度。array 改一个元素不自然，本质是改整个 datum；子表改一行是天经地义；JSONB 有函数能改文档，但仍然是文档值；tsvector 压根不适合业务更新。

再往下看搜索和顺序：array 靠 @>、<@、&& 加 GIN 做集合过滤；子表靠普通索引和 join 最灵活；JSONB 有自己的 GIN 操作符；tsvector 服务的是全文语义。如果你要分词、词形归一、权重、短语、排名，千万别拿 text[] 冒充全文索引。

表格最底下那句就是全篇的判断标准：这个「多值」是不是独立业务实体？是，就拆子表；只是主行的有限集合属性，array 更直接。下一页把它画成一条能照着走的决策路径。

15 · 14 · 地层第一阶 · 建模边界
照着这条路径，就能定下来

把上一页那张表压成一条路径。起点是「一个字段有多个同类型值」，第一个判断是元素有没有独立生命周期：要不要外键、要不要行级审计、要不要单独权限、是不是高频按单元素增删改。只要有一个是「要」，往左走，拆子表，别犹豫。

如果答案都是「不要，它们只是主行的属性」，往下走第二个判断：你要的是文档结构还是全文语义？要文档结构、键存在性、嵌套检索，去 JSONB；要分词、词形归一、权重、短语、排名，去 tsvector。都不需要，右边那个绿框才是 array——而且别忘了配套动作：用 CHECK 固化维度、长度、白名单，用 GIN 支持集合过滤。

这条路径背后其实只有一个判断口径，就是最底下那句：数组越长、更新越频繁、约束越复杂、查询越像 join，就越应该拆子表或者换专门类型。array 的合理边界从来不是「能不能存多个值」——当然能——而是「这些值该不该成为关系模型里的独立行」。

好，假设你现在决定用 array 了。最后几页我们讲怎么把它用对：先算清代价，再落到 SQL，最后是三类角色各自该守的规矩和最容易踩的坑。

16 · 15 · 算清代价
三条收益，五条代价，同一个根源

决定用 array 之后，先把账算清楚。上面三个绿框是收益：模型紧凑，小集合随主行保存，读一行就拿到完整属性；表达力直接，下标、切片、unnest()、array_agg()、@>、&& 全是 SQL 原生；索引可用，GIN array_ops 能把元素集合过滤变成倒排访问。

下面五条陶橙是代价，请逐条对照自己的场景：写放大，更新数组元素通常意味着列值变化，行版本、TOAST、索引维护、WAL 一起动；CPU 扫描，没索引或要函数遍历时元素仍得逐个比，变长元素定位更贵；统计边界，数组统计主要帮常量查询的 @>、&&、<@，复杂表达式和 join 估算可能退回默认值；索引维护，一行数组产生多个 GIN key，元素越多，写入、pending list、VACUUM、查询合并越重；最后是语义边界，重复、NULL、维度、下界都不按直觉来。

中间那条深蓝横带是这一页真正想说的话：所有收益和所有代价，都来自同一件事——它是单个 datum。你不可能只拿前半句。

还有一句必须讲：不要给 array 编造固定性能数字。真实效果取决于数组长度、元素类型、NULL 比例、重复度、选择率、GIN pending list、表膨胀、缓存命中率和 autovacuum 状态。要结论，就自己压测。

17 · 16 · 落到 SQL
一条最小可验证的落地链路

左边这段 SQL 是最小可验证示例，四步：建表时给 tags 加 CHECK 控长度；建 GIN 索引；ANALYZE；然后 EXPLAIN (ANALYZE, BUFFERS) 看计划。素材里还有更完整的一组，包括插入三行示意数据、查 @> 和 &&、用 unnest() 转回关系形态再聚合，以及用 CHECK 表达「一维、最多 8 个、只能取白名单值」的用户渠道表。

右边四步正好对应我们前面讲过的机制层。第一步约束，是把「有限集合」这个建模假设写进数据库，而不是留在文档里。第二步 GIN，是给高频集合过滤一条访问路径。第三步 ANALYZE，是让优化器有元素级统计可用。第四步 EXPLAIN，是承认一件事：索引建了，优化器也未必选，尤其在小表上继续走 Seq Scan 是完全合理的。

两个提醒。想观察 GIN 路径，可以扩大数据量，或者临时 SET enable_seqscan = off 看备选计划；但正式压测绝对不能拿关掉 Seq Scan 的结果当性能结论。另外，素材明确说了没有在当前环境启动实例执行这些语句，所以这里不提供任何伪造输出——这一点我很赞同，编出来的执行结果比没有结果更糟糕。

最后一个信号：如果你的查询里经常出现 unnest(i.tags) 然后去 join、聚合、过滤，那本身就是重新评估建模的信号，说明关系模型可能该显式建子表了。

18 · 17 · 最佳实践
三类角色，守的是同一条边界

把前面所有机制收成三类角色能直接执行的动作。

架构师这边，四条：把 array 定位成有限集合属性，元素有没有独立生命周期是分界线；用 CHECK 固化维度、长度、白名单和空数组约定；如果元素来自另一张业务字典表且必须强一致引用，优先拆子表；需要自然语言检索、分词、排名、短语，就用 tsvector 或外部搜索系统，别拿 text[] 硬扛。

DBA 这边，四条：高频 @>、&&、<@ 建 GIN；批量导入或元素分布变化后 ANALYZE，必要时把统计目标提到 1000；盯住 GIN 索引大小、pending list、autovacuum、表膨胀和 WAL——长数组频繁更新会把问题转成索引维护和版本清理；排查计划同时看 EXPLAIN (ANALYZE, BUFFERS) 和 pg_stats 里的 most_common_elems、most_common_elem_freqs、elem_count_histogram。

业务开发者这边，四条：优先用 ARRAY[…] 构造，别手写复杂字符串 literal；分清 NULL 元素和字符串 NULL；别默认下标从 0 开始；记住 @> 不是包含相同次数，ARRAY[1] @> ARRAY[1,1] 为真。还有一条判断信号：如果你经常 unnest() 之后 join、聚合、过滤，就该重新考虑拆子表了。

你会发现三列说的是同一句话：把 array 当属性用，别把它当明细表用。

19 · 18 · 常见坑
十个坑，其实是一个坑

素材里列了十个常见坑，我没有照抄顺序，而是按成因重新分成三组。

建模坑四个：把 integer[3] 当约束、把数组当集合表、数组太长、把 GIN 当覆盖索引。语义坑四个：忽略 NULL、误解重复元素、默认 0 下标、用 LIKE 去查数组输出文本。查询与运维坑：混淆 x = ANY(tags) 与 tags @> ARRAY[x]、忘记 ANALYZE、以及 unnest() 后高频 join。

其中我最想强调两条，因为它们最隐蔽。一条是 GIN 不是覆盖索引：它保存元素 key，不保存完整数组值，也不保存 MVCC 可见性，所以实际查询常常要访问 heap。另一条是 忘记 ANALYZE：GIN 只是提供了一条访问路径，优化器选不选它，取决于选择率估算准不准——你建了索引却不 ANALYZE，等于把决定权交给默认值。

但请看最底下那句：十个坑其实是一个坑，都在把「单个 datum」误当成「一组行」。只要第一性原则立住了，绝大多数坑不用背，自己就能推出来。这也是我们为什么花整整五页从存储布局往上讲。

20 · 19 · 收束
回到最初那一句

最后收束。左边青绿是适合 array 的场景：标签、枚举集合、候选状态、少量渠道和特征开关；固定位置的数值序列，比如一年 12 个月指标、四个季度值；SQL 参数传递，WHERE id = ANY($1::bigint[])；小集合过滤配合 GIN；还有 array_agg() 表达聚合结果。它们的共通点是：小、同类型、随主行读写。

右边陶橙是不适合的：元素多、增长无上限、频繁按单元素增删改；元素需要外键、唯一、行级权限、审计或独立状态；查询主要是 unnest() 后 join；要按元素位置做复杂范围查询或排序分页；需要分词、归一、权重、短语、排名这类全文语义；需要精确表达重复次数的 multiset 语义。

留三个问题给大家带回去想：第一，如果 text[] tags 平均 5 个元素，但 1% 的行有 5000 个，GIN 索引和选择率估算会受什么影响？第二，为什么 array_typanalyze() 要对一行内重复元素去重后计数，这和 @> 的语义有什么关系？第三，如果业务要「某标签至少出现两次」，array 操作符还能直接表达吗？——答案显然是不能，因为从第一页我们就知道它不是 multiset。

回到开场那句话收尾：array 是主行的有限集合属性，不是一张藏在主行里的小表。看懂了「单个 datum」在磁盘上的样子，它的所有收益、所有代价、所有坑，其实都可以自己推出来。这一讲就到这里，谢谢。
