01顺序扫描 Seq Scan

这一场我们只讲一件事：顺序扫描，也就是执行计划里那四个字，Seq Scan。

它太朴素了，朴素到很多人一看见它就紧张，觉得一定是索引没建好、一定是数据库偷懒。

但今天我想换个讲法：先不问它快不快，先问它到底在替我们解决什么问题。

你看屏幕上这七层，从上往下是 SQL、计划器、计划树、执行器、表访问接口、heap 页面，最后才是缓冲区和磁盘。越往下越接近物理。顺序扫描不是某一层的小技巧，它是把这条链从头走到尾的一种走法。

所以这场演说会沿着这条地层一路往下挖：先看清它和索引怎么分工，再看清它为什么不能少读页，然后进到页面里看可见性判断，最后看系统怎么保护缓存、怎么让多个扫描共享 I/O。

挖到底你会发现，判断一个 Seq Scan 好坏，靠的不是情绪，是四个很朴素的问题。

02明明建了索引，为什么还是 Seq Scan？

先摆三个现场，你大概都遇过。

第一个：索引明明建了，EXPLAIN 里还是 Seq Scan。开发同学第一反应是「索引失效了」，于是开始重建索引、改写法、甚至把 enable_seqscan 关掉。

第二个：大表报表、批处理、count(*)、再加几个低选择率的状态过滤，一起把 I/O 打满。DBA 站在监控前面，不知道该调 SQL、调参数、加索引，还是干脆分区。

第三个：好几个并发的全表扫描互相污染缓存，或者加了并行 worker，吞吐却没按预期上来。

这三件事看起来毫不相干，其实都在问同一句：这一次扫描到底读了多少东西，为什么非读不可？

我们习惯在结果层看它——返回了几行、慢了几秒。可数据库是在成本层做决定的——读几页、怎么读、每行算几次。

把视角从结果层挪到成本层，这三个现场就变成同一个问题的三种表现。

03判断它，而不是消灭它

所以这一场的目标，先说清楚：不是教你怎么消灭 Seq Scan，是教你怎么判断它。

文章里有句话我很喜欢——它的价值在于知道什么时候是正确答案，什么时候是事故信号。这两者长得一模一样，都是执行计划里一行 Seq Scan，区别全在上下文。

屏幕上这七层是我们今天的路线。最上面两层是定位：索引解决什么、它解决什么，以及那个最容易被误会的事实——WHERE 到底管不管读页。

中间三层是机制：主路径、代价模型、页面内发生了什么。

再往下两层是系统保护：大表怎么不冲掉缓存，多个扫描怎么共享 I/O，怎么把块分给并行 worker。

最底下一层是落地：横向对比、收益代价、可验证的实验，还有分角色的最佳实践。

有个规律先记着：越靠下的层，越接近物理，也越接近你能在 EXPLAIN 里看到的事实。我们就从上往下走。

04索引解决「少读」，它解决「读得稳」

先把分工摆正。索引解决的是「怎样少读」——用索引条件把无关的页面跳过去，只回头取需要的那几行。

顺序扫描解决的是另一个同样常见的问题：当查询必须读很多行、很多块，或者根本没有可用索引的时候，怎样把这一整遍读取做得稳定、可预测、少折腾缓存。

你看右边这三条：按物理块顺序读，对预取友好；启动成本低，不用遍历索引、不用构建 bitmap；代价是不能跳页，全表或整个分区都得过一遍。

左边索引那条：精确定位、能跳页，但回表是随机 I/O，而且启动要先走索引。

注意底下这条金色横带——优化器永远按成本选路径，两条曲线谁低谁上。这里没有「高级」和「低级」，只有「这次访问形状更适合谁」。

所以看到 Seq Scan 别急着下结论，先问：这次是要读一小撮，还是要读一大片？

不过在回答这个问题之前，有个事实必须先厘清，它比选择率更基础。

05WHERE 减少的是「返回行」，不是「读取页」

这是全篇最重要的一页，请多看两眼。

上面这一排是堆表的页面，示意画了十个。顺序扫描开始之后，这十个页面一个都不能少，全部要进缓冲区、全部要被检查。底下那行字写着：顺序 I/O 贯穿全部块。

中间三格是每一条候选行都要过的关：页级准备、MVCC 可见性、qual 与投影。

橙色这条虚线才是 WHERE 真正生效的地方——它作用在「行」上，逐行判断要不要往上传。

最下面：绝大多数行被过滤掉，只有很少几行真的返回给上层。

所以你会看到那个最让人困惑的现象：结果只有三行，EXPLAIN 里却有全表的Buffers hit 和 read。

原因不是数据库笨，是它压根没有「跳过页面」的能力。WHERE 是出口的闸门，不是入口的闸门。

这一条如果记住了，后面所有现象都能推出来：为什么低选择率过滤还是全表扫，为什么表膨胀会拖慢它，为什么加索引有时救不了报表。

那既然读页这件事无法回避，数据库就得把「读一整遍」这件事做得尽量聪明。我们先看是谁在做。

06它不是「for 循环读文件」

很多人心里的顺序扫描，就是一个 for 循环：打开文件、从头读到尾。

真实的 PostgreSQL 里，它首先是一个计划节点：优化器决定「用顺序扫描划不划算」，并生成 SeqScan 计划节点，把过滤条件放进 scan qual。

它同时是一个执行器节点：ExecInitSeqScan 初始化状态，SeqNext 一次取一行，交给上层。

而在这两层之下，屏幕这九件事都得同时处理：快照与 MVCC、buffer pin 和 lock、页面剪枝、批量可见性判断、I/O 预取与 read stream、同步扫描起点、并行块分配、执行器 qual 过滤，还有 projection 目标列。

这个清单很重要，因为它解释了后面一个现象：为什么同样「扫一遍表」，有的表特别慢。

慢往往不慢在读，慢在读进来之后这一堆判断。行越宽、死元组越多、表达式越复杂，这一层就越重。

所以别把它想成一个 I/O 动作，它是一个带着完整 MVCC 语义的执行器节点。

接下来把这条路径摊开，看看一行数据究竟怎么从 SQL 走到你手上。

07从 SQL 到元组，路径很短、层次不少

这条主路径其实很短，但层次不少。

上面一排：优化器在 allpaths.c 里先考虑 seq scan 路径，接着生成 SeqScan 计划节点，把 qual 挂上去；执行器这边 ExecInitSeqScan 初始化，SeqNext 一次取一行；再往右是通用表接口 TableAM。

关键在这一句：SeqNext 不直接理解 heap 文件长什么样，它只调 table_beginscan 和 table_scan_getnextslot，拿回一个 tuple slot。

然后才往下折到 TableAM 的默认实现：heap 扫描描述符记下 startblock 和 nblocks，页面读取走 read stream 和共享缓冲区，页面内再遍历 line pointer、判断可见性、算 qual、做投影。

为什么非要分这么多层？因为换一种表访问方法的时候，执行器几乎不用改。这也是 PostgreSQL 能把 heap、列存扩展、外部表都塞进同一套执行器框架的原因。

底下那行小字也别漏：每次只返回一个可见且满足条件的 tuple slot，父节点可能提前停止，比如 LIMIT。

所以「全表扫」不等于「一定要算到最后一块」——但那是上层节点的决定，不是扫描节点自己会跳页。

层次清楚了，我们把它们对到源码上，看看每一层究竟落在哪个文件。

08沿着地层往下，就是调用链往下

这一页是给愿意翻源码的人留的地图，也是这一场「地层」这个形式的来处。

最上面 L7 是 allpaths.c 的 set_plain_rel_pathlist：它先考虑 TID scan，再添加 seq scan，再考虑并行 seq scan，最后才考虑各种 index paths。注意顺序——顺序扫描是兜底路径，永远在场。

L6 是 pathnode.c 的 create_seqscan_path，把 pathtype 设成 T_SeqScan，pathkeys 设成 NIL。这个 NIL 后面会反复出现，它意味着顺序扫描不提供任何天然顺序。

L5 是 costsize.c 的 cost_seqscan，算页面成本、CPU 成本和并行修正。

L4 是 createplan.c 生成计划节点，把过滤条件放进 scan qual。

L3 是 nodeSeqscan.c 的 SeqNext，首次调用创建 TableScanDesc，之后一行一行取。

L2、L1 是 TableAM 接口和 heapam.c 的实际实现：页级扫描、可见性、bulk-read strategy。

09它算的不是「读几行」，是「读几页、算几次」

来看优化器的账本。简化之后是四个部分。

第一块，磁盘运行成本：seq_page_cost 乘 rel.pages。注意是表的全部页数，跟 WHERE 一点关系都没有。

第二块，CPU 扫描成本：cpu_tuple_cost 加上 qual 的单行成本，再乘全表 tuple 数。也是全量。

第三块，输出表达式成本：按估算的输出行数算，这部分才跟返回多少行有关。

第四块，并行修正：CPU 成本按 worker 分摊；源码注释说得很直白，I/O 成本暂不明显分摊，因为操作系统已经会做 aggressive prefetching。

10为什么要取的行越多，索引越容易输

把两条曲线画在一起，那个「反直觉」就变成常识了。

靛青这条是顺序扫描：几乎水平，因为读多少页是恒定的，只有 qual 的 CPU 随行数微微上抬。

陶橙这条是索引扫描：随要取的比例一路往上抬。原因不是索引本身变慢，而是取的行一多，随机定位加回表随机读加可见性判断，累计代价会迅速超过一遍顺序读。

两条线的交叉点，就是分界。左边索引便宜，右边顺序扫描便宜。

这里必须强调一句：这是示意曲线，不是实测数据，我没有编任何性能数字。而且这个分界点非常不稳——random_page_cost 调小、缓存命中变好、行更窄、visibility map 更友好、并行能分摊 CPU，它都会往右移；反过来就往左移。

所以别背「超过百分之多少就该全表扫」这种口诀，那不是数据库的工作方式。

优化器每一条 SQL 都重新算一次账，依据是你这台机器的参数、这张表的统计信息。

账算完了，接下来就该真干活了：一个页面被读进内存之后，到底发生了什么。

11一个页面被读进来，还要过三关

现在进到页面里。

左边是一个 heap 页面的示意：上面是 Page Header 和 line pointers，底下是一格一格的 tuple。绿色是对当前快照可见的，橙色是死元组，白色是空闲的 line pointer。

右边三关，按顺序走。

第一关，页级准备。如果用 page-at-a-time 模式，heap 会先准备当前页面可见 tuple 的 offset 数组；页面 all-visible 且不在 hot standby 特殊场景时，还能走更快路径。

第二关，MVCC 可见性。每个候选 tuple 都要按快照判断一次。

第三关，执行器的 qual 和投影，也就是 WHERE 表达式和目标列。

真实实现里还有个更快的分支：如果页面 all-visible，并且不在 hot standby 的特殊场景里，可见性判断本身可以大幅省掉。

但可见性只是成本的一项。就算读同样的页数，不同数据形状下，这一遍扫描的账单也可能差很远。

13同样「读一遍」，账却不一样

左边写着「同样读一遍表」，页数一样。但右边这四个放大器一开，账单立刻不同。

表膨胀和死元组：页面读进来了，还得判一次不可见，I/O 和 CPU 一起白花。

宽行：每页能放的 tuple 变少，同样行数就要读更多页——连第一项磁盘成本都跟着涨。

复杂表达式：每行多算一次 qual，乘上全表 tuple 数，是个很可观的乘法。

投影列多：tuple deform、内存搬运、网络输出，以及上层排序聚合，全都跟着变重。

右边那个橙框把这些汇总成一份「CPU / I/O 账单」。

这一页想纠正一个很常见的估算方式：拿行数乘一个固定单价去估全表扫描，几乎一定会估偏。

因为真正的单价是由数据形状决定的。所以 DBA 排查慢查询时，除了看计划，还得看 n_dead_tup、看行宽、看表达式复杂度。

好，个体层面的成本讲完了。接下来往上抬一层：一次大扫描，会不会把整个系统拖下水。

14大表扫描不该冲掉整个 shared_buffers

这一页也配了动画，先说它演示什么。

左边是无保护的情况：一次大扫描逐格把 shared_buffers 覆盖掉，青绿色的 OLTP 热页被一格格挤出去。右边启用了 BAS_BULKREAD：热页留在池里不动，扫描读进来的页只在下面那个小环里循环覆盖。

改一下输入里的扫描页数，按播放或单步，看左下角「热页保留」的数字怎么掉，右边怎么一直保持满格。按重置可以重来。

再强调一次：这是机制示意，格子数不是真实缓冲区块数，也不是实测数据。

真实实现里，freelist.c 的 bulk-read ring 基础大小从 256KB 起，会结合 effective_io_concurrency、io_combine_limit 和 pin limit 调整，但最终受 shared_buffers 的 1/8 上限约束。

这个设计的措辞要记准：它不是「让全表扫变快」的手段，是「让全表扫别把系统拖垮」的保护。大扫描需要吞吐，但不该把 OLTP 的热页全部挤出去。

理解了「一个扫描别添乱」，下一页反过来问：好几个扫描能不能别各读各的，干脆一起读。

15几个人扫同一张表，尽量读同一批页

这一页的动画值得放一遍。

一排是表块，上面几个小色条是不同后端的扫描位置。已有扫描已经走到中间，新来的扫描不从表头开始，而是从它附近起步，然后大家一起往前走；走到末尾，沿着下面那条 U 形回环 wrap 回表头，把前面跳过的块补上。

输入可以设 2 到 4 个并发扫描，播放、单步、重置都在下面。你会看到几个指针尽量待在同一批块附近——这正是共享 I/O 的意思。

syncscan.c 的注释说得很直接：目标是让每个页面被读入共享缓冲区之后，参与扫描的后端都能在它被淘汰前处理掉它。

实现上并不强制所有扫描同速，只维护一个小的共享 LRU 位置表，进度也只按间隔上报，避免锁竞争。

它和论文 Cooperative Scans 的思想有相似处——扫描之间共享运行时内存和 I/O；但 PostgreSQL 的实现轻得多，只是「挑个接近已有扫描的起点」，不是完整的请求重排和调度框架。

听起来全是好处。可「从中间开始」这五个字，藏着一个很实际的副作用。

16省了 I/O，也让返回顺序更不可测

看上面两排。

第一排是物理块，橙色那格是第 10 块——同步扫描挑的起点。第二排是应用可能观察到的返回顺序：10、11、12 一直到末尾，然后接 0、1、2 回到前面。

如果业务代码悄悄依赖了「先插的先出来」，这一刻就会出问题：分页翻页会重复、会漏，报表顺序会变。

但我要替数据库说句公道话：这不是同步扫描制造的 bug。SQL 从来没有承诺过无 ORDER BY 查询的返回顺序，只是以前每次都从表头扫，碰巧稳定，大家就把巧合当成了契约。

官方文档对 synchronize_seqscans 明确提醒了这一点，而且这个参数默认是 on；设成 off 能回到「总是从表头开始」的旧行为，代价是失去 I/O 共享。

所以正确动作只有一个，写在右边绿框里：所有分页、所有依赖顺序的 SQL，都老老实实加 ORDER BY，而且要加稳定的排序条件。

这一条我建议直接写进团队的 SQL 规范。

好，并发「一起读」讲完了；大表还有一种完全不同的思路——干脆分着读。

17不是每个人都扫全表，是分块

并行顺序扫描最容易被人想成「开三个进程，各扫一遍全表」，那就成了三倍 I/O。

实际不是。上面是 Gather，下面几个 worker 共享同一份扫描状态 DSM，里面记着 phs_startblock、phs_nallocated。

每个 worker 通过原子 fetch-and-add 领一段连续的块范围，领完扫，扫完再领下一段。底下那一排 chunk 就是被领走的块。

用动画放一遍：设 2 到 4 个 worker，播放或单步，你会看到块被轮流染色，但从不重复，而且每个 worker 拿到的是连续的一段。

为什么非要连续？tableam.c 的注释解释了：早期如果每次只给下一个最高块号，不同进程会把连续 I/O 模式打散，操作系统的 readahead 就白做了。扫描接近末尾时再逐步缩小 chunk，减少长尾等待。

但别在这里期待线性加速。I/O 已经饱和、leader 汇聚结果、worker 启动、tuple 向上传输、上层还有聚合和排序，任何一处都能成为瓶颈。

加 worker 之前，先看它到底卡在哪一层。

到这儿，单个 Seq Scan 里里外外都拆完了。最后要把它放回全局：和其他扫描方法摆在一起，怎么选。

18不是谁高级谁快，是谁更贴合访问形状

把五种方法放到一张决策网格里。

输入是 WHERE、ORDER BY、LIMIT 和统计信息；中间只问一句：能先缩小物理访问范围吗？

能，而且只要很少几行，走 Index Scan；能，但命中中等规模、或者多个条件要合并，走 Bitmap Heap Scan，先用索引定位块，再按块访问 heap；能，而且索引就覆盖了要的列、visibility map 也友好，走 Index Only Scan，尽量不回表。

不能——要读全表或者很大比例，或者压根没有可用索引——那就是 Seq Scan。

底下还有一层：表很大、查询又并行安全，再考虑 Parallel Seq Scan 或者分区裁剪。分区裁剪其实是把「顺序扫描一个大表」变成「顺序扫描一个小分区」，思路和索引不一样，但目的一样：减少要读的块。

文章里那张对比表还列了排序能力和 MVCC 成本，结论都从同一个原则长出来：优化器在比较「读多少块、怎么读块、CPU 处理多少 tuple、能否提前停止、是否需要排序」。

所以千万别把 Seq Scan 简化成「没用上索引」。很多时候它是成本模型的理性选择；当然，统计信息错了、参数不贴硬件、表膨胀严重，这个理性选择也会变坏。

19收益是吞吐，代价是「不能跳」

把收益和代价并排放，你会发现它们不是两份清单，是同一件事的两面。

左边：顺序 I/O 和预取友好所以吞吐稳；不用遍历索引、不用构建 bitmap 所以启动成本低；全表聚合、低选择率过滤、小表查询很直接；还可以用 bulk-read ring 保护缓存、用同步扫描共享 I/O、用并行分摊 CPU。

右边：读取范围通常是整个表或整个分区；WHERE 不能跳过页面；宽行、死元组、表膨胀会同时放大 I/O 和 CPU；没有天然排序，ORDER BY 通常还得再 Sort；对 OLTP 点查可能是灾难信号；同步扫描还会改变无序查询的观察顺序。

你把左右对起来看：左边每一条收益，几乎都来自「老老实实连续读」；右边每一条代价，几乎都来自「不能跳」。

顺带提一句可观测性的新东西：PostgreSQL 19 给使用 ReadStream 的扫描节点加了 EXPLAIN (ANALYZE, IO)，能看到预读距离、I/O 请求大小和并发情况，对 Seq Scan 特别有用。但这是新版本能力，生产环境能不能用，以你实际版本的文档为准，别在 Older 版本上照抄。

判断的抓手就一句：右边这六条里，哪一条正是你线上正在发生的。要回答它，就得动手测。

20五个实验，一条 EXPLAIN 观察链

这一页是回去就能做的五个实验，按顺序排成一条观察链。

6.1 建一张二十万行的表，ANALYZE 之后跑 count(*)。没有过滤条件，优化器通常只能扫描全表；是否并行取决于表大小、max_parallel_workers_per_gather 和并行成本参数。

6.2 给 status 建索引，再查 status = 1。这个列只有五个值，大约命中 20% 的行，优化器很可能仍然选 Seq Scan。这时候别急着喊索引失效，先查统计信息、表膨胀、缓存状态、random_page_cost 和 effective_cache_size。

6.3 换成 id = 1000 的主键点查，正常应该走 Index Scan。如果还是 Seq Scan，常见原因是类型不匹配、列上套了表达式、统计信息异常、索引不可用，或者测试表太小导致顺序扫启动成本更低。

6.4 打开 enable_seqscan = off 再 EXPLAIN，看它到底有没有变。

6.5 查 pg_stat_user_tables，用 seq_scan 和 seq_tup_read 找哪些表经常被顺序扫。但别只看计数下结论：小表频繁 seq scan 完全正常，大表 seq_tup_read 暴涨才需要结合业务时间窗和 I/O 指标分析。

底下那句金色的话请记住：这些 SQL 我没执行，所以这里一个输出结果都没有，也不该有。你自己的环境才是答案。

21它是诊断工具，不是优化手段

6.4 那个实验值得单独讲，因为它是初学者最容易踩的坑。

左边橙框是很多人的心理模型：把开关一关，数据库就被迫走索引了。文档说得很清楚，这个理解不成立。

真实发生的是右边三步：第一，关掉开关只是给 Seq Scan 路径加上极高的代价惩罚；第二，只有当确实存在其它访问路径时，优化器才会改选；第三，如果没有其它方法能读这张表，它照样生成 Seq Scan——因为总得有个能跑的计划。

你在 EXPLAIN 里会看到那个计划成本高得离谱，新版本还会显示 disabled node 信息，但节点本身还在。

所以它的正确用途是诊断：我想看看「假如不用顺序扫描，优化器会选什么、代价差多少」。看完了 RESET 回来。

真正该改的是底下绿框那几件事：定期 ANALYZE、校准 random_page_cost 和 effective_cache_size、补合适的索引或改写 SQL、控制表膨胀。

一句话：参数能帮你问问题，不能替你修数据。

那到底谁来改、改什么？按三个角色分开看最清楚。

22架构师管形状，DBA 管事实，开发者管写法

把最佳实践按角色拆开，是为了让每个人知道自己那一刀该砍在哪。

架构师管形状：如果业务天然按时间、租户、区域访问大表，优先考虑分区或冷热拆分，让「顺序扫描一个小范围」替代「顺序扫描整个大表」；报表型查询别指望二级索引救命，低选择率、多列聚合、宽表扫描更需要列裁剪、物化汇总、只读副本或者 OLAP 系统；建模时控制行宽；让 seq_page_cost、random_page_cost、effective_io_concurrency 这些参数贴近真实硬件。

DBA 管事实：看到大表 Seq Scan 先跑 EXPLAIN (ANALYZE, BUFFERS)，分清是读块多、过滤多、排序多、并行不足还是估算偏差；定期 ANALYZE，关注相关列和表达式统计；控制表膨胀；用 pg_stat_io 这类视图区分 shared buffer 命中和物理读。

开发者管写法：别写「返回几行却扫全表」的 SQL，典型风险是列上套函数、隐式类型转换、前导 %LIKE、低选择率状态列、缺分区键条件；所有分页必须有稳定排序；只取需要的列；LIMIT 当成优化机会但别神化它。

三列不是三份清单，是同一条链路。

23该用它的地方，和该警惕它的地方

有了动作，还得知道边界在哪。

左边适合：小表查询，索引收益不明显；全表聚合、全表导出、批处理校验；谓词命中大比例行，比如状态列、布尔列、低基数枚举列；分区裁剪之后扫描单个小分区；并行安全的大表扫描和报表；还有建索引、VACUUM、ANALYZE 这类本来就要扫 heap 的维护操作。

右边不适合：高 QPS 主键点查、唯一键查、窄范围查；大表里只命中极少行的 OLTP 查询；依赖有序返回却没有 ORDER BY；表膨胀严重、死元组比例高还频繁全表扫；I/O 已经饱和还继续加并行 worker；多租户大表缺租户或时间裁剪条件的后台任务。

请注意两边的措辞：一边是「访问形状本来就是一大片」，一边是「明明只要一小撮却读了一大片」。分界线跟第五页那条完全一样。

所以场景不用背，回到那个问题就行：这次到底要读多少块，这些块本该被读到吗。

清单记不住没关系，把八个常见误判记成四类就够了。

24八个坑，其实只有四类

八个坑，摊开看很杂，归成四类就清爽了。

认知类两条：把 Seq Scan 等同于索引失效；把 enable_seqscan=off 当生产优化。这两条都来自第九页那本账——优化器是按成本选路径，不是按开关站队。

顺序类两条：没有 ORDER BY 却依赖返回顺序；看到并行就期待线性加速。前者对应第十六页的同步扫描，后者对应第十七页里那些真实瓶颈。

数据类两条：忽略 MVCC 和表膨胀；只给 status、is_deleted 这种低基数列建单列索引。前者在第十一页的页面里，后者在第十页的分界线上——低基数索引经常打不过顺序扫描，得靠复合索引、局部索引、分区或者改写。

写法与参数类两条：在列上套函数，比如 WHERE date(created_at) = current_date，让普通索引用不上，应该改成范围条件或表达式索引；还有 random_page_cost、effective_io_concurrency 这些参数长期不贴合硬件，SSD、NVMe、云盘、本地盘的顺序与随机差距根本不一样。

你会发现每一类都能对回前面某一层。这就是这张地层图的用处：出问题先定位层，再选动作。

最后收一下，把整场压成四个问题。

25别急着紧张，先问四句

收尾，把整场压成四句话。

第一问：它读了多少块？EXPLAIN (ANALYZE, BUFFERS) 会告诉你，别凭感觉。

第二问：过滤掉多少行？Rows Removed by Filter 会告诉你，这一问能分出「读得多但确实该读」和「读得多却几乎全扔了」。

第三问：这些块本该被跳过吗？如果业务本来就要全表聚合，答案是「不该跳」，那这个 Seq Scan 就是正确答案，别折腾它。

第四问：如果要跳过，靠什么？屏幕底下这五个出口：索引、分区、统计信息、SQL 改写、数据模型重构。注意顺序——越往右越贵，也越治本。

回到最开始那句话：Seq Scan 的本质不是「慢」，是「用连续吞吐换掉索引定位能力」。当你需要读很多数据时，它可能是最优路径；当你只想要几行却扫完整张大表，它就是建模、索引、统计信息或 SQL 写法暴露出来的工程问题。

真正的判断方法，从来不是看到这四个字就紧张，而是把这四问走一遍。

01顺序扫描 Seq Scan

这一场我们只讲一件事：顺序扫描，也就是执行计划里那四个字，Seq Scan。

它太朴素了，朴素到很多人一看见它就紧张，觉得一定是索引没建好、一定是数据库偷懒。

但今天我想换个讲法：先不问它快不快，先问它到底在替我们解决什么问题。

你看屏幕上这七层，从上往下是 SQL、计划器、计划树、执行器、表访问接口、heap 页面，最后才是缓冲区和磁盘。越往下越接近物理。顺序扫描不是某一层的小技巧，它是把这条链从头走到尾的一种走法。

所以这场演说会沿着这条地层一路往下挖：先看清它和索引怎么分工，再看清它为什么不能少读页，然后进到页面里看可见性判断，最后看系统怎么保护缓存、怎么让多个扫描共享 I/O。

挖到底你会发现，判断一个 Seq Scan 好坏，靠的不是情绪，是四个很朴素的问题。

02明明建了索引，为什么还是 Seq Scan？

先摆三个现场，你大概都遇过。

第一个：索引明明建了，EXPLAIN 里还是 Seq Scan。开发同学第一反应是「索引失效了」，于是开始重建索引、改写法、甚至把 enable_seqscan 关掉。

第二个：大表报表、批处理、count(*)、再加几个低选择率的状态过滤，一起把 I/O 打满。DBA 站在监控前面，不知道该调 SQL、调参数、加索引，还是干脆分区。

第三个：好几个并发的全表扫描互相污染缓存，或者加了并行 worker，吞吐却没按预期上来。

这三件事看起来毫不相干，其实都在问同一句：这一次扫描到底读了多少东西，为什么非读不可？

我们习惯在结果层看它——返回了几行、慢了几秒。可数据库是在成本层做决定的——读几页、怎么读、每行算几次。

把视角从结果层挪到成本层，这三个现场就变成同一个问题的三种表现。

03判断它，而不是消灭它

所以这一场的目标，先说清楚：不是教你怎么消灭 Seq Scan，是教你怎么判断它。

文章里有句话我很喜欢——它的价值在于知道什么时候是正确答案，什么时候是事故信号。这两者长得一模一样，都是执行计划里一行 Seq Scan，区别全在上下文。

屏幕上这七层是我们今天的路线。最上面两层是定位：索引解决什么、它解决什么，以及那个最容易被误会的事实——WHERE 到底管不管读页。

中间三层是机制：主路径、代价模型、页面内发生了什么。

再往下两层是系统保护：大表怎么不冲掉缓存，多个扫描怎么共享 I/O，怎么把块分给并行 worker。

最底下一层是落地：横向对比、收益代价、可验证的实验，还有分角色的最佳实践。

有个规律先记着：越靠下的层，越接近物理，也越接近你能在 EXPLAIN 里看到的事实。我们就从上往下走。

04索引解决「少读」，它解决「读得稳」

先把分工摆正。索引解决的是「怎样少读」——用索引条件把无关的页面跳过去，只回头取需要的那几行。

顺序扫描解决的是另一个同样常见的问题：当查询必须读很多行、很多块，或者根本没有可用索引的时候，怎样把这一整遍读取做得稳定、可预测、少折腾缓存。

你看右边这三条：按物理块顺序读，对预取友好；启动成本低，不用遍历索引、不用构建 bitmap；代价是不能跳页，全表或整个分区都得过一遍。

左边索引那条：精确定位、能跳页，但回表是随机 I/O，而且启动要先走索引。

注意底下这条金色横带——优化器永远按成本选路径，两条曲线谁低谁上。这里没有「高级」和「低级」，只有「这次访问形状更适合谁」。

所以看到 Seq Scan 别急着下结论，先问：这次是要读一小撮，还是要读一大片？

不过在回答这个问题之前，有个事实必须先厘清，它比选择率更基础。

05WHERE 减少的是「返回行」，不是「读取页」

这是全篇最重要的一页，请多看两眼。

上面这一排是堆表的页面，示意画了十个。顺序扫描开始之后，这十个页面一个都不能少，全部要进缓冲区、全部要被检查。底下那行字写着：顺序 I/O 贯穿全部块。

中间三格是每一条候选行都要过的关：页级准备、MVCC 可见性、qual 与投影。

橙色这条虚线才是 WHERE 真正生效的地方——它作用在「行」上，逐行判断要不要往上传。

最下面：绝大多数行被过滤掉，只有很少几行真的返回给上层。

所以你会看到那个最让人困惑的现象：结果只有三行，EXPLAIN 里却有全表的Buffers hit 和 read。

原因不是数据库笨，是它压根没有「跳过页面」的能力。WHERE 是出口的闸门，不是入口的闸门。

这一条如果记住了，后面所有现象都能推出来：为什么低选择率过滤还是全表扫，为什么表膨胀会拖慢它，为什么加索引有时救不了报表。

那既然读页这件事无法回避，数据库就得把「读一整遍」这件事做得尽量聪明。我们先看是谁在做。

06它不是「for 循环读文件」

很多人心里的顺序扫描，就是一个 for 循环：打开文件、从头读到尾。

真实的 PostgreSQL 里，它首先是一个计划节点：优化器决定「用顺序扫描划不划算」，并生成 SeqScan 计划节点，把过滤条件放进 scan qual。

它同时是一个执行器节点：ExecInitSeqScan 初始化状态，SeqNext 一次取一行，交给上层。

而在这两层之下，屏幕这九件事都得同时处理：快照与 MVCC、buffer pin 和 lock、页面剪枝、批量可见性判断、I/O 预取与 read stream、同步扫描起点、并行块分配、执行器 qual 过滤，还有 projection 目标列。

这个清单很重要，因为它解释了后面一个现象：为什么同样「扫一遍表」，有的表特别慢。

慢往往不慢在读，慢在读进来之后这一堆判断。行越宽、死元组越多、表达式越复杂，这一层就越重。

所以别把它想成一个 I/O 动作，它是一个带着完整 MVCC 语义的执行器节点。

接下来把这条路径摊开，看看一行数据究竟怎么从 SQL 走到你手上。

07从 SQL 到元组，路径很短、层次不少

这条主路径其实很短，但层次不少。

上面一排：优化器在 allpaths.c 里先考虑 seq scan 路径，接着生成 SeqScan 计划节点，把 qual 挂上去；执行器这边 ExecInitSeqScan 初始化，SeqNext 一次取一行；再往右是通用表接口 TableAM。

关键在这一句：SeqNext 不直接理解 heap 文件长什么样，它只调 table_beginscan 和 table_scan_getnextslot，拿回一个 tuple slot。

然后才往下折到 TableAM 的默认实现：heap 扫描描述符记下 startblock 和 nblocks，页面读取走 read stream 和共享缓冲区，页面内再遍历 line pointer、判断可见性、算 qual、做投影。

为什么非要分这么多层？因为换一种表访问方法的时候，执行器几乎不用改。这也是 PostgreSQL 能把 heap、列存扩展、外部表都塞进同一套执行器框架的原因。

底下那行小字也别漏：每次只返回一个可见且满足条件的 tuple slot，父节点可能提前停止，比如 LIMIT。

所以「全表扫」不等于「一定要算到最后一块」——但那是上层节点的决定，不是扫描节点自己会跳页。

层次清楚了，我们把它们对到源码上，看看每一层究竟落在哪个文件。

09它算的不是「读几行」，是「读几页、算几次」

来看优化器的账本。简化之后是四个部分。

第一块，磁盘运行成本：seq_page_cost 乘 rel.pages。注意是表的全部页数，跟 WHERE 一点关系都没有。

第二块，CPU 扫描成本：cpu_tuple_cost 加上 qual 的单行成本，再乘全表 tuple 数。也是全量。

第三块，输出表达式成本：按估算的输出行数算，这部分才跟返回多少行有关。

第四块，并行修正：CPU 成本按 worker 分摊；源码注释说得很直白，I/O 成本暂不明显分摊，因为操作系统已经会做 aggressive prefetching。

10为什么要取的行越多，索引越容易输

把两条曲线画在一起，那个「反直觉」就变成常识了。

靛青这条是顺序扫描：几乎水平，因为读多少页是恒定的，只有 qual 的 CPU 随行数微微上抬。

陶橙这条是索引扫描：随要取的比例一路往上抬。原因不是索引本身变慢，而是取的行一多，随机定位加回表随机读加可见性判断，累计代价会迅速超过一遍顺序读。

两条线的交叉点，就是分界。左边索引便宜，右边顺序扫描便宜。

这里必须强调一句：这是示意曲线，不是实测数据，我没有编任何性能数字。而且这个分界点非常不稳——random_page_cost 调小、缓存命中变好、行更窄、visibility map 更友好、并行能分摊 CPU，它都会往右移；反过来就往左移。

所以别背「超过百分之多少就该全表扫」这种口诀，那不是数据库的工作方式。

优化器每一条 SQL 都重新算一次账，依据是你这台机器的参数、这张表的统计信息。

账算完了，接下来就该真干活了：一个页面被读进内存之后，到底发生了什么。

11一个页面被读进来，还要过三关

现在进到页面里。

左边是一个 heap 页面的示意：上面是 Page Header 和 line pointers，底下是一格一格的 tuple。绿色是对当前快照可见的，橙色是死元组，白色是空闲的 line pointer。

注意：页面被整个读进来了，包括那些死元组和空位。它们照样占了 I/O，照样要被检查，只是最后判断为不可见、扔掉。

右边三关，按顺序走。

第一关，页级准备。如果用 page-at-a-time 模式，heap 会先准备当前页面可见 tuple 的 offset 数组；页面 all-visible 且不在 hot standby 特殊场景时，还能走更快路径。

第二关，MVCC 可见性。每个候选 tuple 都要按快照判断一次。

第三关，执行器的 qual 和投影，也就是 WHERE 表达式和目标列。

我想让你带走的判断是：顺序扫描的 CPU 大头，往往不在你写的那个 SQL 表达式，而在「读进来之后，得把每一条都判一遍」。

13同样「读一遍」，账却不一样

左边写着「同样读一遍表」，页数一样。但右边这四个放大器一开，账单立刻不同。

表膨胀和死元组：页面读进来了，还得判一次不可见，I/O 和 CPU 一起白花。

宽行：每页能放的 tuple 变少，同样行数就要读更多页——连第一项磁盘成本都跟着涨。

复杂表达式：每行多算一次 qual，乘上全表 tuple 数，是个很可观的乘法。

投影列多：tuple deform、内存搬运、网络输出，以及上层排序聚合，全都跟着变重。

右边那个橙框把这些汇总成一份「CPU / I/O 账单」。

这一页想纠正一个很常见的估算方式：拿行数乘一个固定单价去估全表扫描，几乎一定会估偏。

因为真正的单价是由数据形状决定的。所以 DBA 排查慢查询时，除了看计划，还得看 n_dead_tup、看行宽、看表达式复杂度。

好，个体层面的成本讲完了。接下来往上抬一层：一次大扫描，会不会把整个系统拖下水。

14大表扫描不该冲掉整个 shared_buffers

这一页也配了动画，先说它演示什么。

左边是无保护的情况：一次大扫描逐格把 shared_buffers 覆盖掉，青绿色的 OLTP 热页被一格格挤出去。右边启用了 BAS_BULKREAD：热页留在池里不动，扫描读进来的页只在下面那个小环里循环覆盖。

改一下输入里的扫描页数，按播放或单步，看左下角「热页保留」的数字怎么掉，右边怎么一直保持满格。按重置可以重来。

再强调一次：这是机制示意，格子数不是真实缓冲区块数，也不是实测数据。

真实实现里，freelist.c 的 bulk-read ring 基础大小从 256KB 起，会结合 effective_io_concurrency、io_combine_limit 和 pin limit 调整，但最终受 shared_buffers 的 1/8 上限约束。

这个设计的措辞要记准：它不是「让全表扫变快」的手段，是「让全表扫别把系统拖垮」的保护。大扫描需要吞吐，但不该把 OLTP 的热页全部挤出去。

理解了「一个扫描别添乱」，下一页反过来问：好几个扫描能不能别各读各的，干脆一起读。

一排是表块，上面几个小色条是不同后端的扫描位置。已有扫描已经走到中间，新来的扫描不从表头开始，而是从它附近起步，然后大家一起往前走；走到末尾，沿着下面那条 U 形回环 wrap 回表头，把前面跳过的块补上。

输入可以设 2 到 4 个并发扫描，播放、单步、重置都在下面。你会看到几个指针尽量待在同一批块附近——这正是共享 I/O 的意思。

syncscan.c 的注释说得很直接：目标是让每个页面被读入共享缓冲区之后，参与扫描的后端都能在它被淘汰前处理掉它。

实现上并不强制所有扫描同速，只维护一个小的共享 LRU 位置表，进度也只按间隔上报，避免锁竞争。

它和论文 Cooperative Scans 的思想有相似处——扫描之间共享运行时内存和 I/O；但 PostgreSQL 的实现轻得多，只是「挑个接近已有扫描的起点」，不是完整的请求重排和调度框架。

听起来全是好处。可「从中间开始」这五个字，藏着一个很实际的副作用。

16省了 I/O，也让返回顺序更不可测

看上面两排。

第一排是物理块，橙色那格是第 10 块——同步扫描挑的起点。第二排是应用可能观察到的返回顺序：10、11、12 一直到末尾，然后接 0、1、2 回到前面。

如果业务代码悄悄依赖了「先插的先出来」，这一刻就会出问题：分页翻页会重复、会漏，报表顺序会变。

但我要替数据库说句公道话：这不是同步扫描制造的 bug。SQL 从来没有承诺过无 ORDER BY 查询的返回顺序，只是以前每次都从表头扫，碰巧稳定，大家就把巧合当成了契约。

官方文档对 synchronize_seqscans 明确提醒了这一点，而且这个参数默认是 on；设成 off 能回到「总是从表头开始」的旧行为，代价是失去 I/O 共享。

所以正确动作只有一个，写在右边绿框里：所有分页、所有依赖顺序的 SQL，都老老实实加 ORDER BY，而且要加稳定的排序条件。

这一条我建议直接写进团队的 SQL 规范。

好，并发「一起读」讲完了；大表还有一种完全不同的思路——干脆分着读。

17不是每个人都扫全表，是分块

并行顺序扫描最容易被人想成「开三个进程，各扫一遍全表」，那就成了三倍 I/O。

实际不是。上面是 Gather，下面几个 worker 共享同一份扫描状态 DSM，里面记着 phs_startblock、phs_nallocated。

每个 worker 通过原子 fetch-and-add 领一段连续的块范围，领完扫，扫完再领下一段。底下那一排 chunk 就是被领走的块。

用动画放一遍：设 2 到 4 个 worker，播放或单步，你会看到块被轮流染色，但从不重复，而且每个 worker 拿到的是连续的一段。

为什么非要连续？tableam.c 的注释解释了：早期如果每次只给下一个最高块号，不同进程会把连续 I/O 模式打散，操作系统的 readahead 就白做了。扫描接近末尾时再逐步缩小 chunk，减少长尾等待。

但别在这里期待线性加速。I/O 已经饱和、leader 汇聚结果、worker 启动、tuple 向上传输、上层还有聚合和排序，任何一处都能成为瓶颈。

加 worker 之前，先看它到底卡在哪一层。

到这儿，单个 Seq Scan 里里外外都拆完了。最后要把它放回全局：和其他扫描方法摆在一起，怎么选。

18不是谁高级谁快，是谁更贴合访问形状

把五种方法放到一张决策网格里。

输入是 WHERE、ORDER BY、LIMIT 和统计信息；中间只问一句：能先缩小物理访问范围吗？

能，而且只要很少几行，走 Index Scan；能，但命中中等规模、或者多个条件要合并，走 Bitmap Heap Scan，先用索引定位块，再按块访问 heap；能，而且索引就覆盖了要的列、visibility map 也友好，走 Index Only Scan，尽量不回表。

不能——要读全表或者很大比例，或者压根没有可用索引——那就是 Seq Scan。

底下还有一层：表很大、查询又并行安全，再考虑 Parallel Seq Scan 或者分区裁剪。分区裁剪其实是把「顺序扫描一个大表」变成「顺序扫描一个小分区」，思路和索引不一样，但目的一样：减少要读的块。

文章里那张对比表还列了排序能力和 MVCC 成本，结论都从同一个原则长出来：优化器在比较「读多少块、怎么读块、CPU 处理多少 tuple、能否提前停止、是否需要排序」。

所以千万别把 Seq Scan 简化成「没用上索引」。很多时候它是成本模型的理性选择；当然，统计信息错了、参数不贴硬件、表膨胀严重，这个理性选择也会变坏。

19收益是吞吐，代价是「不能跳」

把收益和代价并排放，你会发现它们不是两份清单，是同一件事的两面。

左边：顺序 I/O 和预取友好所以吞吐稳；不用遍历索引、不用构建 bitmap 所以启动成本低；全表聚合、低选择率过滤、小表查询很直接；还可以用 bulk-read ring 保护缓存、用同步扫描共享 I/O、用并行分摊 CPU。

右边：读取范围通常是整个表或整个分区；WHERE 不能跳过页面；宽行、死元组、表膨胀会同时放大 I/O 和 CPU；没有天然排序，ORDER BY 通常还得再 Sort；对 OLTP 点查可能是灾难信号；同步扫描还会改变无序查询的观察顺序。

你把左右对起来看：左边每一条收益，几乎都来自「老老实实连续读」；右边每一条代价，几乎都来自「不能跳」。

顺带提一句可观测性的新东西：PostgreSQL 19 给使用 ReadStream 的扫描节点加了 EXPLAIN (ANALYZE, IO)，能看到预读距离、I/O 请求大小和并发情况，对 Seq Scan 特别有用。但这是新版本能力，生产环境能不能用，以你实际版本的文档为准，别在 Older 版本上照抄。

判断的抓手就一句：右边这六条里，哪一条正是你线上正在发生的。要回答它，就得动手测。

20五个实验，一条 EXPLAIN 观察链

这一页是回去就能做的五个实验，按顺序排成一条观察链。

6.1 建一张二十万行的表，ANALYZE 之后跑 count(*)。没有过滤条件，优化器通常只能扫描全表；是否并行取决于表大小、max_parallel_workers_per_gather 和并行成本参数。

6.2 给 status 建索引，再查 status = 1。这个列只有五个值，大约命中 20% 的行，优化器很可能仍然选 Seq Scan。这时候别急着喊索引失效，先查统计信息、表膨胀、缓存状态、random_page_cost 和 effective_cache_size。

6.3 换成 id = 1000 的主键点查，正常应该走 Index Scan。如果还是 Seq Scan，常见原因是类型不匹配、列上套了表达式、统计信息异常、索引不可用，或者测试表太小导致顺序扫启动成本更低。

6.4 打开 enable_seqscan = off 再 EXPLAIN，看它到底有没有变。

6.5 查 pg_stat_user_tables，用 seq_scan 和 seq_tup_read 找哪些表经常被顺序扫。但别只看计数下结论：小表频繁 seq scan 完全正常，大表 seq_tup_read 暴涨才需要结合业务时间窗和 I/O 指标分析。

底下那句金色的话请记住：这些 SQL 我没执行，所以这里一个输出结果都没有，也不该有。你自己的环境才是答案。

21它是诊断工具，不是优化手段

6.4 那个实验值得单独讲，因为它是初学者最容易踩的坑。

左边橙框是很多人的心理模型：把开关一关，数据库就被迫走索引了。文档说得很清楚，这个理解不成立。

真实发生的是右边三步：第一，关掉开关只是给 Seq Scan 路径加上极高的代价惩罚；第二，只有当确实存在其它访问路径时，优化器才会改选；第三，如果没有其它方法能读这张表，它照样生成 Seq Scan——因为总得有个能跑的计划。

你在 EXPLAIN 里会看到那个计划成本高得离谱，新版本还会显示 disabled node 信息，但节点本身还在。

所以它的正确用途是诊断：我想看看「假如不用顺序扫描，优化器会选什么、代价差多少」。看完了 RESET 回来。

真正该改的是底下绿框那几件事：定期 ANALYZE、校准 random_page_cost 和 effective_cache_size、补合适的索引或改写 SQL、控制表膨胀。

一句话：参数能帮你问问题，不能替你修数据。

那到底谁来改、改什么？按三个角色分开看最清楚。

22架构师管形状，DBA 管事实，开发者管写法

把最佳实践按角色拆开，是为了让每个人知道自己那一刀该砍在哪。

架构师管形状：如果业务天然按时间、租户、区域访问大表，优先考虑分区或冷热拆分，让「顺序扫描一个小范围」替代「顺序扫描整个大表」；报表型查询别指望二级索引救命，低选择率、多列聚合、宽表扫描更需要列裁剪、物化汇总、只读副本或者 OLAP 系统；建模时控制行宽；让 seq_page_cost、random_page_cost、effective_io_concurrency 这些参数贴近真实硬件。

DBA 管事实：看到大表 Seq Scan 先跑 EXPLAIN (ANALYZE, BUFFERS)，分清是读块多、过滤多、排序多、并行不足还是估算偏差；定期 ANALYZE，关注相关列和表达式统计；控制表膨胀；用 pg_stat_io 这类视图区分 shared buffer 命中和物理读。

开发者管写法：别写「返回几行却扫全表」的 SQL，典型风险是列上套函数、隐式类型转换、前导 %LIKE、低选择率状态列、缺分区键条件；所有分页必须有稳定排序；只取需要的列；LIMIT 当成优化机会但别神化它。

三列不是三份清单，是同一条链路。

23该用它的地方，和该警惕它的地方

有了动作，还得知道边界在哪。

左边适合：小表查询，索引收益不明显；全表聚合、全表导出、批处理校验；谓词命中大比例行，比如状态列、布尔列、低基数枚举列；分区裁剪之后扫描单个小分区；并行安全的大表扫描和报表；还有建索引、VACUUM、ANALYZE 这类本来就要扫 heap 的维护操作。

右边不适合：高 QPS 主键点查、唯一键查、窄范围查；大表里只命中极少行的 OLTP 查询；依赖有序返回却没有 ORDER BY；表膨胀严重、死元组比例高还频繁全表扫；I/O 已经饱和还继续加并行 worker；多租户大表缺租户或时间裁剪条件的后台任务。

请注意两边的措辞：一边是「访问形状本来就是一大片」，一边是「明明只要一小撮却读了一大片」。分界线跟第五页那条完全一样。

所以场景不用背，回到那个问题就行：这次到底要读多少块，这些块本该被读到吗。

清单记不住没关系，把八个常见误判记成四类就够了。

24八个坑，其实只有四类

八个坑，摊开看很杂，归成四类就清爽了。

认知类两条：把 Seq Scan 等同于索引失效；把 enable_seqscan=off 当生产优化。这两条都来自第九页那本账——优化器是按成本选路径，不是按开关站队。

顺序类两条：没有 ORDER BY 却依赖返回顺序；看到并行就期待线性加速。前者对应第十六页的同步扫描，后者对应第十七页里那些真实瓶颈。

数据类两条：忽略 MVCC 和表膨胀；只给 status、is_deleted 这种低基数列建单列索引。前者在第十一页的页面里，后者在第十页的分界线上——低基数索引经常打不过顺序扫描，得靠复合索引、局部索引、分区或者改写。

写法与参数类两条：在列上套函数，比如 WHERE date(created_at) = current_date，让普通索引用不上，应该改成范围条件或表达式索引；还有 random_page_cost、effective_io_concurrency 这些参数长期不贴合硬件，SSD、NVMe、云盘、本地盘的顺序与随机差距根本不一样。

你会发现每一类都能对回前面某一层。这就是这张地层图的用处：出问题先定位层，再选动作。

最后收一下，把整场压成四个问题。

25别急着紧张，先问四句

收尾，把整场压成四句话。

第一问：它读了多少块？EXPLAIN (ANALYZE, BUFFERS) 会告诉你，别凭感觉。

第二问：过滤掉多少行？Rows Removed by Filter 会告诉你，这一问能分出「读得多但确实该读」和「读得多却几乎全扔了」。

第三问：这些块本该被跳过吗？如果业务本来就要全表聚合，答案是「不该跳」，那这个 Seq Scan 就是正确答案，别折腾它。

第四问：如果要跳过，靠什么？屏幕底下这五个出口：索引、分区、统计信息、SQL 改写、数据模型重构。注意顺序——越往右越贵，也越治本。

回到最开始那句话：Seq Scan 的本质不是「慢」，是「用连续吞吐换掉索引定位能力」。当你需要读很多数据时，它可能是最优路径；当你只想要几行却扫完整张大表，它就是建模、索引、统计信息或 SQL 写法暴露出来的工程问题。

真正的判断方法，从来不是看到这四个字就紧张，而是把这四问走一遍。

这一场就到这里，谢谢。
