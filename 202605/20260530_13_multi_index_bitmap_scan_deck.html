三个条件，三个单列索引

先从一个特别普通的查询讲起。city_id 等于 42，status 等于 1，再加一个最近七天的 created_at，三个条件，表上也老老实实建了三个单列索引。听起来配置挺齐全，对吧？可如果你只学过单列索引和 Index Scan，会发现这题其实没解：优化器顶多挑一个它认为最窄的索引先回表，把另外两个条件留到回表之后当 Filter。问题不在索引不够多，而在「找行」这个动作被绑死在一条索引路径上——你只能沿着一棵 B-tree 给出的顺序往下走，另外两棵树明明也有信息，却没法一起用。这就是我们今天要处理的那个中间地带：多个条件各自有索引，但单个索引都不够好。注意，我说的是「不够好」，不是「用不了」。那到底差在哪？下一页把这个代价摊开看。

代价来自顺序错位

上一页说回表会变贵，贵在哪儿？我们把它拆成两件事。索引扫描吐出来的是 TID，也就是「第几页第几行」，它按索引键的顺序排列；可 heap 页在磁盘上是按物理块排的。这两套顺序根本没有对齐的义务。你看中间那条带子：b7、b1、b7、b3、b8、b2……同一个 b7 被反复访问，下一行又跳回 b1。本来一次顺序扫描能读完的页，现在变成了来回跳的随机 I/O；候选行越多，跳得越凶。所以这里真正需要改的，不是再建一个更神的索引，而是把「访问表的顺序」从索引手里拿回来。只要能让候选集合先算清楚，再按物理页号去读，随机访问就变成了顺序访问。这个念头一转，整个问题就换了一副样子。

PAGE 03 / 20　·　命题 · 全篇的一句话

把「找行」改成「先算集合」

那就把问题换一种问法。别问「该用哪个索引」，问「到底哪些行可能符合条件」。改写之后是四步：第一，每个可索引条件各自去扫自己的索引，通过 amgetbitmap 产出候选 TID，注意这一步不返回任何行；第二，把这些 TID 写进内存里的 TIDBitmap；第三，在内存里做集合运算，AND 就求交集，OR 就求并集；第四，拿合并后的位图，按 heap block 的物理顺序去访问表，顺便完成 MVCC 可见性判断、lossy 页的 recheck 和剩下的过滤。请特别盯住第四步：行的顺序彻底不再由索引决定，而由 heap 物理顺序决定。这就是 Multi-Index Bitmap Scan 的全部主张。收益是随机回表被压成顺序读，代价也同时写死了——必须先建位图，所以有启动成本；顺序换人了，所以索引原本能提供的排序没了。后面所有细节，都是从这一句主张里长出来的。

PAGE 04 / 20　·　边界 · 先排除一个误会

它不是磁盘上的 bitmap index

很多人第一次听到 bitmap scan，第一反应是：哦，磁盘上存了一张位图索引，一个值对应一串 0 和 1。不是的。PostgreSQL core 里压根没有这种「多索引 bitmap index」。它做的是：执行期拿普通的索引访问方法——B-tree、GIN、GiST、BRIN、hash、SP-GiST 都行，只要这个 AM 支持 amgetbitmap——把命中的 TID 写进一块内存结构 TIDBitmap，再用 BitmapAnd 或者 BitmapOr 把几张位图合并起来。这张位图不落盘、不随写入维护、查询一结束就释放。官方文档把这能力叫 Combining Multiple Indexes，说得也很直白：扫描每个需要的索引，在内存里准备表示表行位置的 bitmap，按查询需要 AND 或 OR，最后才去访问实际的表行。把边界划清楚特别有用，因为后面所有代价都能顺着推出来：既然是查询期现算，就一定要先付启动成本；既然放在内存里，就一定受 work_mem 约束，内存不够就要降级；既然用的是普通索引 AM，那它就不是什么更「高级」的索引类型，只是一次执行期的组织方式。

从 SQL 到 heap 的七层剖面

边界清楚了，现在把整套机制剖开。从上往下七层，颜色越深越底层。最上面是应用的 SQL 和 WHERE 条件；第二层是优化器的路径：IndexPath、BitmapAndPath、BitmapOrPath、BitmapHeapPath，在 indxpath.c 和 pathnode.c 里；第三层是代价模型，cost_bitmap_and_node、cost_bitmap_or_node、cost_bitmap_heap_scan，在 costsize.c；第四层把 path 变成 plan，createplan.c 里的 create_bitmap_scan_plan；第五层是执行器节点 BitmapIndexScan、BitmapAnd、BitmapOr，在 nodeBitmap 那一批文件里；第六层是内存结构 TIDBitmap，tidbitmap.c；最底下第七层才是 BitmapHeapScan，真正去读 heap 页、真正吐出行的节点。这里有个特别容易记反的点：BitmapIndexScan 不返回 tuple，它返回的是一张位图；产出行这件事，是它祖先节点 BitmapHeapScan 干的。所以你在 EXPLAIN 里看到一堆 Bitmap Index Scan，别以为行是从那儿来的。记住这个「上四层做决定、下三层干活」的分工，后面每一页都能对上号。

PAGE 06 / 20　·　计划期 · 路径怎么生成

计划期：一条 WHERE 变成一条路径

计划期做的事，是把一条 WHERE 变成一条能执行的路径。第一步，优化器从限制条件里挑出可索引的子句；第二步，indxpath.c 为每个可索引条件生成 IndexPath，也就是候选的索引路径；第三步是最关键的，generate_bitmap_or_paths 负责处理 OR，choose_bitmap_and 负责处理 AND，决定到底把哪几个路径组合起来；第四步，costsize.c 给组合估成本，包括索引扫描、位图合并、heap 页访问和 recheck；第五步，pathnode.c 造出 BitmapHeapPath，再交给 createplan.c 转成计划节点。你会发现，整个「用几个索引」的决策在计划期就定死了，执行期只是照着做。而第三步里藏着两条特别要紧的规则：OR 要求每一臂都能被索引处理，AND 却不是「索引越多越好」。这两条加起来，几乎能解释你在生产里看到的一大半「咦，怎么没用上我建的索引」。我们一个一个说，先看 OR。

OR 的铁律：每一臂都要能索引

为什么 OR 这么严格？因为集合的并集不能缺一块。city_id 等于 42 或者 status 等于 1，两臂都有索引，那就各扫一次、各得一张位图、并起来，一个结果都不会漏。可如果写成 city_id 等于 42 或者 lower(payload) 等于 abc，而 lower(payload) 上没有表达式索引，怎么办？数据库不能只用左边一半的 OR 条件去生成候选集合再回表，因为那样右边那半结果直接就漏了，SQL 的语义就错了。所以整个 OR 子句很难变成 BitmapOrPath，优化器宁可退回别的计划。源码上，generate_bitmap_or_paths 会遍历 OR 子句，对每个 arm 调 build_paths_for_OR，arm 内部若有多条索引路径还会先经 choose_bitmap_and 挑一遍，只有所有 arm 都有可行路径，才调用 create_bitmap_or_path。这是典型的「宁可不做，也不能做错」。落到写法上就一句话：OR 查询要么每一臂都能索引，要么改写、补表达式索引、或者干脆拆查询，半边可索引通常救不了整体。那 AND 呢？AND 没有正确性问题，少用一个索引顶多慢点，应该随便加吧？恰恰相反。

PAGE 08 / 20　·　规则二 · AND 的克制

AND 的克制：索引不是越多越好

按理说，N 个可索引的 AND 条件，把非空子集全枚举一遍、挑最便宜的组合，是最漂亮的做法。PostgreSQL 源码注释说得很直接：这是 O(2^N)，不现实，而且选择率估算本身就很粗糙，穷举出来的「最优」也未必靠谱。所以 choose_bitmap_and 用启发式，五步：第一，几个路径用的是完全相同的一组 WHERE 子句和索引谓词，只留扫描成本最低的那个；第二，按索引访问成本从低到高排序；第三，以每个路径当组合起点，逐个试着加更贵的路径；第四，只有加入之后估算总成本真的下降，才保留这个组合；第五，避免把使用同一 WHERE 子句的多个索引凑在一起，防止选择率被重复计算得过小。这解释了一个特别常见的疑惑：表上明明有三个单列索引，执行计划里却只出现两个 Bitmap Index Scan。别急着怀疑统计信息没收集，优化器很可能只是算过账——多扫一个索引带来的候选集缩小，抵不过多一次索引扫描加一次位图交集。顺便说一句，这个「算账」的准确性，就全押在下一页的代价模型上了。

PAGE 09 / 20　·　代价模型 · 假设与脆弱

代价模型：假设很美，也很脆

代价模型分两段。cost_bitmap_and_node 和 cost_bitmap_or_node 只估索引扫描、位图创建与合并，不估最终 heap 访问；heap 那部分由 cost_bitmap_heap_scan 配合 compute_bitmap_pages 来估。关键在三个假设。BitmapAnd 假设输入条件互相独立，选择率直接相乘——源码注释自己就承认这经常是错的，只是没有足够信息做得更好。BitmapOr 假设输入集合近似不重叠，选择率相加之后 clamp 到 1.0，这对 x IN 某列表那种情况还挺合理，但一般 OR 是真会重叠的。heap 页用 Mackert-Lohman 风格的公式估要读多少页，再结合 work_mem 估 exact 与 lossy 的比例。最容易翻车的是第一条：province_id 和 city_id 高度相关，把它们当独立条件一乘，结果行数被严重低估，成本看着特别乐观，计划就选歪了。解药也明确：CREATE STATISTICS 建扩展统计信息，带上 dependencies、ndistinct、mcv，然后 ANALYZE。所以你会发现，多索引 bitmap scan 的成败，一半在机制，一半在统计信息质量。好，公式讲够了，我们动手把这套集合运算跑一遍。

执行器里的两处工程直觉

执行器层的代码其实很短，但工程含义很实在。nodeBitmapAnd.c 里的 MultiExecBitmapAnd 按顺序跑子计划，每个子计划返回一张 TIDBitmap，第一张当结果，后面用 tbm_intersect 求交；一旦中途结果空了，立刻停止剩下的子计划——再 AND 也不可能把空集变回来。源码还提了一句挺妙的呼应：indxpath.c 按选择率给子计划排序，就是为了让这种提前结束更容易发生。计划期的一个排序决定，到执行期变成了省下几次索引扫描。nodeBitmapOr.c 反过来，它没法早停，但省了别的：如果直接子节点就是 BitmapIndexScan，它不先创建子位图再 tbm_union，而是把当前那张结果位图直接传给子节点，让子节点原地 OR 进去，少一次分配、少一次合并。还有一点最容易被忽略：BitmapAnd 和 BitmapOr 根本不是普通的逐行执行节点，它们的 ExecProcNode 入口会直接报错，实际由 MultiExecProcNode 一次性产出一张位图。也就是说，这两个节点是「批量产出结构」的，不是「一行一行吐数据」的。那这张位图交到 heap 阶段之后，正确性靠什么兜底？

PAGE 12 / 20　·　正确性 · recheck 与 lossy

Recheck Cond 是保险，不是病

看 EXPLAIN 的时候，几乎一定会撞见 Recheck Cond。很多人一看就紧张，觉得计划很差、要复核大量行。其实它是正确性保险，不是病。create_bitmap_scan_plan 在把 BitmapHeapPath 转成计划节点时，会生成 bitmapqualorig，把原始索引条件和部分索引谓词原样留着，原因只有一个：位图可能会变 lossy。exact 页精确到 offset，执行器只查命中的那几行；lossy 页只知道「这一页里有人命中」，具体是哪几行已经记不清了，于是整页的 tuple 都得拿原始条件重查一遍。所以 Recheck Cond 存在，不代表真的发生了大量复核，它只表示执行器把保险留着了。真正该盯的是两个地方：Heap Blocks 里的 exact 和 lossy 各是多少，以及 Rows Removed by Index Recheck 有多少。前者告诉你位图有没有掉精度，后者告诉你掉精度之后实际多做了多少无用功。别看到 Recheck Cond 就调参数，先看这两个数。那什么会把位图逼成 lossy？内存。

PAGE 13 / 20　·　演示 · work_mem 的边界

work_mem 决定位图的精度

这一页拖一下滑块就明白了。TIDBitmap 受 work_mem 约束，每个查询能用多少内存是有上限的。内存不够的时候，位图会 lossify：本来能记到「第几页第几行」，现在退化成只记「第几页」，于是那一整页都被标成 lossy，页里每一行都要拿条件重查。把滑块往右推，相当于把 work_mem 从 64kB 提到 64MB，页会陆续从 lossy 变回 exact，recheck 行数跟着下来。原文给的观察方法也是这个：同一条 SQL，先在 64kB 下跑 EXPLAIN (ANALYZE, BUFFERS)，再在 64MB 下跑，对比 Heap Blocks 的 lossy 和 Rows Removed by Index Recheck。但这里必须踩一脚刹车：不要顺手就在生产上把 work_mem 调到 64MB。work_mem 是「每个排序或哈希操作、每个并发查询」都可能申请的量，一条 SQL 看着温和，乘上并发就是实例级压力。正确顺序永远是先用 EXPLAIN 确认 lossy recheck 真的是瓶颈，再按并发量估内存上界。另外这是定性演示，不是实测数值。

五种方案，一张对比矩阵

把五种方案摆在一起，区别就清楚了。Multi-Index Bitmap Scan 的目标是「多个索引结果做 AND 或 OR，再访问 heap」，它的读取代价是多扫几次索引、做一次位图合并，换来 heap 的顺序访问；启动成本高，索引顺序丢了，写入上要维护多个单列索引；好处是对组合多变的条件特别灵活。多列 B-tree 索引一次扫描通常更精准，还能利用索引顺序，可它只对固定的主路径强，索引更宽、写入更重。单索引加 Filter 维护最轻，代价是过滤被推迟到回表之后，容易放大随机访问。Seq Scan 在结果接近全表时吞吐最稳，也没有索引维护。最后一列，持久化 Bitmap Index，是另一类东西：它用持久化位图表达值到行集合的映射，位运算快，但写放大明显，而且根本不是 PostgreSQL core 里 bitmap scan 的含义。这张表想说明的不是谁更高级，而是每一种方案都在拿某样东西换另一样东西。所以选型的分岔，不在数据库，在你的查询形态。

选型的分岔：主查询稳不稳

所以选型的分岔点，其实只有一个问题：主查询稳不稳定。如果长期固定成 city_id 等于某个值、status 等于某个值，再按 created_at 倒序取前 20 条，那就老老实实建一个多列索引，比如 city_id、status、created_at DESC。一次索引扫描既完成过滤，又按索引顺序返回结果，还能在取够 20 行时早停。Multi-Index Bitmap Scan 在这儿是明显吃亏的：它得先把位图建完，而且 heap 按物理页读，created_at DESC 的顺序彻底没了，通常还得额外排一次序。反过来，如果是检索页、运营后台、报表筛选这种条件组合天天变的地方，今天按城市和状态、明天按品类和时间，那就保留多个单列索引，让优化器按当次条件自由组合，BitmapAnd 或 BitmapOr 都能上，每个索引还能被单列查询单独用。再补三个判断帮忙定案：这条查询强不强依赖索引顺序、单列查询重不重要、写入和 VACUUM 的维护预算还有多少。那这个「组合多变」到底划算到什么程度？

只有中间地带才划算

把选择率从低到高铺开，胜出者会换三次。候选行极少的时候，普通 Index Scan 启动低、还能按索引顺序早停，Top-N 查询尤其明显；bitmap 光是把位图建完就已经亏了。到了中间区间，多个条件各自都不算窄，可交集一下子把候选集压得很小，bitmap 用一次固定的启动成本，换来按 heap block 顺序读表，把随机 I/O 收掉，这时候最划算。再往右，结果接近全表，Seq Scan 的顺序吞吐最稳，多扫几个索引纯属白干，优化器也会老实选全表扫描。然后再叠三个变量：启动成本会让小 LIMIT 查询更偏向 Index Scan；ORDER BY、LIMIT 这类排序需求会把优势推回能保顺序的索引；work_mem 太小产生 lossy page，等于把 bitmap 的曲线整体抬高。要强调一句，这是定性示意，不是实测曲线，本文不引用任何无法核验的性能数字——真正的边界得在你自己的数据上用 EXPLAIN 量。那怎么量？下一页。

适合、不适合，和七个坑

收敛一下。适合的场景四类：多个条件各自选择率一般、但交集明显缩小候选集；运营后台、搜索筛选、报表查询，条件组合经常变化；OR 的每一臂都有可用索引、结果又不接近全表；大表中等选择率过滤，普通 index scan 的随机回表成本偏高。不适合的六类：ORDER BY 加 LIMIT 强依赖索引顺序的 Top-N；单个多列索引能稳定覆盖主路径；结果接近全表，seq scan 更合适；work_mem 很紧张、bitmap 大量 lossify；OR 条件里存在不可索引分支；写入极重的系统，为了偶发的组合查询养着一大堆单列索引。七个坑也顺一遍：把它当持久化 bitmap index、看到 Recheck Cond 就判死刑、给每个字段都建索引期待自动组合、忽略条件相关性、在 Top-N 里强推 bitmap、拿 work_mem 一把梭、OR 只优化一半。你会发现它们指向同一句话：别把「用了索引」当成目标，真正的目标是少读页、少回表、少排序。好，最后我们把整条链收回来。

先算集合，再顺序读表

绕了一圈，回到最开始那句改写：先算候选集合，再按 heap 物理顺序访问表。多个弱选择性条件，各自扫索引得到 TIDBitmap，在内存里做一次 AND 或 OR，然后一次顺序读。换来的代价也很清楚：必须先建位图，所以有启动成本；顺序换成了物理页，所以索引顺序丢失；位图放在内存里，所以内存不够会掉精度、多出 recheck。所以它从来不是「更高级的索引」，而是优化器在中间地带算过账之后的一种取舍。最后补一点视野。Set Query 那条思路讲的是「谓词 → 命中集合 → 集合代数 → 取对象」，和今天这套抽象几乎是同一句话；列式、向量化引擎则会把过滤结果表示成 selection vector、validity mask 或压缩位图，用 CPU 友好的方式批量传播。但边界要守住：TIDBitmap 是执行期的临时结构，目标是减少 heap 随机访问，它不是面向分析场景的持久化压缩位图索引，PostgreSQL 的执行器也不是典型的向量化执行器——候选集合怎么表示，会一路影响到 CPU 和内存效率，这是延伸理解，不是当前实现。留五个问题给大家回去想。第一，为什么 BitmapAnd 能空集早停，BitmapOr 通常不能？第二，对 a 等于问号 AND b 等于问号 ORDER BY c LIMIT 20，什么时候该建 (a,b,c)，什么时候保留 a、b 单列索引？第三，a 和 b 高度相关，独立性估算会怎样影响计划？第四，为什么 PostgreSQL 的 bitmap heap scan 不能自然地支持 index-only scan？第五，列式向量化引擎里的 selection vector，和 TIDBitmap 有哪些相同与不同？前四个都能从今天这条链里推出来，第五个则把视野带到了向量化执行器——候选集合怎么表示，会一路影响到 CPU 和内存效率。想清楚这几个，这套机制就真是你的了。

承接 · NEXT　讲完了。真正的收获不是记住 BitmapAnd 和 BitmapOr 两个节点名，而是学会先问一句：候选集合，能不能先算清楚？
