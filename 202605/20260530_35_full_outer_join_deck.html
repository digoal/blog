01 / 20起点 · WHY

左右两侧，都不能无声消失

支付与订单对账、新旧系统割接、两条数据管道验数——它们问的是同一个问题：谁少了，谁多了，谁的值不一样。
图 1　两侧账本各自独有的部分，正是 INNER JOIN 看不见的部分；FULL JOIN 把两块缺口一起端上桌。

03 / 20盲区 · GAP

三种 join，各自只看得见一半

同一个问题拆成三问：两边都有谁？只在 A 的有谁？只在 B 的有谁？
图 3　用四个 txn_id 做覆盖检验：填色代表该行会出现在结果里。INNER 只覆盖 1、4；LEFT 覆盖 1、2、4；RIGHT 覆盖 1、3、4。

04 / 20定义 · SEMANTICS

官方定义：三块结果拼起来

FULL OUTER JOIN 不是模糊的「全都要」，它是三个集合的 UNION ALL。
图 4　PostgreSQL SELECT 文档与 queries.sgml 的定义：先 inner join，再分别追加左未匹配与右未匹配两组补 NULL 的行。
承接 · NEXT定义可以写成三段 UNION ALL，可 PostgreSQL 执行层并不真的跑三遍。

05 / 20辨析 · MODEL

能拼出等价结果，不等于它就这么执行

「FULL JOIN = LEFT JOIN 加 RIGHT JOIN」是一句方便的近似，但它描述的是结果，不是 PostgreSQL 的计划。
图 5　左：SQL 层可用 LEFT JOIN + RIGHT ANTI + UNION ALL 拼出等价集合，但两侧被扫描两次、各自成计划。右：PG 用单个 Hash Full Join 节点同时维护两侧的匹配状态。
承接 · NEXT单个节点要同时记住两侧的匹配状态，于是执行前先得决定：哪些行配对，哪些行补 NULL。

06 / 20时序 · ORDER

顺序决定命运：ON 在前，WHERE 在后

一次 FULL JOIN 查询，实际按四个阶段走；补 NULL 发生在过滤之前。
图 6　四阶段时序剖面，行数取自本文 DEMO 的示意数据：3+3 行输入 → 2 对匹配 → 补 NULL 后 4 行 → WHERE 只保留 3 行差异。

09 / 20反例 · ON CLAUSE

把金额塞进 ON，同 key 会裂成两条缺失

ON a.txn_id = b.txn_id AND a.amount = b.amount，看起来只是「顺便比一下」,其实改写了「匹配」的定义。
图 9　以 txn_id = 4 为例：ON 只放 key 时输出一行 amount_diff；把金额相等并入 ON 后，两行都不算匹配，各补 NULL 输出，差异被误报成两条缺失。
承接 · NEXT条件放错位置会毁掉语义；条件写得太复杂，则连计划都生成不出来。

10 / 20代价一 · CARDINALITY

结果的下限是 key 并集，上限不设防

两侧未匹配都要留，结果规模天然接近两侧 key 的并集；key 不唯一时，匹配部分还会做乘法。
图 10　示意数据：一对一粒度下输出 4 行（key 并集）；若 A 的某 key 有 2 行、B 有 3 行，匹配部分变成 2×3 = 6 行。
承接 · NEXT结果集大只是看得见的代价，看不见的代价在优化器：它不能像平时那样自由换顺序。

11 / 20代价二 · PLANNER

优化器在这里踩了一脚刹车

普通显式 join 会被 flatten 成一组关系供搜索；FULL JOIN 节点不折叠，当前代码完全不尝试重排它。
图 11　引自 src/backend/optimizer/README：FULL JOIN ordering is enforced by not collapsing FULL JOIN nodes when translating the jointree to joinlist representation。
承接 · NEXT不能重排的根本原因，是两侧的列在 JOIN 之上都可能变成 NULL。

12 / 20代价三 · VARNULLINGRELS

两侧的 Vars 都被标记为「可能为 NULL」

优化器必须区分「扫描层的列值」和「JOIN 之上可能已被 NULL 化的列值」，这个区分叫 varnullingrels。
图 12　引自 optimizer README：「For LEFT and RIGHT outer joins, only Vars coming from the nullable side ... For FULL joins, Vars from both inputs are marked.」
承接 · NEXT语义层、计划层都说清了，现在下到执行器：一个节点怎么把两侧的未匹配都找出来。

一个节点要同时输出两侧的未匹配行，就必须记住哈希侧每个条目「有没有被连过」。
输入 · A 侧 key B 侧 key 0 / 6 阶段

承接 · NEXT同一套双向状态，在 Merge Join 里换了个形态；Nested Loop 则根本没准备。

14 / 20执行器 · NODE MATRIX

只有 Hash 与 Merge 备齐了双向状态

PostgreSQL 的三种 join 节点里，能同时维护 outer/inner 两侧 fill 状态的只有两个。
图 14　字段名取自 nodeHashjoin.c、nodeMergejoin.c、nodeNestloop.c 与 execnodes.h；Nested Loop 只为 left/anti 准备了 nl_NullInnerTupleSlot。
承接 · NEXT既然物理算法只有两条路，那条路的条件就必须能被 hash 或 merge 消化。

15 / 20边界 · JOIN CONDITION

不是任何 ON 条件都能生成计划

没有有效的 hash 或 merge 路径时，planner 不会退化成通用嵌套循环，而是直接报错。
图 15　报错文本来自 joinrels.c；PostgreSQL Wiki 亦说明 FULL JOIN 条件须是 hashable、mergeable 或 constant，否则需要构造成 inner join 加两个 anti join 的 UNION。
承接 · NEXT把能力边界摊开，才好给「到底用哪种写法」一个不靠感觉的判断。

16 / 20横向对比 · TRADE-OFF

五种写法，一张能力对照表

完整差异面换来的是最小的优化空间；拆成多个分支则换个方向付成本。

排障顺序：先分类，再调参

对账结果异常时，先确认语义有没有歪，最后才动内存和索引。

18 / 20工程备选 · DECOMPOSE

拆成三个分支，是工程备选

INNER JOIN + 两个 NOT EXISTS 分支 + UNION ALL，语义等价，代价换成重复扫描与更长的 SQL。
图 18　三分支分别负责「值不同 / 只在 A / 只在 B」；每个分支可单独设计索引与计划，但两侧数据会被多次读取。
承接 · NEXT知道了备选方案，最后要回答的还是那个最朴素的问题：什么时候值得用 FULL JOIN。

19 / 20适用边界 · WHEN

什么时候该用，什么时候别用

判据只有一条：你是不是真的需要「双边缺失信息」。
