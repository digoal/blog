从关系到图：把 join 编译成邻接切片

我们先别急着谈 CSR，也别急着谈扩展。先回到一个很朴素的现场：绝大多数业务系统，一开始根本不是按「图数据库」设计的。用户、订单、设备、账号、公司、资金流、告警、工单、知识条目，都老老实实躺在 PostgreSQL 的普通表里，关系藏在主键、外键、关联表和几个业务字段里。这套设计在上线前是完全正确的，因为事务、约束、权限、备份，PostgreSQL 都已经替你做好了。

真正的变化发生在上线以后。业务开始问一些「关系型」的问题：一个客户两跳内关联了哪些账号和设备；两个主体为什么有关联，中间那条路径是什么；给大模型补上下文时，除了找相似文本，还得沿实体关系把证据补齐；而且所有这些，都希望不迁移数据、不重写业务事务链路，直接接进现有的 SQL。你看，这四个问题没有一个是在问「这张表有哪些行」，它们都在问「这一行沿着关系能走到哪里」。

所以这张剖面图想说的是责任的分布，不是产品的堆叠。最底下这一层，PostgreSQL 源表，承担 WAL、MVCC、约束、权限和备份，它是事实来源，谁也别想替换它；往上依次是注册元数据、节点编号、CSR 边数组、图内索引、SQL 函数；最上面才是业务问题。注意颜色：越深的靛青越底层。今天这一讲，我们就从最上面那层问题，一层一层往下挖，看看 pgGraph 到底在哪一层动了手，又在哪一层老老实实低了头。

这里先埋一个判断标准，后面会反复用到：它不是要替代图数据库，它只是把「反复读同一批关系拓扑」这件事，从每次查询临时拼 join，改成了提前编译好一份可重建的读优化结构。收益和代价，都从这一句里长出来。

PAGE 02 / 21

问题不是「把表画成点和边」

把这四问拆开看，会发现它们长得不一样，但骨架是一样的。第一问是邻域扩展，给一个起点、给一个深度上界，把两跳内碰到的账号、公司、设备全列出来；第二问是路径解释，光回答「有关联」不够，得把中间那条 edge_path 交出来，客服和风控都要拿它写结论；第三问是证据补齐，向量检索能告诉你哪段文本语义相近，但告诉不了你「这个实体和那份出处之间隔着什么关系」；第四问最容易被忽略，它其实不是功能需求，是约束条件——不迁移数据、不重写业务事务链路，把图查询接进 SQL。

为什么第四问这么关键？因为如果允许迁移，最简单的答案就是「换一个专用图数据库」：新的存储、新的查询语言、新的运维、新的权限体系，再加一条同步链路。可一旦把「源表保真」写成硬约束，可选空间立刻收窄：你只能在 PostgreSQL 里面想办法，要么写递归 CTE，要么在 SQL 之外挂一层可重建的派生结构。递归 CTE 是零成本的，属性图扩展是换模型的，pgGraph 走的是中间那条。

还有一个隐含的共同点值得点出来：这四类问题都不是「一次性的」。风控每天要问成百上千次，RAG 每次召回都要补证据，客服每次工单都要解释路径。也就是说，拓扑基本不变，查询反复发生。这句话听起来平淡，但它是后面整篇的立项依据——只有同一批关系被反复读，提前编译一份结构才划得来；如果每个查询都临时定义不同的边语义，编译的成本根本摊销不掉。

那接下来自然要问：既然关系一直都在，为什么现在直接查会别扭？我们到下一页去看递归 CTE 到底在每一跳里做了什么。

PAGE 03 / 21

关系藏在主键、外键和关联表里

先看左边。关系并没有消失，只是被关系模型「拆开」存了：users.id 是主键；orders.user_id 是指向 users 的外键；follows 这张关联表用 src、dst 两列同时引用 users；再往外，status、rel_type、tenant_id 这些业务字段还在 silently 定义着「什么样的边算有效」。所以图不是不存在，它只是被压扁成了若干张表和若干列，要用的时候得现场拼回来。

现场拼回来就是右边这四步。第一步按表名和主键找到起点行；第二步按外键或者关联表 join 出下一跳；第三步对下一跳重复同样的 join——深度是三，就重复三次；第四步还得自己维护 visited、深度、分页和去重，否则遇到环就停不下来，遇到高扇出节点中间结果会直接放大。写成递归 CTE 之后，好处非常明确：完全在线、完全关系化、源表怎么写它就怎么看，MVCC 和权限都是 PostgreSQL 原生的。

问题出在复杂度上。每换一种图拓扑，就要重新写一段递归 SQL；优化器面对多跳扩展，选择率很容易估错，尤其当某一跳的扇出突然变高；重复去重和中间结果放大又会把计划往更慢的方向带。原文说得很克制：「每种图拓扑都要重新表达，查询计划容易被多跳扩展、选择率误判、重复去重和中间结果放大拖慢」。注意这不是说递归 CTE 写错了，而是说代价中心落在了「每次查询都重新发现一遍邻居」上。

既然代价中心是「反复发现邻居」，那最直接的工程思路就是把它提前做掉：能不能在查询之前，把邻居按节点分组编译成一段连续数组，查询时只做扫描？这就是下一页那张转化表要讲的事。

把「反复 join」换成「预编译好的邻接扫描」

这张表是整讲的骨架，我一行一行念，但请你注意每一行的「收益」和「代价」是成对出现的，没有白拿的便宜。第一行，把多表 join 与递归扩展换成 node_idx 上的邻接数组扫描，热循环因此简单、缓存友好；代价是你得构建并维护一份派生图。第二行，起点本来由表名加主键表达，现在要先经 (table_oid, pk) → node_idx 解析成内部编号，好处是所有热路径只认整数，代价是多了一座叫 ResolutionIndex 的桥。

第三行，边类型本来是 rel_type 这样的文本业务字段，现在压成 u8 的 type_id，比较成本极低；代价是用户边标签最多 254 个——这个上限不是随便定的，是类型宽度直接决定的，后面讲最佳实践时还会回来。第四行，过滤本来要回源表判断，现在把注册过的过滤列预编码进 FilterIndex，遍历中就能剪枝；代价是过滤列必须提前注册，不能临时想加就加。第五行，多连接共享大图靠 .pggraph 只读 mmap，OS 页缓存可以共享那些固定数组页；代价是反向 CSR、FilterIndex、edge type registry 这些仍然是每个后端本地的堆结构，不是全共享。

把五行合起来看，结论就一句：pgGraph 选择牺牲一部分写后即时可见性和构建成本，换取读取时的稳定邻接访问。所以它适合「同一批关系拓扑被反复读」的工作负载；不适合「每次查询都改变拓扑」「全图实时 OLAP」「跨库分布式图计算」。这里我想强调一个容易被营销话术带偏的点：它不是让所有图查询都变快，它只是把一类特定查询的代价中心搬了家。

那搬完家以后，这份派生图自己长什么样？下一页用三层把它拆开：逻辑层定义点边是什么，物理层决定怎么存，执行层决定 SQL 怎么进去、结果怎么出来。

逻辑层、物理层、执行层

原文把图式存储分三层，这个分法很值得照抄，因为它能防止一个常见误解：以为装了扩展以后，数据就被搬进图里了。最底下的逻辑层说的是「什么东西算点、什么东西算边」——节点就是源表的一行，边来自外键、关联表或者专门的边表，而节点在业务侧的唯一坐标是 (source_table, primary_key)。这一层完全没脱离关系模型，它只是给关系模型加了一套图的说法。

中间的物理层才动手：节点被编号为连续的 node_idx: u32，边被编译进 CSR 数组——edge_offsets、targets、type_ids，加可选的 weights；旁边还站着两个辅助索引，ResolutionIndex 负责把业务坐标翻译成内部编号，FilterIndex 负责把过滤谓词预编码进图内存。注意这里的关键词是「编译」：这些数组不是查询时算出来的，是构建阶段一次性生成、之后反复读的。

最上面的执行层是 SQL 函数。graph.traverse 做有界邻域扩展，graph.search 做源表属性查找，shortest_path 和 weighted_shortest_path 做路径查询；它们先解析起点，再在 CSR 上跑 BFS、DFS、最短路径，最后返回源表坐标，或者按需要 hydrate 原始行。源码把这几层拆得很干净：builder.rs 读注册目录并流式构建 CSR，node_store.rs 用 Struct-of-Arrays 存节点状态，edge_store.rs 用 CSR 存边并提供 neighbors(node_idx) 连续切片，engine.rs 把 NodeStore、EdgeStore、FilterIndex、ResolutionIndex 和同步状态捏在一起，bfs.rs 和 path_finder.rs 跑热循环，persistence.rs 管 .pggraph 文件格式、CRC、mmap 与原子写入。

为什么我要把模块名念一遍？因为这些不是概念推演，是可以直接翻代码核对的实现事实。也正因为物理层是「编译产物」，它天然不是事实来源：删了可以重建，失效了可以失效，备份恢复、权限、审计仍然围绕 PostgreSQL 表做。这一点在第九节「常见坑」里排第一，不是偶然。

接下来我们进物理层，先看构建：一行源表数据是怎么变成一个整数编号，一条业务关系又是怎么变成 CSR 里的一段下标的。

先编号，再连边

构建从三张注册目录表开始：graph._registered_tables、graph._registered_edges、graph._registered_filter_columns。第一步读定义；第二步用 SPI 游标按 graph.build_batch_size 分批扫源表，这个「分批」很重要，它决定了大表构建时不会把全部源行一次性压进内存；第三步为每一行分配一个连续的 node_idx，同时记下这个节点来自哪张表（table_oid）、主键文本是什么、属于哪些租户（tenant_membership），以及稍后要写进 FilterIndex 的过滤列值。

边要麻烦一些，分两步。先从边源表读出源端点、目标端点、可选权重和可选动态标签；再用一张临时节点查找表，把端点主键解析成内部 node_idx，写进临时边 spool。然后按 (source, target, type_id) 排序，流式喂给 SortedEdgeStoreBuilder，生成 CSR。原文特意点出这里借鉴了稀疏矩阵转置、按行压缩组织的思想：先把边按行分组，再形成 offset 数组，而不是等查询时反复回关系表找邻居。这句话其实就是整篇论文背景的落点。

为什么非要「先 spool、再排序、再流式」？因为如果边不按 source 聚在一起，你就得为每个节点维护一个可变列表，内存里会出现大量分散分配；排序之后，同一起点的边天然连续，offset 数组一次扫描就能算出来，构建期也不必长期持有全部原始边对象。这是典型的用一点构建期 CPU 和临时磁盘/内存，换一个查询期极其简单的数据结构。

产物是两样东西：NodeStore，用 SoA 存节点状态、表 OID 和主键；EdgeStore，用 CSR 存边，neighbors(node_idx) 直接返回连续切片。好，现在到了最该慢下来的一页——这个切片到底长什么样，为什么两次数组读取就能替代一次 join。

邻居是一段连续切片

请把这一页的动画亲手点一遍，比听我讲十遍都管用。公式其实只有一行：节点 i 的出边目标，等于 targets 里从 edge_offsets[i] 到 edge_offsets[i+1] 的这一段；边类型和权重在同样的下标范围内，所以一次切片能同时拿到邻居、类型和权重。edge_offsets 的长度是 node_count + 1，多出来的那一位就是为了让最后一个节点也能用「后一个减前一个」算出边界。

我们按单步走一遍。第一步读 edge_offsets[i]，得到 start；第二步读 edge_offsets[i+1]，得到 end，两者相减就是出度，完全不用遍历；第三步顺序扫描 targets[start..end]，这就是全部邻居；第四步在同样的下标范围读 type_ids，边类型和邻居一一对应；第五步把 (node_idx, type_id) 交给后面的 visited 和剪枝判断。你可以把输入框改成 4 试试——那一格出度是 0，start 等于 end，切片为空，节点直接跳过，连扫描都不用做。

这里最值得停下来体会的是「不需要什么」：不需要哈希表查某个节点有哪些边，不需要二分查找，不需要回表 join，不需要解引用一堆指针。只要两次数组读取定位边界，然后顺着内存往前走。原文把它概括成遍历热路径变成「frontier 出队 → 取连续邻接切片 → 检查候选节点 → 入队」，这个循环短到几乎可以整段待在缓存里。

当然，CSR 也有它的反面：它对读取极其友好，对原地更新极其不友好。Boost 的 compressed_sparse_row_graph 文档里干脆直接写「cannot add or remove vertices or edges」。所以后面讲同步时你会看到，拓扑变更只能走覆盖层或者重建，这不是 pgGraph 偷懒，是数据结构本身的性质。下一页我们先把「为什么连续内存这么关键」说透，顺便把 Ligra 那条论文线索接上。

快在热循环贴近连续内存

我们得把「快」拆到硬件层面，否则很容易变成口号。左边是常见的按对象存：每个节点一段独立分配的邻居列表，扫描时要在好几个堆块之间跳，cache line 不连续，硬件预取器看不出规律；右边是 CSR，targets 是一整条连续数组，某个节点的邻居就是其中一段，扫描是纯顺序的，预取器能提前把后面的 cache line 拉进来。渐进复杂度其实没变，都是 O(n + m)，变的是常数：局部性、分配次数、可序列化程度，以及能不能被 mmap 直接映射。

Ligra 那篇论文就是把这个常识框架化的。它是 2013 年 PPoPP 上 Shun 和 Blelloch 的共享内存图处理框架，接口小得惊人：一个 graph，一个表示「本轮活跃顶点集合」的 vertexSubset，加 vertexMap 和 edgeMap 两个操作。BFS 就是反复用 edgeMap 把当前 frontier 的出边过一遍，靠一个 CAS 判断有没有访问过，生成下一轮 frontier。更有意思的是 edgeMap 会按 frontier 的规模在稀疏和密集两种处理之间切换：frontier 小就顺着活跃顶点的邻接表读，frontier 大就反过来扫所有顶点测试是否属于 frontier。

原文引用 Ligra 时很克制，我也要照着克制：pgGraph 不是通用批量图计算框架，它跑在 PostgreSQL 后端里、服务于 SQL 函数，不做 PageRank、连通分量这类全图分析。它借的只有一条——图算法的内层循环要尽量贴近连续内存访问，减少对象跳转和随机查找。但 Ligra 的「frontier 规模决定策略」这个思想，和后面 bfs.rs 里的剪枝、断路器是同一种工程直觉：别让扩张失控。

顺带把一个伏笔坐实：正因为 CSR 是连续且不可变的，它才能被 mmap 成只读视图、被多个后端共享，也正因为不可变，写后即时可见性就得靠别的机制补。后面讲持久化时会回来。现在先补两块拼图：节点元数据怎么按冷热分开，以及用户写的表名加主键，怎么变成引擎认得的 node_idx。

冷热分离的并列数组，和一座坐标桥

先看左边。NodeStore 没有把每个节点做成一个大对象，而是拆成几条并行数组：is_active 是 tombstone 标记，删除后置为 inactive；table_oids 记节点来自哪张源表；primary_keys 或者 offset 加 bytes，只在输出结果和 hydrate 时才用。原文给了一个很实用的热度判断：is_active 是热的，table_oids 中等，主键是冷的。所以 BFS 在热循环里反复检查 active 状态时，缓存里不会挤进一堆根本用不上的字符串。这就是 Struct-of-Arrays 的价值，不是什么时髦的布局技巧，而是「别让冷数据污染热路径」。

加载 .pggraph 之后，active bits、table OID、主键 offsets 和主键 bytes 都可以从 mmap 区域直接读，不需要在 Rust 堆里再复制一份。这也呼应了前面那句：共享的是文件映射进来的固定数组页，不是所有结构都共享。

右边这座桥更容易被忽略，但没有它整个东西用不起来。用户调用 SQL 时写的是 seed_table := 'public.users'::regclass、seed_id := 'u1'，他不可能知道也不该知道 node_idx 是几。执行器必须先把 (table_oid, pk) 解析成内部节点，ResolutionIndex 就干这件事：构建时先把条目累计起来，finalize 之后转成排序后的字节数组，查询时二分查找；加载 .pggraph 之后，这个索引也可以直接在 mmap 字节段上查。

所以每多一座桥，就多一份代价，也多一份确定性：解析是 O(log n) 的二分，换来后续所有热循环只跟连续整数打交道。把 SoA 和 ResolutionIndex 放一起看，pgGraph 的设计取向就很清楚了——所有能在构建期算好、排序好、压平的东西，都尽量别留到查询期。下一页讲 FilterIndex，会把这个取向推到极致：连「这个邻居该不该要」的判断，都不让它回源表。

搜索和遍历过滤，是两条不同的路径

这一页请务必和第九节的第 4 个坑一起记，因为它是实操里最高频的误会。原文写得很清楚：搜索和遍历过滤是两件事。graph.search() 面向源表列，通过 PostgreSQL 的 SQL 谓词找候选源行，参数叫 property_key、property_value、table_filter、mode，返回 match_type 和 verified；graph.traverse(filter := ...) 面向的是遍历过程中的候选节点，只有注册过的 filter column 才会被预编码进 FilterIndex。

对应到注册动作上，就是上面两个框。graph.add_table(columns := ARRAY['name','status']) 里的 columns，只服务于 search；想让 age >= 40、status in (...) 这类谓词在遍历热循环里直接生效，必须显式调用 graph.add_filter_column('public.users'::regclass, 'age', 'numeric')。两者的执行路径完全不同：一个走 PostgreSQL 的扫描和索引，一个走在图内存里预编码好的值。

FilterIndex 本身也有讲究。它支持 numeric、boolean、text、date、timestamptz、uuid 等类型，会按列的稀疏程度选择 dense 或 sparse 存储，原文给的阈值是「填充值低于节点数 15%」。这句话背后是很朴素的取舍：一列值只在少数节点上出现，就别为每个节点都留一格；反之用 dense 直接按 node_idx 下标访问更快。于是热循环遇到候选节点时，可以直接在内部索引里判断 age 是否大于等于 40、status 是否在集合里、created_at 是否非空，不必每个邻居都回源表。

还有一个反向的提醒：graph.search() 仍然是源表 SQL 谓词，不是全文索引，也不是向量索引的替代品。所以大表上做 contains 搜索，该建的 pg_trgm 还是得建；精确、大小写不敏感的匹配，可以考虑 lower(col::text) 表达式索引。把这两条路径分清楚，你才知道该去优化 PostgreSQL 的索引，还是该去注册一个过滤列。

为什么我这一页的标题叫「剪枝比扩展更重要」？因为 CSR 只解决了「拿邻居很快」，没解决「该拿多少」。社交、风控、知识图谱这类高扇出图，一个起点可能有成千上万条出边，两跳之后就是平方级增长。原文说得很直接：如果没有深度、节点数和 frontier 限制，一次用户查询就可能变成不可控的全图扩张。所以 DBA 那条最佳实践不是保守，是硬要求——不要把无界图扩张暴露给前端。

把前几页连起来看：连续切片让「取邻居」变便宜，FilterIndex 让「判断邻居」不回表，六道闸门让「留下谁」尽早决定。这三者凑齐，才是一个能在生产里被调用的图遍历。下一页我们把视角翻回业务侧，看看这些能力以什么形式出现在 SQL 里。

四个函数，四类问题

把原文 6.3 的四段示例并排放，接口边界就很清楚了。graph.traverse 是有界邻域扩展：给 seed_table、seed_id、max_depth，再用 edge_types、direction、filter、tenant 收窄范围，返回 node_table_name、node_id、depth、edge_path。它对应第一页第一问和第二问，既给邻域也给路径解释。graph.search 是源表属性查找：property_key、property_value、table_filter、mode，返回 match_type 和 verified，注意它走的是源表谓词，跟图内存无关。

另外两个是路径函数。graph.shortest_path 做无权最短路径，返回 step、node_id、edge_label；weighted_shortest_path 做带权最短路径，会用到构建时写进 weights[E] 的权重，返回 edge_weight 和 total_cost。原文 DEMO 里 follows 表有个 strength 列，通过 weight_column := 'strength' 注册，就是给这条路用的。四个函数都带 hydrate 参数：false 的时候只返回坐标和路径元数据，true 的时候才把原始行取回来。

这个「先坐标、后 hydrate」的默认值很值得抄进自己的应用。因为图查询最容易膨胀的地方不是遍历本身，而是把成百上千个命中节点都回表 join 一遍；而多数场景里，前端列表只需要「谁、第几跳、经过什么边」，点开详情才需要完整行。原文给业务开发者的建议也是这一条：UI 返回路径解释时优先给 path、edge_path 和源表坐标，只有展示详情时再 hydrate。

接口讲完，还剩一个很实在的问题：每个 PostgreSQL 后端都是独立进程，如果每个连接都把整张图在内存里复制一份，这套方案根本没法上线。所以下一页讲 .pggraph 文件和 mmap——但我要提前把边界说在前面：共享的是 OS 页缓存里的固定数组页，不是 PostgreSQL 的 shared buffers，也不是跨后端共享 Rust 堆。

派生图不是新存储引擎

persistence.rs 把这件事做得很「文件」而不是很「数据库」。.pggraph 的文件头包含 magic、version、flags、node_count、edge_count、11 个 section offset 和 CRC；主要 section 包括 active bits、table OID 数组、CSR 的 offsets / targets / type_ids / weights、ResolutionIndex、主键 offsets 与 bytes、FilterIndex 的 bincode、以及 edge type registry 的 bincode。左边这张图就是按这个顺序排下来的，注意 CSR 那四段是整块连续数组，这正是它们能被直接映射成只读视图的前提。

写入路径是临时文件、回填 header、fsync、rename——典型的原子替换，不搞原地改写。加载时先验证 magic、版本、CRC、section 边界、对齐、CSR offset 单调性和 target 范围，全部通过之后才把不可变数组 mmap 成只读视图。这一串校验不是形式主义：mmap 之后你几乎是把文件内容当内存直接读，边界错了就是越界访问，所以必须在映射前把结构完整性钉死。

右边是更容易被讲错的地方，我按原文再强调一次：mmap 共享的是 OS 页缓存里那些固定数组页，多个后端可以映射同一批物理页，从而不必把基础图复制进每个后端的 Rust 堆；但它不是 PostgreSQL shared buffers，也不是跨后端共享 Rust 堆。反向 CSR、FilterIndex、edge type registry、同步 overlay 仍然是每个后端本地结构，每个 PostgreSQL 后端都有自己的 active Engine。

理解了这个边界，很多现象就不用奇怪了：为什么开启持久化要关心版本兼容和 auto-load，为什么维护重建会有「双内存窗口」，为什么有些结构没法简单地「大家一起看」。下一页把整个生命周期串起来：构建一次之后，源表还在不停写入，图怎么跟上，又怎么把覆盖层收回去。

基础 CSR 不原地改写

这四行是一个回路，不要把它读成四条独立功能。第一行是构建：注册目录 → graph.build() → .pggraph 原子写入；第二行是查询：多个后端只读 mmap 加载 → resolve 起点、BFS、输出 → 返回源表坐标或按需 hydrate。到这一步为止，图是静态的、干净的、可共享的。

第三行才是现实：源表还在被 INSERT / UPDATE / DELETE。原文给的路径是设置 graph.sync_mode = 'trigger'、graph.enable_sync()、重新 build，之后写入会被触发器记进 _sync_log，graph.apply_sync() 把变更变成节点增量、边覆盖层和 tombstone。注意「基础 CSR 不会原地改写」——overlay 是叠在只读基础图上面的一层，查询时要把两者合并着看。这也解释了为什么 CSR 不可变却还能支持写入：变的不是基础数组，是旁边的增量层。

第四行是收尾。覆盖层或 tombstone 积累到一定程度，就得用 graph.maintenance()（或 graph.vacuum()）把 overlay 合回基础 CSR。原文明确说当前是完整重建，会存在新旧 engine 共存的双内存窗口，所以最佳实践里才建议避开 OLTP 高峰、放到低峰窗口或专门调度里。回路右边那条线就是重建后写出新文件、重新回到第一行。

还有两个必须说清的边界：一是原文特别标注 wal sync mode 和 copy build scan mode 当前都是保留项，不要当成可用生产路径——这种「文档里写了但还不能用了」的地方，照抄进生产方案是要出事的；二是 DBA 要定期看 graph.sync_health() 的 edge_buffer_used、pending_sync_rows、needs_vacuum、needs_rebuild、read_only_reason，别等查询变慢了才想起来有覆盖层。

折中点的边界在哪里

原文第四节给了五个方案八维度的对比表，我把它压成一张定位图。横轴是「关系表保真度 / PostgreSQL 原生运维」，越往右越保留原有 schema、权限、MVCC 和运维习惯；纵轴是「遍历热路径专用化程度」，越往上越为图遍历做了专门的数据结构。左下角基本是目标外区域：跨库分布式全图 OLAP，本来就不该在 OLTP 主库上做。

右下是递归 CTE 和普通 SQL：零派生存储，完全关系化，适合低频、浅层、schema 简单；代价是多跳高扇出时计划不稳。右上是 pgGraph：源表仍是事实来源，同时把邻接编译成 CSR，所以保真度和热路径专用化都高，代价是派生图要构建、同步、维护。左侧是 Apache AGE 这类属性图数据库——它用 graph 命名空间、vertex / edge 表、agtype 和 openCypher，把图模型当成一等存储对象，适合「图本身就是事实来源」的应用；再往上是 Ligra 这类共享内存图计算框架，面向离线批量全图分析，通常不在 OLTP 事务内。

这里我要补一条原文写作时还没完全落地、但今天必须知道的现状。2026 年 3 月，PostgreSQL 社区把 SQL/PGQ 实现合入了 master（对应 PG 19），标准是 ISO/IEC 9075-16:2023：新增 GRAPH_TABLE 表函数、CREATE / ALTER / DROP PROPERTY GRAPH、系统目录和 psql 的 \dG。它的实现是重写器——属性图像视图一样被改写成关系 join，所以现有索引和优化器直接复用，不需要额外存储。但首版只支持固定深度模式，变长路径（*、+、{m,n}）和最短路径还没进这个补丁，那些仍要靠递归 CTE。

这条补充恰好回应了原文第十节的第一问：「如果 PostgreSQL 未来 SQL/PGQ 可以表达图模式，哪些模式适合直接走关系优化器，哪些适合下推到 CSR 运行时？」现在的答案是：标准表达与 CSR 热路径不在同一层。SQL/PGQ 解决「怎么写得标准、怎么复用索引」，pgGraph 解决「反复跑的有界遍历热循环有多便宜」。对固定深度、浅层模式，前者已经很好；对需要预计算邻接、需要路径解释与断路器、需要反复读同一拓扑的场景，后者仍有独立价值。

把这页收成一句：关系表保真度越重要、查询越偏有界邻域，pgGraph 越有价值；如果图本身就是事实来源，或者需要分布式全图算法，就该考虑别的系统。下一页不再谈定位，专门把「什么条件下真的快」和「要付什么」摆在一起。

「CSR 很快」是有条件的

原文第五节开头第一句就是「不要把『CSR 很快』理解成任何图查询都会快」，我很喜欢这种写法，因为它把边界写在收益前面。四条前置条件：同一拓扑被反复查询，构建成本能摊销；查询是有界遍历、路径解释或局部邻域扩展；起点能快速解析，边类型和过滤列能在图内剪枝；结果只需要返回源表坐标，必要时再 hydrate 少量行。少一条，收益就打折。

收益有五个来源，前面其实都出现过，这里串一遍：邻接访问从 join 变成连续数组扫描；访问状态用 bitmap / RoaringBitmap 表达；边标签压成 u8、过滤列预编码；mmap 让固定图数组经 OS 页缓存被后端共享；构建阶段用临时 spool 和排序流式生成 CSR，避免长期持有全部原始边。你会发现没有一条是「算法更聪明」，全都是「把工作提前做掉、把数据摆得更顺」。

代价同样六条，而且和收益一一对应：构建要扫注册表和边源表；基础 CSR 不可变，拓扑变更需要 overlay 或重建；vacuum / maintenance 当前是完整重建，存在双内存窗口；graph.search() 仍走源表 SQL 谓词，不是全文索引或向量索引替代品；边标签用 u8，用户边标签上限 254 个；每个 PostgreSQL 后端有自己的 active Engine，不是所有结构都共享。

我想特别点一下最后两条，因为它们最容易在方案评审里被漏掉。254 这个上限意味着你不能把高基数字段——比如订单号、业务 ID——直接拿去当 edge label，那是热路径上的类型 ID，不是属性；而「每后端独立 Engine」意味着内存规划不能只按一份图算，连接数一多，本地堆里那些不共享的结构要单独估。原文建议构建前跑 graph.estimate()、设置 graph.memory_limit_mb 和 graph.oom_action，就是冲着这个来的。

好，机制、边界、代价都讲完了，接下来给它一副能上手的骨架：从建表注册，到构建检查，到四类查询，再到同步维护，一条最小可复制的 SQL 路径。

从建表到同步，一条最小路径

先声明一件很重要的事：原文明确写了「本文没有在本机安装并启动扩展，因此不提供伪造执行结果」。所以这一页只给模板，不给任何编造的耗时、行数或倍数。做技术演说最忌讳的就是把示意数字讲成实测，我宁可少一张漂亮图表。

三个角色，三套约束

业务开发者那五条，核心只有一个词：有边界。把 graph.traverse() 当成「有边界的关系扩展」，不是任意全图搜索；能用 edge_types、node_tables、tenant、filter 缩小范围就尽早缩小；返回路径解释时优先给 path、edge_path 和源表坐标，只有展示详情才 hydrate；RAG 场景里，向量检索负责「语义相似」，图遍历负责「实体关系补证据」，不要让图遍历替代全文或向量召回。

用在哪，不用在哪

适合这边五类，其实都是同一个模板的变体：从一个已知起点出发，沿已经存在的关系走有限的几跳，并且要求结果能解释。风控是账号、设备、手机号、银行卡、IP、公司之间 1 到 3 跳扩展；客服 CRM 是客户、订单、合同、工单、联系人之间的路径说明；告警根因辅助是服务、实例、任务、依赖、变更之间的邻域搜索；知识库 RAG 是从命中文档实体出发，扩展相邻实体、出处、上下位关系；最后一类最直白——现有 PostgreSQL 应用想补图能力，但不想把主数据迁到图数据库。

不适合这边六类，也都能用一句机制解释。每秒大量拓扑写入、并且要求所有连接立即看到完整一致图，不行，因为基础 CSR 不可变、同步走覆盖层；无深度限制的社交网络全图探索，不行，因为断路器本来就是这套设计的必要组成；跨数据库、跨集群的分布式图 join，不行，因为这是一个进程内的派生索引；PageRank、连通分量这类长时间全图分析放在 OLTP 主库上跑，不行，这也是原文把 Ligra 类框架单独列出来的原因；需要 Cypher、Gremlin、SPARQL、GQL 完整语义，不行，接口是 SQL 函数；边标签高基数到接近业务 ID 级别，不行，u8 上限 254 摆在那儿。

我给一个很实用的三问自检，评审时可以直接用：第一，源表是不是事实来源？如果图本身才是事实来源，去看 AGE 那类系统。第二，拓扑是不是相对稳定、且被反复读？如果每次查询都换边语义，编译不划算。第三，遍历有没有明确上界，结果要不要可解释？如果答案是「越全越好、越深越好」，那你要的其实是离线图计算，不是这个。

八个坑，八条纠偏

第一条，把派生图当事实来源。.pggraph 可删、可重建、可失效，备份恢复、权限和数据审计仍然围绕 PostgreSQL 表做。这是第五页底部那条橙带的反面，也是最容易在故障演练里暴露的一条——有人把图文件当数据库备份了，结果恢复流程根本对不上。

第二条，不设查询断路器。图查询最容易出问题的不是单条边慢，而是高扇出扩张，深度、节点数、frontier、分页必须显式限制。第三条，忘记维护同步覆盖层：trigger sync 能让变更进入 _sync_log 和 overlay，但基础 CSR 不会原地改写，overlay 积累后需要 maintenance / vacuum。这三条是架构级的，出了就是事故；后面五条更偏细节，但一样常见。

第四条，把搜索列和过滤列混淆——columns 供 graph.search() 查源表，add_filter_column() 才进入遍历 FilterIndex，这是第十页那张分叉图。第五条，对 contains 搜索没建索引：graph.search() 还是源表 SQL 谓词，大表 substring 没有 trigram 或表达式索引，会慢在 PostgreSQL 扫描上，跟 CSR 一点关系都没有。第六条，过度依赖 auto-discover：它适合快速开始和规范 FK schema，但关系表、动态 label、权重、多租户、搜索列边界最好手动注册。

第七条，把 edge label 当业务属性乱塞：label 是热路径上的 u8 类型 ID，不适合当高基数属性，高基数属性应该留在节点或边源表列里，或者在业务层过滤。第八条，在主库高峰跑全图维护：maintenance / vacuum 是重建路径，大图应该放到只读副本、低峰窗口或专门调度里。

八条讲完，你会发现没有一条需要新概念，全是把前面已经成立的边界再强调一次。技术选型里真正难的不是学会一个结构，是记住它不承诺什么。最后我们用一页把因果链收起来，顺便留五个值得继续追的问题。

一句话收束，五个开放问题

把整讲压成一条链：业务开始问多跳邻域、路径解释、证据链；递归 join 在高扇出下选择率误判、中间结果放大；于是把关系编译成 CSR 派生图，但源表仍是事实来源；热循环用六道剪枝加断路器把扩张关在边界内；最后，有界遍历、路径解释和 RAG 补证据变得可预期。链子旁边始终挂着同一句代价：写后即时可见性，加上派生图的构建与维护成本。少了这句，前面所有收益都是半句话。

原文第十节留了五个问题，我按今天的进展各补一句。第一问，SQL/PGQ 哪些模式适合走关系优化器、哪些适合下推到 CSR 运行时——2026 年 3 月 PG 19 已合入 SQL/PGQ 固定深度实现，重写为关系 join 并复用现有索引，变长路径和最短路径还在后续补丁里，所以这一问现在有了半个答案。第二问，CSR 读友好但更新不友好，高频在线拓扑变更该用 delta CSR、LSM-like 边段，还是换可变图存储——这其实是在问「覆盖层要不要长期化」。

第三问，RAG 里图关系扩展该放在向量召回前、召回后，还是 rerank 阶段——不同选择会怎样影响召回率和延迟；结合这一讲的结论，我倾向于把它放在召回后补证据，因为图遍历擅长的是有界关系扩展，不是语义召回。第四问，多租户隔离放在节点 membership bitmap、边构建阶段，还是查询入口权限层，各自有什么风险；pgGraph 现在的答案是在第四道闸门用位图，但入口权限层仍应是纵深防御的一部分。第五问，一张边表有上百种关系类型时，哪些该建成 edge label、哪些该留作过滤属性——254 的 u8 上限和 FilterIndex 的注册成本，就是这道题的两个约束。
