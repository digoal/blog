本页讲稿

PostgreSQL 等待事件体系与实现机制

PAGE 01 · 数据库筑基课 · 等待事件 / 00 开篇

咱们从一个特别常见的现场开始：业务说接口超时，你登上去看，CPU 没跑满，磁盘 IO wait 也不高，pg_stat_activity 里几个会话的 state 还是 active，看着都在干活。这时候最容易陷入僵局——数据库到底在忙什么？忙得值不值？该不该优化？

这一场要讲的就是解开僵局的钥匙：等待事件。我会带你从 pg_stat_activity 里那两个不起眼的字段，一路走到 PostgreSQL 内核的共享内存，最后落在一个 32 位整数上。全篇的结论不是推出来的，是拿 PG 20devel 的源码和自己编译的实例互相验证过的：直接读共享内存里的原始值，跟 SQL 视图交叉比对，17 组采样逐条一致，不一致 0 条。

所以主线只有一句：一次等待，怎么变成一个整数，再变回两个字符串。我们把这条链路从上到下剖开，顺便把升级、踩坑、实操一并讲清楚。

系统指标看不见「数据库内部在等什么」

PAGE 02 · 数据库筑基课 · 等待事件 / 01 缘起 · 诊断盲区

先把僵局说透。没有等待事件的年代，DBA 手里基本就两把工具：top 看 CPU、iostat 看磁盘。它们告诉你的是「进程处于什么状态」——比如不可中断睡眠的 D 状态——但不告诉你「数据库内部在等什么」。

问题就出在这儿：一个 D 状态的进程，可能是在等磁盘，可能是在等一把被别的事务占着的行锁，也可能是在等一个还没算完的并行 hash 表。这三种情况从系统层面长得一模一样，可处置动作天差地别：第一种去查存储，第二种去查事务逻辑，第三种去查并行度。

PostgreSQL 9.2 引入等待事件，补的就是这层信息：让数据库自己说清楚，我现在在等什么。它把「进程此刻为什么不能继续干活」做成了一套可分类、可累计、可观测的标准。那有了这层信息之后，判断能精确到什么地步？

把「慢」翻译成「卡在哪」

PAGE 03 · 数据库筑基课 · 等待事件 / 01 缘起 · 两层价值

有了等待事件，「数据库很慢」就不再是一句含糊的抱怨，而能被切成两条完全不同的归因。一条是大量会话卡在 IO / WalWrite，说明 WAL 刷盘是瓶颈，动作是查存储和 checkpoint 配置；另一条是大家都在等 Lock / transactionid，说明一批事务在互相等，动作是查事务设计和隔离级别。同样的「慢」，两个方向，千万别走错。

第二层价值容易被忽略：可累加。单次采样看到的等待是瞬时的，某个会话碰巧在等磁盘，不代表整体有问题。真正有价值的是按类型、按时间窗口做统计聚合，看出结构性的问题。所以 pg_stat_activity 给的是实时视图，pg_wait_sampling 这类扩展给的是聚合视角，两者互补，不是二选一。

还有个隐藏收益：等待事件其实是理解 PostgreSQL 并发机制的钥匙。你问「为什么这个 UPDATE 卡住」，源码的答案是它在 LWLockAcquire 里等 WALWrite 这个 tranche 上的轻量锁，而视图告诉你 wait_event_type = LWLock——等你弄明白编码，会发现源码和观测数据是同一套语言的两面。那这两个字段到底长什么样？

类型可加，事件唯一

PAGE 04 · 数据库筑基课 · 等待事件 / 02 是什么 · 两个字段

SQL 层看到的就是 pg_stat_activity 里的两个字段。wait_event_type 是大类，Lock、LWLock、IO、IPC、Client、Timeout、Buffer、Activity 这种粗粒度归类；wait_event 是具体原因，transactionid、tuple、WalWrite、DataFileRead 这种精确到某个资源的名字。

两者是严格包含关系：一个 wait_event 恰好属于一个 wait_event_type，比如 WalWrite 必然是 IO。为什么要分两层？因为用途不同。类型是可加的，你可以 GROUP BY wait_event_type，得到「这批会话里多少在等 IO、多少在等锁」，用来判断整体健康度；事件是唯一的、不可加的，WalWrite 和 DataFileRead 都是 IO，但持续时间可能差几个数量级，直接相加没意义，它的用处是精确定位。

所以实操里永远是「先看类型定方向，再看事件挖根因」。但这里有个更根本的问题：这两个字段在数据库里到底存了几份？答案可能跟你直觉不一样——先把它抽象成三层模型。

类 / 事件 / 编码：同一份数据的三种看法

PAGE 05 · 数据库筑基课 · 等待事件 / 02 是什么 · 三层模型

精确的模型是三层。最上面是等待类 class，10 个已定义，载体是 wait_classes.h 里的宏，比如 PG_WAIT_IO = 0x0A000000；中间是具体事件 event，枚举 190 个加动态 102 个，载体是 wait_event_types.h、locktag 类型、tranche 编号；最底下是编码 encoding，就是一个 32 位整数，放在 PGPROC.wait_event_info 里，比如 0x0A000052。

注意这三层不是三份数据，是同一份数据的三种看法，而且严格对应：class 提供高 8 位，event 提供低 16 位，合起来就是那个 uint32。这就像地层剖面——越往下越贴近物理实现，越往上越是给人看的分类。

那这个 32 位整数到底怎么切？这是全篇最核心的一页，我专门做了一个可以输入、可以逐步播放的动画，咱们亲手把一个实测值拆开看。

wait_event_info：高 8 位是类，低 16 位是事件

PAGE 06 · 数据库筑基课 · 等待事件 / 03 核心原理 · 32 位编码

先看 wait_classes.h 里那排常量：0x01000000、0x03000000 一直到 0x0B000000。每个常量的高 8 位是 class 编号，低 24 位全是 0。对应的掩码在 wait_event.c 里：WAIT_EVENT_CLASS_MASK = 0xFF000000，WAIT_EVENT_ID_MASK = 0x0000FFFF。

于是位布局就是：高 8 位 class、中间 8 位保留恒 0、低 16 位 event。取 class 和取 event 各一次按位与就够了，连除法取模都不用。我在实测里反复确认过，所有采到的原始值，0x00FF0000 这一段都是 0。

这一页请你自己动手：输入框里默认是实测的 0x0A000052，也可以从下拉里换另外三组实测样本，甚至随便输一个十六进制值。按「播放」或者「单步」，看它先切出 class、再验证保留位、再切出 eventId，最后解出两个字符串；「重置」回到起点。这一步走完，后面所有链条都好理解了。

中间 8 位不是浪费，是给未来留的余量

PAGE 07 · 数据库筑基课 · 等待事件 / 03 核心原理 · 保留位

为什么中间要空 8 位？设想另一种设计：高 8 位 class 加低 24 位 event。看着更紧凑，可一旦将来要新增一个大类，同时还得保持已有 ABI 兼容，你就得从那 24 位里挪位给 class，event 的取值空间被压缩，已经发出去的编码全得改。

现在的做法把 class 钉死在最高 8 位，剩下 16 位整个留给 event，中间 8 位完全空着，任何时候都能拿来扩展划分粒度。低 16 位够不够用？IO 目前 83 个事件，IPC 65 个，最多的 LWLock 89 个 tranche，而 16 位能装 65536 个，绰绰有余。

还有个工程上的小便宜：取 class 和取 event 都只是一次按位与，不需要除法和取模。顺带纠正一个常见误解——中间 8 位不是「另有用途」，当前版本没有任何代码写它；如果你的监控脚本读到中间有值，那不是新特性，是读错内存位置了。编码定下来，接下来问：谁在什么时候把这个值写进去？

等待点前后，各上报一次

PAGE 08 · 数据库筑基课 · 等待事件 / 03 核心原理 · 上报

答案很朴素：业务代码在进入等待循环之前、退出等待循环之后，各调用一次上报函数。典型的等轻量锁，在 lwlock.c 里是 pgstat_report_wait_start(PG_WAIT_LWLOCK | lock->tranche)，然后进等待循环，出来再 pgstat_report_wait_end()。

关键就在那一按位或。PG_WAIT_LWLOCK 是 0x01000000，lock->tranche 是该轻量锁所属 tranche 的编号，或起来就是一个完整的 wait_event_info。等 heavyweight lock 也一样，proc.c 里 WaitLatch() 的最后一个参数就是 PG_WAIT_LOCK | locktag_type；transactionid 在 LockTagTypeNames 数组下标 5，所以 0x03000000 | 5 = 0x03000005，我实测读到的正是这个值。

这里有个重要含义：wait_event_info 只在确实处于等待状态时非零。进程在跑 SQL、没等任何东西，它就是 0，视图里两个字段都是 NULL。也就是说，这是一个「瞬时状态」，不是计数器。那这个瞬时状态存在哪儿？

PGPROC 里最后那 4 个字节

PAGE 09 · 数据库筑基课 · 等待事件 / 03 核心原理 · 存储

存在 PGPROC 里。src/include/storage/proc.h 中，wait_event_info 是结构体的最后一个字段，放在专门的 Status reporting 注释块下，前面紧邻的是 group commit 用的 clogGroupMemberLsn。顺便澄清一个容易混的点：结构体前部还有个 uint8 statusFlags，那是进程状态标志位，跟等待事件毫无关系；pg_stat_activity 里的 state 和 wait_event 是两套独立机制。

PGPROC 数组位于主共享内存。所有 backend 都能读，但每个进程只写自己那一条。这就成了天然的、免锁的、零额外分配的共享状态通道：不持锁、不分配内存、单次 4 字节读写，开销几乎为零。

有意思的是历史。PG 9.2 刚引入等待事件时用的是每进程计数器数组，要靠原子操作或者接受统计误差。2016 年 3 月 Robert Haas 的提交 53be0b1add，标题就叫「Provide much better wait information in pg_stat_activity」，把计数器换成了直接存当前编码的 wait_event_info。这一步的意义是从「累计统计」变成「瞬时状态」——累加适合看总量，但回答不了「此刻这个会话在等什么」，而后者才是诊断时最需要的。存好了，怎么变成你在 SQL 里看到的两个字符串？

两个字符串，来自同一个整数

PAGE 10 · 数据库筑基课 · 等待事件 / 03 核心原理 · 解码

链路是这样：pg_stat_activity 视图依赖 pg_stat_get_activity() 这个 C 函数；它从 PGPROC 里用 UINT32_ACCESS_ONCE() 读出 wait_event_info，再交给 wait_event.c 的两个函数解码——pgstat_get_wait_event_type() 只按 CLASS_MASK 切 classId，pgstat_get_wait_event() 同时用两个掩码切出 classId 和 eventId，再按 class 分派到各自的命名来源。

UINT32_ACCESS_ONCE 这个宏很关键，它保证读 4 字节时不会被编译器重排成两次 2 字节读，也就不会读到「半新半旧」的撕裂值。配合源码里那句「always read and written as four-bytes, updates are atomic」，可以确定并发读写下这个值始终是完整合法的。

所以整条链路最关键的认知是：wait_event_type 和 wait_event 不是两个独立存储的字段，也不是两次独立采集的结果，而是从同一个 uint32 里按不同掩码切出来的两个字符串。这也解释了为什么你永远看不到「类型说等 IO、事件名却是锁」的矛盾组合。不过还有个语义边界：遍历 PGPROC 不持锁，多行之间不保证一致性快照，第 1 行和第 100 行可能来自不同时刻——想做跨会话对比，得自己在应用层做快照。那 eventId 具体怎么变成字符串？有三条不同的路。

292 行视图，只有 190 个枚举

PAGE 11 · 数据库筑基课 · 等待事件 / 03 核心原理 · 190 vs 292

先回答一个让新手困惑的数字问题。在我的 PG 20devel 实例上，SELECT type, count(*) FROM pg_wait_events GROUP BY type 出来一共 292 行、9 个类型：LWLock 89、IO 83、IPC 65、Activity 18、Lock 12、Timeout 11、Client 9、Buffer 4、Extension 1。可源码里手工定义的等待事件枚举只有 190 个。差在哪？

答案是：不是所有类都走「生成枚举」这条常规路径。IO、IPC、Activity、Timeout、Client、Buffer 这 190 个，一个事件对应一个枚举值，枚举值就是事件 ID，由 Perl 脚本从 wait_event_names.txt 生成。Lock 那 12 个的 ID 是锁类型编号，名字运行时从 LockTagTypeNames 数组查；LWLock 那 89 个的 ID 是轻量锁 tranche 编号，名字运行时从 lwlocklist.h 查；Extension 那 1 行是 WaitEventExtensionNew() 动态注册的。190 + 12 + 89 + 1 = 292，账对上了。

这个差异不是记账游戏，它直接关系到「32 位整数怎么装下这些信息」：正因为 ID 的来源可以是运行时编号而不只是枚举，解码才需要按 class 分派到不同的名字表。那 wait_event_names.txt 这个「唯一真相来源」又是怎么回事？

一个 txt，生成三个文件

PAGE 12 · 数据库筑基课 · 等待事件 / 03 核心原理 · 真相来源

wait_event_names.txt 按 Section 分节，节内每行两个制表符分隔的字段：事件名和描述，名字用大写下划线形式，比如 ARCHIVER_MAIN。Perl 脚本 generate-wait_event_types.pl 读它，生成三个文件：wait_event_types.h 的 typedef enum、pgstat_wait_event.c 的名字查找函数、wait_event_funcs_data.c 里 pg_wait_events 视图的静态数据。所以你在源码树里直接找不到 wait_event_types.h——它头部写着 DO NOT EDIT THIS FILE，是构建时生成的。

展示名是机械转换出来的：WAIT_EVENT_WAL_WRITE 拆成 WAL、WRITE 两段，每段首字母保留、其余转小写，拼成 WalWrite。脚本里还有一段特殊处理，LWLock 和 Lock 两类直接用原名，因为 WALWrite、transactionid 这种形式本身就是想要的展示形式；另外还有一段 next，明确对 LWLock、Lock、Extension、InjectionPoint 四类跳过 C 枚举和 C 函数的生成，只产出 SGML 文档。

这些字符串一旦生成就固化在 C 文件里，成了 ABI 的一部分。PostgreSQL 不会为了「更好看」去改一个已发布的事件名，那会破坏下游工具兼容性——这也是 PG 9.2 时代定下的 WALWrite、CopyToWrite 这类命名风格留到今天的原因。讲到这里原理链条完整了，但我不想让你只信我的推导，咱们去看实测。

绕开解码层，直读共享内存原始值

PAGE 13 · 数据库筑基课 · 等待事件 / 04 实证 · 直读内存

要验证「32 位整数怎么编码」，光看 SQL 视图永远只能看到解码后的字符串，必须绕开解码层直读原始值。我的做法是通过 /proc/<pid>/mem 读目标 backend 的 PGPROC 数组。PG 20devel、x86_64 上实测的关键参数是：sizeof(PGPROC) = 896，offsetof(pid) = 24，offsetof(wait_event_info) = 856。

定位四步：读 /proc/<pid>/maps 找 backend 映射的匿名共享段——注意 PostgreSQL 主共享内存是匿名映射，不是 /dev/shm 下的文件，这是第一个坑；然后在该段里按 896 字节步长扫描，用偏移 24 处的 4 字节整数匹配目标 pid；命中后在偏移 856 读 4 字节，就是原始值。实验对照组是本机 PostgreSQL 18.6 和 git 里的 REL_18_6 标签。

第一版实验有缺陷：按 pid 扫描会误匹配到其他结构体，某个无关结构体恰好在偏移 24 处有相同的 pid 值。修法是加约束——读到的 wait_event_info 若非 0，它的 class 部分必须属于已知等待类集合，否则丢弃这个候选。你看，这反过来又用上了前面讲的编码知识。第二个坑是采样竞态，下一页用动画专门演示。

17 组采样逐条一致，不一致 0 条

PAGE 14 · 数据库筑基课 · 等待事件 / 04 实证 · 双读协议

第二个坑更隐蔽：等待事件可能只持续几微秒，从 SQL 查看到内存读取完成，等待早就结束了。这时候你会以为「编码对不上」，其实是状态在采样窗口里变了。解法是双读协议：读内存 wei1，查 SQL 视图，再读内存 wei2；只有 wei1 等于 wei2 时才纳入比对，这就保证了 SQL 查询确实发生在两次内存读取之间。

这一页的动画可以选场景，四组都是真实采到的：select pg_sleep(60) 是 0x09000003 解出 Timeout / PgSleep；行锁冲突 0x03000005 解出 Lock / transactionid；COPY TO 文件 0x0A000012 解出 IO / CopyToWrite；WAL 刷盘 0x0A000052 解出 IO / WalWrite。你还可以勾上「模拟等待在窗口内结束」，看 wei1 和 wei2 不相等时样本被果断丢弃——这正是协议要排除的假不匹配。

最终结果：17 组采样，SQL 视图解码值与共享内存原始值逐条一致，不一致 0 条。这四组数据同时验证了三件事：class 的高位编码、event 的低位编码、中间 8 位保留为 0。另外注意 0x0A000052 和 0x0A000012 是同一个 class、不同 event——这恰好说明为什么必须分两层：类型用来聚合，事件用来定位。编码被实证锁死了，接下来把它用到诊断上。

先看类型，就知道该不该查

PAGE 15 · 数据库筑基课 · 等待事件 / 05 诊断实践 · 八类方向

真实负载采样里，八个大类全部覆盖到了。先看该跳过的：Activity 类的 CheckpointerMain、WalWriterMain、BgwriterMain 基本是后台进程的心跳，进程没事干在等下一轮唤醒，看到就该直接跳过；Client 类的 ClientRead 是 backend 在等客户端发下一条消息，健康的连接池大部分连接都该是这个状态；Timeout 最容易误判，PgSleep 是你自己写的 pg_sleep()，VacuumDelay 是 autovacuum 按比例休眠，CheckpointWriteDelay 是 checkpointer 主动放慢——都是主动、有意为之的等待，不是「卡住」。

再看该查的：IO 类按语义分数据文件读、WAL 写、临时文件读写，大量 BuffileRead 说明排序或哈希溢出到临时文件，该调 work_mem；IPC 类绝大多数与并行查询相关，大量 ParallelHashJoin 说明 worker 互相等，通常是并行度和数据分布不匹配；Lock 是用户级表锁行锁，查事务设计；LWLock 是内核内部轻量锁，名字只差一个字母但机制完全不同，往往是 I/O 压力的连锁反应。

所以「先看类型」这一步本身就能砍掉一大半无效排查：Activity、Timeout 排除在告警之外，Client 去找应用，剩下四类才是数据库侧的重点。不过光看 wait_event_type 还不够，得和 state 一起看——下一页讲一个实战里特别好用的组合判断。

state = active，不等于「在干活」

PAGE 16 · 数据库筑基课 · 等待事件 / 05 诊断实践 · 假忙会话

state 和 wait_event_type 经常被混用，但它们回答的是不同问题：state 说这个会话处于哪个阶段，wait_event_type 说它卡在哪个环节。一个 active 的会话，可能在跑 CPU 密集的排序，没有等待事件；也可能在等磁盘 IO / DataFileRead。所以 state = active 根本不等于「在干活」，这是实战里最常犯的错。

反过来，「state = active 且 wait_event_type IS NULL」才意味着纯 CPU 计算、没等任何东西——数据库慢且大量会话处于这个状态，才需要往 CPU、内存、算法方向查。active 加 IO，瓶颈在存储；active 加 Lock，瓶颈在并发逻辑；idle 加 Client 是健康的，但持续很久可能意味着连接池有问题或者应用侧卡住了；idle in transaction 还持有锁、阻止 vacuum 回收，是 Lock 类等待的常见源头。

把这个组合写成一条 SQL，就是找出「假忙」会话的实用查询。到这儿，PG 自己的机制我们讲透了；但选择都是有代价的，把它跟 Oracle、MySQL 放一起看，才知道 PG 到底换掉了什么。

用「精度」换「零开销」

PAGE 17 · 数据库筑基课 · 等待事件 / 05 诊断实践 · 横向对比

Oracle 是这套思路的集大成者：三层分类，V$SESSION_WAIT 有 SECONDS_IN_WAIT 给单次等待耗时，V$SYSTEM_WAIT_CLASS 给内置累计统计。MySQL 的 performance_schema 走另一条路——每次等待写一行事件记录，带 TIMER_WAIT 纳秒级耗时，理论信息最丰富，但高并发下事件表的写入压力由来已久，社区长期有默认关闭 events_waits_current 的实践。

PostgreSQL 选了完全相反的路线：只存当前状态，不记历史。一个 4 字节字段，读它不需要任何锁，开销几乎为零。代价很明确：单次等待耗时拿不到，累计聚合得靠 pg_wait_sampling 这类扩展以一定频率轮询来近似。所以这是个清楚的取舍——用「精度」换「零开销」。

理解了这个取舍，就不会拿等待事件去干它不擅长的事，也不会抱怨它「信息不够全」：它的设计目标本来就是低开销的实时归因，不是完整的性能剖析。那具体用起来，哪些坑最容易踩？我挑最险的一个讲。

WalWrite ≠ WALWrite

PAGE 18 · 数据库筑基课 · 等待事件 / 05 诊断实践 · 命名陷阱

坑九，也是我自己真踩过的一个：WalWrite 和 WALWrite 只差一个字母大小写，却是完全不同的两个等待事件。IO / WalWrite 是小写 a，等 WAL 写入；LWLock / WALWrite 是全大写 A，等 WAL 写入相关的轻量锁；另外还有 IPC / WaitForWalWrite 和 Activity / WalWriterMain。我第一版写文章时把它们混为一谈，直到交叉验证时脚本对 0x0A000052 解出 WalWrite、而我期望的是 WALWrite，才暴露出来。

为什么会这样？因为两类的命名规则不同。普通类的展示名由枚举名机械转换：WAIT_EVENT_WAL_WRITE 里 WAL 变 Wal、WRITE 变 Write。而 LWLock 和 Lock 跳过了机械转换，直接沿用源码原名——lwlocklist.h 里那个具名轻量锁就叫 WALWrite，全大写 A。

最危险的地方在于：写 WHERE wait_event = 'WALWrite'，你在 IO 类上永远查不到数据；写 'WalWrite' 又会漏掉 LWLock 那部分，而 SQL 一句错都不报。所以教训很硬：涉及等待事件的监控规则，wait_event_type 和 wait_event 要成对写死，不要只写事件名。名字这件事，跨版本还会再坑你一次。

名字的集合变了，位布局没变

PAGE 19 · 数据库筑基课 · 等待事件 / 06 升级与落地 · 版本差异

升级到 PG 20devel 最明显的变化是 BufferPin 变成了 Buffer，而且是改名加扩容同时发生：PG 18 里 WaitEventBufferPin 段只有一条 BufferPin / BufferPin，20devel 里类改名 Buffer 并扩到四条——BufferCleanup、BufferExclusive、BufferShared、BufferShareExclusive。因为 bufmgr 引入了新的缓冲页内容锁机制，等待语义从「等 buffer pin」变成四种内容锁模式，名字跟着语义走是合理的。同时 LWLock 类里的 BufferContent 被移除，语义被这四条吸收了。

对比 REL_18_6 标签和当前源码的 wait_event_names.txt，精确差异是：PG 18 有 274 条，20devel 有 292 条，新增 20、移除 2、净增 18。新增主要来自三条主线：data checksum 在线启用、逻辑解码与 notify 的共享结构保护、以及 WAL 等待目标从 Client 类挪到 IPC 类——提交 56fa044d15 的理由是它们不只等 socket，还可能等本地 fsync 和本地重放，那是磁盘或 CPU 密集的延迟源。等待类的划分依据是「延迟来源的性质」，不是「谁在等」。

但有个好消息：位布局一点没变。REL_18_6 里那段注释——class 占第 1 个字节、event 用低 2 个字节、中间 1 个字节保留给未来——在 20devel 里一字未改，还多了一句关于四字节读写原子性的说明。所以按位解析的工具跨这两个版本可以直接用，真正要改的是按名字匹配的脚本。这正是下一页升级清单的重点。

最危险的不是新增，是静默失配

PAGE 20 · 数据库筑基课 · 等待事件 / 06 升级与落地 · 升级清单

升级前后各跑一次 SELECT type, name FROM pg_wait_events ORDER BY 1,2，diff 两份结果，把差异同步到监控脚本、告警规则和 dashboard 上。特别检查四处：硬编码 BufferPin 的地方要改成 Buffer / BufferCleanup；按事件名做白名单的地方要补进 20 个新事件，尤其 CopyFromRead、CopyToWrite、MergeAppendReady；WaitForWalFlush / Replay / Write 这三个从 Client 搬到了 IPC，类变了匹配条件得跟着改；还有那种「新增就忽略、消失就报警」的监控逻辑，实际移除了两条，升级后可能误报。

这里最危险的是「静默失配」：SQL 不报错，只是永远返回零行。一张硬编码 BufferPin 的 dashboard，升级后悄悄变成空图；一条按旧事件名匹配的告警，从此再也不会触发。新增事件只是没覆盖，改名和消失却是假正常，比前者危险得多。

最稳妥的做法是不硬编码任何名字，直接对 pg_wait_events 的基线做 diff，把 diff 结果喂给规则生成流程。幸运的是依赖 class 数值的工具不受影响，PG_WAIT_IO 在两个版本都是 0x0A000000。讲完升级，最后把这套东西落到不同角色的日常动作上。

三个角色，三套动作

PAGE 21 · 数据库筑基课 · 等待事件 / 06 升级与落地 · 最佳实践

同一套等待事件，三个角色的用法不一样。架构师该把它作为容量规划的输入，而不是只盯 CPU 和 QPS：一个 QPS 不高但大量时间卡在 IO / WalWrite 的系统，和一个 QPS 很高但等待集中在 Client 的系统，瓶颈完全不同；定期采集类型分布、跟踪 Top 3 占比的趋势，分布突变往往比单个慢查询更早暴露问题——Lock 类占比突然涨上去，就是并发逻辑出问题了。

DBA 优先看 Lock 和 LWLock，因为这两类指向并发问题，改配置收效有限、改代码立竿见影，但一定要分清：Lock / transactionid 查事务设计、加锁顺序、隔离级别，LWLock / WALWrite 多半是 I/O 压力大的连锁反应。再就是排查 idle in transaction 长事务，它持有锁、挡着 vacuum，是 Lock 类等待的常见源头；判断要用高频采样而不是瞬时快照，千万别用 psql -c 循环起新进程，进程启动开销会完全淹没状态变化。

业务开发者最该关注的是 Client 和 Lock。Client / ClientRead 占比高，说明数据库在等你的应用，瓶颈在序列化、网络、GC 或者应用内部锁，去数据库里调优基本是白费；Lock 类说明事务设计有问题，比如「先查再插」中间留窗口期，正确做法是依赖唯一约束加 ON CONFLICT 兜底；还有别把长事务当事务用，事务边界要紧贴业务操作。最后，超时日志里只有一个 traceID 时，数据库侧能告诉你那条 SQL 当时在等什么。哪些事它帮不上忙？收个尾。

它告诉你「卡在哪」，不告诉你「为什么卡」

PAGE 22 · 数据库筑基课 · 等待事件 / 07 收束 · 边界与小结

把边界说清楚，这套工具才用得稳。它适合性能归因，尤其是「慢但 CPU 不高」；适合并发问题定位；适合 I/O 瓶颈的初步分型；适合版本升级前后的行为对比；也很适合做教学和源码导读。它不适合精确的单次等待耗时统计，不能替代 pg_stat_statements（一个说卡在哪、一个说哪条 SQL 慢，两者正交），不能替代 profiling，不能当判断系统是否健康的单一指标，也不适合直接做实时告警——那需要专门的采样扩展。

回到开头那个僵局，现在你有确定答案了：Client 占比最高，去查应用；Lock / transactionid 占比最高，去查事务设计；IO / WalWrite 占比最高，去查存储和 checkpoint；Lock / object 占比最高，说明 DDL 被业务查询挡住了，去查锁粒度。等待事件不告诉你「为什么卡」，那是业务语义和系统指标的事；它告诉你「卡在哪」，而这部分它能给你确定答案。

而支撑这一切的实现，比想象中简单：一个 32 位整数，高 8 位是类，低 16 位是事件，中间 8 位留白。你在 pg_stat_activity 里看到的两个字符串，就是这个整数被切开后的两个视图。全篇到此结束，谢谢。
