本页讲稿

GraphBLAS 图式存储与搜索

PAGE 01 · 数据库筑基课 · 数据类型 / 算子 / 执行算法 / 场景实践

今天这一课，讲一个有点反直觉的东西：图，可以不按图来存，也不按图来查。

先把话说准。GraphBLAS 要解决的不是「数据库怎么存图」这个全部问题，它只回答一件事——图搜索和图算法，能不能用一套可组合、可优化、可移植的稀疏算子来表达。

右边这张剖面图就是全篇骨架。最上面是业务里的图问题，最下面是 SuiteSparse 的稀疏执行内核；中间从 SQL 类型、执行控制面、代数运算一层层往下压。越往下越底层，颜色也越深。请注意这个方向：我们不是加一层新语法，而是把上面的问题，翻译成下面能算的东西。

实证材料是本地 OneSparse 源码和项目文档，加上 GraphBLAS 的论文与 API 规范。有个细节先交代清楚：输入的论文名《Mathematical Foundations of Graph Queries》在 GraphBLAS 资料里没有完全同名条目，可核验的是 Kepner 等人在 HPEC 2016 的《Mathematical Foundations of the GraphBLAS》，全篇按后者引用。另外本文没有在本机启动 PostgreSQL 安装扩展，所以不会伪造任何执行输出——后面所有 SQL 的函数名与语法都来自源码和文档。原文里提到的 DeepWiki 查询也只返回了浅层摘要，没有作为关键事实的唯一来源。

那问题来了：业务里到底有哪些「图问题」，值得为它专门压一层代数吗？下一页先看场景。

五个场景，其实是同一个问题

PAGE 02 · 一 · 从业务问题出发

先看五个真实场景。风控问的是账号、设备、手机号、银行卡之间有没有可疑路径；推荐问用户和商品的二跳、三跳能不能补召回；知识图谱问实体是否可达、路径能不能解释；RAG 问相似召回之后能不能沿实体关系把上下文扩出去；运维问服务依赖图里某个节点挂了会波及哪些下游。

把它们摆在一起看，句式其实是一样的：从一批点出发，沿边走一跳或几跳，问「到不到得了」「有多少条路」「影响面有多大」。这就是可达性、邻域扩展和批量分析，不是五种不同的技术。

这一点很重要。因为只要句式一样，就有机会用同一套算子把它们全接住；反过来，如果每个场景各自写一套遍历循环，那五份代码就要各自维护、各自优化、各自踩坑。

传统关系数据库当然能做，join、递归 CTE、临时表都能写出来；专用图数据库也能用 Cypher 或属性图模型做。但两条路各有各的边界，下一页把这个边界摊开——我们不急着给答案，先把「为什么需要新抽象」讲透。

三条路都能走，但都绑死了实现

PAGE 03 · 二 · 现有解法的边界

先说递归 CTE 和普通 SQL。好处是留在关系模型里，低频、浅层的关系查询完全够用，不用引入新系统；代价是多跳之后中间结果容易膨胀，SQL 写得冗长，高扇出多跳的生产查询会很难受。原文横向对比里给它标的「最适合」就是低频浅层关系查询。

再说属性图加 Cypher。点、边、标签、属性是一等模型，路径和模式匹配写起来最直接；代价是引入一套新的模型和系统，事务、权限、同步都要重新对齐。

第三条是手写 CSR 或邻接索引。局部邻域遍历很快，切片扫描很直接；代价是派生索引要自己构建、自己同步，而且一到大规模全图算法就不划算。

三条路看起来互不相干，底下却藏着同一个缺口：每换一个算法，就要重写一套遍历结构和控制逻辑。BFS 写一套 frontier，最短路再写一套，PageRank 又写一套；算法描述和底层实现是绑死的，也就没法把优化成果复用到下一个算法上。

所以真正该问的不是「换哪个系统更快」，而是：能不能把遍历这件事，从「一段过程」变成「一组可组合的运算」？下一页给出 GraphBLAS 的答案。

把图遍历语言，压进稀疏线性代数

PAGE 04 · 三 · 核心命题

GraphBLAS 的答案很干脆：把「图遍历语言」压到「稀疏线性代数语言」里。

普通写法围着 frontier、visited、neighbors 写循环；GraphBLAS 把当前 frontier 看成一个稀疏向量，把图看成稀疏邻接矩阵，用 v @ A 或 A @ v 产生下一层候选，再用 mask 把已经访问过的点挡掉。最短路换半环，三角计数换成矩阵乘加逐元素交集，PageRank 换成矩阵-向量迭代。

写成公式就是图上这一行：C(i,j) 等于对 k 做 add，参数是 multiply(A(i,k), B(k,j))。普通矩阵乘用的是 plus-times，先乘再加；GraphBLAS 的关键动作，是把 add 和 multiply 都抽象出来，让它们承载业务语义。

这不是我自己的推论。GraphBLAS Forum 官方说明里就写着：当图用稀疏关联或邻接矩阵表示时，稀疏矩阵-向量乘就是广度优先搜索的一步；把线性代数计算里那一对标量运算推广成半环，就能把这套原语扩展到一大类并行图算法。原文「3.1」那句「GraphBLAS 的关键不是把所有问题都硬塞进普通矩阵乘法」，说的正是这件事。

换句话说，矩阵乘法在这里不是数值计算技巧，而是一层「可执行的问题描述」。那这层描述要落在什么对象上？得先看图、边表和矩阵三者的等价关系。

边表、图、稀疏矩阵，是同一份关系

PAGE 05 · 四 · 三种等价表示

看这张图：左边是关系边表，中间是有向图，右边是稀疏邻接矩阵——它们是同一份关系的三种表示，信息量完全一样。为了后面能一直复用，我画的是原文 DEMO 里那个四点小图：四条边，0→1、0→2、1→3、2→3。边表里就是四行；画成图是四个节点四条有向边；换成矩阵，就是 A[0,1]、A[0,2]、A[1,3]、A[2,3] 这四个位置有值。

OneSparse 的 README 把这件事说得更透：表格是关系范式，图形是过程范式，矩阵是代数范式，三者表达同样的信息，每条边分别对应表里的一行、图里的一条边、矩阵里的一个元素；开发者可以在三者之间自由切换，选最适合当前任务的那种。

但请盯住右边这个矩阵：有值的位置才需要存，其余格子不是「填了 0」，而是「没有元素」。这个区别看着小，实际上决定了空间成本，也决定了搜索语义。原文特意在「3.2 稀疏存储」里把它拎出来单讲一节，是有原因的。

还有一层工程含义：GraphBLAS 用矩阵下标表达节点，所以业务建模前得先把节点主键映射成整数下标。这件事第 13 页会展开，先记住它——OneSparse 不是属性图系统，不会自动理解 users.id = 「u123」这样的业务主键。

下一页专门拆「不存在」和「0」：这两个东西在关系库里经常混用，在 GraphBLAS 里却是两回事。

元素不存在，不等于值为 0

PAGE 06 · 五 · 稀疏存储的第一原理

先把结论说死：在 GraphBLAS 里，元素不存在，不等于值为 0。

左边是一个空矩阵，十六个格子全空，nvals 等于 0，不消耗任何元素存储。OneSparse 的文档里有个很直观的实证：可以建一个行列都 unbounded 的矩阵，行列上限是 2 的 60 次方，但因为没有存储元素，内存根本不会爆，nrows、ncols 显示那个巨大的上限，nvals 依然是 0。

右边是显式写入 0 的矩阵。注意，0 是一个被存下来的值，它仍然是 stored element，会参与结构 mask，会改变 nvals。GraphBLAS C++ 规范说得很直白：空下标没有隐含的零值，任何操作都不该随意插入显式 0，因为那会导致错误结果——不同半环的零元并不相同。

OneSparse 的 README 补了另一半：没有值的位置被解释成「代数零」，它未必是数字 0，可能是正无穷、负无穷，取决于你用的是哪个半环。布尔半环里它是 false，min-plus 里它常常是 +∞。所以原文的措辞是「GraphBLAS 更像稀疏关系代数执行内核，不是把图塞进普通 dense array」。

工程上两条硬规矩：第一，别用显式 0 表示无边，除非算法确实需要一个「存在且为 0」的元素；第二，很多图算法只关心结构 mask，也就是「有没有元素」，根本不看值——你多写进去一个 0，在它眼里就是多了一条边。这条坑在第九节「常见坑」里排第二。

搞清楚存储语义，才敢谈运算。下一页看半环：同一个矩阵，怎么换一下「加」和「乘」就换了搜索问题。

半环：换掉「加」和「乘」，就换了搜索问题

PAGE 07 · 六 · 核心原理 3.1

上一页说了存储，这一页说运算。普通矩阵乘是 plus-times：先乘，再求和。GraphBLAS 把「乘」和「加」都抽象出来，合起来叫半环。

看这张表：把 add 换成 or、multiply 换成 and，得到布尔可达性——只要存在一条通路就为真，BFS 用的就是这个语义；把 add 换成 min、multiply 换成 plus，就得到最短路的松弛；两个都用 plus，可以表达某些路径计数或度数累加；什么都不换，就是原来的常规数值代数。

原文 3.1 特别提醒：关键不是「把所有问题都硬塞进普通矩阵乘法」，而是把乘法和加法替换成业务语义。这样 BFS、SSSP、路径计数就能共享同一个 mxv / mxm 执行框架，底层优化做一次，上面所有算法都吃到。

OneSparse 的 README 还举了更远的例子：min-plus 属于 Tropical Algebra，用来解最短路径这类最小化问题；Log 半环适合边表示概率的图，兼顾速度和数值稳定性。这说明半环不是语法糖，是可扩展的运算插槽，而且它自带的 JIT 可以把用户定义的半环也编译进去。

那 BFS 具体一轮怎么走？下一页用动画把它拆开，你可以自己选起点。

frontier → 矩阵乘 → 掩码 → 新 frontier

PAGE 08 · 七 · 一轮 BFS 的推演（可操作演示）

这一页可以动手。选一个起点，按播放或者单步，看 frontier 怎么一轮轮往外扩。

用四点小图，边是 0→1、0→2、1→3、2→3。以 0 为例：初始化 frontier 里只有 0，level[0] 等于 0；第一轮沿 A[0,*] 做 v @ A，布尔半环把 1 和 2 找出来，mask 把 visited 里的 0 挡掉，新 frontier 就是 {1,2}，level 都置 1；第二轮 1 和 2 都指向 3，候选里出现两个 3，但布尔半环的 or 会去重，mask 挡掉 0、1、2，新 frontier 是 {3}，level 置 2；第三轮 3 没有出边，frontier 空了，收敛。

你可以把起点换成 1 或者 3 再看一遍，层数会变，但流程完全一样——这就是「同一套算子，换个输入」的意思。

这里有三个点必须盯住。第一，方向：v @ A 还是 A @ v，取决于 src→dst 映射到 A[i,j] 之后你想往哪边传播，写反了结果看着合理其实全反。第二，mask 不能省：没有 visited 的 frontier 会反复回到老节点，轻则结果重复，重则迭代不收敛。第三，布尔半环的 or-and 负责可达性，换成 min-plus 就是在算最短路。

原文 6.2 的 DEMO 只演示了「邻接矩阵乘 frontier 向量」这一个基本动作，并且特别注明真实 BFS 还需要 mask 排除 visited、按方向选 mxv 或 vxm——这页动画就是把那句注释放大。

一轮一轮能跑通，接下来问：这么改写，到底换来了什么？

三个直接收益，都来自「算法与实现解耦」

PAGE 09 · 八 · 改写换来了什么

原文给了三个直接收益，我按因果顺序讲。

第一，算法和实现解耦。算法描述只说 mxv / mxm 加半环加 mask，底层可以自己选 CSR、CSC、bitmap、dense、hypersparse，也可以选 CPU、GPU 或者 JIT kernel。这正是 SuiteSparse:GraphBLAS 那篇 Algorithm 1000 的核心价值之一：把算法接口和具体存储、执行实现分开。你写的是数学，硬件专家优化的是实现，两边不互相绑。

第二，搜索和分析共享一套原语。可达性、最短路、路径计数、中心性、聚类系数，全都落到矩阵和向量操作上，不用每个算法单独实现一套邻接结构。前面说的「五个场景一个句式」，到这里才真正兑现。

第三，数据库内复用。OneSparse 把矩阵、向量、半环、图算法包装成 PostgreSQL 的类型和函数，关系数据可以在库内直接转成 GraphBLAS 对象执行，不用把边表导出去、算完再导回来，SQL 的过滤、聚合能力还能接着用。

不过这三条收益都有前提，而且代价同样明确。下一页先把代价摆出来，免得后面所有结论都站在空中。

四条边界，决定它适合什么、不适合什么

PAGE 10 · 九 · 代价同样明确

四条，一条都别略过。

第一，它不是关系优化器原生的图算子。SQL 优化器不会自动把任意 join 改写成 GraphBLAS，得你显式调用函数；原文 3.3 那张架构图的说明也强调，PostgreSQL 负责的是类型系统、SQL 调用、存储和事务上下文，图算子不是它内建的。

第二，图的更新、事务可见性、权限、增量维护，仍然要由扩展和应用约束处理。PostgreSQL 行更新不会自动等价成矩阵增量更新，除非业务显式维护。

第三，抽象门槛明显高于普通 SQL：矩阵方向、半环、mask、descriptor、稀疏值、显式 0 的区别都得懂。这也是第九节八个坑里占了大半的原因。

第四，一旦要输出复杂路径解释、做属性模式匹配、跨多类点边变长查询，属性图语言仍然更直接。

所以原文的措辞很克制：GraphBLAS 不是「更快的 Cypher」，也不是替代 SQL 递归，它是另一套执行内核；强在批量算法，弱在属性路径表达。带着这份边界，我们往下钻工程实现。

SQL 类型是门面，内核是 GraphBLAS

PAGE 11 · 十 · OneSparse 架构 3.3

三层，从上往下看，正好呼应封面的地层剖面。

最上层是 PostgreSQL：类型系统、SQL 调用、存储和 TOAST、事务上下文都在这里；matrix、vector、scalar、graph 是扩展定义的类型，SQL 定义里 storage = external，适合 TOAST 存储。

中间层是 OneSparse 的 C 扩展：对象包装、flat 与 expanded 之间转换、序列化、参数解包、错误处理。源码路径能看出这条分层——src/matrix/matrix.c 里 new_matrix 创建 GrB_Matrix，matrix_get_flat_size 用 GxB_Matrix_serialize 序列化，expand_matrix 用 GxB_Matrix_deserialize 展开；templates/matrix_header.sql 定义 matrix 类型和 mxm / mxv / vxm 函数以及 @ 操作符；matrix_mxm.c 这些文件把 SQL 参数解包后调用 GraphBLAS API。OneSparse 的 AGENTS.md 也确认了这套 per-type 目录结构和 flat / expanded 双表示。

最下层才是真正干活的内核：SuiteSparse:GraphBLAS 负责稀疏线性代数，LAGraph 负责 BFS、SSSP、PageRank 这些工程化算法，templates/graph_header.sql 与 src/graph/*.c 负责把矩阵包装成 LAGraph 图对象。

这里有个判断很关键：SQL 类型只是门面。你写的 SELECT 看着像普通函数调用，但计算发生在下面的 C 库里；优化器既不知道也不参与。

那问题就来了：一个 GrB_Matrix 是内存里的对象，PostgreSQL 的列却要能存盘、能 TOAST、能跨 SQL 边界传。这两种形态怎么接？

存储格式和计算对象，本来就不是一回事

PAGE 12 · 十一 · Flat / Expanded 3.4

这是数据库扩展最容易踩坑的地方：适合持久化的格式，未必适合计算；适合连续计算的对象，未必适合直接落盘。OneSparse 用 PostgreSQL 的 expanded object framework 做这层桥。

上面这条泳道是计算态：expanded form 里拿的是 GrB_Matrix、GrB_Vector 这些内存对象，连续做多个矩阵操作时可以复用，避免反复反序列化。

下面这条泳道是存储态：matrix_get_flat_size 调 GxB_Matrix_serialize 得到序列化字节，flatten_matrix 把它们写进 flat varlena 结构；DatumGetMatrix 遇到 flat datum 时会 detoast 并反序列化回 expanded object。这样矩阵列就能像普通 PostgreSQL 值一样传递、存储、被 TOAST。

中间两条桥，一条向下是 flatten / serialize，一条向上是 detoast / deserialize。原文 3.4 说得很清楚：flat form 是数据库里的稳定值，expanded form 是当前执行上下文里的计算对象；持久化、跨 SQL 边界和 TOAST 依赖 flat，连续运算的效率依赖 expanded。

这也解释了 DBA 后面要关心的事：一个大矩阵作为单个 PostgreSQL 值存储时，MVCC 版本、TOAST、备份和复制都要按「对象大小」来算，一次更新未必是小更新。

形态问题解决了，下一个问题是入口：业务边表怎么变成矩阵？

matrix_query：三列 SQL 结果变一张邻接矩阵

PAGE 13 · 十二 · 从关系边表进入 GraphBLAS 3.5

matrix_query 是理解「关系表如何进入 GraphBLAS」的关键函数，入口契约很硬：输入 SQL 必须返回三列，第一列 bigint 是矩阵行号，第二列 bigint 是列号，第三列是值，只能是 bool、integer、bigint、float4 或 float8。

源码里它通过 SPI prepare / open cursor / fetch 分批读结果，按第三列类型选 GraphBLAS 类型和 SECOND accum，对每批临时矩阵调 GrB_Matrix_setElement，最后用 GrB_assign 合并进目标矩阵。注意是「分批」，不是一次性把边表全读进内存。

造出 A 之后有两条路：直接在 A 上做半环乘法，自己控制 frontier 和 mask；或者用 graph(a) 把矩阵包装成 LAGraph 图对象，调 bfs、sssp、pagerank、triangle_count、connected_components 这些现成算法。返回的是向量或矩阵——level、parent、distance 之类，再 join 回业务表做 SQL 后处理。

但真正的坑在入口之前：GraphBLAS 的 API 用矩阵下标表达节点，所以业务建模必须先解决「把节点主键映射成连续或至少合法的非负整数下标」。OneSparse 不是属性图系统，不会自动理解 users.id = 「u123」。原文把这句话放在 3.5 末尾，是当作前提条件说的，不是补充说明。

那既然有现成算法，控制面还剩什么？看 mxm 的签名就明白了。

mask、accum、descriptor 不是修饰词，是控制面

PAGE 14 · 十三 · 执行控制面 3.7

把 templates/matrix_header.sql 里的 mxm 签名摊开，除了 a、b 两个输入矩阵，还有一整排可选参数。

op semiring 选搜索语义，默认数值半环、min_plus、plus_plus 各有不同；c 是可选输出对象，允许复用或累积；mask 只允许写入某些位置，BFS 常用它排除 visited；accum 决定新结果和旧结果怎么合并；descriptor 控制转置、替换、mask 取反这些执行行为。

GraphBLAS C API 的设计论文，也就是 Buluc 等人在 GABB / IPDPS 2017 那篇，强调接口要足够通用，不能只暴露几个固定算法——这排参数就是「通用」的代价和收益。OneSparse 老老实实把它们保留在 SQL 签名里，没有为了好上手简化掉。

所以原文给 DBA 和开发者一句提醒：不能只把 @ 当普通乘法。图搜索的正确性经常取决于半环、mask 和方向；OneSparse 里 @ 映射到默认半环乘法，@<+、@++ 映射到特定半环。这也是为什么前面动画页要专门让你选起点、看 mask 的作用。

控制面清楚了，再看算法层：BFS 真的要自己写吗？

BFS 不用自己写，但需要理解它缓存了什么

PAGE 15 · 十四 · LAGraph 3.6

不用。GraphBLAS C API 提供的是基础原语，不等于每个用户都要自己写 BFS。LAGraph 的定位就是「建立在 GraphBLAS 之上的图算法库」。

原文贴了 src/graph/graph_bfs.c 的调用：先 LAGraph_Cached_AT 缓存转置矩阵，再 LAGraph_Cached_OutDegree 缓存出度，然后 LAGr_BreadthFirstSearch 返回 level 和 parent 两个向量。C 层把这两个向量装进 bfs_level_parent 复合类型，SQL 里就能写 (bfs(graph(a), 0)).level 和 .parent。

graph_sssp.c 走的是另一条：读取图矩阵类型和行数，缓存 EMin，再调 LAGr_SingleSourceShortestPath。

这里有个容易混淆的点必须讲清楚：这些 Cached_AT、Cached_OutDegree、EMin 不是 SQL 层的索引，也不是 PostgreSQL 的统计信息，它们是图算法库自己需要的派生属性，缓存在 LAGraph 图对象上。原文特意点破这一点，就是怕 DBA 把它当成可 ANALYZE 的索引。

另外原文也留了分寸：不同权重类型、delta 语义和方向，应以 LAGraph / OneSparse 当前版本文档为准，别照抄示例就上生产。

到这儿，机制讲完了。接下来把它放回坐标系：和别的方案比，它到底站在哪个位置？

五种方案不在同一个赛道上

PAGE 16 · 十五 · 横向对比

这张表是原文第四节的浓缩版，我抽了五个最关键维度。

看「主要目标」这一行就分道扬镳了：GraphBLAS 是用稀疏线性代数表达图搜索和图算法；递归 CTE 是在关系模型里递归扩展；CSR 索引是为已有表建邻接索引加速局部遍历；属性图是把点边属性当一等模型查询；向量库做的是高维相似搜索。它们根本不在同一个赛道上，所以「谁更快」这个问题本身就不成立。

再看「核心表示」：matrix、vector、semiring、mask 对上表、join、递归工作表，对上 node id / offsets / targets，对上 vertex / edge / label / path，对上 vector / ANN index。表示不同，擅长的问句自然不同。

「读取代价」这一行最能说明收益来源：GraphBLAS 是稀疏内核执行，适合批量算法；递归 CTE 多跳容易中间结果膨胀；CSR 是邻接切片扫描，适合有界遍历；属性图靠查询引擎优化；向量库是近似相似召回。

「事务 / MVCC」这一行是数据库读者要特别注意的：GraphBLAS 这一列写的是「由 PostgreSQL 值和扩展语义承接」，递归 CTE 是原生，其余都取决于系统或扩展的维护策略。这不是缺点，但意味着责任边界要自己划清楚。

所以原文给这张表的结论不是排名，而是定位：强在把一批图算法统一到稀疏矩阵内核、让算法复用底层优化；弱在路径模式查询的可读性和属性路径表达。定位清楚了，最后一个问题最实在：什么时候它真的能快？

收益有条件，代价可枚举

PAGE 17 · 十六 · 效果边界

原文第五节开头就泼了冷水：不要凭「SuiteSparse 很快」就推导出所有图查询都会快。收益是有条件的。

左边五条是条件：图能自然表达成稀疏矩阵，非空元素远少于 n×n；任务能批量化或迭代化，比如一轮轮 frontier 扩展、PageRank 迭代、矩阵乘式三角计数；半环和 mask 能把控制逻辑下推到稀疏内核；同一个矩阵会被反复查询或分析，构造与序列化成本能摊销；底层实现能按稀疏度选合适格式，不用开发者手写 CSR / CSC 分支。

右边五条是代价：构造矩阵要扫边表，matrix_query 还要用户给整数下标；PostgreSQL 行更新不会自动等价为矩阵增量更新；大矩阵作为单个值存储时，MVCC 版本、TOAST、备份和复制都要考虑对象大小；返回的向量要 hydrate 回业务行，得维护 node id 到业务主键的映射；性能边界还取决于稀疏度、方向、半环、mask、数据类型、线程 / JIT / GPU 支持和内存带宽。

注意左右两边其实在说同一件事：成本集中在「构造与同步」，收益集中在「复用与批量」。这也是为什么第七节要让架构师「把矩阵对象视为派生分析状态，而不是替代源表」——源表仍然承担事务、约束、权限、审计和备份。

所以工程上别问「GraphBLAS 是否比图数据库快」，要问那四个更具体的问题。下一页把它们做成一条判断路径。

四个问题，决定是否值得构造矩阵

PAGE 18 · 十七 · 工程决策

原文给的四个问题，我按判断顺序排好了。

第一问：我的查询是图算法，还是属性路径查询？如果是 PageRank、BFS、SSSP、三角计数这类批量算法，往 GraphBLAS 走；如果是「找满足复杂属性模式的一条路径」，属性图语言更直接。

第二问：我的点边是否稳定到值得构造矩阵？稳定的一批边反复算，构造成本能摊销；每次 OLTP 写入都要立刻反映到复杂图查询结果，就不合适。

第三问：我的输出是批量分数、距离、level，还是少量可解释路径？前者是向量或矩阵，正好是 GraphBLAS 的返回形态；后者要 hydrate 回业务行，还得解释路径，代价明显。

第四问：我能否接受矩阵对象和源表之间的同步边界？这问的是工程纪律，不是性能。

四个问题都落在左侧，才值得构造矩阵；任何一问落到右侧，先停下来评估属性图或普通 SQL。原文第八节的「适合 / 不适合」两栏，其实就是这四问展开后的答案。判断做完了，来看代码。

四段 SQL，把整条链路走一遍

PAGE 19 · 十八 · 实操 DEMO

第一段，构造邻接矩阵。CREATE EXTENSION、建 edge_list 表，再用 matrix_query 把 SQL 查询结果变成矩阵。这个函数要求三列，前两列 bigint，第三列决定矩阵值类型；原文这里构造的是 int32(4:4) 类邻接矩阵。

第二段，用矩阵-向量乘扩展 frontier。把当前层写成一个 vector，和 A 做 mxv，得到 next_frontier。但请注意原文紧跟的那句注明：这个例子只展示「邻接矩阵乘 frontier 向量」这一个基本动作，真实 BFS 还需要 mask 排除 visited，并按方向选择 mxv 或 vxm。

第三段，调用 LAGraph BFS。SQL 里的 bfs(matrix, bigint) 是一层包装：先 graph($1)，再调用 C 函数 graph_bfs；C 层返回 bfs_level_parent 复合类型，所以能分别取 .level 和 .parent。两个向量，一个记层数，一个记父节点，路径就是靠 parent 回溯出来的。

第四段，权重图上的 SSSP。第三个参数是 scalar delta，底层调 LAGr_SingleSourceShortestPath。原文特地留了一句：不同权重类型、delta 语义和方向应以 LAGraph / OneSparse 当前版本文档为准——别把示例当契约。

最重要的一句在最底下：本文没有在本机启动 PostgreSQL 并安装扩展，所以不伪造任何执行输出。这也是全篇的实证原则——函数名、源码路径、SQL 签名都能追溯，跑出来的性能数字一个都不编。

代码会写了，但生产上最容易翻车的是那八个坑。

八条坑，大半会让算法「跑完但错」

PAGE 20 · 十九 · 常见坑

原文第九节列了八条，我把它们排成这张图。请注意一个共同点：大半不会报错，只会让结果静默变错。

前四条全是正确性问题。矩阵方向搞反，A[i,j] 到底是 i→j 还是 j→i 没统一，BFS 写错方向会得到看似合理但完全反的结果；把 0 当无边，可缺失元素才是无边，显式 0 仍可能参与结构 mask；半环选错，默认 plus_times 既不等于可达性也不等于最短路，BFS 常用布尔语义、SSSP 常用 min-plus 类；忘了 visited mask，frontier 会反复访问旧节点，轻则结果重复，重则迭代不收敛。

中间两条是工程问题。业务主键没映射——GraphBLAS 只认整数下标，源表 id 必须能映射回来；矩阵重建成本被低估——构造不是免费操作，边表扫描、序列化、TOAST 和 WAL 都可能成为瓶颈。

第七条是认知问题：把 LAGraph 当事务图引擎。它是算法库，不负责 PostgreSQL 事务语义、权限模型和增量同步策略，这些还得数据库这一层自己扛。

第八条其实是对前七条的解法：没有小图验算。图算法很容易「跑完但错」，先用 4 到 10 个点的小图手算，再上真实数据。原文第七节给业务开发者的建议也是这句：从小图开始验证 level、parent、distance，再放大到生产图。

把坑反过来读，就是三个角色各自该做的最佳实践。

三个角色，各守一条边界

PAGE 21 · 二十 · 最佳实践

原文第七节按三个角色给了实践建议，我照这个分栏讲，因为责任边界本来就不一样。

架构师那边三件事：先判断问题类型，核心是批量图算法、中心性、可达性、最短路、三角计数才值得评估，如果核心是复杂属性路径和在线点边事务，优先评估属性图模型；设计稳定的节点编号层，业务主键到 node id 的映射必须可重建、可审计、可 join 回源表；把矩阵对象视为派生分析状态，而不是替代源表。

DBA 那边四件事：关注对象大小、TOAST、MVCC 版本膨胀和备份体积，一个大矩阵值更新可能不是「小更新」；关注内存和执行时间，稀疏矩阵算法可能是 CPU / 内存带宽密集型任务，应限制并发和资源组；建立验证查询，每次构造矩阵后至少检查 nrows / ncols / nvals、样本边、方向和类型；不要把 VOLATILE / STABLE 标签当作并发安全承诺，扩展函数的对象复用、inout 参数和就地修改语义要通过测试确认。

业务开发者那边四件事：明确方向，src→dst 映射到 A[src,dst] 后 mxv 和 vxm 表示的传播方向不同；明确「缺失」和「0」的区别；从小图验证 level、parent、distance 再放大；输出结果要能解释，保存 node id 映射表，别只存 GraphBLAS 下标。

底下一句是总原则：源表仍承担事务、约束、权限、审计和备份语义，矩阵只是派生分析状态，两者不要互相替代。把这些实践再收一次，就是「适合」与「不适合」两张清单。

两张清单，把决策四问落到场景

PAGE 22 · 二十一 · 适合与不适合

左栏五条「适合」，本质都是同一件事：成本能摊销、输出是批量结果。同一批边反复做 BFS、SSSP、PageRank、connected components、triangle count；图规模大但稀疏，矩阵能长期复用；希望在 PostgreSQL 内完成「关系数据 → 图算法 → SQL 后处理」闭环；研究型、分析型、风控批处理、推荐召回、知识图谱离线计算；以及需要从算法描述中分离底层实现，未来可能利用 SuiteSparse 的 JIT、并行或 GPU 能力。

右栏五条「不适合」，也都能归到前面四问的某一问：每次 OLTP 写入都必须立即反映到复杂图查询结果；查询主要是「找满足复杂属性模式的一条路径」，而不是批量算法；节点编号无法稳定维护，或者业务无法接受额外映射表；图非常接近 dense，矩阵对象过大，内存和 TOAST 成本不可控；团队只熟悉 SQL，不愿承担半环、mask、descriptor 的学习成本。

所以底下这句结论值得记住：边界不是性能，是「问题类型 + 数据稳定性 + 输出形态」。三者对齐，才谈得上实现选型；三者不齐，再快的内核也用不上。

讲到最后，把整条链路收成一个闭环，并留下几个值得继续想的问题。

关系数据 → 图算法 → SQL 后处理，闭环成立

PAGE 23 · 二十二 · 收束

把全篇收成一条闭环：业务边表在 SQL 里，matrix_query 把它变成稀疏矩阵 A；A 上跑半环加 mask，或者交给 LAGraph 的现成算法；结果是 level、parent、distance 这样的向量；再 join 回业务节点表做 SQL 后处理，写回关系数据。图不再是「另一套系统」，而是这条链路中间的一种数据形态。

这也是原文第八节说的「希望在 PostgreSQL 内完成关系数据 → 图算法 → SQL 后处理的闭环」。它不要求你放弃关系模型，只要求你承认：某些问句用矩阵表达更短、更容易被底层优化。

所以最后这句话我想留得克制一点：把「图」变成一种可以被代数编排的数据类型。真正的边界不在性能，而在问题类型与数据稳定性；源表负责事实，矩阵负责计算。

底下六个问题是原文第十节留下的，我没有替它们编答案，因为每一个都要结合具体业务建模才能答：UUID 主键怎么设计可重建映射表；同一张边表什么时候物化 matrix、什么时候即时构造；大矩阵更新如何影响 MVCC、TOAST、WAL 和复制延迟；level 和 parent 怎么 join 回业务节点表生成可解释路径；做 RAG 时关系扩展与向量索引的结果怎么合并排序；以及哪些 Cypher / SQL:PGQ 路径模式值得改写成矩阵乘。

最后把参考材料与全篇的严谨性说明交代清楚。
