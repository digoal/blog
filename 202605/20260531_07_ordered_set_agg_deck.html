本页讲稿 · N
01 · 聚合之 Ordered-Set Agg

今天这一讲只盯一个看起来很小的问题：为什么一条查 P95 的 SQL，不能像 avg() 那样边扫边算？你可能写过很多次 percentile_cont(0.95) WITHIN GROUP (ORDER BY latency_ms)，语法上它就是一个聚合，但它的执行性质跟 avg 完全不是一回事。

我把全篇拆成七层：语法、解析、目录、执行、排序、结果语义、业务选型。越往下越底层，也越决定上面能做什么。我们从最上面那条 SQL 出发，一层层往下挖，最后再回到选型——因为所有实现细节，最后都会变成一句业务判断：误差能不能被接受。

02 · 一条 P95 SQL，两种执行性质

先看这条最常见的写法：从最近一小时的 api_request_log 里算 latency_ms 的 P95。avg 的做法是维护 sum 和 count，来一行加一行，状态恒定大小，谁先来谁后来无所谓；所以它能流式、能合并、能分给多个并行 worker。

P95 不行。要回答「第 95% 的位置是哪个值」，你必须知道全体输入的相对顺序。除非换近似算法，否则数据库得先把这些值留住、排好序，再去数位置。所以上轨的状态是一个小盒子，下轨的状态是一个和输入行数一起长大的集合。那问题就来了：具体有哪些结果，是非得依赖顺序不可的？

03 · 顺序才有意义的四类问题

四类。第一类是离散分位数 percentile_disc，返回排序集合里真实存在的那个值；第二类是连续分位数 percentile_cont，允许在相邻两个值之间插值，结果可能压根儿不在输入里；第三类是 mode，找出现次数最多的值；第四类是假设排名——把一行虚拟数据放进集合，问它会排第几。

它们的共同点是：答案都落在同一条已排序的输入上。换句话说，顺序不是优化手段，是语义的一部分。既然顺序是语义的一部分，而我们要的是精确结果，那就得先付代价。

04 · 精确的代价：在线性与可合并性

代价写得很直白。官方文档函数表里，mode、percentile_disc、percentile_cont，还有 rank、dense_rank、percent_rank、cume_dist，Partial Mode 一列全部是 No。注意这句话的分量：它们不是 PostgreSQL 内置的并行 partial aggregation 友好聚合。

为什么？要精确，就必须知道全体相对顺序；要知道全体相对顺序，就得保留全量输入并排序；而一个还没消费完的排序对象，不是一个能随便序列化、两两合并的数值状态。所以这不是「数据库没做优化」，是精确语义本身把这条路封了。另一边的 P²、GK、t-digest 走的是完全不同的目标：允许可控误差，换小状态和流式处理。别把两边混成「谁的算法更先进」。

05 · 语法解剖：两类参数，两种生命周期

这套语义在 SQL 里怎么表达？WITHIN GROUP (ORDER BY ...) 是必需的，不是普通聚合那种可选的排序修饰。括号里的 0.95 叫 direct argument，每次聚合调用只求值一次；WITHIN GROUP 里的 latency_ms 叫 aggregated argument，每行输入都要求值一次，全部进入排序集合。

final function 得同时拿到 transition state 和 direct argument，才知道「在哪个集合上取哪个分位点」。这也解释了 parse_agg 为什么拦 rank(x) WITHIN GROUP (ORDER BY x)：x 放在 direct argument 的位置，它不能随行变化。语义想清楚了，我们再看 PostgreSQL 到底给了哪几个函数。

06 · 七个内置函数，两个家族

一共七个，两个家族。aggkind 等于 o 的三个是标准 ordered-set：mode、percentile_disc、percentile_cont；等于 h 的四个是 hypothetical-set：rank、dense_rank、percent_rank、cume_dist。它们共享 WITHIN GROUP 语法，但有个特别容易踩的差异：前三个会忽略聚合输入里的 NULL，后四个不丢含 NULL 的输入行，NULL 怎么排由 ORDER BY 的 NULLS FIRST / LAST 决定。

还有一条硬约束只属于 hypothetical-set：direct arguments 要被拼成一行虚拟输入，所以数量和类型必须和排序列对得上。那这些身份是谁说了算？不是函数名，是系统目录。

07 · 身份由目录定义，执行器只认状态机

打开 pg_aggregate.dat，percentile_cont 的条目里写着 aggkind = o、aggnumdirectargs = 1、aggtransfn = ordered_set_transition、aggfinalfn = percentile_cont_float8_final、aggtranstype = internal。

这五行把三层串起来了：SQL 层看到的是一个聚合函数，解析器看到的是一个带 aggkind、aggorder、aggdirectargs 的 Aggref，执行器看到的是 transition function、final function 和一个 internal 类型的状态。很 PostgreSQL 的设计——目录只声明身份和机制，真正的活儿交给 C 函数。不过一条 SQL 想走到目录，得先过解析器那一关。

08 · 解析阶段：三道闸门挡住错误用法

三道闸门。gram.y 管语法形状：WITHIN GROUP 里必须有 ORDER BY，普通参数位置不能再写 ORDER BY，DISTINCT 和 VARIADIC 也不能放在那个语法位置。parse_func.c 按 aggkind 管语义：ordered-set 必须带 WITHIN GROUP、不支持 OVER、普通聚合不能带 WITHIN GROUP。parse_agg.c 再检查 direct arguments 的数量、类型，以及不能引用未分组列。

回归测试里那个经典错误就出在第三道：SELECT rank(x) WITHIN GROUP (ORDER BY x) FROM generate_series(1,5) x。报错不是 rank 不能用，是 x 被放到了 direct argument 位置——它每次调用只求值一次，不能跟着输入行一起变。闸门过了，输入行才真正进执行器。

09 · 执行流水线：先攒集合，再排序取位

这一页可以动手。上面一排是子计划吐出来的输入行，中间是 tuplesort 的槽位，下面是 final 阶段的动作条。改一下行数和分位点，点播放或者单步，看它怎么一步步走。

注意两个阶段的分工：Agg 节点逐行调用 ordered_set_transition，把非 NULL 的值 put 进 tuplesort，这时候槽内还是乱序的；排序不是 nodeAgg 的通用 ordered aggregate 路径替它做的，而是 ordered-set 自己的 support function 在 final 首次读取结果时调用 tuplesort_performsort，然后按目标位置 skip、get。还有个细节：单列的 ordered_set_transition 遇到 NULL 是整行跳过的，既不存也不计数；多列的 ordered_set_transition_multi 不丢含 NULL 的输入行。

10 · 状态是排序对象，不是数值

源码把状态分成两层，这个分层特别值得记：OSAPerQueryState 每查询一份，放排序列、排序操作符、collation、tuple descriptor 这些跨 group 不变的信息；OSAPerGroupState 每组一份，里面是 sortstate、number_of_rows、sort_done。

状态是排序对象，不是数值，直接带来两个工程现象。第一，它吃 work_mem，超了由 tuplesort 写临时文件，延迟会出现台阶，而不是平滑变慢。第二，目录没有给 combine、serialize 这条合并路径，所以它不是一个能天然 partial / parallel 的聚合。那集合排好之后，到底取哪一行？

11 · 取位公式：disc 取整行，cont 取插值

这一页也能动手。改分位点和 N，单步看两条路径怎么分叉。离散分位数找最小的 K，让 K/N 大于等于 fraction，源码就是 K = ceil(p × N)，然后跳过 K−1 行，返回第 K 行。

连续分位数走另一套：first_row = floor(p × (N−1))，second_row = ceil(p × (N−1))，proportion 是小数部分。两个位置相同就直接返回那一行，不同就调用插值函数；内置支持 float8 和 interval 两类。数组版本更聪明：先把多个 fraction 换成目标行号，按行号排序后顺序读一遍 tuplesort，避免每个分位点重扫一次。公式不同，结果自然也可能不一样。

12 · 同一个 p，两个结果

看三个我算好的示意例子，不是性能基准，只是把差异摆出来。偶数个输入 1、2、3、4 取 p50：disc 是第 2 行等于 2，cont 在 1.5 这个连续位置上插值，得到 2.5。重复值 1、1、9、9 取 p50：disc 是 1，cont 插到 5。非均匀间隔 1、2、3、100 取 p75：disc 是 3，cont 是 27.25。

带星号的值都不在输入集合里。所以业务上要分清：枚举、等级、价格档位，不希望冒出一个不存在的值，用 disc；延迟、耗时这类数值测量，允许插值，用 cont。还有一类函数连取位置都不用，它只数游程。

13 · mode()：把频率统计变成连续扫描

mode() 的实现有个很巧的取舍：它没有建哈希表统计频率，而是先排序，再顺序扫描。排序之后相同的值必然挨在一起，于是频率问题就变成了游程长度问题，状态里只需要维护当前值频次和当前最佳众数。

代价当然还是排序；收益是泛型比较就够了，任意可排序的 anyelement 都能处理，不用为泛型类型构造一套通用哈希状态。并列的时候，它取排序中先遇到的那个值。那如果问题不是取一个值，而是问「假设加一行会排第几」呢？

14 · hypothetical-set：往排序状态里插一行虚拟行

hypothetical-set 的语义是：把 direct arguments 拼成一行，假想它加入了排序集合，问这个窗口函数会给它什么结果。PostgreSQL 的做法很轻——不是往表里插数据，而是在本次聚合的 tuplesort 状态里临时加一个带 flag 的 tuple。

普通输入行 flag 是 0。rank、dense_rank、percent_rank 要让假设行排在 peers 前，用 −1；cume_dist 要排在 peers 后，用 +1。final 扫到 flag 不等于 0 的那一行再算排名。正因为 final 会修改排序状态，目录里 hypothetical-set final function 的 aggfinalmodify 是写入型。注意它和窗口函数的区别：窗口函数给每一行都算位置，hypothetical-set 只回答这一行假设值。

15 · 横向对比：四类方案，各自的目标不同

把边界拉远一点，四类方案放在一起看。Ordered-Set Agg 的目标是精确的每组一个结果；普通聚合是流式压缩；窗口函数是给每行算位置；P²、GK、t-digest 是用小状态做在线近似。

状态大小这一行最关键：精确排序聚合的状态和每组输入行数相关，另外三类要么常数、要么明显小于原始数据。Partial Mode 那一行也别跳过：官方文档标的是 No。所以这张表不是排行榜，是把「你要的到底是什么」问清楚。

16 · 决策线：误差能不能被接受

于是选型的第一步其实是个业务判断，不是技术判断：误差能不能被接受。P99 如果只是监控告警，晚两秒、差一点点，t-digest 这类 sketch 完全够用，还省内存、能流式。

但如果 P50、P95 要进 SLA 结算、审计报表或者离线校验，结果必须能被解释、被复核，那精确语义就值这个成本。换句话说，上一页那张表里最左列不是「更高级」，只是「更可交代」。选定精确这一侧，接下来就得把成本估清楚。

17 · 成本剖面：O(N) 攒，O(N log N) 排

粗略的复杂度是：每组 N 行，transition 做 N 次 put，final 做一次 O(N log N) 排序，再加 O(K) 的定位读取；空间上优先用内存，超过 work_mem 交给 tuplesort 落临时文件。

我刻意不给任何性能数字。数据类型、排序列宽度、work_mem、临时文件设备、分组分布，任何一项都能把结果改得很厉害。正确做法只有一条：拿业务数据或者合成分布，跑 EXPLAIN (ANALYZE, BUFFERS)，看是不是真的在写临时文件。原理讲完，我们落到四条可以执行的 SQL。

18 · DEMO ①②：取位与一次取多点

第一组 DEMO，把 disc 和 cont 放在同一条 SQL 里：输入 1 到 5，p50_disc 取第 ceil(0.5 × 5) 也就是第 3 行，返回 3；p60_cont 落在连续位置 0.6 × (5−1) = 2.4 上，在第 3 和第 4 个值之间插值，得到 3.4。

第二个是数组版本：percentile_cont(ARRAY[0.5,0.9,0.95,0.99])。它跟近似没关系，意义是「一次排序，多点读取」。补一个源码里的细节：PostgreSQL 允许 nodeAgg 合并输入和 transition function 完全相同的 ordered-set 状态，但 hypothetical-set 不共享；数组写法等于把这个意图直接写进语义，可读性也更明确。

19 · DEMO ③④：分组 P95 与假设排名

真上生产，第三个 DEMO 更重要：设一个 work_mem，用 EXPLAIN (ANALYZE, BUFFERS) 看按 tenant_id 分组算 P95。观察重点不是总行数，而是有没有临时文件读写、单个大 tenant 会不会拖慢整体、把 work_mem 调大是不是只是减少了落盘而不是线性加速，以及能不能先按时间、租户、接口维度预聚合。

第四个 DEMO 是假设排名：rank(3)、dense_rank(3)、cume_dist(3) 一起查，验证的是「假设值 3 插进集合会处在什么位置」。再次提醒，它只返回这一行假设结果，不是给每行算位置。本文没有启动实例跑这些 SQL，所以不贴伪造的执行输出。

20 · 最佳实践：三个角色，三套动作

把前面的结论按角色收成动作。架构师定边界：把 Ordered-Set Agg 定位成精确报表能力，不是监控系统里的默认 P99；先判断能不能允许近似；必须精确时按时间窗、租户、业务线分层，控制单组规模。

DBA 盯资源：work_mem、临时文件、慢 SQL 里的 percentile_cont / disc；别只靠调大 work_mem，因为每个查询、每个排序和哈希节点都可能吃内存；用 EXPLAIN (ANALYZE, BUFFERS) 和日志里的 temporary file 信息验证落盘。开发者选函数：不希望插值用 disc，数值测量用 cont，多个分位点用数组版本，别把随行变化的列放进 direct argument。

21 · 场景边界与五个常见坑

最后把边界和坑一次说清。适合的是离线报表里的精确 P50 / P90 / P95、每组规模可控的统计、要 SQL 标准语义的审计复核、以及按排序定义算假设排名。不适合的是每秒写海量指标只要近似 P99 的监控、单组数亿行还要低延迟交互、需要强 partial / distributed merge 的实时分析。

还有个特别常见的误会：以为有 (tenant_id, latency_ms) 索引就能直接跳到 95% 的位置。索引可能帮过滤、也可能提供有序路径，但不能把任意分组的分位数变成常数时间查询，一般聚合执行仍然要处理满足条件的输入集合。底下五个坑也顺手记一下：ORDER BY 写错位置、拿它当窗口函数加 OVER、忽略 NULL 语义差异、误以为 cont 一定等于真实中位数行、高基数分组再叠 P95。

22 · 收束：从语法到选型，是一条自底向上的链

回头把七层重新走一遍：WITHIN GROUP 把顺序写进语义，解析器用三道闸门守住用法，目录用 aggkind 定身份，执行器用 transition 攒集合，tuplesort 做精确排序，然后才有真实值、插值、众数和假设排名，最后回到业务——误差能不能被接受。

所以一句话收束：精确不是免费的；我们选它，不是因为它快，而是因为结果需要被解释、被复核。留三个问题给你：误差允许 0.1% 时你会把近似分位数放在扩展、流处理还是应用侧；已有 (tenant_id, latency_ms) 索引时哪些查询真能受益；如果要做一个可 partial aggregation 的近似 P99，它的 transition state、combine、serialize / deserialize 该长什么样。
