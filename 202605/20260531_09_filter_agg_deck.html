本页讲稿 · N
01 · 聚合之 FILTER Agg

今天只讲一个看起来很小、但特别容易被误用的语法：聚合后面那个 FILTER。你可能写过很多次 sum(amount) FILTER (WHERE status = 'paid')，觉得它跟 CASE WHEN 差不多，甚至觉得它就是一个更时髦的 WHERE。都不太对。

我把它拆成七层：最上面是业务怎么选写法，最下面是 WHERE、FILTER、HAVING 三个门禁的作用范围。中间四层是语法语义、内部表示、执行器求值顺序，还有优化器与并行。越往下越底层，也越决定上面能做什么。我们从一条真实形态的报表 SQL 出发，一层层往下挖，最后回到一句很朴素的判断：我是要选择行，还是要改写值。

02 · 一条报表 SQL，四个行范围

先看这条 SQL：按门店分组，算总订单数、已支付金额、退款金额、APP 订单数。它们来自同一张 orders 表，WHERE 只做一件事——把范围限定到今天的订单。剩下四个指标，各自要的行并不一样。

这就是条件聚合的典型场景。如果不用 FILTER，我们通常会给每个指标写一段 sum(CASE WHEN status = 'paid' THEN amount ELSE 0 END)。能跑，但条件被塞进了参数里。这里先埋一个问题：四个指标的行范围不同，数据库凭什么在一次扫描里同时算出来？答案不在 WHERE，而在每个聚合调用自己身上。

03 · 三层门禁：WHERE / FILTER / HAVING

先把范围说死。WHERE 位于聚合之前，影响整条输入流，被它去掉的行不会进入任何聚合；HAVING 位于聚合之后，聚合都算完了，它才决定哪些分组留下来；FILTER 夹在中间，但它不是流水线上的一段，而是挂在某一个聚合函数上的开关。

PostgreSQL 官方教程用天气表讲过这点：count(*) FILTER (WHERE temp_lo < 45) 只过滤 count 的输入，旁边的 max(temp_lo) 仍然能看到同组所有行。官方文档的语法页还给了可核验的例子：generate_series(1,10) 上，count(*) 是 10，count(*) FILTER (WHERE i < 5) 是 4。所以 FILTER 的本质是聚合函数的局部门禁，不是行级全局过滤。

04 · 一行在组内，会遇到四道门禁

这一页可以动手。左边是组内依次到达的输入行，中间是四个聚合调用，右边是这一个分组累积的 transition state。改一下场景和行数，点播放或者单步，看每一行走过去会发生什么。

注意看「无匹配」那个场景：一行 paid 都没有的时候，paid_amount 显示的是 NULL 而不是 0。这不是动画偷懒，是 sum 对空输入的真实规则，后面我们还会专门讲。你会看到同一个 r1 可以同时进入 orders、进入 paid_amount、跳过 refund_amount、也跳过 app_orders——一次扫描，四个指标，靠的就是每个调用各自判断。既然门禁这么用，那它到底能挂在哪些聚合形态上？

05 · 语法覆盖面：哪些调用能挂 FILTER

官方文档列出的几种聚合语法形态，尾部都带可选的 FILTER：普通聚合、ALL / DISTINCT 形式、带聚合内 ORDER BY 的形式、count(*) 星号形式，还有 ordered-set 的 WITHIN GROUP 形式。窗口函数调用的语法里也有 FILTER，位置在 OVER 之前。

所以 percentile_disc(0.95) WITHIN GROUP (ORDER BY latency_ms) FILTER (WHERE success) 是合法写法，array_agg(event ORDER BY ts) FILTER (WHERE event IS NOT NULL) 也是。但有一条硬边界官方文档写得很清楚：只有「本身是聚合的窗口函数」接受 FILTER，普通非聚合窗口函数不接受；ordered-set 和 hypothetical-set 聚合当前根本不能当窗口函数用。语法这么宽，语义约束就得跟上。

06 · 五条语义硬规则

五条规则，第一条最基础：filter_clause 必须能转成布尔表达式。第二条最容易被忽略：只有结果为 true 的行才被喂给这个聚合，false 和 NULL 都不进入。文档的原话是 only the input rows for which the filter_clause evaluates to true are fed to the aggregate function。

后面三条是从源码和回归测试里来的：FILTER 里不能塞同层聚合函数，回归测试专门覆盖了 aggregate functions are not allowed in FILTER 这个报错；PostgreSQL 允许某些外层引用出现在 FILTER 中，这会影响聚合所属 query level，不能想当然认为它总是内层聚合；普通非聚合窗口函数不支持 FILTER，parse_func.c 会报错。规则立住了，我们看它在内部表示里是什么。

07 · 它不是字符串条件：Aggref.aggfilter

打开 src/include/nodes/primnodes.h，Aggref 里 aggsplit 之类字段旁边，就躺着 aggfilter。它和 args、aggorder、aggdistinct 是并列的，都是「这一次聚合调用」的属性。窗口那边对应的是 WindowFunc.aggfilter。

这一点决定了后面所有现象：它不是独立的 plan node，不是普通的 WHERE 条件，也不是解析器简单把 CASE 重写一遍再交给执行器。普通函数与聚合路径在 parse_func.c 里构造 Aggref，JSON 构造器路径在 parse_expr.c 里构造 Aggref 或 WindowFunc，两边都把结果写进 aggref->aggfilter = agg_filter。既然它是语义树里的字段，解析器就得为它做专门处理。

08 · 解析阶段：它参与聚合层级判断

语法层认出 FILTER (WHERE a_expr) 之后，解析转换用 transformWhereClause 加 EXPR_KIND_FILTER 这个表达式种类，把它处理成布尔表达式；然后 Aggref 被填好。关键的一步在 parse_agg.c：check_agglevels_and_constraints() 会把 filter 和 direct args、regular args 一起交给 check_agg_arguments()，用来判断聚合层级和非法嵌套。

换句话说，FILTER 参与「这个聚合属于哪一层查询」的判断。回归测试覆盖了外层引用、子查询、boolean Var 这些情况，所以别把它当成执行器最后临时看一眼的字符串条件。语义树定下来了，接下来才是真正有意思的部分：执行器怎么让这道门禁既正确又便宜。

09 · 执行器：把四步编译成一个大表达式

PostgreSQL 出于性能原因，没有在 nodeAgg.c 里逐行循环调用 transition function，而是用 ExecBuildAggTrans() 构建一个较大的表达式，把参数求值、过滤、strict 检查和 transition 调用串成一串步骤。好处有两个：减少重复的解释执行开销，也方便 JIT 把整段表达式编译成本地函数。

execExpr.c 里的顺序不能错：如果有 aggfilter 且不是 combine 阶段，先求 filter；结果不为 true，就直接跳到本聚合 transition 工作的末尾；通过之后才求聚合参数、做 strict 检查、调用 transition function。源码注释明确说，过滤放在参数求值之前是为了避免不必要的计算，甚至避免不该发生的副作用。这个「甚至」值得单独看一页。

10 · 求值顺序：FILTER 先于参数求值

这一页也能动手。输入行里有 x = 0，表达式是 sum(10 / x) FILTER (WHERE x <> 0)。改输入集合和被除数，单步看：x = 0 那一行，FILTER 先算出 false，直接跳到末尾，10 / x 根本没被求值，所以不会触发除零错误。

官方文档在表达式求值规则那一节也提醒过：min() 和 avg() 这类聚合是并发计算的，如果某一行会让表达式报除零，别指望先测结果，要用 WHERE 或 FILTER 把问题行挡在聚合之外。反过来，如果某些预排序或改写路径先算排序键、先算参数再过滤，错误行为就变了——这正是 planner 对带 FILTER 的 ordered aggregate 预排序格外保守的原因。特别说明：这是理解执行器约束的例子，不是业务 SQL 风格建议。

11 · FILTER 与 CASE：门在调用上，还是在参数里

很多条件聚合确实能用 CASE 改写，但「结果相同」和「语义清晰、代价相同」是两回事。上轨的 sum(CASE WHEN p THEN x ELSE 0 END)，条件是参数表达式的一部分，每一行都要走聚合输入；下轨的 sum(x) FILTER (WHERE p)，条件是调用的行门禁，没通过的行连参数都不用求。

所以 FILTER 的清楚之处在于它只回答一件事：行是否进入聚合。CASE 的灵活之处在于它回答另一件事：行进入聚合前被映射成什么值。如果业务需要把成功订单映射成 amount、退款订单映射成 -amount、其他映射成 0，CASE 更自然；如果只是多个指标各自挑输入行，FILTER 更自然。那到底哪些改写是安全的？

12 · 等价与不等价：五条边界

把常见目标排一排。条件计数，count(*) FILTER (WHERE p) 和 sum(CASE WHEN p THEN 1 ELSE 0 END) 能对应上；条件求和，sum(x) FILTER (WHERE p) 对应 sum(CASE WHEN p THEN x END)，注意是 END 不是 ELSE 0；条件数组，CASE 版本可能把 NULL 放进数组。

越往后越要小心：array_agg(x ORDER BY y) FILTER (WHERE p) 换成 CASE 版本，未通过行的排序表达式仍然可能被处理；到了 percentile_disc 这类 ordered-set 聚合，direct argument 和 WITHIN GROUP 的参数模型更复杂，通常不建议硬改写。这里面最容易在生产里出事的，是 NULL 和 0 的区别。

13 · 0 还是 NULL，是业务语义

假设一个分组里没有任何一行满足 p。sum(CASE WHEN p THEN amount ELSE 0 END) 会把每一行映射成 0，四行 0 求和，结果是 0；sum(amount) FILTER (WHERE p) 则是一行都没进入这个聚合，sum 按空输入规则返回 NULL。

这不是谁对谁错：0 表示「金额为零」，NULL 表示「没有数据」，是两种业务事实。对 avg、array_agg、json_agg 差别更明显，ELSE 0 会污染均值、把 0 塞进数组或 JSON。还有个连带规则要记住：count(CASE WHEN p THEN 1 END) 之所以能当条件计数，靠的是 count 忽略 NULL，这依赖聚合自身的规则。到底要 0 还是 NULL，先让业务定，再决定 SQL 怎么写。

14 · DISTINCT / ORDER BY 与预排序的保守边界

普通 sum(x) FILTER (WHERE p) 的顺序很干净：先判 p，再求 x。但带 DISTINCT 或聚合内 ORDER BY 的聚合，执行器还要维护排序、去重输入。build_pertrans_for_aggref() 里有个细节：只要存在排序或过滤，就会为聚合输入创建对应的 tuple descriptor 和 slot——FILTER 会进入 per-transition 状态构建，不只是 planner 层的一行注释。

真正的边界在预排序优化。planner.c 会尝试让输入提前满足聚合内 ORDER BY / DISTINCT 的 pathkeys，但源码对带 FILTER 的聚合加了保守检查：如果参数表达式不是简单 Var 或 Const 这类安全形式，就跳过预排序候选。原因是预排序可能先算排序表达式，而正常语义是先应用 FILTER 再处理该聚合的排序输入；如果排序表达式可能报错，提前求值就改变了行为。看见「加了 FILTER 就不预排序」，先想求值顺序，别先怀疑优化器偷懒。

15 · 优化器的四个边界

因为 aggfilter 是聚合调用的属性，优化器至少有四处会碰到它。第一，两个聚合要共享同一个 transition state，ORDER BY、DISTINCT、FILTER 这些 transition 阶段属性必须全同；第二，filter 表达式的成本会计入聚合 transition 成本，源码里还有个 XXX 注释说理想情况应该按选择率折减参数成本，但当前没这么做。

第三，MIN/MAX 索引优化遇到 FILTER 当前直接放弃；第四，并行 partial / final 拆分时，parent Aggref 的 aggfilter 被清空，原始过滤保留在 child 上。这四个不是四个独立特性，是同一件事的四个后果：条件属于聚合调用。把它当普通 WHERE，就会误判很多计划现象。先拆最直观的共享判断。

16 · 聚合共享：条件相同才算同一个聚合

prepagg.c 的注释说得很直白：两个聚合想共享同一个 transition state，ORDER BY、DISTINCT、FILTER 都得一样。所以 SELECT sum(x) FILTER (WHERE p), sum(x) FILTER (WHERE p) 可以被识别为相同聚合；换成第二个是 WHERE q，即便参数都是 x，也不能共享——进入两个状态的行集合不同，硬合并就算错了。

这里有个很实际的坑：status = 'paid' 和 'paid' = status 语义相同，但表达式树未必被识别为同一个 filter。指标一多，重复但写法不同的条件会让执行器做更多工作。真遇到一堆互相重复的复杂 FILTER，可以在子查询里先把公共布尔列算出来。接下来看另一条更让人意外的边界：明明有索引，计划却变了。

17 · MIN/MAX 索引改写：三条 SQL 的分叉

planagg.c 本来可以把某些 min(col) / max(col) 改写成走索引的子查询路径。但源码注释承认：理论上可以把 filter 加到生成子查询的 quals 里，目前没有实现，所以 aggref->aggfilter 不为空时直接返回 false。这解释了一个常见现象：SELECT min(ts) FROM events 可能得到 MinMaxAggPath，而带上 FILTER (WHERE status = 'ok')，即使索引合适也未必触发同一个改写。

这个结论也有独立的实践佐证：有人遇到 max(updated_at) FILTER (WHERE status = 'active') 走全表扫描，把条件挪进 WHERE 后重新拿到索引探针。可别急着当成通用公式——把条件放进 WHERE 只在查询里所有指标都能接受同一个全局条件时才等价。多指标报表往往不满足，这时候你得在「共享一行扫描」和「单个 min/max 用索引」之间做取舍。

18 · 并行聚合：FILTER 在 worker 侧完成

对于支持 partial mode 的聚合，带 FILTER 的 SQL 仍然可能参与并行聚合，前提是聚合函数、表达式和计划满足 parallel safe 这些条件。执行模型是：worker 扫描原始行、逐行求 FILTER、通过的才更新本地 transition state，然后输出 partial state；leader 通过 Gather 收到这些 state，combine 之后跑 finalfn。

setrefs.c 的 convert_combining_aggrefs() 明确把 parent Aggref 的 aggfilter 清空，把原始 aggfilter 留在 child Aggref 上。原因很直接：Finalize 阶段看到的是 worker 输出的 partial state，不是原始业务行，无法也不应该重新执行行级过滤；execExpr.c 里 combine 分支也不再执行过滤。所以两个结论：FILTER 不会阻止所有并行聚合，它不是 DISTINCT / ORDER BY 那类硬限制；但 FILTER 表达式本身不 parallel safe 时，整条查询仍可能拿不到并行计划。

19 · WindowAgg：语义一致，路径不同

nodeWindowAgg.c 里有段 advance_windowaggregate()，注释说它平行于 nodeAgg.c 的 advance_aggregates。窗口聚合的处理更直观：先执行 ExecEvalExpr(filter, econtext, &isnull)，如果结果是 NULL 或 false，就直接 return，不推进窗口聚合状态。

所以 SQL 语义是一致的：FILTER 过滤某个聚合函数的输入。但普通 Agg 为了性能，用 ExecBuildAggTrans() 把过滤、参数求值和 transition 调用编译成大表达式，还可能被 JIT；WindowAgg 则按窗口帧逻辑单独推进。再补一次边界：普通非聚合窗口函数不支持 FILTER，parse_func.c 会报错；ordered-set 和 hypothetical-set 聚合当前也不能用作窗口函数。到这儿四条路线都齐了，可以并排比一比。

20 · 横向对比：四种写法各管一层

把 FILTER、CASE、WHERE、HAVING 并排看。FILTER 的目标是让每个聚合函数选择自己的输入行，不影响旁边聚合，未通过时可跳过参数求值；CASE 是把输入行映射成聚合参数值，NULL 语义由 ELSE 怎么写决定；WHERE 减少整条输入流，能下推、用索引、做分区裁剪；HAVING 在聚合算完后筛分组，只影响输出。

表里最该细看的是「优化器边界」那一行：FILTER 参与 aggfilter 成本、共享判断和 partial child 拆分，CASE 只是普通表达式成本与简化，WHERE 才有完整的下推能力。所以这张表不是排行榜，原则只有一句：尽量把条件放在它真实生效的层次。能全局过滤就用 WHERE，只影响某个指标就用 FILTER，需要值变换就用 CASE，需要按聚合结果筛组就用 HAVING。

21 · 收益从哪来，代价在哪

收益不是「数据库少扫表」，是「少做某些聚合输入和状态更新」。四个因素决定大小：过滤选择率越低，跳过参数求值和 transition 的机会越多；参数表达式越贵越明显，sum(amount) 很便宜，expensive_function(payload) 才看得出差别；transition state 越重越明显，count(*) 很轻，array_agg、jsonb_agg、ordered aggregate 的排序输入更重；还有并列指标的数量，同一次扫描算多个条件指标通常比多次扫描划算。

成本也对得上：每个 FILTER 条件本身仍要按行求值；多个不同 FILTER 让 transition state 无法共享；MIN/MAX 特殊优化会放弃；带 ORDER BY 或 DISTINCT 时预排序要保守处理。我刻意不给性能数字——素材里提到的两篇论文没有在本地找到可核验全文，所以不引用任何实验数据。可以确认的是，PostgreSQL 当前行执行器不是向量化批量条件聚合路径，它的选择是表达式执行引擎加可能的 JIT。真要判断，拿业务数据跑 EXPLAIN (ANALYZE, BUFFERS)。

22 · 实操 DEMO：四组可验证的 SQL

第一组用 generate_series 造一百万行带 status、channel、amount 的表，然后跑 EXPLAIN (ANALYZE, BUFFERS, VERBOSE) 看多指标查询：用的是 HashAggregate 还是 GroupAggregate，聚合节点下方是不是只扫了一次表，VERBOSE 里目标表达式是不是显示 FILTER (WHERE ...)。第二组对比 FILTER 与 WHERE 的边界，两条 SQL 只有在你只关心已支付订单时才等价。

第三组是 MIN/MAX：建索引后分别 EXPLAIN 无过滤、带 FILTER、把条件放进 WHERE 三条，看第一条和第三条更可能拿到利用索引顺序的计划。第四组是除零，用来理解求值顺序，别当成业务写法建议。原文明说没有在本地启动 PostgreSQL 实例执行，所以我这里也不提供虚构输出；请你在自己的测试库里跑，用自己的数据说话。

23 · 最佳实践：三个角色，三套动作

架构师这边，把 FILTER 当指标建模工具，不要当性能魔法。指标平台、宽表报表、BI 查询生成器里，用 FILTER 表达「同一事实表、同一分组维度、多个条件指标」，SQL 更接近指标定义，也更容易审查总量、分子、分母的输入范围。反过来，如果所有指标共享同一个条件，就放进 WHERE，让优化器拿到索引、分区裁剪、连接顺序和行数估计的收益。

DBA 排查慢查询时别只盯有没有 FILTER，按顺序看：WHERE 有没有最大限度减少共同不需要的行、GROUP BY 基数有没有撑爆 Hash Agg 内存或落临时文件、FILTER 条件是否重复复杂含昂贵函数、有没有本可走 MIN/MAX 特殊优化却因 FILTER 失效、并行计划里有没有 Partial Aggregate。开发者更简单，先问一句：我是选择行还是改写值？选择行用 FILTER，改写值用 CASE，全局用 WHERE，筛组用 HAVING；NULL 敏感的指标先定要 0 还是 NULL。

24 · 场景边界与五个常见坑

适合的地方很集中：仪表盘一次查多个分子分母、状态计数，同一事实表按状态渠道风险等级做分组，条件数组、JSON 聚合、分位数聚合，并行聚合里希望 worker 侧先压缩 transition state，还有 SQL 生成器需要稳定表达每个指标自己的过滤条件。不适合的地方也很清楚：条件适用于整个查询且能放进 WHERE；只做一个 min/max 且条件可全局下推；业务语义是按条件把值映射成不同权重；大量复杂且重复的 FILTER 把 CPU 成本顶上去；以及指望 FILTER 自动带来向量化、位图共享或跨聚合条件合并——PostgreSQL 当前没有把这些编译成专门的批量条件聚合算子。

五个坑顺手记一下：把 FILTER 当 WHERE，于是以为 count(*) 也会变少；CASE 的 ELSE 破坏 NULL 语义，avg、array_agg、json_agg 尤其危险；忽视 FILTER 对聚合共享的影响，写法不同就共享不了；以为 FILTER 一定比 CASE 快，其实简单 CASE 可能很便宜、复杂 FILTER 本身可能很贵，要用 EXPLAIN (ANALYZE, BUFFERS) 验证；还有最容易漏的 ordered aggregate 求值顺序边界。

25 · 收束：从作用范围回到一句业务判断

回头把七层重走一遍：WHERE 管行、FILTER 管聚合调用、HAVING 管分组结果；五种聚合形态都支持 FILTER，只有 true 的行进入，窗口聚合另走一条路径；它在内部是 Aggref.aggfilter，不是 plan node 也不是 CASE 重写；执行器用 ExecBuildAggTrans 先判过滤再求参数，所以求值顺序是语义的一部分；优化器的共享、成本、MIN/MAX 改写、partial child 拆分，全都是这个字段带来的后果；最后回到业务——选择行用 FILTER，改写值用 CASE。

所以一句话收束：FILTER 的价值不是「更快」，而是把条件放在它真实生效的层次，让指标定义可被审查、可被复核。留三个扩展问题给你：一个查询有 20 个互斥 FILTER 指标时，执行器能否把它们优化成一次分类后更新不同状态，列存或向量化系统会怎么答；FILTER 的公共子表达式能否自动抽取，还是得靠子查询显式算布尔列；带 FILTER 的 min/max 未来能否改写成带条件的 index scan 子查询——planagg.c 的注释说理论可实现，目前没有实现。
