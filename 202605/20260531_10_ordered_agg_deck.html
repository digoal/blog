01　聚合之 Ordered Agg

这一讲只做一件事：把「聚合函数里的 ORDER BY 和 DISTINCT」这条线，从 SQL 语法一路追到执行器的 transition function。你可以把它当成上一篇 Ordered-Set Agg 的姊妹篇——两篇文章都出现 ORDER BY，但责任的落点完全不同，千万别混。

我先给一张剖面图。最上面是 SQL 表达式，最下面是结果；中间依次是解析、预处理、规划器、执行器初始化、执行器排序。请注意颜色：越深的靛青代表越底层。整场演说，我们会一层一层往下沉，再从执行代价浮回业务决策。素材主要来自 PostgreSQL 官方文档与本地源码，回归测试里的现象我会明确标注是「预期」还是「实测」。

为什么值得单独讲一讲？因为顺序一旦写进聚合调用，代价不是「多一个 ORDER BY 关键字」这么简单：它会改变能不能并行、能不能走 hash 聚合、planner 要不要额外排序。这些都是物理层面的连锁反应。

02　一条看起来无害的业务 SQL

先看这段 SQL。按 customer_id 分组，一次算出用户画像、事件路径、标签数组。写的时候很顺手，读的时候也很像「普通聚合加了个排序」。但请注意 ORDER BY 的位置：它写在每个聚合函数的括号里面，而不是语句末尾。

语句末尾的 ORDER BY 控制结果行的展示顺序；括号里的 ORDER BY 控制的是输入行被 transition function 看到的先后。这个区别看起来只是括号位置，实际上把这类聚合从「状态累加」推到了「序列构造」。string_agg 拼出来的字符串、array_agg 拼出来的数组、jsonb_object_agg 在重复 key 下保留哪个值，全都被输入顺序改变。

所以这条 SQL 真正的问题是：它看起来还像普通聚合，却已经把顺序写进了结果定义。接下来我们把「普通」和「顺序敏感」摆在一起，看差异到底落在哪一步。

03　差别只在 transition 看到的序列

把两类聚合并排看，差异非常干净。左边 sum(x)，三行进来的先后换一换，状态都收敛到 6。因为它的 transition function 只是在更新一个标量状态，加法满足交换律，顺序没有信息量。右边 string_agg 就不一样了：三行是 login、view、pay，时间戳分别是 3、1、2。按到达顺序拼，得到 login > view > pay；按 ts 排好再拼，得到 view > pay > login。值本身变了，不只是「好不好看」。

这里请记住一个词：transition function。它是聚合真正处理每一行的函数。Ordered Agg 的定义就是——这个函数必须按指定顺序看到输入行，结果才有稳定语义。注意图里右侧第一行我标了「未写 ORDER BY · 结果不确定」，不是说它一定错，而是说你没有权利期待它稳定。

那有人会说，我把子查询排好序不就行了？这正是文档专门提醒过的坑，下一页我们把它拆开。

04　顺序必须写进表达式，不能寄望子查询

官方文档 4.2.7 的原话是：Ordinarily, the input rows are fed to the aggregate function in an unspecified order——输入行顺序默认不指定。9.21 节更补了一刀：用排序子查询提供输入「通常可行」，但如果外层查询还有 join 之类的额外处理，子查询的输出可能在聚合计算之前被重排。

为什么会这样？因为子查询的 ORDER BY 只是那个子查询的输出属性，优化器在做连接、做改写、选择 join 顺序的时候，没有义务为外层的聚合保留它。而写在聚合调用里的 ORDER BY 不一样：解析阶段它会被放进 Aggref 的 aggorder 字段，成为表达式自身的一部分，谁改写计划都得带着它走。

所以结论不复杂：需要稳定顺序，就写 array_agg(x ORDER BY k)、string_agg(x, ',' ORDER BY k)、jsonb_object_agg(k, v ORDER BY updated_at)。别假设表扫描顺序、插入顺序或者子查询排序会一直稳定。那顺序成了语义之后，第一个被改变的是谁？是结果值本身——我们看一个最容易踩的例子。

05　顺序不只影响排版，还改变保留的值

这个例子我特别喜欢，因为它把「顺序是语义」变成了可以眼见为实的值变化。官方文档 4.2.7 给的例子是三行：key0 值 1、key1 值 3、key1 值 2。写 jsonb_object_agg(k, v ORDER BY v)，按 v 升序，写入次序是 1、2、3，key1 最后写进去的是 3，所以结果是 {key0: 1, key1: 3}。文档那句 Since jsonb only keeps the last matching key 就是原因。

下面这一行是我按同一条规则往下推的示意，不是文档原例：如果改成 ORDER BY v DESC，写入次序变成 3、2、1，key1 最后写进去的变成 2。同一个查询、同一批行，只换排序方向，结果里的值就换了。所以业务上「保留最新值」还是「保留优先级最高的值」，必须写进 ORDER BY，并且写进接口契约，不能靠默认值。

好，语义这一侧已经坐实了。接下来我们转到物理侧：一旦把顺序写进聚合调用，PostgreSQL 的优化空间会立刻收窄，而且是五个方向同时收窄。

06　顺序契约的五个物理后果

先把账摆出来，免得后面讲到执行细节时觉得是零散知识点。第一、第二条在执行器：每个带 ORDER BY 的聚合、每一组输入可能都要自己排一次序；带 DISTINCT 还要在排序之后比较相邻值跳过重复。第三条在规划器：为了让输入预排序，planner 可能去选更贵的全局排序或者索引路径。第四条在并行能力：prepagg.c 会因为 aggorder 或 aggdistinct 非空，把 hasNonPartialAggs 置成 true，常规的 partial aggregation 就此打住。第五条在聚合策略：带 ordered aggregate 的分组不走 HashAggregate。

这五条其实有共同的根：普通聚合可以把状态留在 hash 表里，行来了就更新；Ordered Agg 必须保证「某个聚合看到的输入序列」正确，而 hash 表本身不提供每组内的有序输入。你可以把后面十几页理解成一句话的展开——顺序需求改变了聚合的物理形态。

不过在追物理之前，得先把定义钉死：Ordered Agg 到底指哪些写法、落在哪些字段、又不包含哪些写法？否则很容易跟上一篇的 Ordered-Set Agg 混淆。

07　Ordered Agg 指两类输入约束

本文所说的 Ordered Agg，范围要划清楚：它指普通聚合调用里的两类输入约束，一是 ORDER BY，二是 DISTINCT，加上它们同时出现时的组合。语法形式就上面两行。注意它是一份「输入顺序或唯一性契约」，不是一个新的执行节点名字。

解析期有两条硬规则。第一条，多参数聚合的 ORDER BY 必须放在所有参数之后，写 string_agg(a, ',' ORDER BY a)；如果写成 string_agg(a ORDER BY a, ',')，语法上仍然合法，但它被解释成单参数聚合带两个排序键，第二个是常量，等于没写。第二条，DISTINCT 和 ORDER BY 同时出现时，ORDER BY 表达式只能引用 DISTINCT 列表里的表达式；源码注释说得更精确：有 DISTINCT 时，ORDER BY 是 DISTINCT 的前缀。回归测试里 string_agg(DISTINCT f1::text, ',' ORDER BY f1) 就是被判错的一类。

这两条规则不是风格建议，是解析阶段就要检查的语义边界。检查通过后，约束会落到 Aggref 节点上——这才是后续所有优化的入口。

08　契约落在 Aggref 的两个字段上

看 Aggref 的字段地图，思路会一下子清楚。aggorder 和 aggdistinct 是两个 SortGroupClause 列表，primnodes.h 的注释说得很直接：它们表示在输入行传给 transition function 之前要应用的排序和去重操作。args 里除了真正的聚合参数，末尾还可能追加 resjunk 的 TargetEntry——那些只是排序用的表达式，对普通聚合来说不算参数。

还有一个字段 aggpresorted，解析阶段先设成 false。它不属于 SQL 语义，而是 planner 后来填上去的物理判断：如果下层路径提供的顺序已经满足这个聚合，就标成 true，执行器可以省掉内部排序。右边三条线正好对应三个层次的职责——解析层写契约、规划层写物理判断、执行层读字段决定要不要排序。

这里顺便把最常见的混淆切断：percentile_cont(0.95) WITHIN GROUP (ORDER BY latency) 也带 ORDER BY，但它是 ordered-set aggregate，aggkind 是 o 或 h，排序由自己的 support function 维护。下一页把两者逐行对比。

09　同一个关键词，两种责任落点

这张表请当成排查手册用。两类聚合都写 ORDER BY，但语法位置、aggkind、排序责任、能否 partial 全不一样。最要紧的是「排序责任」这一行：本文的 Ordered Agg 由通用 nodeAgg.c 路径排序，planner 还可以提前把顺序交给下层路径；Ordered-Set Agg 的排序通常由 support function 自己维护 tuplesort，通用路径不插手。

还有个容易忽略的差异：普通聚合的 ORDER BY 表达式不是聚合参数，只用来排序；ordered-set 聚合里 WITHIN GROUP 的表达式反而就是 aggregated arguments，而括号前面的 direct arguments 每组只算一次。字段布局、执行分支、可并行性都从这里分岔。

所以排查性能时别只看关键字。先看 aggkind，再看计划里是谁在排序。现在我们可以把整条控制链路铺开了：从 SQL 到 transition function，一共四层接力，每一层只做一个决定。

10　一句话下沉七层，每层只做一个决定

把整条链路铺开，会发现它没有「一个叫 Ordered Agg 的节点」。有的只是七个层次各自做的一个小决定：SQL 把顺序写进调用；解析层把它变成 Aggref 字段；预处理层发现它之后关掉 partial aggregation；规划器挑一组 pathkeys 并关掉 hash 聚合；执行初始化决定要不要内部排序；执行器真的排、真的去重、真的按序喂给 transition；最后 finalfn 产出结果。

这也解释了为什么排查这类问题特别费劲：你在 EXPLAIN 里看到的是 Sort、GroupAggregate，看不到「顺序契约」这个东西，因为它分散在 Aggref 的字段、planner 的 pathkeys 和 executor 的分支里。任何一层判断不同，计划形态就不同。

接下来我们逐层放大。先看最上面两层：解析层只负责把语义写进字段，它完全不承诺物理计划长什么样。

11　解析层只写语义，不承诺计划

解析阶段发生的事很朴素：parse_expr.c / parse_func.c 先建出 Aggref，aggpresorted 设成 false；随后 parse_agg.c 的 transformAggregateCall() 把 aggorder、aggdistinct、args 这些字段补齐。语法检查也在这附近完成——ORDER BY 的位置、DISTINCT 与 ORDER BY 的表达式匹配。primnodes.h 还提醒我们，普通聚合的 args 末尾可以追加 resjunk 的 TargetEntry，那些条目只用于排序，不是聚合参数。

关键在于右边那一栏：这一层什么都不承诺。它不决定排序由谁做、不决定走 hash 聚合还是 group 聚合、不决定能不能并行。它只是把「我要这个顺序」写进解析树，让后面每一层都能看见。工程上这很重要——语义和物理计划解耦，planner 才有空间根据代价做选择。

但空间是有限的。到了预处理层，第一个门就被关上了：只要 aggorder 或 aggdistinct 非空，常规 partial aggregation 就不做了。这一条值得单独用一张图讲清楚，因为它最反直觉。

12　为什么 partial aggregation 必须停

prepagg.c 的判断非常干脆：只要 aggref->aggorder 或 aggdistinct 非空，就 numOrderedAggs++ 并且把 hasNonPartialAggs 置成 true。planner 里 can_partial_agg() 看到这个标志就直接返回 false。为什么？看图里三个 worker：A 看到 ts 1 和 4，B 看到 2 和 5，C 看到 3 和 6，各自排好序都没错，但把三个局部数组直接拼起来，全局顺序是乱的。要正确，必须按全局的 ts 重新归并。

有人说 PostgreSQL 不会排序吗？当然会。问题在于 partial aggregation 的契约是「每个 worker 产出一个 transition state，上层用 combine function 合并」。sum 的部分和相加就对了；有序数组的 combine 需要全局归并，而通用聚合框架目前没有把这类 per-aggregate ordered state 当成可并行归并对象处理。nodeAgg.c 文件头的注释也把理由写死了：partial aggregation is not supported in these cases, since we couldn't ensure global ordering or distinctness of the inputs。

这里补一个容易混淆的版本差异：PG16 起，普通的 array_agg 和 string_agg 已经有了 combine function，可以参与并行 partial；但只要调用里带 ORDER BY 或 DISTINCT，prepagg 这条判断照样触发。挡住的是「ordered-input」，不是函数名字。

13　HashAggregate 为什么被关掉

planner.c 里有一句非常直白的注释：Executor doesn't support hashed aggregation with DISTINCT or ORDER BY aggregates。理由也写在旁边——真要做，就得在 hash 表里存下所有输入值，或者并行运行很多个排序，作者的评价是 either of which seems like a certain loser。落到代码就是底下那行：numOrderedAggs 为零、并且 groupClause 可 hash，才允许 hash 聚合；ordered-set 聚合也被计进这个计数。

于是常见计划会偏向 GroupAggregate。好处是「分组顺序」和「组内排序需求」可以在同一条 pathkeys 上讨论：输入如果按 (group_key, agg_order_key) 排好，组是一段连续区间，组内又已经有序，执行器就可以省掉内部排序。代价是这条输入顺序本身可能要靠一次显式 Sort 或索引扫描来提供。

注意这里的因果：不是 GroupAggregate 天生更适合 Ordered Agg，而是 hash 这条路被堵死后，排序这条路成了唯一能同时满足分组与组内顺序的形态。既然一定要谈排序，planner 就顺理成章地想到——能不能让下层路径一次排好，省掉执行器里每个聚合各排各的？这就是 PG16 的预排序优化。

14　PG16 起，planner 会主动去「借」顺序

PostgreSQL 不是一看到 array_agg(x ORDER BY y) 就把排序丢给执行器。commit 1349d279 在 PG16 给 planner 加了这项能力：把聚合的排序需求也写进 group_pathkeys，让下层路径尽量一次提供所需顺序。随后 3226f472 补上 enable_presorted_aggregate 作为回退开关——因为 planner 有时为了预排序会挑一个更贵的全量 Sort，反而不如让 nodeAgg 在组内自己排。

config.sgml 的描述很精确：开启时，planner 尝试生成能为 ORDER BY / DISTINCT 聚合提供预排序输入的计划；关闭时，生成的计划总需要执行器在聚合前做一次隐式排序。默认 on。所以图里两条路径的差别不是结果，而是排序发生在 Sort 节点还是 nodeAgg 内部。这个开关也是 DBA 手里最好用的对照实验：同一条 SQL，开一次、关一次，看 EXPLAIN (ANALYZE, BUFFERS) 谁更快。

不过一个查询可能有好几个 ordered aggregate，各自要不同的排序键，下层路径一次只能给一组顺序。planner 得做选择——这就是 adjust_group_pathkeys_for_groupagg() 的工作。

15　选一组覆盖最多聚合的 pathkeys

这个函数的思路可以概括成「挑一组能服侍最多人的顺序」。它先扫 agginfos，跳过 ordered-set 聚合；带 FILTER 的做保守检查；排序键里有 volatile function 的直接跳过——源码注释说，为了让结果不依赖同查询里其他聚合的排序需求，这类 Aggref 一律自己排。然后把每个聚合的排序需求转成 pathkeys，用 compare_pathkeys 比较强弱，选覆盖数量最多的一组追加到 group_pathkeys，最后把能用上它的 Aggref 标成 aggpresorted = true。

「覆盖」依赖前缀关系。输入按 (group_key, a, b) 排好，可以满足只需要 (group_key, a) 的聚合；反过来，只按 (group_key, a) 排好的输入，满足不了要 (group_key, a, b) 的聚合。右边那条回归测试查询就是这个思想的练兵场：三个 sum 分别按 two、four、four+two 排序，planner 会挑能覆盖较多聚合的那组键。

再往外看一步，这正是 order-aware query optimization 的工程化体现：排序不是只服务最终 ORDER BY，它还能服务 merge join、grouping、distinct、window 和 ordered aggregate。论文里关于 partial ordering 的思路提醒我们，真实计划中常有「已有的部分顺序」，优化器应尽量复用前缀，而不是把排序只当成一个全量 Sort 节点。PostgreSQL 的 incremental sort、pathkeys 和 presorted aggregate 都在往这个方向走。

16　内部排序如何喂给 transition function

这张动画想纠正一个常见误解：执行器不是「边收行边排序边累加」，而是先把这一组、这个聚合的输入元组全部塞进 tuplesort，等组结束时 performsort，再按排好的次序逐行调用 transition function。nodeAgg.c 文件头写得很清楚：If a normal aggregate call specifies DISTINCT or ORDER BY, we sort the input tuples and eliminate duplicates (if required) before performing the above-depicted process。

你可以改输入框里的 ts:v 序列，也可以切 ASC / DESC，然后播放或单步。步骤分四段：先把到达顺序的行逐条推进缓冲区；到 N+1 步执行排序，右侧出现按 ts 排好的输出；接着每步读一行、把 v 追加到 string_agg 的结果里；最后给出完整字符串。注意 separator 是固定的 ' > '。

这也顺带解释了 partial aggregation 为什么难：每个 worker 都得先完成自己那一段「缓冲—排序—transition」，产出的已经是拼好的局部字符串，上层没有全局顺序信息可以重排。接下来把执行器的四种分支摆出来，看看 aggpresorted 到底省掉了哪一段。

17　aggpresorted 决定要不要内部排序

执行初始化时，nodeAgg.c 的 build_pertrans_for_aggref() 会把 Aggref 的排序需求落成 AggStatePerTransData。四个分支按图里顺序判断：ordered-set 聚合直接把 sortlist 置空、aggsortrequired 设 false，通用排序路径不碰它；如果 aggpresorted 为真且没有 DISTINCT，也置空，像普通聚合一样直接 transition，这就是预排序优化真正省掉的东西。

第三分支最值得停下来：只要带 DISTINCT，sortlist 就用 aggdistinct，numDistinctCols 等于排序键个数，aggsortrequired = !aggpresorted。也就是说预排序确实免掉了完整排序，但相邻去重一步也不能省——因为重复值只是变相邻了，并没有自动消失。第四分支是纯 aggorder 且未预排序，那就要老老实实开一个内部 tuplesort。

记住 nodeAgg.h 那句短注释：aggsortrequired 对未 aggpresorted 的 ORDER BY 和 DISTINCT Aggref 为 true。这个布尔值后面会决定表达式解释器走哪条 EEOP 路径。

18　排序结果通过 EEOP 专用步骤进入 transition

这一页把代码路径串起来，回答一个很具体的问题：排好的顺序是怎么送到 transition function 手里的？execExpr.c 的 ExecBuildAggTrans() 先按输入列数选单列还是多列路径；execExprInterp.c 里有 EEOP_AGG_ORDERED_TRANS_DATUM 和 EEOP_AGG_ORDERED_TRANS_TUPLE 两种步骤，负责把输入行放进 tuplesort。nodeAgg.c 的 initialize_aggregate() 决定用 tuplesort_begin_datum 还是 tuplesort_begin_heap，都受 work_mem 约束；到组结束，finalize_aggregates() 调 tuplesort_performsort，再由 process_ordered_aggregate_single / multi 读回排序结果，顺便做去重，最后 advance_transition_function 逐行调用 transfn。

这里有个很漂亮的分层：transition function 完全不知道上游为它排过序。它只是按喂进来的顺序处理输入。Ordered Agg 的语义不是某个函数实现的，而是 Aggref 字段、planner 的 pathkeys、executor 的排序与去重分支共同保证的。

不过预排序的 DISTINCT 还有个额外动作。因为输入已经有序，没有 tuplesort 可以顺带去重了，执行器得自己记住「上一个值是什么」。这一步由 ExecEvalPreOrderedDistinctSingle / Multi 完成，我们用动画看一遍。

19　预排序不等于「什么都不用做」

第二个动画专门讲那个最容易被漏掉的动作。假设下层路径已经按 a 排好序，aggpresorted 为 true，执行器不用开 tuplesort；但 array_agg(DISTINCT a ORDER BY a) 还得把重复值去掉。输入有序意味着重复值必然相邻，于是 PG 加了 ExecEvalPreOrderedDistinctSingle / Multi：缓存上一个值（单列是 lastdatum，多列是 uniqslot），当前值和上一个值相等就跳过，不等才放行并更新缓存。

你可以改整数序列、切 ASC / DESC，播放或单步观察。状态条会逐步说明：先展示下层提供的有序输入，再逐行比较，通过的进入 transition，最后拼出结果数组。多列 DISTINCT 走的是 equalfnMulti，思路一样——比较相邻元组。

所以「预排序省掉的是排序，不是 DISTINCT」。把这句话记住，看执行计划时就不会对「为什么还是慢」感到意外。接下来两个边界：FILTER 和 volatile 表达式，planner 会主动放弃预排序，这不是保守过度，而是为了防止改变错误行为。

20　FILTER 与 volatile：planner 主动放弃预排序

看这条 SQL：array_agg(x ORDER BY 1 / y) FILTER (WHERE y <> 0)。如果由执行器在 Agg 节点内部处理，逻辑上可以先按 FILTER 过滤掉 y = 0 的行，再对剩余行计算 1 / y 排序，不会出错。但 planner 若把排序提前到输入路径，1 / y 就得在 filter 之前求值，除零错误就冒出来了——错误行为被计划形态改变了。

所以 adjust_group_pathkeys_for_groupagg() 对带 FILTER 的聚合做保守检查：参数里只有普通 Var、Const，或者去掉 RelabelType 之后仍然安全的表达式，才允许预排序；更复杂的表达式直接跳过。volatile 是同一类边界：ORDER BY random() 不会被合并到 query-level presort，源码注释要求这类 Aggref 强制自己排序，否则结果会依赖同一个查询里其他聚合的排序需求。回归测试里专门有这类用例。

把这两条记住，看到「明明有索引却没走预排序」时，先别急着怪优化器笨，多半是它在保护语义。原理部分到此闭合，下面进入工程视角：横向对比、代价验证、最小实验、最佳实践和常见坑。

21　把 Ordered Agg 放回算子谱系里

这张表把 Ordered Agg 放回算子谱系里。横着看，五类东西的差别都落在「目标、排序需求、并行能力、内存风险、适合场景」这五行上。最值得琢磨的是「排序需求」这一行：Ordered Agg 可以是每个 Aggref 各要各的排序键，Hash Agg 通常不需要输入排序，Sort/Group Agg 只需要 group key 顺序但可以叠加聚合排序键，Window 要 partition/order key，Ordered-Set Agg 是函数语义自带排序。

底下那句结论请记住：排序需求会改变聚合的物理形态。普通聚合可以把状态留在 hash 表里，行来了就更新；Ordered Agg 必须保证「某个聚合看到的输入序列」正确。hash 表不提供每组内的有序输入，所以那条路走不通，代价就顺着排序、work_mem、并行能力一路传下来。

那收益是什么？收益不是「更快」，而是结果可解释、可重复、符合业务语义。代价也不是抽象的，我们列清楚，并给出验证方法。

22　收益是确定性，代价是排序

收益这一栏，请把它当成产品需求来读，而不是性能指标：用户路径必须按事件时间拼接、审计日志必须按发生顺序聚成 JSON 或数组、标签列表去重并稳定排序以便缓存命中和对比、jsonb_object_agg 遇到重复 key 时排序决定最终保留哪个值。这些场景里，顺序不是展示细节，是结果定义的一部分。

代价这一栏全是排序的衍生品：单个大 group 可能要把整组输入放进排序结构；多个 ordered aggregate 的排序键不兼容时，外部排序只能覆盖一部分，其余还得各自排；DISTINCT 排序之外还要比较相邻值；work_mem 不够就落临时文件；计划形态还可能偏向 GroupAggregate + Sort。多个并发查询叠加时，内存消耗不能按单个 sort 粗估。

最容易犯的错是把 enable_presorted_aggregate 当成「性能开关」一开了之。PG 自己加这个 GUC 就是因为预排序有时反而更贵。正确做法是拿真实数据分布跑 EXPLAIN (ANALYZE, BUFFERS)，重点看 GroupAggregate、Sort Key、Incremental Sort、索引扫描顺序和临时文件，再把开关开一次、关一次做对照。

23　四个最小可验证实验

这四个实验是最小闭环，建议按顺序做。第一，用三行 VALUES 验证「顺序写进聚合内部」：string_agg(v, ' > ' ORDER BY ts) 得到 view > pay > login；同时提醒自己不要写成只依赖排序子查询的形式。第二，验证 DISTINCT 与 ORDER BY 的约束，包括 NULLS LAST 的位置，以及 string_agg(DISTINCT f1::text, ',' ORDER BY f1) 这类表达式不匹配的报错用例。

第三，用 SET enable_presorted_aggregate TO off 加 EXPLAIN，观察计划是否还请求外部排序输入；第四，用三个不同 ORDER BY 的 sum 加 GROUP BY ten，观察 planner 挑哪组排序键，以及含 random() 的排序键不被合并。

这里我必须把话说清楚：原文明确写了没有在本机启动 PostgreSQL 实例执行这些 SQL，语法和预期现象来自官方文档、源码与回归测试。所以这张图里所有「预期」都是可检验的推断，不是我实测出来的统计数字。这一点对技术内容很重要，别把示意数据当成实测结果。

24　先判语义，再算代价

把最佳实践压成一条路径：第一句永远是「顺序是不是业务语义」。如果不是，就别为了结果看起来好看加 ORDER BY，那是白付排序成本。如果是，就把 ORDER BY 写进聚合内部，把顺序变成接口契约的一部分；然后再去验证代价——计划形态、索引、work_mem、DISTINCT、FILTER。注意顺序：不能反过来为了省排序牺牲语义。

右边三个角色各有侧重。架构师要把「顺序是否是结果定义」写进数据接口契约，评估 (group_key, order_key) 组合索引，避免一个查询里堆很多互不兼容的 ordered aggregate。DBA 看 GroupAggregate、Sort Key、Incremental Sort、索引扫描顺序和临时文件，必要时用 GUC 开关做对照，留意 work_mem 和 FILTER 边界。业务开发者只要记住：稳定顺序写进聚合内部，重复 key 明确保留规则，超大数组、超长字符串、超大 JSON 本身就是高风险结果——Ordered Agg 只保证顺序，不替你解决结果过大。

最后那条「拆查询、预聚合、重新设计输出结构」不是失败，而是承认 planner 只能选一组最有利的 pathkeys。多个不兼容排序键硬塞进一个 SELECT，往往不如拆开。

25　索引给出的顺序，能不能直接被用上

看这条常见查询：按 user_id 分组，array_agg(event_id ORDER BY event_time)，还带一个时间范围过滤。如果索引是 (user_id, event_time)，叶子项天然按这两列排好：u1 的 t1、t2、t3 连在一起，接着 u2、u3。于是 pathkeys (user_id, event_time) 同时满足分组顺序和组内排序需求，GroupAggregate 一组一组读，组内已经有序，aggpresorted 可以置 true，执行器免掉内部排序。

但别机械套用。如果过滤先把时间范围裁得很窄，(event_time, ...) 前导的索引可能更划算；而它不满足 (user_id, ...) 这个分组前缀，往往还得补一次 Sort 才能提供分组顺序。原文特别提醒了这一点：索引前导列要由实际 workload 和 EXPLAIN 决定，不是看到 GROUP BY + ORDER BY 就无脑建 (group_key, order_key)。

这里也呼应了前面 pathkeys 的「前缀强弱」：顺序能不能复用，看的是键的顺序是否匹配，而不是列是否出现过。

26　六个反复出现的坑

这六个坑有个共同点：几乎都不是写错语法，而是把实现细节当成了产品语义。第一，依赖子查询排序，简单场景能跑，外层一加 join 就可能被重排。第二，以为 array_agg(DISTINCT x) 自带想要的顺序——去重确实需要比较或排序，但业务要的升序、降序、NULL 位置必须自己写清楚。第三，DISTINCT 与 ORDER BY 的表达式必须匹配，这是解析期硬规则，回归测试里明确有错误用例。

第四，一个查询里堆太多不同排序键，planner 只能选一组最有利的 pathkeys，剩下的聚合照样内部排序；这时候拆查询、预聚合或重设输出结构往往更划算。第五，忽视 volatile 和 FILTER：ORDER BY random() 不并入预排序，复杂排序表达式带 FILTER 会被跳过预排序，两者都是语义保护，不是 bug。第六，把 array_agg(x ORDER BY y) 和 percentile_cont(...) WITHIN GROUP (...) 混为一谈，排查性能时就会看错源码和计划。

27　适合与不适合，以及 Top-N 的边界

适合场景有个共同特征：顺序是结果定义，且规模可控。行为路径、交易流水、审批轨迹按时间聚合；标签权限配置项去重后稳定排序便于比较、缓存、签名；JSON 重复 key 用排序明确谁覆盖谁；小到中等 group，或者已有索引、排序路径能自然提供顺序；报表、审计、导出这类更看重确定性的场景。

不适合场景也有共同特征：排序成本和结果体积都失控。每个 group 极大还同时维护多个不兼容排序；只是为了「看起来有序」；高频在线请求把海量明细聚成巨大数组或 JSON；需要强并行 partial aggregation 的大规模统计。最后一条尤其值得展开：本质上要的是 Top-N，而不是全量有序聚合。

所以底下那条对比要记住：与其 array_agg(x ORDER BY k) 之后再切片，不如先用窗口函数、DISTINCT ON、LATERAL 子查询或 Top-N 索引路径把输入收缩到 10 行，再聚合。前者付了全量排序、大结果传输和客户端解析三份成本，后者让排序规模和结果体积同时下降。

28　把顺序交还给 SQL，把代价交给 planner

最后留五个问题，都是能从这一讲的原理直接推回去的。第一，GROUP BY user_id 加 array_agg(event ORDER BY ts)，(user_id, ts)、(ts, user_id) 还是别的索引更能减少排序？答案要回到 pathkeys 的前缀关系，还要看时间范围过滤。第二，为什么 array_agg(x ORDER BY y) 不能像 sum(x) 那样 partial 之后简单 combine？因为局部有序不等于全局有序。

第三，只要每个用户最近 10 条事件，该全量聚合后切片还是先 Top-N 再聚合？第四，jsonb_object_agg(k, v ORDER BY updated_at) 在重复 key 下保留哪个值，方向反过来会怎样？第五，带 FILTER 的 ordered aggregate，排序表达式提前求值为什么可能改变错误行为？这五个问题分别对应索引、并行、执行规模、结果语义、求值时机。

收束成一句话：顺序写进聚合内部，是把结果定义交还给 SQL；剩下的，是让 planner 用最便宜的方式兑现它。最后说明一下依据——文档 syntax.sgml、func-aggregate.sgml、config.sgml；源码 primnodes.h、parse_agg.c、prepagg.c、planner.c、nodeAgg.c、nodeAgg.h、execExpr.c、execExprInterp.c；回归测试 aggregates.sql。两篇 order-aware optimizer 与 partial ordering 的论文只作思路背景，本地没有全文，所以全文没有引用任何具体实验数字。
