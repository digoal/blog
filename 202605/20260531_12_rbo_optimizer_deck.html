01　优化器之 RBO：规则定义候选，代价选择路径

我们先把这一讲要走的地形摆出来。最上面是用户写的 SQL，它是一句声明：我要哪些数据，不说我怎么去拿。往下一层是解析重写之后的逻辑表达式，这里开始出现大量语义等价的写法。再往下是规则改写、候选路径、代价评估、最优路径，最后才是执行器真正跑起来的 Plan。颜色越深，说明越靠近引擎内部。

这七层不是我为了好看画的。PostgreSQL 的源码就是这么走的：planner() 入口、subquery_planner() 预处理、query_planner() 构造基础关系与连接条件、make_one_rel() 生成路径、add_path() 做竞争、create_plan() 收口。你可以对着 src/backend/optimizer/README 和 planmain.c 一层层核。

今天的主角 RBO，也就是基于规则的优化器，住在第三层。但一开场我就要把边界钉死：PostgreSQL 的主优化器不是纯 RBO。它是用规则生成和裁剪候选路径，再用统计信息和代价模型在这些路径里做选择的 CBO 系统。把这句话记住，后面每一页都在给它补证据。

02　争论的起点：同一条 SQL，没有唯一的正确答案

看左边这条 SQL，三张表 join，三个过滤条件。业务现场一旦计划变慢，会议室里几乎一定会冒出两句话：一句是「有索引就应该先走索引」，另一句是「小表应该先驱动大表」。这两句话不是瞎说，它们来自大量真实调优经验；但它们是经验，不是定理。

为什么不是定理？看右边这五个变量。同一条 SQL，在 1 万行和 10 亿行上，最优计划可能完全不同；冷热数据比例不同、列之间有没有相关性、索引顺序和堆的物理顺序是否一致、数据是不是已经躺在缓存里，都会改写答案。表只有一页的时候，走索引要先读索引页再回堆，反而比顺序扫一遍更贵——PostgreSQL 文档在讲索引使用时就明确提醒过：测试数据太小会误导判断，因为少量行可能只占一个 page。

所以这一讲不打算再给你几条更聪明的口诀。我们要往下一层，看优化器到底用什么机制把「在这些变量下的正确答案」算出来。先说清楚 RBO 的原生问题：关系代数的等价写法太多，需要一个确定性的办法把候选组织起来。

03　RBO 的原生问题：等价写法太多

关系代数有一个基本事实：同一个查询有无穷多种等价写法。最直觉的例子就是谓词下推。filter 放在 join 之后，和把 c.region = CN 尽早推到 customers 上，逻辑上等价；但后者让 join 的输入变小，通常更便宜。所以 RBO 的第一个价值，是用等价变换把 SQL 改成更容易执行的形式。

可这里有个特别要紧的词：通常。规则要成立，得有一串前提。谓词里如果含 volatile 函数，下推会改变函数的求值次数；外连接里 NULL 补全行和过滤位置强相关，挪一下结果就变了；权限屏障和 leakproof 边界更严重，下推可能让优化器读到本来不该暴露的数据；窗口函数也一样，过滤跨过窗口边界会改变结果集。素材里把这四类边界列得很清楚，它们不是理论抬杠，是源码里真的在做的合法性检查。

于是 RBO 的四项价值就立住了：等价变换、合法性排除、启发式减少搜索空间、给扩展系统留规则入口。同时代价也摆在那儿：只看固定优先级不看分布会选错；规则一多，冲突、重复搜索、终止条件都难管；生产上还容易滑向「强制计划」，把统计信息、代价参数、SQL 形态和索引设计的根因盖住。既然规则和选择各有各的活，我们就得把两者的分工画出来。

04　一句话分工：规则定义候选，代价选择路径

这张图是全文的骨架，值得慢一点看。SQL 进来，规则层做等价变换和合法性检查，产出一组候选 Path；统计信息和成本参数从下面喂进代价层，代价层比较 startup cost、total cost、pathkeys 这些维度，最后由 create_plan() 把赢家变成 Plan。注意那两条金的输入线只连到代价层——行数、页数、选择率、随机读成本、缓存假设，这些信息在纯规则系统里根本没有地方安放。

所以纯 RBO 的风险不是「规则写得不够多」，而是错位：它把「生成候选的经验」当成了「选择计划的真理」。有索引就生成 index scan 候选，这没问题；有索引就直接判 index scan 赢，这就跳过了整个代价层。素材里那句总结很准：RBO 先解决哪些计划可以被考虑，CBO 再解决哪个计划最便宜。

这里顺手把一个容易混的说法拆开。有人把 PostgreSQL 叫 RBO，因为它源码里满是规则动作；也有人说它是 CBO，因为最终靠成本选路。两种说法各看到一半。准确的说法是「规则 + 代价」：规则负责把候选 Path 生成出来并排除语义非法或明显无意义的候选，costsize.c 估算成本，add_path() 保留有竞争力的路径，最后选 cheapest Path 转成 Plan。下一页我们就把规则工具箱摊开。

05　规则工具箱：七类常见改写

把工具箱摊开，一共有七类常见动作。选择下推和投影下推负责把过滤和列裁剪往前挪；常量折叠把 x = 1 + 2 变成 x = 3，让条件有机会被索引识别；子查询拉平把一部分 subquery 变成 join，等于给后面的连接顺序搜索开门；join 重排利用内连接的交换律和结合律换顺序；访问路径规则看到可用索引就生成 index scan 候选；物理算子规则把一次等值连接展开成 hash join、merge join、nested loop 等多种实现。

请特别看第 06 和第 07 条的措辞：生成候选、进入竞争。这两条最容易被误读成「有索引就走索引」「能 hash 就 hash」。在 PostgreSQL 里，生成只是让这条路径有资格参加比价，跟谁赢没有必然关系。整个工具箱的共同点在右下角：它们都只改变候选空间的形状。

这也解释了扩展系统为什么喜欢规则入口——FDW、自定义索引访问方法、planner support function，都可以把自己能提供的路径放进同一个候选池，后面统一由代价模型裁决。不过日常讨论里，大家把「规则改写」和「按固定优先级选计划」混着说，结果吵不到一起。下一页把这四个概念摆到一张表上。

06　四个概念，别再混着说

吵架往往是因为词没对齐。第一列「规则改写」，是保持语义等价地改表达式，风险是边界判断错会改结果；第二列「规则选计划」，是按固定优先级直接拍板物理计划，它通常不看统计，所以最容易误选；第三列「代价优化」，是先枚举候选再比成本，强依赖统计和成本参数；第四列 hint 和 enable 开关，是人为禁止或鼓励某类计划，本质是绕过统计。

把 PostgreSQL 放进这张表，它落在第三列，但大量借用了第一列的机制，同时给用户留了第四列做诊断。这就是为什么会有人叫它 RBO、有人叫它 CBO——两边都只看到了一半。素材里那句判断我完全同意：规则负责把候选 Path 生成出来并排除语义非法或明显无意义的候选，costsize.c 估算成本，add_path() 保留有竞争力的路径，最后选 cheapest Path 转成 Plan。

还有一层现实风险值得说：对生产调优来说，RBO 思维容易滑向「强制计划」。一旦习惯了用开关压出想要的形状，就没人再去查统计信息是不是过期、代价参数是不是还符合现在的 SSD、SQL 是不是把谓词写成了不可识别的形态。根因被盖住了，换个版本或换批数据就复发。好，概念清楚了，我们进源码看主链路。

07　主链路：planner() 一路走到 create_plan()

看这条链路。planner() 是总入口，subquery_planner() 做子查询和条件预处理，grouping_planner() 处理聚合、排序、DISTINCT、LIMIT 这些上层结构，query_planner() 处理基础扫描和 join，make_one_rel() 里再分出扫描路径和连接路径，最后由 add_path() 竞争、create_plan() 收口。素材里给了一条完整的调用栈，从 planner() 一直列到 add_paths_to_joinrel()，都在 README 和 planmain.c 里能对上。

关键在中间这三块：每个 base rel 会生成 seq scan、index scan、bitmap scan 等候选；joinrel 会通过动态规划或 GEQO 生成多条 join Path；上层还有排序、聚合、并行的 Path。它们都进同一个池子。所以「遇到索引就直接用索引」这个说法在源码层面就不成立——索引只是让 index scan 这条候选有资格出生，出生之后还要和顺序扫描比价。

下排三个绿色块是收口：add_path() 按 cost、pathkeys、参数化、并行安全保留非支配路径，cheapest Path 胜出，create_plan() 转成 Plan。注意「非支配」这三个字，它意味着留下的可能不止一条——startup cost 低的那条对 LIMIT 有价值，输出有序的那条能省掉上层 sort。带着这个印象，我们钻进 query_planner() 看规则动作。

08　规则真正做的事：改变搜索空间

query_planner() 里有一串名字很长的函数，看着都不像传统意义的「优化规则」，但它们的共同点特别清楚：不是宣判最终计划，而是把表达式整理成更适合枚举和估价的状态。deconstruct_jointree() 拆连接树、收集限制和连接条件；等价类建好之后，reconsider_outer_join_clauses() 重新考虑外连接条件，generate_base_implied_equalities() 推出更多可用于基础关系的限制。

再看剪枝的那一半。remove_useless_joins() 和 remove_useless_self_joins() 能让一个关系直接从搜索空间消失；add_other_rels_to_query() 展开 appendrel 之后做分区裁剪，让某些分区根本不进入扫描候选；reduce_unique_semijoins() 把部分 semijoin 降成普通 inner join；extract_restriction_or_clauses() 从 join 的 OR 条件里提取出单表限制。素材把这些动作归纳成三类空间变化，就是图上那条绿带：关系消失、分区不进场、条件变多。

为什么说这是最健康的位置？因为效果是可验证的：分区少一个，后面的扫描候选就少一批；等价类多推出一条等式，索引和 merge join 就多一个可用条件；join removal 生效，整个 join 层就少一层组合。规则在这里做的是确定性的空间整理，代价模型随后在这个空间里比价。两者分工干净，谁也没越界。下一步看 join 顺序。

09　join 顺序：按层枚举，不是简单左深树

PostgreSQL 的 optimizer README 说得很明确：非 GEQO 的标准 planner 用动态规划生成 joinrel，先考虑二表 join，再三表，逐层直到包含所有表；它会考虑 left-handed、right-handed 和 bushy plans，不是只长一棵左深树。图上四层就是这个过程的骨架。

但枚举不是无节制的。join_search_one_level() 优先考虑存在 join clause 或 join-order restriction 的关系组合；没有连接条件时才生成笛卡尔积候选；bushy join 只在有相关连接条件或顺序约束时才考虑，否则搜索空间会炸。图里那个陶橙的 {A,D} 就是被裁掉的典型：两表之间没有连接条件，不值得为它开一层组合。素材归纳得很准——规则负责「能不能生成」和「是否值得生成」，不是固定指定最终顺序。

还有个容易被忽略的细节：同一组关系 {A,B,C} 可以由不同 join 顺序生成，最后落到同一个 joinrel 上；不同生成方式会向这个 joinrel 添加不同的 Path，可能一条是 nested loop、一条是 hash join，pathkeys 也不同。它们不互相覆盖，而是全部交给 add_path() 竞争。所以到第四层收口时，赢家不是「规则指定的顺序」，而是「在这个 joinrel 上仍有价值的路径」。

10　合法性规则：语义边界不能拿来换性能

前一层讲的是「能生成哪些组合」，这一层讲的是「哪些组合根本不合法」。内连接大多数时候可交换、可结合，所以重排空间大；但外连接不一样，NULL 补全行和过滤条件的位置强相关，把 WHERE 里的右表条件下推，可能直接把外连接退化成内连接。半连接、反连接也一样，EXISTS 和 NOT EXISTS 有自己的语义，不能当普通 join 处理。

LATERAL 是另一种约束：右侧子查询引用了左侧的列，求值时天然有先后依赖，顺序被钉住。volatile 函数更麻烦，每次求值结果都可能不同，谓词一挪动求值次数就变，结果跟着变。leakproof 和权限屏障属于安全边界——优化器不能为了快就把谓词推到不该读的数据上，这在第 3 页讲下推边界时已经出现过一次。窗口函数则是分区边界问题，过滤跨过窗口会改变结果集。

所以请记住这个次序：规则先守住结果正确性，代价模型再在合法候选里挑便宜的。顺序不能颠倒。素材里「坑 3」说的就是这个——把所有 join 都当普通内连接，是调优里最隐蔽也最危险的一类错误。好，现在合法候选都进池了，add_path() 到底用什么标准决定谁留下？

11　开关不是禁令：add_path() 的七个比较维度

pathnode.c 里 add_path() 的注释很关键：一条 Path 值不值得留，不只看 total_cost。它还看 startup_cost，这对 LIMIT、EXISTS、cursor 特别重要；看 pathkeys，输出已经有序就能省掉上层 sort；看 parameterization，nested loop 内侧的索引扫描常依赖外层参数；还看 rows、parallel_safe，以及 disabled_nodes。左边这七条，就是「非支配」三个字的具体含义。

右边是这一讲里我想特别校正的一处细节，也是实证性最强的一处。素材写的是「关闭某类计划更像加了强烈惩罚」，这在 PG 17 及以前准确：源码给被禁用的路径加一个 disable_cost = 1e10 的固定惩罚，社区里可复现的例子是，在没有索引的表上 SET enable_seqscan = off，EXPLAIN 依然显示 Seq Scan，成本变成 10000000000.00 起。问题是分析查询本身的代价现在也可能超过一百亿，固定惩罚就不再决定性，还会悄悄扭曲 join 排序。

PG 18 起改成了 disabled_nodes：不再加巨额成本，而是给每条路径记一个「被禁用节点数」，先选禁用节点最少的，节点数相同再比 cost；EXPLAIN 会在被迫使用的节点上标 Disabled: true。这比旧方案干净得多。但两代的共同结论一致——PostgreSQL 文档说得很清楚，enable_seqscan 只是 discourages 顺序扫描；如果没有其他合法方法，仍然会用顺序扫描。所以开关是诊断工具，不是禁令。

12　代价模型：规则无处安放的信息

看左边这组参数，都是 PostgreSQL 官方配置里能查到的：seq_page_cost 默认 1.0，是整套成本的标定基准；random_page_cost 默认 4.0，反映的是机械盘时代随机读比顺序读贵；再往下是 cpu_tuple_cost 0.01、cpu_index_tuple_cost 0.005、cpu_operator_cost 0.0025，还有并行启动和 tuple 传输成本，以及 effective_cache_size 对缓存规模的粗估。这些数字不是装饰，它们直接乘进每一条路径的估价。

右边是两条主要 cost 的差异。cost_seqscan() 很朴素：表页数算顺序 IO，tuple 数乘 qual 成本算 CPU。cost_index() 复杂得多，它要调用索引访问方法自己的 amcostestimate，拿到 index 成本、选择率、索引顺序和 heap 顺序的相关性，再估算 heap page fetch；如果是 index-only scan，还要根据 visibility map 的 all-visible 比例减少回堆次数。素材里这段写得非常实，因为这就是「规则说有索引通常好」和「代价说这次不一定」之间的全部信息差。

底部那五个问题是纯 RBO 回答不了的：表只有一页，走索引会不会反而慢？返回 30% 的行，随机 heap fetch 是不是比顺序扫更贵？索引与堆物理顺序高度相关时，IO 是不是接近顺序读？数据大部分已缓存，random_page_cost 是不是该下调？LIMIT 10 的时候，低 startup cost 是不是比低 total cost 更重要？如果只有规则，这些量根本没有地方安放。所以 RBO 的合理边界是定义候选与合法性，不是替代代价模型。

13　演示：同一个「有索引」的判断，winner 会翻转

这一页我们把前面的道理做成可以拨的东西。先说清楚边界：这是一个教学示意模型，不是 PostgreSQL 的实测输出，也不是源码里的精确公式。左边顺序扫描按「全表页数乘 1.0 加全行 CPU」估，索引扫描按「索引页加命中行数乘随机页成本，再按缓存命中率打折」估。PostgreSQL 真实的 cost_index() 用 amcostestimate 和 Mackert–Lohman 页抓取估算，还要考虑索引与堆的相关性、visibility map，比这复杂得多。素材作者明确说过没有在本地启动实例，所以不提供伪造的 EXPLAIN 输出，这个克制我完全保留。

但定性结论是稳的，而且正是这一讲的核心。你可以点播放，让选择率从 0.1% 一路扫到 30%，看两条成本条谁短谁长；也可以单步走，或者自己改表页数、random_page_cost 和缓存命中率。选择率很低时，索引只需要回堆很少几行，通常赢；返回比例升高到一定程度，随机 heap fetch 累积起来就比顺序扫全表更贵，winner 翻转。金色虚线标的就是这个临界选择率。

更值得玩的是把 random_page_cost 从 4.0 调到 1.1，或者把缓存命中率拉高——临界点会明显右移，也就是索引能赢的范围变大。这正是官方文档给 SSD 环境的调参建议背后的机制，也解释了两件事：第一，为什么「有索引就该走索引」不是定理；第二，为什么修代价参数比写死一条规则更接近根因。注意，模型里的任何数字都只是公式输出，不能当成真实统计数字引用。

14　GEQO：启发式搜索，不是 RBO 回潮

join 的表一多，穷举动态规划本身就变贵了。PostgreSQL 的应对是 GEQO，Genetic Query Optimizer，官方文档说它用启发式搜索降低复杂查询的规划时间，代价是有时得到不如穷举的计划。默认 geqo_threshold 是 12，也就是 FROM 项达到这个量级时可能启用；FULL OUTER JOIN 只算一个 FROM 项，这类细节文档里也写了。

源码里 geqo() 维护种群、做选择和重组，用 geqo_eval() 评估一个 join tour 的成本；gimme_tree() 按 tour 构造 join clump，但仍然要遵守 join 合法性和 desirability；最终 fitness 取 cheapest total path 的 cost。请特别注意这两个绿框——它们说明 GEQO 也不是纯 RBO，它只是把搜索策略从「穷举动态规划」换成「启发式抽样」，每个候选仍要走一遍路径生成和代价评估。

这也解释了一个常见误判：看到「启发式」就以为规则又回来拍板了。没有。启发式决定的是「去哪些地方找」，不是「找到之后谁赢」。geqo_effort 默认 5，可以在规划时间和计划质量之间调；geqo_seed 能换一组搜索路径，社区里也确实有人用它碰运气找更好的计划。但这些都是搜索控制，不是替代成本模型。把视角再抬高一层，看看别的优化器怎么组织这件事。

15　四种组织方式，一张表看清

这张表把四种组织方式摆平了。纯 RBO 靠固定优先级快速决策，规划开销最低、简单场景稳定，但复杂场景容易误判；PostgreSQL 是规则生成候选加代价选择 Path，强依赖 pg_statistic 和成本参数，用动态规划、GEQO、join 限制和 path pruning 管住搜索空间；Cascades / Volcano 用 memo group 管理逻辑等价表达式和物理实现，扩展性强但工程复杂；Calcite 把优化规则显式暴露成 RelOptRule，HepPlanner 偏规则批处理，VolcanoPlanner 仍可做成本驱动搜索。

这里有两个常被说错的地方值得点出来。第一，把 Calcite 简化成「纯 RBO」是不准确的，它只是把规则显式暴露出来，VolcanoPlanner 照样结合成本。第二，Cascades 的核心贡献不是「规则越多越好」，而是把逻辑等价表达式、物理实现、规则应用和成本搜索组织成可扩展框架——没有 memo 或路径竞争机制，规则越多越容易爆炸，搜索控制和终止条件才是难点。

还有一个判断我挺认同：PostgreSQL 没有采用 Cascades memo 作为主优化器的组织形式，但它有自己的 RelOptInfo / Path 动态规划结构，目标同样是管理候选空间并比较代价。换句话说，从 System R 往后，主流优化器都绕不开成本模型，差别在于「候选空间怎么组织、规则怎么插进去」。谱系清楚了，我们回到工程现场，看 RBO 思想的收益和代价具体落在哪。

16　效果：规则有效，但不体现在替代统计

把收益摊开，五项都跟「候选」有关，没有一项跟「替统计做决定」有关。预处理规则能减少后续规划对象，join removal、分区裁剪、约束排除都让搜索空间直接变小；谓词和等价类推导让索引、merge join、partition pruning 有机会出现；join 合法性规则守住语义；启发式避免无连接 bushy join 把搜索炸开；enable_* 则是给 DBA 一件很实用的诊断工具，用来区分「候选根本没生成」和「生成了但成本不划算」——这两个问题的修法完全不同。

代价这一栏更值得警惕。规则判断本身要花规划 CPU，多表 join、分区多、OR 条件多、等价类多的时候尤其明显；过强的开关会让优化器错过真正更优的计划；统计信息错了，CBO 会在错误输入上做出一个看起来很合理、实际很糟的选择；还有一类最容易被忽略——SQL 自己写得让谓词不可下推、索引条件不可识别，那规则层是没法凭空变出好候选的，这不是优化器笨，是它拿不到可用的模式。

PostgreSQL 文档在索引调优上给的顺序特别务实：先 ANALYZE，用真实数据实验；数据很小时顺序扫描可能自然更优；如果强制关闭某类计划之后新计划确实更快，要继续判断是成本参数问题还是选择率统计问题，而不是把开关当最终方案。这句话其实就是下一页诊断闭环的源头。

17　诊断闭环：先修输入，再修选择

计划一慢，很多人的第一反应是翻开关。这个闭环想纠正的就是这个顺序。第一步永远是看事实：EXPLAIN (ANALYZE, BUFFERS)，把估算行数和实际行数摆在一起，差几个数量级就说明输入已经错了。第二步修统计信息，ANALYZE、扩展统计，先把选择率修准；第三步才校准代价参数，让 seq_page_cost、random_page_cost 反映真实的存储和缓存；第四步改 SQL 形态和索引契约，让好候选有机会被生成。

第五步才是开关，而且限定 SET LOCAL 做对照实验：用 BEGIN / SET LOCAL / EXPLAIN / ROLLBACK 包起来，不污染连接池会话。enable_hashjoin = off、enable_nestloop = off 能告诉你「另一个候选是否存在」；join_collapse_limit = 1 能告诉优化器尊重显式 JOIN 顺序，文档明确说高级用户可以临时这么用。但它们都是探针，不是业务语义的一部分。最后一步回归验证，用真实数据和典型 SQL 看 p95 与计划稳定性。

把顺序反过来会发生什么？你会在错误的统计上挑出一个「看起来更快」的计划，然后把它固化成 hint，等数据分布一变就反噬。素材里那句提醒很到位：根因通常在统计、代价、SQL 形态或索引契约，规则能帮你控制搜索空间，不该替你背这个锅。那这套实验到底怎么设计才可信？下一页给一套可复现的方案。

18　一套可复现的实验，和一条诚实的边界

这一页我想特别强调「不编造」这件事。素材作者写得很坦白：本文未在本地启动 PostgreSQL 实例，所以不提供伪造的 EXPLAIN 输出。这个克制在技术内容里很值钱，因为一条编出来的 cost 数字会让人误以为它是实测结论。所以这一页只给可复现的设计：demo_customers 十万行、demo_orders 一百万行，两个索引分别建在 (customer_id, created_at) 和 region 上，ANALYZE 两张表，region 与 level 之间有人为的相关性，正好用来演示扩展统计。

中间五组对照：先跑基础的 EXPLAIN (ANALYZE, BUFFERS, VERBOSE)，再用 BEGIN / SET LOCAL / ROLLBACK 分别关掉 hashjoin、关掉 nestloop、把 join_collapse_limit 设成 1，最后建 CREATE STATISTICS (dependencies, mcv) ON region, level 再 ANALYZE，看组合条件的选择率估算有没有改善。右边三个观察点最值得盯：估算行数和实际行数差几个数量级没有、join 方法落在哪、过滤条件到底是 Index Cond 还是只在 Filter 里执行。

这里再补一层判断：如果关掉 hashjoin 之后计划变快了，结论不是「以后都关掉 hashjoin」，而是「代价模型可能把 hash join 估便宜了，或者行数估错了」。要继续查统计、成本参数、索引契约。同理，join_collapse_limit = 1 能让显式 JOIN 顺序被尊重，但它是诊断手段；长期方案应该回到统计是否准确、索引是否匹配谓词和连接键、SQL 有没有表达正确的过滤条件。实验之外，日常最容易踩的坑有六个。

19　六个坑，其实是同一个坑的六种长相

六个坑看起来各说各的，其实根因是一个：把「计划形状」当结论，不去检查「估算输入」。坑 1 和坑 2 是一对，都源于把索引或开关当成目的；坑 3 是语义边界，外连接、半连接、反连接、LATERAL、volatile 函数、leakproof 都会限制重排，不能全当普通内连接；坑 4 针对 Cascades 和 Calcite，规则多不等于强，难的是搜索控制、终止和成本剪枝。

坑 5 特别常见：打开 EXPLAIN 看见 Hash Join 或 Nested Loop 就开始下判断。可节点名字本身不说明对错，要看输入行数估算准不准、内外表选得合不合理、有没有重复扫描大表、有没有不必要的排序或临时文件。坑 6 则把责任还给 SQL：函数包列、隐式类型转换、复杂 OR、不可下推的 CTE 边界、表达式和索引不匹配，都会让好候选根本生不出来。这时候不是优化器太笨，是规则层拿不到可用模式。

每一格下面我都给了对应的正确动作，但它们可以合并成一句：先修输入，再看形状。这也是为什么前面要花那么多页讲统计信息、代价参数和搜索空间——不把这一层讲透，最佳实践就只剩一堆零散口诀。接下来按三个角色把动作整理一遍。

20　三类角色，一条共同原则

把动作按角色分一下，会好记很多。架构师管的是「可识别性」：表模型设计时要让常用谓词、连接键、排序键能被优化器认出来；高相关列、组合过滤列、倾斜列要预留扩展统计策略；分区键得和典型查询的过滤条件一致，否则规则层压根没法裁剪；跨库、FDW、湖仓外表还要理解远端下推的能力边界——下推失败的时候，本地端可能要承担巨大数据搬运。

DBA 的顺序是「先修输入，再修选择」：先看 EXPLAIN (ANALYZE, BUFFERS) 比估算与实际；保证 autovacuum 和 autoanalyze 正常，批量导入后主动 ANALYZE；对倾斜列调高 statistics target 而不是全库盲目调高，对明显相关的列建 extended statistics；enable_* 一定用 SET LOCAL 做实验，别污染连接池会话；真的遇到多表 join 规划时间过长，再评估 geqo_threshold、join_collapse_limit、SQL 拆分和物化边界。还有一条容易被忽略：调 random_page_cost 之前先确认存储、缓存和工作负载，别用一条 SQL 去校准全局参数。

开发者这边就四件事：连接条件写清楚，别把 join key 藏进不可索引的表达式；别在过滤列上随便包函数，date(created_at) = ... 可能让普通索引失效，范围条件通常更友好；外连接之后在 WHERE 里过滤右表列要小心，需要稳定顺序就明确写 ORDER BY；分页、TOP-N、EXISTS 要关注 startup cost。最要紧的是别在应用代码里长期写优化器开关——它们不是业务语义的一部分。三个角色共用一条原则：给准确输入、给可识别谓词、给可生成候选，然后相信代价比较。

21　边界：哪些事归规则，哪些事归代价

左边这五件事，都适合用 RBO 的思维去想：理解谓词下推、投影下推、join removal、分区裁剪、子查询拉平这些机制；设计数据库扩展、FDW、索引访问方法和 planner support function；调试「为什么某个候选计划没有出现」；控制大 join 的搜索空间；教学里解释逻辑等价和物理实现的分层。共同点是它们都在回答「候选空间长什么样」，跟具体数据分布关系不大。

右边这六件事就不适合了：大表和倾斜数据上的访问路径选择、多列相关性明显的查询、缓存命中率和存储介质差异很大的系统、OLTP 与 OLAP 混合负载、版本升级后希望计划长期不变的场景，以及最典型的一条——用固定规则替代 ANALYZE、扩展统计、索引设计和 SQL 改写。这些全都依赖数据分布和成本，规则给不出稳定答案。

所以判断标准其实很简洁，写在底下那条金带里：这件事依赖「语义等价与候选组织」，还是依赖「数据分布与成本」？前者用规则，后者交给统计与代价。这条标准比任何口诀都好用，因为它能推。好，最后回到封面的地层剖面，把这一讲收成一句话。

22　把顺序交还给规则，把选择交还给代价

回到最开始那张地层剖面。从上往下：SQL 文本、逻辑表达式、规则改写、候选 Path、代价评估、最优 Path、执行 Plan。七层走完，主命题就一句话——规则定义候选，代价选择路径。现代优化器不是 RBO 或 CBO 二选一，而是把两者放在不同层：规则先划出可考虑的合法候选，代价模型再在候选里比成本。

留五个问题，都能从这一讲的原理直接推回自己的 workload。第一，测试库走 index scan、生产走 seq scan，你会先比哪些统计信息和成本参数？第二，join_collapse_limit = 1 能让 PostgreSQL 尊重显式 JOIN 顺序，它适合什么诊断场景，为什么不适合应用默认？第三，十五表 join 时 GEQO 可能规划更快但计划更差，怎么权衡规划时间和执行时间？第四，要给 PostgreSQL 扩展一个新索引访问方法，应该提供哪些信息，CBO 才能正确比较它和普通扫描？第五，Calcite 的 HepPlanner 和 VolcanoPlanner 分别适合哪类任务，和 RelOptInfo / Path 的思路有什么共同点？

最后交代依据与边界。这一讲主要依据 PostgreSQL 本地源码与官方文档：optimizer/README、planner.c、planmain.c、allpaths.c、joinrels.c、costsize.c、pathnode.c、geqo 相关文件，文档里的 config、indices、perform、planstats、geqo 各章；DeepWiki 对 postgres/postgres 的说明用于交叉核对模块关系。素材列出的几篇论文只作优化器谱系背景，本地没有全文，所以全篇没有引用其中任何实验数字；DEMO 页也没有本地实例，不含实测 EXPLAIN 输出。能核的我都核了，核不了的就明确留白——这大概也算一种工程上的诚实。谢谢。
