01　优化器之 CBO

这一讲只谈一件事：CBO，也就是 cost-based optimization，基于代价的优化。先把结论摆在这儿——它不是某个函数，也不是一条「有索引就走索引」的开关，而是一整套把候选执行方法放到同一把尺子上比较的流水线。你现在看到的七层剖面，就是这条流水线的地层：越往下越贴近执行器，越往上越贴近人写的 SQL。

为什么要用地层来画？因为 CBO 的可靠性是从下往上被托住的。最底下的执行 Plan 长什么样，取决于倒数第二层的搜索有没有留下好路径；搜索比较用的 cost，取决于第四、第五层的基数估计和代价折算准不准；而估计所依赖的统计信息，又是 ANALYZE 从真实数据里采样来的。任何一层松了，上面那句「我选了最便宜的计划」就只是模型里的最便宜，不是现实里的最快。

素材作者给了一个很克制的边界：这一轮没有启动 PostgreSQL 实例，不提供伪造的 benchmark 数字，示例 SQL 是可执行实验但不给实际输出。这个克制我会完整保留——后面凡是需要数字的地方，要么来自 PostgreSQL 官方文档的公开例子并标明出处，要么明确标注为教学示意模型。好，我们先从最上面那层开始：一条 SQL 到底打开了多少扇门。

02　一条 SQL，一个巨大的选择空间

看这条三表查询：orders 连 customers，再连 order_items，三个 WHERE 条件分别落在 region、created_at 和 sku 上。人读它是一句话，优化器读它是一棵要展开的树。第一，谁先过滤？三个入口的选择率可能完全不同。第二，每张表怎么扫？顺序扫描、索引扫描、index only、bitmap heap、并行顺序扫描，都是候选。第三，连接顺序，先连订单和用户，还是先连订单和明细。第四，每个连接点再选 Nested Loop、Hash Join 还是 Merge Join。第五，输出顺序能不能顺带满足 ORDER BY，省掉一次 Sort；要不要开并行。第六，参数化路径、prepared statement 的 generic plan、LIMIT 带来的 startup cost 偏好。

这六类决策是相乘的，不是相加的。表数一多，组合数增长得非常快，所以优化器不可能真的把每个计划都跑一遍再挑。它必须先生成一批候选，再用估计值筛。这里就有两个极端：如果优化器只按你写 SQL 的顺序执行，那么 SQL 的写法本身会变成性能的一部分，换个 JOIN 顺序就变慢；如果只按固定规则执行，比如「有索引就考虑索引」，那数据分布一变就会误判。素材里那句概括很准：CBO 解决的是「正确计划很多，但成本相差几个数量级」的问题。

所以我们得先看清固定规则到底在哪里失灵。下一页只做一个对照：同一条「能用索引就考虑索引」的规则，在 0.01% 和 80% 两种选择率下，会给出完全相反的正确结论。

03　固定规则在真实分布前会翻车

把「能用索引就考虑索引」这条规则放进两个场景。左边选择率 0.01%，一百万行里只命中一百行左右：索引页要读，回表也就那么几行，随机 IO 累积起来几乎可以忽略，索引扫描便宜得多，规则是对的。右边选择率 80%，命中大部分行：索引页的成本照付，回表要按索引顺序去堆里抓几十万行，随机 page fetch 累积起来可能接近甚至超过把整张表顺序读一遍，这时候顺序扫描反而更便宜，规则就错了。

注意这里没有谁「写错」了规则。规则本身是个启发式，它在平均情况下有用，但它手上没有三个关键信息：命中多少行、随机读比顺序读贵多少、数据有多少已经在缓存里。缺了这些量，它就没法比较。素材里那句「选择率 0.01% 的索引扫描很香，选择率 80% 的索引回表可能比顺序扫描还差」，说的就是这件事。

所以 CBO 的出发点不是「更偏爱索引」，也不是「规则越多越好」，而是把可行计划放到同一把代价尺子上比较。可这把尺子要怎么造？下一页把它拆成四步，并且把这笔交易的账单一起摊开——因为 CBO 从来不是免费午餐。

04　CBO 是四步流水线，也是一笔交易

CBO 把「选计划」这件事转成四步。第一，生成候选路径，为每张基表、每组连接关系构造 Path；第二，估算每条路径输出多少行，这一步吃的是统计信息；第三，把 IO、CPU、排序、哈希、并行通信这些不同性质的开销，折算成统一的 cost；第四，选预计代价最低的那条，交给 create_plan() 变成执行器能跑的 Plan。看起来简单，但真正的工程难点全在前三步：候选有没有覆盖好计划、rows 估得准不准、cost 贴不贴近这台机器。

底下这两条时间账是本讲最容易被跳过的一句实话。CBO 不是免费午餐：它要在执行之前多花规划时间、多占内存、多维护一套复杂模型，换的是执行期少做无用功。这也是为什么「极短、极简单的 SQL」被素材列为 CBO 效果有限的场景——查询本身几毫秒就跑完了，Planning Time 反而成了主要成本。而且模型越复杂，可解释性越差：计划突然变了，你得有能力判断是统计过期、代价常数不匹配，还是搜索空间被裁掉了。

认清这笔交易之后，我们就能心平气和地钻进工程实现了。下一页先把四步展开成六个阶段，看看每一阶段到底产出什么。

05　拆开看：六个阶段，各司其职

把四步铺开，其实是六段。逻辑重写先把 SQL 变成更容易优化的关系代数结构；候选生成为基表和连接关系各造一族 Path；统计估计用表行数、页数、直方图、MCV、列相关性和扩展统计，算出选择率和行数；代价计算用 seq_page_cost、random_page_cost、cpu_tuple_cost 这些常数，把 IO 与 CPU 折算成 startup cost 和 total cost；搜索与裁剪在 join order、join method、scan method、pathkeys、parameterized path 之间找路，同时丢掉被支配的路径；最后计划生成把胜出的 Path 转成执行器能跑的 Plan。

这张图里有个很要紧的读法：越靠上的阶段越「便宜」，越靠下的阶段越依赖前面的输入。重写和候选生成决定「好计划有没有被生出来」；统计和代价决定「比较用的数是不是真的」；搜索只是把前四段的结论收敛成一个选择。素材里那句提醒我特别认同：CBO 的关键不是最后选 cheapest，而是前面三件事是否靠谱——候选 Path 是否覆盖了好计划、统计信息能否估准 rows、代价模型是否贴近本机负载。任一环节失真，最后的 cheapest 都只是「模型里的 cheapest」。

那这六段里流通的对象长什么样？下一页把 RelOptInfo、Path、PathKey、Selectivity 和两种 cost 摆到一张图上，顺便说清楚一个常被混淆的点：比较发生在 Path 层，不是 Plan 层。

06　五个关键对象：比较发生在 Path 层

先把最容易混淆的一点说清楚：优化器比较的不是 Plan，是 Path。对一个 join relation，比如 {A B C}，优化器只建一个 RelOptInfo，里面挂一份 pathlist；谁用 Nested Loop、谁用 Hash Join、谁带更好的排序，全都是这个 RelOptInfo 下的不同 Path，彼此竞争。add_path() 持续比较和裁剪，最后留下非支配的那些，再选 cheapest 交给 create_plan() 变成执行器用的 Plan。PostgreSQL 的 optimizer/README 把这条主线写得很直白：构建 Path 树，选能生成目标 relation 的 cheapest Path，再转成 Plan。

Path 上挂着四个决定胜负的属性。rows 是估计输出行数；startup_cost 是吐出第一行之前的成本，LIMIT、EXISTS、cursor 这类「可能不用跑完」的场景特别在意它；total_cost 是跑完整的总成本，默认就拿它比；pathkeys 描述输出顺序，如果一条路径天然满足 ORDER BY，就能省掉上层一次 Sort，于是「稍贵一点但有序」的路径可能整体更划算。Selectivity 是谓词通过比例，比如 0.01 就是预计 1% 的行通过，它是算 rows 的原料。

所以别把 CBO 想成「最后排个序」。它从一开始就在组织一个可比较的对象模型：哪些属性可比、哪些路径值得留、哪些可以在放大之前丢掉。这些对象散落在源码的好几个目录里，下一页给一张地图，方便你回头自己顺着读。

07　一张源码地图：入口、路径、估计

这张地图不是让你背文件名，是给你一条自己核对结论的路。左边是入口：planner.c 是优化器外部入口，处理上层结构；planmain.c 里的 query_planner() 负责规划基本的 scan/join 查询；还有一份最值得先读的 optimizer/README，把 Path 树、cheapest Path、动态规划和 GEQO 的关系讲清楚了。中间是路径生成：allpaths.c 生成基表和连接关系的访问路径，joinrels.c 按层构造 join relation，joinpath.c 给某个 joinrel 添加 Nested Loop、Merge Join、Hash Join。

右边是估计与代价：costsize.c 是代价和行数估计的主要实现，clausesel.c 做布尔条件选择率估计，具体操作符、类型和扩展统计信息的估计在 selfuncs.c 与 src/backend/statistics/。素材作者还特意记了一笔：DeepWiki 查询本轮返回错误，没被当成事实来源，重要结论都回到本地源码与官方文档核对。这个态度我很想强调——讲优化器，最怕的就是拿二手结论当一手证据。

顺着这张图，我们沿主入口实际走一遍。下一页是 query_planner() 的七步主线，看完你会明白「建了索引」这件事在源码里究竟排在第几位。

08　query_planner() 的七步主线

query_planner() 的主线有七步，顺序里藏着设计意图。先 add_base_rels_to_query()，为 jointree 里的基表建 RelOptInfo；再 deconstruct_jointree() 分解连接树和谓词；接着生成等价类、外连接约束、外键匹配、OR 条件抽取这些信息；然后 make_one_rel() 进入主规划。到这里都还在「整理问题」，没有开始挑路径。

第五步 set_base_rel_sizes() 估基表的 rows 和 width，第六步 set_base_rel_pathlists() 才生成基表的扫描路径，第七步 make_rel_from_joinlist() 生成整体连接树的路径。为什么要把估行数放在造路径之前？因为 rows 是 Path 的输入属性，不是事后贴上去的标签。先知道「这条路径大概输出多少行」，后面才能算 cost、才能比较、才能决定谁被支配。这也是为什么统计信息一旦错，后面一整串比较都会跟着歪。

现在钻进第六步。很多人有个朴素预期：我建了索引，优化器就该用索引。但 set_plain_rel_pathlist() 的实际顺序会告诉你，索引只是最后才被加入的一组候选。下一页就把这个顺序画出来。

09　建了索引，不代表优化器会用

set_plain_rel_pathlist() 的顺序特别能纠正直觉：先考虑 TID scan，也就是能不能按元组物理位置直接取；然后加 sequential scan，顺序扫描几乎总会在候选池里；如果这张表可以并行，再生成一条 parallel seq scan；最后才调用 create_index_paths()，把索引扫描、index only scan、bitmap 这类路径加进来。换句话说，索引不是默认选项，是后补的候选。

补进来之后，所有 Path 挂在同一个 RelOptInfo 的 pathlist 里平权竞争。它们各自带 rows、startup_cost、total_cost、pathkeys，谁在比较里不被支配谁留下。所以「我建了索引，怎么 EXPLAIN 还是 Seq Scan」这个问题，正确问法不是「优化器是不是没看见索引」，而是「这条索引路径的 total_cost 为什么比顺序扫描高」。答案通常在三个地方：选择率高、回表随机读多、表又大。

这也提前解释了后面要讲的一个常见坑：看到 Seq Scan 就判定优化器错了，是最普遍也最没道理的误判。索引不是目的，少做无用 IO 才是目的。那优化器凭什么判断「无用」？下一页就把这把尺子拆开，顺便把官方文档里那个著名的 445 算一遍。

10　cost 不是毫秒，是一把相对尺子

先破一个最常见的误解：cost 不是毫秒，也不是真实 IO 次数。PostgreSQL 文档写得很清楚，这些 cost 变量是在任意尺度上度量的，只有相对值有意义；把所有 cost 常量同比例放大缩小，计划选择不会变。默认以顺序页读取成本为基准，seq_page_cost = 1.0，random_page_cost = 4.0，cpu_tuple_cost = 0.01。文档还给了一句很诚实的提醒：没有确定理想 cost 常量的好方法，它们更像整个 workload 的平均值，靠少数几次实验就改是很冒险的。

右边这组数字来自官方文档 14.1 的公开例子，可以逐项复算：回归测试表 tenk1 有 345 个磁盘页、10000 行，顺序扫描的估计成本就是 345 乘 1.0，加上 10000 乘 0.01，等于 445，对应 EXPLAIN 里的 cost=0.00..445.00。文档还顺手说明了另一件事：加一个 WHERE 条件之后，扫描仍然要访问全部 10000 行，所以 cost 不降反升，多出来的是检查条件的 CPU 成本。这个例子很值得记，因为它把「估计行数」和「访问成本」这两件事彻底分开了。

底部的简化公式来自素材 3.2：disk_run_cost 是 seq_page_cost 乘页数，cpu_run_cost 是每行 CPU 成本乘行数，再加 startup_cost 与 targetlist_cost 得到 total_cost。注意文档还特别说，cost 不包含把结果转成文本、传给客户端的时间，因为优化器无法靠换计划改变这部分开销。顺序扫描这条公式很干净，可索引扫描要复杂得多——下一页看它到底要吃多少输入。

11　索引路径的估价为什么复杂得多

顺序扫描那条公式很干净，索引扫描不行，因为它要回答「读索引」和「回表」两段完全不同的问题。第一，索引自身的扫描成本由访问方法的 amcostestimate 提供，不同索引类型算法不同。第二，indexSelectivity 决定命中比例。第三，用这个选择率乘表行数，得到预计要回表的 tuple 数。第四，估要访问多少表页面，这里包含缓存影响和 Mackert–Lohman 近似。第五，indexCorrelation 描述索引顺序和堆表物理顺序的相关性——如果两者高度相关，回表就接近顺序读，会便宜很多。

第六，index only scan 可以借 visibility map 判断页面是否 all-visible，从而减少 heap page fetch。第七，并行路径还要处理 CPU 分摊。这些量一起折算成 startup_cost 和 total_cost，再跟顺序扫描放在同一单位下比。素材里那句解释特别到位：为什么一些「看起来应该走索引」的 SQL 不走索引？因为选择率高、回表随机读多、表又大时，索引路径的 total_cost 可能高于顺序扫描。

请注意，这七项里没有一项是「有没有索引」这个布尔值。全是连续的量。所以「有索引就该走索引」根本不是定理，它只是某个参数区间里的经验。道理讲完了，不如让它动起来——下一页给你四个可以拨的输入，看 winner 怎么翻转。

12　演示：同一个「有索引」的判断，winner 会翻转

这一页我们把前面的道理做成可以拨的东西。先说清边界：这是教学示意模型，不是 PostgreSQL 的实测输出，也不是源码里的精确公式。左边顺序扫描按「全表页数乘 1.0 加全行 CPU」估，索引扫描按「索引页加命中行数乘随机页成本，再按缓存命中率打折」估。真实的 cost_index() 用 amcostestimate 和 Mackert–Lohman 页抓取估算，还要考虑索引与堆的相关性、visibility map，比这复杂得多。素材作者明确说过没有在本地启动实例，不提供伪造的 EXPLAIN 输出，这个克制我完整保留。

但定性结论是稳的，而且正是这一讲的核心。你可以点播放，让选择率从 0.1% 一路扫到 30%，看两条成本条谁短谁长；也可以单步走，或者自己改表页数、总行数、random_page_cost 和缓存命中率。选择率很低时，索引只需要回堆很少几行，通常赢；返回比例升高到一定程度，随机 heap fetch 累积起来就比顺序扫全表更贵，winner 翻转。金色虚线标的就是这个临界选择率。

更值得玩的是把 random_page_cost 从 4.0 调到 1.1，或者把缓存命中率拉高——临界点会明显右移，也就是索引能赢的范围变大。这正是官方文档给 SSD 环境的调参建议背后的机制：文档明确说降低 random_page_cost 会让系统更倾向索引扫描。这里也顺带说明为什么全局调参要谨慎，因为它改的是所有 SQL 看到的世界。好，赢家是比出来的；可要是拿来比较的 rows 一开始就是错的呢？下一页看 CBO 最脆弱的输入。

13　基数估计：CBO 最脆弱的输入

PostgreSQL 对基表行数的估计，形态上就是「表行数乘条件列表的选择率」，源码位置是 set_baserel_size_estimates()。对连接关系，内连接的核心形态是「外侧行数乘内侧行数，再乘外键选择率和连接选择率」，源码位置是 calc_joinrel_size_estimate()。看着只是两个乘法，但它们是整条链路的放大器：单表误差会进入 join，join 误差又会进入更上层的 join、sort、aggregate、limit。

这里有个容易被忽略的因果方向。很多人一看到慢 SQL 就问「是不是 Hash Join 实现不好」，可素材里那句判断更准：如果表 A 的过滤结果被低估 100 倍，优化器会以为 Nested Loop 的内层只会被访问很少几次，于是挑了一个在真实数据量下非常慢的路径。很多「优化器选错计划」的根因，不是 join 算法写得差，而是 rows 估错了。cost 模型再精细，输入错了，比较出来也只是「模型里的最优」。

误差传播本身不是新话题，Ioannidis 和 Christodoulakis 那篇经典论文的标题干脆就叫《On the Propagation of Errors in the Size of Join Results》。那这条乘法链到底能把偏差放大到什么程度？下一页给你一个可拨的倍数，按阶段推演一遍——同样先声明，那是示意推演，不是实测数据。

14　演示：一个 100 倍低估，怎样爬上连接树

这一页是上一页那两个乘法式的动态版。先说边界：它是示意推演，不是 PostgreSQL 实测，也不是从源码里抄出来的精确传播公式；假设「误差按独立性假设逐层相乘」，正是为了把乘法链的危险性看清楚。你可以把单表低估倍数 k 从 100 改成 10，也可以按阶段单步或播放，看四个阶段依次亮起来。

第一阶段，某张表的 rows 被低估 k 倍。第二阶段，join 把两侧输入行数相乘，在两侧都带偏差的示意假设下，偏差来到 k 的平方量级。第三阶段，更上层的 join、sort、aggregate、limit 继续继承这个偏差，到 k 的三次方量级。k 取 100 时，这串数字是 100、一万、一百万——注意，这不是说真实查询一定差一百万倍，而是说明「一个局部误差」经过逐层相乘以后，能变成完全不在同一个数量级上的判断。第四阶段，优化器拿着这些错误的 rows 去比较 cost，于是可能挑错 join 方法、挑错连接顺序。

这就把前面那句「很多优化器选错计划的根因是 rows 估错」落到了可感知的量级上，也解释了为什么调优顺序永远是先看估算与实际行数的差异，而不是先去调 random_page_cost。那误差的源头到底在哪？下一页回到估计函数本身，你会发现 PostgreSQL 其实并不是「傻乘」——它有几种专门的处理，只是仍然受统计信息质量限制。

15　估计函数并不是「傻乘」

素材里特别推荐读 clauselist_selectivity() 的注释，理由就在这张图上。第一条路径，优先尝试 extended statistics 来捕捉跨列依赖，比如省市区、状态与时间这类强相关列；第二条路径，剩下的条件通常按独立性相乘，这是默认兜底假设；第三条路径，对 x > low AND x < high 这类范围查询，会特殊合并上下界，而不是把两个不等式当成独立事件相乘。所以「PostgreSQL 把选择率简单相乘」这个说法是不准确的。

但边界同样清楚。独立性假设是默认兜底，不是被消灭了；函数依赖统计只作用于「列与常量比较」的简单等值条件和常量 IN 子句，官方文档明确说它不用于列与列比较、不用于列与表达式比较，也不覆盖范围、LIKE 或其他条件类型。而且函数依赖还有个有意思的假设：它认为涉及列的条件是兼容、冗余的，遇到 city = San Francisco AND zip = 90210 这种实际零行的组合，它不会给出零，仍会按冗余处理。

所以结论不是「估计函数很聪明，不用担心」，而是「估计函数有几种专门的处理，但它只能在统计信息提供的范围内工作」。估值准不准，最终取决于传感器有没有采到这份信息。下一页就把优化器的三层统计传感器摊开。

16　统计信息：CBO 的传感器

官方文档把统计信息分成三层。最底层是表级规模：pg_class 里的 relpages 和 reltuples，记录页数和行数，由 VACUUM、ANALYZE 和部分 DDL 更新，出于效率考虑不是实时精确值；文档还说，优化器会拿它和表的当前物理大小做一次缩放，得到更接近的近似。中间层是单列分布：pg_statistic，日常看它的视图 pg_stats，里面有 null fraction、n_distinct、most_common_vals、histogram_bounds。最上层是多列与表达式统计：pg_statistic_ext 和 pg_statistic_ext_data。

关键的一句是：ANALYZE 对大表用随机采样，所以统计信息即使刚刚更新过，也总是近似的。想提高精度可以调 default_statistics_target（默认 100），或者对特定列用 ALTER TABLE ... SET STATISTICS 提高 MCV 与直方图的容量；但文档同时把账单写清楚了——更长的 ANALYZE 时间、更大的统计信息存储、更多的估计开销。这不是「调大就好」的旋钮，是一个精度换成本的选择。

这三层里最容易被误用的是扩展统计：很多人以为它能修复一切估值问题。下一页把它支持的三种类型摆开，并把官方文档写明的那条边界单独标出来。

17　扩展统计能修什么，修不了什么

三种类型分工很清楚。ndistinct 估计多列组合的 distinct 数，主要帮 GROUP BY a,b、DISTINCT 多列这类场景，文档还提醒只在确实用于分组、且分组数误估已经造成坏计划时才建，否则就是白花 ANALYZE 周期。dependencies 捕捉函数依赖，适合省市区、状态与时间这种强相关列，但它只覆盖列与常量比较的简单等值条件和常量 IN 子句。mcv 存的是多列最常见值的真实组合，能判断哪些组合兼容，因此更适合热点组合、数据倾斜，也能覆盖 dependencies 处理不了的范围条件。

然后是这条必须记住的边界，来自官方文档 CREATE STATISTICS 页面的 Notes，原话是：Extended statistics are not currently used by the planner for selectivity estimations made for table joins. 也就是说，扩展统计目前不用于表连接的选择率估计。它能改善单表多条件估计，但不能指望它解决所有 join 基数误差。素材作者专门标了这一点，因为「建了扩展统计，join 还是估错」是特别常见的困惑。

另一个高频坑是流程：CREATE STATISTICS 只是在系统目录里登记「要收集什么」，实际数据得靠 ANALYZE 采集，落在 pg_statistic_ext_data。创建完不 ANALYZE，等于什么都没做。讲到这里，该给一个真凭实据了——官方文档里有个非常干净的例子：估 1 行、实际 100 行，建完依赖统计再 ANALYZE，估计就变成 100 行。

18　实证：估 1 行，实际 100 行

这一页给的是真凭实据，数字全部来自 PostgreSQL 官方文档 69.2.1，不是我编的，也不是本地跑出来的。实验数据很干净：建一张表 t，两列 a 和 b 都取 i 模 100，也就是两列值完全相同，100 个组合均匀分布，共 10000 行，ANALYZE 之后查 a = 1 AND b = 1。单看每一列，选择率都是 1%，估得很准；但两个条件一起出现时，优化器按独立性假设把 1% 乘 1%，得到 0.01%，于是估计 rows = 1，而实际是 100 行——两个数量级的低估。

修复动作只有两步：CREATE STATISTICS stts (dependencies) ON a, b FROM t，然后 ANALYZE t。再跑同一条 EXPLAIN，估计变成 rows = 100，和实际一致。优化器识别出这两列条件其实是冗余的，不该重复乘一次。文档同一节还给了两个补充实验：ndistinct 能把 GROUP BY a,b 的组数估计从 1000 修回 100；mcv 因为存了真实组合，能识别出 a=1 AND b=2 这种根本不存在的组合。

这个例子值得反复咀嚼的地方在于：SQL 没改、索引没加、join 方法没换、cost 参数没动，只补了一份统计信息，估计就对了。它把「先修输入，再修选择」这条调优顺序变成了可验证的事实。好，输入这一侧讲完了，我们抬头看另一侧——表一多，连把候选穷举一遍都会变贵，搜索空间是怎么被管住的。

19　搜索空间：System R 到动态规划

System R 那篇经典论文《Access Path Selection in a Relational Database Management System》奠定了关系数据库优化器的基本套路：为单表选 access path，为 join 枚举连接顺序和连接方法，用代价估计挑低成本计划。PostgreSQL 的 optimizer/README 也明确写，标准优化器用动态规划构造 join tree：先找二元 joinrel，再找三元 joinrel，一直做到包含全部 relation 的 final joinrel。

这套设计有个很聪明的收敛点，也是素材特别强调的：同一个 join relation，比如 {A B C}，只建一个 RelOptInfo；不管它是 (A⋈B)⋈C 还是 A⋈(B⋈C) 构造出来的，都在这个 RelOptInfo 里以不同 Path 竞争。好处是优化器在构造更大的 joinrel 之前，就能对小 joinrel 的路径做裁剪——被支配的路径不会带着一堆子组合继续膨胀。

所以动态规划解决的是「怎么枚举不重复」，但还有两个问题没答：允许枚举哪些树形、以及表多到什么程度就不该再穷举了。下一页把这两道闸门一起画出来。

20　枚举哪些形状，以及什么时候停

PostgreSQL 不只考虑左深树。joinrels.c 里 join_search_one_level() 的注释说得很具体：对某个 level，它先考虑 level-1 的 joinrel 与基表连接，再考虑 bushy plans，也就是 {A B} 连接 {C D} 这种两边都是 joinrel 的组合。所以左深树、right-handed 和 bushy plan 都在视野里，只是不同形状带来的搜索规模不同。

搜索空间不会无限放开，四个参数管着它。join_collapse_limit 默认 8，设为 1 就能阻止显式 JOIN 被展开重排；from_collapse_limit 默认 8，管子查询折叠到上层 FROM 的规模；geqo_threshold 默认 12，FROM 项达到这个数量就改用遗传查询优化；geqo_effort 默认 5，取值范围 1 到 10，用来权衡规划时间与找到好计划的概率，它本身不直接起作用，而是用来推算 pool_size、generations 等默认值。还有 geqo_pool_size、geqo_generations、geqo_seed 可以更细地调。

官方文档对 GEQO 的解释特别务实：对于多表查询，穷举搜索花的时间常常比「执行一个次优计划多花的损失」还大，所以用一个关于查询规模的阈值来管理它。这句话其实是整讲的缩影——优化器不是追求理论最优，是在规划时间、内存和搜索质量之间连续折中。那这个折中最具体的实现在哪？下一页看 add_path()。

21　路径裁剪：谁有资格被留下

add_path() 是理解 PostgreSQL CBO 工程性的关键。它不是把所有候选攒到最后排个序，而是在每个 RelOptInfo 的 pathlist 里持续比较、持续裁剪。总成本更低的路径可能支配旧路径；startup cost 更低的路径在 LIMIT、EXISTS、cursor 这类「很可能不用跑完」的场景里值得单独留着；pathkeys 更好的路径输出已经带目标排序，能帮上层省掉一次 Sort；parameterized path 行数更少，但只能在特定 outer relation 已经可用时使用；parallel-safe 的路径在并行场景下更有价值。

这里没有一条规则说「只留最便宜的」。留的是一组互不支配的路径，因为上层环境会改变它们的相对价值。官方文档 14.1 里那个 LIMIT 的例子正好说明这一点：加了 LIMIT 2 之后，优化器改选了 total cost 更高、但 startup 更低的索引扫描，因为 Limit 节点预计只需取五分之一的行，不用付 bitmap scan 的启动成本。

所以 CBO 的现实形态，从来不是理论上的「枚举所有计划再取最优」，而是在规划时间、内存和搜索质量之间连续折中。把视野再抬高一层：同样要解决「候选空间怎么组织」，Volcano 和 Cascades 走的是另一条路，跟这套手写工程结构到底差在哪？

22　Cascades 的 memo，与 PostgreSQL 的 Path

Volcano 和 Cascades 这两篇论文代表另一条重要脉络：把优化器做成可扩展的搜索框架，用 transformation rule 管逻辑等价变换、implementation rule 管物理实现、memo group 管共享的等价表达式，再用 property、cost bound、promise、rule scheduling 组织搜索。它们的思想影响了很多商业数据库和研究系统，设计目标本来就是「让优化器可以被生成、被扩展」。

PostgreSQL 不是照搬 Cascades memo 架构的优化器。它有自己的 RelOptInfo、Path、pathlist，有动态规划加 GEQO，有 planner hook、join/search hook，还有 FDW、CustomPath 和各访问方法自己的 amcostestimate。相同点在于：两边都把逻辑等价表达、物理实现、代价比较和搜索剪枝分开；差异在于，PostgreSQL 的主优化器更贴近手写工程结构，优先保证在成熟 SQL 引擎里长期稳定地跑，而不是提供一个通用 optimizer generator。

素材里的横向对比表还列了另外两列：System R 风格 CBO，以及 Neo / Bao 这类学习型优化器。前者的贡献是奠定「枚举 + 代价」框架，后者想用运行反馈修正传统模型的盲区。这条更年轻的支线，下一页单独讲它的现实落点。

23　学习型优化器站在 CBO 旁边

素材里对学习型优化器的定位很清醒：核心矛盾没变——计划空间非常大，真实成本不可能提前精确知道，只能用统计和模型近似。Neo 更倾向端到端地学习计划选择；Bao 的思路尤其偏工程，它不推翻底层优化器，而是用学习反馈决定「什么时候给什么 hint」，让系统渐进改善。所以这张图我画成一个环：传统 CBO 出计划，执行收集真实反馈，学习模型消化反馈，再以 hint 或 steering 的方式影响下一轮规划，底层优化器始终保留。

为什么「旁边」比「替代」更现实？因为成熟 CBO 里已经有几十年的语义正确性、路径合法性、扩展机制和失败兜底；完全另起炉灶要重新承担这些成本。素材的横向对比表也把学习型优化器的风险写得很直白：泛化、数据漂移、解释性和失败兜底，加上训练和部署复杂度，所以它更适合重复 workload、能收集反馈、也能容忍学习系统运维成本的场景。

四条脉络到现在齐了：System R 给出「枚举 + 代价」的基本框架，Volcano / Cascades 提高框架可扩展性，PostgreSQL 给出长期演化的工程实现，Neo / Bao 试图用反馈补传统模型的盲区。谱系讲完了，回到工程账本——CBO 到底带来了什么，又收走了什么？

24　CBO 的收益与代价，都很明确

把收益摊开，全是「按数据量级选对动作」：小结果集走索引扫描、Nested Loop，避免全表扫描；大结果集走顺序扫描、Hash Join，避免大量随机回表；有有序路径就利用 pathkeys 省掉 Sort；多表 join 先做高选择率过滤，别把中间结果提前放大；大扫描用并行路径，但只在并行启动和通信成本值得的时候。注意，没有一条收益叫「用上了索引」——索引只是手段，少做无用 IO 才是目的。

代价这一栏更值得每天盯。规划成本随 join 表数上升；统计信息一旦过期或采样覆盖不到尾部数据，rows 立刻歪；全局 random_page_cost 是 workload 平均值，没法同时代表冷数据、热数据、SSD、网络盘和全内存；prepared statement 的 generic plan 可能对某些具体参数很差；极端相关性、复杂表达式、用户自定义类型和函数，默认 selectivity 可能根本不够用。官方文档那句提醒我反复引用：没有确定理想 cost 常量的好方法，靠少数实验就改全局值很冒险。

所以评价效果的正确姿势，不是看「有没有用索引」，而是逐节点比较估计与实际，看差异从哪一层开始。下一页给一份能直接照着做的检查清单，附带一个必须记住的安全提醒。

25　评价计划：六个检查点，一条安全线

这条命令是日常诊断的起点，注意是 ANALYZE 加 BUFFERS 加 VERBOSE，不是光秃秃的 EXPLAIN。只看 EXPLAIN 你只能看到估计，看不到实际行数和 buffer 行为。拿到输出后逐节点过六项：rows 估计和 actual rows 差多少；loops 有没有把内层节点重复执行很多次；Buffers 有没有超预期读放大；Sort 或 Hash 有没有 spill 到磁盘；Join 顺序有没有把大中间结果提前放大；短查询里 Planning Time 占比是不是过高。

loops 这一项我要多说一句，因为它最容易被误读。Nested Loop 内层节点显示 actual rows=1 loops=100000，很多人以为只处理了一行，其实总处理量约是十万次内层执行。素材把它单独列成常见坑，原因就在这：一个低估的行数会让优化器以为内层只跑几次，等真实数据进来，循环次数直接把代价放大几个数量级。

还有一条安全线不能省：官方文档明确说 EXPLAIN ANALYZE 会实际执行 SQL，对 DML 要放在事务里并 ROLLBACK，或者只在测试环境执行。诊断工具本身也是生产操作，别顺手在主键上跑一遍 DELETE 的 ANALYZE。清单要落地，得有可复现的实验——下一页给两组可以直接跑的 SQL 设计，以及一个必须守住的诚实边界。

26　两组可执行实验：只给步骤与观察点

第一组实验专门看相关性。建一张 cbo_demo，一百万行，city_id 和 zip_id 都等于 i/100，也就是两列完全相关；先 ANALYZE 再用 EXPLAIN 看 city_id = 100 AND zip_id = 100；然后 CREATE STATISTICS 指定 dependencies 和 mcv，再 ANALYZE，用同一条查询对比。预期观察是：建统计前优化器可能把两个条件当独立事件相乘，低估结果行数；建完统计并重新采集后，单表多条件估计通常更接近实际。如果再加索引，计划可能从 Seq Scan 变成 Bitmap Heap Scan 或 Index Scan，但这取决于选择率、表大小、缓存和 cost 参数，不能预设。

第二组看 join：建 c、o、i 三张表，规模分别是十万、一百万、三百万行，建五个索引再 ANALYZE，用 EXPLAIN (ANALYZE, BUFFERS, VERBOSE) 跑那条三表查询，观察 join 顺序、join 方法、rows 和 loops。想做对照可以用 BEGIN，SET LOCAL 关掉某类 join 方法，EXPLAIN 之后 ROLLBACK，这样不污染连接池会话。但开关只回答「不用这类路径会怎样」，不是长期优化手段。

这里必须守住素材作者的诚实边界：本轮没有启动 PostgreSQL 实例，所以不提供任何实际 EXPLAIN 输出。图里的数据规模来自示例 SQL 的 generate_series，是建表参数，不是性能统计数字。实验之外，真正能长期改善计划质量的是三类角色的日常动作——下一页按架构师、DBA、业务开发者分开讲。

27　三类角色，同一条修复路径

架构师这一栏，核心词是「可估计性」。强相关列、JSON 深层表达式、隐式类型转换、函数包裹列、过度动态 SQL，都会让估计变难；高频查询里的表达式可以考虑表达式索引或表达式统计。索引要按数据分布设计，不是按谓词字段打勾——WHERE a = ? AND b BETWEEN ? ORDER BY c 和只有 b 的范围条件，根本不是同一个索引问题。还有一条常被浪费的资源：分区、CHECK 约束、外键本身就是优化器信息，分区裁剪、约束排除、外键 join selectivity 都能缩小搜索空间；可你要是不写约束，事实上的正确性优化器是不知道的。

DBA 这一栏，顺序最重要：先看 rows 误差，再调 cost 参数。actual rows 和 rows 差几个数量级时，先处理统计信息、数据倾斜、相关性和表达式统计，别一上来动 random_page_cost。让 ANALYZE 跟上数据变化，批量导入、分区切换、热点表大更新、恢复 dump 之后都要主动分析。调全局 cost 要谨慎，官方文档说没有确定理想值的好方法，建议先用表空间级参数、会话级验证或小范围灰度。多列相关性就建扩展统计，常见候选是省市区、状态与时间、租户与业务类型、枚举组合——创建后必须 ANALYZE。

开发者这一栏最贴身：别把 SQL 写成优化器看不懂的形式，比如 WHERE date(created_at) = ...，改成 created_at >= ... AND created_at < ... 这种范围条件；用 EXPLAIN (ANALYZE, BUFFERS) 验证真实路径；警惕「测试环境快、生产慢」，因为数据量、分布、缓存、参数、统计信息都可能不同。三栏合起来其实是同一件事：让优化器手上的统计世界，尽量贴近真实的数据世界。动作清楚了，还得知道边界——哪些场景 CBO 帮得上，哪些帮不上？

28　CBO 帮得上谁，帮不上谁

左边是主场：多表 join、多索引、多谓词组合的复杂查询；数据分布会变化、固定规则无法长期稳定的系统；OLTP 加报表混合负载，需要在低延迟和吞吐之间动态选计划；以及有成熟统计信息、约束、索引和可观测体系的生产数据库。你会发现这些场景有个共同点——正确计划很多，成本差得很大，而且有足够的信息让模型去分辨。

右边是失灵条件，几乎每一条都指向输入或约束。极短极简单的 SQL，规划成本可能比执行成本还明显；统计信息严重缺失或长期过期，传感器就失效了；谓词高度依赖 UDF、外部服务、不可估函数，默认 selectivity 没有依据；数据分布剧烈漂移而 ANALYZE 跟不上，统计世界就滞后于数据世界；还有一类是需求层面的冲突——强实时系统要求计划完全可预测，不接受成本模型带来的计划波动，这不是调参能解决的。

所以 CBO 的能力上限由三件事共同决定：统计信息质量、代价模型贴合度、搜索空间是否被合理管住。它跟 SQL 写得复杂不复杂没有必然关系。最后我们清点一遍高频误判：八个常见坑，每个都配上根因和正确动作，算是把这一讲收口。

29　八个坑，逐个配好根因与动作

这张表可以当速查卡用。把 cost 当毫秒，是把相对单位误当成时间；见 Seq Scan 就判错，是忘了读大部分页面时顺序扫描往往更便宜；忽略 loops，是把「每次一行」误读成「总共一行」；扩展统计创建后忘 ANALYZE，是不知道 CREATE STATISTICS 只登记不采数；以为扩展统计能修所有 join 估计，是忽略了官方文档那条硬边界；用 enable_* 长期关掉某类路径，是把诊断探针当成了治理手段；忽略 prepared statement 的 generic plan，是没意识到参数分布差异；只调数据库参数不看 SQL 语义，是忘了隐式类型转换、排序需求、分页方式、CTE materialization、OR 条件、函数包裹列都会改变候选 Path。

数一数这八条：六条是输入问题——统计、表达式、相关性、参数、SQL 形态；一条是读 EXPLAIN 的方法问题；一条是工具误用。真正「优化器实现有 bug」的情况极少。所以排查顺序几乎总是固定的：先看估计与实际差在哪一层，再修统计与 SQL，最后才考虑代价常数和搜索参数。

讲到这里，主线可以收束了。最后一页把这条因果链重新串一遍，并留六个值得继续追问的问题给下一轮实验——它们都能用前面给的命令和 DEMO 自己验证。

30　把三个脆弱点留在手边

整讲收束成三个支点。第一，候选 Path 有没有覆盖好计划——索引只是后补的候选，SQL 写法、表达式、约束、分区都会决定有哪些路径能被生成。第二，统计信息能不能估准 rows——ANALYZE 采样、单列统计、扩展统计、clauselist_selectivity 的处理方式，共同决定了这个最脆弱的输入。第三，代价模型贴不贴近本机负载——seq_page_cost、random_page_cost、effective_cache_size 这些常数，是 workload 平均值，不是普适真理。这三件事任何一件失真，最后选出来的 cheapest 都只是「模型里的 cheapest」。

所以这一讲真正想留下的不是一个结论，而是一条可重复的诊断路径：先看候选有没有，再看 rows 准不准，再看 cost 像不像，最后才考虑搜索参数和 GEQO。官方文档、optimizer/README、costsize.c 与 clausesel.c 都在那儿，把每个判断落回一手资料，比记十句调优口诀有用。横向那条脉络也别忘了：System R 给框架，Cascades 给可扩展性，PostgreSQL 给工程实现，Neo / Bao 试着补盲区，核心矛盾一直没变——计划空间太大，真实成本不可提前精确知道。

最后留六个问题：LIMIT 与 startup cost、random_page_cost 与全内存、join 估错时的排查顺序、dependencies 与 mcv 的分工、memo 与 RelOptInfo+Path 的取舍、以及 Bao 为什么选择 steering。它们都能用这一讲给的命令和两组 DEMO 自己验证。讲到这里先停一下，下一轮我们拿真实实例逐个回答。
