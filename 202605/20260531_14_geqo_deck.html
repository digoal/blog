01优化器之 GEQO：给大 join 查询装上保险丝

这一讲我们不从「遗传算法是什么」开始，而从一个更土的问题开始：一条 SQL 连了十几张表，优化器到底该花多少时间，想清楚先连谁、后连谁。这个问题不性感，但它是很多生产事故的根。

先记住这张剖面。从最上层的应用 SQL，一路往下到执行计划，中间有七层：解析重写、单表扫描路径、joinlist、连接顺序搜索、连接路径构造、成本评价、最终计划。GEQO 不在最上，也不在最下，它只占第四层。这个位置决定了后面所有结论——它改不了扫描路径，改不了 Nested Loop 还是 Hash Join，也改不了代价模型，它只能决定「按什么顺序去试」。

所以本讲的主线不是背算法口诀，而是一次工程取舍：当规划成本高到不能接受，我们愿意拿多少计划质量，去换一个可预测、可封顶的规划时间。先把这个问句放在心里，后面每一页都是在回答它。

02表越多，连接顺序空间越不像话

先做个不依赖任何数据库的算术。只考虑「谁先跟谁连」的顺序，不考虑每一步用 Nested Loop、Hash Join 还是 Merge Join，也不考虑索引、排序、并行——n 张表的 left-deep 顺序数就是 n!。四张表 24 种，八张表 40320 种，十二张表 479001600 种。右边这个动画可以把 n 从 2 一路点到 16，注意纵轴是对数刻度，不然最后几根柱子会直接冲出画面。

PostgreSQL 的标准做法是动态规划：先构造二元 joinrel，再构造三元，逐层向上，好处是能系统性复用子问题结果。但代价是要维护所有 relation 子集，规模是 2 的 n 次方；十二张表就是 4096 个 joinrel，每个 joinrel 里还不止一条 path。所以膨胀的不只是「顺序数」，还有「要记住的中间状态数」。

这里我要特别说清楚：n! 和 2ⁿ 都是数学公式算出来的，不是我在某台机器上跑出来的 benchmark。原文明确了不伪造实测数字，这一讲也守住这条线——凡是没有实测的，我都标成公式值或示意值。官方把 geqo_threshold 默认设成 12，本质上就是在这条曲线上找了一个经验切点。

03三条路，三种代价

空间摆在这儿，能走的路其实就三条。第一条，继续用动态规划硬搜。好处是结果质量有保障，坏处是 joinrel 和 path 一起膨胀，规划阶段的时间和内存可能先崩。第二条，干脆别搜了，接受一个次优的连接顺序，把代价推给执行阶段——规划是快了，但一条报表 SQL 可能从三秒变成三分钟。

第三条最容易被低估：让应用或 DBA 把顺序写死，比如 join_collapse_limit 设成 1，用显式 JOIN 固定顺序。这看起来很可控，可它把「数据分布变化」的风险从数据库转嫁给了写 SQL 的人。今天这个顺序最优，下个季度数据倾斜变了、统计信息变了，它就过期了，而且没人会收到通知。

官方文档把这件事说得很直白：对多表查询，穷举搜索耗时过长，often longer than the penalty of executing a suboptimal plan——常常比执行一个次优计划的损失还大。注意这句话的重心：它不是说穷举不好，而是说在某些规模下，继续追求最优这件事本身已经不划算了。这就是下一页那个改写的动机。

04核心命题：把「找最优」改写成「按时交卷」

于是 PostgreSQL 做的不是「把搜索变快」，而是把问题改写了。原问题是：在巨大的 join order 空间里找全局最优计划。转化后变成：随机生成并演化一批 join order，在限定评价次数内保留低成本候选。一句话，从「求最优」变成「按时交卷」。

代价写得清清楚楚：不保证最优，同一个查询可能因为 geqo_seed 和参数不同，探索到完全不同的路径。收益也写得清清楚楚：规划时间和内存可控，大 join 查询不会轻易卡死在优化阶段。原文那句判断我很认同——这不是让 PostgreSQL 变聪明的魔法，是给大 join 查询一个可控的规划时间上限。

这里还埋着一个很实用的推论，DBA 尤其要记住：很多「偶发慢 SQL」不是执行器突然变慢，而是这条查询进入 GEQO 之后，这次探索到的 join order 质量变了。执行计划变了，执行时间跟着变，但根因在规划阶段。后面讲排障路径时，我们会回到这句话。

05GEQO 只接管流水线中的一层

把流水线摊开，位置就清楚了。标准 planner 先给每个 base relation 生成 scan path——顺序扫描、索引扫描、位图扫描；然后才是 join order 的问题。GEQO 在这里插一手，给出一个候选的 relation 顺序；接下来每一个 tour 仍然交回标准 planner 去构造 join path、算成本；最后用当前种群里成本最低的 tour 生成 finished join relation。

官方 61.3.1 的原文是：The GEQO planning process uses the standard planner code to generate plans for scans of individual relations. Then join plans are developed using the genetic approach. 请注意前半句——单表扫描计划用的是标准代码。这句话直接否掉了「GEQO 是另一套优化器」这种理解。

所以右侧那两栏值得停一下：GEQO 不生成 scan path、不实现 join 算法、不定义代价模型、也不做统计信息估计。它只做两件事，一是提供候选顺序，二是用标准 CBO 的评价结果挑出最便宜的那个。它跟标准 join search 共享同一套代价模型和 path 生成能力，区别只在搜索策略。这个「共享」是后面横向对比那页的关键。

06一个 if，决定走哪条搜索路径

看源码最省事。src/backend/optimizer/path/allpaths.c 的 make_rel_from_joinlist() 里，判断就是三行：如果 join_search_hook 存在，交给插件；否则如果 enable_geqo 为真并且 levels_needed 大于等于 geqo_threshold，调用 geqo()；再否则，调用 standard_join_search()。没有第四条路，也没有什么智能判断「这条查询适合不适合」。

这里 levels_needed 指的是 joinlist 里需要搜索的 relation 数量，不等于你肉眼数出来的表数。join_collapse_limit 和 from_collapse_limit 控制显式 JOIN、子查询会不会被折叠成更大的 FROM list，折叠之后 levels_needed 就变大了。官方专门提醒：把这两个值设到 geqo_threshold 或更高，可能触发 GEQO，并带来非最优计划。

这个细节在排障里很值钱。有时候你明明只写了八张表，结果还是进了 GEQO，原因不在表数，而在重写阶段的折叠。所以后面 DBA 的排查顺序里，我会把「检查 relation 数与两个 collapse limit」放在调 GEQO 参数之前。

07七个 GUC，分成开关、预算、随机三组

把七个参数按作用分成三组，就不容易记混。第一组是开关和触发：geqo 默认 on，geqo_threshold 默认 12、最小 2。注意官方对 geqo 的措辞是 usually best not to turn it off in production，生产环境通常不建议关，细粒度控制交给 threshold。这一点和很多人「先关掉试试」的直觉正好相反。

第二组是预算：geqo_effort 默认 5、范围 1 到 10，但它 doesn't actually do anything directly——官方原话，它本身不参与搜索，只用来推导其他参数的默认值。geqo_pool_size 和 geqo_generations 默认都是 0，意思是「按 effort 和表数自己算」；手工设的话，pool_size 最小 2、常用 100 到 1000，generations 最小 1。

第三组管随机性：geqo_selection_bias 默认 2.0、范围 1.5 到 2.0，是选择压力；geqo_seed 默认 0.0、范围 0 到 1，决定随机数初值。这一组是「同一条 SQL 为什么这次和上次不一样」的答案入口，后面会单独讲。这里先记住一个容易踩的坑：如果你已经手工写了 pool_size 和 generations，再调 effort 往往不会产生你预期的效果。

08join order 被编码成一条 TSP tour

官方文档给的例子是 '4-1-3-2'：先连接 relation 4 和 1，再依次加入 3 和 2。编码非常朴素——Gene 就是一个 int，代表 initial_rels 里的第几个 relation；Chromosome 是一整条 Gene 串，也就是一个完整的 join order；Pool 里装着一批 Chromosome，外加 size 和 string_length。每个 Chromosome 带一个 worth，是这个候选顺序被评价出来的成本，越小越适应环境。

这里有个非常关键的限定，我在图上写了两遍：这条整数串不是最终物理执行计划的完整描述，它只是生成 join tree 的指南。真实的 SQL 里有 outer join、LATERAL、semijoin、antijoin，有 join clause 的分布，甚至有笛卡尔连接，gimme_tree() 必须能修正、推迟、甚至拒绝不合法的顺序。把这个想成「照单执行的执行顺序」，后面理解评价逻辑就会全错。

PostgreSQL 把这套编码类比成旅行商问题：一个 tour 访问每个 relation 恰好一次。类比很适合遗传算法，因为「每个点访问一次」这个约束天然就能编码成排列。但下一页我要立刻泼一盆冷水——这个类比有明确的官方保留意见，不先说清楚，很容易把 GEQO 误当成理论上天衣无缝的方案。

09借了 TSP 的模型，但边界要立刻说清

为什么非要泼这盆冷水？因为官方在 61.3.2「Future Implementation Tasks」里自己写了保留意见。原文是：In the TSP case, the cost associated with any substring (partial tour) is independent of the rest of the tour, but this is certainly not true for query optimization. 翻译过来：TSP 里一段路径的代价，跟这段路径放在 tour 的哪儿没关系；但查询优化里，一个 join 子树的成本，跟上层怎么选、谓词怎么下推、有没有外连接约束、能不能做参数化路径，全都相关。

紧接着官方还有一句：Thus it is questionable whether edge recombination crossover is the most effective mutation procedure——所以 ERX 到底是不是最有效的重组方式，本身就值得怀疑。这不是我加的评论，是文档原文。

我想让这个边界在讲机制之前就立住。否则很容易出现一种误解：以为 GEQO 是把一个已被证明最优的算法搬进了数据库。不是的。它是九十年代工程约束下的一套务实方案，成熟、可用、有明确收益，同时带着明确的理论保留。后面所有「不保证最优」的结论，根子都在这里。

10稳态 GA：一次只生一个，挤掉最差那个

geqo_main.c 的流程可以压成七步：设 seed；算 pool_size；算 generations；随机初始化种群并立刻逐个评价；按 worth 从小到大排序；然后循环 generations 次，每次选两个父代、用 ERX 生成一个子代、评价这个子代、若不差于最差个体就插回并重新排序；最后用 pool[0] 的 best_tour 生成最终 joinrel。右边这个动画就是把这个循环放慢给你看，可以调 seed、pool 和 gens，单步走一遍四个阶段。

关键词是「稳态」。官方文档 61.3 写得很清楚：Usage of a steady state GA (replacement of the least fit individuals in a population, not whole-generational replacement) allows fast convergence towards improved query plans. 不是整代推翻重来，是每次只换掉最不适应的个体，好处是收敛快——而文档紧接着说，This is essential for query handling with reasonable time，这对「在合理时间内完成查询处理」是必要的。

还有个细节别漏：官方说的是「搜索过程中任意时刻找到的最优」被用来生成最终计划，不是最后一代里随机挑一个。另外初始化种群时，每个 tour 就已经立刻被 geqo_eval 评价过一次了，所以评价次数不是从循环才开始算。这个数字下一页讲预算时会用到。

11一个实证：GEQO 没有变异算子

这一页是我最想强调的「真实实现」和「背口诀」的差别。很多人介绍遗传算法会说选择、交叉、变异三件套。但 PostgreSQL 官方 61.3 的原文是：Mutation as genetic operator is deprecated so that no repair mechanisms are needed to generate legal TSP tours. 变异作为遗传算子已经被弃用，目的就是不需要修复机制来生成合法的 TSP tour。

为什么可以不要变异？因为默认的重组方式是 ERX，edge recombination crossover，它对 TSP 的价值是 keep edge losses low——保留父代里的相邻关系。子代继承的是「边」而不是「位置」，结果天然还是每个 relation 恰好出现一次的合法排列，不会冒出重复或缺失，自然也就不需要一个 repair 步骤去擦屁股。源码里 PMX、CX、PX、OX1、OX2 这些重组实现都还留着，但 src/include/optimizer/geqo.h 里编译选择的是 #define ERX。

右边那三行 tour 是示意值，专门标了「非实测输出」，只是让你看见「继承相邻关系」长什么样。我特意把这句话写在图上，是因为这一讲不编造任何 benchmark 数字——示意就是示意，公式值就是公式值，官方文档原句就是原句。分清楚这三类，技术内容才站得住。

12GEQO 不自己估成本，仍调用标准 planner

geqo_eval() 的关键，不是另发明一套成本模型。它用 tour 指导 gimme_tree() 构造 join relation，最后读取 joinrel->cheapest_total_path->total_cost 当 fitness。官方 61.3.1 还补了一句很实在的话：对每个 join 步骤，三种可能的 join strategy 都会被考虑，所有预先确定的单表扫描计划也都可用，估计成本取其中最便宜的那个。所以分工特别干净——GEQO 负责「搜哪些顺序」，标准 CBO 负责「这个顺序下有哪些物理路径、成本是多少」。

geqo_eval.c 里有几个工程细节，值得记。每次评价会创建一个名为 GEQO 的临时内存上下文，评价完就删掉，避免成百上千次候选评价把整个 planner 生命周期的内存污染掉。gimme_tree 把 tour 当 guideline 而不是死命令：它维护一组已连接的 clump，新 relation 尝试并入；desirable_join() 优先接受有相关 join clause 或 join order restriction 的连接；暂时连不上就推迟；最后还剩多个 clump 才尝试 force join。如果压根形不成单个合法 join relation，geqo_eval 直接返回 DBL_MAX，把这条候选标成极差。

这也解释了前面那句「tour 不是绝对执行顺序」。现实 SQL 里的 outer join、LATERAL、semijoin、antijoin、join clause 分布、笛卡尔连接，都会迫使启发式修正甚至拒绝顺序；源码注释自己都承认，某些 LATERAL 约束下当前启发式仍可能失败。

13评价次数从 effort 一路推出来

没手工设 geqo_pool_size 时，gimme_pool_size() 先按 2 的 (nr_rel + 1) 次方估一个规模，再被 effort 卡在上下限里：maxsize 等于 50 乘 effort，minsize 等于 10 乘 effort。effort 默认 5，所以区间是 50 到 250。没手工设 geqo_generations 时，它默认就等于 pool_size。

于是默认情况下，评价次数大致是两块相加：初始化种群时每个个体评价一次，是 pool_size 次；循环 generations 次、每次一个新子代，又是 pool_size 次。合计约 2 乘 pool_size。这个关系很实用——你把 pool 或 generations 调大，规划阶段就会实打实地多做候选评价，计划质量可能提高，规划时间也一定上去。

但请守住那条边界：这是评价次数的关系，不是执行时间公式。每一次 geqo_eval 的成本，取决于 relation 数、join 约束、path 构造、统计估计、内存上下文分配，差异可以很大。原文特别提醒这点，我也把它写在图上了。

14随机但可复现：geqo_seed 是排障的把手

GEQO 是随机启发式，但 PostgreSQL 给了可复现控制。每次 GEQO 运行前，geqo_set_seed() 会用当前 geqo_seed 重置私有随机数状态。官方 61.3.1 的原句我放在图上了：只要 geqo_seed 和其他 GEQO 参数保持固定，对给定查询（以及统计信息等 planner 输入）就会生成同样的计划；想探索别的搜索路径，改 geqo_seed。

排障时这个把手非常好用。第一步，如果大 join SQL 在 GEQO 下计划不稳定，先固定 seed 做对比，把随机性这个变量锁死。第二步，如果某个 seed 下计划明显差，换几个 seed 验证空间里是不是存在更好的 join order。第三步，也是最容易忘的一步：不要把「换 seed 变快」当成根治。它只证明搜索空间里有更好候选，不证明你的统计信息是对的。

真正稳定的办法，还是原文给的那几条：改善统计、缩小 join 搜索空间、重写 SQL、调整 schema 和索引。后面最佳实践那页会按角色展开，这里先记住顺序——先锁随机性，再谈调参，最后才谈改结构。

15四种策略，共享同一套代价模型

横向看四种做法。标准 join search 用动态规划系统枚举较小空间，小规模下更接近最优，代价是 relation 数上来后规划时间涨得很快。GEQO 用随机初始化加选择、重组、评价，把规划时间交给 pool 和 generation 控制，代价是不保证最优。手工指定顺序把选择权交给人和 SQL 写法，规划时间通常低，但数据分布一变，人工顺序就过期。Volcano/Cascades 那一类用逻辑物理转换规则、memo 和 property 组织可扩展搜索，最优性取决于规则、剪枝和搜索预算，实现复杂度高。

表格里最容易读错的一行是「对统计信息依赖」。四种方案其实都高：GEQO 的评价仍然走标准 CBO，统计信息错了，评价出来的 worth 就是错的，演化得再认真也只是在一堆错误的成本里挑一个最小的。这也是为什么换 seed 救不了过期的统计信息。

所以那一句澄清要重复一遍：它们共享 PostgreSQL 的代价模型和 path 生成能力，区别只在 join order 搜索策略。GEQO 的价值是用搜索质量换规划可控性，不是让优化器变得更聪明。

16收益与成本，都发生在 planning 段

把时间轴画成两段，很多争论就消停了。GEQO 的作用域只覆盖 planning：它避免大量 relation 的 join order 动态规划爆炸，把候选评价次数约束在 pool 和 generation 附近，让大 join 查询有机会在合理时间内规划完。这三条都是规划阶段的收益。

成本也全在计划质量上：可能错过标准搜索能找到的更优顺序；质量受随机路径、种群大小、迭代次数、统计信息共同影响；复杂约束下 tour 只是 guideline，gimme_tree 的启发式可能失败或被迫产生不理想连接；调大参数会增加规划时间，但不保证线性提高计划质量。

官方 61.3.2 还给了另一条边界，我放在图注里：每个候选 join sequence 都会从头调用标准 planner 的 join selection 和 cost estimation，不同候选共用相似子序列时会大量重复计算。缓存子连接成本可能显著提速，但要在内存上付钱——这又是一次典型的工程取舍。

这里对排障有个直接推论：只盯 execution time 是不够的。GEQO 的价值和风险都在 planning，所以后面会反复强调 EXPLAIN (ANALYZE, SETTINGS) 里的 planning time。

17参数不是越大越好，是按 workload 设预算

把图左边这两条线看仔细：上面那条靛青实线，是规划时间，基本随评价次数增长，这个关系比较确定；下面那条青绿虚线，是找到更好计划的概率，递增、趋平、而且不保证。我特意用直角阶梯而不是平滑曲线，也特意标了「无刻度、非实测」——这里是定性趋势，不是我编出来的性能数字。

右边三组参数各有各的杠杆。geqo_threshold 决定从近穷举切到 GEQO 的 relation 数；pool_size 和 generations 直接决定种群规模和迭代次数；selection_bias 和 seed 管的是选择压力、随机路径与可复现性。官方 61.3.2 自己说，参数设置仍需要在「计划最优性」和「计算时间」之间找折中，说明这件事到今天也没有一个万能值。

所以常见策略是这样的：想减少进入 GEQO，提高 threshold，但接受更高规划成本；想让 GEQO 多探索，提高 pool 或 generations，但接受更长 planning time；想降低自动展开带来的搜索空间，降低两个 collapse limit；想验证人工顺序，用 join_collapse_limit = 1 做实验。每一条都是交换，不是免费午餐。

18最小 DEMO：让它触发，再让它可复现

给一个最小实验模板，三步。第一步，建一个 schema，造 12 张结构相同的表，每张用 generate_series 插一万行，然后 ANALYZE。第二步，把 geqo 打开、geqo_threshold 压到 4、geqo_seed 固定成 0.0，对 12 表 JOIN 跑 EXPLAIN (VERBOSE, COSTS ON, SETTINGS ON)。第三步，把 geqo 关掉，同一条 EXPLAIN 再跑一次，对比计划形态和规划耗时。

三个观察点写在图上了。SETTINGS ON 应该能显示非默认的 planner 参数，比如 geqo_threshold 和 geqo_seed；固定 seed 重复执行，在统计信息和环境不变的前提下计划应可复现；改成 seed 等于 0.7 之后，可能看到不同的 join order，也可能因为数据太规则而看不出明显差异——最后这半句很重要，看不出差异不代表机制没生效。

两条纪律必须说在前面。第一，不要在生产库随意对超大 join 查询关闭 GEQO，这个实验只适合可控环境，官方本来就建议生产别关 geqo。第二，真实排障要用 EXPLAIN (ANALYZE, BUFFERS, SETTINGS)，同时关注 planning time、execution time，以及估算行数和实际行数的差距。还有一句诚实话我写在图注里：这些 SQL 是可执行模板，本轮并没有启动 PostgreSQL 实例去跑，所以这里不汇报任何实测数字。

19先分清慢在 planning 还是 execution

排障路径我从一条命令起：EXPLAIN (ANALYZE, BUFFERS, SETTINGS)。先看 planning time 和 execution time 各占多少。如果 planning time 占比高，往左走——检查 relation 数、geqo_threshold、两个 collapse limit；确认进了 GEQO 之后，固定 seed，再对照不同 seed、pool、generation。如果 execution time 高，往右走——先看 rows 估计是不是偏差巨大，再看 join method 和索引路径，检查 ANALYZE、扩展统计、数据倾斜和选择率，最后才轮到 join order。

为什么这个顺序不能反？因为 GEQO 的评价完全依赖标准 CBO 的成本估计。统计信息错了，worth 就是错的，这时候调 pool 调 seed，等于是让优化器更认真地在错误答案里挑一个。原文给 DBA 的排查路径也是同样的次序：先定位，后调参，最后才谈结构。

还有一条粒度上的建议：如果某条 SQL 极关键，可以在会话级临时调整参数，不建议全库盲目改。常见策略我都写在图注里了——提高 threshold 减少进入 GEQO、提高 pool 多探索、降低 collapse limit 缩小搜索空间、用 join_collapse_limit = 1 验证人工顺序。每一条都该有对照、有记录。

20三类角色，三种正确动作

把建议按角色分开，是因为杠杆长在不同的地方。架构师手里是搜索空间：对报表、BI、权限展开、宽星型模型、自动生成 SQL 的系统，控制单条 SQL 的 join relation 数；用物化中间结果、预聚合、宽表、语义层拆分、分阶段查询，减少一次性 join；给 ORM 或查询生成器设上限，别让动态拼接拼出几十张表的单 SQL；对关键查询建立可重复的计划回归测试，至少记录 EXPLAIN (SETTINGS, COSTS) 和主要 join order。

DBA 手里是定位与预算：先分清 planning 还是 execution，固定 seed 做对照，按 SQL、角色、会话粒度调参，别全库盲改。业务开发者手里其实是 SQL 的生成方式——不要把权限、标签、画像、事实表、维表、明细表一次性全拼进一条无限膨胀的 SQL；限制自动生成 SQL 的可选维度，必要时先落临时表或物化视图；避免无谓笛卡尔连接和缺失 join 条件；给高选择性过滤条件建索引并及时 ANALYZE。

还有一句给开发者的提醒挺有意思：当 DBA 来问业务选择性、字段相关性、典型参数时，别只丢一个 SQL 模板过去。实际参数分布会影响计划，这不是客套话——它直接决定统计信息能不能把 rows 估准。三类角色合起来就一个共同原则：把 GEQO 当复杂模型查询的最后防线，不是常规调优工具。

21哪些场景适合，哪些不该指望它

左边四条适合：relation 数很多、标准 join search 规划时间明显不可接受；SQL 来自报表、BI、规则引擎、知识库推理、自动查询生成器；业务能接受启发式计划，只要求整体规划时间可控；不是极端延迟敏感的点查，而是复杂分析或管理后台查询。共同点是——你愿意用一点计划质量，换一个不炸的规划时间。

右边四条不适合：少数核心交易 SQL，延迟和计划稳定性要求极高；连接数其实不多，真问题是统计过期、索引缺失或谓词不可优化；多表连接强相关、严重倾斜，却没有合适统计信息支撑；应用把几十个可选维度全拼进一条 SQL，还期望数据库自动永远选对。最后还有一条隐含的：你需要严格可解释、可预测的 join order，却没有计划回归测试。

所以那句收束话值得念一遍：GEQO 是「大 join 查询规划成本」的保险丝，不是「坏 SQL 自动变好」的优化器外挂。保险丝的作用是让系统在过载时不要烧毁，不是让电路变得更高效。

22六个坑，都源于把它放错了层

六个坑快速过。第一，只调 geqo_seed 不修统计信息——换 seed 只是换一条随机探索路径，根因若是 rows 估计错，那只能碰运气。第二，全库关闭 GEQO——实验有用，生产全局关闭可能让大 join 查询在规划阶段吃掉大量时间和内存。第三，把 geqo_effort 当直接开关——官方原话是它 doesn't actually do anything directly，只用于算别的参数默认值。

第四，忽略 join_collapse_limit——显式 JOIN 默认仍可能被重排，想验证人工顺序得先理解它。第五，忽略 planning time——很多排障只看执行时间，可 GEQO 的价值与风险都在规划阶段。第六，期待 GEQO 解决所有多表问题。

下面那条带子我特意列全了它修不了的东西：错误的 join 条件、缺失索引、过期统计、表达式不可索引、隐式类型转换、数据倾斜、work_mem 不足、IO 瓶颈。八类问题，没有一类在 join order 搜索这一层。调任何 GEQO 参数都不会改变它们——这六个坑，说到底是同一个坑：把 GEQO 放错了层。

23一次工程取舍，不是一套算法口诀

把整条链收一遍：表一多，连接顺序空间先膨胀；三条路各有代价；于是把「找最优」改写成「按时交卷」；改写只发生在流水线的一层；候选被编码成一条 tour；用稳态 GA 演化；每个候选仍由标准 CBO 估价；最后由预算、随机性和官方写明的边界共同界定它能走多远。八步，从头到尾是同一个问句：愿意拿多少计划质量，换多少规划可控性。

出处我列在图上，方便回去核对：官方文档 geqo.html 和 runtime-config-query.html 的 19.7.3；本地源码 allpaths.c 的触发分叉，以及 geqo_main、geqo_eval、geqo_pool、geqo_selection、geqo_erx 和 geqo_gene.h；论文这边是 Ioannidis 与 Kang 1990、Bennett 等 1991、Whitley 等 1989 的 ERX 与 Genitor 工作。这一讲的关键事实，都回到官方文档和源码核验过。

最后留五个延伸问题，图上那一行就是：15 表偶发慢，先固定 seed 还是先提 pool，为什么；gimme_tree 为什么不能机械执行 tour；pool 从 250 提到 1000，规划时间、计划质量、稳定性分别怎么变；ERX 为何不一定适合 join optimization；ORM 生成的超大 SQL，先改数据库参数还是先约束生成器、边界在哪。这几个问题没有标准答案，但如果你想清楚了该用哪一层的证据去回答，这一讲的目的就达到了。
