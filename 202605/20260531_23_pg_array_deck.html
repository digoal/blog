PAGE 01 / 22
一行内部的同类型小集合

今天不从语法开始，从一句判断开始：array 适合保存一行内部的小规模、同类型、多值属性。这句话听着平平无奇，但它是后面所有取舍的总开关。

我把整套知识按地层排好了：最底下是物理存储，往上是类型与维度、操作符语义、GIN 索引、统计信息、执行计划，最上面才是建模决策。为什么这么排？因为上面每一个「该不该」，答案都藏在下面的「是什么」里。你不知道数组整体是一个 varlena 值，就不会明白为什么改一个元素会写一行新版本；你不知道 GIN 只登记了四个策略号，就不会明白为什么位置查询用不上索引。

实证上，这些结论都能回到 PostgreSQL 官方文档 8.15、9.19、9.25，以及源码 array.h、arrayfuncs.c、ginarrayproc.c、array_typanalyze.c。我们不编性能数字，只讲可以自己验证的机制。

先看最上面那层：需求到底长什么样。

PAGE 02 / 22
一行天然带一组值，有四种写法

应用里太常见了：用户有多个标签，商品有多个适用渠道，文章有多个关键词，规则命中多个枚举项，设备一次上报多个指标。老三样做法是逗号拼字符串、拆子表、存 JSON。

逗号字符串最省事，代价是数据库失去了类型、比较和索引语义——LIKE 会误匹配，分隔符要转义，大小写和空格都得自己兜。子表最规范，外键、唯一、审计都天然，但对一个只有三个标签的字段，多一张表、多一次 JOIN 就偏重。jsonb 灵活，可如果值的本质就是「同类型数组」，它给的是不必要的结构自由度，schema 容易漂移。

所以请注意，array 的价值从来不是「少建一张表」。它是把「行内同类型小集合」放进了类型系统：每个元素有确定类型，数组有维度和下界，支持下标、切片、拼接、unnest、ANY/ALL、包含与重叠，并且可以用 GIN 建倒排索引。

那这个「放进类型系统」，具体划的是哪条线？

PAGE 03 / 22
划一条线：原子属性，还是关系实体

判断标准只有一句话：这个集合是否属于当前行的原子属性？ 如果是，数组很自然；如果集合里每个元素都有自己的创建时间、来源、权限、状态、外键和审计，它已经不是简单属性，应该拆表。

举个能落地的例子。文章的三个标签，跟文章同生共死，读写都是整行一起读，那就是原子属性。可一旦产品说「标签要记录是谁打的、什么时候打的、置信度多少、过不过期、能不能被某个角色查看」，这三个字符串就已经变成三条关系记录了。你还把它们塞在数组里，就等于自己放弃了外键、唯一约束、权限和审计，后面每一项都得在应用层重新造一遍。

这条线不是偏好，是约束能力上的硬差异：数组元素不能直接建外键，也不能直接加唯一约束。原文把它写成了一句很克制的话——array 的价值不是少建一张表，而是给小集合字段一个清晰边界。

好，边界定了。往下沉一层，看看类型系统到底给了它什么。

PAGE 04 / 22
把多值属性放进类型系统

PostgreSQL 允许把表列定义成变长多维数组，元素可以是内置类型、用户定义基础类型、枚举、复合类型、range 或 domain。关键是元素类型固定：数据库因此可以调用元素类型自己的输入输出、比较、哈希、排序和等值函数，而不是把它当成一段文本。

由此长出六类能力：维度与下界的元数据；下标、切片、拼接；unnest 展开做统计；ANY/ALL 做标量对元素的比较；@>、<@、&& 做集合成员判断；以及 GIN 倒排索引。写查询的时候，业务关系可以直接翻译成集合关系：tags @> ARRAY['postgres'] 是包含，tags && ARRAY['database','optimizer'] 是相交，'postgres' = ANY(tags) 是标量成员判断，unnest(tags) 加 GROUP BY 就是标签统计。

这比逗号字符串可靠得多，因为类型、比较和索引三件事都在数据库里，不在应用约定里。

但先别急着写 DDL——类型系统有个非常容易踩的坑。

PAGE 05 / 22
integer[3] 只是文档说明

官方文档 8.15.1 有两句特别值得抄下来的话：当前实现忽略任何提供的数组尺寸限制；当前实现也不强制执行声明的维度数。原文说得很直白：声明尺寸或维度数只是文档，不影响运行时行为。

所以 CREATE TABLE t (a int[3]) 不会限制只能存三个元素，text[][] 也不会保证一定是二维。同一元素类型的数组，无论尺寸和维度，都被认为是同一个类型。如果你在代码评审里看到有人用 int[3] 当约束，那是个纯装饰。

真要约束，就显式写 CHECK：CHECK (array_ndims(tags) IS NULL OR array_ndims(tags) = 1) 管维度，CHECK (cardinality(tags) <= 16) 管数量，再加上 NOT NULL DEFAULT '{}' 把空集合固定下来。为什么维度判断要允许 NULL？因为空数组的 array_ndims 返回 NULL，写死等于 1 会把空数组挡在门外。

说到空——这里其实有三种「空」，它们不是一回事。

PAGE 06 / 22
NULL 数组、空数组、NULL 元素

先把三个概念钉死：NULL::int[] 是列值本身未知；'{}'::int[] 是一个非 NULL、元素数为 0 的数组；ARRAY[1,NULL,3] 是数组存在，但某个位置是 NULL。另外还有下界和维度：下界默认 1 但可以不是 1，比如 '[0:2]={10,20,30}'::int[]；PostgreSQL 内部维度上限 MAXDIM 是 6。

再看四个边界行为，都是文档里写明的：array_length('{}'::int[], 1) 返回 NULL 而不是 0，判断元素总数要用 cardinality()；下标越界返回 NULL 而不是报错；切片完全越界返回空的零维数组而不是 NULL，官方特意注明这跟非切片行为不一致，是历史原因；部分越界的切片会被静默压缩到重叠区域。

这几条不是考据癖。生产里最稳的写法就是：集合列一律 NOT NULL DEFAULT '{}'，并且禁止 NULL 元素。否则 ANY/ALL 的三值逻辑、@> 的匹配结果、以及应用层的判空会互相打架，排查起来非常贵。

现在概念清楚了，我们下到最底那一层——物理存储。

PAGE 07 / 22
ArrayType 不是一串文本

源码 src/include/utils/array.h 给出的普通数组结构很朴素：vl_len_ 总字节数、ndim 维度数、dataoffset 在有 NULL 位图时指向数据起点、elemtype 元素类型 OID、dimensions[] 每维长度、lower bnds[] 每维下界，然后是可选的 NULL bitmap 和实际元素数据。

元素按 row-major order 存放，也就是最后一个下标变化最快。ARRAY[[10,20,30],[40,50,60]] 在磁盘上的顺序就是 10 20 30 40 50 60，这跟文档里数组比较、unnest 的访问顺序是一致的。

这里最值得记住的是 elemtype：数组不是「文本里的一串值」，它明确记录了元素类型。正因为元素类型固定，PostgreSQL 才知道该调哪个比较函数、哪个哈希函数、怎么输入输出。这也解释了为什么 array_contain_compare() 能逐元素用元素类型的等值操作符去比。

结构决定行为。我们顺着这个头部，往下推四条一定会遇到的工程现象。

PAGE 08 / 22
TOAST 以整个数组为单位

第一条，宽数组会作为一个 varlena 值被 TOAST，整个数组可以被压缩或外部存储。第二条更关键：可 TOAST 的元素不能各自独立 out-of-line。源码注释说得很清楚，tuple toaster 并不知道数组内部的元素在哪里，所以数组整体才是 TOAST 单元。这意味着「每行塞一个超大数组」不只是写入慢，压缩和外部存储的效率也会变差。

第三条，对数组中一个元素做更新，本质仍是生成新的行版本。MVCC 下不是原地改一个小格子——这句话后面讲写放大时会再回来。第四条，数组可以有非 1 下界，但绝大多数应用不要依赖它，除非业务下标本身确实有意义。

你会发现，这四条没有一条是「语法知识」，全都是结构推出来的。这也是为什么我坚持从存储往上讲：记住结构，行为就不用背了。

好，往上一层，看操作符到底在判断什么关系。

PAGE 09 / 22
成员关系，不是多重集合关系

官方文档 9.19 写得很明确：包含操作符认为一个数组被另一个包含，是指它的每个元素都能在对方里找到；重复项不作特殊处理，因此 ARRAY[1] 和 ARRAY[1,1] 彼此都被认为包含对方。四个常用操作符是 @> 包含、<@ 被包含、&& 重叠、|| 拼接。

源码层面，arrayfuncs.c 里的 arrayoverlap()、arraycontains()、arraycontained() 都调用 array_contain_compare()。文件注释说明这类比较只考虑数组元素、忽略维度信息；函数里用元素类型的等值操作符逐元素比较，NULL 元素不会被当作普通值匹配。

所以这三个操作符的舒适区是集合成员判断：这个标签在不在、这两个集合有没有交集。它们不适合表达「第 3 个位置必须是什么」，也不适合表达「重复 2 次才算包含」。位置约束请用下标、切片，或者干脆换一个更明确的数据模型。

接下来把两个最容易翻车的反直觉结论单独摊开看。

PAGE 10 / 22
重复不计数，NULL 不匹配

第一个反直觉：ARRAY[1] @> ARRAY[1,1] 为真，反过来也为真。包含语义更接近「元素是否出现过」，不是「多重集合计数是否足够」。如果你的业务真的需要「库存里有两件才算满足」，请 unnest 后计数，或者改模型，别指望 @>。

第二个反直觉：NULL 不是普通元素。实践中 {1,2,NULL} @> ARRAY[NULL] 返回 false，就算数组里真有 NULL 也一样；要检测 NULL 元素得用 array_position(tags, NULL) IS NOT NULL。而 NULL = ANY(...) 走的是三值逻辑，结果是 NULL 而不是 false。

官方文档 9.25 把 ANY/ALL 讲得很干净：空数组上 ANY 返回 false、ALL 返回 true；右数组含 NULL 且没有 true 结果时，ANY 返回 NULL 而不是 false；ALL 则在没有 false 结果、但含 NULL 时返回 NULL。生产代码里，最省事的做法就是别让数组元素为 NULL。

语义层清楚了，索引才有的谈。GIN 到底把什么存进了树里？

PAGE 11 / 22
GIN 把数组元素倒排成 key

GIN 的核心就是倒排索引。src/backend/access/gin/README 说：entry tree 里存 key，每个 key 指向包含该 key 的 heap 行指针集合。对数组来说，key 就是数组元素。

pg_amop.dat 给内置的 gin/array_ops 登记了四个可索引操作符，策略号分别是：&& 1 号、@> 2 号、<@ 3 号、= 4 号。支持函数在 ginarrayproc.c：ginarrayextract() 把待索引数组拆成 key，ginqueryarrayextract() 拆查询数组并按策略选 search mode，ginarrayconsistent() 根据 key 命中情况判断候选行。

源码里还藏着几条非常实用的细节：对 &&，至少一个非 NULL 查询元素命中即可，普通 consistent 路径可以 recheck=false；对 @>，所有查询元素都要命中，且查询里有 NULL 时不能证明包含；对 <@，源码直接注释「can't do anything else useful here」，必须 recheck；对 = 也一样，因为数组相等还涉及维度、顺序和 NULL 处理。

这些文字读起来有点绕。下一页我们把它真正跑一遍。

PAGE 12 / 22
一个谓词怎样走完 GIN 路径

这一页请动手。左边输入查询元素，比如 pg,array，中间选操作符，然后点「播放」或者「单步」。演示里的堆表是四行固定数据：T1 是 {pg,array,storage}，T2 是 {pg,gin,index}，T3 是 {json,array,schema}，T4 是 {pg,optimizer,statistics}。这不是真实测量，是一个把源码逻辑摊开的可验证示意。

先看默认情况 @>：拆出 pg 和 array 两个 key，posting 分别是 T1,T2,T4 和 T1,T3，策略 2 要求所有 key 命中，取交集得到候选 T1，consistent 判 recheck=false，回表后结果还是 T1。

再切到 &&：策略 1 只要任一 key 命中，取并集，候选变成四行，同样 recheck=false。切到 <@：策略 3 无法只凭 key 证明，全部行都是候选、recheck=true；切到 =：候选是所有 key 都命中的行，但因为相等还要求顺序、维度完全一致，recheck=true，最后结果可能是空。把操作符来回切几次，「为什么 <@ 和 = 需要 recheck」就不再是背诵，而是看得见的因果关系。

路径看懂了，下面就能说清 GIN 帮得上和帮不上的边界。

PAGE 13 / 22
舒适区是成员关系，盲区是位置

数组 GIN 的舒适区很明确：CREATE INDEX article_tags_gin_idx ON article USING gin (tags)，然后查 tags @> ARRAY['postgres'] 或 tags && ARRAY['database','optimizer']。这两个谓词正好落在策略 2 和策略 1 上，走 Bitmap Index Scan 是自然的。

盲区同样明确。第一，tags[2] = 'postgres' 是位置查询，不是成员关系查询，GIN array_ops 不服务它；如果这类查询重要，建表达式索引 CREATE INDEX ... ((tags[2])) 或者改模型。第二，'postgres' = ANY(tags) 是标量对数组的比较构造，它不是 array_ops 的成员关系谓词，GIN 用不上，通常是顺序扫描。想用索引，就把谓词改写成 tags @> ARRAY['postgres']。

这一条特别值得写进团队规范，因为 = ANY 读起来比 @> 更顺，很多人会顺手写下，然后在慢查询里才发现问题。验证方式永远是 EXPLAIN (ANALYZE, BUFFERS)；另外小表不走索引完全正常，别拿五条数据下结论。

索引决定了候选行从哪来，但优化器会不会选它，还要看统计信息。

PAGE 14 / 22
优化器看的是常见元素，不是整列

数组列的选择率估算不是普通标量估算。array_typanalyze.c 的注释说得很清楚：整数组完全相同的重复可能很少，但很多数组共享个别元素，长数组尤其如此，而且因为 analyze.c 的宽度阈值低，标量统计可能整个缺失。所以它除了标准统计，还额外收集两类信息：常见数组元素及其频率 MCELEM，以及每行不同元素个数的直方图 DECHIST。

算法用的是 Lossy Counting，Manku 与 Motwani 2002 年那篇论文的方法。源码注释里还有一句很漂亮的因果说明：同一个数组内的重复元素不会改变 <@、&&、@> 的行为，所以统计时每个元素在一行里只计一次。你看，第九页那个反直觉结论，在这里直接影响了统计口径。

选择率函数在 array_selfuncs.c：arraycontsel() 估 @>、&&、<@；scalararraysel_containment() 能把 const = ANY(array_var) 折算成类似 array_var @> ARRAY[const] 的包含问题。工程含义很直接：不 ANALYZE、或者元素分布很偏但统计目标太低，优化器就可能选错扫描方式和 JOIN 顺序；超宽数组还会被分析宽度阈值跳过。动作就是 ANALYZE 加必要时 SET STATISTICS 1000。

讲到这里，机制层基本齐了。还差一块最容易被忽略的代价：更新。

PAGE 15 / 22
改一个元素，写的是整行

SQL 层确实可以写 UPDATE article SET tags[2] = 'postgresql' WHERE id = 1，看起来像在改一个小格子。但从 MVCC 和存储角度看，这仍然是更新整行的一个列值：PostgreSQL 生成新行版本，旧版本等待 vacuum 清理；如果数组较宽，还可能牵涉 TOAST 值变化。

连锁成本有四笔：新行版本写入和 WAL 增加、GIN posting list 或 posting tree 的维护、旧版本等待 vacuum 带来的表膨胀、以及频繁 array_append 造成的持续写压力。再叠加并发维度——两个事务同时改同一行数组的不同元素，也会争同一行锁。

所以准确的说法不是「不能更新数组」，而是把它当成字段整体更新，不要当成轻量级内嵌明细表。高频追加、删除元素的集合，应该拆子表，让每一行明细独立承担自己的 MVCC 生命周期。

把这条接上前面的 TOAST 结构、GIN 维护、统计质量，完整的代价账就能算清了。

PAGE 16 / 22
五笔代价，都有对应动作

把代价摊成一张表：写放大——改一个元素也生成新行版本，动作是控制数组大小、频繁变更拆表；空间放大——宽数组 TOAST、WAL、GIN posting 维护，动作是限制 cardinality、定期观察表和索引膨胀；统计不准——元素分布偏斜导致计划误判，动作是 ANALYZE 和必要时提高统计目标；约束不足——元素不能直接外键、唯一、审计，动作是 CHECK 兜底、复杂关系拆表；NULL 混乱——三种语义不同，动作是默认空数组、禁止 NULL 元素。

这里我想特意停一下，讲讲实证态度。原文有一句我很赞同：不要在没有测试的情况下承诺性能数字。实际效果取决于表行数、每行元素个数、元素基数和分布偏斜、谓词是 @> 还是位置访问、GIN pending list 与 vacuum 行为、返回行数是否需要大量回表。这些都可以在自己的环境里用 EXPLAIN 量出来，但量之前不该先给结论。

收益也是实打实的三条：把多值属性从字符串协议变成数据库类型、成员关系可以用 @>/&&/ANY 清晰表达、GIN 把元素倒排避免每次全表扫描再拆数组。

现在把 array 放回四种数据类型的横向坐标里，看它到底占哪一块。

PAGE 17 / 22
列值、关系、文档、区间

这张表不用逐格念，抓四句话就够：array 是「列值」，子表是「关系」，jsonb 是「结构文档」，range 是「点集区间」。主要目标不同，后面的约束能力就跟着不同。

最关键的差异在「外键 / 唯一 / 审计」这一行：子表最自然，array 和 jsonb 对元素都不自然，range 只对区间整体自然。再看「局部更新」：除了子表，另外三个本质都是更新列值。索引上，array 用 GIN array_ops 或表达式索引，子表可以用 B-tree、hash、GIN、GiST，jsonb 用 GIN jsonb_ops，range 用 GiST / SP-GiST。

所以选型不该问「哪个更先进」，而该问「我的业务问题本质是集合成员判断，还是关系实体」。前者 array 很好；后者硬用 array，会让约束和演化一路变难。适合场景也顺着这条线排下来：标签、枚举集合、小 ID 列表、固定维度参数归 array；订单明细、成员关系、授权流水归子表；动态属性和外部 payload 归 jsonb；时间有效期、价格区间、排班冲突归 range。

把这张表压一压，其实就是两个可以现场问出口的问题。

PAGE 18 / 22
两个问题定边界

第一个问题：元素是否需要独立生命周期、外键、审计？ 是，直接拆子表——订单明细、成员关系、授权流水都属于这一类，别再往下走了。否，才进入第二个问题。

第二个问题：值是否结构异构、键名经常变化？ 是，考虑 jsonb，比如埋点属性、第三方回调、半结构化配置；否，才是 array 的舒适区：同类型、数量受控、整列读写为主、查询主要是包含 / 重叠 / 成员判断。

这跟原文的判断完全一致：array 是「小集合字段」的工具，不是替代关系模型的万能容器。我特别喜欢这个顺序，因为它把「拆表」放在第一问——大部分踩坑不是因为不会用 array，而是因为该拆的时候没拆，等到数组里塞了几千个元素、还要按元素查权限，迁移成本就高了。

原则给出来了，还得落成能对照自己业务的场景清单。

PAGE 19 / 22
适合与不适合，一眼可查

适合的一边：文章、商品、用户画像上的少量标签；规则引擎里的少量枚举条件；一行记录中的固定周期指标，比如四个季度金额；查询主要是「是否包含某些值」或「是否与某集合相交」；元素没有独立生命周期，不需要外键和审计。

不适合的一边：订单明细、购物车明细、班级学生、项目成员这类强关系数据；元素需要频繁单独增删改且更新冲突明显；元素需要外键、唯一约束、权限、审计字段；每行可能有几千几万甚至更多元素；查询主要按位置、范围、排序窗口或元素属性过滤；业务需要不规则多维结构——顺带说一句，{{1,2},{3}} 这种不规则数组不是 PostgreSQL 原生 array 的模型，真需要 ragged array，通常该考虑 jsonb 或子表。

最后那句判断我建议贴在评审规范里：如果你会说「这行记录有几个标签」，array 可能合适；如果你会说「这些标签本身要管理、授权、审计、过期、关联别的表」，请拆表。

原则都有了，接下来给一套能在自己环境里跑完、不依赖任何虚构输出的最小实验。

PAGE 20 / 22
六步跑完，用 EXPLAIN 说话

原文的 DEMO 设计得很干净，六步。第一步建表：tags text[] NOT NULL DEFAULT '{}'，加 array_ndims 和 cardinality <= 16 两个 CHECK。第二步插五行，故意留一行 ARRAY[]::text[] 空数组。第三步对三条查询做 EXPLAIN (ANALYZE, BUFFERS) 拿基线：包含、重叠、标量 = ANY。

第四步 CREATE INDEX ... USING gin (tags) 再 ANALYZE article。第五步重复同一批 EXPLAIN，对比扫描方式和回表。第六步用 unnest 做标签统计，再验证那几条容易踩的语义：空数组和 NULL 数组的区别、array_length 对空数组返回 NULL、重复元素不影响 @>、NULL 元素不被 @> 匹配、ANY/ALL 在空数组上的取值。

有一句话必须原样转达：本文没有在本机连接 PostgreSQL 执行，所以不提供虚构输出。如果计划没用上 GIN，先查 pg_stats 的 null_frac、n_distinct、most_common_elems；小表不走索引是正常的，真要验证索引价值，得构造接近生产的数据量、元素分布和返回比例。

实验验证的是机制，上线前还得把八个高频坑快速过一遍。

PAGE 21 / 22
把坑和正确写法放在一起

快速扫一遍，每一条都配了正确写法。坑一，声明长度不生效，用 CHECK (cardinality(a) = 3)。坑二，把 NULL 数组当空数组，用 NOT NULL DEFAULT '{}'。坑三，用 array_length 判空会拿到 NULL，改用 cardinality(tags) = 0。

坑四，以为 @> 会计算重复次数，其实 ARRAY[1] @> ARRAY[1,1] 为真。坑五，数组元素含 NULL，写入前就该禁止。坑六，以为 GIN 服务位置查询，tags[1] = 'postgres' 得靠表达式索引。坑七，频繁局部更新导致膨胀，高频变更集合请拆子表。坑八，过度使用多维数组——很多应用的二维结构实际是明细行或 JSON 文档，不要为了「看起来像矩阵」牺牲约束和可演化性。

这八条有个共同点：它们都不是语法错误，而是把 array 当成了别的东西——当成了约束、当成了空集合、当成了多重集合、当成了子表。回到第二页那条边界，绝大多数坑自动就消失了。

最后，把架构师、DBA、业务开发者三个角色的动作连成闭环。

PAGE 22 / 22
上线不是建一个字段就结束

三个视角各管一段。架构师：把 array 定位成行内小集合，元素有属性、状态、创建时间、来源、权限、审计、外键时直接拆子表；强约束写显式 CHECK；无序集合写入前去重排序。DBA：对 @>、&& 高频查询建 GIN，建完 ANALYZE，观察 pg_stats.most_common_elems，元素分布偏斜就提高统计目标，同时盯索引大小、写入延迟、autovacuum、WAL、pending list 和 TOAST 膨胀。业务开发者：用参数绑定传数组而不是拼字符串，默认空数组，写入前去重并规范大小写，成员查询优先写 @> 或 &&。

这六步要连成闭环：建模、约束、索引、统计、执行计划验证、后续演化。原文那句提醒很到位——否则数组很容易从「简化模型」变成「难拆的数据包袱」。

回到开头：array 适合保存一行内部的小规模、同类型、多值属性。优势是表达紧凑、类型明确、成员查询可索引；代价是数组整体仍是一个列值。现在这句话里的每一个词，应该都对应着我们走过的某一层地层了。剩下的问题留给大家：标签需要创建人和置信度时怎么迁移？每行 5 个元素和 500 个元素，GIN 的写入成本与查询收益会怎么变？什么时候该从 array 演化成子表，迁移时如何保持读写兼容？
