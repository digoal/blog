PAGE 01 封面：七阶地层总览与核心命题

大家好，欢迎来到数据库筑基课的 PostgreSQL 物理复制专题。很多工程师第一次搭 PG 主备时，脑子里默认物理复制就是「把主库的数据文件实时同步到备库」。这句话其实只对了一半。如果我们掀开 PostgreSQL 的地层剖面往下看，你会发现最底层的基座是合法的 base backup、$PGDATA 目录以及 timeline 历史；而在基座之上真正流动的唯一事实来源，其实是 WAL 日志，也就是 Write-Ahead Log。主库先把每一次变更顺序追加成 WAL，再通过 walsender 沿着复制协议发给备库的 walreceiver，备库落盘刷盘后交由 startup 进程按顺序重放，最终长出一个和主库二进制兼容、事务严格一致的整库副本。今天所有的推演，我们都紧扣 PostgreSQL 本地官方文档（比如 high-availability.sgml、protocol.sgml）以及核心源码（walsender.c、walreceiver.c、slot.c、syncrep.c）和四个官方 recovery 测试用例来实证。先抛第一个根本问题：既然最终都要得到一份一模一样的数据文件，为什么 PG 不直接拷贝数据文件，而偏要绕道 WAL 呢？我们看下一页。

PAGE 02 问题本质：为什么复制 WAL 而非数据页

承接刚才的问题，咱们来推演一下如果不走 WAL，数据库复制会遇到什么死胡同。左边的路径 A 是只靠周期性全量备份，这很直观，但 RPO 完全被备份间隔锁死，一旦主库宕机，最后一次全备之后的事务全丢；路径 B 是直接去拷贝数据文件，听起来实时，但数据库文件从来不是静态文件——后台写入进程、Checkpoint、hint bit 标记、FSM 空闲空间映射、VM 可见性映射，还有事务状态文件每时每刻都在并发变化，直接拷文件必然遇到页撕裂和事务不一致。PostgreSQL 给出的解法非常干净：既然主库本地提交路径本来就以 WAL 作为崩溃恢复的唯一事实来源，那只要备库从一个合法的 base backup 起步，按顺序重放之后所有的 WAL，就能精确恢复到任意一致的 LSN。这一转化直接带来右侧的四项硬收益：恢复模型完全同源、顺序追加日志极适合网络传输和归档追赶、重放同时还能打开 Hot Standby 承接只读查询、并且能把同步提交的确认点自然延伸到备库。但做架构必须同时把五项代价摊在桌面上：物理复制只能整库同版本、备库恢复态不能独立写入、网络和重放慢会直接影响 RPO 与提交延迟、复制槽可能把主库 pg_wal 拖爆，而且物理复制本身不包含自动故障切换。明白了为什么必须走 WAL 流，下一步我们把主备两端的进程和组件完整拼成一张架构蓝图。

PAGE 03 整体架构：主备进程与 WAL 连续性

这张架构蓝图把物理复制最核心的十个角色放到了同一个坐标系里。先看左侧主库 Primary：业务写事务落盘到本地 pg_wal 后，每条来自备库的复制连接，主库都会分配一个专属的 walsender 进程，对应我们在 pg_stat_replication 里看到的每一行。重点看主库下方两个常被误解的组件——Replication Slot 物理复制槽和 WAL Archive 归档。很多同学以为槽和归档是在「帮着复制数据」，其实不是，它们保护的是追赶所需的 WAL 连续性：槽防止主库把备库还没拿走的 WAL 提前删掉，归档则提供长时间离线后的回补后路。再看右侧备库 Standby：数据目录下只要放了 standby.signal，实例启动就进入恢复模式。walreceiver 通过复制协议把 WAL 拉到本地 pg_wal 并刷盘，同时沿着图里那条金色虚线不断向主库回报 write、flush 和 apply 的 LSN 进度；而真正让数据对 Hot Standby 只读查询可见的，是最后面的 startup 重放进程。底部红框再强调一遍语义边界：物理复制和逻辑复制虽然都可能用到复制协议和复制槽，但物理复制是整库物理记录恢复，解决 HA 和读扩展；表级同步、跨版本升级或异构结构，那是逻辑复制的领地。全景看清楚了，接下来我们直接钻进源码，先看主库侧的 walsender.c 是怎么工作的。

PAGE 04 上游机制：walsender 协议与状态机

打开源码 postgres/src/backend/replication/walsender.c，文件头就把定位写透了：walsender 是一个不处理普通 SQL 的特殊 backend，它只听得懂 repl_gram.y 里定义的一小组复制协议命令。大家看左边这六条核心命令：连上来先 IDENTIFY_SYSTEM 核对 system identifier 和当前 timeline，防止接错库；接着按需创建或读取物理复制槽、拉取 TIMELINE_HISTORY 或用 BASE_BACKUP 拉基础备份；最后发出 START_REPLICATION，指定起点 LSN 和 timeline。右半边就是 StartReplication() 的完整推演链。第一步，如果指定了 slot，先 acquire 并且硬性禁止拿 logical slot 来做物理复制；第二步，选择发送的 timeline——注意这里源码留了一个伏笔：如果当前节点自己也在恢复中，说明它正扮演级联复制的中间备库；第三步，校验请求的起点不能超过本机已经 flush 的 WAL。校验通过后，walsender 发送 CopyBothResponse 进入双工循环，先把状态置为 catchup，调用 WalSndLoop(XLogSendPhysical) 从磁盘追发滞后的 WAL；直到彻底追平、没有待发数据时，才把状态切为 streaming。记住这个 catchup 到 streaming 的切换：我们在 pg_stat_replication 里盯状态、以及后面同步复制判断备库能不能参与提交确认，都高度依赖这个状态。主库发完，我们立刻跟到网络另一头，看 walreceiver.c 怎么接住这条流。

PAGE 05 下游机制：walreceiver 刷盘与级联唤醒

来到备库侧的 walreceiver.c。首先注意一个源码级细节：当 startup 进程觉得该开始流复制时，它会通知 postmaster 拉起 walreceiver；但 walreceiver 不会自己去读建立连接所需的 GUC 配置，而是严格从共享内存读取 startup 传下来的 conninfo、slotname、receiveStart 和 receiveStartTLI。图的上半部分是 WalReceiverMain() 的启动六步：动态加载 libpqwalreceiver，目的是让数据库核心进程不直接强链接 libpq；连上上游后立刻执行 IDENTIFY_SYSTEM 校验两边是不是同一个集群；检查 timeline 并补拉缺失的 timeline history 文件；如果配置了临时槽就创建临时物理槽；最后调 walrcv_startstreaming() 进入接收循环。下半部分是消息主干 XLogWalRcvProcessMsg()，它把收到的包分成两路：遇到 Keepalive 保活包，就更新上游最新的 WAL end，如果主库要求回复则立刻回传进度；遇到真正的 WALData，先由 XLogWalRcvWrite() 按段写入本地文件、更新 writtenUpto，再由 XLogWalRcvFlush() 执行 fsync、更新共享内存里的 flushedUpto。最妙的地方就在右侧的双重唤醒箭头：flushedUpto 一推进，walreceiver 不只唤醒本地的 startup 进程继续重放，在允许级联复制时还会同时唤醒本机的 walsender！这就是为什么一个中间备库刚刷完上游的 WAL，马上就能继续转发给下游备库。现在发送端和接收端全打通了，我们把整条链路拉直，用下一页的交互模型亲手走一遍四个 LSN 和同步提交闸门。

PAGE 06 交互演练 1：WAL LSN 四段管线与提交闸门

这一页我们配了一个可交互的 WAL LSN 管线模拟器。大家可以先看这五个横排节点：主库本地落盘的 current_wal_lsn、主库发出的 sent_lsn、备库写进操作系统的 write_lsn、备库 fsync 落盘的 flush_lsn，以及最后 startup 重放完毕的 replay_lsn。为什么强调用四段管线来理解物理复制？因为你只要切换上方工具栏里的 synchronous_commit 级别，再点「单步推进」或「自动演示」，就能直观看到那个陶橙色的 WAL 数据包走到哪一道闸门，主库才会给客户端返回提交成功。选 local 或 off 时，数据包刚落完主库本地盘就放行，异步最快但有丢数据窗口；选 remote_write，数据包传到备库写进 OS 缓存就放行，注意此时备库还没 fsync，备库操作系统宕机照样丢；默认同步 on 必须等到备库 fsync 完成推进 flush_lsn 才放行；而 remote_apply 则要一直等到 startup 重放完毕、事务对只读查询可见才释放主库提交，代价是把备库的重放延迟直接算进主库响应时间。明白这条管线后，下一个现实问题马上就来了：流复制总有网络抖动或断开的时候，备库断流之后是不是直接就废了？我们看下一页的恢复循环模拟。

PAGE 07 交互演练 2：备库三层恢复循环与提升

物理复制最容易被忽略的底层事实，就是官方文档反复强调的这段恢复循环：备库找下一段 WAL 时，网络流复制从来不是唯一来源，甚至不是第一顺位。大家可以点击上方工具栏切换三个场景，跟着高亮状态走一遍。只要数据目录存在 standby.signal，备库从 base backup 启动后就进入虚线框里的三层循环：第一步先调 restore_command 去归档里找 WAL，这是离线很久之后的长追赶后路；归档没有，第二步查本地 pg_wal，保证备库重启后不用重复拉取已经收到但还没重放的 WAL；本地也没有，第三步才通过 primary_conninfo 连上游做低延迟流复制。如果选「2. 断流回退归档」，你会看到流复制一旦断开，备库不会报错退出，而是顺着下方陶橙色虚线回到循环起点重新从归档和本地 pg_wal 重试，直到网络恢复或者被管理员 promote。选「3. Promote 提升切换」则展示了退出循环的唯一边界：提升前备库会尽量把已有归档和本地 WAL 应用完，然后切换新的 timeline 并生成 timeline history 文件，正式成为可写主库。这就是为什么生产环境要把「归档 + 流复制 + 复制槽」组合起来用。说到复制槽，它到底怎么保护 WAL，又为什么经常把主库磁盘打爆？下一页我们来实操模拟。

PAGE 08 交互演练 3：物理复制槽与爆盘边界

复制槽本质上是上游在 $PGDATA/pg_replslot 下持久保存的一份消费进度，源码在 slot.c 里。它的核心字段叫 restart_lsn——只要槽还存在，主库就把 restart_lsn 钉死成「绝对不能删」的下界，保证备库短暂离线后还能原位续传。但可靠追赶和主库爆盘其实是同一件事的两面。我们可以用上方的模拟器还原官方测试 019_replslot_limit.pl 的完整过程：默认 max_slot_wal_keep_size 设为 20GB，此时点几次「主库写入 WAL」，模拟备库失联而主库持续写入。你会看到保留带一路逼近 20GB 红线，pg_replication_slots 里的 safe_wal_size 不断缩小；一旦越过 20GB，槽的 wal_status 先进入 extended、再滑入 unreserved 危险区；这时候只要点一下「触发 Checkpoint」，主库回收超限 WAL，槽立刻变成 lost，备库日志就会报 wal_removed 彻底失效。反过来，如果你把上限切到 -1 也就是默认无限保留，槽永远不会 lost，但主库的 pg_wal 会被失联备库活活拖爆。所以工程上的正确动作非常清晰：必须给 max_slot_wal_keep_size 设合理的非无限上限，同时监控 wal_status、safe_wal_size 和 inactive_since，把未知的爆盘灾难变成可控的告警边界。WAL 连续性和空间边界都拿捏住了，接下来看同步复制：主库怎么在多个备库之间做提交仲裁？

PAGE 09 交互演练 4：同步复制 FIRST 与 ANY 仲裁

打开 syncrep.c，文件头给出一条非常反直觉但极其优雅的设计：同步复制的等待和释放逻辑全在主库单边完成，备库根本不知道主库上哪笔事务是关键资金写入、哪笔是普通日志，备库唯一要做的就是老老实实持续上报自己的 write、flush、apply 位置。主库根据 synchronous_standby_names 的两种现代语义来仲裁，这也是官方测试 007_sync_rep.pl 重点验证的逻辑。大家可以在上方工具栏直接点击测试：在 FIRST 2 (s1, s2, s3) 优先级模式下，排在前面的 s1 和 s2 成为 sync，s3 是 potential 替补；如果你点一下把 s1 设为离线，s3 会立刻顶上来变成 sync，提交照常放行。切到 ANY 2 (s1, s2, s3) 法定人数模式，三个备库都是 quorum 候选，只要任意两个达到目标 LSN 就释放提交，抗单节点抖动能力更好。但最关键的演示是：无论哪种模式，只要你把其中两个备库都点离线，剩下在线备库不足 2 个，左侧主库仲裁器立刻变成红色 WAITING 阻塞状态！同步复制的风险绝不只是「慢一点」，候选数量一旦不够，所有同步提交都会卡死。因此生产上要么备足候选节点，要么故障时有预案立刻下调同步要求并 reload。到这里，物理复制的核心内核已经全部拆解完毕。下一步我们跳出来做横向对比：它和归档、逻辑复制、存储复制各自站在什么位置？

PAGE 10 横向对比：四种复制方案边界矩阵

架构选型最怕张冠李戴，这张矩阵把四种常见复制方案拉到六个维度上直接对齐。先看前两列：物理流复制按 WAL 记录实时发送，延迟低，负责主备 HA 和读扩展；文件级 WAL log shipping 按完整的 WAL segment 文件归档，延迟取决于段写满或 archive_timeout，但它极其稳定、适合长时间离线追赶。这两者不是二选一，生产里最稳的组合永远是同时开启——流复制扛低延迟，归档扛长缺口恢复。再看第三列逻辑复制：它按表和发布订阅同步逻辑变更，最大优势是支持跨主版本升级、异构表结构和选择性同步，而且订阅端可以有本地写入；但它有 DDL、序列和写入冲突的限制，不适合直接当作完整的高可用 failover 替代方案。第四列存储层复制工作在块设备或文件系统层，对数据库内部事务感知弱，必须极其小心地处理写顺序、一致性快照和脑裂边界。最后划一句红线：复制槽保护的是上游不要过早删除 WAL，如果主库本地磁盘直接物理损坏，复制槽救不了你，它绝对不能替代异地归档。定好选型之后，上线运行最核心的问题就是可观测性：到底怎么判断物理复制跑得好不好？我们看下一页。

PAGE 11 效果评估：四段 LSN 差值与收益代价

千万不要用一句含糊的「我们复制延迟小于 1 秒」来汇报物理复制的健康度。真正靠谱的观测方法，是查主库的 pg_stat_replication 和备库的 pg_stat_wal_receiver，按图上方这四段 LSN 字节差逐段排障。第一段，pg_current_wal_lsn() 减 sent_lsn 变大，说明主库写 WAL 比发得快，要排查 walsender、网络带宽或下游背压；第二段，sent_lsn 减 write_lsn 变大，瓶颈卡在网络传输或者备库 walreceiver 写操作系统慢；第三段，write_lsn 减 flush_lsn 变大，直接指向备库磁盘 IO 慢、WAL fsync 跟不上；第四段，flush_lsn 减 replay_lsn 变大，说明备库 startup 重放跟不上，或者备库上的只读长查询正在和恢复重放打架。中间黄色提示条特别重要：很多人把 write_lag、flush_lag、replay_lag 当成「还要多久能追平」，其实它们只衡量最近一段 WAL 到达对应阶段的耗时；另外一定要盯紧 pg_replication_slots.safe_wal_size，接近 0 或变负就是红灯。下半部分的五张卡片把异步 HA、同步 HA、读扩展、灾备追赶和级联复制的收益与代价并排摆了出来——数据库架构没有免费午餐，每拿一项收益，都要清楚付出的对应代价。理论和监控都齐备了，下一页我们直接看标准搭建模板和官方源码测试怎么跑。

PAGE 12 实操与实证：搭建模板与 Recovery 测试

这一页分左右两块：左边是可以直接落地的标准搭建模板，右边是 PostgreSQL 官方源码里最值得读的四个 recovery 测试用例。先看左边四步闭环：第一步在主库创建带 REPLICATION 权限的 repl 角色，并用 pg_create_physical_replication_slot 创建物理槽，注意把 immediately_reserve 设为 true，建槽同时立刻保留 WAL；第二步在 postgresql.conf 里配好 wal_level=replica、max_wal_senders、max_replication_slots、wal_keep_size 以及关键的 max_slot_wal_keep_size='20GB'，同时在 pg_hba.conf 用 scram-sha-256 放行 replication 伪库连接；第三步在备库执行 pg_basebackup，带上 -Fp -Xs -P -R -S standby_a，-R 参数会自动生成 standby.signal 和连接信息，记得再补上 restore_command 接好归档后路；第四步双端查视图验真：主库看 pg_stat_replication 和 pg_replication_slots，备库看 pg_is_in_recovery() 和 pg_stat_wal_receiver。右边四个官方 Perl 测试脚本在 postgres/src/test/recovery/t/ 目录下，如果你本地编译了 PG 源码，非常建议在临时目录或 CI 里跑一遍：001 验证流复制与级联只读，007 验证 FIRST/ANY 切换，019 验证槽超限进入 lost，047 验证 Checkpoint 期间推进物理槽的安全性。搭建和测试都清楚了，下一步我们把整套知识落到三个具体岗位的日常工程守则上。

PAGE 13 最佳实践：三类角色守则与场景边界

物理复制在生产里出事故，往往不是因为某个参数拼错了，而是架构师、DBA 和业务开发者三方的认知边界没对齐。先看数据库架构师：第一原则是先定义业务 RPO 和 RTO，再选异步还是同步，不要为了「看起来安全」一刀切全业务同步；核心写入可以用 on 或 remote_apply，可补偿写入用 local 或 off；跨机房同步必须把网络 RTT 算进提交延迟；而且必须补齐外部 HA 仲裁、VIP 或连接串重连、脑裂防护和旧主重建的完整闭环。再看 DBA：每个备库必须有唯一的 application_name，否则同步复制选主和监控都会乱套；每个物理槽都要有明确的 owner 和 max_slot_wal_keep_size 上限，长期离线备库果断评估重建而不是无限攒 WAL；开了 hot_standby_feedback 减少只读冲突时，必须同步盯紧主库表膨胀；failover 之后旧主必须走 pg_rewind 或重做 base backup，绝不能直接回写。再看业务开发者：备库就是只读节点，异步备库读到旧数据是正常行为，读后写一致性要靠路由、LSN 等待或按事务 remote_apply 来解；连接串里的 target_session_attrs 只是辅助寻址，不是 HA 仲裁；大报表和长事务要做好管控，避免撞上恢复冲突。底部两栏划清了适用与不适用边界：同城 HA、读分流、备份卸载和级联复制是物理复制的主场；而少数表同步、多主写入、跨大版本混跑，请果断转向逻辑复制或其它架构。最后一页，我们用一份十坑排雷清单和五个思考题收尾。

PAGE 14 排雷与延展：十大常见坑与五个思考题

来到最后一页，我们把原文总结的十大生产高频坑归成了三个域，方便大家上线前逐条核对。第一域是 WAL 与复制槽：只开流复制却既不配归档也不用槽，一旦落后就只能重做 base backup；开了槽却不设 max_slot_wal_keep_size，备库一失联主库 pg_wal 直接爆盘；还有人误把 wal_keep_size 当成精确保留上限，其实它只是最小保留量，落后照样断。第二域是同步复制与提交级别：候选备库不够导致提交无限卡死；忘了配唯一的 application_name；把 remote_write 当成持久落盘，忘了它没做 fsync；以及把 remote_apply 当成免费的强一致读，结果把备库重放抖动全导进了主库延迟。第三域是切换运维与底层认知：failover 后忽略 timeline history 或放任旧主回写；长只读查询引发恢复冲突或在开启 hot_standby_feedback 后拖垮主库 vacuum 导致膨胀；最后也是最致命的一条——千万别以为有了物理复制就不用做备份，误删表和逻辑坏数据会被物理复制分毫不差地同步到所有备库，独立备份和 PITR 永远不可或缺。右侧留了五个进阶架构思考题，涵盖按事务分级同步、跨地域级联权衡、replay_lag 为 NULL 的监控语义、槽进 unreserved 时的止损决策，以及写后立即可见的路由策略。建议大家结合自己的业务负载，回到 PG 源码和测试集里逐一验证。今天这节 PG 物理复制筑基课就到这里，谢谢大家！
