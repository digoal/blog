P.01 PostgreSQL shared buffer 管理

大家好，今天我们一起进入数据库筑基课的核心专题——PostgreSQL 的 shared buffer 管理。很多应用开发者甚至不少运维同学，一提到 shared_buffers，第一反应就是 postgresql.conf 里的一个内存大小参数，觉得调大一点缓存就多一点、查询就快一点。但如果我们把 PostgreSQL 的存储内核像地层剖面一样切开来看，你会发现 shared buffer 绝对不是一块普通的内存池。看这张地层剖面图：从最上层的 SQL 扫描算子往下，依次经过 BufferTag 页面身份映射、Pin 和 Content Lock 并发控制、Clock-Sweep 与 Buffer Ring 替换策略、固定大小的 8KB 页面槽位，再到脏页写回和 WAL 先行约束，最底层才与操作系统的 Page Cache 和磁盘交接。本节课的所有结论都直接基于 PostgreSQL 源码目录 src/backend/storage/buffer/ 下的 README、bufmgr.c、freelist.c、buf_table.c、buf_init.c 以及官方文档，不凭空猜测，也不编造数字。那么，一切机制都要从问题出发：操作系统明明已经有 Page Cache 了，PostgreSQL 为什么还要大费周章地自己维护一套受控的共享缓存池？我们看下一页。

P.02 为什么不能只靠操作系统读 8KB 页面？

数据库访问数据，真正难的地方从来不是「怎么把一个 8KB 的页面从磁盘读进内存」，而是围绕这个页面并发读写时暴露出的五个底层矛盾。第一个矛盾，多个 backend 进程可能同时读同一个热点页，总不能每个进程都去磁盘读一份，所以需要用 BufferTag 和 SharedBufHash 建立全局共享映射。第二个矛盾，A 进程正在扫描这个页面里的元组，B 进程绝不能半路把这个槽位换给别的磁盘块，这就引出了 Pin 和 Content Lock。第三个矛盾，页面被改脏之后，必须标记为 BM_DIRTY，而且写回数据文件之前必须确保对应的 WAL 已经落盘，操作系统 Page Cache 根本不懂数据库的 WAL 顺序。第四个矛盾，一旦业务跑起大表全表扫描、VACUUM 或 COPY，这些只读一遍的冷数据不能把 OLTP 的核心热页全部冲出缓存，因此需要 Clock-Sweep 和 Buffer Ring。第五个矛盾，脏页写回不能全部压在前台查询身上，也不能在某个时间点形成写 I/O 尖峰，必须靠 bgwriter 和 checkpointer 协同削峰。但同时代价也很明确：shared_buffers 越大，单个 checkpoint 周期内可能累积的脏页越多，而且 PostgreSQL 依然依赖操作系统的 Page Cache。所以官方文档在 config.sgml 第 1785 到 1819 行给出了一条非常务实的经验边界：专用数据库服务器可以从内存的 25% 起步，超过 40% 通常未必更好，而且调大 shared_buffers 往往需要同步提高 max_wal_size 来摊平写回过程。带着这五个问题，我们下沉一层，看看内核究竟用哪四个核心数据结构把这套机制撑起来的。

P.03 Shared Buffer 的逻辑到物理四层映射

应用开发者看到的是 SQL，DBA 看到的是命中率和 I/O，而内核里真正承载这些行为的，就是屏幕上这四组紧密咬合的数据结构。最左边是 BufferTag，定义在 buf_internals.h 的 150 到 168 行。它用 tablespace、database、relation、fork 和 block number 五个字段，唯一标定「当前缓存的是哪一个磁盘块」。中间的 SharedBufHash 定义在 buf_table.c，负责把 BufferTag 映射到具体的槽位编号 buf_id。注意一个很关键的实现细节：这个哈希表本身并不自带锁，调用者必须先按 Hash 分区拿到对应的 BufMappingLock。拿到 buf_id 之后，就能直接按数组下标定位到两个一一对应的数组：一个是 BufferDescriptors，存放每个槽位的 BufferDesc 元数据，记录 refcount、usage_count、BM_DIRTY、BM_VALID、I/O 状态和内容锁；另一个是 BufferBlocks，真正存放每个 8KB 的页面内容。根据 buf_init.c 的 74 到 140 行，PostgreSQL 在启动时会按 NBuffers 一次性把 BufferDescriptors、BufferBlocks、用于 I/O 等待的 BufferIOCVArray，以及给 Checkpoint 排序用的 CkptBufferIds 全部申请完毕。这也解释了为什么 shared_buffers 是一个启动级参数——运行期间槽位总数是锁死的，修改它必须重启数据库。既然静态结构已经铺开，接下来我们让数据流动起来，亲自走一遍 ReadBuffer 的命中与未命中路径。

P.04 ReadBuffer：先查 Hash，Miss 再找 Victim

这一页我们内置了交互式路径演示，你可以切换「缓存命中」和「缓存未命中」两种场景，单步或自动观察锁与状态的流转。所有普通读取请求最终都会进入 bufmgr.c 的 ReadBuffer_common 函数。第一步它会先分流：如果是临时表，直接走进程私有的 Local Buffer，不参与共享内存争用；如果是普通共享表，就进入 BufferAlloc。在 BufferAlloc 里，内核先构造 BufferTag，算出哈希值找到对应的 BufMappingLock 分区，加上共享映射锁去查 SharedBufHash。先看绿色快路径——如果命中，事情非常简单：给这个 buffer 加上 Pin（也就是 refcount 加一），立刻释放共享映射锁，直接返回。这就是为什么高并发热页读取可以做到极低延迟。再看陶橙色的慢路径——如果未命中，代价就陡然上升：先释放共享映射锁，调用 GetVictimBuffer 去挑一个可复用的槽位；如果挑出来的 Victim 恰好是脏页，还得先把它 Flush 落盘。拿到干净的槽位后，重新申请排他 BufMappingLock，把新的 BufferTag 到 buf_id 的映射插进哈希表，设置 BM_TAG_VALID，释放映射锁，最后才置上 BM_IO_IN_PROGRESS 发起磁盘读 I/O，读完标为 BM_VALID 并返回。这里一定要留心一个极易混淆的点：无论是 Hit 还是 Miss，BufferAlloc 返回给你的只是一个「已 Pin、不会被别人换走」的页面，绝不代表你可以直接往里面写数据。读写页面内容，必须遵守下一页的并发访问规则。

P.05 Pin 护身份不被换走，Content Lock 护内容并发安全

PostgreSQL 源码里的 storage/buffer/README 第 12 到 111 行，把 shared buffer 的并发规则写得清清楚楚，核心就是把两套保护彻底拆开：Pin 和 Content Lock。第一道防线是 Pin，本质上是共享引用计数 refcount。它的唯一职责是保护「页面身份」——只要有人 Pin 住这个槽位，替换算法就绝不能把它回收给别的磁盘块。但反过来，未 Pin 的页面指针绝对不能继续使用，因为它随时可能被换走。第二道防线是 Content Lock，它是一种短期持有的内容锁，分为 Shared、Share-Exclusive 和 Exclusive 三级，用来保护页面内部字节和元组的并发一致性。看图下方这五种典型操作，精度要求层层递进：扫描页面或检查元组提交状态，需要 Pin 加 Shared 锁，允许多进程并发读；更新 Hint Bits 这类非关键缓存标记，或者写出脏页 FlushBuffer 时，需要 Pin 加 Share-Exclusive 锁，防止写出中途页面被修改导致校验和异常；如果是插入元组或修改 xmin、xmax，则必须持有 Pin 加 Exclusive 排他内容锁；而最严格的是物理删除元组或页面整理 Compact，不仅需要 Exclusive 内容锁，还必须确认 refcount 等于 1，也就是全系统没有任何其他 backend 正 Pin 着这个页面。理解了这两套防线，下一个问题自然浮出水面：当共享内存槽位全部占满、发生 Cache Miss 时，内核怎么在百万级并发下快速找到一个 refcount 为 0 的 Victim 槽位？我们看下一页的 Clock-Sweep 模拟器。

P.06 Clock-Sweep：用 usage_count 换取高并发替换速度

为什么 PostgreSQL 默认不用教科书里经典的严格 LRU，而是选了 Clock-Sweep？答案只有四个字：并发速度。严格 LRU 每次页面命中都要把节点挪到全局链表头部，在高并发多核环境下，全局链表锁瞬间就会成为性能瓶颈。PostgreSQL 在 freelist.c 的 StrategyGetBuffer 里用了一个极其轻量的环形扫描指针 nextVictimBuffer，配合每个槽位上的 usage_count 来近似热度。你可以点击上方的「单步推进」亲自观察：指针每扫到一个槽位，先看它有没有被 Pin——被 Pin 就直接跳过；再看它的 usage_count 是否大于 0——如果大于 0，就把它减一，给它留一次机会然后跳过；只有遇到 refcount 为 0 且 usage_count 为 0 的槽位，才用原子 CAS 抢占 Pin 并作为 Victim 返回。注意 buf_internals.h 第 136 到 147 行的源码注释：BM_MAX_USAGE_COUNT 设为 5，这是一个刻意权衡的折中值——设得太大虽然更接近 LRU，但指针可能需要绕很多圈才能找到可用槽位，反而拖慢分配速度。现在你还可以点击「模拟大表顺序扫描」，对比「默认 Clock-Sweep」和「Buffer Ring 隔离模式」的差别：一旦一次性大扫描涌进来，如果没有 Ring 限制，它会迅速消耗热页的 usage_count；而开启 Ring 后，大扫描被关在右侧的小窗口里循环，左侧 OLTP 热页毫发无损。下一页我们把 Buffer Ring 的三种策略展开讲透。

P.07 Buffer Ring：把一次性大扫描锁死在极小环内

刚才在模拟器里我们直观看到了 Buffer Ring 的威力，现在从源码层面把它的三种典型应用场景对齐。在 freelist.c 的 GetAccessStrategy 和 GetAccessStrategyWithSize 中，PostgreSQL 为三类「一次性大吞吐操作」设计了专门的环形策略，并且硬性规定任何 Ring 的槽位数量上限不得超过 shared_buffers 的八分之一，也就是 NBuffers / 8。第一种是大家最常见的大表顺序扫描 Seq Scan，README 第 206 到 231 行说明它传统上使用 256KB 的小环，也就是大约 32 个 8KB 页面。扫完第 32 页，第 33 页直接复用第 1 页的槽位，对整个 shared buffer 的污染几乎可以忽略不计。第二种是 VACUUM 清理任务，它也会遍历大量包含死元组的页面，它的环大小受 vacuum_buffer_usage_limit 参数控制，方便 DBA 在清理速度和在线业务稳定性之间做精细调节。第三种是批量写入，比如 COPY IN 和 CTAS 建表，README 说明它默认使用 16MB 的环，同样受限于 shared_buffers 的 1/8。不过这里有一个非常重要的连锁反应：在批量写入或 VACUUM 过程中，Ring 里的页面会被改脏；当环绕一圈需要复用一个脏页时，就触发了我们下一个核心话题——脏页到底由谁来写回，以及 WAL 先行约束如何守住崩溃恢复的底线。

P.08 脏页写回：三方协作削峰，WAL 先行守底线

很多排查数据库延迟抖动的同学，最容易踩的坑就是把「事务提交」和「数据页落盘」画等号。其实在 PostgreSQL 里，这两件事是解耦的。你可以点击上方的四个路径按钮逐一演练。先看路径 A：页面被修改后，内核调用 MarkBufferDirty 打上 BM_DIRTY 标记，同时页面头部记录了最新的 Page LSN。事务提交时，真正必须同步落盘的是 WAL 日志，只要 WAL 持久化，崩溃后就能从最新 Checkpoint 重放恢复，数据页完全可以留在内存里稍后异步写回。那么数据页最终由谁写回呢？图中间展示的三条并行通道就是三方协作机制。最理想的是路径 B 的 background writer，它会定期沿着时钟指针提前扫描，把「很快就要被复用」的脏页悄悄写回磁盘，把写 I/O 从前台查询路径里剥离出去。其次是路径 C 的 checkpointer，按 checkpoint_timeout 和 checkpoint_completion_target，把整个周期的脏页均匀摊平刷盘，并写下 Checkpoint WAL 记录，推进崩溃恢复的起点。最需要警惕的是路径 D：如果后台写得不够及时，前台业务进程在 GetVictimBuffer 找槽位时撞上了脏页，就不得不自己拿 Share-Exclusive 锁调用 FlushBuffer 同步刷盘，用户查询延迟立刻抖动。而且无论哪条路径，都必须经过顶部的生死红线——XLogNeedsFlush 校验：如果这个数据页对应的 WAL 还没刷盘，数据页绝对不能先落盘，必须先刷 WAL 或者拒绝复用这个脏页。到这里，shared buffer 内部的读、锁、换、写四大闭环全部打通了。接下来我们跳出内核，把它放到整个系统架构里，与操作系统 Page Cache 和应用缓存做一次清晰的横向对比。

P.09 Shared Buffer、OS Page Cache 与应用缓存并非替代关系

在实际架构评审中，经常有人问：既然操作系统有 Page Cache，业务层又有 Redis 这类应用缓存，那 shared buffer 到底该占多大比重？看这张横向对比矩阵，答案其实非常清晰——这三层缓存管的根本不是同一类语义，它们不是三选一的替代品，而是上下咬合的协作层。PostgreSQL 的 shared buffer 负责「数据库语义」：它按 BufferTag 精确识别 relation、fork 和 block，用 Pin 和 Content Lock 维护 MVCC 并发安全，并且死守 WAL 先写规则和 Checkpoint 边界。操作系统的 Page Cache 负责「文件系统语义」：它只认文件 inode 和偏移量，擅长跨进程块缓存、顺序预读和设备队列调度，但它完全不理解什么是元组可见性，也不知道数据库的 WAL 顺序。而应用侧缓存负责「业务语义」：它缓存的是拼装好的业务对象、权限判断、聚合结果或幂等 Token，目标是减少 SQL 调用次数，绝不能拿它去替代数据库的一致性机制。正因为 PostgreSQL 明确依赖操作系统 Page Cache 做二次缓冲和预读，官方文档才反复提醒：把绝大部分内存都塞给 shared_buffers，反而会挤压 OS 缓存空间、加剧双重缓存并让 Checkpoint 变得异常沉重。既然每一层都有收益也有代价，下一页我们就把 shared buffer 的收益与成本摊开算一笔明白账。

P.10 收益与成本并存：高命中率不等于无延迟抖动

做工程决策最忌讳只谈收益不谈代价。左边青绿色这五条，是 shared buffer 给系统带来的核心红利：热页共享大幅减少物理读、Pin 与内容锁守住并发正确性、bgwriter 与 Checkpointer 摊平写 I/O、Clock-Sweep 与 Ring 保护核心工作集，以及与 WAL 联动保障崩溃可恢复。但右边陶橙色这五条固有代价同样真实存在：同一份数据可能同时占着 shared buffer 和 OS Page Cache 造成双重缓存；高并发访问同一热点页会触发 Hash 分区锁或 Content Lock 争用；缓存越大，单次 Checkpoint 攒下的脏页越多；当真实工作集远大于内存时，再精妙的替换算法也只能减损而无法消灭磁盘 I/O；并且参数之间高度联动，动了 shared_buffers 就得联动看 max_wal_size 和 bgwriter。所以我特别想强调底部这条诊断铁律：千万不要迷信「缓存命中率 99% 就一切正常」。在真实的 OLTP 故障里，我们见过太多命中率高达 99.5% 却依然频繁超时的案例——真凶往往不是物理读，而是 Checkpoint 写回尖峰、WAL Flush 卡顿或者热点页的 Content Lock 排队。反过来，一个分析型查询命中率不高，但只要顺序读配合 OS Page Cache 吞吐平稳，完全在可接受范围内。既然不能只看命中率，那生产环境里到底该怎么看？下一页给出四组实操 SQL，帮你搭起完整的观测闭环。

P.11 四组核心 SQL：从参数基线到等待事件闭环

性能诊断讲究实证，不看证据拍脑袋调参是最危险的。这一页整理的四组 SQL 可以直接在你的测试或生产只读观测中按顺序执行。第一步先定参数基线：同时查看 shared_buffers、max_wal_size、checkpoint_timeout 和 checkpoint_completion_target，把缓存容量和写回窗口放在一起看。第二步用 pg_buffercache 扩展做抽样透视：关联 pg_class，看前 20 名到底是哪些表和索引占着 shared buffer，它们的脏页比例高不高，大扫描跑完之后核心热点表有没有被挤出去。记住这里是抽样诊断，不要做成每秒高频轮询。第三步看写回来源：查 pg_stat_bgwriter、pg_stat_checkpointer 和 pg_stat_io。重点对比 client backend 自己写的页数和后台写的页数——一旦前台写脏页偏多，用户侧延迟就会抖动，需要回头检查 bgwriter 是否太保守、或者 Checkpoint 周期是否过密。第四步聚合 pg_stat_activity 里的等待事件：如果看到大量 BufferIO、BufferPin 或者 LWLock BufferMapping 等待，就说明问题出在访问路径、热点争用或替换压力上，绝不能简单归结为「内存不够大」。有了这四组可落地的诊断证据，下一步就是分角色协同治理了。

P.12 三方协同治理：边界规划、参数联动与访问克制

shared buffer 出了问题，单靠 DBA 调几个参数往往治标不治本，需要架构师、DBA 和业务开发者三方站在各自的位置上做对动作。对数据库架构师来说，核心是「定边界、做隔离」：把 shared buffer 当作一致性与性能边界而非业务缓存；在设计负载时，把 OLTP 热点请求和报表大扫描、VACUUM、建索引明确隔离开，给批处理划定维护窗口；读多系统盯热页驻留，写多系统盯脏页写回周期。对 DBA 来说，核心是「守基线、重联动」：shared_buffers 从 25% 起步，把「超过 40% 未必更好」作为经验护栏；调大缓存后务必联动观察 max_wal_size、Checkpoint 日志和前后台写比例；把 pg_buffercache 当听诊器抽样用，而不是当心电图无限高频扫。对业务开发者来说，核心是「控扫描、减放大」：高峰期严禁无条件全表扫描，分页、归档和报表必须带边界条件；索引不是越多越好，多余索引会直接放大写入时的脏页数量，而缺索引会放大读页数量；控制长事务避免拖垮 VACUUM 清理；批量写入尽量走 COPY 和分批提交，不要用海量单行事务去轰炸 buffer manager 和 WAL。但还有一个前提：在动手优化之前，我们必须先确认眼前的问题究竟是不是 shared buffer 引起的。下一页我们来看适用边界和八个最常见的坑。

P.13 先分清真伪瓶颈，再避开八个高频认知误区

工程排障里最浪费时间的，就是对着伪瓶颈猛调参数。上半部分帮大家划清了真伪瓶颈的边界。左边青绿色这五类才是真正适合围绕 shared buffer 优化的场景：OLTP 热点页反复读引发物理读或映射锁争用、写多场景下前台被迫写脏 Victim 导致延迟抖动、Checkpoint 周期刷盘引发 I/O 尖峰、混部大扫描造成缓存污染，以及做内核或扩展开发时的锁管理。而右边陶橙色这五类，千万不要让 shared buffer 背锅：SQL 缺索引或执行计划跑偏导致多扫了几万页；业务层反复查同一份复杂聚合结果却不加应用缓存；总数据集远大于内存且完全随机访问；底层存储写延迟高或 WAL Flush 慢；或者根本是云盘 IOPS 限流和 cgroup 限制。下半部分总结了八个一线最常踩的坑：把 shared_buffers 当成越大越好、只看命中率、以为有 Ring 就能高峰期随便全表扫、把 Pin 和 Content Lock 混为一谈、以为提交就等于数据页落盘、调大缓存却不调 max_wal_size、拿 pg_buffercache 高频全量监控，以及把页面缓存和业务对象缓存混为一谈。避开这八个坑，你就已经超过了绝大多数只会背参数公式的调优方案。最后一页，我们把源码阅读地图和六个进阶思考题留给大家。
