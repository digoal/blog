P01 PostgreSQL 2PC：内核地层剖面与工程边界

大家好，欢迎来到「数据库筑基课」的两阶段提交专题，也就是 2PC。今天我们不讲空泛的分布式概念，而是沿着 PostgreSQL 官方源码——主要是 twophase.c、xact.c、lock.c 和官方 SGML 文档——像做地质勘探一样，把 2PC 从应用协调层一直剖开到磁盘上的 WAL 和 pg_twophase 目录。

先看画面上这七层工程剖面：最上面是外部事务管理器，也就是协调者；往下穿过 SQL 协议层的三条命令——PREPARE TRANSACTION、COMMIT PREPARED 和 ROLLBACK PREPARED；再往下就进入了 PostgreSQL 内核的共享内存、Four Resource Managers 资源管理器、WAL 日志流，以及跨越 Checkpoint 后才会落盘的 pg_twophase 状态文件，最底层是崩溃恢复与 pg_xact 提交状态树。

PostgreSQL 官方文档 xact.sgml 在开篇就点破了一个核心定位：PostgreSQL 的 2PC 模型接近 X/Open XA，它是为外部事务管理器准备的，除非你正在写事务管理器，否则普通业务代码不应该直接手写 PREPARE TRANSACTION。记住这个前提，我们马上来看它究竟解决什么问题。

P02 跨资源原子决定：把不确定窗口收束到受控状态

我们先用一个小实验把问题具象化。假设一次下单要同时写三个独立资源：订单库、库存库、支付账务库，业务硬性要求三边要么全成功，要么全失败。大家可以用图区上方的控制条切换「普通顺序提交」和「2PC 两阶段提交」，并注入不同的故障点来看效果。

如果应用按顺序执行：先提交订单库，再提交库存库，最后提交支付库。单库事务再强，它也只管自己那个 PostgreSQL 实例。一旦订单库提交成功，轮到库存库时网络超时或进程崩溃，订单已经落袋、库存状态未明、支付还没触发——这就是经典的「部分提交窗口」。就算你事后写反向补偿，补偿操作本身也可能失败。

2PC 的破局思路非常朴素：把一次「提交」拆成两段。第一阶段叫 Prepare，每个参与者先把本地事务推进到『我以后一定能提交或回滚』的状态并持久化；第二阶段叫 Finish，协调者收齐所有人的承诺、落盘全局决定后，再统一发 COMMIT PREPARED 或 ROLLBACK PREPARED。

注意一个关键认知：2PC 并没有让网络超时或宕机消失，而是把风险集中到了受协议约束的 Prepared 状态里。代价也很直接——事务在 Prepared 期间继续占着锁和 MVCC 清理边界。所以 2PC 的正确姿势是『短时间悬挂、由事务管理器兜底关闭』，绝对不是给业务做人工暂停按钮。接下来，我们剖开内存，看看 Prepared 事务在 PostgreSQL 里到底长什么样。

P03 不是「提交一半」：Dummy PGPROC 与共享内存结构

很多人初学 2PC 有个典型误解，以为 Prepared Transaction 是「已经提交了一半」。其实完全不是。在 COMMIT PREPARED 执行之前，它写的数据对其他事务依然是不可见的；对发起它的原会话来说，PREPARE TRANSACTION 执行完后甚至有点像 ROLLBACK——原会话立刻没有活动事务了，甚至可以直接断开连接。

那原会话都断开了，数据库怎么还能记住这个事务没结束、怎么继续挡住别人的并发修改呢？答案就在图上的共享内存结构里。PostgreSQL 启动时会根据 max_prepared_transactions 预留一块固定容量的TwoPhaseState 共享内存数组 prepXacts[]——注意，这个参数默认是 0，也就是默认禁用，且只能重启修改。

每一个 Prepared 事务占用一个 GlobalTransactionData 条目，里面记录了小于 200 字节的全局标识 GID、本地真实事务号 FXID、owner、prepare 时的 WAL 起点 prepare_start_lsn，以及 valid/ondisk/inredo 状态位。最精妙的设计是 pgprocno 字段：它指向一个虚拟进程，也就是 Dummy PGPROC。

PostgreSQL 把这个 Dummy PGPROC 挂进全局的 ProcArray，再把原事务的锁全部过户到它名下。这样一来，快照机制、TransactionIdIsInProgress() 和锁管理器根本不需要大改架构，就能像对待普通活跃进程一样感知它。那么，原会话到底是在哪个瞬间把接力棒交出去的？我们看下一页的 9 步内核路径。

P04 EndPrepare 是不可逆边界：先刷 WAL，再脱离原会话

这一页我们顺着 src/backend/access/transam/xact.c 里的 PrepareTransaction()，把 9 个关键步骤拆开来看。大家可以点上方的「单步推进」或「播放演示」，跟着高亮节点走一遍内核主路径。

第 1 步先触发延迟触发器、关闭 portal、处理 ON COMMIT 动作。第 2 步做准入拦截：凡是碰过临时表、导出过快照或者涉及会话绑定状态（比如 LISTEN/NOTIFY）的事务，直接拒绝 Prepare，因为原会话马上要退出，这些会话级状态没法移交给别的会话。

第 3 步 MarkAsPreparing() 去 TwoPhaseState 里占坑，检查 max_prepared_transactions 是否为 0、GID 长度是否超过 GIDSIZE，以及 GID 有没有撞车。第 4、5 步是 StartPrepare() 和一组 AtPrepare_*() 回调，把事务头信息、子事务、待删文件、锁、谓词锁、统计和 MultiXact 全部打包成 2PC state data。

重点看第 6 步——陶橙色标出的 EndPrepare()。它会写入一条 XLOG_XACT_PREPARE WAL 记录并立刻调用 XLogFlush() 刷盘。源码注释在这里写了一句非常有名的话：『If we crash now, we have prepared』。在这之前报错，事务还能直接回滚；一旦刷盘完成，参与者就对协调者做出了不可撤回的承诺，哪怕下一毫秒断电，重启后也必须恢复这个 Prepared 事务。

最后第 7 到 9 步：MarkAsPrepared() 把 Dummy PGPROC 放进 ProcArray，PostPrepare_Locks() 迁移锁，最后清理原进程状态并释放 locking_backend。接下来我们放大第 4、5、8 步，看看 2PC state data 和锁迁移的细节。

P05 不止记一个 GID：资源管理器与锁迁移机制

很多人以为 2PC 持久化无非就是记个 GID 和事务号，其实远远不够。想一想：普通事务在提交或回滚时，除了改事务状态，还要删建表/删表遗留的物理文件、发缓存失效消息、合并表统计、释放行锁表锁和可串行化谓词锁。2PC 事务未来可能是在崩溃重启后、由另一个全新会话来结束的，所以这些收尾上下文必须全部封存进 2PC state data。

看图左半边：StartPrepare() 先写下 TwoPhaseFileHeader，里面装着 magic、XID、database、owner、prepared_at、子事务 XID 数组、commit/abort 各自要删的 relfilenode、shared invalidation 消息和 replication origin 信息。紧接着，twophase_rmgr.c 定义的四大内置资源管理器依次通过 RegisterTwoPhaseRecord() 追加记录： 第一，Lock，记录普通事务级锁的 LOCKTAG 和锁模式，恢复时重新加锁，结束时释放； 第二，PgStat，记录事务性表统计增量，结束时按提交或回滚语义合并，崩溃恢复不需要重建； 第三，MultiXact，保存关联的 oldest member MultiXactId，防止多事务行锁信息被误清理； 第四，PredicateLock，为 Serializable 隔离级别保存谓词锁与 SerializableXact，确保隔离级别正确性不打折。

再看图右半边的锁迁移红线：lock.c 里的 AtPrepare_Locks() 会忽略会话级锁和 VXID 锁，但会把原本留在进程局部的fast-path relation lock 强制提升到共享主锁表里。随后的 PostPrepare_Locks() 把锁从当前 MyProc 过户给 Dummy PGPROC。源码注释特别强调：这一步必须抢在 ProcArrayClearTransaction() 之前完成，否则别的进程会看到锁还在、但原事务已经不在运行列表里的矛盾状态。

现在这份完整的 state data 准备好了，它是不是每次都要写进 pg_twophase 目录呢？答案可能会颠覆直觉，我们看下一页。

P06 短事务不落盘：WAL 与 pg_twophase 的状态切换

这是 PostgreSQL 2PC 设计里非常漂亮的一个工程优化，大家可以用上方的场景切换按钮，分别演示「短事务」和「跨 Checkpoint 长事务」。

如果每次 PREPARE TRANSACTION 都在 PGDATA/pg_twophase 目录下建文件、写盘、fsync、结束再删文件，高频 2PC 场景的文件系统元数据开销会非常难看。所以 twophase.c 采用了两级生命周期策略：

在短事务路径里，PREPARE 时只把 state data 写进 WAL，并在共享内存 gxact->prepare_start_lsn 里记住 WAL 起点，此时 ondisk 标志是 false，pg_twophase 目录根本不会产生文件。只要在下一个 Checkpoint 之前执行 COMMIT PREPARED 或 ROLLBACK PREPARED，内核直接顺着 prepare_start_lsn 从 WAL 里把 state data 读回来完成收尾。

那什么时候才会写 pg_twophase 呢？当一个 Prepared 事务迟迟没结束，跨越了 Checkpoint。CheckPointTwoPhase() 会检查条件：条目有效或来自 redo、尚未 ondisk、且 prepare_end_lsn 小于等于 redo_horizon。满足条件就说明旧 WAL 未来可能被回收，必须由 RecreateTwoPhaseFile() 把它复制到 pg_twophase 下成为独立状态文件，重新计算 CRC-32C 校验并 fsync 文件，最后还要无条件 fsync pg_twophase 目录本身，确保目录项持久化。

这也给了 DBA 一个极实用的巡检信号：健康的生产库里，pg_twophase 目录通常应该是安静、几乎空的。如果里面长期躺着一堆文件，不用猜，一定存在长时间未关闭的 Prepared 事务。接下来我们看最终的终结与崩溃恢复路径。

P07 先落决定再放锁：FinishPrepared 与崩溃重建

这一页我们把二阶段的「正常收尾」和「崩溃恢复」放在同一张蓝图里对比，大家可以切换上方的三条路径进行动态推演。

先看 FinishPreparedTransaction(gid, isCommit)：第一步 LockGXact() 找到目标条目，校验是否被并发占用、操作者是不是 owner 或 superuser、当前连接的 database 是否一致。第二步看 gxact->ondisk，决定去 pg_twophase 读文件还是按 prepare_start_lsn 去 WAL 读 state data。

最关键的是第四步：调用 RecordTransactionCommitPrepared() 或 RecordTransactionAbortPrepared()，写入 XLOG_XACT_COMMIT_PREPARED 或 XLOG_XACT_ABORT_PREPARED 并同步刷盘。源码里专门强调了两件事：第一，这条提交记录绝对不能被优化掉，因为之前已经写过 Prepare WAL；第二，它不支持异步提交 async commit，因为对 2PC 来说异步提交在语义上没有意义。

只有在最终决定铁板钉钉进入 WAL 之后，内核才依次执行 TransactionIdCommitTree() 更新 pg_xact、ProcArrayRemove() 摘掉 Dummy PGPROC、删除待删文件、调用四大 RMGR 的 postcommit/postabort 回调释放锁，最后 RemoveGXact() 清理共享内存和磁盘文件。

再切换看崩溃恢复路径：普通未提交事务重启后一律当回滚处理，但 Prepared 事务绝不能默认回滚。恢复启动时，restoreTwoPhaseData() 先扫 pg_twophase；WAL 重放遇到 PREPARE 调 PrepareRedoAdd()，遇到 COMMIT/ABORT PREPARED 调 PrepareRedoRemove()；最后由 PrescanPreparedTransactions() 推进 nextXid、RecoverPreparedTransactions() 重建 Dummy PGPROC 和锁表。官方恢复测试 023_pitr_prepared_xact.pl 甚至专门验证了：即便 PITR 恢复到 PREPARE 之后的还原点，新拉起的实例依然要等显式 COMMIT PREPARED，数据才会可见。

内核原理到这已经闭环，接下来我们做一次架构级的横向对比。

P08 单库事务、2PC、补偿事务与逻辑复制 two_phase

在真实架构评审里，最常被问到的问题就是：『我到底该用单库事务、2PC，还是应用层的补偿事务/Saga？』我们用这张矩阵图把三者的本质差异摊开。

普通单库事务的协调者就是 PostgreSQL 自己，事务一结束锁立刻释放，但在跨多个独立实例、消息队列或外部账务系统时，它天生没有跨资源投票能力。应用补偿事务（比如 Saga 或 Outbox 模式）则反过来：先做正向业务，失败了再跑反向补偿，好处是不长期占着数据库锁、可用性高，代价是业务必须能承受『先错后补』的最终一致窗口，而且无法处理不可逆的外部动作。

PostgreSQL 2PC 处在强原子跨资源提交的位置：外部事务管理器当协调者，参与者靠 PREPARE 持久承诺，崩溃后恢复状态继续等决定。它换来了最硬的原子提交语义，但也把锁占用、XID 边界、崩溃恢复和协调者高可用日志全套复杂度都带进了系统。

另外看底部这条独立地层带，很多同学容易把本地 2PC 和逻辑复制里的 two_phase 选项混为一谈。两者不是替代关系，而是不同层次：本文讲的是 PostgreSQL 作为本地 XA 参与者的内核 2PC；而逻辑复制的 two_phase 是订阅端与复制槽的配置，用来决定 logical decoding 和 apply worker 是否按 prepare/commit prepared 边界去流式解码和回放事务。搞清楚这两层边界后，我们来看生产运维的收益与代价。

P09 收益清晰，代价同样刚性：被遗忘的 Prepared 事务

评估一项内核特性，不能只看它的收益清单，更要算清它的刚性成本。图左边青绿色列出了 2PC 的四项明确收益：跨资源原子决定、会话解耦、WAL 明确界定恢复语义，以及通过 RMGR 回调保证锁、谓词锁、MultiXact 与统计的可恢复性。

但图右边陶橙色标出的五项代价同样刚性，而且环环相扣。首先是额外的 WAL 写入和不可优化的同步刷盘，以及启动时固定预留的 max_prepared_transactions 共享内存。更致命的是「被遗忘的 Prepared 事务」所触发的爆炸半径：

第一环，由于 Dummy PGPROC 依然持有事务锁，而且在 pg_locks 里没有普通的活跃 backend pid，它悄无声息地就能把后续的 DDL 和 DML 全部堵死。 第二环，ProcArray 里只要还挂着这个 Prepared XID，系统就一直认为它处于 in-progress 状态，直接拖住全局 xmin 边界，导致 VACUUM 无法回收死元组、无法推进冻结，极端情况下甚至逼近 XID wraparound 风险。 第三环，如果主库调大了 max_prepared_transactions 而备库没跟上，standby 上的查询可能直接被拒绝。 第四环，一旦没有协调者日志，DBA 面对一条孤零零的 GID 根本无法判断该提交还是回滚，凭感觉人工操作极易制造账务事故。

这就是官方文档反复强调『不用就把 max_prepared_transactions 保持为 0』的根本原因。接下来，我们用最小可验证实验，直观演示它的可见性、锁阻塞与排障查询。

P10 最小可验证实验：可见性隔离与行锁阻塞观测

这一页我们还原原文的最小可验证实验——注：原文为了不污染本地环境，严格按官方语法和回归测试 src/test/regress/sql/prepared_xacts.sql 整理，不伪造终端输出；我们用交互式双会话模拟器把每一步的状态变化直观演练出来。

大家可以先选「实验一：可见性与提交/回滚」，点「执行下一步」。前提是测试库已经配置了 max_prepared_transactions 大于 0。当会话 1 插入 id=1 并执行 PREPARE TRANSACTION 'demo_2pc_gid_1' 后，立刻查询 demo_2pc 是看不到这行数据的，但查 pg_prepared_xacts 能清晰看到这条 GID 记录。执行 ROLLBACK PREPARED 后记录彻底消失；而对 id=2 执行 PREPARE 再执行 COMMIT PREPARED，数据才正式对普通查询可见。

再切换到「实验二：行锁阻塞观察」。会话 1 对 id=1 执行 SELECT ... FOR SHARE 并 PREPARE TRANSACTION。此时原事务看起来已经结束，但当你切到会话 2 执行 SELECT ... FOR UPDATE NOWAIT 时，会立刻报锁冲突失败——因为行锁已经过户给了 Dummy PGPROC，依然牢牢攥在手里，直到任意有权限的会话执行 ROLLBACK PREPARED 才释放。

图右下角还放了排障必备的观测思路：先查 pg_prepared_xacts 按 prepared 时间算 age；再关联 pg_locks。特别提醒一句：不是所有 Prepared 锁都能单靠 transactionid 关联出来，实战排障一定要留意 pg_locks 中 pid IS NULL 的行以及等待链关系，结合外部事务管理器日志再做决断。下面我们把这些经验沉淀为分角色的最佳实践。

P11 三条防线：架构师、DBA 与业务开发者的职责边界

既然 2PC 的风险横跨应用、协调者和数据库内核，单靠 DBA 盯着监控或者单靠研发写 SQL 都兜不住，必须把职责拆成图上这三条青绿色的工程防线。

第一条防线是数据库架构师：首先克制技术冲动，只有强一致跨资源提交才引入 2PC，能用 Outbox、幂等消息或 Saga 解决的绝不上 2PC；其次必须配备具备持久化决策日志的外部事务管理器，PostgreSQL 只是参与者不是协调者；第三，GID 命名必须带全局事务号和分片信息，能从 pg_prepared_xacts 一眼反查协调者日志；第四，把 Prepared 生命周期纳入 SLO，正常秒级关闭，分钟级告警并介入，绝不允许小时级、天级常态存在。

第二条防线是 DBA：不用就保持 max_prepared_transactions = 0；开了就必须监控 pg_prepared_xacts 的数量与最大 age；查锁等待别只盯 pid，遇到 pid IS NULL 立刻联查 pg_prepared_xacts；绝对不能凭感觉随手 COMMIT 或 ROLLBACK PREPARED，那是业务最终判决，必须先核对协调者日志；最后，standby 的 max_prepared_transactions 必须不低于 primary。

第三条防线是业务开发者：别在普通业务代码里手写 2PC；Prepare 之前把远程 API、长查询剥离出去，让事务只包最小原子写入；正确处理超时——COMMIT PREPARED 超时不代表失败，必须查状态而不是盲目重试正向业务；同时保证协调者重发终结指令时，能够幂等处理已完成或 GID 不存在等边界状态。接下来我们梳理适用边界和八大常见坑。

P12 什么场景该用，以及八个必须避开的工程深坑

我们把原文第八章的适用场景和第九章的八个常见坑整合到这一张决策蓝图里。左半边清晰划出了适用与不适用边界： 适合 2PC 的，是银行清算、核心账务这类原子性严于可用性、由成熟 XA 事务管理器统一调度、事务极短且故障演练充分的系统。 不适合的，则是普通微服务里『顺手保一致』、需要等待人工审批或外部支付回调的长停留流程、高频大批量长事务，以及压根没有协调者日志可查、或者本就可接受最终一致的业务。

右半边是必须绕开的八大深坑，每一个背后都对应前面讲过的内核机制： 坑一，把 PREPARE TRANSACTION 当事务暂停按钮，锁和 XID 边界会一直挂着； 坑二，忘记设 max_prepared_transactions 或主备不匹配，直接报错或挡住备库查询； 坑三，GID 用无意义短字符串，事故现场根本找不到对应的全局事务日志； 坑四，Prepared 长期不关，拖垮 VACUUM 回收甚至诱发 XID wraparound； 坑五，把 COMMIT PREPARED 网络超时误判成失败，盲目重试引发双倍入账； 坑六，在含临时表、导出快照或 LISTEN/NOTIFY 的事务里尝试 Prepare，直接触发会话绑定限制； 坑七，以为 2PC 能绕开 Serializable 隔离级别成本，其实 Prepare 前依然要做序列化检查并持久化谓词锁； 坑八，同一业务里部分走 2PC、部分走补偿，却没划清原子边界，给人虚幻的强一致错觉。

避开这八个坑，你的 2PC 实践就稳了一大半。最后一页，我们用五个延伸思考题和官方源码索引来收束整堂课。

P13 五个深层思考题与 PostgreSQL 官方源码锚点

最后这一页，我们把整堂课落回两个维度：左边是原文提出的五个极具启发性的延伸思考题，右边是支撑全篇每一个结论的PostgreSQL 官方文档、C 源码与回归/恢复测试锚点。

大家可以带着这五个问题做课后推演： 第一，如果协调者已经落盘了最终决定，但某个参与者磁盘永久损坏丢失数据，2PC 本身能不能自动修复业务一致性？显然不能，2PC 依赖参与者持久守约，永久丢盘需要跨系统对账与灾备恢复。 第二，为什么 PostgreSQL 要费劲引入 Dummy PGPROC，而不是只在 pg_prepared_xacts 里放一行元数据？因为整个锁表、ProcArray 和快照可见性都是围绕 PGPROC 构建的，用虚拟进程才能无缝复用这套高并发基础设施。 第三，PREPARE 之后数据不可见但锁还在，这对在线 DDL、VACUUM 和索引维护分别意味着什么？意味着表锁会卡住 DDL 排队，事务号会卡住 VACUUM 清理与并发建索引的等待阶段。 第四，如果业务允许最终一致，Outbox 加幂等消费帮数据库卸掉了哪些内核压力，又把哪些复杂度转移给了应用层？ 第五，在逻辑复制链路开启 two_phase 后，下游 subscriber 上的 Prepared 事务该由谁监控和兜底清理？
