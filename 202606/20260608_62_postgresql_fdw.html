数据库筑基课 —— PostgreSQL FDW

FDW 不是简单的跨库查询工具，而是用 SQL 对象描述外部数据源、用 FdwRoutine 回调接入优化器与执行器的内核扩展机制。

课程定位
执行器接口 + 场景实践 + 跨库访问边界，打通从 Catalog 到远端游标的全链路。
本质抽象
不把外部数据变成本地 heap，而是通过 FdwRoutine 向优化器与执行器声明能力。
核心警示
把 FDW 当成本地表用，是很多生产事故的起点——必须看清网络、事务与故障域边界。

01 · PROBLEM STATEMENT
痛点剖析与问题转化

为什么不用应用层拼装、ETL 或 dblink？

没有 FDW 时，优化器对外部数据完全失明；FDW 将跨源访问转化为「外部源向内核声明能力」的标准契约。

设计取舍：不实现完整 Table Access Method
外部数据源不需要变成本地存储引擎，只需通过 FdwRoutine 暴露扫描与可选扩展回调即可融入 SQL 生态。
牺牲的代价：单机路径变成跨系统协作路径
「本地优化器 + FDW 扩展 + 外部系统」任何一段估错、变慢、语义偏差或权限变化，都会直接冲击最终 SQL。

FdwRoutine 能力矩阵：最小扫描型 vs 完整型

官方文档明确：只有扫描回调是必需的，其余皆为可选；file_fdw 是最小标杆，postgres_fdw 是完整型参考实现。

读源码的最佳切入路径
先读 contrib/file_fdw/file_fdw.c 理解最小扫描闭环，再读 contrib/postgres_fdw/postgres_fdw.c 掌握下推、写入与异步。
自研 FDW 的克制原则
如为对象存储写 FDW，应优先实现扫描、列裁剪、谓词下推与 EXPLAIN；强一致写入与行锁不应在初期硬上。

下推是正确性优先：哪些条件能发给远端？

FDW 性能好不好，第一看能否下推过滤/JOIN/聚合/排序/LIMIT，第二看估价准不准；安全审查不过关的条件一律留在本地。

选择测试 SQL
判定：可安全下推 → Remote SQL
为什么 STABLE 函数 now() 也会被拦下？
源码 contain_mutable_functions() 实际检查 func_volatile != PROVOLATILE_IMMUTABLE，防止本地与远端时钟差异导致语义混乱。
扩展函数下推的前提
非内置函数必须在 SERVER 的 extensions 选项显式声明、声明为 IMMUTABLE，且两端扩展版本与行为严格一致。

06 · CONNECTION & TRANSACTION
对应原文图 4 · connection.c

按 User Mapping 缓存连接，用 REPEATABLE READ 锁快照

postgres_fdw 不是全局连接池；每个本地 Backend 独立缓存远端连接，且远端事务隔离级别与两阶段提交存在明确边界。

可观测与释放函数
使用 postgres_fdw_get_connections() 查看活跃连接，用 postgres_fdw_disconnect() / disconnect_all() 主动断开。
keep_connections 的权衡
设为 off 可在事务结束后关闭连接以缓解连接数暴涨，但代价是频繁建连带来的握手延迟与 CPU 开销。

07 · ARCHITECTURAL COMPARISON
四方案对比与收益/代价账单

FDW 是联邦访问接口，不是魔法本地化

FDW 比 dblink 更像表、比 ETL 更新鲜、比应用直连易治理，但网络、统计、连接与故障域成本一样都不会凭空消失。

一句话选型准则
FDW 适合「少量、可过滤、能下推、频率可控」的外部访问；一旦变成高频大量复杂跨源事务，应切回同步或同库化。
file_fdw 的独特生态位
面向服务器本地 CSV、日志或程序输出，零下推、只读，是低成本临时 SQL 分析的利器。

IMPORT FOREIGN SCHEMA 的隐藏注意项

09 · OPERATIONS & BEST PRACTICES
对应原文图 5 · 观测诊断闭环

从 Remote SQL 到远端 EXPLAIN ANALYZE 的排障闭环

慢查询绝不能只看本地执行计划；按「查 Remote SQL → 辨下推 → 查远端计划与等待 → 调统计/连接/代价」闭环推进。

排障黄金第一刀
先判 Remote SQL 是否合理：若未下推，查远端索引毫无意义；若已下推仍慢，再切入远端计划、锁与网络。
避免大表对大表跨库 Join
除非执行计划明确证实远端过滤后结果集很小，否则禁止把大 foreign table 与本地大表直接 Join。
