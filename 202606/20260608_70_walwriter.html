P01 walwriter 调度：后台刷盘机制与异步风险边界

大家好，欢迎来到数据库筑基课。前面我们已经聊过 WAL 为什么存在、WAL buffer 怎么承接并发写入，以及 XLogFlush 到底把什么推进到了稳定存储。今天我们顺着写入路径再往下钻一层，专门把一个看起来很小、但生产里极容易被误解的后台进程讲透——那就是 walwriter 的调度机制。大家可以先看屏幕上这张七层地层剖面图。从最上面的业务事务提交，往下经过共享 WAL buffer、walwriter 后台调度、XLogBackgroundFlush 决策链、WALWriteLock 临界区，再到操作系统页缓存 write LSN，最后才落到最底层的稳定存储 flush LSN。整节课我们不做任何黑盒猜测，也不编造性能数字，所有结论都直接回到 PostgreSQL 本地源码——包括 walwriter.c、xlog.c、xact.c 和官方文档——一步一步推演清楚。那我们就先从生产线上最常撞见的五个真实困惑说起。

承接：生产环境里，问题往往不是从源码开始，而是从几类令人困惑的线上现象暴露出来的。
P02 它解决什么问题：降前台 I/O、定风险窗口、可调取舍

很多团队第一次真正关心 walwriter，往往是从左侧这五类线上现象开始的：比如开了 synchronous_commit=off，提交延迟确实降了，但没人敢拍胸脯说「断电最多丢多久的数据」；或者高并发小事务时，监控里还是冒出 WALWrite、WALBufMapping，甚至 wal_buffers_full 一直在涨；又或者调 wal_writer_delay 时左右为难，调小怕 fsync 太密，调大怕丢更多数据。要解开这些困惑，得先明确 walwriter 到底解决哪三件事。第一，它帮前台 backend 提前把完整的 WAL 页写到磁盘文件，降低前台在提交、buffer 复用或复制路径上被迫做长 I/O 的概率。第二，它给异步提交划出了一条可计算的底线——源码和文档明确指出，异步提交记录最坏在约三倍 wal_writer_delay 内落盘。第三，它通过时间和容量两个参数，把「只写到操作系统」还是「继续刷到稳定存储」做成了一个清晰的工程取舍。当然，任何工程机制都有代价：调小延迟会加密 fsync，调小 flush_after 会更积极刷盘，而且最关键的一点——它绝对不是同步提交的替代品，同步提交永远由前台 XLogFlush 兜底。明白了目标与代价，接下来我们看看在 PostgreSQL 的后台进程版图里，walwriter 究竟什么时候出场。

P03 进程定位与启动边界：只在 PM_RUN 阶段登场

我们看这张进程启动边界图。PostgreSQL 里有 checkpointer、bgwriter、walwriter 这几位常见的后台同事，但它们的上岗时间完全不同。翻开 postmaster.c 你会发现，checkpointer 和 bgwriter 在 PM_STARTUP、PM_RECOVERY、PM_HOT_STANDBY 到 PM_RUN 这些阶段都可能需要干活；唯独 walwriter，只在 PM_RUN 正常运行期才启动。逻辑其实特别直白：启动、崩溃恢复或者热备只读阶段，数据库根本不接受普通事务产生新的 WAL 插入流，自然不需要 walwriter 来帮着后台写刷。在 proctypelist.h 里，进程类型 B_WAL_WRITER 直接绑定到 WalWriterMain。它一启动，就会把自己的 proc number 登记到共享内存的 ProcGlobal->walwriterProc 里，这样其他前台 backend 就能精准找到它的 latch 来叫醒它。而且 walwriter.c 文件头专门留了一句架构铁律：千万别往 walwriter 里塞 WAL segment 预创建这类额外职责，因为它的循环周期直接绑定了异步提交的最大风险窗口。那它的主循环到底是怎么运转的呢？我们进下一页，动态跑一遍看看。

P04 WalWriterMain 主循环：周期轮询、50 轮休眠与 Latch 唤醒

从调度视角看，walwriter 并不是什么神秘的复杂调度器，核心就是一个由 WaitLatch 驱动的七步死循环。大家可以点击上方的「播放」或者「单步执行」，跟着高亮节点一起推演。每一轮循环里，它会先根据 left_till_hibernate 判断自己这轮会不会睡过去，并调用 SetWalWriterSleeping 把状态写进共享内存；接着 ResetLatch 清掉旧信号，处理 SIGHUP 或 SIGTERM 中断，然后调用最核心的 XLogBackgroundFlush 干活。干完活之后看结果：如果这轮有有效工作，left_till_hibernate 立刻重置回 50；如果啥也没干，就往下减一。源码里定了两个常量：LOOPS_UNTIL_HIBERNATE 等于 50，HIBERNATE_FACTOR 等于 25。也就是说连续 50 轮空闲后，WaitLatch 的等待时间会从默认的 200 毫秒拉长到 5 秒，进入低功耗休眠。这里有一个非常精妙的设计细节：如果它睡了 5 秒，那刚进来的异步提交岂不是要等 5 秒才落盘？不会！大家可以点一下「触发异步提交唤醒」按钮——正因为它在休眠前提前标了 WalWriterSleeping=true，前台异步提交一看到这个标志，就会立刻调用 SetLatch 把它从 5 秒长睡里一巴掌拍醒，瞬间恢复 200 毫秒活跃节奏。好，既然它醒来只为了调 XLogBackgroundFlush，那我们下一刻就拆开这个函数内部的决策链。

承接：每次醒来真正干活的核心函数只有一个——XLogBackgroundFlush()，它的决策链比「刷到最新 LSN」精细得多。
P05 XLogBackgroundFlush 决策链：完整页优先，时间与容量双阈值

很多人直觉以为 walwriter 每次醒来就是把 WAL 一股脑刷到最新的 insert LSN。翻开 xlog.c 里的 XLogBackgroundFlush，你会发现它其实分了整整四层决策，我们可以通过上面的五个场景按钮逐一验证。第一层，恢复态直接返回。第二层，读取共享请求 LogwrtRqst 后，它故意做了一步向下取整：WriteRqst.Write 减去对 XLOG_BLCKSZ 的余数，退回到最后一个完整 WAL 页的边界。这就是吞吐优先的设计——高负载下尽量写整页，避免碎片化小写，并且此时 flexible=true。第三层，只有当完整页都已经 flush 到位了，它才会转头看 XLogCtl->asyncXactLSN，专门处理当前这个还没写满的不完整页里的异步提交记录，而且此时 flexible=false，必须实打实写到那个 LSN。第四层最关键：写完之后到底要不要 fsync？这里有一道四选一的 Flush 判定门——只要满足「wal_writer_flush_after 等于 0」「首次调用」「距上次 flush 超过 wal_writer_delay」或者「未 flush 块数达到 flush_after」任意一条，就执行 write 加 flush，把底部青绿色的 flush LSN 推上去；否则就只 write 到操作系统缓存，不发 fsync。最后拿到 WALWriteLock 调 XLogWrite 并唤醒 walsender。那么，这个 asyncXactLSN 到底是谁放进去的？我们接着看前台异步提交路径。

P06 异步提交唤醒与 3× wal_writer_delay 最坏窗口推导

这一页我们专门用逻辑推演回答生产里被问得最多的问题：wal_writer_delay 默认 200 毫秒，为什么源码 walwriter.c、transam/README 和官方文档 wal.sgml 都口径一致地说，异步提交最坏可能丢大约 600 毫秒、也就是三倍 delay 的事务？先看上半部分 xact.c 的分叉：同步提交走 XLogFlush，前台干等落盘；异步提交不等，而是调用 XLogSetAsyncXactLSN。它做三件事：把共享内存里的 asyncXactLSN 推高；如果 walwriter 正在休眠，立刻 SetLatch 叫醒；哪怕没休眠，只要 flush_after 等于 0 或者积压块数达标，也会立刻叫醒。既然都会主动叫醒，为什么最坏还是要等三个周期？大家可以点一下「播放三周期推演」，也可以拖动滑块试试把 delay 调到 1000ms。在周期 1，事务 T 异步提交返回成功，它的记录落在当前不完整页里，walwriter 醒来一看前面还有满的完整页，于是优先去写完整页。到了周期 2，因为高负载下 XLogWrite 对完整页采用 flexible=true 弹性写出，为了少发写请求，最坏可能多占一个周期，事务 T 所在的尾页依然没被刷盘。直到周期 3，完整页终于到位，walwriter 转向捕获 asyncXactLSN 并强制 flexible=false 落盘，事务 T 这才安全。所以这不是 bug，而是 PostgreSQL 在高吞吐与可计算风险之间有意画出的边界：默认 200ms 对应约 600ms，调到 1 秒就变成约 3 秒。理解了时间，我们再把容量参数合进来一起看。

P07 时间与容量双旋钮：wal_writer_delay 与 wal_writer_flush_after

我们把 guc_parameters.dat 和 config.sgml 里关于 walwriter 的两个核心参数放到一个二维工程平面上看，一切瞬间就清晰了。横轴是时间维度 wal_writer_delay，默认 200 毫秒，范围 1 到 10000 毫秒；纵轴是容量维度 wal_writer_flush_after，默认 1MB，也就是 1024 乘 1024 除以 XLOG_BLCKSZ，最小值是 0。注意两个参数都是 SIGHUP 生效，改完 reload 即可，不需要重启实例。看右侧这个二维平面：只有当距上次 flush 的时间还没到 delay，并且未 flush 的 WAL 积压量也没到 flush_after 时，系统才落在左下角灰色区域——只 write 到操作系统缓存，不触发物理 fsync。一旦越过右侧虚线，时间阈值触发刷盘；一旦越过上方虚线，容量阈值触发刷盘。这里特别提醒一句：低写入量系统往往被横轴 delay 支配，而高 WAL 生成系统更容易先撞上纵轴的 flush_after。如果把 flush_after 设成 0，上方虚线直接压到原点，灰色区消失，变成只要有活就立刻 flush。而且无论这两个旋钮怎么拧，同步提交依然归前台 XLogFlush 管。说到前台，这就引出了下一个极易搞混的问题：前台 backend 到底什么时候会自己下场写 WAL？

承接：弄清后台怎么写之后，必须破除一个高频误解：有了 walwriter，前台 backend 就不再写 WAL 了吗？
P08 前后台分工：walwriter 是前移减负，而非唯一落盘者

线上经常有人问：「我们明明开着 walwriter，为什么监控里前台业务进程还在等 WALWrite，还在自己写盘？」其实答案就写在 walwriter.c 的文件头注释里：普通 backend 完全有权在 walwriter 跟不上时，自己拿 WALWriteLock 写 WAL 并做 fsync。看图左侧这四条陶橙色的前台路径，每一条都是绕不开的硬逻辑：第一，同步提交时，xact.c 必须调用 XLogFlush 保证本地落盘；第二，共享 WAL buffer 写满了，AdvanceXLInsertBuffer 需要复用旧槽位，如果旧页还没写出，前台只能自己推着写；第三，Buffer Manager 在刷永久表脏页之前，受 WAL-before-data 原则约束，必须先确保对应 page LSN 的 WAL 已经落盘；第四，两阶段提交、SLRU 写出、控制文件更新和复制发送，也都会直接或间接推动刷盘。所以前后台的分工本质上不是「后台独占」，而是「前后台共用 WALWriteLock 和 XLogWrite 这道大门」。walwriter 的真正价值在于提前把水位往前推：等前台真正来调 XLogFlush 时，发现目标 LSN 已经被后台刷过了，就能立刻返回。搞清了前后台分工，我们再把视野放宽到另外两个常被混为一谈的后台进程：checkpointer 和 bgwriter。

P09 进程分工对比：walwriter、backend、checkpointer、bgwriter

这张对比矩阵建议大家收藏。生产调优里最常见的误诊，就是把四个进程的症状安错脑袋。你看，walwriter 只管后台写刷 WAL 和约束异步提交窗口，调用 XLogBackgroundFlush，不决定同步提交何时返回；前台 backend 扛着事务持久性的大旗，同步提交时必须等 XLogFlush 返回；checkpointer 负责推进检查点，决定崩溃恢复要回放多长的 WAL，核心参数是 checkpoint_timeout 和 max_wal_size；而 bgwriter 盯着的是 shared buffers 里的脏数据页，虽然它写数据页前也受 WAL-before-data 约束，但它根本不负责调优 WAL 刷盘频率。PostgreSQL 刻意把「事务持久性」「后台 WAL 推进」「数据页写回」「恢复边界」拆成四套独立机制。下次遇到数据页刷盘导致的 I/O 抖动，别去拧 wal_writer_delay；遇到同步提交尾延迟飙升，也别指望 bgwriter 救场。分清了进程角色，我们再把 WAL 自身的三条写刷路径和水位线对齐对比一下。

承接：同样容易混淆的，还有 write LSN 与 flush LSN 这两条水位线——只写不刷、后台刷盘与同步刷盘有何本质区别？
P10 三条写刷路径：只 write、后台 write+flush 与同步提交 flush

看上方这条 WAL 水位标尺：从左到右依次是 flush LSN、write LSN 和 insert LSN。对于 fdatasync、fsync、fsync_writethrough 这类主流的 wal_sync_method，write 只是把数据交给了操作系统页缓存，机器掉电一样会丢；只有 flush LSN 才是真正写进稳定存储的崩溃安全边界。对应下方三条路径：路径 A 是 walwriter 只 write，它没达到时间或容量阈值，只把 write LSN 往前推一步，省了一次 fsync，减轻后续写盘压力，但崩溃仍可能丢。路径 B 是 walwriter 的 write 加 flush，一旦触发双阈值之一，它会把青绿色的 flush LSN 一并推进，直接压缩未刷盘积压和异步风险窗口。路径 C 则是前台同步提交 flush，事务返回前必须把 flush LSN 推过自己的 commit LSN，fsync 延迟直接暴露在客户端感知路径上。把这三条水位和代价分清之后，理论推演就全部闭环了。接下来进入实证环节：在真实数据库里，我们怎么用系统视图观测这些信号，建立科学的调参闭环？

P11 观测闭环与实操 SQL：先度量四类信号，再决定动不动参数

做数据库调优最忌讳拍脑袋改参数。这张闭环图把实操拆成三步。第一步先问清楚目标：如果你想缩异步提交风险窗口，才优先看 wal_writer_delay 和 flush_after；如果你想降同步提交延迟，主战场在存储 fsync、WALWriteLock 争用、group commit 和同步复制。第二步，用四组视图拿证据：查 pg_settings 确认参数和 sighup 上下文；查 pg_stat_activity 和 pg_wait_events，注意空闲时看到 WalWriterMain 完全正常，而且一定要区分大小写——WALWrite 是 LWLock 锁等待，WalWrite 是文件写 I/O 等待；查 pg_stat_wal 重点盯 wal_buffers_full，它一涨就说明前台被迫下场写 WAL 了；有 pg_stat_io 的版本再按 object='wal' 拆开看各个后台的 writes、fsyncs 和耗时。第三步，在测试库动手实证：用 SET LOCAL synchronous_commit TO off 跑一批写入，对比提交前后和 sleep 1 秒后 insert_lsn、write_lsn、flush_lsn 的追赶过程。切记，这里我们不给任何虚构的性能提升百分比，因为真实收益完全取决于你的存储、负载和拓扑，一定要在同配置压测环境对比 p95、p99 和 fsync 耗时分位数。观测方法有了，那团队里三个核心角色分别该怎么做？

P12 工程最佳实践与适用边界：架构师、DBA 与开发者各司其职

原理落地到团队协作，架构师、DBA 和业务开发者各有明确的动作边界。作为架构师，千万别把 synchronous_commit=off 当成一个单纯的性能开关，它本质上是业务一致性策略。只有事件可重放、低价值日志统计、或者上游有可靠消息源的业务才适合异步提交；核心账务和订单状态必须守住 synchronous_commit=on 甚至更高等级的同步复制。作为 DBA，动参数前坚持先做四项观测，盯着 p95、p99 尾延迟和 WAL 生成突刺，不要只看平均延迟被假象蒙蔽。作为业务开发者，最安全也最推荐的写法，是在单个可丢事务的 BEGIN 块里使用 SET LOCAL synchronous_commit TO off，让它只包裹那一条日志写入，绝不污染全局会话；同时应用层必须配套幂等键或上游重放机制。下半部分这张红绿对照表，也帮大家快速划清了排障边界：小事务异步窗口、fsync 频率平衡、wal_buffers_full 排查，这些找 walwriter 没错；但同步复制远端慢、单次大事务提交慢、数据页刷盘抖动、归档堆积或者 fsync=off 引发的损库，全都不在 walwriter 的管辖范围内。落地前，我们再花一页把生产里最容易踩的六个坑彻底排干净。

P13 生产排雷：关于 walwriter 与异步提交的六个高频误区

这六个坑几乎覆盖了生产线上关于 walwriter 百分之九十的误判，我们逐条对着源码纠偏。第一坑，把 wal_writer_flush_after=0 当成关闭刷盘。实际正好相反，官方文档写得明明白白，0 代表只要有工作就立即 flush，刷盘会变得更激进。第二坑，以为 delay=200ms 最多丢 200ms。前面我们已经完整推演过，因为完整页优先和 flexible 写出，最坏边界是三倍 delay，也就是约 600ms。第三坑，同步提交一慢就急着调 walwriter。记住，同步提交等的是前台 XLogFlush，先查磁盘 fsync、WALWriteLock 争用和同步复制。第四坑，看到 walwriter 停在 WalWriterMain 就觉得 WAL 很闲。它空闲很正常，真正要查的是前台有没有在等 WALWrite、WalSync，以及 wal_buffers_full 有没有涨。第五坑，把 synchronous_commit=off 和 fsync=off 混为一谈。前者顶多丢掉崩溃前几百毫秒已返回的尾事务，数据库本身依然是完整一致的；而 fsync=off 放弃了关键文件落盘，断电后可能导致整个数据库损坏。第六坑，以为 XLogSetAsyncXactLSN 只服务事务提交。其实翻看 xact.c，事务 abort 路径同样会调用它，目的是推进流复制并避免 WAL backlog 堆积。排完这六个雷，我们来看最后一页源码坐标与思考题。
