## 先搞清楚：Cognee 和普通记忆系统有什么不同？

市面上大多数 AI 记忆项目，核心思路是： **你把文本给我，我切成块，做向量嵌入，存起来，你搜的时候我找最像的几个块还给你。**

这叫「向量检索」，本质上是模糊匹配。

Cognee 走的是完全不同的路： **你把文档给我，我不仅要存，还要读懂它。我会抽取出里面的实体、实体之间的关系、事件的来龙去脉，然后把这些信息建成一张知识图谱。**

打个比方：

- **普通记忆系统** = 一个文件柜。你把纸放进去，找的时候翻出最相关的几页。
- **Cognee** = 一个图书管理员。你给她一本书，她不仅放好，还会画出这本书的知识结构图——哪个概念和哪个概念有关、谁引用了谁、来龙去脉是什么。

这就是 Cognee 的核心差异： **不是「匹配」，而是「理解」。**

  

## Cognee 的「图」到底是什么图？

很多人一听到「知识图谱」就犯怵，觉得这是学术界搞的复杂东西。但 Cognee 的图其实不难理解。

它本质上是三样东西：

### 1. 实体（Entity）
就是「名词」——人、技术、概念、产品。

比如你告诉 Cognee：「微服务架构中，API 网关负责路由、限流和认证。」

它提取出的实体就是：`微服务架构`、`API 网关`、`路由`、`限流`、`认证`。

### 2. 关系（Relation）
实体之间的「动词」或「介词」——负责、属于、包含、导致。

上面的例子中，关系就是：`API 网关 → 负责 → 路由`，`API 网关 → 负责 → 限流`。

### 3. 三元组（Triplet）
实体 + 关系 + 实体 = 一条知识。

`(API 网关) — 负责 → (路由)` 就是一个三元组。

一张知识图谱，就是成千上万个这样的三元组连在一起形成的网络。

**所以 Cognee 的「图」不是什么玄学，就是一个实体关系网。** 它的特别之处在于：它不是让你手动建的，而是你给文档，它自动用 LLM 帮你抽。

  

## 真正厉害的地方：ECL 流水线

Cognee 的核心引擎叫 **ECL 流水线**——Extract（提取）→ Cognify（认知加工）→ Load（加载）。

这个流水线决定了 Cognee 「理解」文档的方式和别的项目有本质区别。

### 第一阶段：Extract（提取）

不只是分块。Cognee 会先对文档做**分类**——判断是技术文档、新闻文章、还是代码。然后根据文档类型做针对性的**分块策略**。

这一步就已经和普通 RAG 不一样了。普通 RAG 是「一刀切」，固定块大小；Cognee 是「看菜下饭」。

### 第二阶段：Cognify（认知加工）

这是 Cognee 的核心——也是「图」诞生的地方。

在这个阶段，Cognee 会对每个文本块做三件事：

1. **实体提取**——LLM 扫描文本，识别出所有有意义的实体
2. **关系提取**——LLM 分析实体之间的关系
3. **摘要生成**——给每段文本生成一个精炼的摘要

这些实体和关系被组合成三元组，准备存入知识图谱。

这一步非常关键： **大多数记忆系统只做向量化，Cognee 做的是「理解后的结构化」。**

### 第三阶段：Load（加载）

把结构化后的数据存入三层存储：
- **图数据库**——存实体和关系（Ladybug / Neo4j / Neptune）
- **向量库**——存文本块的语义向量（LanceDB / Chroma / PGVector）
- **关系型数据库**——存元数据和索引

三管齐下，互不打架。

  

## 14 种搜索策略：图的力量在这里爆发

如果你只是做简单的「找相似的文本」，那向量检索就够了。但 Cognee 提供了 **14 种搜索策略**，这才是图的真正威力所在。

我来拆几个最有特色的：

### GRAPH_COMPLETION（默认策略）
这是 Cognee 的招牌。先在图谱里做**多跳遍历**——从你问的实体出发，沿着关系走到相关联的实体，拿到一大片上下文。然后把这些上下文喂给 LLM，生成最终答案。

举个例子：你问「API 网关挂了会怎么样？」
- 如果是普通 RAG：找文本里提到「API 网关挂了」的段落，拼给你。
- 如果是 Cognee：从「API 网关」出发，沿着关系走到「路由」「限流」「认证」「微服务架构」，再走到「服务A」「服务B」……它会给你一张完整的影响分析图。

这就是「图」的力量——**它不是找相似，而是做推理。**

### TRIPLET_COMPLETION
直接搜三元组结构。比如你搜「什么负责路由？」，它返回 `(API 网关) — 负责 → (路由)`。结果清晰、结构化。

### TEMPORAL
时间感知搜索。如果你灌入了带时间信息的数据，可以问「上个月关于 X 的决定是什么？」。Cognee 会结合时间轴和图谱做筛选。

### NATURAL_LANGUAGE
把自然语言转成结构化图谱查询。你不需要学 Cypher 或 SPARQL，直接用中文问就行。

还有其他 10 种策略，覆盖了摘要搜索、代码搜索、多模态搜索等场景。

**14 种策略不是说让你手动选，而是 Cognee 内部会根据查询自动匹配最优策略。** 这是工程上的硬功夫。

  

## 一个 Postgres 搞定所有存储——这设计很妙

Cognee 在存储架构上做了一个我觉得非常聪明的决定： **一个 Postgres 实例同时做图、向量、关系存储。**

之前我用过很多知识图谱项目，基本都是 Neo4j + Elasticsearch + PostgreSQL 三件套，运维起来相当痛苦。

Cognee 的做法是：
- **默认内嵌**：Ladybug（图库）+ LanceDB（向量库）+ SQLite——零配置开箱即用
- **生产方案**：一个 Postgres + pgvector（向量 + 关系），再加 Ladybug/Neo4j（图）

这个方案的好处是：
1. **运维简单**——不用维护三个独立的存储系统
2. **事务一致**——所有操作在一个数据库事务里
3. **成本低**——不需要买三个数据库实例

对于中小型团队来说，这真的是个福音。

  

## 还支持 OWL 本体——这个很多人没提

Cognee 一个很少被提及但很重要的特性是： **支持 OWL 本体文件。**

OWL（Web Ontology Language）是语义网的标准语言。你可以定义一个 OWL 文件来描述你的领域知识结构——比如「在金融领域，一个「客户」可以有多个「账户」，每个「账户」有「交易记录」」。

把这个 OWL 文件喂给 Cognee，它建图的时候就会按照你定义的框架来组织知识。 **这意味着 Cognee 的知识图谱不是瞎建的，而是有「骨架」的。**

对于企业级应用来说，这非常关键——你的知识库不再是「一堆文本堆在那里」，而是「有结构、可查询、可推理」的资产。

  

## 真实感受：Cognee 用起来怎么样？

说实话，Cognee 的学习曲线比 Mem0 陡一些。不是因为它难用，而是因为它**概念多**。

你用 Mem0，核心就两个操作：`add` 和 `search`。你用 Cognee，要理解 `remember`、`recall`、`ECL 流水线`、`14 种搜索策略`、`图谱遍历`——概念确实多了一个量级。

但这是有原因的：
- **Mem0** 解决的是「记住对话中的事实」——可以很薄，几行代码搞定
- **Cognee** 解决的是「理解文档中的知识」——天然就更复杂

如果你只是想让 AI 记住用户偏好的颜色、名字、喜欢的语气，Cognee 确实有点杀鸡用牛刀。

但如果你在做的是：
- **企业知识库**——几百份文档，需要 AI 能理解文档之间的关联
- **研究助手**——需要追踪概念的演变和相关关系
- **技术文档问答**——问题涉及多个知识点的交叉推理

那 Cognee 是当下最好的选择之一。

而且好消息是，Cognee 的默认配置（Ladybug + LanceDB + SQLite）是开箱即用的，`pip install cognee` 之后就能跑。上手体验一下图谱搜索和普通 RAG 的差别，你就知道我说的是什么了。

  
## 总结：Cognee 的「图」到底牛在哪？

最后用一句话总结：

**Cognee 不是在做「记忆」，而是在做「理解」。它的图不是炫技，而是让 AI 真正能「读懂」文档之间的深层关系。**

几个核心 takeaways：

| 维度 | Cognee 的做法 | 和普通 RAG 的区别 |
|------|---------------|-------------------|
| 对文档的理解 | 提取实体+关系，建知识图谱 | 普通 RAG 只做分块+向量化 |
| 搜索方式 | 14 种策略，多跳图谱推理 | 普通 RAG 只做向量相似度 |
| 存储架构 | 图+向量+关系，一个 Postgres | 通常只需要向量库 |
| 领域适配 | OWL 本体定义知识骨架 | 没有领域概念 |
| 输出质量 | 结构化答案，而非文本片段拼接 | 返回相似文本段落 |

如果你对 AI 记忆层感兴趣，Cognee 绝对是值得深入研究的项目。它的「图」不是花架子，而是实打实在工程上把「知识结构化」这件事做到了可落地的程度。

项目地址：`github.com/topoteretes/cognee`

## 第一步：装

Cognee 的安装和其他 Python 项目一样：

```bash
pip install cognee
```

我现在用的是 Python 3.11，在一个干净的虚拟环境里跑的。整个过程大概一分钟，没有遇到什么奇怪的依赖冲突。

装完之后验证一下：

```python
import cognee
print(cognee.__version__)
# 输出: 0.4.1（你看到的时候版本可能已经变了）
```

零报错。第一关过了。

  

## 第二步：喂数据

Cognee 的核心操作叫 `remember`——把数据喂给它。你可以喂一段文本，也可以喂一个文件。

先来个最简单的：

```python
import asyncio
import cognee

async def main():
    # 重置一下，清掉之前的记忆
    await cognee.prune.prune_data()
    await cognee.prune.prune_system()
    
    # 喂一段文本
    text = """
    微服务架构中，API 网关负责路由、限流和认证。
    每个微服务实例可以独立部署和扩展。
    当用户请求到达时，API 网关先验证身份，再把请求转发到对应的服务。
    """
    
    await cognee.add(text)
    print("✅ 数据已喂入")

asyncio.run(main())
```

运行之后你会看到一些日志输出，大概意思是 ECL 流水线开始跑了——Extract（提取）、Cognify（认知加工）、Load（加载）。

这里有个细节我当初找了半天才懂： **第一次运行 Cognee 会自动创建本地存储。** 默认用的是 SQLite + LanceDB + Ladybug（一个嵌入式图数据库），不需要你配置任何东西。这对于想快速体验的人来说非常友好。

  

## 第三步：搜一下

数据喂进去了，来看看 Cognee 怎么搜。

```python
import asyncio
import cognee

async def main():
    # 重置和喂数据略，同上面的一样
    
    # 问一个问题
    result = await cognee.search("API 网关有什么作用？")
    print(result)

asyncio.run(main())
```

输出是这样的（我整理了一下格式）：

```
基于 Cognee 的图谱推理结果：

API 网关在微服务架构中承担以下核心作用：
1. 路由 — 将用户请求转发到对应的微服务
2. 限流 — 控制访问流量，防止服务过载
3. 认证 — 验证用户身份，确保安全

信息来源与图谱关联：
- (API 网关) — 负责 → (路由)
- (API 网关) — 负责 → (限流)  
- (API 网关) — 负责 → (认证)
- (API 网关) — 属于 → (微服务架构)
```

看到最后那部分了吗？ **这不是普通的文本片段匹配，而是三元组输出。** Cognee 不是从原文里「找了一段最像的」还给你，而是把它自己构建的知识图谱里和问题相关的实体关系提取出来，重新组织成答案。

我再试一个需要「推理」的问题：

```python
result = await cognee.search("如果 API 网关挂了，哪些功能会受影响？")
print(result)
```

输出：

```
基于图谱推理：API 网关负责路由、限流和认证三项核心功能。
如果 API 网关不可用，以下功能会受影响：
1. 路由 — 无法将请求转发到微服务 → 所有服务不可访问
2. 限流 — 无法控制流量 → 后端服务可能被突发流量打垮
3. 认证 — 无法验证身份 → 系统安全性下降
```

注意，原文里并没有「如果 API 网关挂了会怎么样」这段话。 **Cognee 是自己从图谱里推出「路由、限流、认证都依赖 API 网关」，然后推理出「如果网关挂了，这三项都会受影响」。**

这就是它的核心卖点： **不是检索，而是推理。**

  

## 第四步：看看图的内部

Cognee 搜的时候背后用到了图，但你看到的是最终答案。如果想直接看看它建的图长什么样呢？

可以用 `search` 配合不同的搜索类型：

```python
from cognee.api.v1.search import SearchType

# 只看三元组，不要 LLM 生成的答案
result = await cognee.search(
    "API 网关",
    search_type=SearchType.TRIPLET_COMPLETION
)
print(result)
```

输出：

```
[
  Triplet(head="API 网关", relation="负责", tail="路由"),
  Triplet(head="API 网关", relation="负责", tail="限流"),
  Triplet(head="API 网关", relation="负责", tail="认证"),
  Triplet(head="API 网关", relation="属于", tail="微服务架构"),
  Triplet(head="微服务实例", relation="可以", tail="独立部署"),
  Triplet(head="微服务实例", relation="可以", tail="独立扩展")
]
```

这就是 Cognee 从你那三段话里提取出来的知识图谱。每一行就是一个三元组，合在一起构成了这张小图。

如果你把数据量加大——比如喂十篇技术文档进去——这个图就会变得非常丰富。你搜「限流」的时候，Cognee 可能顺着关系走到「API 网关」→「微服务架构」→「服务发现」→「负载均衡」，给你一整条知识链路。

**你喂得越多，图越密，推理能力越强。** 这是 Cognee 最性感的地方。

  

## 第五步：用文件做记忆

喂文本只是开胃菜。Cognee 真正的主场是喂文档。

假设你有一个技术文档目录：

```python
import cognee
import asyncio
from pathlib import Path

async def main():
    await cognee.prune.prune_data()
    await cognee.prune.prune_system()
    
    # 喂一个目录下的所有文档
    docs_dir = Path("./tech-docs")
    for md_file in docs_dir.glob("*.md"):
        await cognee.add(str(md_file))
        print(f"✅ 已加载: {md_file.name}")
    
    # 跨文档搜索
    result = await cognee.search("微服务和单体架构有什么区别？")
    print(result)

asyncio.run(main())
```

Cognee 的 ECL 流水线会处理每份文档，提取实体和关系，然后把跨文档的图谱合并在一起。所以你搜的问题可能涉及文档 A 的概念和文档 B 的概念，Cognee 能把它们串起来。

  

## 一些实操中的经验

跑了几轮下来，有几个经验值得分享：

**1. 默认配置够用，但别指望小数据出奇迹**

Cognee 的图推理能力在三五段话上也能体现出来——就像我上面演示的那样。但要真正感受到图的威力，建议至少喂 5-10 份有内容关联的文档。数据量上来了，图谱的连接密度上来了，多跳推理的效果才会有明显提升。

**2. search 的默认行为**

Cognee 默认用的是 `GRAPH_COMPLETION` 搜索类型——先走图谱做多跳遍历，然后把遍历到的上下文喂给 LLM 生成答案。这意味着你换不同的 LLM（OpenAI / Claude / DeepSeek），答案的文风和深度会不一样，但图谱遍历的结果是一致的。

目前 Cognee 默认用的是 OpenAI，如果你没有配 OPENAI_API_KEY，它会提示你需要设置。也可以换成其他模型，在初始化时配置。

**3. 不要和 Mem0 比「谁更好」**

我之前的文章详细对比过这两个项目。实操之后的感受更明确： **它们是两种东西。**

- Mem0 的核心场景是「对话记忆」：用户说了什么、偏好什么、决定了什么——这些是操作级别的记忆。
- Cognee 的核心场景是「知识记忆」：文档里有什么实体、实体之间什么关系——这些是知识级别的记忆。

两个可以一起用，不矛盾。Mem0 管用户上下文，Cognee 管领域知识。

**4. 第一次跑的时候看日志**

Cognee 的日志输出其实很详细，会打出 ECL 流水线每一步在做什么。建议第一次跑的时候不要静默，看看 Extract 阶段识别出了什么实体、Cognify 阶段提取了什么关系。这样你能更直观地理解它内部的工作方式。

  

## 总结

实操下来，我对 Cognee 的评价是：

- **上手简单**——`pip install` 之后几行代码就能跑
- **默认配置友好**——Ladybug + LanceDB + SQLite 零配置开箱即用
- **图的威力在小数据上也能看到**——三元组输出和多跳推理不是 PPT 功能，是真的能跑出效果
- **真正的价值在大数据量下释放**——文档越多，图越密，推理越强
