## 背景

> 同一个需求，两个开源项目选择了完全不同的路。

最近做 AI Agent，发现一个绕不开的问题 —— **大模型没有记忆**。

你跟它聊完一次，下次它就不认识你了。传统方案是把整段聊天历史都塞进 prompt，但这样 token 烧得太快了，而且信息一多，模型反而"迷失"在上下文里。

于是出现了专门的「AI 记忆层」项目 —— 给 AI 装一个长期记忆系统。

这个领域现在有两个开源项目最受关注： **Mem0**（`github.com/mem0ai/mem0`）和 **Cognee**（`github.com/topoteretes/cognee`）。

我都装了一遍、跑了一遍、在 Claude Code 里集成体验了一遍。这篇聊聊我的真实感受。

---

## 先说结论：它们解决的是同一个问题，但哲学不同

这是整篇文章最重要的一句话：

- **Mem0 的核心诉求**：记住**对话中**的事实、偏好、决策，让 AI Agent 更个性化。
- **Cognee 的核心诉求**：把文档和知识变成**结构化图谱**，让 AI 能"理解"而非"匹配"。

打个比方：

- **Mem0** 像一个**私人秘书** —— 你说了什么、喜欢什么、讨厌什么，她都记着。下次聊的时候，她帮你把相关的回忆找出来。
- **Cognee** 像一个**图书馆管理员** —— 你把一本书给她，她不只是存放，还会梳理章节目录、提取核心概念、画出知识点之间的关系图。

一个偏**对话记忆**，一个偏**知识管理**。

## 安装体验

### Mem0 安装

```bash
pip install mem0ai

# 如果需要 NLP 增强（混合搜索 + 实体提取）
pip install mem0ai[nlp]
python -m spacy download en_core_web_sm
```

如果你是 TypeScript 用户：

```bash
npm install mem0ai
```

安装完就能用，默认配置开箱即走 —— 它自带内嵌存储，不需要连任何外部服务。

最简单的用法：

```python
from mem0 import Memory

memory = Memory()
memory.add([
    {"role": "user", "content": "我喜欢吃披萨，讨厌西兰花"}
], user_id="user123")

results = memory.search("吃的偏好", user_id="user123")
print(results)
```

还有 CLI：

```bash
npm install -g @mem0/cli
mem0 init
mem0 add "喜欢深色模式" --user-id alice
mem0 search "Alice 的偏好" --user-id alice
```

### Cognee 安装

```bash
pip install cognee
```

同样开箱即走，默认用内嵌存储（SQLite + LanceDB + Ladybug）。

最简单的用法：

```python
import cognee, asyncio

async def main():
    await cognee.remember("Cognee 把你的文档变成 AI 记忆。")
    results = await cognee.recall("Cognee 是做什么的？")
    for result in results:
        print(result)

asyncio.run(main())
```

有 CLI：

```bash
cognee-cli remember "文本"
cognee-cli recall "查询"
```

也有 TypeScript SDK：

```bash
npm install @cognee/cognee-ts
```

### 安装对比

| 维度 | Mem0 | Cognee |
|------|------|--------|
| pip 安装 | `pip install mem0ai` | `pip install cognee` |
| 默认存储 | 内嵌 SQL + Vector + Graph | 内嵌 SQLite + LanceDB + Ladybug |
| 开箱即用 | ✅ 是 | ✅ 是 |
| 需要外挂 DB | ❌ 不需要 | ❌ 不需要 |
| TypeScript SDK | ✅ `npm install mem0ai` | ✅ `npm install @cognee/cognee-ts` |
| CLI | ✅ `mem0` | ✅ `cognee-cli` |

**我的感受**：两个安装都非常丝滑，`pip install` 完就能跑。Mem0 的 API 更接近聊天记忆的场景（传 messages 列表），Cognee 的 API 更偏知识管理（传文本/文档）。

## 核心用法：方向完全不同

这是最关键的区别，值得展开说。

### Mem0：从对话中提炼记忆

Mem0 的设计出发点就是**对话记忆**。它的核心 API 是 `add()` —— 你传一段对话进去，它自动提取事实、偏好、计划，存起来。

```python
from mem0 import Memory

memory = Memory()

# 多轮对话，自动提取记忆
memory.add([
    {"role": "user", "content": "我叫张三，是一名后端工程师"},
    {"role": "assistant", "content": "你好张三！我来帮你记录"},
    {"role": "user", "content": "我主要用 Python 和 Go，最近在学习 Rust"},
    {"role": "assistant", "content": "好的，我记下了"}
], user_id="zhangsan", agent_id="my-agent")

# 检索相关记忆
results = memory.search("用什么语言", user_id="zhangsan")
```

内部做了什么事：
1. **去重检查** —— 先查已有记忆，避免重复存储
2. **事实提取** —— LLM 从对话中提取事实（"张三用 Python、Go、学习 Rust"）
3. **嵌入存储** —— 提取出的每条事实做向量化，存入向量库
4. **实体链接**（可选） —— 记忆中提到的人、技术、组织等建立关联

检索时用了**多信号融合**：
- **语义搜索** —— 向量相似度
- **关键词匹配** —— BM25 精确匹配
- **实体关联** —— 提升与当前实体相关的记忆权重
- **时间权重** —— 新近记忆优先

**一句话**：你聊，它记，你问，它找。

### Cognee：从文档中构建知识图谱

Cognee 的设计出发点是**知识管理**。它的核心 API 是 `remember()` + `recall()` —— 你传一段文本或文档进去，它抽取出实体和关系，构建知识图谱。

```python
import cognee, asyncio

async def main():
    # 记住一条知识
    await cognee.remember("微服务架构中，服务间通过 API 网关通信，网关负责路由、限流和认证。")
    
    # 查询
    results = await cognee.recall("API 网关的职责是什么？")
    for r in results:
        print(r)

asyncio.run(main())
```

内部做的事更复杂 —— 它有一个完整的 **ECL 流水线**（Extract, Cognify, Load）：

1. **分类** —— 判断文档类型
2. **分块** —— 把文档切成合理大小的块
3. **实体提取** —— LLM 识别实体（微服务、API 网关、路由、限流、认证）
4. **关系提取** —— 实体之间的关系（API 网关→负责→路由）
5. **图谱构建** —— 存入知识图谱数据库
6. **摘要生成** —— 给每块内容生成摘要
7. **向量嵌入** —— 给文本块和摘要做向量化

检索时支持 **14 种搜索策略**：
- `GRAPH_COMPLETION` —— 图谱遍历 + LLM 补全（默认）
- `RAG_COMPLETION` —— 传统 RAG 检索
- `TRIPLET_COMPLETION` —— 主-谓-宾结构搜索
- `TEMPORAL` —— 时间感知搜索
- `NATURAL_LANGUAGE` —— 自然语言转结构化查询
- 等等

**一句话**：你给文档，它建图谱，你问知识。

### API 对比

| 维度 | Mem0 | Cognee |
|------|------|--------|
| 核心写 API | `add(messages, user_id)` | `remember(data, session_id?)` |
| 核心读 API | `search(query, user_id)` | `recall(query, session_id?)` |
| 输入格式 | 对话消息列表 | 文本/文件/URL |
| 输出 | 相关记忆片段 | 图谱查询结果 |
| 删 | `delete()` / `batch_delete()` | `forget()` |
| 更新 | `update()` / `batch_update()` | （通过重写图谱） |
| 额外 | `get()` 获取单条 | `improve()` 反馈学习 |

## 技术架构的差异

### Mem0：轻量级，专注对话

```
对话 → LLM 提取事实 → 去重 → 嵌入 → SQL + Vector + Graph 存储
                                      ↓
                          多信号检索 → 返回相关记忆
```

- **存储层**：SQL（事实元数据）+ Vector（语义搜索）+ Graph/KV（实体关系）
- **插件体系**：24 种 LLM、30 种向量库、15 种嵌入模型、4 种图谱库、5 种重排序器
- **算法创新**：2026 年 4 月发布的新记忆算法，单次 ADD-only 提取，性能大幅提升

**优点**：
- 上手极快，几行代码集成
- 插件生态丰富，几乎什么都能接
- 基准测试数据亮眼

**缺点**：
- 偏"浅层"理解 —— 提取的是显式事实，而非深层知识结构
- 对长文档支持偏弱（设计定位就是对话记忆）
- 事实提取质量依赖 LLM 能力

### Cognee：重架构，面向知识

```
文档 → 分类 → 分块 → LLM 提取实体+关系 → 构建知识图谱 → 摘要 → 嵌入
                                                                    ↓
                                             14 种搜索策略 → 返回结构化结果
```

- **存储层**：图数据库（Ladybug/Neo4j/Neptune）+ 向量库（LanceDB/Chroma/PGVector）+ 关系型 DB
- **统一 Postgres 方案**：一个 Postgres 实例同时做图、向量、关系存储，这是 Cognee 的亮点
- **ECL 流水线**：Extract → Cognify → Load，结构化的三步处理流程
- **本体支持**：支持 OWL 本体文件，接地到标准语义框架

**优点**：
- 知识理解深度更深，实体关系完整
- 14 种搜索策略，适应不同查询场景
- 一个 Postgres 搞定所有存储，运维简单
- BEAM 基准测试成绩好（100K: 0.79, 10M: 0.67）

**缺点**：
- API 设计偏"文档处理"，对话记忆不是强项
- 学习曲线更陡 —— 要理解 ECL 流水线、图谱搜索等概念
- 实体提取消耗的 token 可能更多（但深度也更深）

### 一张表看懂

| 维度 | Mem0 | Cognee |
|------|------|--------|
| 核心定位 | 对话记忆 | 知识图谱记忆 |
| 提取方式 | LLM 提取事实 | LLM 提取实体+关系 |
| 存储核心 | SQL + Vector | 图 + Vector + SQL |
| 默认向量库 | （可配置，默认嵌入） | LanceDB |
| 默认图谱库 | （可配置，可选） | Ladybug（内嵌） |
| 搜索策略 | 多信号融合（语义+关键词+实体+时间） | 14 种（图谱/RAG/三元组/时间等） |
| 是否支持本体 | ❌ | ✅ OWL 本体 |
| 文档处理 | ❌ 专注对话 | ✅ PDF/DOCX/代码/图片/音频 |
| 增量更新 | ✅ ADD-only 自动去重 | ✅ 流水线增量处理 |
| LLM 依赖 | 是（事实提取和检索都需要） | 是（实体提取和搜索都需要） |
| 本地运行 | ✅ 可完全本地（Ollama） | ✅ 可完全本地（Ollama/Llama.cpp） |

## 集成方式

### Mem0：遍地开花

Mem0 的集成面非常广，几乎覆盖了所有主流 AI 框架：

- **MCP 服务器**：`mcp.mem0.ai`（远程）或 OpenMemory 自托管
- **Claude Code 插件**：通过 MCP 或 agent skills 集成
- **Vercel AI SDK**：一等公民 `@mem0/vercel-ai-provider`
- **LangChain / LlamaIndex / CrewAI / AutoGen / OpenAI Agents SDK** 等 30+ 框架
- **Chrome 扩展**：浏览器里用

在 Claude Code 里用 Mem0：

```bash
# 通过 CLI 快速注册
npm install -g @mem0/cli
mem0 init --agent --agent-caller claude-code
mem0 add "我主要用 Python"
```

之后 Claude Code 的对话就会自动调用记忆 —— 不用你自己操心。

### Cognee：MCP + 插件

Cognee 同样提供 MCP 服务器：

```bash
# Docker 启动 MCP 服务器
docker run --env-file ./.env -p 8000:8000 cognee/cognee:main
```

MCP 暴露三个核心工具：`remember`、`recall`、`forget`。支持 SSE、HTTP、stdio 三种传输协议。

Claude Code 集成：

```bash
# 通过 MCP 配置接入
# 之后在 Claude Code 里可以直接用 cognee 的记忆能力
```

也有 LangChain/LlamaIndex 集成。

**我的感受**：Mem0 在 Agent 框架集成上走得更远 —— 它有一个专门的 Vercel AI SDK provider，这在 AI 应用开发里是很大的一个生态卡位。Cognee 走的是更标准的 MCP 路线，兼容性好，但没那么"深入"。

## 当你想用的时候

### 选 Mem0

- **你做的是对话型 AI Agent** —— 客服机器人、个人助手、角色扮演
- **你想让 AI 记住用户的偏好和信息** —— "用户喜欢简洁的回答"、"用户是后端开发者"
- **你需要快速集成、不想折腾存储** —— 开箱即用，几行代码搞定
- **你的输入主要是对话** —— 而不是文档、PDF、代码
- **你追求基准测试上的硬指标** —— LoCoMo 92.5、LongMemEval 94.4 确实能打

### 选 Cognee

- **你在做知识密集型应用** —— 企业知识库、文档问答、研究助手
- **你需要 AI 理解文档之间的深层关系** —— 不只是"哪段文本匹配"，而是"这个实体和那个实体什么关系"
- **你希望用一套存储搞定图+向量+关系** —— 一个 Postgres 跑所有
- **你的数据源主要是文档/PDF/代码** —— 而不是聊天对话
- **你想给知识建立本体分类** —— 用 OWL 文件定义领域语义

### 可以一起用吗？

可以，而且我觉得这是最佳实践。

思路是这样的：

1. **Cognee 做底层知识库** —— 把公司文档、技术手册、代码库灌进去，构建完整的知识图谱。这是"图书馆"。
2. **Mem0 做上层对话记忆** —— 在 Cognee 查询结果的基础上，Mem0 记住用户在对话中表现出的偏好和意图。这是"秘书"。
3. **查询时先走 Cognee 拿知识，再走 Mem0 拿用户偏好，最后 LLM 综合回答**。

两个并不冲突，一个管"世界知识"，一个管"用户记忆"。

## 一些大实话

**Mem0 做得好的**：API 设计非常直觉 —— 用过 OpenAI 的人都会觉得熟悉，基本零学习成本。插件生态确实丰富，30 种向量库、24 种 LLM，几乎不会遇到"我这个模型不支持"的情况。基准测试也舍得下功夫，LoCoMo 从 71.4 提到 92.5，这个提升幅度是实打实的。

**Mem0 的短板**：定位就是对话记忆，如果你想把一本 300 页的技术手册灌进去让它理解 —— 这不是它的设计目标。另外，它提取的是"事实"而非"结构"，所以对于"这个 API 的请求流程是什么样的"这类问题，表现不如知识图谱方案。

**Cognee 做得好的**：知识图谱的深度确实比纯向量检索强太多。你用 Cognee 查"API 网关的职责"和用传统 RAG 查，体验完全不同 —— 它能给你结构化的答案，而不是几段相关文本的拼接。一个 Postgres 跑全部存储的架构也很对我胃口，运维简单。

**Cognee 的短板**：上手比 Mem0 复杂，要理解图谱、ECL 流水线这些概念。文档处理流水线如果文档格式千奇百怪，偶尔会踩坑。对纯对话场景（比如需要记住用户偏好）来说有点杀鸡用牛刀。

## 最终总结

| 对比项 | Mem0 | Cognee |
|--------|------|--------|
| 一句话定位 | 给 AI Agent 装私人秘书 | 给 AI Agent 建图书馆 |
| 核心场景 | 对话记忆、用户偏好 | 知识图谱、文档理解 |
| 安装复杂度 | 极低，pip install | 极低，pip install |
| 默认开箱 | ✅ 完全可用 | ✅ 完全可用 |
| API 风格 | `add/search`，类聊天 | `remember/recall`，类知识库 |
| 输入类型 | 对话消息列表 | 文本/文档/URL/代码 |
| 输出类型 | 事实片段 | 知识图谱查询结果 |
| 存储统一性 | 各自独立配置 | 一个 Postgres 全搞定 |
| 搜索多样性 | 多信号融合（4 种） | 14 种搜索策略 |
| Agent 框架集成 | 30+ 框架，深度集成 | MCP 标准集成 |
| 基准测试 | LoCoMo 92.5, LongMemEval 94.4 | BEAM 100K: 0.79, 10M: 0.67 |
| 研究论文 | arXiv:2504.19413 | arXiv:2505.24478 |
| 开源协议 | Apache 2.0 | Apache 2.0 |
| 背后团队 | Y Combinator S24，美国 | Topoteretes UG，柏林 |
