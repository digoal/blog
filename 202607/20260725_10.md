## 一、AI 记忆的「统一存储」之选

AI 应用做持久记忆，通常需要三件套：

- **向量数据库**：语义相似度搜索（pgvector、Milvus、Pinecone）
- **图数据库**：实体关系推理（Neo4j、KuzuDB）
- **关系数据库**：元数据管理（PostgreSQL、MySQL）

这意味着你要同时维护三套系统——每套都有自己的部署、备份、监控、扩缩容。

**Cognee** 打破了这个局面。它是一个开源 AI 记忆平台，允许你只用 **一个 PostgreSQL 数据库** 搞定以上所有事情。底层用 `pgvector` 做向量索引，用关系表存知识图谱，而 PostgreSQL 19 新引入的 **SQL/PGQ（SQL Property Graph Queries）** 标准语法让你可以直接用 SQL 写图遍历查询。

一句话概括：

> Cognee 负责「把信息提取成知识图谱 + 向量」——PostgreSQL 19 + pgvector + SQL/PGQ 负责「存和查」。

## 三、PostgreSQL 里到底存了什么

很多人觉得「知识图谱」很玄乎。Cognee 的 PostgreSQL 适配器把它**拍平成了两张关系表**，我们直接看看。

### 3.1 `graph_node` 表——实体

```sql
CREATE TABLE graph_node (
    id              TEXT PRIMARY KEY,
    name            TEXT,
    type            TEXT,
    properties      JSONB,
    source_ref_keys TEXT[],       -- 数据溯源
    created_at      TIMESTAMPTZ,
    updated_at      TIMESTAMPTZ
);
```

每一行就是一个实体——可以是一篇文章、一个人名、一个概念。  
`type` 表示实体类型（`Document`、`Entity`、`Chunk`），`properties` 是任意属性（JSONB）。

### 3.2 `graph_edge` 表——关系

```sql
CREATE TABLE graph_edge (
    source_id           TEXT REFERENCES graph_node(id),
    target_id           TEXT REFERENCES graph_node(id),
    relationship_name   TEXT,
    properties          JSONB,
    source_ref_keys     TEXT[],
    created_at          TIMESTAMPTZ,
    updated_at          TIMESTAMPTZ,
    PRIMARY KEY (source_id, target_id, relationship_name)
);
```

每一行就是一个关系——比如「Cognee → 使用 → PostgreSQL」。  
`relationship_name` 就是关系类型，`source_id` → `target_id` 构成有向边。

### 3.3 向量集合表——语义搜索

Cognee 为每个需要索引的字段自动创建向量表：

```sql
CREATE TABLE "Entity_name" (
    id      TEXT PRIMARY KEY,
    payload JSON,
    vector  vector(1536)  -- 维度取决于嵌入模型
);
```

向量搜索使用 pgvector 的余弦距离：

```sql
SELECT id, payload, vector <=> :query_vector AS distance
FROM "Entity_name"
ORDER BY distance
LIMIT 10;
```

### 3.4 混合查询：图谱 JOIN 向量

Cognee 的 `PostgresHybridAdapter` 可以在一条 SQL 里同时做图谱遍历和向量搜索：

```sql
SELECT gn.id, gn.name, gn.type, ge.relationship_name,
       vc.vector <=> :query_vector AS distance
FROM graph_edge ge
JOIN graph_node gn ON gn.id = ge.target_id
JOIN "Entity_name" vc ON vc.id = gn.id
WHERE ge.source_id = :node_id
ORDER BY distance
LIMIT 10;
```

**向量帮你找到相关内容，图谱帮你理解实体间的关系**——两者互补。

 

## 四、SQL/PGQ：用 PostgreSQL 19 原生语法查知识图谱

### 4.1 什么是 SQL/PGQ？

SQL/PGQ（SQL Property Graph Queries）是 **ISO SQL:2023 标准** 的一部分，定义了一套在 SQL 中查询属性图（Property Graph）的标准语法。

PostgreSQL 19 是第一个原生支持 SQL/PGQ 的开源关系数据库。它引入三个核心概念：

| 语法 | 作用 |
|------|------|
| `CREATE PROPERTY GRAPH` | 在现有关系表之上定义一个属性图视图 |
| `GRAPH_TABLE` | 在 SQL 中嵌入图查询 |
| `MATCH` | 图模式匹配（类似 Cypher 的 `(node)-[edge]->(node)`） |

关键理解：**SQL/PGQ 不是在 PostgreSQL 里重新实现了一个图数据库，而是在关系表之上定义了一个「图视图」，让你可以用图查询语法来查关系表。** 数据还是存在普通表里，但查询方式多了图模式匹配这一维。

### 4.2 在 Cognee 的表上定义属性图

Cognee 的数据已经存在 `graph_node` 和 `graph_edge` 里。用 SQL/PGQ，我们可以在这两张表之上定义一个属性图：

```sql
CREATE PROPERTY GRAPH cognee_graph
  VERTEX TABLES (
    graph_node LABEL entity
      PROPERTIES (id, name, type, properties)
  )
  EDGE TABLES (
    graph_edge
      SOURCE KEY (source_id) REFERENCES graph_node(id)
      TARGET KEY (target_id) REFERENCES graph_node(id)
      LABEL relationship
      PROPERTIES (relationship_name, properties)
  );
```

这条语句执行后，PostgreSQL 就知道 `graph_node` 是顶点表、`graph_edge` 是边表，以及它们的关联关系。**它不复制数据，不创建新表，只是注册了一个元数据映射。**

### 4.3 用 MATCH 写图查询

定义好属性图之后，就可以用 `GRAPH_TABLE` + `MATCH` 来写图遍历查询了。

**查询所有实体和它们之间的关系：**

```sql
SELECT *
FROM GRAPH_TABLE(cognee_graph
  MATCH (a IS entity)-[e IS relationship]->(b IS entity)
  COLUMNS (
    a.name AS source_name,
    a.type AS source_type,
    e.relationship_name AS relation,
    b.name AS target_name,
    b.type AS target_type
  )
)
ORDER BY source_name;
```

这比传统 SQL 的 JOIN 写法更直观。传统 SQL 你需要自己 JOIN `graph_node` 两次（一次取源、一次取目标）：

```sql
-- 传统 SQL 写法
SELECT s.name AS source_name, e.relationship_name, t.name AS target_name
FROM graph_edge e
JOIN graph_node s ON s.id = e.source_id
JOIN graph_node t ON t.id = e.target_id;
```

**按类型过滤：**

```sql
SELECT *
FROM GRAPH_TABLE(cognee_graph
  MATCH (a IS entity WHERE a.type = 'Concept')
        -[e IS relationship]->(b IS entity)
  COLUMNS (a.name AS concept, e.relationship_name AS rel, b.name AS related)
);
```

**查找某个实体的所有邻接节点（1 跳邻居）：**

```sql
SELECT *
FROM GRAPH_TABLE(cognee_graph
  MATCH (a IS entity WHERE a.name = 'Cognee')
        -[e IS relationship]->(b IS entity)
  COLUMNS (b.name AS neighbor, e.relationship_name AS edge_label)
);
```

### 4.4 变长路径查询（K 跳遍历）

SQL/PGQ 支持变长模式匹配，这是传统 SQL 很难做到的事情。比如查「Cognee」3 跳内能到达的所有实体：

```sql
SELECT *
FROM GRAPH_TABLE(cognee_graph
  MATCH (a IS entity WHERE a.name = 'Cognee')
        -[e IS relationship]->{1,3}(b IS entity)
  COLUMNS (a.name AS start, b.name AS end, e.relationship_name AS last_hop)
);
```

对比 Cognee 内部目前用递归 CTE 的实现：

```sql
WITH RECURSIVE neighborhood(id, hops) AS (
  SELECT unnest(ARRAY['Cognee']), 0
  UNION
  SELECT CASE WHEN e.source_id = n.id THEN e.target_id ELSE e.source_id END,
         n.hops + 1
  FROM neighborhood n
  JOIN graph_edge e ON (e.source_id = n.id OR e.target_id = n.id)
  WHERE n.hops < 3
)
SELECT * FROM neighborhood;
```

**SQL/PGQ 的 MATCH 语法显然更简洁、更可读。**

### 4.5 与 pgvector 结合

SQL/PGQ 处理图谱遍历，pgvector 处理向量相似度。两者在 PostgreSQL 19 中可以无缝结合：

```sql
-- 先用 SQL/PGQ 找到相关实体，再用 pgvector 排序
SELECT v.*
FROM GRAPH_TABLE(cognee_graph
  MATCH (a IS entity WHERE a.name = 'Cognee')
        -[e IS relationship]->(b IS entity)
  COLUMNS (b.id AS node_id, b.name AS node_name)
) g
JOIN "Entity_name" v ON v.id = g.node_id
ORDER BY v.vector <=> :query_vector
LIMIT 10;
```

这条查询完成了一个完整的推理链路：**从「Cognee」出发→遍历图谱找到相关实体→按向量相似度排序→返回最相关的结果。** 一个数据库，一条 SQL，零数据搬运。

 

## 五、pgvector 向量搜索

### 5.1 基本相似度搜索

```sql
-- 余弦距离（默认，Cognee 内部使用）
SELECT id, payload, vector <=> :query_vector AS distance
FROM "Entity_name"
ORDER BY distance
LIMIT 10;

-- 如果要用内积或 L2：
-- SELECT id, payload, vector <#> :query_vector AS inner_product
-- SELECT id, payload, vector <-> :query_vector AS l2_distance
```

### 5.2 带元数据过滤

Cognee 的向量表用 `payload` (JSONB) 存元数据，`belongs_to_set` 字段标记所属数据集：

```sql
SELECT id, payload, vector <=> :query_vector AS distance
FROM "Entity_name"
WHERE payload->'belongs_to_set' ?| ARRAY['knowledge_base']
ORDER BY distance
LIMIT 10;
```

这利用了 PostgreSQL 的 JSONB 索引 + pgvector 的近似索引（IVFFlat/HNSW），在同一套数据库里完成过滤+向量搜索。

### 5.3 创建索引加速

```sql
-- IVFFlat 索引（适合高召回率场景）
CREATE INDEX ON "Entity_name" USING ivfflat (vector vector_cosine_ops)
  WITH (lists = 100);

-- HNSW 索引（适合高精度场景，PG17+ pgvector 支持）
CREATE INDEX ON "Entity_name" USING hnsw (vector vector_cosine_ops);
```

### 9.2 图谱构建耗时

第一次 `remember()` 会调用 LLM 提取实体和关系，比较慢。建议：

- 大批量数据分批次写入，用 `dataset_name` 组织
- 需要快速响应先用 `session_id` 做轻量缓存，后续 `improve()` 同步到图谱
- 生产环境用 `run_in_background=True` 异步构建

### 9.3 SQL/PGQ 的 PostgreSQL 版本

SQL/PGQ 是 **PostgreSQL 19** 引入的特性。如果你的 PostgreSQL 版本低于 19，`CREATE PROPERTY GRAPH` 和 `GRAPH_TABLE` 语法不可用。但 Cognee 本身不依赖 SQL/PGQ——它在 PG12+ 上都能正常运行，内部用递归 CTE 和 JOIN 实现图谱查询。SQL/PGQ 是你**直接查数据库时多了一种更强大的查询方式**。

## 十、总结

Cognee + PostgreSQL 19 + pgvector + SQL/PGQ 这套组合的价值在于：

1. **一个数据库就是全部基础设施**——图谱、向量、元数据全在一处
2. **SQL/PGQ 让你用标准 SQL 写图查询**——`MATCH` 模式匹配比递归 CTE 直观十倍
3. **pgvector 补齐向量搜索**——余弦距离、IVFFlat/HNSW 索引、JSONB 过滤，全在 PostgreSQL 里
4. **Claude Code 插件开箱即用**——装完就自动记忆项目上下文
5. **MCP 协议不锁定厂商**——Claude Desktop、Cursor、VS Code 都能接

**适用场景：**
- 你在用 Claude Code 写代码，想让 AI 记住项目上下文
- 你在开发 AI Agent，需要一个统一存储后端
- 你想用 PostgreSQL 一栈搞定，不想引入一堆中间件

**一句话：Cognee 负责把信息变成知识，PostgreSQL 19 + pgvector + SQL/PGQ 负责把这套知识存好、查快、查得灵活。**
