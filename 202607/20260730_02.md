## 制作过程  
在 macOS M2 笔记本上进行制作, 假设你已安装 Docker Desktop APP.  
  
如果无法下载 postgresql base image, 可先配置代理 (新版本 Docker Desktop 已支持 http 及 socks5 proxy), 参考: [《Docker proxy》](../202407/20240704_01.md)  , 或配置 Docker desktop mirror , settings - Docker Engine  
```
  "max-concurrent-downloads": 1,
  "registry-mirrors": [
    "https://docker.1ms.run",
    "https://dockerproxy.net",
    "https://hub.rat.dev",
    "https://docker.xuanyuan.me",
    "https://docker.m.daocloud.io"
  ]
```
  
注意, 如果配置了下面这个dns, 在 docker build 之前一定要删掉 dns 配置, 否则无法解析 host.docker.internal proxy 配置.  
```
  "dns": [
    "223.5.5.5",
    "8.8.8.8"
  ],
```
  
**假设在宿主机已有 http_proxy: `0.0.0.0:22222` , socks5: `0.0.0.0:11112`, build 时以及容器启动后会用到, 有一些科学上网需求.**

````
# CLAUDE.md

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

## 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

## 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

## 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

## 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

---

## 下载网页方法约定
当已经给定了网址 URL 需要获取该网页的内容时, 不要使用大模型内置的 Fetch 接口. 
对于无需翻墙即可获取的网页内容, 则推荐使用 curl -sL --noproxy '*' --max-time 30 获取, 提高速度.
当不使用代理无法下载网页内容时, 无需重试. 说明需要翻墙, 改成使用 curl --socks5-hostname host.docker.internal:11112 来进行获取.
你应该先根据直觉判断是否需要翻墙, 自行根据以上进行选择. 无法判断时, 先不翻墙(也就是使用 curl -sL --noproxy '*' --max-time 30), 当无法获取再翻墙(也就是使用 curl --socks5-hostname host.docker.internal:11112).

## WEB搜索约定
当需要搜索时, 优先使用 mcp__MiniMax__web_search tool, 而不是 mcp__web-search__web_search tool.

## 本机环境介绍

本机已安装了 DuckDB , SQLite 都可直接在命令行中进行调用, 位于 /root/.duckdb/cli/latest/duckdb , /usr/local/bin/sqlite3
````

脚本内容  
```  
#!/bin/bash  
# 配置root用户bash环境变量  

cat >> /root/.bashrc <<'EOF'
alias ll='ls -larth'  
alias rm='rm -i'  
alias cp='cp -i'  
alias mv='mv -i'  
export PGUSER=postgres

if [ ! -d /var/lib/postgresql/root ]; then
    cd /
    mv /root /var/lib/postgresql/
    ln -s /var/lib/postgresql/root /root
else
    # /var/lib/postgresql/root 存在，检查 /root 是否为软链接
    if [ ! -L /root ]; then
        rm -rf /root
        ln -s /var/lib/postgresql/root /root
    fi
fi
  
if [ ! -d /var/lib/postgresql/tmp ]; then
    cd /
    mv /tmp /var/lib/postgresql/
    ln -s /var/lib/postgresql/tmp /tmp
else
    # /var/lib/postgresql/tmp 存在，检查 /tmp 是否为软链接
    if [ ! -L /tmp ]; then
        rm -rf /tmp
        ln -s /var/lib/postgresql/tmp /tmp
    fi
fi

EOF

cat >> /root/.bashrc <<'OUTER'
if [ ! -f /var/lib/postgresql/.bash_profile ]; then
    cat > /var/lib/postgresql/.bash_profile <<'EOF'
#!/bin/bash
# 配置postgres用户bash环境变量
alias ll='ls -larth'
alias rm='rm -i'
alias cp='cp -i'
alias mv='mv -i'
EOF

    chown postgres:postgres /var/lib/postgresql/.bash_profile
    chmod 644 /var/lib/postgresql/.bash_profile
fi
OUTER


rm -rf /root/env_root.sh  
```

```  
docker exec -ti pg bash  
```

## 注意事项
1、一定要选择和使用和 CPU 架构相关的镜像. Intel/AMD 都选择 x86_64 镜像. 苹果笔记本如果是 M 芯片, 选择 ARM 镜像.  
  
2、注意磁盘的剩余空间是否足够, 建议选择较大的盘来存储和运行容器. 根据需要更改命令中的目录路径.   
  
3、给docker desktop分配足够的cpu、内存、磁盘空间资源.   (具体设置问AI) 
  
4、启动时触发的 env_root.sh 里面会把 root 目录移动到 data volumn , 也就是宿主机, 如果 data volumn 已存在, 则直接删除容器初始化时的 root , 软链 data volumn 中的 root, 正常使用没问题, 如果你的 data volume 中的 root 被不小心污染了, 可以备份改名, 然后重新创建容器, 即可使用容器中的 root, 然后人工修复一下问题.  
   
5、以上命令行都是 macOS/Linux 中可以直接运行的, 对于 Windows PowerShell 或 cmd 命令行, 请使用 AI 转换一下再执行. 例如

## 使用实践
创建容器后的实践总结.   

1、给 git 配置代理, 假设宿主机启用了 `socks5 proxy`, 监听 `0.0.0.0:11112`
```
git config --global http.proxy socks5://host.docker.internal:11112
git config --global https.proxy socks5://host.docker.internal:11112
```
  
2、使用 Hermes profile, 一鱼多吃.  
  
[《用 Hermes profile 一鱼多吃: 配置多个 gateway, 多个人格角色, 多个服务》](../202608/20260813_01.md)  
    
3、如果你在 Linux 中跑容器来隔离与宿主机的环境, 防止容器越狱到宿主机. 可以改一下 docker run 中的:   
```
--privileged=true

改成

--cap-add ALL --cap-drop SYS_ADMIN --security-opt apparmor=unconfined --security-opt seccomp=unconfined
```
  
macOS 作为宿主机使用`--privileged=true`无安全问题, 因为 Docker 运行在虚拟机（LinuxKit）里，和你的 macOS 是物理隔离的。  
```
你的 macOS（宿主机）
    └── 虚拟机（LinuxKit，轻量级 Linux）
            └── Docker 引擎
                    └── 你的 Linux 容器（Hermes）
```
  
  
## 未来优化
主要是瘦身、架构适配、集成/修炼 Agent (包括环境、skill、包、自进化等) 屠龙之术.  

1、多阶段构建（建议重构 Dockerfile）
  
当前是单阶段构建，所有中间文件（源码、编译依赖）都保留在最终镜像中。建议使用多阶段构建.  
  
2、合并 RUN 层
  
将多个 RUN 命令用 `&&` 连接成一个 RUN 命令。这能避免中间层产生大量临时文件，每个 RUN 都会产生一个独立层。 
  
3、使用多阶段构建, 第一阶段部署版本变化不频繁的基本依赖, 第二阶段部署可能经常变化的软件.  
  
4、现有的 docker image 问题: 大、每次软件版本升级后需要 build, 较难维护. 未来考虑拆成多个小 image, 使用 compose up. 
  
5、未来这个 Agent 需要不断使用、打磨, 沉淀下来的是数据、经验、技能(SOP)、记忆的组织、稳态的程序等等. 

使用 Agent 就像玩游戏, 给这个 Agent 练级, 屠龙宝刀在手, 还怕啥锤子.   

未来甚至可以修炼各个角色, 就跟玩游戏角色炼号一样, 核心资产是号本身(沉淀下来的东西).

玩六了还能设计成产品SKU, 例如“陪练、代练、教练、出租、买断、代安装、云市场收费镜像”等.
