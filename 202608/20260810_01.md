## 背景

先说结论，省得你翻到最后才发现：用户提问里"OpenAI 宣布停止发展 Codex""未来全力发展封闭体系云端""被便宜好用的 DeepSeek 架空"——这三条前提几乎全部站不住脚。下面我把事实摆出来，再讲清楚 OpenAI 到底在干什么。

先说那条最容易引起误解的新闻：2026-08-09，OpenAI 关停了 Atlas 浏览器。原因是"浏览器里的 AI 代理能力转移到 ChatGPT 和 Codex 中"，同时 ChatGPT 团队与 Codex 团队在组织架构上合并。这听起来像"砍掉客户端"，对吧？但反过来看——Atlas 的能力是被 Codex 吃掉的，不是 Codex 被砍掉的。这条新闻很可能就是"OpenAI 放弃 Codex"这个说法在网上流传的源头。

## 实际上，OpenAI 在 Codex 上是反着来的

把 2025 年 4 月到 2026 年 7 月这段时间线摊开，OpenAI 在 Codex 上做了至少 6 件加码动作，每一件都在扩张：

- 2025-04：Codex CLI 开源（Apache-2.0，Rust 实现，终端级编码代理）；
- 2026-02-02：发布 Codex macOS 桌面 App，支持多 Agent 并行 + 工作树隔离 + Skills；
- 2026-03：Windows 桌面 App 上线；Codex Security（代码安全审计）发布；
- 2026-05：Codex for Chrome 扩展 + iOS/Android 移动端远程接入 Mac；
- 2026-06：收购 Ona（提供安全云沙箱的初创公司），团队并入 Codex；
- 2026-07：Codex Security CLI 开源，纳入 CI/CD。

OpenAI 自家研究员 Roon 在 2026 年的几次公开访谈里说过自己 100% 用 Codex 写代码，并提到某个内部项目 5 个月产出 100 万行代码"没一行手写"（Semafor 2026-01）。这是把 Codex 当核心战略产品在吃自己狗粮的画风，不是"被架空然后放弃"的画风。

![Codex 产品矩阵](../svg/codex-product-matrix-20260810-0700-00.svg)

更准确地说，Codex 不是"一个客户端"，而是一组八个形态的客户端矩阵——CLI、桌面 App、IDE 扩展（VS Code/JetBrains/Xcode）、Web、Chrome 扩展、移动端、安全扫描 CLI、应用服务器。它们共享同一个 Codex 应用服务器内核（基于 JSON-RPC + stdio 上的 JSONL 流），前端形态各异，后端逻辑统一。

## "开源"背后的真相：客户端免费，后端收钱

很多人把"Codex CLI 是开源的"等同于"Codex 是开放的"。这两件事不是一回事。

Codex CLI 的代码确实开源、Apache-2.0 协议，Rust 写成，但它跟上游模型的通信走的是 OpenAI 的 Responses API——这是一个私有协议、不开源，OpenAI 自己官方推荐"所有新项目都应该使用 responses 接口"。

![Responses API 与 Chat Completions 协议对比](../svg/responses-vs-chatcompletions-20260810-0700-00.svg)

Responses API 和大家熟悉的 Chat Completions 差在哪？端点路径不同（`/responses` vs `/chat/completions`）、角色类型不同（Responses 支持 `developer` 角色、优先级高于 `system`）、独有参数（`reasoning`、`store`、`include` 这些 Chat Completions 根本不识别）、SSE 事件流的命名和语义也不同。直接互换会得到 404 或者请求超时。

DeepSeek 想接入 Codex，要么自己实现 Responses API 兼容端点（DeepSeek 已经这么干了，V4-Flash 已支持，V4-Pro 8 月初跟上），要么就在客户端和上游之间架一层协议转换网关（CC Switch、Moon Bridge、ccx 这些工具干的就是这个）。

这是 OpenAI 的护城河设计，不是 bug。客户端开源是为了拉开发者生态、收集使用数据、做品牌渗透；后端协议私有是为了让上游模型调用绕不开 Responses API 这条路。Responses API 在 Codex 生态里用得越广，第三方模型厂商要适配的工作量就越大——它们要么自己投入工程做兼容，要么走协议转换网关，无论哪条都会把开发者引向 Responses API 的接口语义。

这套打法跟 90 年代的浏览器之争是同一个剧本——客户端免费开源抢用户，后端协议掌握在自己手里收钱。Chromium 开源、WebKit 部分接口不公开、Chrome 的 V8 引擎有些优化路径私有，道理一模一样。

## 本地 + 云端，不是二选一

"未来全云端"这个假设也对了一半。Codex 的工程架构确实把"重型能力"放在云端，但客户端本身不是纯云端 SaaS。

![Codex 本地 + 云端双模架构](../svg/codex-architecture-20260810-0700-00.svg)

本地侧做什么：终端 UI、本地文件读写、本地 Git 操作、本地进程执行、AGENTS.md/Skills 加载、协议转换决策——你的代码、Git 状态、文件系统结构全部留在你自己的机器上。

云端侧做什么：模型推理（GPT-5.3-Codex 这些千亿参数的模型本地跑不动）、沙盒执行环境（`codex exec`、CI/CD 长任务跑在隔离容器里）、会话状态存储（`store=true` 时 OpenAI 侧保存上下文）、Hosted Shell Containers（云端托管的 shell 容器）、Server-side Compaction（服务器端做记忆压缩）。

为什么这个双模是工程上必然的？模型太大、本地扛不动要云端；沙箱要做隔离、用户机器千差万别要云端；但 UI 和本地文件操作必须在本地——开发者要看 diff、要审批命令、要保留本地 Git 状态，Worktrees 模式之所以必须支持本地 Git，是因为 Agent 不能直接动主分支。

Ona 被收购的意义也在这里——Ona 提供"安全、预配置的云环境"，让 Codex Agent 能跑更长时间的任务。这不是要消灭本地端，是把云端沙箱做厚。

## DeepSeek 真正冲击的是哪一层

冲击是真实存在的，但冲击点不在 Codex 这一层，而在 API 定价层。

几个可验证的数据：OpenRouter 平台 2026-08-03 到 08-07 的周榜显示，DeepSeek V4 Flash 新旧版本合计调用量 11.31T tokens，OpenAI GPT-5.6 Luna 仅 3.54T tokens，差距约 3 倍。DeepSeek-V4-Flash 输出单价 0.28 美元/百万 token，直接触发 OpenAI 把 GPT-5.6 Luna 降价 80%（财联社 2026-07-31）——Luna 输入价从 $1 降到 $0.2，输出价从 $6 降到 $1.2。

但这个"3 倍"有几个边界得说清楚：OpenRouter 只是第三方分发平台，OpenAI 通过 ChatGPT 桌面端、Azure、企业直签产生的调用都不在统计里；OpenRouter 偏向长尾开发者和价格敏感用户，OpenAI 自有渠道偏向企业和高 ARPU 用户；Token 数不等于收入，GPT-5.6 Luna 单价仍高于 DeepSeek。

DeepSeek 吃掉的主要是 OpenAI API 经济里低单价、长尾中小开发者这一段——替代品是直连 DeepSeek API 或者用国内云转售——而不是 OpenAI 的企业级 Codex 订阅、云端沙盒执行、安全审计这一段。这两段的用户画像、付费意愿、替换成本完全不同。

![Codex 双层策略](../svg/codex双层策略-20260810-07-01-25.svg)

所以 DeepSeek 和 OpenAI 当前的关系，更像是"国产模型跑在 OpenAI 的客户端框架上"——这种关系在云计算时代叫"应用层跑在别人生态上"，对 OpenAI 的威胁有限，反而强化了 Responses API 作为事实标准的地位。

顺带提醒一下：DeepSeek 在 2026-08 发出 API 涨价预警（"预计涨幅较大"，搜狐 2026-02-13、腾讯 2026-08-06）。一个被"协议收编"的厂商，应该跟随主导方定价；DeepSeek 选择主动涨价，说明定价权在自己手里。这是"被收编"叙事最大的反向证据。

## OpenAI 真正要警惕的对手

如果真要说"谁在挑战 OpenAI 的 Codex"，不是 DeepSeek，是另外两条战线。

**第一条：Claude Code。** 2026 年 Anthropic 的企业客户 ARR 已经突破 470 亿美元（钛媒体 2026-05-29），4 个月内从 140 亿翻了三倍多。Claude Code 在开发者社区的体验口碑（实时协作控制感）普遍被认为优于 Codex 的"无人值守全自动"路线。在 npm 周下载量这个指标上，两家有过不同时期的领先——2025 年下半年 Claude Code 领先，到 2026 年 5 月 Codex 已经反超到 12 倍（CSDN 2026-05-11）。这不是谁碾压谁，是缠斗。

但 OpenAI 自己做了一个耐人寻味的动作： **2026-03 开源 Codex Plugin CC**，让 Claude Code 用户不离开 Claude Code 就能把当前代码交给 Codex 独立审查（腾讯 2026-03-31、2026-07-30）。如果 Claude Code 是真正被开发者握在手里的入口，那 OpenAI 这套操作的意思是——承认自己的客户端不是入口，只能作为"模型/审查能力的提供方"被调用。这跟"客户端锁定入口"的比喻正好反过来了。

**第二条：新晋 agent 框架。** OpenClaw（105k GitHub Stars）、Hermes Agent（89.9k Stars，Nous Research）、OpenCode（70k+ Stars）在 2026 上半年快速崛起。共同特征：MIT 协议、模型无关、原生支持 Claude / GPT / Ollama / 本地模型 / OpenRouter 200+ 模型。OpenClaw 在 2026-04-25 发布的 v2026.4.24 中，把 DeepSeek V4 Flash 设为新用户上手默认模型，直接取代了 Claude Sonnet。

这批新兴框架根本不走 Codex 客户端，也无所谓 Responses API 协议——它们的协议层要么是 Chat Completions，要么是自实现的抽象层。开发者刚开始用 agent 框架，默认跑的就是 DeepSeek 或其他模型，根本没经过 OpenAI 的 Responses API。这条威胁线，三位专家都没充分展开。

![中美 AI 势力地图](../svg/中美AI势力地图-20260810-07-25-00.svg)

## 中美地缘这条隐藏的轴

还有一个维度容易被忽略。OpenAI 在 2024-07 已经终止对中国大陆提供 API 服务；美国从 2022 年起限制英伟达 A100/H100 出口中国，2025 年扩大 AI 芯片出口管制和模型权重限制。这条线的逻辑是：OpenAI 主动放弃了中国市场，DeepSeek 能在中国做到极致低价，是因为没有美国算力市场的成本结构——DeepSeek 用 512 张 H800 训 R1，仅 80 小时（Nature 2025-09 封面）。

反过来说，OpenAI 想重新进中国，地缘上已经不可能。所以策略转向绑定盟友市场 + Stargate 算力内循环（5000 亿美元、8GW、未来三年投资超 4500 亿美元，腾讯 2025-10-31）——这才是"封闭体系"的真实驱动力，不是云端 SaaS，而是自营算力 + 自营模型 + 自营客户端的硬资产路线。

中美 AI 竞争的本质，不是"开源 vs 闭源"的口水仗，是两套算力体系 + 两套监管体系的并行：美国阵营闭源 + 高 ARPU 企业客户 + 自营算力；中国阵营开源 + 低价格长尾 + 国产算力 + 国家补贴。

## 三个核心结论的边界

**结论一：OpenAI 没有放弃 Codex，反而在加大投入。**

- 适用场景：2025-04 至 2026-08 的时间窗口内。
- 不适用场景：如果未来 6 个月内 Codex CLI/App 突然停止维护（类似 Redis 改协议导致社区分叉），则结论失效。
- 证伪手段：Codex CLI 仓库 archival、Codex 工程团队公开转岗、IPO 招股书中 Codex 业务不再单独披露。
- 证明手段：Codex CLI 月度 commits、Codex App MAU、Codex Security 企业客户数。

**结论二：DeepSeek 冲击的是 OpenAI API 定价，不是 Codex 客户端。**

- 适用场景：2025-Q1 至 2026-Q3，对中小开发者、低 token 单价的推理场景。
- 不适用场景：企业级私有部署、安全审计、CI/CD 集成、强合规场景——DeepSeek 几乎无法替代 OpenAI Codex。
- 证伪手段：出现头部企业把 Codex 安全审计全部替换为 DeepSeek 直连 + 内部脚本的公开案例。
- 证明手段：OpenAI 2026Q4 财报中 Codex 订阅用户数、企业 ARR。

**结论三：OpenAI 走的是"开源客户端 + 后端协议锁定"，不是"封闭云端"。**

- 适用场景：Responses API 强制、Codex 客户端开源、第三方模型可接入但需适配协议的当前架构下。
- 不适用场景：如果 OpenAI 未来收回第三方模型接入，本结论需重新评估。
- 证伪手段：Responses API 被 OpenAI 闭源、第三方模型可绕过 Codex 直接 P2P 调用。
- 证明手段：Codex 客户端中"切换模型"后实际调用链路是否仍走 Responses API、Token 计费是否仍由 OpenAI 出账。

不过也不能太绝对——这套双层锁策略能成立的隐含前提是"开发者主动选择 Codex 作为入口"。当开发者选择 Claude Code、Cursor、OpenClaw、Hermes Agent 作为入口时，Responses API 是 0 价值的，因为调用链根本不会经过 Codex 客户端。所以这套策略的真实适用范围，是"OpenAI 自家客户端内的开发者"，而非"全球 AI 编程开发者"。

## 一句话回答

OpenAI 不是"放弃 Codex、转向封闭云端"，而是把 Codex 升级成"开源客户端矩阵 + Responses API 后端协议 + 云沙箱纵深"的三位一体战略产品。DeepSeek 没有架空 Codex，反而正在被 Codex 用协议收编——但这个"收编"只在 OpenAI 自家客户端内成立。真正让 OpenAI 睡不着觉的对手，是 Claude Code（企业级编程市场的体量差距）和 OpenClaw/Hermes 这批新晋框架（它们默认绑定 DeepSeek，根本不走 Codex）。

如果只看调用量数字，会被"DeepSeek 3 倍领先"的标题党带跑；只要把时间线、客户端矩阵、协议层动作摆在一起看，OpenAI 的战略意图就很清楚——它要做 AI 编程时代的操作系统，不是某一家模型的 API 商。

  

顺带提醒一下：我引用 Claude Code 和 Codex 在 npm 周下载量上的对比时，特意用了 2026-05 的最新数据（CSDN 2026-05-11，Codex 周下载 8610 万、Claude Code 720 万）。网上很多文章还在引 2025 下半年的旧数据（"Claude Code 领先 26 倍"），那是一年前的快照，跟今天的方向正好相反——这也是为什么"被 DeepSeek 架空"这种叙事听起来合理但站不住脚：它依赖的数据往往是过期的或口径有偏的。
