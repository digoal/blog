## 1. 这个工具是什么

`utils/docker/` 是一个**轻量化的 Docker 封装器**，把 `freebuff` CLI 装进一个标准化的容器里，从而：

- 跨 macOS / Linux / Windows (WSL / Git Bash) 行为一致
- 不用在主机上污染 `node`、`npm`、`expect`、`inotify-tools` 等依赖
- 在隔离环境里运行 freebuff，但项目目录通过 mount 双向同步
- 自动处理主机凭据（`~/.config/manicode/credentials.json`）注入

它**不**是一个 Web 服务，也不是 RPC 框架；它本质上是用 Docker 模拟了 `freebuff` 的本地运行环境。

## 2. 一句话使用方式

在 `freebuff-community` 仓库根目录执行：

```bash
./utils/docker/start-freebuff.sh              # 交互式询问项目路径
./utils/docker/start-freebuff.sh ./my-project # 直接指定项目路径
```

首次运行会自动 `docker build`，之后只要 `utils/docker/` 下脚本未变就会复用镜像。

## 3. 整体架构（先看这张图）

```
┌─────────────────────────── 主机 ───────────────────────────┐
│ start-freebuff.sh                                           │
│   ├─ 校验/构建 docker 镜像                                  │
│   ├─ 创建 <project>/.freebuff/comm/                         │
│   │     ├─ messages.txt  (host → container)                 │
│   │     └─ responses.txt (container → host)                 │
│   └─ docker run --privileged                                │
│         ├─ mount 项目父目录到 /workspace                    │
│         └─ mount ~/.config/manicode → /workspace/.config/.. │
│         └─ exec message-bridge.sh (tail -f responses.txt)   │
└─────────────────────────────────────────────────────────────┘
                            │  docker run
┌────────────────────────── 容器内 ──────────────────────────┐
│ entrypoint.sh                                               │
│   ├─ mkdir .freebuff/comm + chmod 777                      │
│   ├─ 选择性 cp 项目文件到 /tmp/freebuff_workspace/...       │
│   ├─ npm install                                            │
│   ├─ cp 凭据到 ~/.config/manicode/credentials.json         │
│   └─ exec freebuff-wrapper.sh                               │
│                                                            │
│ freebuff-wrapper.sh (expect)                                │
│   ├─ 写 "CONTAINER READY" 到 responses.txt                 │
│   ├─ spawn freebuff                                         │
│   ├─ inotifywait messages.txt → send "\r" to freebuff      │
│   └─ expect freebuff 输出 → append 到 responses.txt        │
└─────────────────────────────────────────────────────────────┘
```

**核心通信模型**：双向文件队列 + `inotify` 事件 + `expect` 串口复用。

## 4. 推荐用法

### 4.1 给项目做一次「干净启动」

```bash
cd /path/to/your-project
/path/to/freebuff-community/utils/docker/start-freebuff.sh "$PWD"
```

要点：
- **必须传绝对路径**，脚本内部会 `cd "$PWD"` 一次来解析。
- 项目目录的**父目录**才是 mount 的目标；容器内 `/workspace/<项目名>/...` 才是项目本体。

### 4.2 让容器自带调试输出

```bash
DEBUG=true ./utils/docker/start-freebuff.sh ./my-project
```

开启后：
- 启动器会更详细地打印 mount、路径解析步骤。
- 退出时自动 `docker stop` + `docker rm` 容器（默认保留容器以便复用日志）。

### 4.3 把 freebuff 的「项目知识」喂给它

`freebuff` 会读项目根目录下的 `knowledge.md`（项目知识库）。建议在项目里维护：

```
my-project/
├── knowledge.md        ← 项目专属知识/约定/上下文
├── package.json
├── src/
└── ...
```

容器内 `entrypoint.sh` 显式 cp 了 `knowledge.md`，配合通用项目结构（`README.md` / `tsconfig.*` / `vite.config.*` / `public` / `src`）。如果你的项目结构不在这个清单里，**要么补 `entrypoint.sh` 的拷贝列表，要么把项目改造一下**——否则 freebuff 拿到的就是一份空工程。

### 4.4 复用全局凭据

脚本默认读取主机的 `~/.config/manicode/credentials.json`，挂载到 `/workspace/.config/manicode/`，再在容器内拷贝到 `~/.config/manicode/credentials.json`。只要主机上这份文件存在、格式正确，freebuff 启动后即可登录。

### 4.5 同时在容器内查看实时输出

`message-bridge.sh` 会 `tail -f <project>/.freebuff/comm/responses.txt`。如果你想侧录日志：

```bash
# 另开终端
tail -f /path/to/your-project/.freebuff/comm/responses.txt
```

或者直接看容器内日志：

```bash
docker ps                       # 找到 freebuff 容器 ID
docker logs -f <container_id>
```

## 5. 常见踩坑与对策

| 症状 | 根因 | 对策 |
| --- | --- | --- |
| 启动卡在 “Waiting for comm directory and files” | 容器没真正启动 / 没写 `CONTAINER READY` | `docker ps` 看是否在跑；`docker logs <id>` 看 entrypoint 报错；多半是 `PROJECT_PATH` 为空 |
| freebuff 进程没回应 | 凭据缺失或失效 | 确认主机 `~/.config/manicode/credentials.json` 存在且有效 |
| 代码改完容器里没生效 | 容器挂载的是**父目录**，但工作目录在 `/tmp/freebuff_workspace/` 里 | 编辑后要么重启容器，要么改用挂在 `/workspace` 上的真实路径做 in-place 编辑 |
| Windows 下路径不识别 | PowerShell / Git Bash / WSL 路径格式不同 | Git Bash 用 `/c/Users/...`；WSL 用原生 Linux 路径；PowerShell 用 `C:/Users/...` |
| 镜像重建每次都很慢 | `start-freebuff.sh` 在脚本改动时强制重建 | 仅当真的改了 `Dockerfile` / `*.sh` 时才需要；否则 `docker tag` 现有镜像可临时绕过 |
| 容器启动报权限错误 | `.freebuff/comm/` 权限不足 | `chmod -R 777 .freebuff`；脚本默认 `chmod 666` 文件 + `chmod 777` 目录，仍取决于挂载点的 umask |
| `inotifywait` 报错导致消息不发送 | inotify 句柄耗尽或内核参数太小 | `sudo sysctl fs.inotify.max_user_watches=524288`；或在容器里 `cat /proc/sys/fs/inotify/max_user_watches` 看看 |
| `messages.txt` 出现「消息重发」 | 写入和 `inotifywait` 之间存在 race | 在主机端写入时 sleep 0.1 再写，并保证 `messages.txt` 在写完后**整体替换**（write 完整内容），不要 echo 一行 + sleep 一行 |

## 6. 修改/扩展本工具的最佳实践

如果你要 fork 或二次开发（贡献给社区），请遵循 `knowledge.md` 已经沉淀的约定：

1. **镜像小而稳**：`node:20-slim` + `apt-get clean && rm -rf /var/lib/apt/lists/*` 同层；按「系统包 → 构建工具 → npm」顺序装，最大化层缓存。
2. **永远不要直接写挂载卷**：entrypoint 把项目复制到 `/tmp/freebuff_workspace/` 再操作，避免污染主机文件。
3. **不要把消息文件放在项目根目录**：放在 `.freebuff/comm/` 子目录，并 `chmod 666` 文件 / `chmod 777` 目录，方便容器/主机读写。
4. **不要在容器里跑 tmux/screen**：容器主进程本身就是交互式；额外的 session manager 会导致递归执行。用 Docker 自带的 `-it`。
5. **terminal 处理走 expect**：脚本工具用 `expect` 做串口复用，不要试图用纯 bash here-doc 喂 freebuff（readline 缓冲会很别扭）。
6. **保持脚本可移植**：使用 `stat -c %Y` / `stat -f %m` 兼容 BSD/GNU；用 `tput` + ANSI 回退兼容不同终端；不要硬编码 `sed -i`（macOS 不支持）。
7. **双向通信优先用文件 + inotify**，而不是命名管道：易调试、易观察、易恢复。`knowledge.md` 里把两种方案的取舍写得很清楚，请保持文件方案。
8. **日志必须带来源和毫秒级时间戳**：主机打 `[HOST]`，容器打 `[WRAPPER]` / `[CONTAINER]`，并附 `date '+%Y-%m-%d %H:%M:%S'`，便于跨边界关联。

## 7. 适用与不适用

**适合**：
- 你想在任何项目里跑 freebuff，又不想污染主机的 Node/npm/expect 版本。
- 你需要在 CI 或临时容器里跑 freebuff（例如 GitHub Actions 自托管 runner）。
- 你想给团队/学员一个统一可复用的「freebuff 沙箱」。

**不适合**：
- 你希望 freebuff 直接读写主机路径做实时协作——目前 entrypoint 会复制到 `/tmp`，要 in-place 编辑需自行改造。
- 你想做高并发/多用户隔离——每个用户自己起一个容器即可，但共享文件系统会有 IO 争用。
- 你想在 ARM64 / Windows 容器里跑——基础镜像和 `expect` 在某些 Windows 容器上有兼容性问题，请先在目标环境跑通基础 `freebuff` 再用本封装。

## 8. 一份「检查清单」

每次启动前 30 秒自检：

- [ ] Docker 已安装并能跑 `docker run hello-world`
- [ ] `~/.config/manicode/credentials.json` 存在且未过期
- [ ] 项目根目录有 `package.json`（或你想用的构建工具的清单）
- [ ] 项目根目录有 `knowledge.md`，描述你想让 freebuff 知道的上下文
- [ ] 传入的路径是**绝对路径**或脚本相对当前目录解析得到的**已存在目录**
- [ ] 出问题时设 `DEBUG=true` 重跑一次，拿到完整日志后再求助

按这份清单走，绝大多数「卡住」的启动都能在一次重试里恢复。
