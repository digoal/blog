## 一、从终点反向推演：好的Agent框架必须满足什么？

在谈论DeepSeek Harness（以下简称DSH）之前，先做一次思维实验。

如果我们从用户最终需求出发，反向推演一个优秀Agent框架的设计原则，会得到什么？

### 1. 用户只关心结果，不关心你的实现

> 用户说"帮我查今天A股涨跌幅前五的股票"，他不在乎用的是哪个LLM、用了什么提示词技术、接了哪个工具。他只在乎：结果准不准，过程能不能检查，错了能不能撤回。

推演出的设计要求：
- 结果可追溯 → 需要完整的执行日志
- 过程可审计 → 每一步工具调用都要记录
- 错误可回滚 → 需要会话持久化与重放机制

### 2. 用户的需求是变化的，框架必须能扩展

> 今天接搜索工具，明天接代码执行，后天接数据库——用户的Agent永远在变。框架不能每加一个工具就重构一次代码。

推演出的设计要求：
- 插件式架构 → 新能力不需要改核心代码
- 工具是公民 → 工具和模型享有同等地位
- 可热插拔 → 不停机更换实现

### 3. 调试一个Agent比写一个Agent还难

> 当Agent做错事时，你需要知道：是哪一步出错了？是工具返回了垃圾数据？是提示词被污染了？还是模型产生了幻觉？这在传统架构里几乎是黑盒。

推演出的设计要求：
- 全链路可观测 → 事件日志必须完整
- 干预点必须存在 → 在每一步之间都能拦截、修改、拒绝
- 隔离测试 → 能单独测试某个工具或某段提示词

### 4. 不能绑定在任何一家模型厂商上

> 今天用DeepSeek，明天用Claude，后天用GPT-5——用户有权选择，框架不能设壁垒。

推演出的设计要求：
- 模型无关 → LLM是接口，不是绑定
- Provider可替换 → 一行配置切换后端

### 5. 生产级Agent必须能"记住"和"继续"

> 用户让Agent写了一份报告，半小时后回来继续修改——Agent必须记得之前说了什么、做了什么决定、调用了哪些工具。

推演出的设计要求：
- 会话持久化 → 关闭窗口不丢上下文
- 状态可 fork → 能分支探索不同方案
- 会话可分享 → 能导出对话记录给同事

## 二、DSH的答案：一切皆插件，事件即架构

带着这五个设计要求，再看DeepSeek Harness的设计，会发现它不是凭空产生的——它是为解决这些问题而生的逆向工程。

### 核心哲学：没有特权核心

DSH没有"核心代码"需要被扩展。传统框架有一个强耦合的内核，所有功能都围绕它展开——这意味着改核心会影响一切，不改核心又无法实现新需求。

DSH的答案是：没有内核，只有插件。

```text
┌─────────────────────────────────────────────┐
│              DeepSeek Harness               │
│                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ Session  │  │  Tools   │  │   LLM    │  │
│  │  Plugin  │  │  Plugin  │  │  Plugin  │  │
│  └──────────┘  └──────────┘  └──────────┘  │
│                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │  Shell   │  │  Web     │  │ Subagent │  │
│  │  Plugin  │  │  Plugin  │  │  Plugin  │  │
│  └──────────┘  └──────────┘  └──────────┘  │
│                                             │
│  所有插件平等，谁都不是核心，             │
│  每个都是可替换的"零件"                   │
└─────────────────────────────────────────────┘
```

每一个插件向共享上下文（Context）注册自己的服务（Service）、事件（Events）和副作用（Effects）。没有插件能绕过Context直接调用另一个插件，所有依赖都通过`inject`声明——这意味着加载顺序不是写死的，而是由依赖关系自动决定的。

### Cordis：让插件真正"可插拔"的底层框架

DSH的插件架构由[Cordis](https://github.com/cordiverse/cordis)驱动。Cordis提出了一个编程范式：时空可组合性（Spatiotemporal Composability）。

这三个词分别对应：

- Composable（可组合）：插件可以叠加、覆盖、替换，不需要修改原有代码
- Spatial（空间性）：每个Agent可以有自己独立的插件子集（scoped registration），一个Agent的配置不会污染另一个Agent
- Temporal（时间性）：所有注册都是可逆的副作用（Reversible Effects）——插件卸载时，所有它安装的东西都会被干净地拆除

### 事件溯源：Session Log是唯一真相来源

DSH的另一个核心设计：模型看到的一切，必须来自日志。

```
用户输入 → SessionEvent（追加写入）→ 模型历史 ← 工具输出 → SessionEvent（追加写入）
```

没有任何中间状态。Agent的每一次工具调用、每一段模型输出，都以不可变事件追加到Session Log。这带来了一个关键属性：你永远可以用这段日志重建整个对话。

这解决了AI应用中最痛苦的问题之一——Agent做了错误的决策，但你不知道是哪一步出了问题。 在DSH里，答案是：看日志。

### Capability Seams：接口即边界

DSH提出了一个优雅的概念：Seam（接缝）。

一个Seam由三部分组成：

1. Service Definition（接口声明）——这个能力做什么
2. Service Provider（实现）——谁在做
3. Consumer（消费者）——谁来用（通常是模型）

```
  Service Definition（接口）
         △
         │ 实现可替换
  Service Provider A ←─→ Service Provider B
         │
         ▼
     Consumer（模型用的就是这个接口）
```

以文件系统为例：
- 同一个`ctx.fs`接口，可以指向本地文件系统，也可以指向远程沙箱
- 对Agent来说，调用方式完全相同
- 换一个Provider，整个Agent就运行在隔离的沙箱里——无需修改任何工具代码

这就是DSH所说的"换一处实现，整个产品跟着变"。

### Profile + Bundle：可组装的发行格式

DSH通过两层机制分发能力：

- Bundle：一个插件集合的发行格式（cordis.yml + 代码）
- Profile：Bundle的叠加顺序清单

```text
Profile = [bundle/base, bundle/web-app, ...] + 用户patch

用户patch → Home级patch → Profile级patch → Bundle层叠
```

这意味着：
- 用户可以在不fork代码的情况下，修改任何插件的行为
- 不同场景（开发/生产/隔离）可以用不同Profile
- 每个Bundle都是可叠加、可覆盖的增量

## 三、DSH的杀手级特性：站在用户痛点上看

### 1. 热修复而不重启

在传统Agent系统里，如果工具出错了，通常需要重启整个进程。DSH的事件系统让插件可以在运行时卸载、更新、重新加载——因为每个注册都是可逆的副作用，拆除时自动清理所有痕迹。

### 2. 一个Agent，多种身份

通过scoped registration，DSH支持在同一个进程里运行多个Agent，每个Agent拥有独立的工具集、提示词和执行策略。这不是简单的"多租户隔离"——它意味着你可以让一个Agent同时扮演两个角色（分析师+开发者），而不互相干扰。

### 3. Session Fork：分支探索

Session Log是不可变的，但可以Fork。当Agent在解决一个问题时，可以随时"分支"——尝试另一种方案而不丢失原始路径。这比传统的"上下文窗口清理"优雅得多。

### 4. 工具即服务，不只是函数

DSH的工具系统不是"注册一个function"那么简单。每个工具都是完整的Capability：
- 有Schema（模型知道怎么调用）
- 有执行策略（超时、重试、权限）
- 有事件系统（执行前、执行后、异常）

```text
tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
```

每一步都是一个事件瀑布（Waterfall），监听者可以拦截、修改、拒绝。

## 四、为什么这件事重要

### AI Agent的信任危机

今天的AI Agent有一个根本性的信任危机：用户不知道Agent在想什么、在做什么、为什么这样做。传统的LLM应用把一切都押注在"模型足够好"上——但模型会出错、工具会返回垃圾数据、提示词会被prompt injection攻击。

DSH的答案是：不要相信模型，要相信架构。

当每一个操作都被记录、当每一步都有拦截点、当工具的权限被精确控制——即使模型会犯错，整个系统的行为仍然是可预测和可审计的。

### 从"AI Native"到"架构驱动"

过去几年，AI应用开发走了一条弯路：过度依赖模型能力，回避架构问题。 简单场景可以靠LLM的涌现能力解决，但生产级应用需要的不是更好的模型，而是更好的运行时架构。

DSH代表了一种范式转变：从"模型驱动"到"架构驱动"。不是让AI自己管理自己，而是用工程化的架构来约束和放大AI的能力。

## 五、谁应该关注DSH

- AI应用开发者：如果你在构建需要长期运行、可审计、多工具协作的Agent系统，DSH的插件架构会大幅降低复杂度
- 企业AI平台团队：Session Log的持久化 + 细粒度权限控制，是合规审计的基础
- LLM应用架构师：Seam模型让你真正实现"后端无关"——换模型商不需要重写工具
- AI Agent研究者：全链路事件日志让调试和实验变得系统化

## 六、总结：DSH在解决什么问题

| 用户痛点 | 传统方案 | DSH方案 |
|---------|---------|--------|
| 工具扩展需要改代码 | 插件热插拔，但依赖复杂 | 一切皆插件，Context是唯一耦合点 |
| Agent出错不知道哪步问题 | 靠日志，但日志不完整 | 事件溯源Session Log，完整重建 |
| 想换LLM但工具要重写 | Provider绑定 | Capability Seam，接口与实现分离 |
| 多Agent场景隔离困难 | 进程隔离，资源浪费 | Scoped Registration，同进程隔离 |
| 生产环境需要审计 | 事后补日志 | 运行时完整记录，不可篡改 |
| 想分支探索不同方案 | 复制上下文，繁琐 | Session Fork，一键分支 |

---

DeepSeek Harness的本质，是用工程化的严谨来驯服AI的不确定性。

它不承诺让AI不犯错——它承诺让AI的错误可被发现、可被理解、可被修复。

这，才是生产级AI应用该有的起点。
