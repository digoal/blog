## 一句话定义

The Librarian 是一个本地优先的 MCP 服务器，解决了"技能过多反而拖累 Agent"这个根本矛盾——它让 Agent 从"带着全部技能跑"变成"临时问图书馆该用哪个"。

---

## 背景故事：泳池边的一小时

这个项目最独特的地方是它的诞生过程。

2026年6月10日，一个人在泳池边用手机打字，问了这样一个问题：

> *"我装了 3000 个技能，到底装得越多越好，还是越少越好？"*

Claude 的回答很直接：越少越好。 每个技能都会占用上下文 token，描述重叠还会造成触发混乱。50个技能，描述相互干扰，触发变得不确定；8个精准的技能，触发几乎可以预测。

但 collection 有 3000 个。解决方案不是安装更少，而是给图书馆配一个管理员——把 collection 留在磁盘上，Agent 永远不加载它，只在需要时问图书馆。

一小时后，代码就部署好了。泳池边的对话原文保存在 `ORIGIN.md` 里。

## 核心问题：技能过载

### Agent 技能生态的"朴素陷阱"

当前 Agent 框架（Claude Code、Cursor、Windsurf 等）的技能系统有一个根本矛盾：

- 技能数量增加 → 触发不确定性增加
- 技能数量增加 → 每次调用的上下文 token 开销增加
- 技能描述重叠 → 相似技能互相竞争，错误触发

直觉上的"多装技能 = 能力更强"在实践中被证伪。一个设计精良的技能，胜过五个模糊重叠的技能。

### 传统解法的局限

| 解法 | 局限 |
|------|------|
| 减少技能数量 | 人工维护成本高，无法动态适配任务 |
| 提示词工程 | 无法解决 token 开销，触发依然混乱 |
| 按需加载 | 实现复杂，不同框架差异大 |

Librarian 的解法：把"选择权"从中枢（Agent）转移到专门的检索层，让语义搜索 + 多样性算法决定该推荐什么，而不是把所有描述塞进 Agent 上下文。

## 技术架构

### 单文件设计

`server.py` 约 600 行，包含：

```
技能解析 → 向量化 → 存储 → 检索 → 多样性重排 → AFM 可选精排 → 输出
```

无外部框架依赖：`mcp[cli]`（MCP 协议）、`httpx`（Ollama 调用）、`pydantic`（类型验证）。

### 检索管道（5步）

```
intent 输入
  ↓
1. Ollama embed (nomic-embed-text, /api/embed)
  ↓
2. Cosine 相似度搜索 ~3000 个技能向量（SQLite）
  ↓
3. MMR 多样性 + 近因衰减（反单调机制）
  ↓
4. [可选] AFM rerank：Apple on-device model 精排（fit 1-10 + why/why-not）
  ↓
5. JSON 短列表返回
```

### 五大工具

| 工具 | 方向 | 作用 |
|------|------|------|
| `librarian_find` | 只读 | 语义检索，返回排名列表 |
| `librarian_brainstorm` | 只读 | 宽松检索 + 随机 wildcards，发散思维 |
| `librarian_report` | 只写 | Agent 报告结果（worked/false + 备注） |
| `librarian_reindex` | 写入 | 增量扫描，hash 检测变更，只重嵌变化文件 |
| `librarian_stats` | 只读 | 集合健康度摘要：热技能、死亡技能、低成功率技能 |

### 三个反单调机制

MMR（最大边际相关性）多样性重排：
候选技能按相似度排序后，逐个选取——每个新选中的技能不仅要和查询意图相似，还要和已选中的技能不相似，避免推荐三个功能重叠的技能。

近因衰减（Recency Decay）：
最近 N 次（默认10次）被推荐过的技能会受到惩罚分数，防止"三个常客霸榜"。这解决了 v1 的核心问题——"总是推荐同样三个技能"。

Wildcards（Brainstorm 专用）：
在多样性检索结果之外，随机注入 2 个与当前意图无关的技能，给意外留出空间。

## 生产数据：8周运行报告

USAGE-REPORT.md 公开了截至 2026-08-04 的真实数据：

### 核心指标

| 指标 | 2026-08-04 | 2026-07-17 |
|------|-------------|-------------|
| 索引技能数 | 3,125 | 3,030 |
| 服务查询数 | 130 | 87 |
| 活跃天数 | 26/56 | 18/38 |
| Agent 回报率 | ~59% | ~51% |
| 回报"成功" | 37 | 21 |
| 回报"失败/未用" | 39 | 23 |
| 曾被推荐的技能 | 302（9.7%） | 226（7.5%） |
| 从未被推荐 | 2,823（90.3%） | 2,804（92.5%） |

### 关键发现

反馈循环有效且质量在提升。 回报率从 51% 升到 59%，说明 Agent 越用越习惯这个机制。更有意思的是备注的质量——Agent 写的失败原因是诊断性的：

> *"Wrong domain — needed pool→cover assign, not command palette"*
> *"All three recommendations were SwiftData, product brief mandates GRDB"*

负样本的区分价值。 分析 23 个"失败"报告：大多数不是"用了但不好用"，而是"不相关 / 用别的方法解决了"。负样本主要测量的是排序精度，而不是技能质量。这个区分对 curation 决策很重要。

HIG 家族是最成功案例。 `apple-hig-swiftui-macos`、`apple-hig-settings`、`apple-hig-inspectors` 等 8 个技能全部被报告成功——描述精准、触发条件清晰。

近因衰减的双刃剑。 `public-repo-launch` 被推荐、使用、成功——第二天完全相同的意图却得到了不同的推荐，因为那个技能被近因惩罚了。正确的惩罚机制，但实施过激。

## 深层洞察

### 1. 技能生态的结构性问题

当前 Agent 技能生态有一个被忽视的基础设施缺陷：技能描述重叠导致触发混乱，技能数量增加反而降低系统可靠性。 这个问题在"技能市场"出现后会更严重——当用户可以一键安装成百上千个技能，这个矛盾会指数级爆发。

Librarian 是第一个认真对待这个问题的开源项目。它不是去解决"如何写好技能描述"，而是承认描述会重叠，然后从系统层面解决问题。

### 2. 反馈循环设计的经济学

`librarian_report` 是一个非常克制的设计选择：Agent 只能写结果，不能改技能或排名。 决策权始终在人类手里，Agent 贡献数据而非判断。

这解决了一个常见的代理问题：如果 Agent 可以改排名，它可能会为了减少自己的工作量而撒谎（报告假的"成功"）。Append-only + 人类审查的组合，让数据变得可信。

### 3. 公开生产数据的价值

USAGE-REPORT.md 公开了真实的 8 周运行数据，包括失败分析和待改进项。这是工程诚信的体现——没有挑选最好的数字，而是呈现真实分布。

90.3% 的技能从未被推荐过，这个数字告诉我们：技能 collection 存在严重的冗余，但大多数技能不是垃圾，只是和当前任务不匹配。 这些"死亡技能"不是删除候选，而是等待合适的触发时机。

### 4. Librarian 的定位：基础设施而非产品

Librarian 不是一个可以直接使用的"产品"，而是一个基础设施组件。它需要配合：
- 一个 MCP 客户端（Claude Code、Cursor、Goose 等）
- Ollama（本地向量化）
- 一个技能 collection（3000+ 技能）

这个设计让它高度可复用，但也意味着用户需要一定的技术背景才能部署。这是一把双刃剑：技术用户获得了控制权，但非技术用户被排除在外。

## 待改进项（来自生产数据）

1. `librarian_gaps` 的阈值问题： 计划用 0.45 绝对阈值检测"意图空白"，但 nomic-embed-text 的 cosine 相似度实际落在 0.6–0.9 区间，0.45 永远不触发。需要分布相关的阈值（底部十分位 ≈ <0.65）+ outcome 信号组合。

2. 成功清除近因惩罚： `worked: true` 的报告应该重置该技能的近因惩罚，让经过验证的技能不被刻意隐藏。

3. 区分 outcome 词汇： "不相关 / 没使用"和"使用了但失败"是两种不同的信号（排序精度 vs 技能质量），当前笼统为 `worked: true/false`。成本最低的改进：给 `librarian_report` 加一个 `used` 标志。

4. 近因衰减的精细化： 当前衰减是二元的（全有或全无），可以改为渐进的衰减曲线，避免"连续两天相似任务得到不同推荐"的过激情况。
