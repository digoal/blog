## 背景


## 先说结论：DuckDB 2.0 的重点，不只是更快

如果只看标题，DuckDB 2.0 很容易被理解成一次常规大版本升级：新功能更多，查询更快，存储更省。

但把官方预览文章从头读完，会发现一个更重要的变化：DuckDB 正在从“进程内分析引擎”，走向“可连接、可观测、可扩展的数据库平台”。

这不是说 DuckDB 要替代 PostgreSQL、MySQL 或 Spark。更准确的说法是：它正在覆盖过去数据库产品之间的中间地带。

它可以继续嵌在 Python 里，也可以查询 S3 上的湖仓数据；可以作为一次性分析工具，也开始具备长期运行服务需要的能力。

## 01｜为什么 DuckDB 要开始当服务器？

DuckDB 最初的魅力，是“不需要服务器”。

装一个库，打开一个文件，直接写 SQL。对于数据分析、数据科学和本地 ETL，这种体验非常舒服。

但当多个客户端需要共享数据库时，进程内模式就会遇到一个现实问题：谁来持有连接？谁来管理并发？谁来统一观测？

DuckDB 2.0 的答案是 Quack + CONNECT。

一个 DuckDB 进程可以通过 Quack 提供数据库服务，另一个 DuckDB 通过 `CONNECT` 把会话指向远端数据库：

```sql
ATTACH 'quack:server.example.com'
    AS qk (TOKEN 'my_token');

CONNECT qk;
SELECT count(*) FROM events;
DISCONNECT;
```

这里真正值得注意的，不是多了一个连接命令，而是 DuckDB 原本就具备的事务、MVCC 和多连接能力，开始被放到长期运行、多人共享的场景里。

而且 `CONNECT` 不局限于 DuckDB。官方还提到，新的远程下推优化器可以把 SQL 直接发送给 PostgreSQL 和 MySQL，避免把整张表拉回本地再计算。

DuckDB 并没有放弃“嵌入式”路线，而是在嵌入式和服务化之间增加了一座桥。

## 02｜JSON 已经够灵活，为什么还要 VARIANT？

JSON 的优点是灵活，缺点也是灵活。

同一列里可以出现不同结构的数据，但如果数据库把它们简单地当成文本处理，查询、压缩和存储都会付出代价。

DuckDB 的 `VARIANT` 可以理解成“不是文本的 JSON”。

它允许不同记录拥有不同形状，同时自动识别半结构化数据中反复出现的共同结构，并进行 shredding。这样做的好处是：

- 不需要事先声明一个完全固定的 schema；
- 数据仍然可以获得较好的压缩效果；
- 查询可以直接在拆分后的结构上执行；
- 对结构不断演进的日志和事件流更友好。

DuckDB 1.5 已经引入了 VARIANT，2.0 则把这条链路继续补齐：从存储读取、扫描下推，到 Parquet 的读写，再到 `variant_*` 函数。

例如：

```sql
CREATE TABLE events (payload VARIANT);

INSERT INTO events
VALUES ('{"user": {"id": 42}}'::JSON::VARIANT);

SELECT variant_type(payload), variant_keys(payload)
FROM events;
```

这背后的方向很清晰：半结构化数据不应该只能在“灵活”和“高性能”之间二选一。

## 03｜分析数据库为什么需要触发器？

很多人一听到触发器，就会想到传统业务数据库。

但当 DuckDB 开始支持长时间运行的服务，触发器就不再是“为了像某某数据库”而添加的功能，而是审计、同步和自动化逻辑的基础设施。

DuckDB 2.0 支持：

- `BEFORE` 与 `AFTER` 触发器；
- `FOR EACH ROW` 与 `FOR EACH STATEMENT`；
- `REFERENCING OLD/NEW TABLE`；
- 多个触发器；
- 触发器表上的 `RETURNING`；
- `DROP TRIGGER`。

典型场景是审计表：目标表发生更新，触发器自动把旧值和新值写入审计表。

```sql
CREATE TRIGGER trg_audit AFTER UPDATE ON target
REFERENCING OLD TABLE AS o NEW TABLE AS n
FOR EACH STATEMENT
    INSERT INTO audit
    SELECT n.id, o.val, n.val
    FROM o
    JOIN n ON o.id = n.id;
```

这意味着什么？

DuckDB 正在从“我帮你分析数据”，向“我可以参与数据系统的运行”迈进一步。

## 04｜SQL 能不能直接表达相似度搜索？

DuckDB 2.0 还在继续扩大 SQL 的表达边界。

对 AI 和向量工作负载来说，`NEAREST` joins 很值得关注：top-k 相似度搜索可以直接写成 JOIN 子句。

```sql
SELECT q.user_id, t.product_id
FROM users q
JOIN products t APPROX NEAREST 2
BY SIMILARITY array_cosine_similarity(q.embedding, t.embedding);
```

除此之外，2.0 还带来了一批更适合数据流水线的语法能力：

- DML 放进 CTE；
- 嵌套 schema；
- `$变量`语法；
- `json_set`、`json_insert`、`json_replace`、`json_remove`；
- 带 `USING KEY` 聚合的递归 CTE。

这些功能的共同点是：原本需要脚本或 glue code 串起来的步骤，越来越可以被压缩到一条可优化、可组合的 SQL 里。

## 05｜远程 Parquet 的瓶颈，为什么不只是 CPU？

数据放在本地磁盘时，很多人习惯把性能问题归因于 CPU 或内存。

但当数据在 S3 等对象存储上，查询经常是“计算还没开始，数据已经在路上了”。

DuckDB 2.0 把异步 I/O 推进到引擎的多个层面，让 I/O 层和查询处理层能够独立扩展并行度。

官方介绍中，Parquet、CSV 和 DuckDB 自有格式都在接入异步 I/O，同时也加入了新的 `MMAP` 和 `DIRECT_IO` 模式。

网络存储，是这项改动的主要受益者。

此外，DuckDB 2.0 还强化了：

- zone map 对更多类型和谓词的剪枝；
- Parquet Bloom filter；
- 对 `IN`、函数谓词等条件的 row group 跳过；
- 面向 DuckLake、Iceberg 和 Hive 分区 Parquet 的分区感知规划。

这里有一个需要特别说明的官方微基准：

| 版本 | 百万边图递归可达性查询 |
|---|---:|
| DuckDB v1.5.4 | 4.90 秒 |
| DuckDB v2.0 preview | 0.12 秒 |

官方称其约快 40 倍。

但这只是特定硬件、特定数据和特定查询的微基准，不能直接推导出所有生产任务都会获得 40 倍提升。正确的理解是：递归 CTE 引擎重写、聚合下推、磁盘 spill 和更强剪枝，正在系统性降低查询成本。

## 06｜为什么大版本要动存储格式、解析器和扩展 API？

DuckDB 2.0 的底层变化，可能比几个 SQL 新语法更值得长期关注。

### 存储格式 v2.0

新的默认存储格式带来：

- 列元数据惰性加载；
- 默认启用 `DICT_FSST` 字符串压缩；
- 更紧凑的删除存储；
- 更强的损坏校验；
- 更高效的 checkpoint vacuum。

对宽表、大索引和长期运行的数据库来说，打开更快、内存更低，比单次 benchmark 的峰值速度更重要。

### 全新的 SQL 解析器

DuckDB 2.0 使用自研的 PEG-based 解析器。

用户理想上应该感觉不到它，因为设计目标是兼容旧解析器。但对扩展生态而言，意义很大：扩展未来可以参与 grammar，提供新的 SQL 语法；错误信息也能获得更精确的源码位置。

### 稳定 C API

过去很多扩展依赖不稳定的 C++ API，每个版本都需要重新适配和构建。

2.0 扩大稳定 C API，并通过声明式规范生成头文件和 ABI。目标是：扩展可以一次编译、长期复用，再通过可信仓库进行签名和分发。

好的底层重构，不是让用户学习更多，而是让生态能够做更多。

## 07｜DuckDB 2.0 到底在改变什么？

把这些功能放在一起看，DuckDB 2.0 的主线就出来了：

1. 从单进程分析，走向可连接的服务；
2. 从固定结构，走向高性能半结构化数据；
3. 从查询工具，走向包含触发器和观测能力的运行时；
4. 从 SQL 查询，走向数据工程和向量工作流的统一表达；
5. 从本地文件，走向面向对象存储和湖仓的异步访问；
6. 从版本绑定扩展，走向更稳定、更可治理的插件生态。

但这里有一个边界不能忽略：DuckDB 2.0 目前仍是预览。

官方明确表示，正式发布前细节可能变化，并提示新默认存储格式、lambda 语法迁移等 breaking changes。

所以，如果现在要试，建议按这个顺序：

- 用 preview build 在副本数据上验证；
- 测试真实业务 SQL，而不是只跑官方 demo；
- 单独检查扩展、存储格式和 lambda 迁移；
- 为备份、回滚和版本并行运行留出路径。

## 最后：小鸭子没有变成大象，而是覆盖了更多中间地带

DuckDB 2.0 不是“我要替代所有数据库”。

它更像是在重新画一条连续谱：一端是 Python 里的嵌入式分析，另一端是云上的长期数据服务，中间还有湖仓查询、日志处理、向量搜索和轻量多租户场景。

一句话总结：

> DuckDB 2.0 不只是更快的小数据库，而是在把进程内分析引擎推向可连接、可观测、可扩展的平台。
