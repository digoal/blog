## 写在前面：为什么要做开源贡献？

你可能听过"开源"这个词无数次了——GitHub 上几百万个仓库，大到 Linux 内核，小到一个 Markdown 渲染插件。但你有没有想过，**你也可以成为其中的一份子**？

做开源贡献对高校学生来说有三个直接好处：

1. **简历含金量**——"给 XX 开源数据库提交过 PR 并被合入"，这句话比写十个课设都有说服力。
2. **真实工程训练**——学校的代码只需要跑通就行，开源项目的代码要经得起全世界的 code review。
3. **认识一群厉害的人**——开源社区的维护者、贡献者，很多都是业界的资深工程师，他们会认真看你的代码并给你反馈。

这篇文章用一个真实的开源项目—— **OpenTenBase**（腾讯系分布式 HTAP 数据库）做示例，带你走完从注册 GitHub 到合入 PR 的全流程。

**不需要你是数据库专家。** 你只需要会基本的 Git 操作，有一台能上 GitHub 的电脑，再加上一个 AI 编程助手。

---

## 全流程一览

先看全貌，再逐步拆解：

```
注册 GitHub 账号
      ↓
签署 CLA（贡献者许可协议）
      ↓
浏览 Issue，找到你想贡献的
      ↓
在 Issue 里讨论思路
      ↓
申请 Assign（认领任务）
      ↓
Fork → Clone → 新建分支
      ↓
Vibe Coding（AI 辅助编码）
      ↓
写测试用例
      ↓
跑测试（回归测试 + 新代码测试）
      ↓
提交 PR
      ↓
等待审核，按反馈修改
      ↓
合入！恭喜你成为 OpenTenBase 开源贡献者 🎉
```

接下来一步一步来。

## 第 1 步：注册 GitHub 账号

如果你还没有 GitHub 账号，去 [github.com](https://github.com) 注册一个。

**几个小建议：**

- 用户名取一个专业一点的，别用 `xXx_DarkKnight_xXx` 这种——以后简历上要放的。
- 头像放一张正常的图片，不一定是证件照，但别空着。
- 在 Profile 里写几句自己的介绍，比如"XX 大学计算机系大三学生"。

注册完之后，设置好 SSH Key。后面 clone 代码要用：

```bash
# 生成 SSH Key（如果还没有的话）
ssh-keygen -t ed25519 -C "your_email@example.com"

# 查看公钥
cat ~/.ssh/id_ed25519.pub
```

复制公钥，去 GitHub → Settings → SSH and GPG keys → New SSH key，粘贴进去保存。

---

## 第 2 步：签署 CLA

**CLA 是什么？** Contributor License Agreement（贡献者许可协议）——简单说就是一份法律文件，你签了它就表示：*"我贡献的代码是我自己写的（或有权贡献的），我同意项目使用这些代码。"*

**为什么要签？** 这是保护你和项目双方的。没有 CLA，项目无法确认你的代码来源合法；对你来说，CLA 也明确了你的贡献者身份。

**怎么签？** 不同项目有不同方式：

- 有些项目用 [CLA Assistant](https://cla-assistant.io/)——你提 PR 时会自动弹出，点击签署就行。
- 有些项目有专门的 CLA 签署页面。
- 有些项目使用 DCO（Developer Certificate of Origin），需要在 commit 信息里加 `Signed-off-by` 行。

对于 OpenTenBase，去项目仓库 [https://github.com/OpenTenBase/OpenTenBase](https://github.com/OpenTenBase/OpenTenBase) 查看 README 或 CONTRIBUTING 文件中的 CLA 说明，按指引完成签署。如果找不到明确的 CLA 入口，可以在 Issue 区提问——维护者通常很乐意指引新贡献者。

> **提示：** 很多项目的 CLA 签署是一次性的。签完一次，后续所有 PR 都不需要再签。

---

## 第 3 步：找一个你想贡献的 Issue

打开 OpenTenBase 的 [Issues 页面](https://github.com/OpenTenBase/OpenTenBase/issues)。

**新手怎么挑 Issue？**

看标签（Label）——很多项目会给 Issue 打标签：

| 标签 | 含义 |
|------|------|
| `good first issue` | 专门留给新人的，难度低 |
| `help wanted` | 项目组希望社区来做的 |
| `bug` | 修 Bug，通常范围明确 |
| `documentation` | 改文档，对新手最友好 |
| `enhancement` | 新功能/改进 |

**给新手的选择建议（由易到难）：**

1. **文档类**——修错别字、补充使用示例、翻译文档。零风险，适合第一次 PR。
2. **Bug 修复类**——特别是有复现步骤的 Bug，范围明确，不容易做偏。
3. **小功能增强类**——比如增加一个配置项、补全一个边界检查。
4. **测试用例类**——给已有功能补测试。这个对理解代码很有帮助。

> **心态建议：** 第一次 PR 不用追求"改了很多代码"。哪怕只是修了一个文档的错别字，只要走完了完整流程，你就已经超过了 99% 的同龄人。

---

## 第 4 步：在 Issue 里讨论思路

找到想做的 Issue 后，**不要直接动手写代码**。先在 Issue 下面留言，说明：

1. 你想认领这个 Issue
2. 你打算怎么做（简要说思路）
3. 你有什么不确定的地方

**举个例子：**

> Hi, I'm interested in working on this issue. I'm a CS student new to OpenTenBase.
>
> My plan:
> - Read through the related source code in `src/backend/xxx/`
> - Implement the fix by adding a boundary check in `some_function()`
> - Add a regression test
>
> Questions:
> - Should I also update the docs for this change?
> - Is there a specific coding style guide I should follow?
>
> I'd love to be assigned to this issue. Thanks!

**为什么要先讨论？**

- 避免做了半天发现方向不对。
- 让维护者知道有人在做，避免重复劳动。
- 维护者可能会给你关键提示，节省你大量时间。

---

## 第 5 步：申请 Assign

在 Issue 讨论中，你可以直接说"Could you please assign this issue to me?"。维护者会把 Issue 分配给你。

被 Assign 后，这个 Issue 就"归你了"——别人看到也不会重复做。

**注意：** 被 Assign 后要在合理时间内推进。如果一两周都没有动静，维护者可能会取消分配。所以认领了就要行动起来。

---

## 第 6 步：Fork + Clone + 新建分支

### 6.1 Fork

去 [OpenTenBase 仓库](https://github.com/OpenTenBase/OpenTenBase)，点右上角的 **Fork** 按钮。这会在你的 GitHub 账号下创建一份完整的代码副本。

### 6.2 Clone

把 Fork 出来的仓库克隆到本地：

```bash
# 用你自己的用户名替换 YOUR_USERNAME
git clone git@github.com:YOUR_USERNAME/OpenTenBase.git

cd OpenTenBase
```

然后设置上游仓库（upstream），方便以后同步最新代码：

```bash
# 添加上游仓库
git remote add upstream git@github.com:OpenTenBase/OpenTenBase.git

# 验证
git remote -v
# origin    git@github.com:YOUR_USERNAME/OpenTenBase.git (fetch)
# origin    git@github.com:YOUR_USERNAME/OpenTenBase.git (push)
# upstream  git@github.com:OpenTenBase/OpenTenBase.git (fetch)
# upstream  git@github.com:OpenTenBase/OpenTenBase.git (push)
```

### 6.3 新建分支

**永远不要在 `main`（或 `master`）分支上直接改代码。** 新建一个描述性的分支名：

```bash
# 先同步最新代码
git fetch upstream
git checkout main
git merge upstream/main

# 新建分支并切换过去
git checkout -b fix/issue-123-add-boundary-check
```

分支命名建议：`fix/issue-xxx-简要描述` 或 `feat/issue-xxx-简要描述`。

## 第 7 步：Vibe Coding——用 AI 辅助编码

这是最有趣的一步。 **Vibe Coding** 就是用 AI 编程助手来辅助你写代码——你描述需求，AI 帮你生成代码框架，你再审查、修改、测试。

### 为什么要用 AI？

对于一个你还不熟悉的大型代码库（OpenTenBase 有 **17.8 万行 C/C++ 代码**），想要从零读懂每个模块是不现实的。AI 可以帮你：

- **快速理解代码结构**——"这个函数是干什么的？调用链是怎样的？"
- **生成代码草稿**——"帮我写一个边界检查函数"
- **生成测试用例**——"帮我为这个函数写 3 个测试场景"
- **解释错误信息**——"这个编译错误是什么意思？怎么修？"

### 工具推荐

| 工具 | 特点 | 适合场景 |
|------|------|---------|
| Workbuddy | 浏览器插件形态，可读取当前页面上下文（如 Jira 需求、GitHub PR、设计稿），主动感知用户工作状态，支持多轮任务拆解与进度追踪，打通浏览器与本地开发环境的轻量级桥接 | 需求理解与任务分解阶段，例如：读 Jira 需求自动拆子任务、根据 PR diff 生成 review 要点、将设计稿标注转化为前端待办清单；同时也适合日常的信息汇总和跨平台上下文切换 |
| GitHub Copilot | 编辑器内嵌，实时补全 | 写代码时用 |
| Claude / ChatGPT | 对话式，适合问答和分析 | 读代码、讨论方案时用 |
| Cursor / Windsurf | AI-native IDE | 整个开发流程 |
| Antigravity / agy | 终端 AI 助手，可直接操作文件 | 命令行开发 |
 
另外推荐使用 codegraph 生成代码地图, 让 AI 可以更好的理解 openTenbase 代码. 

### Vibe Coding 的正确姿势

**❌ 错误方式：** 把整个 Issue 丢给 AI，让它全部生成，然后直接提 PR。

**✅ 正确方式：** 把 AI 当成你的"资深同事"——你来主导，它来辅助。

**具体操作流程：**

**1) 先理解上下文**

```
你（对 AI 说）：
"我要修复 OpenTenBase 的 Issue #123。
这个 Issue 说的是：在 xxx 场景下，yyy 函数没有检查输入边界，
导致可能的数组越界。请帮我分析一下这个函数的代码，
以及它的调用链。"
```

AI 会帮你梳理代码逻辑。但你要自己验证——打开对应的源文件，对照着看。

**2) 讨论解决方案**

```
你（对 AI 说）：
"我理解了。我的修复思路是在函数入口加一个边界检查，
超出范围时返回错误码。你觉得有没有遗漏的场景？"
```

**3) 让 AI 帮你写代码草稿**

```
你（对 AI 说）：
"请帮我写出这个修复的代码。注意遵循 OpenTenBase 现有的
代码风格——用 Tab 缩进，函数命名用小写下划线风格。"
```

**4) 审查 AI 生成的代码**

这一步最关键——**不要无脑复制粘贴**。你要检查：

- [ ] 逻辑对不对？
- [ ] 有没有影响到其他功能？
- [ ] 代码风格和项目一致吗？
- [ ] 变量名、函数名起得有意义吗？
- [ ] 错误处理完善吗？

> **给同学们的忠告：** 开源社区的维护者对 AI 生成的低质量 PR 非常敏感。如果你直接复制 AI 输出不加审查就提 PR，大概率会被关闭，而且会留下不好的印象。 **AI 是工具，不是替代品。** 最终提交的代码，你要能解释每一行为什么这么写。

## 第 8 步：写测试用例

**没有测试的代码 = 没有写完的代码。**

这一步很多新手会跳过，但它恰恰是区分"写完了"和"做好了"的关键。

### 怎么写测试？

先看项目里已有的测试是怎么写的：

```bash
# 在 OpenTenBase 项目里找测试文件
find . -name "*test*" -o -name "*regress*" | head -20
```

模仿已有的测试格式，为你的修改写测试。你可以让 AI 帮你：

```
你（对 AI 说）：
"我修改了 xxx 函数，加了边界检查。
请帮我写测试用例，需要覆盖以下场景：
1. 正常输入，预期正常返回
2. 边界值输入（刚好在界限上）
3. 越界输入，预期返回错误码
4. 空输入"
```

### 测试的基本原则

1. **正向测试**——正常输入，验证正确输出
2. **负向测试**——异常输入，验证正确的错误处理
3. **边界测试**——卡在边界上的输入
4. **回归测试**——确保你的改动没有破坏已有功能

---

## 第 9 步：跑测试

### 9.1 编译项目

```bash
# OpenTenBase 基于 PostgreSQL，编译流程类似
./configure --prefix=/your/install/path
make -j$(nproc)
make install
```

编译不过？别慌。把错误信息贴给 AI，它通常能很快帮你定位问题。

### 9.2 跑回归测试

**回归测试 = 确保你的改动没有破坏已有功能。**

```bash
# 跑 PostgreSQL 风格的回归测试
make check
```

如果有测试 FAIL，说明你的改动可能影响了已有功能。这时候需要排查——是你的代码引入了 Bug，还是测试本身需要更新。

### 9.3 跑你新写的测试

确保你新加的测试也能通过。

**一个完美的状态是：**
- ✅ 所有已有测试通过（回归测试）
- ✅ 你新写的测试也通过
- ✅ 编译零 Warning（这个不强求，但做到了加分）

## 第 10 步：提交 PR

### 10.1 提交代码

```bash
# 查看改动
git diff
git status

# 添加文件
git add .

# 提交（写清楚做了什么）
git commit -m "Fix boundary check in xxx_function() for issue #123

- Add input validation at function entry
- Return error code for out-of-range inputs
- Add regression tests for boundary cases"
```

**Commit Message 怎么写？**

```
第一行：简要概括（50 字以内）
                                     ← 空行
后续行：详细说明做了什么、为什么这么做
- 改动点 1
- 改动点 2
- 改动点 3

Fixes #123                           ← 关联 Issue 编号
```

### 10.2 推送到你的 Fork

```bash
git push origin fix/issue-123-add-boundary-check
```

### 10.3 创建 Pull Request

推送完后，去 GitHub 上你的 Fork 页面，会看到一个提示："Compare & pull request"。点它。

**填写 PR 描述——这很重要！**

一个好的 PR 描述模板：

```markdown
## What does this PR do?

Fixes #123.

This PR adds boundary checking to `xxx_function()` to prevent
array out-of-bounds access when input exceeds the valid range.

## Changes

- Added input validation at the entry of `xxx_function()`
- Returns `ERROR_OUT_OF_RANGE` for invalid inputs
- Added 4 regression test cases covering normal, boundary,
  out-of-range, and null input scenarios

## How to test

1. Build the project with `make`
2. Run `make check` to verify all regression tests pass
3. Specifically test with: [describe how to manually test]

## Related Issues

Closes #123
```

## 第 11 步：等待审核，按需修改

提交 PR 后，维护者会来审查你的代码（Code Review）。

### 可能会遇到什么？

1. **✅ 直接通过**——恭喜！（不过第一次 PR 很少这样）
2. **💬 Request Changes**——维护者提了修改意见。这是正常的，也是学习的好机会。
3. **❓ 提问**——维护者问你为什么这么实现。准备好解释你的思路。

### 怎么处理修改意见？

```bash
# 在你的分支上继续修改
git checkout fix/issue-123-add-boundary-check

# 做修改...

# 提交修改
git add .
git commit -m "Address review feedback: use safer comparison operator"

# 推送（PR 会自动更新，不需要新开 PR）
git push origin fix/issue-123-add-boundary-check
```

**关键点：推送到同一个分支，PR 会自动刷新。** 不需要关掉旧 PR 再开新的。

### 处理修改意见的心态

- 不要把 Code Review 当成"找茬"——维护者是在帮你写出更好的代码。
- 如果不理解修改意见，礼貌地追问。
- 如果你觉得自己的写法也合理，可以解释你的理由，和维护者讨论。开源社区鼓励技术讨论。

---

## 第 12 步：合入！🎉

当维护者对你的代码满意了，他们会合入（Merge）你的 PR。

**合入之后，你就是 OpenTenBase 的开源贡献者了。**

你的名字会出现在项目的 Contributors 列表里。这是实实在在的、全世界可见的贡献记录。

### 合入后的善后

```bash
# 切回 main 分支
git checkout main

# 同步上游最新代码（包含你刚被合入的改动）
git fetch upstream
git merge upstream/main

# 删除本地的特性分支（已经合入了，不需要了）
git branch -d fix/issue-123-add-boundary-check

# 删除远程的特性分支
git push origin --delete fix/issue-123-add-boundary-check
```

## 常见问题 & 避坑指南

### Q：英语不好怎么办？

A：用 AI 帮你翻译和润色。在 Issue 里讨论、写 PR 描述时，可以先用中文写好思路，然后让 AI 帮你转成英文。OpenTenBase 是国内发起的项目，用中文也可以沟通。

### Q：代码不会写怎么办？

A：从文档类 Issue 开始。修错别字、补充示例、改 README——这些不需要写代码，但会让你走通整个 PR 流程。流程走通了，下次再挑战代码类 Issue。

### Q：提了 PR 很久没人回复怎么办？

A：可以在 PR 下面友好地 @一下维护者。等一两周没回复是正常的——维护者通常都是业余时间做开源。

### Q：我的 PR 被拒绝了怎么办？

A：看维护者的拒绝理由。可能是方向不对、可能是实现方式不好、也可能是项目已经有其他计划了。这不丢人——被拒的 PR 也是宝贵的学习经历。调整后再来。

### Q：怎么保持和上游同步？

A：定期拉取上游的最新代码，保持你的 Fork 是最新的：

```bash
git fetch upstream
git checkout main
git merge upstream/main
git push origin main
```

## 附录：OpenTenBase 代码架构速览

> 以下内容基于 [digoal 的 OpenTenBase 源码剖析文章](https://github.com/digoal/blog/blob/master/202609/20260904_06.md)。

理解项目架构会帮助你更好地选择 Issue 和定位代码。

### OpenTenBase 是什么？

OpenTenBase 是腾讯发起的企业级分布式 HTAP 开源数据库，从 Postgres-XL 演进而来。 **一个 SQL 进来，需要 3 个组件协作完成**：

```
你的 SQL
   ↓
CN (Coordinator Node)     ← 解析 + 重写 + 分布式规划
   ↓
GTM (Global Transaction)  ← 全局事务号 + 全局快照
   ↓
DN (DataNode) × N         ← 实际数据存储 + 执行
   ↓
返回结果
```

### 三大组件

| 组件 | 代码位置 | 代码量 | 干什么的 |
|------|---------|--------|---------|
| **GTM** | `src/gtm/` | 76,237 行 | 全局事务管理——分配全局事务号、管理全局快照 |
| **CN** | `src/backend/pgxc/` | — | 用户接入点——解析 SQL、分布式规划、跨节点聚合 |
| **DN** | 跟 PG backend 类似 | — | 存数据、执行 SQL、返回结果给 CN |

### 关键独有模块

| 模块 | 代码量 | 用途 |
|------|--------|------|
| `opentenbase_ora_package_function` | 49,475 行 | Oracle 兼容包（DBMS_RANDOM / DBMS_LOB / VARCHAR2 等） |
| `pgxc_ctl` / `opentenbase_ctl` | 21,679 行 | 集群管理工具 |
| `pgvector` | 11,912 行 | AI 向量数据库能力 |
| `postgres_fdw` | 10,950 行 | 外部数据源访问 |

**新手选择贡献方向的参考：**

- **想做数据库内核**→ 看 `src/backend/` 下的 Bug 修复类 Issue
- **想做 Oracle 兼容**→ 看 `contrib/opentenbase_ora_package_function/` 相关 Issue
- **想做 AI 方向**→ 看 `contrib/pgvector/` 相关 Issue
- **想做运维工具**→ 看 `contrib/opentenbase_ctl/` 相关 Issue
- **想写文档**→ 看 `doc/` 目录和 README 相关 Issue
