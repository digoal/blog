## 背景  

  
> 当 PostgreSQL 因为 MVCC 机制让 vacuum 性能抖动 40% 时,天翼云 OpenTeleDB 用 contrib/xstore 这个独立模块把它压到 5% 以内。  
> 这篇文章从一行 `UPDATE` 看穿 XStore 的原位更新 + Undo 体系到底怎么实现。  
  
---  
  
## 一、当你给 PG 表发一条 UPDATE,它发生了什么  
  
如果你在 PostgreSQL 上执行:  
  
```sql  
UPDATE orders SET price = 999 WHERE id = 1;  
```  
  
**PG 干了 3 件"不必要"的事**:  
  
1. **产生 dead tuple** —— 新版本写在表里,旧版本标记为 `t_xmax = 你的 xid`  
2. **写两份 heap page** —— 旧版本不删,新版本追加  
3. **写两份 index page** —— 所有索引都更新  
  
**结果**:表越来越大,`vacuum` 必须定期扫表清理 dead tuple,**而 vacuum 跑的时候性能抖动 40% 以上**——这是 PG 原生最大的痛点。  
  
天翼云 OpenTeleDB 给 PG 装的 **XStore 引擎**,用**原位更新 + Undo 体系**把这 3 件事都干掉。

## 三、3 大创新点全部实查(README 说的,我们一个一个验证)  
  
README 第 5-9 行写了 3 大独家能力:  
  
> - **XProxy**:十万级原生连接上限,自动读写分离与负载均衡  
> - **XStore**:原位更新 + Undo 日志,从根本杜绝空间膨胀  
> - **XRaft**:在数据库核内完成自动高可用,杜绝脑裂  
  
我从源码**逐个验证**:


## 四、XStore 原位更新怎么工作的:从代码看真实现  
  
### 4.1 PG 原生的 UPDATE 流程(MVCC 多版本)  
  
PG 的 `heap_update` 干这事:  
  
```  
1. 在 page 里找一个空 slot,放新版本  
2. 把新版本 t_xmin 设为当前 xid  
3. 把旧版本 t_xmax 设为当前 xid(标记被新版本替换)  
4. 更新所有索引  
```  
  
**问题**:旧版本不删,dead tuple 越攒越多,**vacuum 必须扫全表**。  
  
### 4.2 XStore 的 inplace update 流程(看真代码)  
  
我从 `xheapam.c` 找到 XStore 的原位更新函数(注释里明确写 `use_inplace_update = true`):  
  
```c  
// contrib/xstore/src/xheap/xheapam.c:1140  
exec_evaluate_inplace_update(Relation relation, ...,  
                            bool *inplace_update) {  
    bool use_inplace_update = true;  // 默认走原位更新  
    // ...  
    ExecQual...   // 评估 WHERE 条件  
    // ...  
}  
```  
  
**XStore 的原位更新流程**:  
  
```  
1. 找到目标 tuple(用 xstore 的 RowPtr 直接定位)  
2. 把旧版本整行复制到 Undo 日志(不是留在 page 里)  
3. 在原位更新列  
4. 更新索引(索引也是原位更新)  
5. 提交后,旧版本只在 Undo 日志里,不在 heap page 里  
```  
  
**关键代码**:`xheapam.c:1068` `put_inplace_update_xtuple()` 把 inplace update 写盘。  
  
### 4.3 Undo 体系:旧版本去哪了  
  
PG 的 dead tuple 在 heap page 里,等 vacuum 回收。XStore 的旧版本**写入独立的 Undo 日志**:  
  
```  
contrib/xstore/src/undo/   (8,242 LOC)  
├── undolog.c       3,636 行  Undo 日志入口  
├── undobuffer.c    Undo 缓冲区管理  
├── undorecord.c    Undo 记录格式  
├── undofile.c      Undo 文件 I/O  
├── undoxlog.c      Undo WAL 集成  
├── undofetch.c     Undo 历史版本读取(回滚/老快照)  
├── undotxn.c       Undo 事务管理  
├── undoworker.c    Undo 后台 worker(回收过期 Undo)  
└── undodesc.c      Undo 描述符  
```  
  
**Undo 文件存什么**:  
- 旧版本的完整 tuple 数据  
- 旧版本的 xmin / xmax(用于事务可见性判断)  
- 对应 page 的 row pointer(用于反向定位)  
  
**Undo 跟 Heap 的关系**:  
- **Heap page 只有最新版本**——不积累 dead tuple  
- **Undo 文件是"时间机器"** ——任意时间点的版本都能从 Undo 找回来  
- **不需要 vacuum 回收 heap**——只需要 Undo worker 清理过期 Undo  
  
## 五、原位更新在 BTree 索引里怎么做  
  
README 第 8 行写: **"对索引采用原位更新,彻底告别扫表式 Vacuum"** 。我从代码验证:  
  
`contrib/xstore/src/xbtree/` 16,055 行 — 这是**为 XStore 重新设计的 BTree 索引**。  
  
```c  
// contrib/xstore/src/xbtree/xbtvisibility.c:268  
/*  
 * if the index tuple was a non-inplace update, the tuple is now effectively  
 * gone; if it was an inplace update, we just need to check undo...  
 */  
```  
  
**XStore 索引的关键改造**:  
- 索引 tuple 标记**走原位更新**(在原 index tuple 上改 key,而不是 delete + insert)  
- 索引 tuple 跟 Undo 日志挂钩——**老快照能看到老索引**  
- **不需要 vacuum 扫表回收索引 dead tuple**  
  
**这就是 README 宣传的"5% 性能抖动"的真来源**:  
- vacuum 不再扫表  
- 不再处理大量 dead tuple  
- 后台 Undo worker 渐进式清理过期 Undo  
  
## 六、给你 5 个核心概念(给入门者)  
  
如果你是 PG DBA,第一次接触 OpenTeleDB,这 5 个概念先懂:  
  
### 6.1 概念 1:XStore = contrib 扩展  
  
XStore **不是改 PG 内核**,是 contrib 扩展。你升级 PG、迁移 PG 业务时,XStore 表跟 PG heap 表**可以共存**。  
  
```sql  
CREATE EXTENSION xstore;  
CREATE TABLE hot_orders (...) USING xstore;  -- XStore 表  
CREATE TABLE cold_orders (...);              -- 仍是 PG 原生 heap 表  
```  
  
### 6.2 概念 2:原位更新 = heap page 不积累 dead tuple  
  
XStore 引擎下,**每次 UPDATE 只改原 tuple**(把旧版本写到 Undo),heap page **永远不会膨胀**。  
  
### 6.3 概念 3:Undo = heap 之外的"时间机器"  
  
所有历史版本存在 Undo 文件里,跟 heap page **物理分离**。回收只针对 Undo,**不影响 heap 性能**。  
  
### 6.4 概念 4:XProxy = 独立 C 实现的连接池  
  
不依赖 PG 自身的 connection pool(那个很弱),XProxy 是个**独立 C 进程**,基于 epoll,**10 万级连接**不是营销数字。  
  
### 6.5 概念 5:XRaft = 没在代码里找到  
  
这份代码里**没有 XRaft 独立实现**——可能没开源、可能没合并。 **这是个 gap,需要更多信息**。  
  
## 七、专家关心的 4 个工程细节  
  
### 7.1 细节 1:XStore 的"原位更新"跟 zheap 是什么关系  
  
openGauss 2017 年有 zheap(原位更新),PostgreSQL 社区 2019 年也有 zheap 提案。  
  
XStore 跟 zheap 思路类似但实现不同:  
- **zheap**:通过 `TPD`(Tuple Processing Data)机制存 undo  
- **XStore**:独立 Undo 文件体系,跟 heap page 完全物理分离  
  
XStore 的 Undo 体系**借鉴了 zheap 思想**(`undolog.c` 头部有 "Portions Copyright 2020 Huawei Technologies Co.,Ltd")。  
  
### 7.2 细节 2:原位更新对长事务的影响  
  
PG 原生 MVCC 隔离下,长事务会让 vacuum 卡住(因为不能回收被长事务需要的 dead tuple)。  
  
XStore 的 Undo 体系对长事务**更友好**:  
- **Heap 不膨胀**——事务跑了 1 天,heap 也只占那 1 天  
- **Undo 独立清理**——Undo worker 看事务的"高水位线",自动跳过还需要的 Undo  
  
**结论**:长事务场景下,XStore 比 PG 原生更省空间、性能更稳。  
  
### 7.3 细节 3:Undo 文件的清理策略  
  
XStore 的 `undoworker.c` 实现 Undo 后台清理:  
  
```c  
// 简化逻辑(实际代码更复杂)  
if (undo_record.xmax < global_oldest_xmin) {  
    // 这个 Undo 没人需要了,可以清理  
    free_undo_record(undo_record);  
}  
```  
  
**关键点**:`global_oldest_xmin` 是所有活跃事务最老的 xid。  
- 短事务场景:Undo 清理很快  
- 长事务场景:Undo 保留时间长,但 heap 仍稳定  
  
### 7.4 细节 4:索引原位更新的代价  
  
**好处**:不需要 vacuum 扫表回收索引 dead tuple  
  
**代价**:  
- 索引 leaf page 可能碎片化(因为原位更新不重新组织 page)  
- 索引分裂比 PG 原生更频繁  
  
**XStore 的应对**:`xbtree/xbtrecycle.c` 实现 leaf page 整理,但**这个整理是后台渐进式**,不影响 DML 性能。  
  
## 八、给 DBA 的 4 个现实问题  
  
如果你在评估"用 OpenTeleDB 替代 PG",我有 4 个诚实的问题:  
  
1. **你的业务是高频 UPDATE 吗?** 如果是订单状态、账户余额这种,XStore 收益最大;如果你是只读 OLAP,XStore 跟 PG heap 区别不大。  
  
2. **你能接受 XStore 的局限吗?** XStore 跟 PG heap 表**语法基本一致,但少数特性不支持**(如 partial index、某些 index AM)。 **先跑一遍你的 DDL 验证**。  
  
3. **你的索引碎片化能接受吗?** 索引原位更新是"性能换碎片",XStore 跑久了 leaf page 会碎片,**需要定期 `REINDEX CONCURRENTLY`** 。  
  
4. **XProxy 你会用吗?** XProxy 是个独立 C 进程,**部署、监控、运维要单独考虑**。如果你的应用已经用 pgbouncer 跑得好,不一定换。  
  
## 九、给 OpenTeleDB 社区的 3 个建议  
  
我作为 PG 老用户,提 3 个不吐不快:  
  
1. **XRaft 何时开源?** README 提了但代码里没有,这个 gap 让用户**难以信服**。请明确时间表。  
  
2. **XStore 跟 zheap / openGauss MOT 的差异白皮书**:XStore 的 Undo 体系跟 zheap 类似,**技术演进路径要公开**,不要让用户自己去扒代码对比。  
  
3. **XStore 的"索引碎片化"实测数据**:原位更新是性能换碎片,**跑了 1 个月后索引大小、查询性能的变化**需要公开。
