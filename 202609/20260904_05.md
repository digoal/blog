## 一、PG 的 32 位 XID 困境 
  
如果你读过我的前几篇文章,你已经知道:  
- 2016-2021 年,我在博客系列里反复吐槽 PG 的 32 位 XID  
- 2026-08-28,金仓 V009R002C016 发布了"64 位 XID"特性 — 但**实现细节未公开**  
- 2026 年,PG 社区内部讨论了多次"64 位 XID patch",**全部没有合并**(详见 `pgsql-hackers` 邮件列表)  
  
但有一个**最早、最完整、最优雅**的方案,值得单独写一篇文章 — **Heikki Linnakangas 2013 年提出的 "page epoch" 机制**。  
  
它不是把 XID 从 32 位改成 64 位那么简单,它是**不破坏 page 格式、不增加 tuple 头大小、还能把 freeze 从"全表扫"降级为"自然变更"** 的精妙设计。  
  
## 二、入门者能看懂的"半圆困境"  
  
PG 用 32 位 `uint32` 存事务号(`TransactionId`)。这个设计有 3 个独立但交织的问题:  
  
### 2.1 问题 1:43 亿事务的硬上限  
  
一个数据库集群,理论上**最多同时存在 43 亿个事务号**。听起来很多,但电商订单库日均事务量动辄 5000 万 — **4 天就撑爆**。  
  
### 2.2 问题 2:环形 XID 的"半圆"语义  
  
PG 的 XID 不是线性递增,而是**环形**。`uint32` 模 2³² 后会绕回起点。 **为了区分"过去事务"和"未来事务",PG 把 43 亿空间切成两半**:顺时针方向 = 过去,逆时针方向 = 未来。  
  
判断 XID 在不在"过去"的算法是:  
  
```c  
bool TransactionIdPrecedes(TransactionId xid1, TransactionId xid2) {  
    int32       diff = (int32) (xid1 - xid2);  
    return (diff < 0);  
}  
```  
  
### 2.3 问题 3:tuple 必须 freeze  
  
**当 XID 走过"半圆边界"时,老 XID 会变成"未来事务"** — 所有 tuple 上的 t_xmin 都从"过去"变成"未来",**这些数据会从 MVCC 视野里"消失"** 。  
  
PG 的防御机制是 **freeze**:  
- autovacuum 周期性扫表,把超过 frozen 边界的 tuple 标记为 `HEAP_XMIN_FROZEN`  
- 一旦标记,这条 tuple **永远可见**,不再参与 MVCC 判断  
  
**但 freeze 的代价是全表扫描 + 写 IO** — 大表 freeze 一遍可以拖慢整个集群。  
  
## 三、Heikki 方案的核心思想  
  
2013 年 Heikki 在 PostgreSQL wiki 页 `Freezing_XIDs_without_extra_write_I/O` 上发表了一个**核心思想**([原文链接](https://wiki.postgresql.org/wiki/Freezing_XIDs_without_extra_write_I/O)):  
  
> **"The trick is to add a field to the page header indicating the 'epoch' of the XID, while keeping the XIDs in tuple header 32-bit wide"**  
  
### 3.1 翻译成工程师语言  
  
每个 heap page 的 header 里**多存一个 epoch 字段**(32 位或更大)。  
**tuple header 里的 t_xmin 仍是 32 位**。  
但 MVCC 解读一个 tuple 的 XID 时,**真实的 XID 是 `(page.epoch << 32) | tuple.xmin`** 。  
  
### 3.2 关键洞察: **epoch 不是显式存的**  
  
Heikki 方案最精妙的部分: **不显式存 epoch**。  
  
```  
"Instead of storing the epoch explicitly, we infer how old an XID is from PageLSN"  
```  
  
每个 tuple 写入时,它的 t_xmin 真实值是当时分配的 XID。当 XID 走过 2³¹ 边界时(进入新的 half-epoch),PG 在 `pg_control` 文件里**记录这个边界的 LSN**。  
  
```c  
// PG 内部的 epoch 边界表(简化)  
typedef struct HalfEpochBoundary {  
    XLogRecPtr      begin_lsn;       // 这个 half-epoch 开始时的 WAL LSN  
    TransactionId   begin_xid;       // 这个 half-epoch 开始时的 XID  
} HalfEpochBoundary;  
  
// pg_control 里的实际表  
HalfEpochBoundary  half_epoch_boundaries[3]; // 至少 2 个  
```  
  
**当 MVCC 解读 tuple XID 时**:  
1. 读 tuple 的 t_xmin 和它所在 page 的 PageLSN  
2. 查 half-epoch boundaries 表,确定 PageLSN 落在哪个 epoch 内  
3. 用 tuple.xmin + epoch 拼出真实的 64 位 XID  
  
### 3.3 一个具体例子  
  
```  
数据库状态:  
  half_epoch_boundaries[0] = {begin_lsn=0/1000, begin_xid=2^31}  
  half_epoch_boundaries[1] = {begin_lsn=1/2000, begin_xid=3*2^31}  
  half_epoch_boundaries[2] = {begin_lsn=2/3000, begin_xid=4*2^31}  
  
当前最新 XID = 5*2^31 (在第 5 个 half-epoch)  
  
查询遇到一个 tuple:  
  tuple.t_xmin = 100  
  tuple.page.PageLSN = 1/1000  (在 half_epoch_boundaries[0] 和 [1] 之间)  
  
MVCC 判断:  
  PageLSN 1/1000 落在 half_epoch_boundaries[0] 之后, [1] 之前  
  所以 page 上的 XID 真实范围是 [2^31+1, 3*2^31-1]  
  tuple.t_xmin = 100 → 但 100 < 2^31+1 → 实际 XID 是 100 + 2*2^31 (最近一次 epoch 重置)  
  
  注意:这本质上是"半 epoch"的偏移量计算  
```  
  
**关键**:tuple.xmin 仍是 32 位,但 page epoch 让 MVCC 能解读出"真实 64 位 XID",**不需要改 tuple header 大小**。  
  
## 四、方案的 3 个核心优势  
  
按 wiki 原文:  
  
> " **The biggest advantages of this idea are: Freeze XIDs without extra disk I/O. No need to add additional info in pages. Don't break the disk compatibility.** "  
  
### 4.1 优势 1: **Freeze 不需要写 IO**  
  
**核心洞见**:传统 freeze 必须"扫表 + 写元组头"。  
**新方案:freeze 只在 page 已经被更新时才发生**。  
  
```  
传统 freeze:  
  autovacuum 扫整张表  
  对每个未冻结 tuple 写新的 infomask  
  → 大量磁盘 IO  
  
新方案 freeze:  
  - tuple 的 t_xmin 不需要 freeze  
  - page 上的 XID 范围由 PageLSN 推断  
  - freeze 只在 UPDATE/DELETE 时发生(写 page 自然)  
  → 不需要专门的 freeze 流程  
```  
  
### 4.2 优势 2: **page 格式完全兼容**  
  
**核心洞见**:32 位 epoch 字段**不需要显式存**。Heikki 用 PageLSN 反推 epoch。  
  
```  
传统 page header 24 字节:  
  pd_lsn, pd_checksum, pd_flags, pd_lower, pd_upper, pd_special, pd_pagesize_version  
  
新方案 page header:  
  (不变) 24 字节  
  + (可选) 32 位 epoch,放在 pd_special 里  
  
或者:  
  完全不变 — 用 PageLSN 反推 epoch  
```  
  
**代价:每个 page 多 4 字节**(如果显式存 epoch),**或者 0 字节**(如果用 PageLSN 推断)。  
  
### 4.3 优势 3: **磁盘兼容性**  
  
```  
传统 page format:  
  page (24 byte header + data) — 32-bit XID  
  
新方案 page format (选项 A):  
  page (24 byte header + 4 byte epoch + data) — 64-bit XID  
  
  兼容性: 不兼容 — 旧 PG 读 28 byte header 会解析错  
  
新方案 page format (选项 B, Heikki 偏好):  
  page (24 byte header + data) — LSN-based  
  
  兼容性: 兼容 — 旧 PG 仍能读,只是不能解读 epoch  
```  
  
**选项 B(Heikki 偏好)实现了真正的磁盘兼容** — 老数据库文件可以原样读,只是新功能(epoch 解读)失效。  
  
## 五、关键技术细节  
  
### 5.1 Half-epoch 边界表的设计  
  
Heikki 在 wiki 里说:  
  
> "Since any transaction cannot be running for more than 2^31 XIDs consumed, the page could span at most 2 ranges and we need to remember at least 2 ranges' begin-LSN: prev-range and current-range."  
  
**关键数学**:  
- 一个 tuple 在被 UPDATE/DELETE 前,它的 XID 最多"老"2³¹  
- 所以一个 page 上的 tuple XID 最多跨 **2 个 half-epoch**  
- 因此 `pg_control` 只需要存**最近 2 个 half-epoch 边界**  
  
### 5.2 Freeze 时机变了  
  
```  
传统 PG freeze:  
  1. autovacuum 周期性扫表  
  2. 对每个未冻结 tuple 写 HEAP_XMIN_FROZEN  
  3. IO 成本高  
  
Heikki 方案 freeze:  
  1. 不需要专门 freeze 流程  
  2. UPDATE/DELETE 时,自然产生新 tuple 版本  
  3. 老版本被清理(dead tuple 回收)  
  4. 无需修改 page header  
  5. IO 成本接近 0  
```  
  
**但有个 corner case**:完全不更新、不删除的 tuple 怎么办?  
- 这种 tuple 的 PageLSN 永远不变  
- PageLSN 指向的 epoch 可能已经走远  
- 此时,MVCC 需要"显式冻结" — **Heikki 方案**用 `autovacuum_freeze_max_age = 2*10^9` 兜底,**仍要扫,但只扫有未冻结 tuple 的 page**  
  
### 5.3 CLOG truncate 的简化  
  
传统 CLOG truncate 的动机: **"XID 要循环了,老 XID 的提交状态可以被冻结覆盖"** 。  
Heikki 方案下: **XID 不再循环(变成 64 位半 epoch 推进)** ,**CLOG truncate 频率大幅降低**。  
  
## 六、Alexander Korotkov 2017 年的改进  
  
2017 年 Heikki 跟进了一个新版本([pgsql-hackers 邮件](https://postgresql.org/message-id/CAA4eK1%2B097Bu6jHrUrebmdcokeO_z36-wP34-w8fpER1j_gbhQ%40mail.gmail.com))。Alexander Korotkov 提议: **不要用 PageLSN 推断,而是在 page header 显式存 base XID**。  
  
```c  
typedef struct PageHeaderData {  
    // 原来 24 字节  
    FullTransactionId  pd_base_xid;  // 新增 8 字节,这个 page 的 XID 起点  
    // ...  
};  
```  
  
**tuple 的 t_xmin 不变**(仍是 32 位),但**真实 XID = `page.pd_base_xid + tuple.t_xmin`** 。  
  
**优势**:  
- 不依赖 LSN,逻辑更清晰  
- MVCC 判断时不需要查 half-epoch 表  
- **page header 多 8 字节**(比 LSN 方案多 4 字节)  
  
**Tom Lane + Heikki 的反馈**:  
- Tom Lane:担心 index page 也加 8 字节是浪费(index 不需要 base XID)  
- Heikki:可以把 base 放在 heap page 的 special space,index page 不放  
  
## 七、为什么 PG 没合并这个方案  
  
**这不是技术不够好,是 PG 决策保守**:  
  
### 7.1 原因 1: **XID wraparound 还没真发生**  
  
PG 的 freeze 机制虽然笨,但**有效**。过去 20 年,绝大多数 PG 实例靠 autovacuum 没出过 wraparound 事故。 **没有火烧眉毛的痛点 → 没有动力**。  
  
### 7.2 原因 2: **改 page format 影响生态**  
  
PostgreSQL 的生态(备份工具如 pgBackRest、监控如 pg_stat、复制如 pglogical) **都依赖 page 格式**。改 page header 加 epoch,这些工具全部要改,**社区不愿意承受**。  
  
### 7.3 原因 3: **真痛点是长事务**  
  
PG 的"freeze 风暴" 真实根因是**长事务 + autovacuum 跳过 page**。改进 autovacuum 长事务跳过算法(2018 年后已多次优化)比改 XID 架构更直接。 **先治标(autovacuum 改进),再治本(64 位 XID)** 是 PG 社区的工程哲学。  
  
### 7.4 原因 4: **没合并 PoC 还在 64 位 XID 上跑** ([2017 年 Heikki](https://postgresql.org/message-id/5370D323.1070606@vmware.com))  
  
PG 社区在邮件列表里反复讨论,但**没有 committer 接手**。Heikki 自己是 PG core team,**他提交过 64 位 XID 提案但被搁置**。  
  
## 八、专家关心的实现细节  
  
### 8.1 Half-epoch 边界表的实现  
  
```c  
// src/include/access/transam.h (Heikki 方案)  
typedef struct HalfEpochBoundary {  
    XLogRecPtr      begin_lsn;  
    TransactionId   begin_xid;        // 这是绝对 XID,不是 32 位  
    TransactionId   begin_xid_mod;    // begin_xid mod 2^32  
} HalfEpochBoundary;  
  
// pg_control  
typedef struct ControlFileData {  
    // ...  
    HalfEpochBoundary  half_epoch_boundaries[2];  
    // ...  
} ControlFileData;  
```  
  
**注意**:`begin_xid` 是真实的 64 位 XID(没发生 wraparound),`begin_xid_mod` 是它 mod 2³² 的值(用于快速比较)。  
  
### 8.2 MVCC 解读 tuple XID 的算法  
  
```c  
// heap tuple visibility check (伪代码)  
bool HeapTupleSatisfiesMVCC(HeapTuple tup, Snapshot snap) {  
    XLogRecPtr page_lsn = PageGetLSN(tup->page);  
    int epoch_idx = find_epoch_by_lsn(page_lsn, half_epoch_boundaries);  
    TransactionId epoch_xid = half_epoch_boundaries[epoch_idx].begin_xid;  
  
    // 真实 XID = epoch 起点 + tuple.xmin  
    FullTransactionId real_xid = epoch_xid + tup->t_xmin;  
  
    // MVCC 判断  
    return XidInSnapshot(real_xid, snap);  
}  
```  
  
**关键**:`epoch_xid + tup->t_xmin` 是 64 位加法,结果真实是 64 位 XID。  
  
### 8.3 PageLSN 推断 epoch 的算法  
  
```c  
int find_epoch_by_lsn(XLogRecPtr lsn, HalfEpochBoundary *boundaries) {  
    // 线性扫描,因为最多 2 个 epoch 边界  
    for (int i = 1; i >= 0; i--) {  
        if (lsn >= boundaries[i].begin_lsn) {  
            return i;  
        }  
    }  
    // 不应该到这里,fallback 用最旧 epoch  
    return 0;  
}  
```  
  
### 8.4 升级路径  
  
Heikki 方案**完美支持升级**:  
- 旧 PG(无 epoch):page LSN 仍然存在,只是 `half_epoch_boundaries` 数组为空,fallback 到当前 32 位算法  
- 升级到新 PG:`half_epoch_boundaries` 自动初始化,新写入的 page 走 epoch 路径,老 page 走 fallback  
- **不需要停机 + 不需要全表 rewrite**  
  
**对比 zheap / zedstore**:这些实验项目**需要全表 rewrite**,Heikki 方案优势明显。  
  
## 九、对 PG 18 / 19 的启示  
  
PG 18 邮件列表里**仍然没合并 64 位 XID**。原因不是技术不够好,是**社区优先级**。  
  
按 Heikki 方案的成熟度,**完全可以分阶段合并**:  
  
**阶段 1**(短期,半年):  
- 引入 half-epoch 边界表(写入 pg_control)  
- 引入 epoch 推断函数  
- **不改 page format**  
- **向后兼容**:新功能只对新 page 生效  
  
**阶段 2**(中期,1-2 年):  
- 引入 freeze 优化:autovacuum 不再扫 all-visible page  
- 引入 vacuum_max_freeze_age 兜底  
- **autovacuum IO 降 50%+**  
  
**阶段 3**(长期,3-5 年):  
- 引入 64 位分配号(分配层 + tuple header 同时改)  
- **完全消灭 wraparound 风险**  
  
**这个 3 阶段路径**比金仓"一步到位"更稳健 — 金仓的"64 位 XID"如果没有阶段 1 的铺垫,直接做阶段 3, **代码改动量极大,容易出 bug**。  
  
## 十、对金仓的启示  
  
金仓 V009R002C016 公开宣称"支持 64 位 XID"。 **具体实现未公开**,但**有可能采用 Heikki 方案**的某些思想:  
  
- **如果采用 page epoch**:每个 page 多 4 字节,但 page format 兼容性较好  
- **如果采用 base XID in page header**:每个 page 多 8 字节,但逻辑更清晰  
- **如果采用 tuple header 64 位化**:tuple 多 12-16 字节,但最彻底  
  
**我推测金仓最可能采用第三种(tuple header 64 位化)** ,因为:  
- 金仓的版本说明说"分配层 64 位",但**没说 page 兼容性**,**暗示 page format 变了**  
- 中国信创数据库**不需要 100% 兼容 PG 生态**,可以接受 page format 变化  
- tuple header 64 位化 = 真正的 64 位 XID  
  
**但**: **没公开实现,这一切都是推测**。  
  
## 十一、入门者看完这一篇应该能讲清的 5 个点  
  
### 11.1 32 位 XID 的本质  
  
不是"4 字节存事务号"那么简单,**而是 4 字节的事务号 + 环形比较 + 半数冻结**。理解 PG 的 MVCC 必须理解"半圆"。  
  
### 11.2 Freeze 的本质  
  
不是"清理老数据",**而是"防止老 XID 跨过半圆变未来"** 。理解 freeze 必须理解 wraparound。  
  
### 11.3 Heikki 方案的核心思想  
  
不是"把 XID 改成 64 位",**而是"在 page header 存 epoch,让 32 位 tuple XID 仍能表达 64 位信息"** 。理解这个方案的关键是 **"信息冗余"** 。  
  
### 11.4 PageLSN 推断 epoch 的精妙  
  
LSN 天然是**单调递增的物理时间戳**。XID 走过 2³¹ 边界时,记下当时的 LSN,**回溯任意 tuple 的 epoch 不需要额外存**。理解这个关键是 **"用物理时钟代替逻辑时钟"** 。  
  
### 11.5 升级路径的工程价值  
  
不改 page format → **旧 PG 文件仍能读**(升级无风险)。Heikki 方案的最大学术价值不是"64 位", **是"无破坏升级路径"** 。  
  
## 十二、专家能看懂的 5 个隐藏陷阱  
  
### 12.1 陷阱 1:index page 也需要 base XID 吗?  
  
Heikki 方案里,**index page 不需要 base XID**。理由:  
- Index page 上的 XID 只是"key 是否在某个事务后被删除"  
- MVCC 不解读 index 的 XID 做可见性判断  
  
**Tom Lane 担心**:万一未来有 index 需要解读 XID,改 schema 很难。  
  
### 12.2 陷阱 2:half-epoch 表会膨胀吗?  
  
不会。 **最多 2 个 entry**(prev + current)。定期 swap。  
  
### 12.3 陷阱 3:PageLSN 推断能完全可靠吗?  
  
**不能 100% 可靠**:  
- crash recovery 时,page LSN 可能还没刷盘  
- 此时 tuple 的 LSN 可能小于实际 epoch 边界 LSN  
- 需要 fallback 机制: **"epoch 边界 LSN 比 page LSN 小时,用最旧 epoch"**  
  
### 12.4 陷阱 4:长事务的 page epoch 怎么处理?  
  
长事务(运行 > 2³¹ 事务) **理论上不可行**(wraparound 风险)。  
但 Heikki 方案下,**长事务的 XID 仍被分配**(不是真阻塞),**只是它的 snapshot 不能跨越 epoch 边界** — 否则 tuple 可见性错乱。  
  
### 12.5 陷阱 5:CLOG truncate 不能完全省  
  
虽然 wraparound 没了,但 CLOG 仍会无限增长(每个提交事务写 2 bit)。 **仍要 truncate**,只是频率大幅降低。  
  
## 十三、写在最后  
  
**Heikki 2013 page epoch 方案**是 **PG 社区 13 年来最优雅、最完整的 64 位 XID 改造方案**。 **它没合并不是因为技术不够好**,**是因为 PG 社区保守 + 没有 merge committer 接手**。  
  
金仓 V9 的 64 位 XID 改造, 不管是哪种实现方式, **都站在 Heikki + Robert Haas + Alexander Korotkov 这些前人肩膀上**。 **值得致敬**。  
  
**下一次 PG 社区真的合并 64 位 XID,大概率就是 Heikki 这个方案的某个变体**。
