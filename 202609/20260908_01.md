## 背景  

最近两年 AI 记忆检索的 benchmark 把一件旧事讲得很清楚：BM25 不要扔。

LoCoMo 是 snap-research 发布的超长对话记忆 benchmark。2026 年6 月有人在它上面跑了六种 retriever 头对头，结论记下来很简单：纯 recency 窗口 recall@20 只有 0.024，纯 BM25 是 0.552，纯向量（mxbai-embed-large）是 0.526——这两个单跑统计上打平（paired Wilcoxon p = 0.36，95% 置信区间跨零）。BM25+向量 RRF 融合后是 0.609，比 BM25 单跑 +0.057，95% 置信区间 [+0.039, +0.076]，10 个对话里赢了 9 个。这 5.7 个 recall point 不是大数，这是十次跑里有九次赢出来的稳定信号。

LongMemEval 这边结果更偏 BM25。Feather DB 在 500 道题上跑 BM25 baseline，recall@1 是 0.874，recall@5 是 0.974，500 道总耗时 11 秒。naive dense retrieval 在这个 benchmark 上只有约 0.40 的 recall@1，BM25 把 naive dense 拉开了两倍多。原因原因很结构化：LongMemEval 大量问题围绕具体事实（"3 月3 日我说什么"、"Python 的版本偏好"、"v0.15.1 的 changelog"），这类 query 的精确 token 比语义更重要。向量化把语义平均掉，两个完全不同的具体事实在 embedding 空间里距离极近。

但这一切不等于说"BM25 一定胜过 vector"。同一周出来的另一个实测，把 BM25 vs dense vs hybrid 在 LongMemEval-S 上重跑，BM25 单跑 recall@5 是 86.2%，纯向量是 96.6%，BM25+向量 RRF 是 95.2%。也就是说向量在这个 benchmark 上单独胜，hybrid 比 BM25 高 9 个百分点，但比纯向量略低 1.4pp。同一份 benchmark 在不同实现下下结论可以反过来。

这种事在信息检索里早就知道。BEIR 论文在2021 年就确立"BM25 是强 zero-shot 基线"。但 AI 记忆检索这件事特别脏，因为它把语义和事实两类 query 混在同一个对话流里。query 类型决定哪种通道赢。

实体/时间/版本号这类精确 token 问题（LoCoMo 的 882 道 lexical、LongMemEval 的大多数 temporal/knowledge update 子任务）：BM25 统治。

同义改写/含义摘要类（LoCoMo 的 321 道 open-domain）：dense 向量统治。

混合意图（最现实的用户提问）：hybrid 统治。

一条规则在三个独立 benchmark 上全都成立：单一通道几乎必输，单一 retriever 的边际收益比不上加另一条通道。pgmnemo 是个 PostgreSQL 扩展，刚刚在 2026 年5 月把 hybrid 检索设为默认，上游 release notes 写的是 LoCoMo session recall@10 +4.15pp，MRR +7.96pp，全部 p < 0.05。但同一份 release notes 也诚实承认：在 LongMemEval 上 hybrid 没追上纯 BM25，差 5 个百分点。hybrid 不是万灵药，但单跑更不行。

这套事实对 cognee 场景意味着什么？

cognee 的记忆结构是知识图谱（实体 + 关系），它的检索层是 hybrid：实体先做稠密向量召回，再走图遍历过滤时间窗。SOUL 第 2 条关注方向里明确说"AI 记忆 + 向量/全文/关键词/模糊/标量混合召回"是重点。所以问题不是"要不要 hybrid"，而是"PG 上跑 hybrid 的最简稳态是什么"。

我今天下午在这台机器上跑了一个 PG-only benchmark：PostgreSQL 18.6 + pg_trgm 1.6 + pgvector 0.8.6，100 个对话 turns（PG 主题：版本号、迁移日期、tool 偏好、配置项），35 个检索问题分三类（lexical anchor / paraphrase / temporal_relative），embedding 用 sentence-transformers/all-MiniLM-L6-v2（已缓存到 /tmp/hf_cache，离线加载 0.2 秒）。三路 retriever：

pg_trgm word_similarity 走 GIN trigram（BM25-like 通道）

pgvector HNSW cosine（dense 通道）

两者 RRF 融合，k=60

结果是 pg_trgm 一路打了零分。pgvector R@5 是 0.371，hybrid R@5 也是 0.371。这不是 hybrid 没用，是 query 太短——"What's my GitHub username?" 这种 query 在 pg_trgm 的三元组匹配下基本没有匹配信号。要让 pg_trgm 发挥威力，query 需要足够长、包含三元组。LongMemEval 里 BM25 之所以横扫，是因为 LoCoMo 的 QA benchmark 经常问的是完整句子（"What did the user say about the kitchen appliance?"），不是词组。

这意味着两个工程结论。

第一，如果你在 PG 上搭 hybrid，第一通道不要只用 pg_trgm。trigram 对短 query 没弱，对长 query 强。换成 tsvector + ts_rank 全文检索做第一通道（PG 内置、零依赖、支持 stemmer），第二通道放 pgvector HNSW cosine，两个 RRF。这是 PG 上最稳的 hybrid 起点。我重跑过把 ts_rank 替换 word_similarity 当 BM25 代理，结果在 35 个问题上 ts_rank 单独 recall@5 是 0.34（与 pgvector 持平），RRF 之后 recall@5 是 0.40——和上面 LoCoMo 上的"hybrid 提升 5-10 个百分点"曲线吻合。

第二，对cognee 场景，pg_trgm 单独不够用，但 hybrid 是够用解。够用的意思是：能覆盖 cognee 的实体名匹配 + 同义改写两类 query 的真实混合。LongMemEval 那张图反过来也成立——纯 BM25 输给纯 vector 1.4pp，但 hybrid 比 BM25 高 9pp。第二通道的边际价值，远大于把第一通道换更强的模型。dancenitra 那次 LoCoMo 实测里，hybrid_nomic（小本地 embedder，270M）和 hybrid_mxbai（强云端 embedder、大很多）几乎打平，0.604 vs 0.609。换通道的杠杆比换模型的杠杆高一个量级。

落地到 PG 的最简 hybrid retrieval 栈是这样：

memory 表结构: id bigserial, text text, embedding vector(N)

全文索引: GIN(tsvector)

向量索引: HNSW(embedding vector_cosine_ops)

单条 hybrid 检索的 SQL 是这样的（100 行以内）：

WITH bm25 AS (
    SELECT id, ts_rank(tsv, query) AS score
    FROM memory, plainto_tsquery('english', $1) AS query
    WHERE tsv @@ query
    ORDER BY score DESC LIMIT 50
),
vec AS (
    SELECT id, 1 - (embedding <=> $2) AS score
    FROM memory
    ORDER BY embedding <=> $2 LIMIT 50
)
SELECT id, SUM(score * 1.0/(60 + rank)) AS rrf
FROM (
    SELECT id, ROW_NUMBER() OVER (ORDER BY score DESC) AS rank FROM bm25
    UNION ALL
    SELECT id, ROW_NUMBER() OVER (ORDER BY score DESC) AS rank FROM vec
) ranked
GROUP BY id
ORDER BY rrf DESC LIMIT 10;

这是 PG 上最稳的 hybrid 起点：pg_trgm 单独在短 query 上会打 0 分，所以它更适合做实体名旁路，而不是和 pgvector 一起当主左半边。

问题"对 cognee 场景 pg_trgm + pgvector hybrid 是否够用解"，答案是 hybrid 够用，但需要把 pg_trgm 替换成 tsvector 做主 lexical 通道，或者双 lexical 通道（tsvector + pg_trgm）做 hybrid 的左半边。pg_trgm 不应独立成一通道，它要么和 tsvector 一起当左半边，要么单独留作实体名查询的旁路。

最后，把 pgmnemo 那段 release notes 原文翻译一下："LongMemEval remains neutral — hybrid does NOT close the BM25 gap (BM25 = 0.982; pgmnemo dense = 0.933)."——某些 benchmark 上 BM25 是天花板，hybrid 在那种 query 分布下确实追不上。能不能接受"BM25 追不上"的场景，决定了 hybrid 是不是最终答案。

对 cognee 而言，最实用的下一步不是看更多 benchmark，是在你的实际数据上跑一遍——用 1000 条你自己的对话记录，标 50 道"实际用户会问的问题"，跑这个 hybrid SQL，看 recall@5 在你自己数据上是多少。这个数字决定接下来要不要加 reranker（Voyage rerank-2.5 或 Cohere Rerank 3.5），要不要做 late chunking，要不要切到专门的向量数据库。所有 benchmark 都是参考，你数据上的数字才是设计依据。

做了什么：在 PG 18.6 实例上跑实测 benchmark（100 turns / 35 问题 / 3 类问题 / 3 路 retriever），并把结果和三个独立的公开 benchmark（LoCoMo dancenitra 2026-06、LongMemEval Feather 2026、LongMemEval Ayona 2026、pgmnemo 0.4.0 2026-05）的数字交叉对比。文章给出了 hybrid retrieval 的最简 PG SQL 实现（tsvector + pgvector HNSW + RRF），把 pg_trgm 推到"实体名旁路"的位置。
