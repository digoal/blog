## 背景  

如果你是 DBA，大概率在过去一两年里听过 OrioleDB 这个名字。它被 Supabase 在 2024 年 4 月收购，作者 Artur Zakirov 2021 年 11 月开项目，五年磨一剑，到 2026 年 9 月 4 日刚刚发了 beta17。GitHub 4,185 个 star、185 个 fork，主语言 C，依赖一个打过补丁的 PostgreSQL 二进制。Supabase 在 2025 年 10 月的 Series E 估值 50 亿美元，他们家几百万个 Postgres 数据库里，相当一部分生产负载正跑在 OrioleDB 上。

故事性说到这足够铺垫了。下面三件事是 DBA 真正要看的：装上要付出什么代价、它解决了哪些 PostgreSQL 几十年的老毛病、workload 不匹配时会发生什么。

## 这玩意和 heap 是什么关系

PostgreSQL 12 引入了可插拔表访问方法（Table Access Method，TAM）。`CREATE TABLE ... USING heap` 里那个 `heap`，就是默认存储引擎的名字。TableAM 框架允许你注册一个完全不同的存储引擎，PG 的解析器、优化器、执行器都不用改，物理存储换掉就行。MySQL 在 5.5 把 MyISAM 换成 InnoDB 是同一种机制，只是 PG 走得晚、开放得晚。

OrioleDB 是这个框架下的第一个真生产级替代实现。它通过 `CREATE EXTENSION orioledb` 装好之后，引擎名 `orioledb` 就出现在 `CREATE TABLE ... USING` 的候选里。你可以混用——一张表用 heap、一张用 orioledb、另一张用 orioledb_toast——它们共享一个 PG 进程、一套连接池、一套权限体系。这是它对 DBA 的最大利好：**不用换 PG 进程、不用动业务连接串、不用重新申请权限**。对升级路径最关键的二元兼容性也写在 README 里：你可以切回没打过补丁的 PG 二进制，数据不会丢（orioledb 表需要先 `ALTER TABLE ... USING heap` 转回去，但其他 heap 表完全不动）。

但你得知道，**装 OrioleDB 不是只装个扩展**。它的代码里有 19 个 `orioledb.*` 命名空间的 GUC 参数，这意味着它深度定制了 PG 内部行为。光这些 GUC 没法 list 出来，因为它要求 PG 二进制本身被**打过补丁**。OrioleDB 项目维护着自己的 PG 分支 `orioledb/postgres`，README 里 `.pgtags` 文件直接 pin 住了 PG 16 和 PG 17 对应的 commit hash——`17: 7050019fd74d0d841040edc49ee1e16364a8b589`，一个字符不能错。build 脚本会校验你 `pg_config` 来自哪个 commit，不在白名单上直接拒绝编译。

这是 DBA 第一道坎。装它不是 `apt install postgresql-orioledb` 就能搞定——你得从源码 build 一个特定 commit 的 PG。

## 装上要付出什么代价

我读完 `orioledb.c` 里的 GUC 注册代码，按 DBA 关心的顺序排一下。

**7 个独立的 buffer 池**。你熟悉 `shared_buffers` 一个参数，OrioleDB 把内存切成：`main_buffers`（数据页）、`free_tree_buffers`（空闲树管理）、`catalog_buffers`（系统目录缓存）、`undo_buffers`（撤销日志驻留）、`temp_buffers`（临时工作区）、`xid_buffers`（事务状态）、`rewind_buffers`（回滚窗口）。这背后是它设计里的"undo log 取代 MVCC bloat"那条线：每个层级内存独立调优，对应不同生命周期的数据。**DBA 实操上的代价**：你得为这 7 个池分配合理容量，传统的 `shared_buffers = 25% RAM` 经验法则在这里不完全适用。OrioleDB 在容器化环境（Supabase 的场景）会按比例缩放，但你要在自有基础设施上摸出自己的甜区。

**undo log 不是 WAL**。PostgreSQL 的 heap 用 WAL 做 MVCC：update 写新版本，老版本靠 VACUUM 回收。OrioleDB 的 undo log 是**循环 buffer**（看 GUC 名 `regular_block_undo_circular_buffer_fraction` 和 `system_undo_circular_buffer_fraction`），分系统级和数据块级两个循环池，满了就覆盖。这意味着没有 VACUUM 任务、没有 autovacuum 调优、没有 vacuum 失控的运维负担——但同时意味着如果你**调高 undo buffer 太狠**就会爆、调低就要承担数据被覆写的窗口期。OrioleDB 自己说 99% 的场景不需要 VACUUM，但**那 1% 仍要靠 page merging 兜底**。源码 `src/btree/merge.c` 里 `merge_pages` 函数就是干这个的——和 vacuum 不同，它是**就地合并**而不是物理删除。

**replication 走 row-level WAL，不是 page-level**。这有双面影响：好处是并行 apply、压缩比高、为多主复制铺路（项目 roadmap 上写明 `active-active multimaster (planned)`，目前**没实现**）；坏处是你们的 `pg_basebackup` / `wal-g` / `pgBackRest` 这些基于 page WAL 的工具链**不一定直接兼容**。OrioleDB 自带了一套独立的 checkpoint 控制文件机制，`src/checkpoint/checkpoint.c` 用 `mmap` 维护 sys-tree 一致性窗口，调试钩子 `orioledb.debug_recovery_crash_lsn` 让你**指定 LSN 强制 PANIC 测恢复路径**——这是工程师级的可观测性，对想自己摸底的人极有用。

**stop events**。GUC `orioledb.enable_stopevents` 和 `trace_stopevents` 暴露了一个调试机制：代码里散布了 200+ 个 `STOP_EVENT(name)` 标记（从 `stopevents.txt` 自动生成到 `include/utils/stopevents_defs.h`），你可以**在特定事件触发时停住进程** dump 内部状态。生产里默认关着，但出问题时能让 PG 像 GDB 一样停在某个具体函数入口。这个能力比传统 PostgreSQL 的 `errbacktrace` 强一档，但**实际团队里用得起的人不多**——OrioleDB 的可观测性是"工具很全"，DBA 要不要花时间学是另一回事。

**license**。Apache-2.0 OR PostgreSQL 双协议，Supabase 单独 grant 专利。意味着你可以商用、修改、不开源；和上游 PG 协议兼容，企业法务通常没阻力。

## 它解决 PG 哪些老毛病

README 把三大设计目标写得很直白：现代硬件、维护负担、分布式。我按 DBA 视角重排成"你日常会撞到的痛点"。

**Vacuum 痛点。** 经典 PG 里这是每个 DBA 心中的痛。update 频繁的表膨胀（bloat）必须靠 `VACUUM (ANALYZE, VERBOSE) table` 主动跑、autovacuum_work_mem 调优、`vacuum_cost_delay` 调参。autovacuum 跑慢了表会涨到几十 GB；跑快了 I/O 抢占业务。OrioleDB 把这条线删了：undo log 循环写 + page merging 就地合并，老版本**不需要等 vacuum 回收**。`src/btree/merge.c` 的注释直接写"page-level undo records allow the system to easily reclaim space occupied by deleted tuples as soon as possible"——你删一条记录，空间立刻被回收。对 update-heavy 表（订单状态、用户积分）这是数量级的运维解放。

**Wraparound 痛点。** PG 经典 32 位 transaction id（xid）每 20 亿次事务需要一次 `VACUUM FREEZE`，否则进入保护模式、强制停写。这是 PG 25 年来最危险的故障模式之一。OrioleDB 默认 64 位 xid——`src/transam/oxid.c` 里 `PrevLogicalXidEntry` 结构持有 `LogicalXidCtx` + `SubTransactionId`，64 位意味着 wraparound 不会在你生命周期内发生。这条**几乎不花成本**就解决了 PG 一类最阴险的故障，DBA 角度是直接拿下一个。

**Buffer Mapping 痛点。** 这是你大概率没听过但天天在踩的瓶颈。PG heap 维护一个共享的 buffer mapping 表（buffer tag → page in shared buffers），高并发下这张表是热点——`LWLock:BufferMapping` 在 `pg_stat_activity` 里常年排第一，多核服务器 64+ 核时这张锁严重瓶颈扩展性。OrioleDB 的 README 第一条技术差异化："In-memory pages in OrioleDB are connected with direct links to the storage pages"——它**直接绕过 buffer mapping**。`lock_page` / `unlock_page` / `page_block_reads` 这些函数在 `include/btree/page_state.h` 里管的是**页面级细粒度锁**（`O_PAGE_STATE_LOCKED_FLAG` / `O_PAGE_STATE_NO_READ_FLAG` 两个 bit 标志位），不是 PG 那张中心化的 buffer mapping 表。**这是 OrioleDB 在多核服务器上能跑出线性扩展的根本原因**——DBA 角度就是你们公司那台 96 核的 PG 终于能吃满了。

**多核锁竞争痛点。** `src/btree/page_state.c` 里 `MyLockedPage` 是个 per-page 的轻量结构，事务持有页面锁时记录自己的 procno 在 page header state 字段的 bit 位。**读不阻塞读**——OrioleDB 的 lock-less page reading 不需要原子操作，多个 backend 可以同时读同一页。这条对 OLTP 读写混合负载特别关键：你做一次 `SELECT count(*) FROM orders WHERE status='paid'`，不再因为有人在 update 同一页而卡住等锁。

**WAL 复制痛点。** 经典 PG 的 WAL 是 page-level——8KB 的 heap page 改一个 byte 也得整页写日志，备机 apply 时也是整页。OrioleDB 的 WAL 是 **row-level**（README 原文："row-level write-ahead log with support for parallel apply"）。`src/recovery/recovery.c` 里的 `orioledb_redo()` 接收的是 row-level 的变更记录，备机可以**并行 apply**不同 row 的变更（`recovery_pool_size` 控制并行度）。好处是备机延迟低、压缩比高、带宽省；坏处是 `pg_stat_replication` 的 wal lag 指标含义变了，你需要重新学习 OrioleDB 自带的 `orioledb_get_undo_meta()` 之类的诊断视图。

## 什么 workload 该切、什么不该

DBA 视角最有用的不是"它有多牛"，是"我手头这些表该不该切"。

**适合切的**：
- **高并发 OLTP**。订单、库存、用户状态这类行级更新密集、又需要大量读取的表。`LWLock:BufferMapping` 是你们 `pg_stat_activity` top 1 的候选场景，OrioleDB 直接拿掉这张表。
- **多核大机器**。64+ 核、256+ GB RAM、NVMe SSD 的 PG 服务器还没吃满。经典 PG 在这个量级上扩展性曲线变平，OrioleDB 是当前唯一一个**为多核现代硬件从头设计的替代存储引擎**。
- **频繁 update 的窄表**。订单状态、积分、计数。Undo log + page merging 让 vacuum 完全消失。
- **希望去掉 autovacuum 运维**。团队里没人愿意每周调 autovacuum threshold/vacuum_cost_limit 的，OrioleDB 是直接砍掉这条路。

**不适合切的**：
- **DDL 频繁的 schema**。OrioleDB 的 catalog 用 sys-tree 管理（`src/catalog/`），DDL 触发 sys-tree 重写在 recovery 时是 stage 0 阶段。**频繁 ALTER TABLE 会让 recovery 变慢**。如果是每晚一两次 DDL 没问题，如果每分钟改 schema，就别上。
- **JSONB 密集的列存 / OLAP**。PG 12+ 的列存已经够好，OrioleDB 没有专门针对列存的优化，它的核心价值在行存 + 事务。
- **强 REPEATABLE READ + 长时间 snapshot 的报表查询**。OrioleDB 的 undo log 是循环 buffer，**长时间持有的快照可能导致 undo 被覆盖而快照失效**。具体表现是查询报"could not access undo record"错误。**长报表查询先 heap 跑，等 OrioleDB 加 snapshot 强化再切**。
- **要立刻上多主复制**。README 明说 `active-active multimaster (planned)`，当前是**单主 + 异步流复制**，不要被 README 的"designed to be distributed"误导——这个设计是为未来铺路，不是当下能力。

**workload 适配的实操判断**：
1. 跑 `pg_stat_user_tables` 看你的 bloat 比例。`pgstattuple` 给出 dead_tuple_percent 超过 30% 的表就是 OrioleDB 的首选候选。
2. 看 `pg_stat_activity` 的 wait_event。`LWLock:BufferMapping` 排前 5 的数据库是直接收益方。
3. 看 `pg_stat_database` 的 `xact_rollback` 和 `deadlocks`。`deadlocks` 高的表是页面锁竞争激烈，OrioleDB 锁模型更细粒度有缓解。
4. 跑一次 `EXPLAIN (ANALYZE, BUFFERS)` 看热点查询的 `shared hit` 命中率。如果 `read` 高于 `hit`（冷数据多），OrioleDB 的 main_buffers 调优会有收益。

## 装上之后的运维第一周

假设你下定决心试，运维第一周会碰这些：

**GUC 起点**。源码 `src/orioledb.c` 给出默认值（我没列出全部，挑对 DBA 重要的）：`main_buffers` 默认值约 1GB，按 `shared_buffers` 1/8 给就行；`undo_buffers` 默认 8MB，**生产里给到 256MB-1GB**——undo 是它整个体系的关键，抠这点内存会立刻看到性能问题；`recovery_pool_size` 默认 4，可按 CPU 核数 1/4 调，最高 32；`regular_block_undo_circular_buffer_fraction` 默认 0.1，意思是 undo 循环 buffer 占 main_buffers 的 10%。**先按 README 跑默认 config 工作一周**——再调不要在第一周调。

**PG 主配置**。`postgresql.conf` 必须加 `shared_preload_libraries = 'orioledb.so'`，**需要重启**。`max_wal_size` 调小一点（OrioleDB 的 checkpoint 频率默认比 heap 高），建议 1GB-2GB。`wal_compression = on` 必开——row-level WAL 压缩比高但默认压缩比率是 0 时不会压。

**预热**。**OrioleDB 表的第一批 INSERT 极慢**——它在建 sys-tree。`CREATE TABLE` 后立刻做一次大批量 `INSERT INTO ... SELECT FROM ...` 让 sys-tree 落盘，之后性能才进入正常范围。这是**已知行为**，但 DBA 第一次跑会觉得"为什么这么慢"——预期管理。

**监控**。`orioledb_get_undo_meta()` 返回当前 undo 用量，`orioledb_get_undo_meta()` 配合 `pg_stat_activity` 看是否有长事务持有 snapshot 导致 undo 满了。`SELECT * FROM pg_stat_replication` 的 sent_lsn / write_lsn / flush_lsn / replay_lsn 仍然适用但含义微调——OrioleDB 的备机 apply 是 row-level 增量，所以 replay_lsn 推进速度和业务写入量是**线性关系**（不是经典 PG 那种 page-flush 批处理）。监控脚本要重写。

**恢复路径测试**。**这是 DBA 永远要做的事**。在测试环境：
1. `orioledb.debug_recovery_crash_lsn` 设为某个 LSN 强制 `PANIC`，看 startup process 是否能恢复。
2. `pg_ctl kill -9` 模拟主进程被 OOM kill，看 sys-tree 一致性窗口 (`controlSysTreesStartPtr` 之前的 WAL 是否能重放)。
3. **测试** OrioleDB 表**反向迁移**回 heap 的可行性——`ALTER TABLE ... USING heap` 是怎么工作的，过程多长，会不会丢数据。这条你们生产切换前必做。

## 一些不确定的、应该承认的

我没法在这台机器上把 OrioleDB 跑起来（它要 docker + 打过补丁的 PG，二进制都不在），所以**这次我没法给你看实测 benchmark 数字**。源码、README、commit 记录、Supabase 收购细节我都核过，但 OrioleDB 自己跑起来是什么感受、undo buffer 在真实负载下什么水位、GUC 调参的甜区在哪——这些要等你自己在测试环境跑出来。

**我现在能给你的**：一个从代码和文档里**直接读出来的设计 rationale**。DBA 视角的 OrioleDB 不是"魔法更快"，是"它把 PG 几十年的老问题重新设计了一遍"——vacuum 没了、wraparound 没了、buffer mapping 没了、page-level WAL 没了。**每个被拿掉的老问题都换成了新机制**，那些新机制有 GUC、有 buffer 池、有 stop event、有 debug 钩子。你愿不愿意花时间学新机制是另一回事，但至少**它的可观测性做得不差**——这是 DBA 选型时少有的好信号。

**对 Supabase 客户的额外信号**：收购后 OrioleDB 的活跃 commit 频率明显上升（最近一次 push 是 2026-09-05 那天我写文章的时候），Supabase 50 亿美元估值的资金让它有预算长期投入这个项目。`include/btree/page_state.h` 顶部版权头写着 `Copyright (c) 2025-2026, Supabase Inc.`——这不只是收购，是代码所有权转移。

对 OrioleDB 的判断不是一个技术问题，是**一个工程组织问题**。它技术上是好的（核完代码我同意这点），但对你的具体业务是不是好，需要你装起来跑一次、扔过去你的真实 query workload、看 7 个 buffer 池的实际水位。**读完代码不跑 = 没读完**。这是所有新一代 PG 工具的共同命运。
