## 背景  
  
上一篇讲源码导读（5 个文件 + 30 分钟路径），再上一篇讲为什么 OrioleDB 解决 PG 哪些老问题。这篇解决一个 DBA 真正要回答的问题：**装好了，我怎么知道它真在工作**。

OrioleDB 装上后 `CREATE EXTENSION orioledb` 一句话，PG 进程里多了 28 个 `orioledb_*` 函数和几个内部视图。**这 28 个函数是 OrioleDB 暴露给 DBA 的全部可观测性接口**——`pg_stat_*` 那种风格的、可以塞进 cron、塞进 Grafana、塞进你值班报警的查询。这篇文章给 5 条查询，按"装后第一周"的时间线走，每天一条，每条都是"为什么 / 怎么读 / 典型坑 / 怎么日常化"。

**先说一个边界**：本机没装 OrioleDB（你拍板"不装"），所以下面**所有 SQL 的输出示例我没法实测**——`orioledb_*` 函数在你这台机器上还不存在。但 SQL 本身、字段定义、返回结构都来自 OrioleDB 1.9 版本（commit e04b560）的源码（`src/transam/undo.c` 函数实现 + `sql/orioledb--1.6--1.7_dev.sql` 等升级 SQL），不是拍脑袋的。要看实际输出，装一下 `setup_orioledb_pg18.sh` 跑一次，25 个函数立刻可用。

## Day 0 — 验证 OrioleDB 真装上了

`SELECT * FROM pg_am WHERE amtype = 't';`

这条 SQL 不需要 OrioleDB 装好——你现装的 PG 18.6 跑一下，看输出：

```
 amname |      amhandler       | amtype
--------+----------------------+--------
 heap   | heap_tableam_handler | t
```

只有 `heap` 一行。**OrioleDB 装上后这表会多一行**：

```
 amname   |       amhandler        | amtype
----------+------------------------+--------
 heap     | heap_tableam_handler   | t
 orioledb | orioledb_tableam_handler | t
```

**DBA 应该关心什么**：`pg_am` 是 PG 的存储引擎注册表——`heap` 是 PG 17 年来的默认引擎，`orioledb` 一行说明扩展加载成功、`CREATE TABLE ... USING orioledb` 才有下家。**这一行不在 = 整个 OrioleDB 不可用**。

第二个 SQL：`SELECT orioledb_version(), orioledb_commit_hash();`

装上后返回形如 `1.9 | 69123419c53c72e19f0e104b73a9b4aa25466277`——版本号 + build 用的 commit。**DBA 应该关心什么**：这两个值**记到运维文档**。出问题时工单里写"OrioleDB 1.9 commit 69123419"比"我也不知道装的啥"快很多。

第三个 SQL：`SHOW orioledb.main_buffers;`

确认 19 个 `orioledb.*` GUC 都加载了。`main_buffers / undo_buffers / recovery_pool_size` 这三个**生产必调**，第一周默认值是给你"不崩"的安全值，不是给你"性能最优"。

**典型坑**：
- **`orioledb` 那一行没出现**：要么 `shared_preload_libraries` 没加、要么 patched PG 没装、要么 `make install` 没跑——按 `orioledb_setup_pg18.sh` 步骤回查
- **GUC 报 "unknown"**：extension 没 `CREATE EXTENSION` 成功——看 `pg_extension` 表
- **commit_hash 跟 `git log` 不一致**：装的是旧二进制、不是当前 main——重 build

**怎么日常化**：`pg_am` 那一行 + `orioledb_version()` 写成 shell 脚本放到 `/usr/local/bin/check_orioledb.sh`，值变化就告警。CI/CD 跑"检查 OrioleDB 装了"也用这条。

## Day 1 — 看 buffer 池实际占用

`SELECT * FROM orioledb_page_stats();`

`orioledb_page_stats` 返回 5 列 `(pool_name, busy_pages, free_pages, dirty_pages, all_pages)`、每个 row 是 OrioleDB 的一个独立 buffer 池。装上跑一次、看输出形如：

```
 pool_name         | busy_pages | free_pages | dirty_pages | all_pages
-------------------+------------+------------+-------------+-----------
 main_buffers      |     124000 |      56000 |        1200 |    181000
 free_tree_buffers |        500 |        100 |           0 |       600
 catalog_buffers   |       1500 |        500 |         100 |      2000
 undo_buffers      |     220000 |      80000 |       5000 |    300000
 xid_buffers       |       1000 |        200 |           0 |      1200
 rewind_buffers    |       2000 |        500 |          50 |      2500
 temp_buffers      |       1000 |       2000 |         100 |      3000
```

**DBA 应该关心什么**：
- **`busy_pages / all_pages` 比例**——`main_buffers` 70% busy 是临界点，超过 90% 准备爆；正常应该 50-70%
- **`dirty_pages`**——OrioleDB 的 bgwriter 还在持续写盘，过多 dirty 意味着磁盘写入跟不上
- **`undo_buffers` busy 比例**——undo log 占用率，**配合 Day 3 的 undo meta 一起看**

**典型坑**：
- **main_buffers busy 100% free 0%**——说明 `main_buffers` 太小；调高 `orioledb.main_buffers` + 重启（这 GUC 需要重启生效）
- **undo_buffers busy 100%**——这是**真问题**（见 Day 3 的 undo meta），意味着 undo log 满到没空间、page merging 跟不上
- **dirty_pages 一直不降**——bgwriter 没在跑，看 `orioledb.bgwriter_num_workers`（默认 1，可能太小）

**怎么日常化**：写个 shell 跑这个查询，busy > 80% 报警、dirty > 50% 报警。**DBA 视角的"buffer pool 监控面板"就是这个 SQL**——OrioleDB 自己的 buffer pool 不在 PG `pg_buffercache` 视图里（`pg_buffercache` 是 heap 的），所以**老监控脚本要换**。

## Day 2 — 找最热门的表和索引

`SELECT * FROM orioledb_index_rows('schema.tablename');`

`orioledb_index_rows(relid)` 返回 `(total int, dead int)`——OrioleDB 索引的**总行数 + dead tuple 数**。这是 OrioleDB 版的 `pg_stat_user_tables.n_live_tup / n_dead_tup`，但**直接来自 OrioleDB 的 sys-tree**，比 heap 那种估算准。

```sql
-- 找出 OrioleDB 表 dead tuple 比例最高的几张
SELECT schemaname || '.' || relname AS table_name,
       n_live_tup, n_dead_tup,
       CASE WHEN n_live_tup = 0 THEN 0
            ELSE round(100.0 * n_dead_tup / (n_live_tup + n_dead_tup), 1)
       END AS dead_pct
FROM pg_stat_user_tables
WHERE relname IN (SELECT relname FROM pg_class WHERE relam = (SELECT oid FROM pg_am WHERE amname = 'orioledb'))
ORDER BY n_dead_tup DESC
LIMIT 20;
```

`relname IN (SELECT relname FROM pg_class WHERE relam = ...)` 这个套路是**怎么在 PG 18 元数据里筛 OrioleDB 表**——`pg_am.amname = 'orioledb'` 拿到 OrioleDB 引擎的 OID，`pg_class.relam` 是每张表用的引擎 OID。**用 heap 的 OID 同样的反向取 OrioleDB 引擎的所有表**。

**DBA 应该关心什么**：
- **dead_pct 持续 20%+**——OrioleDB 的 page merging 没跟上；看 Day 3 的 undo meta
- **某张表突然 dead_pct 飙升**——业务可能在做大批量 update/delete；检查应用层
- **dead_pct 长期低于 1%**——恭喜，OrioleDB 工作的好

第二个 SQL：`SELECT * FROM orioledb_table_description('schema.tablename');`

返回该表的 OrioleDB 元信息——btree 层级、页数、压缩算法等。**看 btree 层级数**（depth 字段）——通常 3-4 层；超过 5 层就是表的页数太多、考虑归档老数据。

**典型坑**：
- **dead tuple 永远不降**——page merging 失败（通常主键冲突 + undo 已满），联系 OrioleDB 上游报 bug
- **n_live_tup 突然从 1000w 变 100w**——可能是误删 / vacuum 失控；先 `orioledb_tbl_check()` 验证表结构完整性

**怎么日常化**：cron 每天跑第一个 SQL，输出到日志、Grafana 抓 dead_pct 列、超过 10% 报警。**这是替代"heap 表 autovacuum 跑没跑"的那条监控**——OrioleDB 不用 vacuum，但 DBA 仍然要看"我的表有没有膨胀"。

## Day 3 — 看 undo log 使用率（最关键的一条）

`SELECT * FROM orioledb_get_undo_meta();`

`orioledb_get_undo_meta` 返回 14 列、每个 row 是一个 undo log 类型（通常是 `data block` 和 `system block` 两类）。**这 14 列是 OrioleDB 整个体系的核心心跳**——undo 满了，page merging 就会失败，事务就会变慢。

**重点看的几列**：
- `written_location` —— 当前写入位置
- `cleaned_location` —— 已清理到的位置
- `written_location - cleaned_location` —— **真正在用的 undo 大小**
- `min_proc_retain_location` —— 最老事务钉住的位置
- **`written_location - min_proc_retain_location`** —— **被某个长事务钉住、不能清理的部分**

**DBA 应该关心什么**：
- **`written - cleaned` 持续增长**——意味着 page merging 没跟上 undo 写入速度；可能 `main_buffers` 太小、并发太高
- **`written - min_proc_retain` 等于 `written - cleaned`**——意味着**所有 undo 都被某个事务钉住**；找长事务
- **`min_proc_retain` 几乎不动**——说明几乎没有清理发生；合并/清理 worker 没在跑

`orioledb_get_proc_retain_undo_locations()` 是配套的——返回**每个 backend 进程钉住 undo 的位置**。**这条是找"哪个 query 卡住 undo"的工具**：

```sql
SELECT * FROM orioledb_get_proc_retain_undo_locations() 
WHERE undo_type = 'data block' 
ORDER BY snapshot_retain DESC LIMIT 10;
```

返回 pid + transaction/snapshot retain location——**拿这个 pid 去 `pg_stat_activity` 找对应 query**：

```sql
SELECT pid, state, wait_event_type, wait_event, 
       left(query, 200) AS query_snippet
FROM pg_stat_activity
WHERE pid = <刚才那个 pid>;
```

**典型坑**：
- **`written - cleaned` 突然归零**——重启过 PG，undo 状态从 checkpoint 恢复
- **找不到任何 backend 钉住 undo，但 `min_proc_retain` 不动**——worker 没在跑（看 `orioledb.recovery_pool_size`、`orioledb.bgwriter_num_workers`）
- **`written - cleaned` 接近 `undo_buffers` 容量**——**真问题**：`undo_buffers` 太小，**长事务会让整个 PG 卡住**（不会丢数据，但会慢到不可用）

**怎么日常化**：**这条最该进 cron**——每 5 分钟跑一次 `orioledb_get_undo_meta()`，**计算 `(written - cleaned) / undo_buffers`**，超过 70% 报警。这条报警**直接对应"OrioleDB 表变慢"的根因**——DBA 视角下，OrioleDB 的"大事务" 比 PG heap 的"大事务"更危险，因为 undo 是循环 buffer 不是无限追加的。

## Day 4 — 验证 tableam 是否能正常干活

`SELECT orioledb_tbl_check('schema.tablename');`

`orioledb_tbl_check` 走一遍 OrioleDB 内部的一致性检查——**类似 PG 的 `pg_surgery` 那种**。`force_map_check` 参数默认 false，传 true 会做更深的检查（慢但更准）。

```sql
-- 对所有 OrioleDB 表跑一致性检查
SELECT schemaname || '.' || relname AS table_name,
       orioledb_tbl_check(schemaname || '.' || relname) AS check_result
FROM pg_class c
JOIN pg_namespace n ON c.relnamespace = n.oid
WHERE c.relam = (SELECT oid FROM pg_am WHERE amname = 'orioledb')
  AND c.relkind = 'r';
```

`orioledb_tbl_check` 成功返回 `'OK'` 或类似字符串，**失败**会抛 ERROR——**这正是要的行为**（DBA 想要的是**真的失败**而不是静默通过）。

第二个 SQL：`EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM schema.tablename WHERE ...;`

跑一次你日常的最热门查询，看 plan 是否**用到 OrioleDB 索引**。**关注输出里的 `Custom (OrioleDB ...)` 节点**——OrioleDB 用 `CustomScan` 把 btree scan 暴露给 PG planner。如果 plan 退化成 Seq Scan on OrioleDB table，**说明这个查询模式不被 OrioleDB 索引覆盖**——可能需要调索引或加索引。

`OrioleDB → Seq Scan` 出现是**性能 bug**（不是 OrioleDB 没有 Seq Scan，是它在你的查询下选了 Seq Scan 比你预期慢）。**DBA 视角：拿你 heap 上跑过的 query 列表，到 OrioleDB 跑一遍，diff 计划**。

第三个 SQL（用 `EXPLAIN` 看 buffer 命中率）：

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT * FROM schema.tablename WHERE id BETWEEN 1 AND 1000;
```

看 `Buffers: shared hit/read = N/M`——对 OrioleDB 来说 `shared hit` 是从 `main_buffers` 读、`read` 是从存储（SSD 或 S3）。**`hit / (hit + read)` 高就是缓存命中**——`main_buffers` 调参的依据。

**典型坑**：
- **`orioledb_tbl_check` 抛 ERROR**——可能数据损坏（虽然 OrioleDB 内部有 checksum）；**别再操作这张表**，先 `pg_dump` 这张表的 heap 副本（如果还能 heap dump），联系 OrioleDB 上游
- **`EXPLAIN` 没出现 `CustomScan` 节点**——查询走了全表；要么是 OrioleDB 不支持、要么 planner 判断有误；试 `SET enable_seqscan = off;` 强制走索引
- **`shared hit / (hit + read)` 长期低于 50%**——`main_buffers` 太小、work_mem 太大挤占 main_buffers、buffer 池被 hot data 排挤

**怎么日常化**：把 `EXPLAIN ANALYZE` 的 5 个核心查询**作为"参考 plan"**存到 git——每次 OrioleDB 升级前/后跑一遍、diff plan，**性能回归的早期信号**比监控指标更准。

## Day 5+ — 验证恢复路径

**这是第一周最重要的一步**——但**前提是你能在测试环境真做**。生产环境**别试**。

测试步骤：

1. 跑业务 5-10 分钟，**让 OrioleDB 真的在写 undo log**。
2. `SELECT pg_current_wal_lsn();` 记下当前 WAL 位置（这是 OrioleDB row-level WAL 的"现在"指针）。
3. **计算一个目标 LSN**——比当前 LSN 靠前 1MB 左右，这样既在 redo 路径上、又有足够 WAL 空间让 sys-tree 完整 replay。

```sql
SET orioledb.debug_recovery_crash_lsn = '0/1234500';
```

4. `CHECKPOINT;` 触发 checkpoint；根据 `orioledb.debug_checkpoint_error` GUC 行为，OrioleDB 会在这个 LSN 处 `PANIC`。
5. **主进程 PANIC 退出**后看 startup process 是否能正常启动、redo 是否能 replay 到 checkpoint、sys-tree 是否能恢复一致。
6. 启动后跑 `SELECT count(*) FROM schema.tablename;` 对比 PANIC 前的行数——**必须一致**。

**如果行数对不上、启动时报"orioledb recovery worker failed to replay WAL container"**——这是个**真实问题**，不该在生产复现之前遇到。

**配套查询**：

```sql
-- 看 OrioleDB 当前的 recovery 状态
SELECT * FROM orioledb_get_xid_meta();
```

`orioledb_get_xid_meta` 返回 4-5 列（Oxid、xid、csn 等）——`xid` 是 PG 经典 32 位 transaction id（即使 OrioleDB 内部用 64 位 OXid，对外仍兼容 32 位 xid），`csn` 是 OrioleDB 自己的 commit sequence number。

**典型坑**：
- **PANIC 后 startup process 自己也 panic**——通常是 `recovery.c` 第 4 阶段（`workers_synchronize` + `apply_pending_sk_fixups`）死锁；先看 pg.log 找 "orioledb recovery worker detached unexpectedly"
- **行数对不上但没报 ERROR**——**最危险的坑**，事务一致性问题；停服、联系上游
- **`debug_recovery_crash_lsn` 触发不了 PANIC**——可能是 GUC 没生效（看 `SHOW orioledb.debug_recovery_crash_lsn`），或 OrioleDB 还没把 dev-only 行为开放给你

**怎么日常化**：

`debug_recovery_crash_lsn` 这种**生产永远不开**——是 dev/test 工具。但它的存在**意味着 OrioleDB 项目对恢复路径测试有第一性支持**。生产恢复流程不靠"运气好"——你**有**可工程化测试的方法。建议每个版本升级前**必跑一次** `debug_recovery_crash_lsn` 流程，作为 release gate。

## 5 个 SQL 之外的延伸

这 5 条是**装后第一周必跑**的——给你 OrioleDB 的"基本健康度"。**长跑运维**需要更多查询，下面这些**DBA 也该知道存在**：

`orioledb_get_current_oxid()` —— 当前 OXid（64 位事务 ID），DBA 拿这个 + 跨日差值算"OrioleDB 事务吞吐"。

`orioledb_get_rewind_queue_length()` 和 `orioledb_get_rewind_evicted_length()` —— rewind buffer 队列长度。**rewind 是 OrioleDB 的"事务回滚窗口"**——`orioledb.enable_rewind = on` 时启用，事务 commit 后短时间内能回滚（类似 savepoint）。两个函数告诉你**还有多少 rewind 窗口可用、已经 evict 多少**。

`orioledb_has_retained_undo()` —— 是否有事务还在持有 undo（简单 true/false）。`true` 时配合 `orioledb_get_proc_retain_undo_locations()` 看谁在持有。

`orioledb_evict_pages('schema.tablename', maxLevel)` —— 手动驱逐某个表的页面。**应急用**：`main_buffers` 爆了、其他表页面被排挤、你想强制让 OrioleDB 释放某张表的缓存。**生产慎用**——这是个有副作用的工具。

`orioledb_write_pages('schema.tablename')` —— 强制 flush 某张表的 dirty pages 到磁盘。**也是应急用**——比如快照前你想确保 OrioleDB 状态完全落盘。

`orioledb_table_oids()` / `orioledb_index_oids()` / `orioledb_table_pages()` —— **OrioleDB 的物理层**。返回每张表在磁盘上的 `datoid / relid / relnode` 三个 OID + 页面列表。**一般不查**，但**做 `pg_basebackup` 验证、磁盘故障恢复**时用得到。

## 一些不确定的、应该承认的

这些 SQL 的输出**我没实测**——OrioleDB 在你机器上还没装。**函数定义、字段名、返回行数**全部来自 OrioleDB 1.9 源码（`src/transam/undo.c` 4036-4110 行定义 14 列，`sql/orioledb--1.6--1.7_dev.sql` 定义函数 schema），但**实际值域**需要你装了之后跑一次才知道。**Dead tuple 阈值 10% / 20% 是经验值**，不是 OrioleDB 官方告警阈值——OrioleDB 项目目前没给"DBA 健康度判据"这种东西，需要你自己的 workload 跑出来。

**OrioleDB 项目还在 beta（beta17，2026-09-04）**——这些函数在 1.10 / 1.11 之后的版本里签名可能变、`pg_am` 那行的列可能加新字段。我引用的源码是 2026-09-05 时的 main 分支 commit e04b560，**版本会动**。

**DBA 视角的最后一句**：装 OrioleDB 不是装个 PG 扩展那么简单——它是一个**新的存储子系统**，需要新的监控、新的健康度判据、新的恢复测试流程。**这 5 个 SQL 是最低门槛的第一周动作**，够让你判断"OrioleDB 装上了且活着"。要判断"OrioleDB 在我的 workload 上比 heap 快"——下一篇姊妹文都不够，得你自己在测试环境跑 perf 脚本、`pgbench -M prepared`、你业务 query 的端到端延迟对比。**读完 SQL 不跑 = 跟没读一样**。
