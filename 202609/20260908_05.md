## 背景  

如果你上个月第一次听说 Neon，大概率会把它当成"AWS Aurora 的开源版"。这个理解**对了一半，但错的那一半是致命的**。Aurora 的核心创新是"共享存储层的 PG 集群"——主从 6 副本、计算层可读、存储层是 Quorum。Neon **不是这个架构**。Neon 是**把 PG 拆成 compute 和 storage 两层独立子系统、scale to zero 是核心卖点、branch 是 copy-on-write 的秒级操作**的全新平台。

Aurora 把你的 PG 改造成"高可用企业版"。Neon 把你对"PG 实例"这个概念本身的认知拆掉重装。**DBA 视角下，Neon 的真正冲击不是更快或更高可用，是它改变了你"管一台数据库"这个心智模型**。

Neon 项目代码在 `neondatabase/neon` 仓库，2026-09 时 23,042 个 star、1,085 个 fork、Apache-2.0 协议、主要语言 Rust（不是 C）。302,354 行 Rust 代码——是 OrioleDB（13 万行 C）的 2.5 倍、比 PG 本身（100+ 万行 C）的三分之一。**这不是一个存储引擎项目，是一个 serverless 平台项目**。

## 4 个组件，对应 4 个 PG 老问题

Neon 的 README 一句话讲完架构："A Neon installation consists of compute nodes and the Neon storage engine." 拆开看有 4 个真正干活的子系统，每个解决一个具体问题。

**Compute nodes**——无状态 PG。这是 `compute/` 目录干的事。**关键事实**：Neon 跑的是**普通 PostgreSQL**（标准 C 二进制），不是 PG fork。Neon 在 PG 之上贴的 patches 数量极少（远少于 OrioleDB 那 10+ 个 patch），大部分 PG 核心代码保持上游原样。`compute/manifest.yaml` 里有 50+ 条 PG `postgresql.conf` 设置，**DBA 视角最有冲击力**的：

```yaml
fsync: "off"
hot_standby: "off"
effective_io_concurrency: "20"
```

**`fsync: "off"`**——这是 Neon 设计哲学的核心。Neon 的 compute 节点不直接管持久化，**WAL 发给 safekeeper**、持久化在 safekeeper 那边完成。compute 节点自己写盘是临时 cache，关掉 fsync 不损失任何持久性保证。**对 DBA 来说这是反直觉的**——你 25 年 PG 经验说"fsync 永远开"，Neon 告诉你"在你这个架构下，关掉 fsync 才是对的"。

`hot_standby: "off"`——compute 节点不接收复制流量（流复制关），只对外服务读写。**所有复制都是 safekeeper 那边的事**。

`pageserver/` 114,285 行 Rust——**Neon 真正的核心**。Pageserver 是个**远程存储层**——接收 safekeeper 发来的 WAL，**按 Page version（不是按整页）存到云对象存储**。`pageserver/src/tenant.rs` 12,926 行——这是 Neon 的"集群管理器"等价物，**每个 tenant 多个 timeline（branch）、timeline 内是分层的 LSN 序列**。

pageserver 核心数据模型在 `pageserver/src/tenant/timeline/`：

- `init.rs` 89 行 `Decision` enum——**layer 装载/不装载的判定**：`Evicted`（远程有元数据，本地无文件）、`Resident`（本地有文件，metadata 匹配）
- `compaction.rs` 4,584 行——**Neon 自己的 vacuum**。合并 layer、清理旧版本
- `layer_manager.rs`——**layer 文件的索引与状态机**
- `walreceiver.rs`——pageserver 收 WAL 的入口

**layer** 是 Neon 对 PG page 的扩展概念。**PG 8KB page 不可变**——每次 update，PG 写新 page（标记 old page 死掉，等 vacuum）。Neon 的 layer 是**一段时间内修改过的 page 集合**——按 LSN 范围切。读一个 page = 找到包含这个 page 的最新 layer + 链回历史的 layer。这是 Neon's **MVCC 在 page-version 维度**的实现。

`safekeeper/` 19,148 行 Rust——WAL 接收服务。**关键概念**：safekeeper 不是传统 PG 备库。传统备库**拉**主库 WAL，safekeeper 是 compute 节点**推**WAL 过来、3 个 safekeeper 节点形成**quorum 共识**（Raft 变种）。`safekeeper/src/wal_storage.rs` 40-76 行是核心 trait `Storage`，定义了 `write_lsn / flush_lsn / write_wal / flush_wal / truncate_wal` 等抽象。`state.rs` + `control_file.rs` 维护 WAL 状态机。

`storage_controller/src/service/safekeeper_service.rs` 1,127 行 `tenant_timeline_safekeeper_migrate`——**safekeeper 成员动态变更**算法（RFC-035 实现）。这是**分布式系统最难的子问题之一**——如何在不丢数据、不停服务的前提下把某条 timeline 从一组 safekeeper 迁到另一组。Neon 把这个写成可单机测试的纯函数，靠 `SafekeeperGeneration` 单调递增做并发控制。**DBA 视角的"primary 切换"在这变成了"timeline 迁移"——对应用透明**。

`proxy/` 31,090 行 Rust——**SQL 连接代理**。**这不是 pgbouncer 那种简单的连接池**——它还要做鉴权（SCRAM、jwt）、branch 选择、请求路由、限流。`proxy/src/auth/` 处理多种认证方式（`backend/jwt.rs` 1,382 行单独处理 JWT 鉴权）。`proxy/src/serverless/sql_over_http.rs` 1,062 行——**SQL over HTTP 的核心**：Neon 的 HTTP API 走这里，**每个 HTTP 请求被翻译成一个 PG 事务**。**这是 Neon 跑 serverless 工作流的事实标准**——Lambda 调一次 `fetch(POST /sql)`，proxy 把请求路由到 compute 节点、起一个新 PG 进程、跑 SQL、返回结果、关掉 PG 进程。

`storage_controller/` + `storage_broker/` + `endpoint_storage/`——**4 个子系统的协调层**。storage_controller 决定 tenant 放哪个 pageserver shard、placement policy 怎么选、tenant 怎么迁移；storage_broker 是 pageserver 之间共享存储的协调者（`storage_broker/src/broker.rs` 873 行）；endpoint_storage 是 compute 节点的生命周期管理（`endpoint_storage/src/endpoint.rs` 1,299 行）；控制面 `control_plane/` 8,853 行 Rust 加上 2118 行的 `neon_local` 二进制（**这个就是 Neon 自带的本地起 cluster 工具——DBA 视角下"先起一个 Neon 跑起来"的官方路径**）。

## 4 个范式转移：DBA 视角看 Neon 真正改变的事

Neon 不是"PG 的更好实现"——它是**让你对"PG 实例"这个心智模型重写**的工程。

**第一：PG 启动从 10 秒变 200 毫秒**。传统 PG 实例起一个进程 = 启动一个 PG 二进制 + 读 shared_buffers + 应用 WAL 到 recovery point。哪怕空数据库，10 秒是常态。Neon 的 compute 节点启动 = `cargo run` 一个标准 PG 进程 + 接上 `pageserver` HTTP API 拉 page。**PG 进程不存数据、不需要 recovery 跑全套 checkpoint**——pageserver 那边数据早已持久化，compute 起来就 200ms。**对 serverless 工作流来说**——Lambda 冷启动从 1 秒变 200 毫秒，PG 数据库不再是"贵重的持久资源"，是"函数调用的瞬时输入"。

**第二：branch 从小时变秒**。你用 git branch 几秒，PG branch 几小时（`pg_dump | createdb`）。Neon 的 branch = **一次 pageserver copy-on-write**。`tenant/timeline.rs` 285-331 行有 `parent timeline` 和 `child timeline` 字段，child timeline 持有 `branch_point_lsn`——读请求落到 pageserver 时，**child timeline 的 page 优先于 parent 的**。**DBA 视角下，preprod branch 创建立刻可用、用完即扔**。Neon 的 marketing demo 视频里常用这个——你给一个 PR 临时起一个 branch 跑 50 个测试、合并后分支自然失效。**这不光是"快"——它改变了 dev/test/PR review 的工作流**。

**第三：scale to zero 真的工作了**。传统 PG 实例停了 = 数据库不可用。Neon 的 compute 节点停了 = 数据还在 pageserver 里，再来一个连接，**新 compute 节点从 pageserver 拉 page、200ms 后服务**。`compute/manifest.yaml` 里的 `idle_in_transaction_session_timeout: "300000"`（5 分钟）和 activity monitor 是负责"什么时候让 compute 节点休眠"的关键。**对开发/测试环境**——一个月跑 10 小时的 dev DB，**成本按 10 小时算**而不是按 7×24 算。Neon 的免费层就是这个模型。

**第四：主从复制的语义改了**。传统 PG 主从 = primary 写、从库拉、复制延迟秒级、primary 挂了从库提升（30 秒~几分钟不可用）。Neon 的"主从"是**safekeeper quorum**——3 个 safekeeper 节点任何时刻都接收所有 WAL，**没有 primary 概念**（更接近 Spanner 的 TrueTime 模型，但弱一些）。Compute 节点挂了，**新 compute 节点从 3 个 safekeeper 任意一个拉 WAL**就能恢复。**DBA 视角下"primary 切换"运维剧本彻底作废**——你不再演练"主挂了从提升"。

## DBA 视角的"该不该考虑 Neon"

**不能直接说"该"或"不该"**——Neon 的形态跟传统 PG 自建实例根本不是同一物种。下面几条判断帮你想清楚。

**考虑 Neon 的 workload**：
- **大量 serverless / 短连接 / 弹缩需求**——Vercel / Next.js 部署、Lambda 后端、edge functions，每个连接寿命 1-3 秒。Neon 的 SQL over HTTP 专门为这种场景设计
- **大量 dev/branch/test 环境**——preprod 跑测试、PR review、staging replica。Neon 的 branch 模型是这些场景的最优解
- **冷启动敏感**——用户/函数等数据库响应超过 200ms 就嫌慢。Neon 解决冷启动
- **预算敏感 + 低峰期长**——传统 RDS 7×24 算钱，Neon scale to zero 真的能把成本降到 1/5
- **在云上不在自建机房**——Neon 跑在 AWS S3 之上，**自建机房你用不了 Neon**

**不适用于 Neon 的场景**：
- **超低延迟**——你每条 query 的 SLA 是 1ms。Neon compute 拉 page 走 pageserver HTTP，**本地直连 PG 实例的延迟是 50-100μs，Neon 是 1-5ms**——快 20 倍。**对延迟极敏感的交易系统不适合**
- **大库 + 大单事务**——pageserver 收 WAL、按 layer 切。如果你的事务是 GB 级别的单事务、持续 1 小时，**layer 跨度过大、compaction 困难**。Neon 适合中小事务高频，不是大单事务
- **需要 PG 扩展（pg_xxx）能本地直装**——Neon 的 compute 节点是 `neondatabase/compute-node-v16` 镜像，**白名单之外的扩展装不了**。你的 `pg_cron` / `pg_partman` / `timescaledb` 能不能用要先看文档
- **必须 BYOC（带自己的云）**——Neon 只在 Neon Cloud 跑（`neon.tech`）。**没有 self-hosted Neon 商用版**——开源版本叫 neon_local，**只用于测试和开发**。你要是想"在自己的 K8s 上跑 Neon 给客户用"，**目前没有可买的服务**
- **要严格的合规**——数据在 AWS S3、跨 region 复制、第三方控制台管理。**自建 PG 实例你的合规边界是清楚的，Neon 多了一层"你的数据现在在 Neon Cloud 的 S3 桶里"**

**Neon 的几个不显眼成本**：
- **分支不能太多**——每个 branch 持有自己的 layer 集合，**tenant 内 branch 数量是 pageserver 内存的硬约束**。1000 个 branch = 1000 倍 metadata 开销
- **extension 限制**——见上
- **postgres 兼容性**——Neon 跑 PG 14/15/16/17，**每个版本的 compute 镜像固定**。你升级 PG 大版本 = 切到新镜像 + 数据重导（pageserver 自动，但要时间）
- **数据出 Neon 难**——Neon 提供 `pg_dump` 导出和 pageserver S3 下载，但你"想用 AWS DMS 把 Neon 数据搬到自建 PG"这条路**没官方支持**

## Neon vs OrioleDB 怎么选

这两件事是不同抽象层，**不冲突**：
- **OrioleDB** = 把 PG 的**存储层**重写。**PG 进程还是 PG 进程，只是 `CREATE TABLE ... USING orioledb`**。**单实例级别**的优化。多核、零 vacuum、64-bit xid
- **Neon** = 把 PG 的**服务模型**重写。**PG 进程变成无状态 compute 节点**，WAL 走 safekeeper quorum，存储走 pageserver + S3。**集群级别**的创新。scale to zero、秒级 branch、冷启动

**两件事可以叠加**：**Neon 的 compute 节点理论上可以跑 OrioleDB**（compute 节点是标准 PG + 扩展加载 `orioledb.so`）。这意味着你在 Neon 上能同时拿到：
- Neon 的存算分离 / scale to zero / branch（**集群级**）
- OrioleDB 的零 vacuum / 多核扩展性 / 64-bit xid（**单实例级**）

但这条路目前**没有官方支持**——Neon 的 compute 镜像默认是 `neondatabase/postgres` 上游版，不是 patched。**你想要 OrioleDB-on-Neon，需要自维护一个 patched compute 镜像**——这对你的工程团队是个真投入。

**Neon 适合的是"我们公司没有 DBA 团队、但需要 PG、能接受 serverless 范式"**。Aurora 适合的是"我们公司有 DBA、但不想自己管 PG 基础设施、能接受企业级 closed-source"。OrioleDB 适合的是"我们公司有强 DBA、想榨干单机 PG 性能、能接受源码层介入"。

**它们不在一个赛道**。

## DBA 视角的最后一句

Neon 项目**30 万行 Rust + 9 个核心子系统**——这是**平台级**的工程投入（Supabase 投资 Neon、AWS Aurora 是同量级）。**DBA 视角下，上不上 Neon 不是技术判断**——是**公司战略判断**：

- 你们公司有 DBA 团队、有自建机房习惯、想"从 PG 14 升到 PG 17 但不迁移数据"——**Neon 不适合你**
- 你们公司业务在 Vercel 上、每月 PG 账单是开发支出大头、dev 环境用完就关——**Neon 是答案**
- 你们公司在评估"上云还是不上云、PG 自建还是托管"——**Neon 是个新选项，它不是"PG on AWS RDS"也不是"PG on Aurora"**

我读完 Neon 30 万行 Rust、读 docs/ 几十个 md、读 control_plane 的核心模块，**没找到工程上"看着不对劲"的地方**——`cargo run --bin neon_local` 起本地 cluster 是官方推荐路径，SafekeeperGeneration 单调递增的并发控制是对的，pageserver 的 layer 模型是对的，proxy 的 serverless SQL over HTTP 是对的。**但我没装**——Neon 装起来比 OrioleDB 重（要 Rust 1.88 toolchain + 30-60 分钟 cargo build），我前面 OrioleDB 三篇已经花了不少时间，**Neon 这台机器这次不装**。要装，按 `docs/docker.md` 用 `docker-compose up` 是 5 分钟起步路径；用 cargo 装是 30-60 分钟但能跑本地完整 cluster。

DBA 视角的最后一句**和 OrioleDB 三篇一样**：

**读完代码不跑 = 没读完**。Neon 的代码再好、概念再新——你拉一个生产 workload 在 Neon free tier 上跑一周，**那 5 TB 流量用完、那 200ms 冷启动测过、那 branch 创了 50 个删了 49 个、那 pgvector 用得起来用不起来**——这些数据点比 30 万行 Rust 更能回答"该不该上"。
