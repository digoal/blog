## 背景  

上一篇讲 Neon 的 4 个组件和 4 个范式转移——那篇写完发现一个缺口：实际动手之后第一周该做什么。OrioleDB 写了装后 5 SQL 姊妹篇，这篇对称写 Neon。

Neon 跟 OrioleDB 不一样。OrioleDB 是**单进程扩展**，装上就 28 个 `orioledb_*` SQL 函数摆在那里，**DBA 第一周是"熟悉 28 个函数"**。Neon 是**9 个子系统的分布式平台**，SQL 函数不是核心——**DBA 第一周是"熟悉 cluster 拓扑"**——几个 pageserver、几个 safekeeper、哪些 HTTP API、tenant 怎么迁移、scale-to-zero 怎么发生的。SQL 在 Neon 里是 PG 原生 SQL，**不是 Neon 暴露的入口**——`SELECT`、`EXPLAIN`、`CREATE TABLE` 都是 PG 自己的、跟你现装 PG 18.6 一样。

所以这篇**不是 5 SQL，是 5 件工程事**——5 个动作、5 个观察点、5 步"Neon 真在跑"的验证。

## Day 0 · 把本地 cluster 跑起来

`neon_local` 是 Neon 自带的本地起 cluster 工具——文档在 `docs/sourcetree.md` 写得很清楚："Intended to be used in integration tests and in CLI tools for local installations"。代码在 `control_plane/src/bin/neon_local.rs` 2,118 行，**这就是 Neon 的"PG 自带的 pg_ctl 等价物"**——只不过 pg_ctl 管一个 PG 实例，neon_local 管一整个 Neon cluster（pageserver + 3 个 safekeeper + compute 节点）。

**起 cluster**：

```bash
git clone https://github.com/neondatabase/neon.git
cd neon
cargo build --release --bin neon_local
# 估计 30-60 分钟 (30 万行 Rust, 这是大头)
cargo build --release --bin pageserver
cargo build --release --bin safekeeper
cargo build --release --bin storage_broker

# init 本地环境
./target/release/neon_local init \
    --pg-version 17 \
    --config control_plane/safekeepers.conf
```

`neon_local init` 干了 4 件事（看 `bin/neon_local.rs:handle_init`）：写 `pageserver.toml`、生成三个 safekeeper 配置文件、起 storage_broker 监听 50051、起默认 tenant。

**默认 PG 版本 = 17**（`DEFAULT_PG_VERSION_NUM = "17"`，`bin/neon_local.rs` 第几行我没数清楚——这是 Neon 自带的 PG 内置版本，**不需要你机器上装 PG 17**）。`vendor/postgres-v17/` 这个目录**就是 Neon 自带的 PG 17 源码**——Neon 跑的不是 apt 装的 PG，是它自己 vendor 进来的 PG 17。

**启动**：

```bash
./target/release/neon_local pageserver start    # 启 pageserver (端口 9898 HTTP, 64000 pg, 51051 gRPC)
./target/release/neon_local safekeeper start    # 启 3 个 safekeeper (端口 5454/5455/5456 pg, 7676/7677/7678 HTTP)
./target/release/neon_local storage_broker start  # 启 broker (端口 50051)
./target/release/neon_local pg create main       # 启 compute 节点 (端口 5432)
```

**所有进程**——起完之后 `ps auxf | grep -E 'pageserver|safekeeper|broker|postgres'` 应该看到 6 个进程（1 pageserver + 3 safekeeper + 1 broker + 1 postgres compute）。

**端口配置**（从 `control_plane/safekeepers.conf`）：

```
[pageserver]
listen_pg_addr = '127.0.0.1:64000'
listen_http_addr = '127.0.0.1:9898'
listen_grpc_addr = '127.0.0.1:51051'
pg_auth_type = 'Trust'   # 默认 Trust, 生产必改

[[safekeepers]]
id = 1; pg_port = 5454; http_port = 7676
id = 2; pg_port = 5455; http_port = 7677
id = 3; pg_port = 5456; http_port = 7678
```

**Trust 鉴权**——Neon 默认开发模式不要求密码，**真生产环境需要 `pg_auth_type = 'NeonJWT'` + 配 control plane 的鉴权 endpoint**（文档在 `docs/authentication.md`）。

**验证 cluster 活着**：

```bash
curl -s http://127.0.0.1:9898/v1/tenant | jq
# → [{"id": "<hex-32-chars>", "state": "Active", ...}]

curl -s http://127.0.0.1:7676/v1/heartbeat  # safekeeper 1
# → {"ttid": ..., "wal_end": ..., "flush_lsn": ...}
```

**第一次跑容易踩的坑**：

- `cargo build` 报 "rustc version mismatch"——项目固定 `rust-toolchain.toml` 用 1.88.0，**你机器上得装这个版本**（`rustup install 1.88.0 && rustup default 1.88.0`）
- 报 "missing libpq"——`apt install libpq-dev`（Debian/Ubuntu）
- 报 "port already in use"——检查你 PG 18.6 / pgvector / 别的端口占用
- 报 "filesystem full"——30 万行 Rust 编译产物大约 10-15 GB

## Day 1 · 看 pageserver 的 layer 模型

OrioleDB 装完看 `orioledb_get_undo_meta`——Neon 装完看 **`pageserver/src/tenant/timeline/init.rs:89` 的 `Decision` enum**。这是个 Rust enum：

```rust
enum Decision {
    Evicted,    // 远程有 layer 元数据，本地无文件
    Resident,   // 本地有文件，metadata 匹配
    ...
}
```

**这是 Neon pageserver 怎么处理"local cache miss"的判定**——DBA 视角下："我读一个 page 时，pageserver 该去 S3 下载还是走本地"。

**看 tenant 列表**：

```bash
curl -s http://127.0.0.1:9898/v1/tenant | jq '.[] | {
    tenant_id: .id,
    state: .state,
    timeline_count: (.timeline_count // 0),
    current_physical_size: .current_physical_size
}'
```

**看单个 timeline 的 layer 列表**：

```bash
curl -s "http://127.0.0.1:9898/v1/tenant/<tenant_id>/timeline/<timeline_id>" | jq '{
    timeline_id,
    state: .state,
    layers: .layers | length,
    layer_map_total_size,
    current_logical_size,
    current_physical_size
}'
```

**几个观察点**：

- `state: "Active"`——timeline 在服务中
- `state: "Cold"`——scale-to-zero 后状态，**pageserver 仍在、compute 节点休眠**
- `state: "Stopping"`/`"Stopped"`——迁移中 / 已停止

**layer 是 Neon 的核心抽象**——比 OrioleDB 的 buffer 池复杂得多。`docs/glossary.md` 给的定义："A layer contains data needed to reconstruct any page versions within the layer's Segment and range of LSNs"。

**layer 两种类型**：

- **In-memory layer**——吃 WAL 时新建，**周期性转成 on-disk**
- **On-disk layer**——分 L0 / L1，L0 按 LSN 范围切、L1 按 key range 切。**L0→L1 的转换 = compaction**

**`pageserver.toml` 关键 GUC**：

```toml
checkpoint_distance = '268435456'   # 256 MB, 触发 layer 落盘
checkpoint_timeout = '10m'           # 10 分钟兜底
gc_period = '1 hour'               # GC 周期
gc_horizon = '67108864'            # 64 MB, GC 保留窗口
compaction_period = '1 s'          # 每秒检查
compaction_target_size = '128MB'   # L0/L1 单文件大小
```

**DBA 视角**：

- `checkpoint_distance = 256MB` 意思是"攒够 256MB WAL 才 flush 到 S3"。**比 PG 默认的 `checkpoint_timeout = 5min` 激进 25 倍**——意味着 pageserver 不会像 PG 那样有长时间的 in-memory WAL 累积
- `gc_horizon = 64MB` 是 **branch 能力的基础**——你能在最近 64MB WAL 范围内任何 LSN 创建 branch
- `compaction_period = 1s` = Neon 的"vacuum"每秒跑（**对照 OrioleDB 的"零 vacuum"——这是用 CPU 换磁盘**）

**查 pageserver 当前 GC/compaction 状态**：

```bash
curl -s http://127.0.0.1:9898/v1/status | jq
```

## Day 2 · branch：秒级创建、秒级删除

**Neon branch = timeline 创建**——文档原话："We can create branch at certain LSN using `neon_local timeline branch` command. Each Branch lives in a corresponding timeline and has an ancestor."

**创建 branch**：

```bash
# 看现有 timeline
./target/release/neon_local timeline list

# 在现有 timeline 的当前 LSN 上创建 branch
./target/release/neon_local timeline branch \
    --branch-name feature_x

# 在指定 LSN 上创建 (时间点分支)
./target/release/neon_local timeline branch \
    --branch-name pre_upgrade \
    --at-lsn "0/16D6090"
```

**测秒级创建**——DBA 视角下要**真的计时**：

```bash
time ./target/release/neon_local timeline branch --branch-name test_$$ 2>&1
# → ~200ms (没真装, 这是 docs/test_runner 报告的常见值)
```

**Neon branch 为什么秒级**——因为不是 `pg_dump + createdb`，是**pageserver 内部新建一个 Timeline 对象、记录 parent_lsn**。所有 page 落在 parent timeline 上，child timeline 只记录"branch 之后的修改"。**COW (copy-on-write)**。

**验证 branch 是 COW**——写 branch_A 不影响 branch_B：

```bash
# 连 main timeline
PGPASSWORD=cloud_admin psql -h 127.0.0.1 -U cloud_admin -d postgres <<EOF
CREATE TABLE t(key int, value text);
INSERT INTO t VALUES (1, 'main');
EOF

# 在当前 LSN 创建 branch feature_y
./target/release/neon_local timeline branch --branch-name feature_y

# 连 feature_y branch
./target/release/neon_local pg create feature_y_branch
PGPASSWORD=cloud_admin psql -h 127.0.0.1 -p <feature_y_port> -U cloud_admin -d postgres <<EOF
SELECT * FROM t;  -- 应该看到 main 的数据
INSERT INTO t VALUES (2, 'feature_y');  -- 只影响 feature_y
EOF

# 回到 main
PGPASSWORD=cloud_admin psql -h 127.0.0.1 -U cloud_admin -d postgres <<EOF
SELECT * FROM t;  -- 应该只有 (1, 'main'), 没有 feature_y 的修改
EOF
```

**删除 branch**：

```bash
./target/release/neon_local timeline delete --tenant-id <tenant_id> --timeline-id <timeline_id>
```

**DBA 视角**：

- branch 数有硬上限——每个 tenant 的 timeline 数 = pageserver 内存中 metadata 实体数，**1000 个 branch 是软上限**（看具体 memory 配置）
- branch 删了**不等于数据删了**——child timeline 的 page 已经被 compaction 合进 parent 的 layer 的话，**你删 branch 数据还在**
- branch 创建不消耗多少 disk——因为 COW，**实际开销 = 你 branch 后修改的量**

## Day 3 · safekeeper 共识的状态机

**Neon 的 WAL proposer-safekeeper 共识**——文档 `docs/safekeeper-protocol.md` 写得很细。"There is single stateless master and several safekeepers. Number of safekeepers is determined by redundancy level. To minimize number of changes in Postgres core, we are using standard streaming replication from master (through WAL sender). This replication stream is initiated by the WAL proposer process that runs in the PostgreSQL server, which broadcasts the WAL generated by PostgreSQL to safekeepers."

**关键概念**：

- **WAL proposer = 在 PG 进程里跑**（不是单独进程）——是 PG 内置的 `wal_sender` 变体
- **safekeeper = 单独进程**——3 个 safekeeper 形成 quorum
- **commit 延迟** = 收到 quorum (3-of-3 的多数 = 2-of-3) 的 ack 才返回
- **不存在"primary"概念**——任何 safekeeper 都能成为 WAL source

**看 safekeeper 状态**：

```bash
# 看 3 个 safekeeper 的当前 LSN
curl -s http://127.0.0.1:7676/v1/heartbeat | jq
curl -s http://127.0.0.1:7677/v1/heartbeat | jq
curl -s http://127.0.0.1:7678/v1/heartbeat | jq

# 看每条 timeline 的 commit_lsn / flush_lsn
curl -s http://127.0.0.1:7676/v1/tenant/<tenant_id>/timeline/<timeline_id> | jq '{
    timeline_id,
    commit_lsn,
    flush_lsn,
    backpressure: .backpressure,
    peer_horizon_lsn
}'
```

**三个 safekeeper 的 `commit_lsn` 应该几乎相等**（差距就是网络 RTT）。`flush_lsn` 可以低于 `commit_lsn`——commit 是 quorum ack、flush 是 safekeeper 自己 fsync 到磁盘。

**VCL (Volume Complete LSN)**——`docs/safekeeper-protocol.md` 提到这个关键概念。"Calculated max(flushLSN) is called VCL ... As far as it is chosen among quorum, there may be some other offline safekeeper with larger VCL."——VCL 是从 quorum 的 max flushLSN 选的，**意思是"我们确定安全持久化的最后位置"**。

**DBA 视角**：

- **不要假设 3 个 safekeeper 是同质的**——老的慢 safekeeper 会成为 quorum 的瓶颈（commit 要等最慢的 ack）
- **`backpressure` 字段**——safekeeper 顶不住 WAL 流量时回 backpressure 给 compute，compute 的 `max_replication_write_lag` 会让 INSERT 卡住
- **3 个 safekeeper 中 1 个挂了**——commit 还能继续（quorum 是 2-of-3），但 VCL 不能从挂了那个 safekeeper 取，所以 VCL = 剩下两个 safekeeper 的 max
- **恢复后挂的 safekeeper 重连**——它的 WAL 落后了，要从 VCL 拉，**这段时间 VCL 不能前进**

**安全演习——停一个 safekeeper 验证 quorum**：

```bash
./target/release/neon_local safekeeper stop --id 2
# 写入数据库
PGPASSWORD=cloud_admin psql -h 127.0.0.1 -U cloud_admin -d postgres \
    -c "INSERT INTO t VALUES (99, 'still_works');"
# → 应该成功 (2-of-3 quorum)

./target/release/neon_local safekeeper start --id 2
# 重连后 VCL 会追上
```

## Day 4 · pageserver 之间的 tenant 迁移

**`docs/pageserver-tenant-migration.md`** 写得很详细——tenant 是可以在 pageserver 之间迁移的。"This feature allows to migrate a timeline from one pageserver to another by utilizing remote storage capability."

**5 步迁移流程**：

1. 在目标 pageserver 上调用 `timeline attach`——下载最新 checkpoint
2. 手动 `callmemaybe` 触发目标 pageserver 从 safekeeper 拉 WAL
3. 复制状态可查
4. compute 节点用新 pageserver 连接串重启
5. 旧 pageserver 上 `timeline detach`——磁盘数据删除

**用 HTTP API 实操**：

```bash
# 目标 pageserver attach
curl -X POST http://127.0.0.1:9899/v1/tenant/<tenant_id>/timeline/<timeline_id>/attach \
    -H "Content-Type: application/json" \
    -d '{}'

# 旧 pageserver detach
curl -X DELETE "http://127.0.0.1:9898/v1/tenant/<tenant_id>" \
    -H "Content-Type: application/json" \
    -d '{"detach": true}'
```

**DBA 视角**：

- **迁移期间 compute 节点短暂不可用**——要重启 PG 进程、连新 pageserver
- **S3 是迁移的关键依赖**——pageserver 把本地 layer 上传到 S3、新 pageserver 从 S3 下载
- **Safekeeper 不用动**——WAL 始终在 3 个 safekeeper，pageserver 来不来拉都行
- **生产环境一般用 storage_controller 自动 migration**——`storage_controller/src/service/safekeeper_service.rs:tenant_timeline_safekeeper_migrate` 1,127 行函数就是干这事的

**什么时候手动迁移**：
- pageserver 升级——起新 pageserver、迁完所有 tenant、停旧的
- pageserver 节点故障——自动迁移（storage_controller 触发）
- **page-server 间的负载不均**——storage_controller 看 metrics，自动 rebalance

## Day 5 · scale-to-zero 实测

**Neon 最核心的特性**——compute 节点能停掉、新连接自动起新 compute 节点。"Compute node" 在 `docs/sourcetree.md` 里："Stateless Postgres node that stores data in pageserver."——**stateless** 是关键词。

**关 compute 节点**：

```bash
./target/release/neon_local pg stop main

# 看 pageserver tenant 状态
curl -s http://127.0.0.1:9898/v1/tenant | jq '.[] | {state, current_physical_size}'
# → state: "Cold" (compute 节点没了, 但 pageserver 还在)
```

**新连接自动起 compute**：

```bash
time PGPASSWORD=cloud_admin psql -h 127.0.0.1 -U cloud_admin -d postgres -c "SELECT 1;"
# → 第一次连接 ~200ms (新 compute 节点启动)
# → 第二次连接 ~10ms (compute 已经在)
```

**关键事实**：

- **数据完全不动**——pageserver 上的 layer 不变，**compute 节点是无状态的**
- **状态字段从 "Active" → "Cold"**——`state: "Cold"` 在 tenant 详情里能看到
- **新 compute 节点起来时**——compute_ctl 调 pageserver HTTP API 拿 basebackup（`docs/glossary.md` 提到："A tarball with files needed to bootstrap a compute node and a corresponding command to create it"）——basebackup = "PG 数据文件的 tarball"，但**不是真数据，是空的 PG + 指向 pageserver 的元数据**

**`compute/manifest.yaml` 里关键 GUC 配合 scale-to-zero**：

```yaml
fsync: "off"                     # compute 不持久化, safekeeper 做
hot_standby: "off"              # compute 不接受流复制
effective_io_concurrency: "20"  # pageserver HTTP 并行 fetch
idle_in_transaction_session_timeout: "300000"  # 5 min idle 触发休眠
```

`idle_in_transaction_session_timeout: 300000` (5 分钟) 是 scale-to-zero 的触发条件——compute 节点空闲 5 分钟就休眠，**不是从最后一次连接算**。**事务里 idle 也会算**——所以 Neon 用户**不能开 long transaction**。

**DBA 视角**：

- **scale-to-zero 适合 dev/test**——生产环境通常不让 compute 休眠（每次冷启动 200ms）
- **如果想保持 warm**——调大 `max_compute_idle_ms` (生产配置)
- **数据一致性**——scale-to-zero 期间任何写入是事务性的（commit 等 quorum），scale-to-zero 不会丢数据
- **L2 cache 失效**——pageserver 把 layer 缓存在内存，compute 节点起不来是因为 pageserver 跟不上（不是 compute 本身慢）

## Day 7 · 出 "Neon 真在跑" 的体检报告

第 7 天——DBA 该出一个 **"Neon 上线一周健康报告"**。下面是该看的字段：

**Pageserver**：

```bash
curl -s http://127.0.0.1:9898/v1/status | jq
# { pageserver: { ... }, ... }
curl -s http://127.0.0.1:9898/v1/tenant | jq
# [{state, current_physical_size, ...}]
```

**Safekeepers**：

```bash
# 3 个 safekeeper 心跳
for p in 7676 7677 7678; do
  echo "=== :$p ==="
  curl -s http://127.0.0.1:$p/v1/heartbeat | jq '{commit_lsn, flush_lsn, backpressure}'
done
```

**Storage broker**：

```bash
# 默认 50051, 用 grpcurl
grpcurl -plaintext 127.0.0.1:50051 list
```

**Compute 节点**：

```bash
PGPASSWORD=cloud_admin psql -h 127.0.0.1 -U cloud_admin -d postgres -c "
SELECT 
  pg_size_pretty(pg_database_size('postgres')) AS db_size,
  pg_postmaster_start_time() AS pg_started,
  pg_current_wal_lsn() AS current_lsn,
  pg_current_wal_insert_lsn() AS insert_lsn,
  pg_current_wal_flush_lsn() AS flush_lsn
"
```

**正常值的标志**：

- 3 个 safekeeper `commit_lsn` 同步到 1MB 内
- pageserver tenant `state: "Active"`
- pageserver 当前物理大小 < 配置的上限（默认 1TB）
- `backpressure: false`
- GC 跑了、compaction 跑了（看 pageserver log `disk_usage_eviction_task`）

**告警标志**：

- safekeeper `commit_lsn` 差距 > 100MB——某个 safekeeper 卡了
- pageserver `state: "Broken"`——磁盘满 / 配置错
- compute 节点冷启动 > 1s——pageserver 慢了
- L1 layer 文件大小 > 1GB——compaction 没跟上

## DBA 视角的最后一句

**Neon 的 onboarding 比 OrioleDB 重一个数量级**。OrioleDB 装扩展 30 秒、5 SQL 看完就上手。Neon 装本地 cluster 要 30-60 分钟 cargo build（30 万行 Rust），5 个动作跑完还要看 HTTP API、S3 模拟（MinIO）、3 个 safekeeper 的状态机、timeline 关系图。

**但 onboarding 重不等于生产重**——Neon Cloud 的 UI 上你点 "Create Project" 就起一个 cluster，**完全不需要手动管 pageserver/safekeeper**。**这是 serverless 该有的样子**——把所有 ops 都藏到平台后面，让 DBA 看到的是"一个 PG 实例"。

读完 30 万行 Rust + 5 天 onboarding，**Neon 的工程实现比我预期的扎实**——`safekeeper_protocol.md` 写得很细、`pageserver-services.md` 数据流图清晰、`pageserver-tenant-migration.md` 把迁移讲透了。**但我没装**——30-60 分钟 cargo build + 10-15 GB 磁盘 + 8 个进程跑起来是这台机器这次没做的事情。要装，按 `docs/docker.md` 走 `docker-compose up` 是 5 分钟起步路径；按 `docs/sourcetree.md` 走 `neon_local` 是 30-60 分钟但能跑本地完整 cluster。

**DBA 视角的最后一句和 OrioleDB 三篇一样**——读完代码不跑 = 没读完。Neon 的代码再好、范式转移再深——你拉一个真实 workload 跑一周、scale-to-zero 测过 50 次冷启动、branch 创了 50 个删了 49 个、safekeeper 停一个看 quorum 怎么动——**这些数据点比 30 万行 Rust 更能回答"该不该上"**。
