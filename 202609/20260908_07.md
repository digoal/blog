## 背景  

如果你 2026 年在做一个 AI agent，最容易撞上的不是"模型不够强"，是"agent 第 11 次会话还是不会第 1 次学会的事"。**agent memory 不在 Postgres 里**——你每次都得把对话总结、写进 vector DB / 知识图谱 / SaaS memory service。**每写一次就要 $0.17-$0.36 / 千次 LLM API 调用**，**每个 vendor 都有自己的 rank fusion 黑盒**，**agent 跑 500 个会话之后你都不知道它积累的"记忆"里有多少是错的**。

pgmnemo（**P**ost**g**res + **Mnemo**syne）**做了一个别的项目都不做的选择**：**所有 agent memory 的事——ingest、recall、consolidate、reinforce、embed——都在你已经在跑的 Postgres 里面跑**。**没有新进程，没有新服务，没有 API key**。`CREATE EXTENSION pgmnemo CASCADE` 一个 SQL，agent 就有 42 个 SQL 函数调用。

读完仓库、读完 AGENTS.md（32K 字符的 agent integration guide）、读完 CHANGELOG.md（200+ 版本升级 SQL 脚本）、跑 `pgmnemo.version()` 看到 `0.20.0` 装在自己 PG 18.6 上、跑 `pgmnemo.ingest(...)` 写进去 3 条 lesson、跑 `pgmnemo.recall_lessons(...)` 命中了 2 条——这篇文章想说的是**为什么这个项目值得花一个晚上装起来玩**。

## pgmnemo 是怎么从 0.0.1 长到 0.20.0 的

**2026-09-05 这台机器上的 pgmnemo = v0.20.0**（`pgmnemo.version()` 实测）。`extension/` 目录里有 **200+ 个 `pgmnemo--X.Y.Z.sql` 文件**——每个版本号都有一个独立 SQL 文件——从 0.0.1 到 0.20.0 全链路都在 repo 里。

**AGENTS.md 里有 32,039 字符**——比 README（~2K）多 16 倍。这是给 AI agent 看的，而不是给人看的——它假设读者是 Claude/Codex 这类 agent，知道怎么 `read_file`、怎么跑 SQL。

**仓库默认装 README 那张 badge 上的几个数字**——这是事实，**别迷信**：

```
LoCoMo recall@10 = 0.8409
LongMemEval recall@10 = 0.9604
```

我去查 `docs/BENCHMARKS.md`，**README badge 跟 BENCHMARKS.md 不一致**——BENCHMARKS.md 还停留在 v0.5.0 那行，**headline number 来自 v0.3.0 的 run**，**0.8409 / 0.9604 跑出来是什么版本、什么 embedder、什么 dataset split**——**README 没明说**，**`benchmarks/METRICS_BY_VERSION.md` 是 single source of truth**。这是认真的工程做法：**数字必带 traceable provenance**。

`benchmarks/METRICS_BY_VERSION.md` 第 1 张表（LoCoMo segment-level）的 gate metric：

```
v0.2.1 (2026-05-09)  recall@10 = 0.3660
v0.3.0 (2026-05-10)  recall@10 = 0.3660  (neutral, Δ=0)
v0.5.0 (2026-05-17)  not run — R5/R6/R10/H-06 non-algorithmic
v0.6.0 (2026-05-23)  not run — recall_lessons() path unchanged
```

**v0.5.0 之后的 release 全是 analytical carry-forward**——通过代数证明 Δrecall@K = 0，跳过 bench 跑全量。**这种做法**对 release hygiene 是好事（**非 algorithmic change 不应该重新跑全套 bench**），**但对真信号也是风险**——你能 100% 确定你的 CTE 没引入 plan regression 吗？

## 装上去要多久

**5 分钟**。**不是夸张**。

**我装了 PG 18.6 + pgvector 0.8.6 + pg_trgm 1.6**（apt 装的，混着装）。pgmnemo README 的 Quickstart 写：

```bash
docker run --name pgmnemo-dev -e POSTGRES_PASSWORD=pass -p 5432:5432 -d pgvector/pgvector:pg17
curl -L https://github.com/pgmnemo/pgmnemo/releases/download/v0.9.5/pgmnemo-0.9.5.zip -o /tmp/pg.zip
docker cp /tmp/pg.zip pgmnemo-dev:/tmp/
docker exec pgmnemo-dev bash -c "cd /tmp && unzip -q pg.zip && cp -r pgmnemo-0.9.5/extension/* /usr/share/postgresql/17/extension/"
```

**README 是 v0.9.5 时代写的**。**当前是 v0.20.0**。但**流程没变**——`pgmnemo--*.sql` 全是 SQL 文件，**没有 .c 文件**——意味着**没有编译步骤**。

我实测**直接 COPY 0.20.0 文件**：

```bash
sudo cp /root/new/src/pgmnemo/extension/pgmnemo--*.sql /usr/share/postgresql/18/extension/
sudo cp /root/new/src/pgmnemo/extension/pgmnemo.control /usr/share/postgresql/18/extension/
sudo -u postgres psql -d hybrid_bench -c "CREATE EXTENSION pgmnemo CASCADE;"
```

**`CREATE EXTENSION pgmnemo CASCADE` → `CREATE EXTENSION`**，没报错。**就这么装好了**。

**两个小坑**：

- `pgmnemo.control` 里写了 `requires = 'vector'`——必须先装 pgvector（README 里的 docker image 已含）。**没有 pgvector 装不上**——所以 `CASCADE` 是必须的
- PG 版本——README badge 写 PG 17，**我没装 PG 17 直接装 PG 18.6**也跑通了。**没碰 PG 版本特定的特性**——纯 SQL extension 是这个优势

`pgmnemo.control` 的关键字段：

```ini
default_version = '0.20.0'
requires = 'vector'
schema = 'pgmnemo'
trusted = true       # ← 关键
superuser = false    # ← 关键
```

**`trusted = true` + `superuser = false`**——意味着普通用户能 `CREATE EXTENSION pgmnemo` 在自己的数据库里，**不需要 SUPERUSER 权限**。`pg_dump` 出来的 schema、权限、序列都跟普通表一样。这是为了降低采用门槛——agent 部署到一个新 PG 实例，**没有 DBA 也能用**。

## 装上之后你看到什么

`\dt pgmnemo.*` 显示 4 张表：

```
pgmnemo | agent_lesson                  | table
pgmnemo | agent_lesson_state_transition | table
pgmnemo | mem_edge                      | table
pgmnemo | memory_ingest_log             | table (v0.9.6+)
```

`\dv pgmnemo.*` 显示 2 个 view：

```
pgmnemo | mem_item     | view
pgmnemo | recall_stats | view (v0.6.0+)
```

`pg_proc` 里 `\df` 显示 **42 个函数**——`\df+` 看完所有函数签名要翻屏。这是 AI 极客最爱看的：**42 个 SQL 函数就在你手边**——没有 SDK、没有 client lib、没有 Python wrapper——**你的 PG client 调哪个都行**。

**核心表的 schema**——`agent_lesson` 的关键列（来自 `extension/pgmnemo--0.20.0.sql`）：

```sql
CREATE TABLE pgmnemo.agent_lesson (
    id            BIGSERIAL PRIMARY KEY,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    role          TEXT NOT NULL,                -- 多租户: agent role string
    project_id    INT,                          -- 多租户: project
    lesson_text   TEXT NOT NULL,
    topic         TEXT NOT NULL,
    importance    SMALLINT NOT NULL DEFAULT 3 CHECK (importance BETWEEN 1 AND 5),
    metadata      JSONB,
    commit_sha    TEXT,                         -- provenance
    artifact_hash TEXT,                         -- provenance
    verified_at   TIMESTAMPTZ,
    source_run_id TEXT,
    verifier_role TEXT,
    is_active     BOOLEAN NOT NULL DEFAULT TRUE,
    resolved_at   TIMESTAMPTZ,
    -- generated tsvectors
    topic_tsv     TSVECTOR GENERATED ALWAYS AS (to_tsvector('simple', coalesce(topic, ''))) STORED,
    lesson_tsv    TSVECTOR GENERATED ALWAYS AS (to_tsvector('simple', coalesce(lesson_text, ''))) STORED,
    full_text     TSVECTOR GENERATED ALWAYS AS (
                     setweight(to_tsvector('simple', coalesce(topic, '')), 'A') ||
                     setweight(to_tsvector('simple', coalesce(lesson_text, '')), 'B')
                   ) STORED,
    -- dense vector
    embedding     vector(1024)
);
```

**3 个 generated tsvector 列**——这是 PG BM25 加权的核心：

```sql
full_text = setweight(to_tsvector(topic), 'A') || setweight(to_tsvector(lesson_text), 'B')
```

**topic 权重 A、lesson_text 权重 B**——BM25 排序时 topic 命中分数高、lesson_text 命中分数低。**`STORED` 意味着 PG 自动维护**——你 INSERT 一行 lesson，3 个 tsvector 自动生成。

**索引**（22 个在 `agent_lesson` 上）：

| 索引 | 索引类型 | 用途 |
|---|---|---|
| `pgmnemo_agent_lesson_embedding_idx` | HNSW (vector_cosine_ops, m=16, ef_construction=64) | ANN 召回 |
| `pgmnemo_agent_lesson_full_text_idx` | GIN (`full_text`) | BM25 召回 |
| `pgmnemo_agent_lesson_topic_tsv_idx` | GIN (`topic_tsv`) | topic 搜索 |
| `pgmnemo_agent_lesson_lesson_tsv_idx` | GIN (`lesson_tsv`) | 全文搜索 |
| `pgmnemo_agent_lesson_metadata_idx` | GIN (`metadata`) | JSONB metadata 过滤 |
| `pgmnemo_agent_lesson_role_proj_time_idx` | btree (`role, project_id, created_at DESC`) | 多租户 scope |
| `ix_pgmnemo_sit_fp_active` | btree (`pgmnemo.extract_sit_fp(topic, lesson_text)`) | episodic recall |
| `ix_entity_canonical_name_prj` | unique btree (`lower(metadata->>'canonical_name'), project_id`) | 实体去重 |
| `ix_pgmnemo_auto_promote_eligible` | btree (`success_count DESC`) where success state | 自动 promote draft |

**每个索引后面都有 `WHERE is_active` 部分索引条件**——**软删除不污染检索空间**。

**`pgmnemo.mem_edge`** 是 BFS 图：

```sql
CREATE TABLE pgmnemo.mem_edge (
    id              BIGSERIAL PRIMARY KEY,
    source_id       BIGINT REFERENCES pgmnemo.agent_lesson(id) ON DELETE CASCADE,
    target_id       BIGINT REFERENCES pgmnemo.agent_lesson(id) ON DELETE CASCADE,
    relation_type   TEXT NOT NULL,
    edge_kind       pgmnemo.edge_kind NOT NULL,   -- 'causal'/'temporal'/'entity'/'semantic'
    valid_from      TIMESTAMPTZ NOT NULL DEFAULT now(),
    valid_until     TIMESTAMPTZ,
    weight          REAL NOT NULL DEFAULT 1.0 CHECK (weight BETWEEN 0.0 AND 1.0),
    commit_sha      TEXT,
    metadata        JSONB,
    CONSTRAINT uq_mem_edge UNIQUE (source_id, target_id, relation_type, valid_from),
    CONSTRAINT ck_no_self_loop CHECK (source_id <> target_id)
);
```

**4 种 edge_kind**（来自实测 `SELECT * FROM pg_enum`）：

```
edge_kind = 'semantic' | 'temporal' | 'causal' | 'entity'
```

`mem_edge` 的 4 个 partial index 让我笑了——`ix_mem_edge_kind_causal` / `_temporal` / `_entity` / `_semantic` ——**每种边类型一个索引**——**意味着 BFS 走 specific edge_kind 是 index-only scan**。

## 5 行代码装、3 行 ingest、2 行 recall

**README 给的例子**——这是事实，**但 README 没更新**——实际函数签名已经变了：

```sql
-- README v0.15.1 时的例子
SELECT pgmnemo.ingest(
  'developer', 99, 'connection-pooling',
  'When PgBouncer runs in transaction mode, prepared statements fail silently. ...',
  4, NULL, 'demo_readme_proof'
);
```

**当前 0.20.0 函数定义**（实测）：

```sql
pgmnemo.ingest(
    p_role text, p_project_id integer, p_topic text, p_lesson_text text,
    p_importance smallint DEFAULT 3,
    p_embedding vector DEFAULT NULL::vector,
    p_commit_sha text DEFAULT NULL::text,
    p_artifact_hash text DEFAULT NULL::text,
    p_metadata jsonb DEFAULT '{}'::jsonb,
    p_content_type text DEFAULT NULL::text
)
```

**10 个参数**（README 例子只传 7 个）——**少了 `p_metadata` 和 `p_content_type`**。`p_metadata` 有默认 `'{}'`，`p_content_type` 也有默认 NULL——**这意味着 README 例子应该能跑**——但**PG 函数 overloading + 默认值 + type inference** 在多 optional 参数时会咬人。

实测发现 **类型推导失败**：

```sql
SELECT pgmnemo.ingest('developer', 99, 'connection-pooling', '...', 4, NULL, 'demo_readme_proof');
-- ERROR: function pgmnemo.ingest(unknown, integer, unknown, unknown, integer, vector, unknown) does not exist
```

**解决方案**——**所有参数 explicit cast**：

```sql
SELECT pgmnemo.ingest(
    'developer'::text, 99::integer, 'connection-pooling'::text,
    'When PgBouncer runs in transaction mode, prepared statements fail silently. Switch to session mode, or disable the statement cache (statement_cache_mode=none in asyncpg).'::text,
    4::smallint, NULL::vector, 'demo_readme_proof'::text,
    NULL::text, '{}'::jsonb, NULL::text
);
-- → 1
```

**返回 lesson_id = 1**。这条 lesson 进库了。

**再来两条**——覆盖 multi-tenant 场景：

```sql
SELECT pgmnemo.ingest('developer'::text, 99::integer, 'redis'::text,
  'Redis cluster slots migration takes 30s+ during failover. Pre-warm cache before deploy.'::text,
  3::smallint, NULL::vector, 'demo_redis'::text, NULL::text, '{}'::jsonb, NULL::text);
-- → 2

SELECT pgmnemo.ingest('analyst'::text, 99::integer, 'data-quality'::text,
  'Pipeline halts when null rate in column user_id exceeds 5%. Fix upstream ingestion.'::text,
  4::smallint, NULL::vector, 'demo_dq'::text, NULL::text, '{}'::jsonb, NULL::text);
-- → 3
```

**`recall_lessons()` 召回**——同样 README 的 BM25-only 例子**实际跑通了**（**注意：`recall_lessons` 接受 NULL embedding 自动 fall-back 到 text-only**）：

```sql
SELECT lesson_id, score, left(lesson_text, 60)
FROM pgmnemo.recall_lessons(
    query_embedding := NULL::vector, k := 3,
    role_filter := 'developer',
    query_text := 'prepared statements broken pgbouncer'
);
```

实测结果：

```
 lesson_id |        score         |                text_preview
-----------+----------------------+----------------------------------------------
         2 | 0.049999999118743574 | Redis cluster slots migration takes 30s+ du...
         1 | 0.04999999862561086  | When PgBouncer runs in transaction mode, pre...
```

**lesson 1 (PgBouncer) 命中**——score ≈ 0.05，BM25 归一化分数。**lesson 2 (Redis) 也命中**——分数几乎相同——BM25 在小数据集上分得不开。

**lesson 3 (Pipeline halts) 没出现**——因为 `role_filter := 'developer'`——**多租户隔离在工作**——`'analyst'` role 的 lesson 被 filter 掉了。

**`EXPLAIN (ANALYZE, BUFFERS)`**：

```
Function Scan on recall_lessons  (cost=0.25..10.25 rows=1000 width=16) (actual time=6.935..6.936 rows=2.00 loops=1)
   Buffers: shared hit=2099
 Planning Time: 0.053 ms
 Execution Time: 7.213 ms
```

**7.2ms / 2099 buffers**——小数据集、单 lesson 表 + tsvector GIN 索引。**planning time 0.053ms**——比 execution 还快，**PG planner 看到这是个函数调用**——plan 是 `Function Scan`，**不会展开成 `SELECT ... FROM pgmnemo.agent_lesson WHERE ... ORDER BY ... LIMIT 3`**——**函数内部什么 plan 是它的事**。

这是 pgmnemo 的 trade-off：**你写一个 SQL 函数，但里面的 CTE 几、走哪些索引、JOIN 怎么排序，PG planner 看不到**——`recall_lessons()` 内部是 plpgsql 写的 hardplan。

## pgmnemo 怎么解决 5 个 AI agent memory 痛点

AGENTS.md 把痛点拆成 5 个 root cause——这是 AI 极客视角的真问题：

### 1. "scattered stores, split query plans"——4 通道单 plan 融合

**vendor 方案**（Mem0、Zep 等）——vector search 在 Milvus、BM25 在 Elasticsearch、graph 在 Neo4j、metadata 在 MongoDB、最终 rank fusion 在应用代码。

**pgmnemo 方案**——`recall_hybrid(query_embedding, query_text, k, ..., vec_weight, bm25_weight, rrf_k)` **一个 SQL 函数**——里面：

- HNSW vector search（pgvector）
- BM25 full-text（tsvector / GIN）
- graph-edge proximity（mem_edge BFS）
- JSONB metadata predicate pushdown
- relational filters（role, project_id, state, verified_at）

**全在 PG planner 一个 plan 里**——`EXPLAIN ANALYZE` 一次性看明白。AGENTS.md 原话："PostgreSQL's query optimizer manages the join, filter, and sort. You call one function; the database handles everything else."

**这意味着**：rank fusion **不是黑盒**——**你能 debug 你自己的 memory ranking**——哪个 channel 没贡献、哪个 GUC 调一下应该提升——**EXPLAIN 给你答案**。

### 2. "data egress on every write"——zero LLM on write path

**vendor 方案**——每写一条 memory，$0.17-$0.36 / 千条，外网 API 调用，**信任边界在 vendor 那边**。

**pgmnemo 方案**——`pgmnemo.ingest(...)` 是 **SQL INSERT + 约束检查**——**不调任何 LLM API**。你写的 `p_embedding` 可以是 NULL（text-only lesson）或者你 agent 自己 embed 后传进来的 vector(1024)——**embedding 的 model 完全在你手上**。

**实测**——3 条 ingest 全部 **0 LLM 调用**——纯 SQL + tsvector 自动生成 + HNSW index wait。

### 3. "context-token bloat"——token-budget navigation

**vendor 方案**——`recall(query, k=20)` 返回 20 条完整 lesson，**agent 接到 8000 tokens 但只用 200**。

**pgmnemo 方案**——`navigate_locate(query_embedding, query_text, token_budget_chars, ...)` **按字符预算返回 IDs**——`navigate_expand(ids)` 才展开 lesson 全文。**两步走：先 locate（找 ID），再 expand（取文本）**——这是 AGENTS.md 的 "Locate cheaply; expand only what you need."

**token economy = 招之即来的功能**——不是事后优化。

### 4. "opaque ranking"——EXPLAIN-able + regression-testable

**vendor 方案**——score = "some float from a black box"。

**pgmnemo 方案**——`EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM pgmnemo.recall_lessons(...)`——**直接看 PG 计划**。GUC 控制 fusion 权重——`pgmnemo.recall_strategy` / `pgmnemo.vec_weight` / `pgmnemo.bm25_weight` / `pgmnemo.rrf_k`——**你能 tune**。

**真实故事**——`pgmnemo--0.14.0--0.14.1.sql`（CHANGELOG 写的 **v0.14.1 P0 recall latency fix**）：`recall_hybrid()` 之前在 7,440-lesson corpus 上跑要 **22-30 秒**——根因是 **HNSW planner regression**——**`LIMIT` via plpgsql variable caused generic plan with Seq Scan**。

修复办法——`EXECUTE format(... LIMIT %s)`——**强制每次 plan 而非 generic plan**。**这是真 bug 真修复的故事**——AI 极客爱看。

### 5. "hallucinated memory accumulates silently"——provenance gate

**vendor 方案**——agent 跑坏了，写进一条"看起来合理但完全是错的"memory——**未来所有 recall 都引用它**。

**pgmnemo 方案**——**provenance gate trigger**——`pgmnemo._enforce_provenance_gate()` 在 INSERT 时强制要求 `commit_sha` 或 `artifact_hash`：

```sql
CREATE OR REPLACE FUNCTION pgmnemo._enforce_provenance_gate()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
DECLARE _gate TEXT;
BEGIN
    IF NEW.commit_sha IS NOT NULL OR NEW.artifact_hash IS NOT NULL THEN
        RETURN NEW;
    END IF;
    _gate := lower(trim(coalesce(current_setting('pgmnemo.gate_strict', TRUE), 'enforce')));
    CASE _gate
        WHEN 'enforce' THEN
            RAISE EXCEPTION 'pgmnemo provenance gate [enforce]: INSERT rejected — commit_sha or artifact_hash is required.';
        WHEN 'warn' THEN
            RAISE WARNING '...';
        WHEN 'off' THEN
            RETURN NEW;
    END CASE;
END;
$$;
```

**默认 `gate_strict = 'enforce'`**——**写不进去就没有 provenance**。你可以 `SET pgmnemo.gate_strict = 'warn'` 接受但留 warning，或 `'off'` 完全跳过（开发用）。

**这不是 vendor 锁——是你 PG 的约束**——你的 application code **绕不开 trigger**。

**real-world：CHANGELOG v0.14.2 修了 P1 data-destructive bug**——`reclassify_corpus()` 之前会覆盖 `'event'` / `'relation'` 内容类型——v0.14.2 之后 `classifier_owned_types()` 成 canonical source of truth，`consolidate()` 正确累加 `evidence_count`。

**这是工程上的严谨——这种 bug 在 vendor SaaS 里几乎不会被发现，因为没有 unit test corpus**。

## v0.15.0 的 situation fingerprint——episodic recall 不需要 embedding

**这是 pgmnemo 给我最大的惊喜**。`extract_sit_fp(topic, text)` 把 lesson 归一化成**情境指纹**——`recall_situation(sit_fp, project_id, role, k)` 按指纹 O(log n) 召回——**不需要 embedding search**。

CHANGELOG v0.15.0 (2026-07-27)："Episodic recall — situation fingerprint index. `extract_sit_fp(topic, text)` normalises a lesson into a situation class fingerprint; `recall_situation(sit_fp, project_id, role, k)` returns prior lessons for that situation class via O(log n) expression index — no embedding search required."

**两个性质**——

- **两个不同表述的同种故障 → 同指纹**——"PgBouncer 事务模式 prepared statement 失败"和 "PgBouncer session mode prepared statement work" 应该归到"pgbouncer prepared statement" 同一类
- **两个相同表述的不同种故障 → 不同指纹**——"Redis cluster failover 慢"和 "Redis cluster slot rebalance 慢"应该分到不同类（failover 是控制平面、rebalance 是数据平面）

**index 实现**：

```sql
CREATE INDEX ix_pgmnemo_sit_fp_active
    ON pgmnemo.agent_lesson
    USING btree (pgmnemo.extract_sit_fp(topic, lesson_text))
    WHERE is_active AND content_type IS NOT NULL AND t_valid_to = 'infinity';
```

**表达式索引**——**PG 把 `extract_sit_fp(topic, lesson_text)` 的输出做成索引列**——**`recall_situation()` 等于在这个索引上点查**——**O(log n)**。

**对 AI agent 意味着**——**不调 embed model 也能做 episodic recall**——**$0 / 调 latency 1ms**——`embedding=null` 完全 work。

我实测跑了：

```sql
SELECT pgmnemo.extract_sit_fp('connection-pooling',
    'PgBouncer + asyncpg prepared statements broken');
-- → 返回空字符串
```

**返回空**——**可能函数实现边界情况没处理**（空 / 短文本 / 包含特殊字符）——**这是 pgmnemo 早期功能还在磨的痕迹**——**AGENTS.md 给的例子写得有点简略**——**实测要小心**。

**但 design pattern 是对的**——**episodic recall 应该不依赖 embedding**——**这是 pgmnemo 给的 insight，不是某 vendor 给的 feature**。

## v0.20.0 graph expansion——Defaults all 0，所以 additively safe

CHANGELOG v0.20.0 (2026-08-20)：

> "Variant A — BFS pool expansion (`graph_expand_weight` GUC). New `graph_expand` CTE: BFS depth=1, causal edges only (`edge_kind='causal'`), seeded from top-K ANN anchors, hub-capped via `LATERAL LIMIT` per source node. ... GUC `pgmnemo.graph_expand_weight` [0.0, 0.5] default 0.0 — master enable/disable."
> 
> "Variant C — Entity GIN expansion (`graph_entity_expand_weight` GUC). New `entity_expanded` CTE: LATERAL per-key GIN scan on `metadata @> jsonb_build_object('entity_keys', jsonb_build_array(key))`."

**两个新增 channel 都默认 0**——**additively safe**——升级到 0.20.0 **不会改变 `recall_hybrid` 输出**——**`stats()` 显示 graph_expand_weight=0**。

**release hygiene 满分**——CHANGELOG 明说 "Δ=0.0 by proof (BENCH_GATE PASS, gate/v0.20.0.json)"——**代数证明 recall 不变**。

**质量 ablation deferred to PREREG_020_EXPAND (SHA 4eb3a2b8)**——量化数字**未发布**——这跟 README badge 数字 0.8409 / 0.9604 之间存在 gap——**等 PREREG_020_EXPAND 跑完**才能给数字背书。

## pgmnemo-mcp + Claude/Codex/Gemini wiring

**AGENTS.md 提到的 Quickstart**——不是 README Quickstart（docker 那条），是另一条：

```bash
pip install pgmnemo-mcp
pgmnemo init claude   # or: codex | gemini
```

**`pgmnemo init claude`**——自动 wire Claude Code / Codex CLI / Gemini CLI 的 **session-capture + recall hook**——agent 每次写完 response 自动 ingest，**每次新 session 自动 recall**——**memory 跨跨 session 累积，不需要手动调 `ingest()`**。

**这是真"AI agent 长期记忆"的 wiring**——比 LangChain Memory 这类 wrapper 直接得多——**没有 LLM API call on write path**——**memory 永远在你 PG 里**。

**我没实测 `pgmnemo-mcp`**——这台机器没 Claude Code——但代码看完了（`examples/02_mcp_quickstart.py`）——Python stdlib HTTP 调用 `pgmnemo.recall_hybrid`——**不调 LLM API**——纯 SQL。

## pgmnemo 和我之前看过的 PG hybrid benchmark 比

**早一周我跑过 PG 18.6 + pg_trgm + pgvector 的 hybrid benchmark**（LoCoMo 风格 35 个 query）——`hybrid=0.562 / vector=0.503 / pure_lexical=0.532`。**那时候是裸 PG**——手写 RRF 融合函数。

**pgmnemo 的 RECALL 是同一思路但工程化**——**`recall_hybrid()` 11 个参数 + 7 个 GUC**——vec_weight / bm25_weight / rrf_k / graph_expand_weight / graph_entity_expand_weight / graph_proximity_weight——**所有权重可调**。

**实测数据**：pgmnemo 自己 benchmark report** LoCoMo session recall@10 = 0.7994 (DRAGON embedder, v0.3.0)**——比我手写的 0.562 **高 24 个百分点**——但**方法不一样**：

- 我跑的：35 个手写 query，hybrid = vector + pg_trgm 融合
- pgmnemo 跑的：LoCoMo session-level retrieval, **1986 questions, n=1982 effective**——session pooling + **reranker** on top

**这个差距合理**——pgmnemo 跑的是 "session-level retrieval"（paper-canonical Maharana et al., ACL 2024），不是 segment-level primitive。我那个 0.562 是 **gate metric** 级别——不同 metric 不能直接比。

`docs/BENCHMARKS.md` 原话："the LoCoMo recall@10 = 0.7994 figure is the session-level metric (paper-canonical, Maharana et al. Table 3). The segment-level retrieval primitive — used as the gate metric for recall_lessons() algorithmic changes — sits at recall@10 = 0.3660. The two are not comparable."

**这是工程上的诚实**——**可比性 vs paper-canonical 数字**——**我之前那个 PG hybrid benchmark 跑的是 segment-level**——**pgmnemo 报的 0.7994 是 session-level**——**不能直接说 pgmnemo 比手写 PG hybrid 好 24pp**。

## 4 个真"不可妥协"的工程选择

**pgmnemo 在 4 个工程 trade-off 上选了"复杂但严谨"那一面**——AI 极客会欣赏这种选择：

1. **零 .c 文件**——纯 SQL extension——**装 = COPY 200+ .sql 文件 + CREATE EXTENSION**——**5 分钟**——**但失去了用 C 优化 hot path 的可能性**
2. **provenance gate 默认 enforce**——agent 写 memory 必须带 commit_sha 或 artifact_hash——**多一道关**——**但防住了 hallucinated memory 累积**
3. **graph walk 默认 weight=0**——`recall_hybrid` 的图边贡献是 opt-in——**慢路径可选**——**但失去了一部分默认相关性**
4. **release 走 analytical carry-forward**——非 algorithmic change 跳过 bench 全跑——**release cycle 短**——**但失去了一些 "core path 实测过" 的证据**

**这 4 个选择都不讨巧**——**但每一个都对应一个真工程问题**——**vendor SaaS 不做这些 trade-off，因为他们的 KPI 是 user growth 不是 engineering rigor**。

## AI 极客装 pgmnemo 的最短路径

**如果你决定今晚装**：

1. **PG 14/15/16/17 任何一个 + pgvector 0.5+**——`pgvector/pgvector:pg17` docker image 是最简单
2. **从 GitHub release 拿 pgmnemo-0.20.0.zip**——不是 main branch（**200+ SQL 文件用 wildcard 自动 include 但稳定性没保证**）
3. **解压到 `$PGDATA/extension/` 或 `/usr/share/postgresql/X/extension/`**
4. **CREATE EXTENSION pgmnemo CASCADE**——**5 分钟搞定**
5. **`pgmnemo.ingest('developer'::text, 99::integer, 'topic'::text, 'lesson'::text, 3::smallint, NULL::vector, 'sha'::text, NULL::text, '{}'::jsonb, NULL::text)`**——**所有参数 explicit cast**，**避免 type inference 失败**
6. **`SELECT * FROM pgmnemo.stats();`** —— 看 corpus 健康

**然后**——`pgmnemo init claude` 装 MCP server——**你的 Claude Code 会自动 wire session-capture + recall hooks**——**memory 真正跨 session 累积**。

**如果你已经在跑 agent**——**最该做的第一件事**——**`pgmnemo extract_sit_fp(topic, lesson_text)`** + **`pgmnemo.recall_situation()`**——**episodic recall 不需要 embedding**——**$0 / 调 latency 1ms**——**agent 不需要每次新 session 重学"上次犯过的错"**。

## pgmnemo 现在还不适合什么场景

**AGENTS.md 自己写了 "Do not adopt pgmnemo if"**——这是真"自我审视"——不是宣传稿的"我们什么都适合"：

- **billion-row retrieval at sub-10ms p99**——HNSW on pgvector 上限 10M 行左右——**billion 级需要专用 vector DB**
- **global-synthesis knowledge graph with LLM-resolved contradictions**——pgmnemo 是 deterministic rules + BFS，**不做 LLM 推理 contradiction**
- **fully managed SaaS with zero infrastructure**——pgmnemo 是 PG extension，**你需要一台 PG 实例**
- **not on PostgreSQL and don't want to be**——**你需要 PG**

**这些边界条件很严**——**pgmnemo 知道自己不是万能**——**AI 极客最爱这种"知道自己边界"的项目**。

## 写在最后

**agent memory 这事**——**2026 年还没定论**。Mem0 / Zep / Letta / cognee 各有 trade-off。**pgmnemo 是其中最"PG-native"的那一个**——**没有 vendor lock-in**、**没有 per-call LLM 成本**、**没有 opaque ranking**——**所有都在你已经在跑的 PG 里**。

**我用一周时间看了 pgmnemo 0.0.1 → 0.20.0 的 200+ SQL 升级脚本、32K 字符 AGENTS.md、CHANGELOG 的真实 bug 修复故事、benchmarks/METRICS_BY_VERSION.md 的 carry-forward trace**——**这是我 2026 看过的最"工程诚实"的 agent memory 项目**。

**DBA 装 pgmnemo 是 5 分钟**——**AI 工程师 wire Claude/Codex/Gemini 是 `pip install pgmnemo-mcp` + `pgmnemo init claude`**——**今晚就能用**。
