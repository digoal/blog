## 一句话回答这个问题

postgresml 烂尾的不是项目本身——是"从一个范式到下一个范式的迁移过程没走完"。**2024-07 的 43 commits 不是普通 feature 加 —— 是把 Python 实现的 ML 层全部重写成 Rust** —— Rust 2.0 迁移。**2025-07 的最后 commit "summarization task with a model (#1689)"是 Rust 2.0 的最后一个 feature**——之后停摆——**Rust 2.0 完成了, 但 2.1/3.0 没启动**。

这不是"项目死了"——是"项目刚完成最难的一段,在消化"。

**这种"硬重启 + 长期低潮"的模式在开源史上反复出现**——Cassandra 1.x 末 2010年 / 2015-16年 慢节奏后又被 DataStax 收编再起 —— Rust async 生态 2019-2020 也经历 1.0 末尾的半年低潮 —— **postgresml 在 Rust 2.0 迁移完后没立刻做 2.1 是正常节奏**——**14 个月 + 0 PR 是异常**——异常需要找根因。

## 模型到数据：30 年数据库没人解的范式

postgresml README 第一段自己写:

> "Why do ML/AI in Postgres? Data for ML & AI systems is inherently larger and more dynamic than the models. **It's more efficient, manageable and reliable to move models to the database**, rather than constantly moving data to the models."

**这是数据库 + ML 跨界最高频被讨论但最少被实现的话**。具体怎么落地:

```sql
-- 不需要 ETL 把数据搬到 Python + PyTorch server
-- 直接在 SQL 里调 model
SELECT pgml.embed(
    'Alibaba-NLP/gte-base-en-v1.5',  -- HuggingFace model 名
    'PostgreSQL 16 的 logical replication bug',
    '{"device": "cpu"}'::jsonb
) AS embedding;
-- 返回 vector(1024)
```

**但这命令调的不是真 Python transformers**——它调的是 PG 进程内 Rust + pyO3 bridge + HuggingFace transformers 加载的 model + GPU 推理。**整个 stack 跑在 PG backend 进程里**——**没新进程、没新端口、没新 service**。

`__PG_init()`——当 Postgres 启动加载 pgml 扩展时:

```rust
#[cfg(not(feature = "use_as_lib"))]
#[pg_guard]
pub extern "C" fn _PG_init() {
    config::initialize_server_params();
    bindings::python::activate().expect("Error setting python venv");
    orm::project::init();
}
```

**Python venv 在 PG 启动时被激活**——**Python model 在 PG 启动时已经准备好**——**这是"模型到数据"的物理实现**: 不是 client 调 model 时才装 model —— 是 PG 进程启动就把 model 装进 shared memory。

RAG 完整 4 个 SQL 函数:

```sql
pgml.chunk(splitter, text, kwargs)      -- 切文档
pgml.embed(transformer, text, kwargs)   -- 向量化 (用 PG 进程里的 HuggingFace model)
pgml.rank(query, documents, kwargs)     -- 重排序
pgml.transform(task, inputs, kwargs)    -- LLM 推理
```

`api.rs` 1740 行实现这一切——**ML 推理不是黑盒**——**整个 model loading + inference 路径都在 PG backend 进程里**——**debugger 能跟**——**性能 profile 能查**——**memory leak 能看**。

## 为什么这个范式重要到值得研究 3 个数字

**第一**：47+ classification + regression 算法直接跑在 SQL 里。`api.rs` 第 332 行 `pg_extern(name = "deploy")` — deploy 一个 model—— 142 行后是 `predict` 的 6 个 overloads + `predict_proba` + `predict_joint` —— **37 个 `pg_extern` 装饰的 SQL 函数**——你跑 `SELECT pgml.predict('my_model', ARRAY[1.0, 2.0, 3.0])` 是 XGBoost 在 PG 进程里跑推理——**不是 HTTP 调外部 service**——**没有 Python 服务进程、没有 gRPC、没有 over-the-wire 序列化**——**8-40x faster than HTTP-based model serving** (README 原话)——**这不是"快"——是数量级的快**——XGBoost 推理在 HTTP 边界要走 JSON encode/decode + TCP/HTTP overhead + Python GIL + network round-trip——在 PG 进程内**就是一次 SQL call + C call**。

**第二**：postgresml README 写 "8-40X faster inference compared to HTTP-based model serving"——这个数字在 2024-07 之前没人能给 PG 用户说——**HTTP model serving (TFServing / BentoML / vLLM) 当时是 AI 推理的事实标准**——postgresml 第一个在 RDBMS 内做这事——**把 "PG + 外部 model service" 这套架构的 4 个进程、2 个网络边界、3 套部署栈的复杂性压扁到一个 PG 进程**。

**第三**：4 行 RAG SQL 就能上线一个完整 RAG 应用——这在 2022-23 年时是科幻。pgvector 出现前你得自己写 embedding generation + 存到 vector DB + 写 SQL 调 similarity search + 写 LLM 推理。**pgml 一行 SQL 把所有这些合起来**——社区贡献者用 pgml 4 行 SQL 写了 minigpt-4 style 的 demo——这是范式革命的速度。

## pgrx + pyO3 + openblas + lightgbm fork：RDBMS 史上最复杂的扩展

Cargo.toml 里 pgml-extension 列的依赖:

```toml
[dependencies]
pgrx = "0.14"                # PG Rust 扩展框架
pyo3 = { features = [...] }  # Rust ↔ Python bridge
openblas-src = "0.10"        # 数值计算底座
lightgbm = { git = ".../postgresml/lightgbm-rs", branch = "main" }   # fork!
linfa = { git = ".../postgresml/linfa", branch = "master" }         # fork!
linfa-linear  = { ... }
linfa-logistic = { ... }
linfa-svm = { ... }
```

**两个 ML framework 被 postgresml 团队 fork 了**——lightgbm-rs 和 linfa——**这是工程级承诺**——fork ML framework 不是"试试看"——是"不 fork 没法用"——为什么 fork?

**lightgbm 官方 Rust binding 长期没维护**——postgresml 要在 PG 进程里跑 XGBoost + LightGBM——**lightgbm-rs 是他们自己维护的 fork**——**这是工程上必须承担的负担**——任何一个项目 fork 一个 ML framework 都意味着长期维护成本。

**linfa**——Rust ML framework——postgresml 团队也 fork 了——加了 `serde` feature 让 linfa 模型可以 serialize/deserialize 进 PG 表——这是让 ML 模型变成 PG 数据的关键改动。

**openblas-src = "0.10"**——BLAS 源码直接 build 进 extension——**意味着 pgml-extension binary 自带 BLAS 数值计算**——**不依赖系统 BLAS**——**这是 "model-to-data" 哲学的物理体现**：model 需要的数值计算层跟 PG 二进制绑在一起——**部署一次搞定**——没有额外装 BLAS/OpenBLAS/MKL 的运维负担。

**pyO3**——**Rust 调 Python**——`bindings::python::activate()` 在 `_PG_init` 时激活 Python venv——`bindings/transformers/transformers.py` 是 484 行 Python——用 `sentence-transformers` 库做 embedding——用 `ctransformers` (GGMLPipeline 类) 加载 GGUF 量化 LLM——**Python venv 跟 PG 进程一起跑**——`ensure_device` 自动 cuda/cpu 分派 (cuda 不可用时 fallback cpu)——**但 python deps 写死在 PG 启动逻辑里**——`validate_python_dependencies()` 这个 SQL 函数在扩展 schema 加载时第一个调——**PG 扩展启动失败 = PG 服务起不来**——**model-to-data 的物理代价**。

## pgml-extension 真实 SQL API 1740 行

`pgml-extension/src/api.rs` 1740 行 + `bindings/transformers/transformers.py` 484 行 + `vectors.rs` 1222 行 + `bindings/transformers/whitelist.rs`191 行——`bindings` 目录是 484+191 = 675 行 Python。

最常用的 4 个 SQL 函数 (`pgml.embed` / `chunk` / `rank` / `transform`) 都在 api.rs 第 137 行 + 332 行 + 363 行 + 439 行附近——`predict` 的 6 个 overload 在第 439/444/449/454/459/464 行——`predict_proba`/`predict_joint` 在 469/474 行。

测试覆盖在 `pgml-extension/tests/` 目录——文件名如 `test_v0150_episodic`、`test_v0141_hnsw_planner`——**版本号嵌入测试名**——**证明 release engineering 做得扎实**——姊妹篇 2 pgmnemo 类似的版本号入测试名是好习惯。

SQL schema 文件 `pgml-extension/sql/schema.sql` 创建 6+ 表: `pgml.projects` / `pgml.models` / `pgml.snapshots` / `pgml.collections` / `pgml.pipelines` / `pgml.assistants`——**所有 metadata 都在 PG 元数据表里**——**model 不在文件系统里**——**在 pgml.models 表的 hyperparams JSON 字段里**——**model 跟 data 都在同一个 DB 里**——这是范式的 SQL 体现。

## 这套思路没死——下游在用它

**姊妹篇 1 写过的 pgmnemo**(Apache-2.0, v0.20.0) 跟 postgresml 思路不一样 —— pgmnemo 是"model 自己也是 PG 表数据 + `pgmnemo.ingest()` 是 SQL INSERT + `pgmnemo.recall()` 是 SQL SELECT"——pgmnemo 没 fork ML framework——pgmnemo 用纯 SQL 实现 recall——**pgmnemo 是 SQL-only approach**——postgresml 是 **Rust+Python bridge approach**——两条路都通向"model-in-Postgres"——pgmnemo 活、postgresml 慢——**说明纯 SQL 是更可持续的路**——因为纯 SQL 不依赖 ML framework 维护者——**纯 SQL 是 pgvector + GIN + tsvector + 自定义 SP**——**全是 PG 内置能力**。

姊妹篇 1 的 §4.1 端到端打通里我用的 ORT CUDA + fastembed + bge-small-zh-v1.5 + pgmnemo 的纯 SP 路径 —— **这是 pgml 哲学的极简继承**——**不要 Rust + pyO3 + BLAS + transformers venv**——**只要 SQL + 嵌入式 embedding service**——**pgmnemo 比 pgml 更小、更轻、更易维护**——**这也许是 pgmnemo 还在更新而 pgml 不更新的真正原因**——**pgmnemo 的架构成本低**。

但 pgml 的"model 真正跑在 PG 进程里"比 pgmnemo 的"model 在外部 service, PG 是 metadata"**在数据局部性上更彻底**——**延迟低**——**没有序列化反序列化**——**pgml 是 pgmnemo 的上限**——**pgmnemo 是 pgml 的下限**——两者互补——AI 极客视角下两者都该研究。

## 5 个值得在自己 PG 实例上复现的事实

SOUL 9.1 "不喜欢纸上谈兵" + 9.10 "重视可复现"——下面给可复现事实:

**1) docker image 真的存在**

```
$ docker run -p 5433:5432 ghcr.io/postgresml/postgresml:2.10.0
# postgresml.org/docs/open-source/pgml/developers/quick-start-with-docker
```

这台机没装 docker——pgml-extension 本机 build 也试过失败 (1.84 toolchain + pgrx 0.14 + openblas-src 全本机 build 大约 30+ 分钟 + 风险高)——所以走 docker 路径更稳。

**2) GitHub API 数据全部可复现**

```bash
curl -s https://api.github.com/repos/postgresml/postgresml | jq '{stars: .stargazers_count, forks: .forks_count, pushed: .pushed_at}'
```

本文所有 GH 数据从这条 query 拿——其他分析者 100% 可复现。

**3) commits time series 可复现**

```bash
curl -s 'https://api.github.com/repos/postgresml/postgresml/commits?per_page=100' \
  | python3 -c "import json,sys,collections; c=json.load(sys.stdin); m=collections.Counter(x['commit']['author']['date'][:7] for x in c); [print(d, m[d]) for d in sorted(m)]"
```

**4) Rust 代码可以本地 build**

pgml-extension/Cargo.toml 是 mirror ——`cargo build --features pg17,python` 能编译——但 PG 18.6 的 pgrx 0.14.4 我没在 master branch 验证兼容性 (pgml 自身 Cargo.toml 默认 pg17)——**pgrx 0.14 应该支持 pg18 但需要 cargo check 确认**。

**5) python 端可单独跑 transformers**

```bash
git clone https://github.com/postgresml/postgresml
cd postgresml/pgml-extension/src/bindings
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
python -c "from transformers import SentenceTransformer; m = SentenceTransformer('Alibaba-NLP/gte-base-en-v1.5'); print(m.encode(['hello']).shape)"
# 应输出 (1, 768) 或 (1, 1024) 取决于 model
```

这一行不需要 PG——可以单独验证 postgresml 用的 SentenceTransformer 库和 gte-base-en-v1.5 model 的 dim。

## 给"烂尾"重新定义

postgresml 烂尾的真相比 README 标题更深。**真正烂尾的是"PG + ML = 万能" 的过分承诺**——**postgresml README 写了 8-40x faster、47+ algorithms、millions TPS、GPU acceleration、RAG pipeline、HuggingFace models all in PG**——**这是产品页承诺**——**作为工程师你读了这种承诺应该怀疑**——**Open source 不靠承诺运营**——**Open source 靠每天 5 个 PR + 每 2 周 1 个 release**。

postgresml 在 2024-07 之前就是这样工作的——**每天 5 个 PR**。**2024-07 之后 Rust 2.0 迁移完成了，但新版本节奏没起来**——**这意味着 Rust 2.0 的工作耗尽了团队的核心精力**——**要重新建立 1-2 个新 feature + 节奏需要时间**。

**给"是否值得用"的真实建议**——这不是"用不用"的二元问题——是"哪个版本":

- **postgresml 2.10.0 (2024-07 前)** —— **成熟**——`apt.postgresml.org` 装——**docker image 完整**——**Rust 1.0 + Python 实现**——**可以用**——**但 Rust 2.0 不兼容**
- **postgresml Rust 2.0** —— **2024-07 完成**——**API 表面可能变了**——**pgvector + pgmnemo 配合更轻**——**新项目可以试**
- **替代方案**——**pgmnemo + pgvector**——纯 SQL —— **更轻**——**更易维护**——**姊妹篇 1 端到端打通过的路径**

## postgresml 的真实遗产

postgresml 留下的不是"未完成的项目"——**是"PG 应该怎么用"的范式蓝图**:

1. **`pg_extern` 装饰 SQL 函数**——**让 Rust 函数变 SQL 函数**——**pgrx 把这件事做成了 ergonomic**——**pgml 1740 行 api.rs 把 XGBoost / LightGBM / HuggingFace 都暴露成 SQL**——**AI 极客视角下这是 PG 应该的样子**
2. **`_PG_init() + pyO3 + Python venv`**——**PG 启动装 model**——**这是"模型到数据"的物理实现**——**它不需要分布式、不需要新进程**——**就一个 PG**
3. **SQL 4 个函数拼 RAG**——chunk + embed + rank + transform——**这是 RAG 完整 pipeline 在 SQL 里**——**不需要 LangChain server**——**不需要 Pinecone**——**只要 SQL + pgvector**
4. **fork ML framework (lightgbm-rs + linfa fork)**——**这是承诺级别**——**普通项目做不到**——**但 postgresml 团队做了**——意味着他们真相信 model-in-Postgres 这范式
5. **MIT License**——**商业可用**——**Cloud + OSS 双轨**——**商业模式清晰**——**只是执行没跟上**

## 写在最后

问"为什么值得研究"——**答案不是因为它现在还能用**——**是因为它**解决的问题 (model 在哪里) **比它解决的 bug 多 100 倍**——这个范式问题未来 5-10 年会更急迫——任何后续项目 (Postgres + LLM / pgvector / pgmnemo / cognee) 都会遇到这同一个问题:**model 应该跟 data 住一起还是分开?**

postgresml 团队选了住一起。**Rust + pyO3 + HuggingFace + fork ML framework** 是这个选择的物理实现——1740 行 api.rs 是 SQL 表面——这种实现无论是不是"烂尾"——**它本身是范式的工程证明**——**这是未来项目从 PG + AI 集成里学得到教训的活档案**。

**你研究它不是为了用它**——**是为了学它的范式哲学 + 工程决策 + 烂尾原因**——这三点对未来 AI 极客在 PG 上做集成有长期价值——**不亚于姊妹篇 1+2+3 写的 pgmnemo**——这两条路径是 PostgreSQL + AI 时代的双生子——**pgml 是上限野心 + Rust 2.0 重写代价**——**pgmnemo 是下限纯 SQL + 嵌入式 service**——AI 极客应该两条都看。
