## 背景  

2026 年 9 月,在 PG 18.6 跑 CREATE EXTENSION age 就能用 Apache AGE 1.8.0 跑 openCypher,在 PG 19 master 能用 SQL:2023 标准 GRAPH_TABLE 跑属性图。同一个 PG 上的图,两条路线,两种哲学,两种用法。AI 上下文管理实践者关心这件事,因为 AI 记忆 / Agent 行为 / 知识图谱本质都是图查询——"找出 A 关联的所有概念"或"A 用过哪些工具"——这种多跳推理需要图。

AGE 走的是 2018 年的 openCypher(Neo4j 贡献的 Cypher 子集)+ 自定义 agtype + VLE DFS 实现。PG 19 SQL/PGQ 走的是 SQL:2023 标准 + GRAPH_TABLE 子句 + pg_catalog 集成。两者在 AI 上下文管理场景下的取舍是这篇文章要拆的事。

## 先看本机实测: AI 上下文图在 PG 里长什么样

```bash
# 本机 PG 18.6 + AGE 1.8.0
sudo apt-get install postgresql-18-age   # apt.postgresql.org 仓库
sudo -u postgres psql -d postgres
```

```sql
CREATE EXTENSION age;
LOAD 'age';
SET search_path = ag_catalog, "$user", public;

-- 1. 建图: 模拟 AI 上下文管理 schema
SELECT create_graph('ai_ctx');
SELECT create_vlabel('ai_ctx', 'Agent');        -- AI agent (claude-code / gpt-4 等)
SELECT create_vlabel('ai_ctx', 'Memory');       -- 单条记忆/经验/教训
SELECT create_vlabel('ai_ctx', 'Concept');      -- 概念/技术/术语
SELECT create_elabel('ai_ctx', 'remembers');    -- Agent -> Memory
SELECT create_elabel('ai_ctx', 'uses');         -- Agent -> Concept
SELECT create_elabel('ai_ctx', 'related_to');   -- Concept <-> Memory / Concept <-> Concept
```

`create_vlabel` / `create_elabel` 是 AGE 暴露的 DDL SP——**底层把 vertex/edge 变成 PG 真表**——`\d ai_ctx."Memory"` 看到的:

```sql
              Table "ai_ctx.Memory"
   Column   |  Type   | Nullable |    Default
------------+---------+----------+-----------------------------------------
 id         | graphid | not null | _graphid(_label_id(...), nextval(...))
 properties | agtype  | not null | agtype_build_map()
Indexes:
    "Memory_pkey" PRIMARY KEY, btree (id)
Triggers:
    _age_cache_invalidate AFTER INSERT OR DELETE OR UPDATE
Inherits: ai_ctx._ag_label_vertex
```

**这不是"图数据库",是 PG 里 4 张表**。`Agent` / `Memory` / `Concept` 是 3 张 vertex 表,每张都继承 `_ag_label_vertex` parent table;`remembers` / `uses` / `related_to` 是 3 张 edge 表,继承 `_ag_label_edge`,比 vertex 表多 2 列 `start_id` 和 `end_id`(都是 graphid)。`graphid` 是 AGE 引入的自定义类型,组成是 (label_oid, seq)——**全局图内唯一**。

**agtype** 是另一个 AGE 自定义类型——JSONB-like lite——vertex/edge 的 properties 就用它存。`agtype.c` 13260 行,占 AGE 总代码 21%——**这是 AGE 工程最大块的实现**,也说明 AGE 选了**自实现序列化协议**,没复用 PG 内置 JSONB。

## 把数据装进去——AI 上下文管理实战 schema

```sql
-- 装入 AI 上下文管理实测数据
SELECT * FROM cypher('ai_ctx', $$
    CREATE (a:Agent {name: 'claude-code', version: '2.1.260'}) RETURN a
$$) AS (a agtype);
-- {"id": 1125899906842625, "label": "Agent", "properties": {"name": "claude-code", "version": "2.1.260"}}::vertex

SELECT * FROM cypher('ai_ctx', $$
    CREATE (c:Concept {name: 'pgvector', topic: 'vector search'}) RETURN c
$$) AS (c agtype);

SELECT * FROM cypher('ai_ctx', $$
    CREATE (m:Memory {text: 'PostgreSQL shared_buffers 25% of RAM', importance: 4}) RETURN m
$$) AS (m agtype);
SELECT * FROM cypher('ai_ctx', $$
    CREATE (m2:Memory {text: 'pg_trgm index on text column for similarity', importance: 3}) RETURN m2
$$) AS (m2 agtype);

-- 关联
SELECT * FROM cypher('ai_ctx', $$
    MATCH (a:Agent {name: 'claude-code'}), (c:Concept {name: 'pgvector'})
    CREATE (a)-[:uses]->(c) RETURN a, c
$$) AS (a agtype, c agtype);

SELECT * FROM cypher('ai_ctx', $$
    MATCH (a:Agent {name: 'claude-code'}), (m:Memory)
    CREATE (a)-[:remembers]->(m) RETURN a, m
$$) AS (a agtype, m agtype);
-- (2 rows)  -- 2 条 memory 都连上了

SELECT * FROM cypher('ai_ctx', $$
    MATCH (c:Concept {name: 'pgvector'}), (m:Memory)
    WHERE m.text CONTAINS 'shared_buffers'
    CREATE (c)-[:related_to]->(m) RETURN c, m
$$) AS (c agtype, m agtype);
```

**这是真实 AI 上下文管理 schema**——Agent 是 LLM/agent runtime、Memory 是单条经验/教训/对话历史、Concept 是 topic/技术/术语、`remembers/use/related_to` 是关系边。**实际 AI agent 项目可以用这个 schema 直接建上下文图**。

## 1 跳召回 + 2 跳召回 + 关系路径召回

AI 上下文管理的真实问题不是"找出所有 Memory"——是"找出相关 Memory"——**找相关的两条路径**:

1. **直接关系**——Agent 自己记得什么(1 跳)
2. **间接关系**——Agent 通过中间概念相关的 Memory(2 跳)
3. **相似语义**——Memory 跟另一个 Memory 文本相似(BM25/pg_trgm/pgvector)

**图路线负责前两条**——文本路线负责第三条——**AI 上下文管理 = 图 + 标量 + 向量 三路召回融合**——姊妹篇 1 pgmnemo 的 `pgmnemo.recall_hybrid()` 就是这种融合的通用实现。

**Q1: 1 跳召回——claude-code 记得什么**

```sql
SELECT * FROM cypher('ai_ctx', $$
    MATCH (a:Agent {name: 'claude-code'})-[:remembers]->(m:Memory)
    RETURN m.text, m.importance
    ORDER BY m.importance DESC
$$) AS (text agtype, imp agtype);
```

实测返回:

```
                     text                      | imp
-----------------------------------------------+-----
 "PostgreSQL shared_buffers 25% of RAM"        | 4
 "pg_trgm index on text column for similarity" | 3
```

**Q2: 2 跳 VLE 召回——claude-code 通过 pgvector 概念间接相关的 Memory**

```sql
SELECT * FROM cypher('ai_ctx', $$
    MATCH (a:Agent {name: 'claude-code'})-[:uses]->(:Concept)-[:related_to]->(m:Memory)
    RETURN DISTINCT m.text, m.importance
$$) AS (text agtype, imp agtype);
```

实测返回:

```
                  text                  | imp
----------------------------------------+-----
 "PostgreSQL shared_buffers 25% of RAM" | 4
```

**claude-code -> uses -> pgvector -> related_to -> Memory "shared_buffers 25%"**——2 跳路径召回命中 1 条——这是图召回的核心价值:不靠文本相似度,只靠 schema 关系。

**Q3: 变长边(VLE)1-N 跳召回**

```sql
SELECT * FROM cypher('ai_ctx', $$
    MATCH (a:Agent {name: 'claude-code'})-[:remembers*1..3]->(m:Memory)
    RETURN DISTINCT m.text
$$) AS (text agtype);
-- 2 rows: 同一 1 跳的 2 条 memory
```

**注意**——AGE openCypher 不支持 `[:rel1|rel2*1..3]` 多 label VLE(只支持单 label)——这是 openCypher 子集的限制,**标准 Cypher 支持**——AGE 选了工程化裁剪,落地时如果有 VLE 多 label 需要走多次 query 自己合并——**这种限制 AI 极客要知道**,不能假设 openCypher = Cypher。

## PG 18.6 SQL 直查 vertex 表——Cypher 是 PG SQL 的"语法糖",不是替代

```sql
SELECT * FROM ai_ctx."Memory";

       id        |                                properties
-----------------+------------------------------------------------------------------------
 844424930131969 | {"text": "PostgreSQL shared_buffers 25% of RAM", "importance": 4}
 844424930131970 | {"text": "pg_trgm index on text column for similarity", "importance": 3}
```

```sql
SELECT * FROM ai_ctx."remembers";

       id        |   start_id    |     end_id    | properties
-----------------+---------------+---------------+------------
 1688849860263937 | 1125899906842625 | 844424930131969 | {}
 1688849860263938 | 1125899906842625 | 844424930131970 | {}
```

**vertex/edge 是真 PG 表**——`ai_ctx."Memory"` 直接 SQL 查——`properties` 列是 agtype(JSONB-like)。这意味着:

- **Cypher 不是图数据库唯一入口**——你可以在 PG SQL 里直接 JOIN vertex 表
- **Cypher 不是替代 SQL**——是 SQL 的**邻域 DSL**——用 PG 的 planner/optimizer/executor
- **AI 上下文管理 = 多语言融合**——同一张 vertex 表既能 Cypher 也能 SQL——SQL JOIN agtype 做混合召回

```sql
-- SQL + agtype hybrid query: 找出 importance >= 3 的 memory (SQL 过滤)
SELECT id, properties->>'text' AS memory_text, (properties->>'importance')::int AS imp
FROM ai_ctx."Memory"
WHERE (properties->>'importance')::int >= 3
ORDER BY imp DESC;
```

## Apache AGE 工程代价: 61,642 行 C 的重量

| 模块 | 行数 | 职责 |
|---|---|---|
| utils/adt | **32,357** | agtype (13,260 行) + VLE DFS (3,897 行) + global graph state (2,234 行) |
| parser | 15,177 | Bison grammar (`cypher_gram.y`) + clause (9,511 行) + expr (2,761 行) |
| executor | 5,358 | `cypher_merge` 等 |
| nodes | 1,223 | execution tree nodes |
| commands | 1,492 | CREATE GRAPH / CREATE LABEL DDL |
| catalog | 1,148 | ag_graph / ag_label / ag_namespace |
| optimizer | 746 | cyph_path 等 |
| **总** | **61,642** | |

**utils 模块占 52%**——**AGtype 序列化协议 + VLE DFS 路径算法是 AGE 工程量最大的两块**。`age_global_graph.c` 2234 行维护**整个图的全局状态**——`GRAPH_global_context` + `create_GRAPH_global_hashtables` + `age_vertex_stats` / `age_graph_stats`——Cypher query 每次要查 vertex/edge 统计信息、路径搜索都要走这个全局 context——这是 AGE 的性能 critical path。

**`age_vle.c` 3897 行** 实现 `sp_agtype_to_direction` / `sp_compute_paths`——VLE 是"变长边"的缩写,就是 Cypher 的 `[:rel*1..5]` 多跳路径语法——DFS 跑路径——栈用 `GraphIdStack`(数组栈,O(1) push/pop,序列内存访问,no linked-list pointer chasing)——AGE 的 VLE 比 Neo4j 用的 recursion BFS 优化过。

**AI 上下文管理实践者读这数,要理解**——AGE = **617 行 / star 的 C 代码密度**——比 PG 整体 100+ 万行小很多——AGE 把"图"装进 PG,代价是 6 万行——这代价分摊给所有图查询——**AI 上下文管理场景下用 AGE,等于每次查询多负担 6 万行 C 的代码审计 + 维护成本**。

## PG 19 SQL/PGQ 用标准 SQL 干 AGE 同样的事

2026 年 3 月 16 日,PG master commit `2f094e7a` "SQL Property Graph Queries (SQL/PGQ)" 合并——SQL:2023 标准正式进 PG master——**48 个相关 commits,最近一个 2026-09-02** "Coerce GRAPH_TABLE pattern WHERE clauses to boolean"。

**`parse_graphtable.c`** 是 PG 19 SQL/PGQ 入口——`GraphElementPatternKind` enum 定义 4 种 graph element pattern:

```c
case VERTEX_PATTERN:        return "vertex";
case EDGE_PATTERN_LEFT:     return "edge pointing left";
case EDGE_PATTERN_RIGHT:    return "edge pointing right";
case EDGE_PATTERN_ANY:      return "edge pointing any direction";
case PAREN_EXPR:            return "nested path pattern";
```

`transformGraphTablePropertyRef` 把 `<variable>.<property>` 解析为 `GraphPropertyRef` node——`<variable>` 是 graph pattern 绑定的元素 alias,`<property>` 是 property graph 上定义的属性——和 AGE 的 `MATCH (a {name: 'claude-code'}) RETURN a.name` 异曲同工。

**PG 19 catalog** ——**4 个表**集成进 `pg_catalog`:

```
pg_propgraph_element    -- vertex/edge metadata (oid, pgepgid, pgerelid, pgealias, pgekind, pgesrcvertexid)
pg_propgraph_link       -- edge -> vertex links
pg_propgraph_label      -- labels (vertex / edge 类型)
pg_propgraph_property    -- property definitions
```

**`pg_propgraph_element.pgekind`** — `v` / `e` — vertex / edge 区分——**`pgesrcvertexid`** 是 edge -> 源 vertex 的引用——**这是 PG 19 标准化的图数据模型**——AGE 的 `_ag_label_vertex` / `_ag_label_edge` 也存类似数据,只是放 `ag_catalog` 而非 `pg_catalog`。

**PG 19 SQL/PGQ 语法**(从 `sqlpgq.c` regress test 套件 + `parse_graphtable.c` 推断):

```sql
CREATE PROPERTY GRAPH ai_ctx
  VERTEX TABLES (Agent KEY(id), Memory KEY(id), Concept KEY(id))
  EDGE TABLES (
    remembers    KEY(id) SOURCE KEY(start_id) DESTINATION KEY(end_id),
    uses         KEY(id) SOURCE KEY(start_id) DESTINATION KEY(end_id),
    related_to   KEY(id) SOURCE KEY(start_id) DESTINATION KEY(end_id)
  );

SELECT n.text, n.importance
FROM GRAPH_TABLE (ai_ctx
    MATCH (a IS Agent | name = 'claude-code')
         -[:remembers]-> (m IS Memory)
    RETURN m.text, m.importance
) AS n
ORDER BY n.importance DESC;
```

**`GRAPH_TABLE(... MATCH ... RETURN ...)`** 是 SQL:2023 标准子句——把图模式匹配当 SQL table function 用——**不是新查询语言**,是 SQL 扩展——**这跟 AGE 的 `SELECT * FROM cypher(...)` 本质一样**——区别是 SQL/PGQ 把 MATCH 关键字直接 inline 进 FROM 子句,AGE 把整个 cypher() 当函数调用。

## AGE vs SQL/PGQ: 选型的关键对比

| 维度 | Apache AGE 1.8.0 | PG 19 SQL/PGQ |
|---|---|---|
| Query 语法 | openCypher 子集 + `cypher()` SP | SQL:2023 `GRAPH_TABLE(... MATCH ...)` |
| Parser 集成 | Bison 独立 grammar (`cypher_gram.y` + `ag_scanner.l`) | 集成进 PG 标准 parser (`parse_graphtable.c`) |
| 数据类型 | `agtype` 自定义 (13,260 行 C) | PG 标准类型 + `pg_propgraph_*` 4 表 |
| Catalog | `ag_catalog` schema (2 张表:ag_graph + ag_label) | `pg_catalog` 集成 (4 张表:pg_propgraph_element + ...) |
| Graph 实现 | vertex/edge 是 PG 真表继承 `_ag_label_*` | vertex/edge 是 PG 真表 + pg_propgraph_element 元表 |
| VLE 多跳 | `[:rel*1..3]` 单 label 限定 | `[:rel*1..3]` 标准 Cypher 全部 label pattern |
| 性能 critical path | `age_global_graph.c` 全局状态 | 集成进 PG planner |
| 成熟度 | 4799 stars + 4799 forks + Apache TLP | PG 22K+ stars 内置 |
| PG 版本 | PG 13-17 + **PG 18 (1.8.0)** | **PG 19 master** (未发布) |
| Driver | Python / Java / Go ANTLR generated | 标准 PG client (libpq + SQL syntax) |

**AI 上下文管理实践者怎么选**:

**短期(2026 现在)**——**AGE 1.8.0 + PG 13-18**——**能跑**——apt.postgresql.org 直接 apt install `postgresql-18-age`——开箱即用——openCypher 语法熟悉——文档全——社区(Apache TLP)持续维护——**这是当下唯一生产可行选择**。

**中期(2027+)**——**PG 19 发布 + SQL/PGQ 稳定**——**SQL 标准 + 集成进 PG planner**——age 这种独立扩展会被 PG 内置吸收——graph 这种 PG 内置 query language 长期看更可持续——**但 PG 19 release date 是 TBD**。

**长期(2028+)**——**AI 上下文管理会偏向混合召回**——图查询负责多跳关系召回,向量查询负责语义召回,标量查询负责精确过滤——pgmnemo 那条姊妹篇 1+2+3 的 `pgmnemo.recall_hybrid()` 是这个趋势的早期实现——**图召回在 AI 上下文管理里的地位是"关系路径 + 实体解释",不是"全量召回"**——这意味着 AGE 跑通几条核心 Cypher 就够用,**不必把所有数据搬到 AGE**——**用 cypher(`ai_ctx`, ...) 查关系 + 用 SQL JOIN 查 agtype + 用 pgvector 查语义**——**三路融合是 AI 上下文管理的合理架构**。

## 三个 AGE 工程深水区——AI 上下文管理会撞上

**第一个: agtype 序列化的代价**——`agtype.c` 13260 行——vertex/edge properties 都序列化成 agtype——**比 JSONB 多一层**——每次 INSERT/UPDATE 走 `agtype_build_map` 默认值——每次 SELECT 走 `agtype_out` 反序列化——**AI 上下文管理场景下,vertex 经常更新**——(比如 Memory 节点 importance 字段每次 reinforce 改一次)——agtype 序列化反序列化成了 hot path——pgvector + pg_trgm + tsvector 这几个 PostgreSQL 内置类型都是 PG 原生 datum,没这种 serialization 层。

**第二个: VLE DFS 不支持多 label**——openCypher 子集裁剪——`MATCH (a)-[:uses|remembers*1..3]->(m)` 这种多 label VLE 在 AGE 直接报 syntax error——AI 上下文管理里的"找出 Agent 1-3 跳内所有关联 Memory"(经过 uses / remembers / related_to 任意边)就要分多个 query 写——Cypher 原生 + Neo4j 是支持的,这是 AGE 的开放问题——`age_vle.c` 实现是单 label DFS,要扩展成多 label 需要改 BFS/DFS 算法。

**第三个: cache invalidation 靠 trigger**——`_age_cache_invalidate` AFTER INSERT/DELETE/UPDATE TRIGGER 调 `age_invalidate_graph_cache()`——**每次写表触发 cache 失效**——AI 上下文管理写频率高(Memory 节点 importance reinforce + Concept 节点关联更新)——**每次写都 cache miss,下次读重新计算**——`age_global_graph.c` 里 `create_GRAPH_global_hashtables` 会重新建 hashtable——**这是 AGE 性能瓶颈之一**——`age.global_cache` 在 AGE 0.5+ 引入但 1.8.0 还没完全替代 trigger-based invalidation。

**所以 AGE 适合**——**图查询频率 < 写频率**——**AI 上下文管理大多数场景是"读完上下文→决策→写一次 Memory"——读多写少**——**这个 workload 适合 AGE**——但**高频记忆更新**(比如每个 token 后 reinforce)就不适合。

## PG 19 SQL/PGQ 的未来价值

`pg_propgraph_element` / `pg_propgraph_link` / `pg_propgraph_label` / `pg_propgraph_property` 这 4 张表在 `pg_catalog`——**和 PG 内置元数据平级**——**意味着 PG planner 能看图元数据做 join optimization**——AGE 的 `ag_catalog` 是独立 schema,planner 看 graph 元数据要走 custom path——**这是 PG 19 SQL/PGQ 的工程优势**。

`parse_graphtable.c` 的 `transformGraphTablePropertyRef` 把 `<variable>.<property>` 解析为 `GraphPropertyRef` node——**PG 的 expression tree 加了一种 node**——planner 看到这种 node 时能跟普通 column 一样做统计 / 估算 / 索引选择——**`pgesrcvertexid` 在 catalog 里**——**planner 可以做"先 join vertex 表 + edge 表 + filter"的优化**——这是把图当"一类特殊 table"的优化空间。

**AI 上下文管理实践者等 PG 19 release**——**等 SQL/PGQ 在生产环境能用**——**到时 AI 上下文管理的图路线迁移成本最低**——SQL/PGQ 是标准,迁移过去不像 age -> pgvector 这种扩展切换——`GRAPH_TABLE(...)` SQL 扩展到时是 PG 语法一部分——所有 PG client / ORM / 驱动都原生支持——**这是标准化的工程价值**。

## 现在写 AI 上下文管理 schema 怎么选

**方案 1: 纯 PG 18 + AGE 1.8.0 + pgvector + pg_trgm**

```sql
-- 标量召回: BM25 + pg_trgm
SELECT * FROM ai_ctx."Memory"
WHERE properties->>'text' % 'PostgreSQL tuning';

-- 向量召回: pgvector 存 embedding (在 properties 里加 'embedding' 字段)
SELECT * FROM ai_ctx."Memory"
ORDER BY (properties->>'embedding')::vector <=> $1
LIMIT 10;

-- 图召回: AGE 多跳关系
SELECT * FROM cypher('ai_ctx', $$
    MATCH (a:Agent {name: 'claude-code'})-[:uses]->(:Concept)-[:related_to]->(m:Memory)
    RETURN m.text
$$) AS (text agtype);
```

**优势**——当下能跑——AGE + pgvector + pg_trgm 三个扩展都成熟——**真正的"全 SQL + 多模型"**。
**劣势**——agtype 序列化代价——VLE 多 label 不支持——cache invalidation trigger 频繁。

**方案 2: 等 PG 19 release,SQL/PGQ + pgvector + pg_trgm**

```sql
-- 标量召回: 同上
-- 向量召回: 同上
-- 图召回: GRAPH_TABLE 子句
SELECT n.text, n.importance
FROM GRAPH_TABLE (ai_ctx
    MATCH (a IS Agent | a.name = 'claude-code')
         -[:remembers]-> (m IS Memory)
    RETURN m.text AS text, m.importance AS importance
) AS n
ORDER BY n.importance DESC;
```

**优势**——SQL 标准——planner 优化空间大——driver 通用。
**劣势**——**PG 19 未发布**——SQL/PGQ 还在 master branch——生产用需要 PG 19 release + 1-2 年稳定期。

**方案 3 (推荐): pgmnemo 走 SQL 路线 + AGE 走 Cypher 路线,融合 pgvector**

姊妹篇 1 + 2 + 3 的 pgmnemo 是 SQL 路线 (`pgmnemo.recall_hybrid` 是 SQL stored procedure 实现 hybrid retrieval)——AGE 是 Cypher 路线——**这两条路不冲突**——AI 上下文管理 = **SQL 召回 + Cypher 召回 + 向量召回**三路融合——pgmnemo 管 metadata + 标量 + 向量召回——AGE 管关系路径召回——**AI 极客视角的"最小可行 AI 上下文管理"**——**这是当下(2026)能跑的最完整方案**。

## 6 个真事实点 — 在 PG 18.6 实测都过了

**事实 1: AGE 1.8.0 在 PG 18.6 装上就 work**

## 给 AI 上下文管理实践者的真实建议

读 AGE + PG 19 SQL/PGQ 源码 + 实测 PG 18.6 + Apache AGE 1.8.0 这套组合,3 个具体建议:

**第一,age 不是长期方案**——`agtype` 自定义序列化 + VLE 单 label 限制 + cache invalidation trigger ——这 3 个工程深水区决定 AGE 适合"读多写少 + 简单多跳"的 workload。AI 上下文管理如果走 age,不要把高频记忆更新 (每个 token 后 reinforce 那种)放在 age 里——高频写 + age 的 trigger-based cache invalidation 会让读性能雪崩。**age 适合"长生命周期的事实 / 关系"""低频改 / 高频读"**——(比如 Agent 的偏好表 / 项目上下文)。

**第二,pg 19 sql/pgq 是未来方向但不是现在选项**——PG 19 未发布,SQL/PGQ 在 master——48 commits 历史但没在生产环境跑过——**AI 上下文管理实践者要"等 PG 19 release + 至少 1 年稳定期"再考虑切换**——在那之前,age 1.8.0 + pg 18 是当下唯一生产可行的"PG 上的图"方案。

**第三,真正的 ai 上下文管理 = 三路融合,不是图独尊**——pgmnemo 那条姊妹篇 1+2+3 的 `pgmnemo.recall_hybrid()` 已经实现 SQL 路线 + 向量 + 标量融合——age 是关系路径召回的补充——pgvector + pg_trgm 是文本召回——**AI 上下文管理 = pgmnemo (标量 + 向量) + age (关系路径) + pgvector (语义) 三路融合**——**别让任何一条路线独尊**。

AGE 1.8.0 是当下最实在的 PG 上的图路线,但它在工程上有 3 个深水区;PG 19 SQL/PGQ 是未来,但 PG 19 未发布。AI 上下文管理实践者当下要做的是——**用 age 1.8.0 + pgvector + pg_trgm 三路召回融合**——**等 PG 19 发布**——**到时把 age 的 cypher() 改写成 GRAPH_TABLE(...) SQL 标准,工作量集中在 schema 迁移 + driver 升级**——**PG 17 -> PG 19 升级时一并做这个迁移最划算**——**别在 PG 18 上花太多精力改 age-specific 代码,PG 19 后所有这些代码都要改写**。

AGE 是当下唯一生产可行,SQL/PGQ 是未来方向——这两个事实不冲突,**同时**用——age 管关系路径,pgvector + pg_trgm 管语义/标量,pgmnemo 管标量召回融合——**AI 上下文管理 = 三路召回融合**,不是任何单一路线的胜利——是 PG 生态多模型协同的工作——**Apache AGE 工程代价 6 万行 C,PG 19 SQL/PGQ 工程代价 3000+ 行 C,PG vector 几千行 C,pg_trgm 几百行 C,PG mnemo 200+ SQL 文件**——**PG 生态把 AI 上下文管理的每条召回路线都做成了 PG 扩展**——**AI 极客在 PG 18 上能做完整的 AI 上下文管理,不需要新数据库**。
