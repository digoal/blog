## 背景  


2026 年 9 月有一类新需求, AI agent 的持久化记忆需要: 身份主目录、organization 子树范围、Memory 的 EPISODIC / FACT / PREFERENCE / DECISION / PROCEDURAL / EXPERIENCE 六种类型 × RUNTIME_CONTEXT / CHANNEL_MEMORY / AGENT_MEMORY / WORKSPACE_MEMORY / ENTERPRISE_KNOWLEDGE 五种 scope × CANDIDATE / ACTIVE / STALE / CONFLICTED / SUPERSEDED / EXPIRED / MIGRATED / ARCHIVED / QUARANTINED / UNAVAILABLE 十种生命周期状态 + A2A 跨 agent 协作 + Graph Runtime + DB4A2A dispatch 协议 + Security Domain authorization + RLS 行级隔离 + **ollama qwen3-embedding 1024 维原生对接 entity_embeddings 表 + HNSW vector_cosine_ops 索引** + 可读管壁板。这种"介于 plugin 与 database 之间"的标准化约定, 就是 **川序 (Chuanxu)** —— PG 18.3+ 适配版本叫 AI-Agent-Infra-with-PG-Community-Edition, Apache 2.0, **78 个 sql migration 文件 + 88,000 行 Python + 26 个文档 + 88 个 lib API**。**它不是数据库、不是 plugin —— 它是介于这两者之间的 Schema 标准化约定** —— mem0 这种 AI memory plugin 在川序上跑, 跟姊妹篇 1 pgmnemo-mcp 完全同源 —— **ollama qwen3-embedding 1024 维原生 + 零 workaround + 零 zero-pad**。

## 把川序当 Schema 而不是 product 看

`docs/introduction_zh.md` 自己定义: "**川序 (Chuanxu) 是基于数据库的 AI Agent 管理平台, 为企业内部及外部智能体保存身份、组织、知识、记忆、工作上下文、任务状态及治理记录。数据库负责持久状态和数据授权, 模型负责推理与生成, Agent 运行进程负责执行。三者凭据和权限分别管理**"。

**"三者凭据和权限分别管理"** 这句是关键 —— 这意味着川序不是 plugin (它不直接调 LLM)、不是 database (它不实现存储)、它**只**定义中间这层的契约 —— 任何 Agent runtime (Hermes Agent / OpenClaw / LangChain / mem0 / powercontext) 只要遵守这契约就能用。任何 PostgreSQL 18.3+ 都能跑这契约。

`README.md` 进一步讲架构: **"It collapses the conventional 'Redis + vector DB + graph DB + object store' stack into a single PostgreSQL kernel"** —— 川序**不**发明新数据库,**不**发明新图,**不**发明新 vector store —— 它用 **pgvector** + **pg_trgm** + **Apache AGE** + **RLS** + **pgcrypto** + **pg_cron** + **ollama** 这些 PG 内置 / 扩展 / 周边工具, 把它们编排成 AI agent infra 的完整 schema。

`SKILL.md` 第 2 行定义对接原则: "**This package is Skill-first and framework-neutral. Any Agent runtime that can install or read SKILL.md and execute the packaged HTTP, MCP, or CLI workflows can use the platform**" —— 任何能读 SKILL.md 的 runtime 都能用 —— 这是"川序是 Schema 而不是 product"的物理证据。

**关键表的真实 schema** (从 `\d` 实测):

```sql
-- agent_registry: 川序的 agent 元数据中心
CREATE TABLE public.agent_registry (
    agent_id varchar(64) NOT NULL,        -- PK
    agent_name varchar(256),
    agent_type varchar(64),
    capabilities jsonb,
    config jsonb,
    status varchar(32) NOT NULL DEFAULT 'ACTIVE'
        CHECK (status IN ('ACTIVE','INACTIVE','SUSPENDED','DECOMMISSIONED','DORMANT','POOL')),
    agent_role varchar(32) NOT NULL DEFAULT 'WORKER'
        CHECK (agent_role IN ('WORKER','COORDINATOR','SYSTEM')),
    ...
);
-- 7 个索引 + 2 CHECK constraints + 19 张其他表 FK 引用

-- entities: AI 上下文管理核心实体表
CREATE TABLE public.entities (
    entity_id bigint GENERATED ALWAYS AS IDENTITY,
    entity_type varchar(32) NOT NULL
        CHECK (entity_type IN ('MEMORY','KNOWLEDGE','TASK_OUTPUT','EXPERIENCE',
                               'HARNESS_TEMPLATE','SPEC','SKILL','LOOP_DEFINITION','OTHER')),
    title varchar(512), content text, summary varchar(2000),
    importance numeric(3,1) DEFAULT 5 CHECK (importance BETWEEN 1 AND 10),
    owned_by_agent varchar(64),      -- RLS 主键
    visibility varchar(16) NOT NULL DEFAULT 'SHARED'
        CHECK (visibility IN ('PRIVATE','SHARED','PUBLIC')),
    search_vector tsvector,           -- 自动生成
    workspace_id bigint, branch_id bigint,
    ...
) PARTITION BY LIST (entity_type);    -- 9 个分区

-- entity_embeddings: ollama 1024 维原生对接表 (33_v4_3_7 + 37_v4_4_2 + 61_v4_4_10)
CREATE TABLE public.entity_embeddings (
    entity_id bigint NOT NULL,
    entity_type varchar(32) NOT NULL,
    embedding vector(1024) NOT NULL,    -- ← ollama qwen3-embedding 原生 1024 维直通
    embedding_model varchar(128),
    embedding_dim integer NOT NULL,
    embedding_space_id varchar(128) NOT NULL DEFAULT 'LEGACY_DEFAULT',
    embedding_profile_id varchar(128),
    embedding_contract_id varchar(128),
    content_digest varchar(64),
    source_mode varchar(32) NOT NULL DEFAULT 'LEGACY',
    validation_status varchar(32) NOT NULL DEFAULT 'UNVERIFIED',
    created_at timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (entity_id, entity_type, embedding_space_id)
);
CREATE INDEX idx_ee_embedding ON entity_embeddings USING hnsw (embedding vector_cosine_ops);
CREATE INDEX idx_ee_space_contract ON entity_embeddings (embedding_space_id, embedding_contract_id);

-- agent_session: session 历史
CREATE TABLE public.agent_session (
    session_id bigint GENERATED ALWAYS AS IDENTITY,
    agent_id varchar(64), owner_user_id varchar(64), workspace_id bigint,
    branch_id bigint, is_active boolean,    -- PARTITION BY LIST (is_active)
    context jsonb,                          -- mem0 message 存在这里
    ...
) PARTITION BY LIST (is_active);
-- RLS POLICY as_agent_isolation: agent_id = current_agent_identity() OR COORDINATOR role
```

**这是川序"介于 plugin 与 DB 之间"的物理证据** —— 每个表都有 `agent_id` + `visibility` + RLS policy —— plugin 写 INSERT 时只能写自己 owned_by_agent 的行; SQL 查询时 RLS 自动 scope; PL/pgSQL trigger 自动维护 `search_vector` —— **plugin 不需要做权限检查** —— 川序 schema 替你做完了。

**`entity_embeddings` 表的设计哲学** —— **不在 `entities` 表里塞 `embedding` 列** —— **单独建表 + PK (entity_id, entity_type, embedding_space_id)** —— 支持多 embedding space 并存 (ollama / OpenAI / BGE-M3 各一个 space) + 多 embedding profile (HNSW vs IVFFLAT) —— **川序"中间层 Schema" 把多模态 + 多模型 + 多空间都用 SQL 表达**。

## mem0 + ollama qwen3-embedding 1024 维对接川序的实测

`/tmp/mem0_ollama_chuanxu_demo.py` (本机 PG 18.6 + ollama 0.33.3 + qwen3-embedding:0.6b 实测 8 步全 work):

```python
def embed_ollama(text: str) -> list[float]:
    """ollama qwen3-embedding:0.6b -> 1024-dim float list. 走 stdlib urllib."""
    req = urllib.request.Request(
        'http://127.0.0.1:11434/api/embed',
        data=json.dumps({'model': 'qwen3-embedding:0.6b', 'input': text}).encode('utf-8'),
        headers={'Content-Type': 'application/json'},
    )
    with urllib.request.urlopen(req, timeout=30) as resp:
        data = json.loads(resp.read().decode('utf-8'))
    return [float(x) for x in data['embeddings'][0]]

class Memory:
    """mem0ai.Memory 的 core API surface, backend = 川序 schema + ollama 1024 维."""

    EMBEDDING_MODEL = 'qwen3-embedding:0.6b'
    EMBEDDING_DIM = 1024
    EMBEDDING_SPACE_ID = 'ollama_qwen3_1024'

    def add(self, messages, **kwargs):
        for msg in messages:
            content = msg['content']

            # 1. 写 agent_session (会话历史)
            INSERT INTO agent_session (agent_id, owner_user_id, context, ...);

            # 2. 写 entities (返回 entity_id)
            INSERT INTO entities (entity_type='MEMORY', title, content,
                                   owned_by_agent=..., visibility='PRIVATE', ...)
            RETURNING entity_id, entity_type;

            # 3. 调 ollama qwen3-embedding 拿 1024 维向量
            vec = embed_ollama(content);  # 1024 floats

            # 4. 写 entity_embeddings (vector(1024) + embedding_model + space_id)
            INSERT INTO entity_embeddings
                (entity_id, entity_type, embedding, embedding_model, embedding_dim,
                 embedding_space_id, source_mode, validation_status)
            VALUES (..., ..., vec::vector, 'qwen3-embedding:0.6b', 1024,
                    'ollama_qwen3_1024', 'EXTERNAL', 'UNVERIFIED')
            ON CONFLICT (entity_id, entity_type, embedding_space_id) DO UPDATE
            SET embedding = EXCLUDED.embedding;

    def search(self, query, top_k=5, use_vector=True):
        if use_vector:
            # ollama 1024 维 -> HNSW cosine 距离
            qvec = embed_ollama(query);
            SELECT e.*, 1 - (ee.embedding <=> qvec::vector) AS cosine_sim
            FROM entities e JOIN entity_embeddings ee
              ON ee.entity_id = e.entity_id AND ee.entity_type = e.entity_type
                 AND ee.embedding_space_id = 'ollama_qwen3_1024'
            WHERE e.entity_type = 'MEMORY' AND e.owned_by_agent = current_agent_identity()
            ORDER BY ee.embedding <=> qvec::vector LIMIT 5;
        else:
            # 标量 ILIKE (走 search_vector tsvector)
            SELECT * FROM entities
            WHERE title ILIKE '%query%' OR content ILIKE '%query%';
```

## 给 AI 上下文管理实践者的选型建议

**川序适合的场景**:

- **企业 / 团队级 AI agent infra** —— 多个 agent + 多个 Human 用户 + 多个 organization + 多个 workspace + 多个 security domain + 知识图谱 + 记忆治理 + 审计 + 凭据管理 + 配额 + 模型网关 + **多 embedding model 共存** —— **这些需求在一起时, 川序一站式**
- **AI agent 数据需要 governance** —— "模型输出不是事实或授权证明" (docs/memory-lifecycle.md 原话) —— **川序的 Memory Family → Version → Representation → digest 链**就是为治理设计
- **需要 PostgreSQL 内置能力** —— pgvector / pg_trgm / AGE / pgcrypto / pg_cron / RLS —— 不想维护 Redis + Pinecone + Neo4j + S3 多栈
- **需要多 embedding model + 多 vector space** —— 比如同一个实体在 `ollama_qwen3_1024` 空间有一份 + 在 `openai_3large_3072` 空间有一份 —— **川序 embedding_space_id + UNIQUE PK + 多 profile_id** —— 比单 vector store plugin 灵活

**川序不适合的场景**:

- **单 agent / 单用户 / 不需要 governance** —— 70+ 张表是过设计 —— mem0 + SQLite 就够
- **不需要 graph** —— pgvector + pg_trgm + RLS 3 项足够时
- **团队没有 DBA** —— 川序 v4.4.12 要 PG 18.3+ + 78 个 migration SQL 按序执行 + Python 3.14+ + RLS policy 理解

**同 mem0 / cognee / langchain 怎么选**:

- **只想要 AI memory** —— mem0 + SQLite, 不上川序
- **想 AI memory + 图关系** —— cognee + PG, 不上川序
- **想 AI agent infra 全栈 + governance + 多 embedding space** —— 川序, mem0 当 plugin 之一接入

**给 SOUL 关注方向的对接建议** —— PG 公众号 + AI 上下文管理 —— **川序 = "AI Agent Infra with DB"项目主推方向** —— **本机 PG 18.6 + AGE 1.8.0 + pgmnemo 0.20.0 + 川序 70+ 表 + ollama 0.33.3 + qwen3-embedding:0.6b** —— **AI 上下文管理实践者的"全栈研究环境"装齐了** —— **姊妹篇 1~13 + 这篇** —— **pgvector + pg_trgm + AGE → 主篇 + 5 实测姊妹篇 + 川序主 schema + ollama-native 1024 维** —— **这是 "PostgreSQL + AI" 专题的完整封面**。

## 川序 spec 真不真的设计哲学

`docs/introduction_zh.md` 第 6 行设计哲学: **"三者凭据和权限分别管理"**。这三者指:

1. **数据库** —— PG DBA 持有 DBA 账户 + Schema Owner 凭据
2. **模型** —— 川序只转发 HTTP, 不持久 LLM 凭据在 DB
3. **Agent runtime** —— 持有 short-lived token + Ed25519 key pair

**"凭据分别管理"是物理隔离原则** —— 任何 Agent 失去凭据只影响该 agent, 不影响 DB / 不影响其他 agent —— **这是 enterprise grade 的 zero-trust 设计**, 不是 PG 内部 RLS 单一维度能做到的, 是 **runtime + DB + model gateway 三方各自负责一部分**。

`docs/security.md` 第 5 段提到: **"Agent database credentials are distinct from end-user and admin credentials. Business Agents receive neither database credentials nor a Schema Owner fallback"** —— **business agent 不持有 DB 密码** —— 这是川序跟 mem0/pgvector 最大的差异 —— **mem0 假设 agent 有 DB 密码** (SQLAlchemy + connection string) —— **川序假设 agent 不应该有 DB 密码**: **agent 调川序 HTTP API, 川序自己调 DB, DB 密码只有川序自己持有**。

`SKILL.md` 第 8 节 Business Agent Registration 完整流程就是 **"零 DB 密码 agent"** 的实现 —— **User-sponsored one-use Enrollment Token + Ed25519 key pair + instance-scoped short-lived tokens** —— agent 永远不碰 DB 密码。

`33_v4_3_7_bootstrap_embedding.sql` + `61_v4_4_10_external_embedding_authorization.sql` 的设计哲学延伸:

- **`embedding_space_id`** —— 多 embedding space 共存, 防止 "vector store 一统天下" 单点故障
- **`embedding_model`** + **`embedding_dim`** + **`content_digest`** —— 审计三件套 (哪个 model 算出来的 + 几维 + 内容指纹), 出问题能定位
- **`embedding_contract_id`** —— `61_v4_4_10_external_embedding_authorization.sql` 加的 contract 字段, 谁能调外部 embedding API 都得注册 contract
- **`source_mode IN ('LEGACY', 'EXTERNAL', 'INTERNAL')`** + **`validation_status IN ('UNVERIFIED', 'VERIFIED', 'STALE')`** —— embedding 数据生命周期管理, 防止 "vector 算出来但没人审"
