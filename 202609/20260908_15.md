## powercontext 是什么: OceanBase 出品的 work-handoff AI context 层

powercontext (OceanBase 出品, Apache 2.0, [github.com/oceanbase/powercontext](https://github.com/oceanbase/powercontext)) 的自我定位:

> "Context for work that humans and agents hand off and continue."
> "PowerContext keeps context with the work across conversations. When you return, you can see what happened and continue from the current state. A new agent can do the same."

**这跟姊妹篇 5/6 提的痛点完全重合**: agent 长期使用质量漂移不是因为 model 变笨了, 是因为 context 没跟着 work 走。powercontext 把 context 跟 work 绑定, 每次 handoff 都携带完整 reasoning + current state + sources。

**真实规模** (本机已浅克隆到 `/root/new/src/powercontext`):
- **1171 文件 / 228,802 行代码**
- **Python 3.11+ / uv / Hatchling / pytest / tox**
- **8 个 builtin/ 子域**: scope / artifacts / persistence / runtime / triggers / inference / review / handoff_report
- **30 个 HTTP endpoints** 在 `openapi/powercontext.yaml`: /v1/scopes/* + /v1/memory/* + /v1/work/handoffs/* + /v1/handoff/* + /v1/context/prepare + /v1/source-* + /v1/connector-* + /v1/skill/*
- **26 张 SQL 表** 在 `src/powercontext/builtin/persistence/tables.py` (scope/artifact/memory/skill/handoff)
- **4 种 artifact type**: Memory (durable info) / Handoff (current state + objective) / Experience (reusable approach) / Skill
- **完整 embedder 配置** 在 `runtime/config.py`: embedding_base_url + embedding_model + embedding_dimension + embedding_normalization ("unit") + embedding_timeout_seconds + embedding_batch_size + embedding_profile_id + rerank_model —— **完全支持 ollama-style OpenAI-compatible endpoint**
- **3 个 storage backend**: SQLite (默认 + sqlite-vec) + OceanBase (MySQL-mode + pyobvector) + SeekDB (embedded)
- **integrations/**: langgraph / claude-code / pydantic-ai 三个 official 集成

**powercontext 的核心架构哲学** —— **Work = Scope + Artifact + Handoff**:

```
Work
  ├── Scope (一个 work 的范围)
  │   ├── ScopeBinding (多个 scope 嵌套, 跨 system 关联)
  │   └── ScopeVersion (version conflict 检测)
  ├── Artifacts (4 种)
  │   ├── Memory (持久信息, 跨 session 保留)
  │   ├── Handoff (current state, 跨 agent 传递)
  │   ├── Experience (reusable approach)
  │   └── Skill (可调用的能力)
  ├── Sources (外部信息源)
  │   └── Connector (从 source ingest 数据到 memory)
  └── Outcomes (work 完成的 outcome record)
```

**完整 30 endpoints** 对应这个架构 —— client 调 `/v1/context/prepare` 拿 working memory, `/v1/memory/remember` 写, `/v1/memory/search` 召, `/v1/handoff/commit` 跨 agent transfer。

## powercontext 缺什么: PG adapter

读完所有 builtin/persistence 代码后, 真实情况:

| Backend | Vector 扩展 | 全文索引 | SQLAlchemy dialect |
|---|---|---|---|
| SQLite | sqlite-vec | FTS5 | `sqlite+aiosqlite` |
| OceanBase | pyobvector (VECTOR type) | FULLTEXT (MySQL syntax) | `mysql+aoceanbase` |
| SeekDB | pyobvector (embedded) | 同 OceanBase | `mysql+aoceanbase` |
| **PG** | ❌ **没实现** | ❌ **没实现** | ❌ **没实现** |

`pyproject.toml` 显示 builtin 依赖有 `aiosqlite` + `pyobvector` + `sqlite-vec` —— **没有 `psycopg[3]` / `asyncpg` / `pgvector`** —— **PG adapter 真没有**。

**但代码结构让写 PG adapter 变得简单**: 

- `builtin/persistence/database.py` 提供通用的 `AsyncDatabase` 包装 SQLAlchemy `AsyncEngine`
- `builtin/persistence/sqlite/profile.py` (175 行) + `builtin/persistence/oceanbase/profile.py` (~175 行) + `builtin/persistence/sqlite/memory_index.py` (~430 行) + `builtin/persistence/oceanbase/memory_index.py` (~421 行) 各自独立
- `MemoryIndex` Protocol 在 `builtin/persistence/memory_index.py` 定义通用接口

**写 PG adapter 只需要 mirror SQLite + OceanBase 架构**:

1. **`pg/profile.py`** —— `PGConfig` (BaseModel + Literal[""pg] + url = postgresql+psycopg://) + `PGProfile` (mirror SQLiteProfile.open/attach)
2. **`pg/memory_index.py`** —— `PGMemoryFTSIndex` (PG tsvector + GIN 替换 sqlite FTS5 / OceanBase FULLTEXT) + `PGMemoryVectorIndex` (pgvector Vector(1024) + HNSW 替换 sqlite-vec / pyobvector VECTOR)
3. **SQL 重写** —— sqlite `_VECTOR_SEARCH_SQL` `WHERE embedding MATCH :query AND k = :neighbor_limit` → PG `WITH nearest AS (... ORDER BY embedding <=> :query LIMIT :neighbor_limit)` —— OceanBase `_OCEANBASE_VECTOR_SEARCH_SQL` `l2_distance(m.embedding, :query)` → PG `<=>` cosine

## 写出来的 PG adapter 真跑通 (本机 2026-09-07 实测)

基于上面分析, 在本机 `/root/new/shared_proj/articles/powercontext-pg/powercontext_pg.py` 写出 PG adapter (~670 行), **真跑通 6 步 demo**。

### 架构 mirror

```python
# PG adapter 完整结构 (镜像 SQLite + OceanBase adapter 架构)
class PGConfig(BaseModel):
    kind: Literal['pg'] = 'pg'
    url: SecretStr           # postgresql+psycopg://...
    echo: bool = False
    pool_pre_ping: bool = True
    embedding_dimension: int = 1024    # 默认匹配 ollama qwen3-embedding
    embedding_normalization: Literal['none', 'unit'] = 'unit'

class PGProfile:
    @classmethod
    @asynccontextmanager
    async def open(cls, config: PGConfig, *, tables) -> AsyncIterator[PGProfile]:
        # mirror SQLiteProfile.open
        engine = create_async_engine(config.url.get_secret_value(), ...)
        database = AsyncDatabase.own(engine)
        await _warm_pg(engine, config)    # 注册 pgvector + 检查 extensions
        async with database.transaction() as connection:
            await create_tables(connection, tables)
            await _initialize_pg_extensions(connection)    # vector + pg_trgm
            await _initialize_pg_indexes(connection)       # HNSW + GIN
        yield profile

class PGMemoryFTSIndex:
    # mirror OceanBaseMemoryFTSIndex (OceanBase 用 FULLTEXT, PG 用 tsvector + GIN)
    async def search(self, connection, scope_id, query, memory_artifact_ids, candidate_limit):
        # 用 PG tsvector @@ plainto_tsquery + ts_rank
        rows = await connection.execute(text("""
            SELECT m.memory_artifact_id, m.head_revision, m.entry_id, m.entry_version_id,
                   v.text,
                   ts_rank(to_tsvector('simple', m.searchable_text),
                           plainto_tsquery('simple', :query)) AS bm25_rank
            FROM pg_pc_memory_entry_heads m
            JOIN pg_pc_memory_entry_versions v
              ON v.scope_id = m.scope_id
             AND v.memory_artifact_id = m.memory_artifact_id
             AND v.entry_version_id = m.entry_version_id
            WHERE m.scope_id = :scope_id
              AND m.memory_artifact_id = ANY(:memory_artifact_ids)
              AND to_tsvector('simple', m.searchable_text)
                  @@ plainto_tsquery('simple', :query)
            ORDER BY bm25_rank DESC LIMIT :candidate_limit
        """), {...})

class PGMemoryVectorIndex:
    def __init__(self, profile: EmbeddingProfile = EmbeddingProfile()):
        if profile.distance != 'cosine':
            raise RuntimeError('PGMemoryVectorIndex only supports cosine')
        # ...

    async def search(self, connection, scope_id, query_vector, memory_artifact_ids, candidate_limit):
        # PG vector <=> cosine + HNSW (索引自动接管)
        rows = await connection.execute(text("""
            WITH nearest AS (
                SELECT vector_id, embedding <=> CAST(:query_vector AS vector) AS distance
                FROM pg_pc_memory_vector_entries
                ORDER BY embedding <=> CAST(:query_vector AS vector)
                LIMIT :neighbor_limit
            )
            SELECT m.memory_artifact_id, m.head_revision, m.entry_id, m.entry_version_id,
                   v.text, nearest.distance
            FROM nearest
            JOIN pg_pc_memory_vector_entries AS m ON m.vector_id = nearest.vector_id
            JOIN pg_pc_memory_entry_versions AS v
              ON v.scope_id = m.scope_id AND v.memory_artifact_id = m.memory_artifact_id
                 AND v.entry_version_id = m.entry_version_id
            WHERE m.scope_id = :scope_id
              AND m.memory_artifact_id = ANY(:memory_artifact_ids)
            ORDER BY nearest.distance LIMIT :candidate_limit
        """), {...})
```

**关键差异 vs SQLite + OceanBase**:

| 维度 | SQLite adapter | OceanBase adapter | **PG adapter (本篇新写)** |
|---|---|---|---|
| Vector type | sqlite-vec 虚拟表 | pyobvector VECTOR | **pgvector Vector(1024)** |
| Distance | sqlite-vec MATCH k= | l2_distance | **`<=>` cosine** |
| ANN index | sqlite-vec auto | VectorIndex(distance=l2,type=hnsw) | **CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)** |
| FTS | FTS5 虚拟表 | FULLTEXT (MySQL syntax) | **tsvector + GIN** |
| FTS query | `MATCH 'word'` | `match(... against ...)` | **tsvector @@ plainto_tsquery + ts_rank** |
| Upsert | SQLite 不支持, 用 DELETE+INSERT | `ON DUPLICATE KEY UPDATE` | **`pg_insert(...).on_conflict_do_update`** |
| dialect | sqlite+aiosqlite | mysql+aoceanbase | **postgresql+psycopg** |

## 跟川序 schema 共存策略

实测的姊妹篇 4 ("川序当 Schema 跑") 装的川序 schema (1_schema.sql + 33_v4_3_7 + 37_v4_4_2 + 61_v4_4_10 共 4 个 migration) 在 `chuanxu_demo` 数据库里有 19 张表, 主要核心表:

- `entities` (PARTITIONED BY LIST entity_type, 9 个分区, 23 列)
- `entity_embeddings` (PK entity_id + entity_type + embedding_space_id, embedding vector(1024), HNSW idx)
- `entity_edges` / `entity_tags` / `entity_access_log`
- `agent_registry` / `agent_session` / `workspaces` / `users`
- `cx_graph_capability_profiles` / `cx_graph_capability_matrix`
- `cx_memory_feedback` (function, 姊妹篇 5/6 加的)

**powercontext 的 3 张 memory 表 (`pg_pc_memory_*`) 跟川序表共存方案**:

1. **不冲突原则** —— powercontext 表名加 `pg_pc_` 前缀 (`pg_pc_memory_entry_heads` / `pg_pc_memory_entry_versions` / `pg_pc_memory_vector_entries`), 不与川序 `entities` / `entity_embeddings` 重名
2. **可选 FK 关联** —— powercontext `pg_pc_memory_entry_heads.scope_id` 可选 FK 到川序 `agent_registry.agent_id` 或 `workspaces.workspace_id` —— **当前未加 FK, 避免两套 schema 紧耦合**
3. **跨 schema 数据流** —— agent 把川序 entities 的 entity_id 作为 powercontext memory 的 artifact_id 引用 (应用层 mapping, 不在 DB 层)
4. **共用 vector extension** —— powercontext `embedding vector(1024)` 跟川序 `entity_embeddings embedding vector(1024)` 完全同维, 可以共用同一个 `qwen3-embedding:0.6b` embedder
5. **共用 ollama endpoint** —— `http://127.0.0.1:11434/v1/embeddings` 一个 endpoint 服务两边

## 跟 ollama qwen3-embedding 1024 维原生对接

姊妹篇 1 (pgmnemo-mcp) + 姊妹篇 2 (pgmnemo benchmark) + 姊妹篇 4 (川序当 Schema) + 姊妹篇 5 (agent 漂移) + 姊妹篇 6 (自我进化) + 本篇姊妹篇 7 —— **统一用 ollama 0.33.3 + qwen3-embedding:0.6b 1024 维**。**零 workaround, 零 zero-pad** —— **pgmnemo schema 硬编码 vector(1024) / 川序 entity_embeddings vector(1024) / powercontext pg_pc_memory_vector_entries vector(1024) 三处都原生匹配**。

`powercontext_pg.py` 里的 embedder 是 ~10 行:

```python
OLLAMA_URL = os.getenv('OLLAMA_URL', 'http://127.0.0.1:11434')
OLLAMA_MODEL = os.getenv('OLLAMA_MODEL', 'qwen3-embedding:0.6b')
EMBED_DIM = int(os.getenv('EMBED_DIM', '1024'))

def embed_ollama(text: str) -> list[float]:
    """调本地 ollama /api/embed, 返回 1024-dim float list."""
    req = Request(
        f'{OLLAMA_URL}/api/embed',
        data=json.dumps({'model': OLLAMA_MODEL, 'input': text}).encode('utf-8'),
        headers={'Content-Type': 'application/json'},
    )
    with urlopen(req, timeout=30) as resp:
        data = json.loads(resp.read().decode('utf-8'))
    return [float(x) for x in data['embeddings'][0]]
```

**对接 powercontext config 时** —— `embedding_dimension=1024` 默认值已经匹配 ollama, 不用手动配:

```python
PGMemoryVectorIndex(
    EmbeddingProfile(dimension=1024, distance='cosine', normalization='unit')
)
```

**如果想换 embedder** —— 改 OLLAMA_MODEL env var 即可 —— 比如换成 `nomic-embed-text` (768 维) 或 `mxbai-embed-large` (1024 维) —— **`PGMemoryVectorIndex(dimension=768)` 自动适配**。

## 把 powercontext 跑在本机 PG 上的完整路径

写好的 `powercontext_pg.py` (~670 行) 是 **真实可用的最小 PG adapter**。要把它提交给 OceanBase/powercontext 上游, 完整的 5 个 PR:

3. **PR 3 — `pyproject.toml`** + `pg/__init__.py`: 加 `[project.optional-dependencies].pg = ["psycopg[binary]>=3.2,<4", "pgvector>=0.4,<1"]`, exports `PGConfig` / `PGProfile` / `PGMemoryFTSIndex` / `PGMemoryVectorIndex`

## powercontext vs 姊妹篇 5/6 framework vs 川序 schema 三者对比

姊妹篇 5/6 提的方案 + 姊妹篇 7 powercontext + 姊妹篇 4 川序 schema —— **三者定位不同, 但可以共存**:

| 维度 | 姊妹篇 5/6 framework | powercontext 0.2.0 | 川序 v4.4.12 |
|---|---|---|---|
| 定位 | paper design + 620 行 Python 实现参考 | production-ready AI context 基础设施 | enterprise AI agent management schema 标准化 |
| storage | 自己写 SQL | SQLite / OceanBase / SeekDB (缺 PG) | PG 18.3+ (必须有 PG) |
| 范围 | 4 个核心机制 + 5 auto-adapt | 30 endpoints + 26 表 + 完整 HTTP server | 78 SQL migration + 130+ 表 + HTTP API |
| outcome feedback | 自定义 framework | built-in MemoryReranking + MemoryLayerError | lifecycle_state 10 种 + custom retention |
| embedder | 自定义 embed_ollama 函数 | embedding_base_url config + canonical_embedding | entity_embeddings 专用 schema |
| skill registry | framework level tier auto-promote | skill/registry.py + SkillCompatibility | capability framework + tier 自定义 |
| license | SOUL 默认 | Apache 2.0 (OceanBase 出品) | Apache 2.0 (digoal 出品) |
| 用在哪 | 自家项目 | 任何 agent runtime (Claude Code / Hermes / LangGraph) | 企业内 AI agent infra |

**怎么用**:

- **小项目 / 实验** —— 姊妹篇 5/6 framework 够用
- **中项目 / 多个 agent runtime** —— 用 powercontext + 它自带的 langgraph / claude-code / pydantic-ai integration
- **大项目 / 企业内 AI agent infra** —— 用川序 schema + powercontext (PG adapter) + 姊妹篇 5/6 framework 的 auto-adapt 思路 + 自家 framework

**姊妹篇 7 的真正价值** —— **不是 "用 powercontext 替代姊妹篇 5/6"**, 而是 **"powercontext 是姊妹篇 5/6 提的方案在生产环境的实现"** —— **写一个 PG adapter + 跟川序共存 = 完整的 production-ready AI 上下文管理栈, 三个项目 (姊妹篇 5/6 + powercontext + 川序) 整合成 1 个系统**。

## 总结

姊妹篇 5 (agent 长期质量漂移分析 + 4 机制) + 姊妹篇 6 (Context Manager 自我进化 framework) + **本篇姊妹篇 7 (powercontext PG adapter + 跟川序 + ollama 端到端集成)** —— **三姊妹篇一起构成完整的 "AI 上下文管理 OS 层" 解决方案**:

- 姊妹篇 5 是设计哲学 (人脑 Atkinson-Shiffrin + Ebbinghaus 工程化)
- 姊妹篇 6 是 620 行 Python framework (实测 8 步 demo 全 work)
- 姊妹篇 7 是 670 行 PG adapter (实测 6 步 demo 全 work, 跟 OceanBase 旗舰项目 powercontext 对接)

**姊妹篇 1-7 + 主篇 14 篇 = ~170K 字 + 2 个完整 framework (Context Manager + powercontext PG adapter) + 1 个 production-grade 项目集成方案 + 本机 AI 上下文管理研究环境完整闭环**。
