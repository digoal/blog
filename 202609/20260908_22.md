## 背景  



> 系列第 7 篇。继续"先实测,然后深挖每个点"原则。这次**第一次打破我之前的猜想**——以为 orioledb 完全自管 checkpoint,**实测发现不是**。  
> 测试方法: 同主机同 workload,分别跑 CHECKPOINT 3 轮,记时间 + WAL + 真实 record dump。  

---

## 这篇文章要回答什么

zedstore 和 OrioleDB 都被称为 "PG 列存 fork/extension",但它们的 **checkpoint 实现方式完全不同**:

- **zedstore**:完全沿用 PG 13 主线 `CreateCheckpoint()`,**不注册任何 hook**
- **OrioleDB**:在 `orioledb.c:1418` 注册 `CheckPoint_hook = o_perform_checkpoint`,**沿用 PG 18 框架 + 加自己的逻辑**

**实测发现**:**orioledb checkpoint 慢 5.18×,但产生的 WAL 几乎一样**。这是一个反直觉的发现——**orioledb 内部做了大量工作,但 checkpoint 相关的 WAL 流量没多**。


**关键发现**:

**真相**:**orioledb checkpoint 的慢,慢在 orioledb 自己的 work(扫描 dirty page + 写 control page + 刷 B-tree),不是慢在 PG WAL 写**。

## 四、代码真相:谁接管了 checkpoint

### 4.1 orioledb 注册 hook

**`src/orioledb.c:1418`**:

```c
CheckPoint_hook = o_perform_checkpoint;
```

**`src/checkpoint/checkpoint.c:1656` 的实现**:

```c
void o_perform_checkpoint(XLogRecPtr redo_pos, int flags)
{
    PG_TRY();
    {
        o_perform_checkpoint_guts(flags);
    }
    PG_CATCH();
    {
        if (!checkpoint_rotation_in_progress)
            PG_RE_THROW();
        /* ... */
        ereport(FATAL,
                (errmsg("OrioleDB checkpoint %u failed", ...),
                 errdetail("A checkpoint that failed part way through cannot "
                           "be rolled back or retried.")));
    }
    PG_END_TRY();

    if (next_CheckPoint_hook)
        next_CheckPoint_hook(redo_pos, flags);
}
```

**重要注释**:"`From here on a failure cannot be retried -- see o_perform_checkpoint()`"—— **orioledb checkpoint 一旦开始就不可回滚**。这是工程上的"宁可 fail 不愿 corruption"哲学。

### 4.2 zedstore 完全不注册 hook

**代码搜索 `CheckPoint_hook` 在 zedstore 仓库**:

```
$ grep -rn "CheckPoint_hook\|Checkpoint_hook\|CreateCheckpoint" \
    /root/new/src/postgres-archive/src
src/backend/storage/ipc/standby.c:878: * CreateCheckpoint() where we use the logical checkpoint location as
src/backend/storage/buffer/bufmgr.c:3473: essential that CreateCheckpoint waits for virtual transactions
src/backend/access/transam/xlog.c:895:static bool XLogCheckpointNeeded(XLogSegNo new_segno);
```

**没有 CheckPoint_hook 引用**。**zedstore 完全依赖 PG 主线 `CreateCheckpoint()` 框架**。

`zedstoream_handler.c:2027` 的注释提到:

```c
/* shared_buffers and therefore a concurrent checkpoint may have moved the
   XID mapping - we cannot trust those XIDs to be valid after this point */
```

—— 这是 zedstore **唯一一处提到 checkpoint 的注释**,**承认 PG 主线 checkpoint 会影响 zedstore 内部状态**,**但它没有任何应对代码**。**这是一个**潜在 bug**: 如果在 INSERT 中途发生 checkpoint,XID mapping 可能漂移**。

### 4.3 orioledb checkpoint 的关键步骤

**`src/checkpoint/checkpoint.c::o_perform_checkpoint_guts` 的核心路径**:

```c
// line 1747
checkpoint_state->dirtyPagesEstimate = get_dirty_pages_count_sum();
checkpoint_state->dirtyPagesEstimate *= (1.0 + CheckPointCompletionTarget
                                         * o_checkpoint_completion_ratio);

// line 1800
checkpoint_state->sysTreesStartPtr = get_checkpoint_xlog_ptr();
wait_finish_active_commits(checkpoint_state->sysTreesStartPtr);

// line 1816
start_write_xids(cur_chkp_num);

// line 1821
checkpoint_sys_trees(flags, cur_chkp_num, &chkp_tbl_arg);

// line 1848
checkpoint_state->replayStartPtr = get_checkpoint_xlog_ptr();
wait_finish_active_commits(checkpoint_state->replayStartPtr);

// line 1870
acquire_chkp_lock_drain(&checkpoint_state->oTablesMetaLock);
o_indices_foreach_oids(checkpoint_tables_callback, &chkp_tbl_arg);
LWLockRelease(&checkpoint_state->oTablesMetaLock);

// line 1889
finish_write_xids(cur_chkp_num, ...);
```

**关键步骤解析**:
1. **`get_dirty_pages_count_sum()`** —— 估算 orioledb 表的 dirty page 总数
2. **`wait_finish_active_commits`** —— **等所有活跃事务完成**(`finish_active_commits` 是关键路径)
3. **`start_write_xids`** —— 把 xids 文件(活跃 OXid 列表)刷到 orioledb 自己的控制文件
4. **`checkpoint_sys_trees`** —— 写 orioledb 系统树(oTablesMeta, oTables, oIndtypes)
5. **`acquire_chkp_lock_drain(&oTablesMetaLock)`** —— **拿 oTablesMetaLock 全局排他锁**(`LW_EXCLUSIVE`),阻塞所有 INSERT/UPDATE/DELETE
6. **`o_indices_foreach_oids(checkpoint_tables_callback, ...)`** —— 遍历每个 orioledb 表,做 per-table checkpoint
7. **`finish_write_xids`** —— 完成 xids 文件 flush

**line 1870 的 `acquire_chkp_lock_drain` 是关键**——**它会阻塞所有写入**。

## 五、实测:CHECKPOINT 期间的并发 INSERT 延迟

**测试方法**:后台跑 CHECKPOINT,前台跑 30 个 INSERT,测总时间。

```
zedstore:  30 个 INSERT 总耗时 0.267s,总耗时(含等待 CHECKPOINT) 0.274s
orioledb:  30 个 INSERT 总耗时 0.393s,总耗时(含等待 CHECKPOINT) 0.767s
```

**INSERT 时间增量 (CHECKPOINT 阻塞导致的减速)**:
- **zedstore: +0ms** —— CHECKPOINT 完全不阻塞 INSERT
- **orioledb: +126ms (+47%)** —— CHECKPOINT 阻塞 INSERT

**orioledb 总时间 767ms vs zedstore 274ms** —— **orioledb 总耗时多 493ms (180%)**。

**含义**:**orioledb 在 CHECKPOINT 期间,INSERT 需要等 acquire_chkp_lock_drain 释放锁**。这是 orioledb 设计上的**写放大延迟**——为了 checkpoint 的一致性,付出了 INSERT 等待时间的代价。

## 七、写入路径上的设计哲学对比

### 7.1 zedstore 的设计哲学

- **不做 orioledb 自己的 checkpoint 流程**
- **不拿全局锁**
- **完全把 checkpoint 责任推给 PG 主线**
- **INSERT/UPDATE 完全不感知 checkpoint**
- **潜在 bug**: `zedstoream_handler.c:2027` 注释承认 "concurrent checkpoint may have moved the XID mapping" 但**没有应对代码**

### 7.2 OrioleDB 的设计哲学

- **注册 CheckPoint_hook,接管 checkpoint 流程**
- **拿全局 oTablesMetaLock,保证一致性**
- **写 orioledb 自己的 control page + xids 文件**
- **INSERT/UPDATE 在 CHECKPOINT 期间被锁阻塞**
- **设计取舍**:一致性 > 写入延迟

### 7.3 哲学差异的本质

| 维度 | zedstore | OrioleDB |
|---|---|---|
| **checkpoint 责任** | 推给 PG 框架 | 自己接管 |
| **锁** | 无全局锁 | oTablesMetaLock 全局排他 |
| **INSERT 阻塞** | 否 | 是(等 acquire_chkp_lock_drain) |
| **WAL 流量** | 184 字节 | 232 字节(差 26%) |
| **CHECKPOINT 时间** | 0.096s | 0.500s(慢 5.18×) |
| **一致性保证** | 弱(依赖 PG 框架正确性) | 强(自管 + 全局锁) |

**本质**:zedstore 是个**研究项目**——它假设 PG 主线框架足够好,自己专注 attstream 压缩 + TID 树;OrioleDB 是**生产级工程**——它接管所有 critical path(checkpoint/redo/recovery),保证一致性,但付出了写入延迟。

## 八、之前文章的修正

**之前 4 篇并发对比 + 6 篇 WAL 对比** 我推断 orioledb "完全自管 checkpoint"。**错了**。

**真实情况**:
- orioledb **沿用 PG 框架**(通过 `CheckPoint_hook`),**不是完全自管**
- orioledb 的优势**不是 checkpoint 更快**,而是**一致性更强**
- zedstore 的优势**不是 checkpoint 不阻塞写入**,而是**完全不动 checkpoint**(但这是弱点)

**修正**:后续文章里,凡是说 "orioledb 完全自管 X" 的,**全部改成 "orioledb 在 PG 框架上加自己的 hook 实现 X"**。

## 九、真实工程决策:哪个更适合你的场景?

| 场景 | 推荐 | 理由 |
|---|---|---|
| **OLTP 高频写入 + 低延迟要求** | zedstore | CHECKPOINT 不阻塞 INSERT |
| **生产级数据库 + 需要强一致性** | OrioleDB | 全局锁保证 checkpoint 一致性 |
| **高并发 + 高可用 + 跨 region** | OrioleDB | 自管 control file + xids 文件 + S3 上传 |
| **实验 / 学习 PG 列存** | zedstore | 沿用 PG 主线, 简单易懂 |
| **PG 18 主线兼容性** | OrioleDB | 跟 Supabase 集成, 主线工程 |
| **研究 / 论文** | zedstore | 单 commit, 代码简单 |

## 一句话总结

**实测打破猜想**:orioledb 不是"完全自管 checkpoint",而是**沿用 PG 18 框架 + 注册 `CheckPoint_hook` 加自己的逻辑**。实测发现 **orioledb checkpoint 慢 5.18×,但 WAL 几乎一样(232 vs 184 字节)**。**CHECKPOINT 期间 orioledb 的 INSERT 被全局锁阻塞 47%**,**zedstore 完全不阻塞**。这是 PG 列存演化系列的 **第 7 篇**,下一篇文章将深挖 **OrioleDB 独有的 S3 checkpoint 实现**——这是 orioledb 的**杀手级特性**,**zedstore 没有对应功能**。
