## 背景  


> 系列第 9 篇,**最后一篇**。这次又打破了我之前的猜测——以为"OrioleDB redo 因为 record 小所以更快"。**实测不是**—— OrioleDB redo 慢 2.27×,**即使 6 个 worker 并行**。  
> 测试方法: 同主机同 workload,分别跑 100k INSERT + force shutdown + 重启, 测 ready-to-connect 时间 + redo 内部耗时。  

---

## 这篇文章要回答什么

之前第 6 篇 WAL 文章我推断:

> "OrioleDB redo 应该比 zedstore 快,因为 record 小"

**实测发现反了** —— **OrioleDB redo 慢 2.27×**,即使它**有 6 个 recovery worker 并行处理**。

这是为什么?

- **zedstore**:**单线程 redo**,走 PG 主线 startup process,**简单 switch-case**
- **OrioleDB**:**6 个 worker 并行 redo**,**三阶段 replay**(sys-trees / data / toast-consistent),**OXid + xmin 协调** —— **协调开销 > 并行收益**

---

## 一、实测环境

```
zedstore: PG 13devel + zedstore fork, port 54329
orioledb: PG 18.6 + OrioleDB beta17, port 54330
workload: 100k INSERT, 100 字节 val
```

**测试流程**:
1. 准备表 + INSERT 100k 行(不 commit)
2. `pg_ctl stop -m immediate` —— 模拟崩溃
3. 重启 PG, 测启动到 `database system is ready to accept connections` 的时间

## 四、代码真相:两个 redo 哲学

### 4.1 zedstore redo 极简设计 (`zedstore_wal.c:22-64`)

```c
zedstore_redo(XLogReaderState *record)
{
    uint8 info = XLogRecGetInfo(record) & ~XLR_INFO_MASK;
    switch (info)
    {
        case WAL_ZEDSTORE_INIT_METAPAGE:        zedstore_redo_init_metapage(record); break;
        case WAL_ZEDSTORE_UNDO_NEWPAGE:         zedstore_redo_undo_newpage(record); break;
        case WAL_ZEDSTORE_UNDO_DISCARD:         zedstore_redo_undo_discard(record); break;
        case WAL_ZEDSTORE_BTREE_NEW_ROOT:       zedstore_redo_btree_new_root(record); break;
        case WAL_ZEDSTORE_BTREE_REWRITE_PAGES:  zedstore_redo_btree_rewrite_pages(record); break;
        case WAL_ZEDSTORE_TIDLEAF_ADD_ITEMS:    zedstore_redo_tidleaf_add_items(record); break;
        case WAL_ZEDSTORE_TIDLEAF_REPLACE_ITEM: zedstore_redo_tidleaf_replace_item(record); break;
        case WAL_ZEDSTORE_ATTSTREAM_CHANGE:     zedstore_redo_attstream_change(record); break;
        case WAL_ZEDSTORE_TOAST_NEWPAGE:        zedstore_redo_toast_newpage(record); break;
        case WAL_ZEDSTORE_FPM_DELETE_PAGE:      zedstore_redo_fpm_delete_page(record); break;
        case WAL_ZEDSTORE_FPM_REUSE_PAGE:       zedstore_redo_fpm_reuse_page(record); break;
        default: elog(PANIC, "zedstore_redo: unknown op code %u", info);
    }
}
```

**42 行代码** —— **单 thread, 单 switch-case**。**完全靠 PG 主线 startup process 调度**。

### 4.2 OrioleDB redo 三层架构 (`src/recovery/recovery.c`)

**1. `o_recovery_start_hook` (line 1144)** —— 启动 recovery workers
```c
void o_recovery_start_hook(void)
{
    before_shmem_exit(recovery_on_proc_exit, (Datum) -1);
    recovery_single = *recovery_single_process = IsFatalError();
    ...
    for (i = recovery_first_worker; i <= finish; i++)
    {
        workers_pool[i].handle = recovery_worker_register(i);
        state->queue = shm_mq_attach(GET_WORKER_QUEUE(i), NULL, workers_pool[i].handle);
    }
}
```

**2. `orioledb_redo` (line 1225)** —— 主 redo 入口,**三阶段 replay**
```c
void orioledb_redo(XLogReaderState *record)
{
    Assert((XLogRecGetInfo(record) & ~XLR_INFO_MASK) == ORIOLEDB_XLOG_CONTAINER);
    ...
    // Stage 0: replayStartPtr 之前 - 只 replay sys-tree WAL
    // Stage 1: replayStartPtr 之后 - replay data WAL
    // Stage 2: toastConsistentPtr 之后 - replay SK fix-up

    if (record->ReadRecPtr >= checkpoint_state->controlReplayStartPtr && !replay_start_reached)
    {
        workers_synchronize(record->ReadRecPtr, true);
        apply_deferred_checkpoint_undo();
        replay_start_reached = true;
    }
    if (record->ReadRecPtr >= checkpoint_state->controlToastConsistentPtr && !toast_consistent)
    {
        workers_synchronize(record->ReadRecPtr, true);
        apply_pending_sk_fixups();
        toast_consistent = true;
        workers_notify_toast_consistent();
    }
    if (record->ReadRecPtr >= checkpoint_state->controlSysTreesStartPtr)
    {
        replay_container(msg_start, msg_start + msg_len, recovery_single,
                         record->ReadRecPtr, record->EndRecPtr);
    }
}
```

**3. `worker_send_msg` (line 5340)** —— shmem message queue 通信
```c
static void worker_send_msg(int worker_id, Pointer msg, uint64 msg_size)
{
    RecoveryWorkerState *state = &workers_pool[worker_id];
    if ((RECOVERY_QUEUE_BUF_SIZE - state->queue_buf_len) < msg_size)
        worker_queue_flush(worker_id);
    memcpy(state->queue_buf + state->queue_buf_len, msg, msg_size);
    state->queue_buf_len += msg_size;
}
```

## 五、三阶段 replay 的设计意图

**Stage 0**(`sysTreesStartPtr` 之前):
- **只能 replay sys-tree WAL**(oTablesMeta, oTables, oIndtypes 等元数据树)
- **不能 replay data WAL**(因为 data 描述符依赖 sys tree 一致性)

**Stage 1**(`replayStartPtr` 之后):
- **可以 replay data WAL** (主表 + 索引)
- sys trees 已经一致,**data 描述符可以装配**

**Stage 2**(`toastConsistentPtr` 之后):
- **处理 PK->SK fix-up** (pending_sk_fixups)
- toast 状态已经一致,可以修复 SK(PK 改了但 SK 没改)

**每个 stage 切换时,先 `workers_synchronize` 让所有 worker 完成当前 batch,然后 apply 跨阶段 fix-up**。

**这是 PG 主线 redo 不会做的事** —— PG 主线假设 single heap,没有"sys tree consistency"的概念。

## 六、OrioleDB redo 测试 hooks

OrioleDB 在 redo 上提供了 **3 个测试 hook**(zedstore 都没有):

| Hook | GUC | 用途 |
|---|---|---|
| `debug_recovery_crash_lsn` | `orioledb.debug_recovery_crash_lsn` | 在指定 LSN 触发 PANIC 模拟中间崩溃 |
| `replay_until_lsn` | `orioledb.replay_until_lsn` | 限定 replay 范围(短 replay 测试) |
| `recovery_target_time` | PG 主线 | 时间点 recovery |

**debug_recovery_crash_lsn 实现**(`recovery.c:1242`):

```c
#ifdef IS_DEV
if (unlikely(XLogRecPtrIsValid(debug_recovery_crash_lsn)) &&
    record->ReadRecPtr >= debug_recovery_crash_lsn)
    elog(PANIC, "orioledb.debug_recovery_crash_lsn reached at %X/%X",
         LSN_FORMAT_ARGS(record->ReadRecPtr));
#endif
```

—— **专门用于测试 redo 中间崩溃场景**。**这是 zedstore 完全没的设计**。

**这是 OrioleDB 是"生产级"、zedstore 是"研究项目"的另一个证据**。

## 七、自动 fallback 机制

OrioleDB redo 有**自动 fallback 到单进程**:

`recovery.c:1187-1195`:
```c
workers_pool[i].handle = recovery_worker_register(i);
if (workers_pool[i].handle == NULL)
{
    /* Not enough slots for background workers. */
    for (i--; i >= 0; i--)
        TerminateBackgroundWorker(workers_pool[i].handle);
    recovery_single = *recovery_single_process = true;
    finish = -1;
    ereport(WARNING, (errcode(ERRCODE_CONFIGURATION_LIMIT_EXCEEDED),
                      errmsg("unable to start recovery workers"),
                      errdetail("You must increase max_worker_processes value ... Fallback to recovery in single-process mode.")));
}
```

**如果 `max_worker_processes` 不够启 worker**,**自动切单进程 redo**,**不报错** —— 这是工程友好设计。

## 八、之前文章的修正

**第 6 篇 wal-record-comparison.md** 我推断:

> "OrioleDB redo 应该比 zedstore 快,因为 record 小"

**实测反了** —— **OrioleDB redo 慢 2.27×**。

**为什么?**OrioleDB redo 不是简单的"replay WAL record":
1. **3 阶段 replay** —— 跨阶段同步开销
2. **OXid + xmin 协调** —— 维护 64-bit OXid 快照
3. **replay_container** —— 每个 WAL record 解析为 logical record
4. **shmem mq 通信** —— worker 间协调

**这些开销的总和 > 并行收益**。**OrioleDB 用一致性换性能**。

## 九、真实工程决策:哪个更适合你的场景?

| 场景 | 推荐 | 理由 |
|---|---|---|
| **冷启动恢复快** | zedstore | redo 快 2.27× |
| **崩溃一致性保证** | OrioleDB | 三阶段 replay + fallback + 测试 hooks |
| **开发 + 调试 redo** | OrioleDB | 3 个测试 hook, panic mid-replay 容易复现 |
| **小数据库 + 低写入** | zedstore | redo 简单粗暴, 维护成本低 |
| **大数据库 + 高写入** | OrioleDB | redo 用并行 + 分阶段, 大数据量扩展性更好 |
| **HA + 自动故障恢复** | OrioleDB | 自动 fallback + 严格一致性 |
| **PG 18 主线兼容** | OrioleDB | PG 18 extension, Supabase 集成 |

**核心取舍**:**zedstore 牺牲一致性换速度,OrioleDB 牺牲速度换一致性**。
