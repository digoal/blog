## 这篇文章要回答什么

之前文章提到 OrioleDB 论文宣传 "raft 友好",**没说清楚怎么 raft 友好**。这次我**实测验证**核心机制 —— `SWITCH_LOGICAL_XID` 让 logical decoder 能把 heap + Oriole 修改合并成一个事务流,**不分裂**。

**关键发现**:
- OrioleDB 的 logical xid 是 **32-bit**(不是 64-bit OXid),**跟 PG 标准 XID 一样**
- `SWITCH_LOGICAL_XID H2O`(Heap To Oriole)记录只 **9 字节** —— topXid + subXid
- 触发条件严格:**必须 heap + Oriole 同一事务**才触发
- logical decoder 看到 `SWITCH_LOGICAL_XID` 调 `ReorderBufferAssignChild(topXid, subXid)` —— **PG 主线 API** 把 Oriole 修改关联到 heap 事务

## 一、OrioleDB 的逻辑 XID 设计

**OrioleDB 的 OXid 是 64-bit**(内部事务 ID),**logical xid 是 32-bit**(暴露给外部)。这是关键设计。

让我看 `WALRecXid` 的结构(`include/recovery/wal.h:85-92`):

```c
typedef struct
{
    uint8        recType;                       // 1 byte
    uint8        oxid[sizeof(OXid)];            // 8 bytes (64-bit Oriole OXid)
    uint8        logicalXid[sizeof(TransactionId)];  // 4 bytes (32-bit)
    /* Since ORIOLEDB_WAL_VERSION = 17 */
    uint8        heapXid[sizeof(TransactionId)];     // 4 bytes (32-bit)
} WALRecXid;
```

**`logicalXid` 是 32-bit** = **PG 标准 `TransactionId`**。

**为什么是 32-bit?**
- PG 的 logical decoder 用 32-bit XID 标识事务
- 如果 OrioleDB 用 64-bit OXid,**logical decoder 完全无法处理**
- 用 32-bit logical xid 兼容 PG 主线的 ReorderBuffer API

**OrioleDB 的 logical XID 32-bit 空间有限,但通过 `SWITCH_LOGICAL_XID` 关联到 heap 的 32-bit XID,完整对接 PG 主线事务系统**。

## 二、`WAL_REC_SWITCH_LOGICAL_XID` 的精确定义

**`include/recovery/wal_record.h:27-39`** —— 这是**最核心的注释**:

```c
/*
 * WAL_REC_SWITCH_LOGICAL_XID:
 *   Record type for a case when both heap and Oriole apply changes within a
 *   single transaction, so one logical xid is assigned by heap, and the other
 *   is assigned by Oriole.
 *   This record defines a connection between Oriole's sub-transaction xid and
 *   a xid of the top heap transaction which is needed for logical decoder.
 *   Otherwise, without this connection, main transaction suddenly becomes
 *   split into two independent parts.
 *   From logical decoder's point of view this looks like two independent
 *   transactions but in fact internally related to each other. This situation
 *   outcomes in troubles for logical decoder with visibility of heap
 *   modifications in Oriole's sub-part due to incorrect state of the
 *   MVCC-historical snapshot.
 */
```

**翻译**:
1. 当一个事务同时修改 heap + Oriole,**heap 给一个 XID,Oriole 给一个 logical xid**
2. **SWITCH_LOGICAL_XID 建立 Oriole sub-xid 和 heap top-xid 的关联**
3. **没有这个关联**,**事务会分裂**为两个独立部分
4. logical decoder 看到两个独立事务,**MVCC snapshot 不正确**

## 三、`WALRecSwitchLogicalXid` 结构 (`include/recovery/wal.h:94-99`)

```c
typedef struct
{
    uint8        recType;                                // 1 byte
    uint8        topXid[sizeof(TransactionId)];          // 4 bytes
    uint8        subXid[sizeof(TransactionId)];          // 4 bytes
} WALRecSwitchLogicalXid;
```

**总 9 字节** —— **OrioleDB 最小的 logical record**(只关联两个 XID,不存任何表/数据信息)。

**X-Macro 注册**(`include/recovery/wal_record.h:59`):
```c
X(WAL_REC_SWITCH_LOGICAL_XID,   17, "SWITCH_LOGICAL_XID", wal_parse_rec_switch_logical_xid)
```

## 四、`add_switch_logical_xid_wal_record` 实现(`src/recovery/wal.c:633-655`)

```c
void
add_switch_logical_xid_wal_record(TransactionId logicalXid_top, TransactionId logicalXid_sub)
{
    WALRecSwitchLogicalXid *rec;

    if (local_wal.contains_switch_xid)
        return;                                  // 一个 LocalWal 缓冲只写一个 SWITCH

    local_wal.contains_switch_xid = true;
    Assert(!is_recovery_process());
    flush_local_wal_if_needed(sizeof(*rec));

    rec = (WALRecSwitchLogicalXid *) (&local_wal.buffer[local_wal.buffer_offset]);
    rec->recType = WAL_REC_SWITCH_LOGICAL_XID;
    memcpy(rec->topXid, &logicalXid_top, sizeof(TransactionId));
    memcpy(rec->subXid, &logicalXid_sub, sizeof(TransactionId));

    local_wal.buffer_offset += sizeof(*rec);
}
```

**关键设计**:
- **`if (local_wal.contains_switch_xid) return;`** —— **一个 LocalWal 缓冲只写一个 SWITCH**,避免重复
- 用 `flush_local_wal_if_needed` 保证 buffer 足够

## 五、实测触发场景

**关键步骤**:在 `postgresql.conf` 加 `log_min_messages = debug4`,让 server 端 DEBUG 输出到 `pg.log`。

### 5.1 测试 SQL

```sql
-- 准备
DROP TABLE IF EXISTS heap_t;
DROP TABLE IF EXISTS ori_t;
CREATE TABLE heap_t (id int primary key, val text COLLATE "C");
CREATE TABLE ori_t (id int primary key, val text COLLATE "C") USING orioledb;
INSERT INTO heap_t VALUES (1, 'init-h');
INSERT INTO ori_t VALUES (1, 'init-o');

-- A: 只 Oriole 事务
BEGIN;
UPDATE ori_t SET val = 'o-only-1' WHERE id = 1;
COMMIT;

-- B: 只 heap 事务
BEGIN;
UPDATE heap_t SET val = 'h-only-1' WHERE id = 1;
COMMIT;

-- C: 跨事务 (heap + Oriole)
BEGIN;
UPDATE heap_t SET val = 'h-cross-1' WHERE id = 1;
UPDATE ori_t SET val = 'o-cross-1' WHERE id = 1;
COMMIT;
```

### 5.2 实测 PG log

**A: 只 Oriole 事务** —— `oxid 111 logicalXid 4286578688 top heapXid 0 useHeap 0`
- **logicalXid 4286578688**(分配的 Oriole logical xid)
- **top heapXid 0**(**没分配 heap xid**)
- **useHeap 0** = **不通过 heap 路径**
- **没触发 SWITCH_LOGICAL_XID**

**B: 只 heap 事务** —— **不分配 Oriole OXid**,**没触发任何 OrioleDB log**

**C: 跨事务** —— `oxid 108 logicalXid 4286578688 top heapXid 818 useHeap 1`

```
DEBUG:  logical xid acquired: 4286578688
DEBUG:  SWITCH_LOGICAL_XID H2O heap xid 818 -> oriole xid 4286578688
DEBUG:  XACT_EVENT_PRE_COMMIT oxid 108 logicalXid 4286578688 top heapXid 818 current heapXid 818 useHeap 1
DEBUG:  XACT_EVENT_PRE_COMMIT wal_joint_commit for SWITCH_LOGICAL_XID H2O
        oxid 108 logicalXid 4286578688 top heapXid 818 current heapXid 818
DEBUG:  XACT_EVENT_COMMIT oxid 108 logicalXid 4286578688 top heapXid 818 current heapXid 818 useHeap 1
```

**关键观察**:
1. **`logical xid acquired: 4286578688`** —— 分配 logical xid
2. **`SWITCH_LOGICAL_XID H2O heap xid 818 -> oriole xid 4286578688`** —— **写入 SWITCH_LOGICAL_XID**
3. **`H2O`** = **H**eap **T**o **O**riole(方向)
4. **`wal_joint_commit for SWITCH_LOGICAL_XID H2O`** —— **PRE_COMMIT 时联合提交**
5. **`useHeap 1`** = **通过 heap 路径**

## 六、`ReorderBufferAssignChild` 调用(`src/recovery/logical.c:716-732`)

```c
case WAL_REC_SWITCH_LOGICAL_XID:
{
    XLogRecPtr xlogPtr = ctx->xlogRecPtr + rec->offset;
    TransactionId topXid = rec->u.swxid.topXid;
    TransactionId subXid = rec->u.swxid.subXid;

    elog(DEBUG4, "RECEIVE record type %d (%s) %u=>%u oxid " UINT64_FORMAT
         " logicalXId %u heapXid %u xlogPtr %X/%X",
         rec->type, recname, topXid, subXid,
         rec->oxid, rec->logicalXid, rec->heapXid, LSN_FORMAT_ARGS(xlogPtr));

    Assert(TransactionIdIsValid(topXid));
    Assert(TransactionIdIsValid(subXid));

    ReorderBufferAssignChild(ctx->decodeCtx->reorder, topXid, subXid, xlogPtr);

    break;
}
```

**核心调用**:**`ReorderBufferAssignChild(ctx->decodeCtx->reorder, topXid, subXid, xlogPtr)`** —— 这是 **PG 主线 logical decoding API**!

**`ReorderBufferAssignChild` 的作用**:
- 在 logical decoder 的 `ReorderBuffer` 里建立 parent-child 关系
- `topXid` = 父事务(heap 主事务)
- `subXid` = 子事务(Oriole 子事务)
- `xlogPtr` = SWITCH_LOGICAL_XID 的 WAL 位置

**这是为什么 OrioleDB "raft 友好"的真正原因**:
- 没有 SWITCH_LOGICAL_XID:Oriole 修改在 logical decoder 看是独立事务,**raft 流分裂**
- 有 SWITCH_LOGICAL_XID:`ReorderBufferAssignChild` 让 logical decoder 把 Oriole 修改作为 heap 事务的子部分,**raft 流保持完整**

## 七、完整事务流 vs 跨事务流

**没有 SWITCH_LOGICAL_XID 的世界**(假设 OrioleDB 没实现):

```sql
BEGIN;
UPDATE heap_t SET val = 'h-1' WHERE id = 1;  -- PG XID = 818
UPDATE ori_t SET val = 'o-1' WHERE id = 1;  -- Oriole OXid = 108
COMMIT;
```

**logical decoder 输出(naive)**:
```
BEGIN 818
UPDATE heap_t ...
COMMIT 818
BEGIN 108           <- **分裂成两个事务!**
UPDATE ori_t ...
COMMIT 108
```

**raft 复制问题**:**follower 看到两个独立事务**,但**它们应该在原始节点是一个事务**。**如果 follower 网络分区,可能看到 818 但没看到 108** —— **数据不一致**。

**有 SWITCH_LOGICAL_XID 的世界(OrioleDB 真实实现)**:

```
BEGIN 818
UPDATE heap_t ...
SWITCH_LOGICAL_XID H2O 818 -> 4286578688   <- 关键!
UPDATE ori_t ...
JOINT_COMMIT 818, 4286578688
```

**logical decoder 输出**:
```
BEGIN 818 (parent)
   SUB_XID 4286578688
   UPDATE heap_t ...
   UPDATE ori_t ...
COMMIT 818 (with sub_xid)
```

**raft 复制正确**:**事务是一个原子单元**,**follower 看到完整的 818 事务,包括 Oriole 修改**。

## 八、为什么 OrioleDB 不直接用 heap 的 XID?

读者可能问:**为什么 OrioleDB 不直接用 heap 的 XID?** —— 这涉及到**三层事务 ID 设计**:

| ID | 长度 | 用途 |
|---|---|---|
| **heap XID** | 32-bit | PG 主线事务 ID,logical decoder 用 |
| **Oriole logical XID** | 32-bit | 暴露给 external(兼容 PG 主线) |
| **Oriole OXid** | 64-bit | **内部事务 ID**(不暴露) |

**为什么有 3 层?**
- **heap XID**(32-bit): 只在 PG 主线事务生命周期内有效,**事务提交后可能被 vacuum 回收**
- **Oriole OXid**(64-bit): **永久事务 ID**,即使 heap XID 被回收,Oriole DB 内部仍能用 OXid
- **logical XID**(32-bit): **暴露给 logical decoder**,必须是 PG 标准 32-bit TransactionId

**SWITCH_LOGICAL_XID 的作用**:
- 把 Oriole logical XID(暴露层) 关联到 heap XID(PG 主线)
- Oriole DB 内部用 OXid 做 permanent 引用
- logical decoder 用 logical XID 做 transient 引用

## 九、OrioleDB `WAL_REC_JOINT_COMMIT` 配合

**`include/recovery/wal_record.h:54`**:
```c
X(WAL_REC_JOINT_COMMIT,         12, "JOINT_COMMIT",       wal_parse_rec_joint_commit)
```

**`wal_joint_commit` 是 OrioleDB 跨事务的"联合 commit"** —— **heap COMMIT + Oriole COMMIT 合并成一个 record**。

**事务流**:
```
BEGIN heap (xid 818)
  UPDATE heap_t ...
  UPDATE ori_t ...        <- Oriole 拿 logical xid 4286578688
  SWITCH_LOGICAL_XID H2O  <- 818 -> 4286578688
JOINT_COMMIT (818, 4286578688)
```

**logical decoder 看到**:
- 一个事务 (XID 818)
- 包含 heap + Oriole 修改
- `ReorderBufferAssignChild` 建立关联
- 输出完整事务给 raft 层

## 一句话总结

**SWITCH_LOGICAL_XID 是 OrioleDB raft 复制的核心**:9 字节 minimal record 建立 Oriole logical XID 和 heap XID 的关联,logical decoder 调 `ReorderBufferAssignChild` 重组事务。**实测确认**:只 Oriole 事务不触发,只 heap 事务不触发,**跨事务触发 `H2O`**(Heap To Oriole),配合 `WAL_REC_JOINT_COMMIT` 让 logical decoder 输出完整事务流。**这是 OrioleDB 比 zedstore 先进的真正原因** —— **OrioleDB 兼容 PG 主线 logical decoder,而 zedstore 自定义 WAL 完全不在 PG logical decoder 视野里**。下一篇文章将深挖 **OrioleDB WAL 备份机制**(`archive_library = 'orioledb'` + `s3_archive_*` 模块),以及 **第 12 篇 S3 recovery 实测**——从 mock S3 下沉到本地恢复的真实耗时。
