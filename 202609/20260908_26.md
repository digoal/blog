## 背景  

> 系列第 11 篇。这次实测 OrioleDB 的 **PG 18 archive_library API 实现** —— `archive_library = 'orioledb'` 直接把 WAL 传到 S3,**不走 shell command**。这是 zedstore 完全没的能力。  
> 测试方法: 配 `archive_library = 'orioledb'` + s3_mode = on,跑跨事务 + `pg_switch_wal()`,看 WAL 是否被 archive + SWITCH_LOGICAL_XID 是否被完整保留。  

---

## 这篇文章要回答什么

之前 8/9/10 篇我假设 OrioleDB 的 S3 模式是 "checkpoint 专用" —— **错了**。这次实测发现 **OrioleDB S3 模式覆盖了 checkpoint + archive + redo + recovery 全链路**。

**关键发现**:
- `archive_library = 'orioledb'` 是 **PG 18 archive_library API** 的完整实现 —— 不需要 `archive_command`
- **preload + archive 分离** —— preload 提前 schedule,减少 archive 延迟
- **SWITCH_LOGICAL_XID 在 archive 路径上正常工作** —— logical decoder replay archived WAL 时,完整事务流可以恢复

---

## 一、传统 PG vs OrioleDB 的 archive 路径

### 1.1 传统 PG (PG 13/14/15/16)

```ini
archive_mode = on
archive_command = 'cp %p /wal_archive/%f'   # shell command
```

**问题**:
- 调用 shell,**慢**(每次 fork + exec shell)
- **单线程**(archive_command 串行执行)
- **不支持 preload**(必须在 archive 时立即传)
- **shell 安全风险**(命令注入)

### 1.2 OrioleDB (PG 18 + OrioleDB extension)

```ini
archive_mode = on
archive_library = 'orioledb'   # PG 18 新 API
```

**优势**:
- 直接走 OrioleDB 内部 C 代码,**快**
- **3 个 S3 worker 并行处理**(`orioledb.s3_num_workers`)
- **preload 预 schedule** —— 在 WAL 切换前 schedule S3 upload,减少 archive 延迟
- **SWITCH_LOGICAL_XID-aware** —— archive 完整保留事务流

## 二、`archive_library` API 实现 (`src/s3/archive.c`)

**`src/s3/archive.c:80-93`** —— `ArchiveModuleCallbacks` 注册:

```c
static bool s3_archive_configured(ArchiveModuleState *state);
static void s3_archive_preload_file(ArchiveModuleState *state,
                                     const char *file, const char *path);
static bool s3_archive_file(ArchiveModuleState *state,
                             const char *file, const char *path);

static const ArchiveModuleCallbacks s3_archive_callbacks = {
    .check_configured_cb = s3_archive_configured,
    .archive_preload_file_cb = s3_archive_preload_file,
    .archive_file_cb = s3_archive_file
};
```

**`src/s3/archive.c:100-107`** —— 入口:

```c
const ArchiveModuleCallbacks *
_PG_archive_module_init(void)
{
    if (!preloadHash)
        make_preload_hash();
    return &s3_archive_callbacks;
}
```

**3 个 callback 的功能**:

### 2.1 `s3_archive_configured` (line 112-116)

```c
static bool
s3_archive_configured(ArchiveModuleState *state)
{
    return orioledb_s3_mode;
}
```

**只在 `orioledb.s3_mode = on` 时启用** —— **生产 build 默认禁用**(之前 S3 文章发现的事实)。

### 2.2 `s3_archive_preload_file` (line 123-144)

```c
static void
s3_archive_preload_file(ArchiveModuleState *state,
                        const char *file, const char *path)
{
    PreloadHashItem *item;

    if (!orioledb_s3_mode)
        return;

    elog(DEBUG1, "archive preload %s", file);

    item = hash_search(preloadHash, &file, HASH_ENTER, &found);
    if (found)
    {
        elog(WARNING, "double call of archive_file_preload_cb() for %s");
        return;
    }

    item->location = s3_schedule_wal_file_write((char *) file);
}
```

**关键设计**:
- **PG 18 在 WAL 切换前调 preload**,**提前 schedule S3 upload**
- **不阻塞 WAL switch** —— schedule 是异步的
- **deduplication** —— 同一个文件不会 schedule 两次

### 2.3 `s3_archive_file` (line 151-...)

```c
static bool
s3_archive_file(ArchiveModuleState *state,
                 const char *file, const char *path)
{
    S3TaskLocation location;
    PreloadHashItem *item;

    if (!orioledb_s3_mode)
        return false;

    elog(DEBUG1, "archive %s", file);

    item = hash_search(preloadHash, &file, HASH_FIND, &found);
    if (item)
    {
        location = item->location;
        // 同步等 S3 upload 完成
        // 必须等确认才能删原 WAL
    }
    // ...
}
```

**关键设计**:
- **`archive_file` 必须同步等 S3 upload 完成** —— PG 主线要这个确认才能删原 WAL 文件
- **复用 preload 时的 location** —— 减少重复 schedule

## 五、跨事务 + WAL archive 实测

### 5.1 跨事务 SQL

```sql
-- 准备
DROP TABLE IF EXISTS heap_t;
DROP TABLE IF EXISTS ori_t;
CREATE TABLE heap_t (id int primary key, val text COLLATE "C");
CREATE TABLE ori_t (id int primary key, val text COLLATE "C") USING orioledb;
INSERT INTO heap_t VALUES (1, 'h-init');
INSERT INTO ori_t VALUES (1, 'o-init');

-- 跨事务
BEGIN;
UPDATE heap_t SET val = 'h-cross' WHERE id = 1;
UPDATE ori_t SET val = 'o-cross' WHERE id = 1;
COMMIT;
SELECT pg_switch_wal();
```

### 5.2 PG log

```
DEBUG:  SWITCH_LOGICAL_XID H2O heap xid 773 -> oriole xid 64
DEBUG:  XACT_EVENT_PRE_COMMIT wal_joint_commit for SWITCH_LOGICAL_XID H2O
        oxid 62 logicalXid 64 top heapXid 773 current heapXid 773
DEBUG:  XACT_EVENT_COMMIT oxid 62 logicalXid 64 top heapXid 773 current heapXid 773 useHeap 1
DEBUG:  archive 000000010000000000000004
DEBUG:  S3 schedule empty dir write: ./pg_wal/archive_status 1 (2788)
DEBUG:  S3 dir put data/1/pg_wal/archive_status/ pg_wal/archive_status
DEBUG:  archive preload 000000010000000000000005
DEBUG:  archive 000000010000000000000005
```

**关键发现**:
1. **`SWITCH_LOGICAL_XID H2O heap xid 773 -> oriole xid 64`** —— 跨事务触发 SWITCH
2. **`wal_joint_commit for SWITCH_LOGICAL_XID H2O`** —— PRE_COMMIT 时联合提交
3. **`oxid 62` 是 OrioleDB 64-bit OXid**(内部); **`oriele xid 64` 是 32-bit logical XID**(暴露)
4. **`pg_switch_wal()` 触发 archive**: WAL 4 → WAL 5

### 5.3 logical decoder 完整路径

```
WAL 文件  ──archive──>  S3  ──replay──>  logical decoder  ──output──>  raft 流
                                                       │
                                                       └─ SWITCH_LOGICAL_XID
                                                          │
                                                          └─ ReorderBufferAssignChild
                                                             │
                                                             └─ 重组跨事务为单事务
```

**完整 raft 复制链路**:
1. **Primary 节点**记录 WAL(含 SWITCH_LOGICAL_XID + JOINT_COMMIT)
2. **OrioleDB archive** 把 WAL 传到 S3(`PUT /wal/<filename>`)
3. **Replica 节点**从 S3 拉 WAL + replay
4. **logical decoder** 解析 WAL,看到 SWITCH_LOGICAL_XID 调 `ReorderBufferAssignChild`
5. **重组事务**为单一流
6. **raft 层**应用到 follower 节点

**这是 SWITCH_LOGICAL_XID 设计的终极目的** —— **让 OrioleDB + PG 主线 logical decoder + raft 复制 = 完整事务流**。

## 六、与传统 `archive_command` 对比

| 维度 | `archive_command` | `archive_library = 'orioledb'` |
|---|---|---|
| **调用方式** | shell command(每次 fork+exec) | 直接 C 函数调用 |
| **速度** | 慢(每次 shell 开销) | 快(直接函数) |
| **并行** | 单线程 | 3 个 S3 worker 并行 |
| **preload** | 不支持 | 提前 schedule |
| **安全** | shell 注入风险 | 无 shell |
| **SWITCH_LOGICAL_XID-aware** | 自动保留(因为是 raw WAL copy) | 自动保留 |
| **依赖** | shell + 工具(cp/rsync) | OrioleDB extension |
| **生产 build** | 任何 PG | 仅 IS_DEV=1 |

**OrioleDB 的 `archive_library` 是 PG 18 新 API 的最佳实践** —— **比 `archive_command` 在每个维度上都更好**。

## 一句话总结

**OrioleDB archive_library = 'orioledb' 是 PG 18 archive_library API 的完整实现** —— preload 提前 schedule + 3 个 S3 worker 并行 + 直接 C 函数调用,比传统 `archive_command` 在每个维度上都更好。**实测触发 `SWITCH_LOGICAL_XID H2O` + `wal_joint_commit` + `archive 000000010000000000000004`** 全链路,**让 logical decoder 可以从 S3 拉回的 WAL 正确重组跨事务**。这是 OrioleDB raft 复制的完整路径:**Primary WAL → archive 到 S3 → Replica replay → logical decoder → ReorderBufferAssignChild → raft 流**。**OrioleDB S3 模式不只是 checkpoint,是 PG 数据库全云原生方案**。下一篇文章 **第 12 篇** 将实测 **S3 recovery** —— 从 mock S3 下沉 + WAL replay 的真实耗时,完成 OrioleDB 云原生最后一环。
