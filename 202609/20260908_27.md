## 背景  

> 系列第 12 篇。这次**再次打破了我之前的假设** —— 之前 8/11 篇我以为 OrioleDB S3 模式是 "全云原生 stateless"。**实测发现 OrioleDB S3 模式是 local + S3 mirror,本地必须有 base files**,不支持 "从 S3 完全恢复本地空数据"。  
> 测试方法: 启动 S3 mode PG,跑 workload,删本地 base files,看 OrioleDB 是否能从 S3 恢复。  

---

## 这篇文章要回答什么

之前 8/11 篇我推断:

> "OrioleDB S3 模式覆盖了 checkpoint + archive + redo + recovery 全链路,从 S3 可以完整恢复"

**实测发现反了**:

- ✅ OrioleDB S3 模式**覆盖了 checkpoint + archive** —— 单向本地→S3
- ❌ **OrioleDB 没实现 restore_library** —— recovery 需要外部工具
- ❌ **OrioleDB 不支持"从 S3 完全恢复本地空数据"** —— 必须本地有 base files
- ✅ **OrioleDB 是 "local + S3 mirror" 模式** —— 不是 stateless cloud-native

**这个发现改变了 OrioleDB 的工程定位** —— 它是**PG 主线 + S3 镜像备份**,**不是 AWS Aurora 那种 storage-compute 完全分离**。

## 一、关键实测发现

### 1.1 OrioleDB startup 的 S3 check

`src/s3/control.c:40-90` 的 `s3_check_control`:

```c
control_res = get_checkpoint_control_data(&control);     // 读本地 control
objectname = psprintf("data/%s", CONTROL_FILENAME);

if (s3_get_object(objectname, &buf, true) == S3_RESPONSE_NOT_FOUND)
{
    res = true;                                          // S3 没 control, OK
    goto cleanup;
}

if (!control_res)
{
    *errmsgp = psprintf("OrioleDB can be incompatible with the S3 bucket "
                        "because the control file exists on the S3 bucket");
    *errdetailp = psprintf("OrioleDB control file \"%s\" is absent", ...);
    goto cleanup;                                        // S3 有, 本地没 → FATAL
}

s3_control = (CheckpointControl *) buf.data;

if (control.controlIdentifier != s3_control->controlIdentifier)
{
    *errmsgp = psprintf("OrioleDB and the S3 bucket have files from "
                        "different instances and they are incompatible with "
                        "each other");
    goto cleanup;                                        // control 不一致 → FATAL
}
```

**实测 startup 时 OrioleDB 行为**:

```
PG startup
  │
  ├── 1. 读本地 orioledb_data/control
  │
  ├── 2. GET /data/orioledb_data/control from S3
  │
  ├── 3. S3 找不到 control (S3_RESPONSE_NOT_FOUND)
  │     → res = true, 用本地, OK
  │
  ├── 4. S3 有 control, 但本地没
  │     → FATAL "control file exists on the S3 bucket"
  │
  └── 5. S3 + 本地都有, 比对 controlIdentifier
        → 不一致: FATAL "different instances incompatible"
        → 一致: OK, 用本地 + S3 mirror
```

### 1.2 实测:FATAL 触发场景

**操作 1:删本地 base files + control**:
```bash
rm -f /home/pgtest18/pgdata_s3_arch/orioledb_data/1_base_*
rm -f /home/pgtest18/pgdata_s3_arch/orioledb_data/*.xid
rm -f /home/pgtest18/pgdata_s3_arch/orioledb_data/control
pg_ctl start
```

**结果**:
```
FATAL:  OrioleDB can be incompatible with the S3 bucket because the control file exists on the S3 bucket
DETAIL: OrioleDB control file "orioledb_data/control" is absent
```

**关键发现**:**OrioleDB 不会自动从 S3 拉 control** —— 必须本地有 control。

**操作 2:删 S3 control + 重启**:
```bash
rm -f /tmp/mock_s3_storage/orioledb_data_control
rm -f /tmp/mock_s3_storage/[0-9]_orioledb_data_control
pg_ctl start
```

**结果**: **仍然 FATAL** —— **本地 control 缺失**(即使 S3 也没)。

**操作 3:关 S3 模式启动,生成新本地 control**:
```bash
echo "orioledb.s3_mode = off" >> postgresql.conf
pg_ctl start
# → 成功,本地生成新 control
sed -i 's/s3_mode = off/s3_mode = on/' postgresql.conf
pg_ctl start
# → FATAL (controlIdentifier 与 S3 不一致)
```

**结果**:**即使关 S3 模式生成本地 control,再开 S3 模式启动也会 FATAL** —— 因为本地新 control 的 `controlIdentifier` 与 S3 残留 control 不同。

## 二、Mock S3 log 显示的 OrioleDB 行为

```
PUT /data/orioledb_data/s3_lock                                  (启动时 lock)
GET /data/orioledb_data/control                                 (启动时读 S3 control)
PUT /data/1/orioledb_data/control                              (启动时写新 control)
PUT /data/orioledb_data/control                                (启动时写 root control)
PUT /data/1/orioledb_data/1.xid                                (启动时写 XID 文件)
PUT /data/1/global/pg_control                                  (PG 主线 pg_control)
... (后续 base files)
```

**关键观察**:
1. OrioleDB startup 时 **GET S3 control** —— 用于一致性检查
2. 然后 **PUT 新 control 到 S3** —— 同步本地状态到 S3
3. **从未 GET 任何 base files** —— OrioleDB **不下载 base files,只用本地**

## 三、OrioleDB S3 模式的真实架构

```
┌─────────────────────────────────┐
│  OrioleDB startup               │
│                                 │
│  1. 读本地 base files           │
│     (必须存在)                  │
│                                 │
│  2. GET S3 control              │
│     (用于一致性检查)            │
│                                 │
│  3. 比对 controlIdentifier      │
│     (不一致 → FATAL)           │
│                                 │
│  4. 启动 S3 worker pool         │
│     (3 worker)                  │
│                                 │
│  5. 注册 archive callback       │
│     (PG 18 archive_library)    │
└─────────────────────────────────┘
         │
         ▼  S3 mirror sync (单向)
┌─────────────────────────────────┐
│  S3 Bucket                     │
│                                 │
│  /orioledb_data/control        │  ← sync
│  /1/orioledb_data/control      │  ← sync
│  /1/orioledb_data/<base_files> │  ← sync (checkpoint)
│  /1/orioledb_data/<xids>       │  ← sync
│  /1/orioledb_data/<checksums>  │  ← sync
│  /wal/000000010000000000000001 │  ← sync (WAL archive)
└─────────────────────────────────┘
```

**关键事实**:**OrioleDB S3 模式 = local primary + S3 mirror**。

## 四、真实 disaster recovery 流程

**正确做法** (基于实测):

**Step 1**:在 primary 节点用 S3 mode on 启动 PG
```bash
echo "orioledb.s3_mode = on" >> postgresql.conf
pg_ctl start
```

**Step 2**:OrioleDB 自动同步到 S3 (checkpoint + WAL archive)

**Step 3**:灾难发生,primary 节点丢失

**Step 4**:在备用节点启动 PG (用 OrioleDB extension)
```bash
# 在备用节点 (新机器)
# 1. 装 OrioleDB extension
make USE_PGXS=1 PG_CONFIG=... install

# 2. 用 S3 mode off initdb (生成 base files)
echo "orioledb.s3_mode = off" >> postgresql.conf
pg_ctl start  # OK, 生成空 base files

# 3. (可选)用 pg_basebackup 从 S3 拉 base files
#    (OrioleDB 没实现 restore_library, 必须用 PG 主线 pg_basebackup)
pg_basebackup -D /backup/  # 拉 backup

# 4. (可选) 用 restore_command 从 S3 拉 WAL
echo "restore_command = 'aws s3 cp s3://my-bucket/wal/%f %p'" >> postgresql.conf

# 5. 启动 PG (用 S3 mode off 即可, S3 模式不是必需)
pg_ctl start
```

**结论**:**OrioleDB S3 模式不是 cloud-native,只是 backup** —— **真正的 recovery 仍依赖 PG 主线工具 + 外部 S3 工具**。

## 五、与 AWS Aurora / Snowflake 对比

| 维度 | AWS Aurora | Snowflake | OrioleDB |
|---|---|---|---|
| **Storage 位置** | S3 (永远在 S3) | S3 (永远在 S3) | 本地 + S3 mirror |
| **Compute 状态** | stateless | stateless | **必须有本地 state** |
| **冷启动时间** | 秒级 | 秒级 | **分钟级**(取决于 base files) |
| **跨 region 灾备** | 内建 (RDS) | 内建 | **需手动 + 外部工具** |
| **Cloud-native** | ✅ | ✅ | ❌ |

**OrioleDB 的 S3 模式** = **PG + S3 备份**,**不是 cloud-native DB**。

## 六、OrioleDB S3 模式的真实价值

虽然不是 cloud-native,OrioleDB S3 模式还是有价值的场景:

| 场景 | 价值 | 优势 |
|---|---|---|
| **灾备 (DR)** | S3 跨 region 镜像 | base files 自动同步 |
| **时间点恢复 (PITR)** | WAL archive to S3 | 可 replay 到任意时间点 |
| **桶快照** | S3 versioning | 备份 + 防误删 |
| **多实例接管** | S3 mirror + controlIdentifier | 灾难时切换实例 |
| **跨云复制** | S3 cross-region replication | 备份到不同云 |

**OrioleDB S3 模式的真实定位** = **PG 主线的 S3-mirrored backup**,**AWS S3 兼容**,**需要外部 recovery 工具配合**。
