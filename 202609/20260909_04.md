## 第一部分: zheap 是什么

### 1.1 项目背景

zheap 是 **EnterpriseDB (EDB)** 在 2019-2021 年间开发的 PostgreSQL 补丁集,目标是解决 heap 表的 MVCC 痛点。

**关键事实**:
- **代码位置**: `/root/new/src/zheap/`
- **分支**: `zheap_undo_record_set_pg_14.1` (基于 PG 14.1)
- **最后提交**: 2021-12-14 (daf86a9)
- **核心代码**: 30KB (zheapam.c 9499 行 + tpd.c 3283 行 + zheapam_handler.c 2089 行 + zundo.c 1912 行)
- **状态**: 未被 PG 主线接受,补丁集停滞

### 1.2 核心设计:undo-based tuple header

传统 heap tuple header 存储了完整的 MVCC 信息:

| 字段 | 大小 | 说明 |
|---|---|---|
| `t_xmin` | 4 字节 | 插入事务 ID |
| `t_xmax` | 4 字节 | 删除/更新事务 ID |
| `t_cid` | 4 字节 | 命令 ID (cmin/cmax) |
| `t_infomask` | 2 字节 | 标志位 |
| `t_infomask2` | 2 字节 | 扩展标志位 |
| `t_hoff` | 1 字节 | 头部偏移 |
| **合计** | **17 字节** | |

zheap 的 `ZHeapTupleHeaderData` 只有:

```c
typedef struct ZHeapTupleHeaderData
{
    uint16  t_infomask2;   /* 属性数量 + 事务槽 + 标志 */
    uint16  t_infomask;     /* 标志位 */
    uint8   t_hoff;         /* 头部大小 */
    bits8   t_bits[FLEXIBLE_ARRAY_MEMBER];  /* NULL 位图 */
} ZHeapTupleHeaderData;
```

**固定部分只有 5 字节** —— 少了 12 字节。

**交易信息去哪了?**
- **xmin/xmax/cmin/cmax** → 存入 undo 日志
- **事务槽 ID** → 存入 `t_infomask2` 的高 5 位 (`ZHEAP_XACT_SLOT`)

### 1.3 页面结构:TransInfo 槽 + TPD 溢出

zheap 页面 opaque 区域存储的是 `TransInfo` 数组,而不是传统 heap 的 `pd_lower/pd_upper`:

```c
typedef struct TransInfo
{
    FullTransactionId fxid;     /* 8 字节:完整事务 ID */
    UndoRecPtr       urec_ptr;  /* 8 字节:undo 记录指针 */
} TransInfo;
```

**每个 TransInfo 占 16 字节**,存储:
- 最近修改该页 tuples 的事务的 FullTransactionId
- 对应的 undo 记录位置

**页面级事务槽数量**: `ZHEAP_PAGE_TRANS_SLOTS` (定义在 `bufpage.h`,典型值 8-16)

**当槽不够用怎么办?** → TPD (Transaction Pointer Directory) 溢出页。

### 1.4 TPD:事务槽的"扩容条"

`tpd.c` (3283 行) 实现了 TPD 机制:

```
┌─────────────────────────────────────┐
│ zheap 页面                            │
│ ┌─────────────────────────────────┐ │
│ │ PageHeaderData                  │ │
│ ├─────────────────────────────────┤ │
│ │ ItemIdData[1..n]               │ │
│ ├─────────────────────────────────┤ │
│ │ Tuple Data                      │ │
│ └─────────────────────────────────┘ │
│ ┌─────────────────────────────────┐ │
│ │ ZHeapPageOpaqueData             │ │
│ │ TransInfo[0..ZHEAP_PAGE_TRANS_SLOTS-1] │
│ └─────────────────────────────────┘ │
└─────────────────────────────────────┘
         │
         │ 槽不够用时
         ▼
┌─────────────────────────────────────┐
│ TPD 页面 (块 N+1)                     │
│ ┌─────────────────────────────────┐ │
│ │ TPD Header                      │ │
│ ├─────────────────────────────────┤ │
│ │ TPD Entry 0 (扩展槽映射)         │ │
│ │ TPD Entry 1                     │ │
│ │ ...                             │ │
│ └─────────────────────────────────┘ │
└─────────────────────────────────────┘
```

**TPD Entry 结构** (tpd.c):
- 存储页面上所有 tuple 的事务槽映射
- 当 tuple 的事务槽 > `ZHEAP_PAGE_TRANS_SLOTS` 时,使用 TPD 槽
- TPD 页面存储在 zheap 文件内部,由 meta page 跟踪

**关键设计**:
- 每个 zheap 页面最多需要 2 个 TPD buffer (正常 1 个,跨页更新时 2 个)
- TPD 页面通过 meta page (`ZHeapMetaPageData`) 管理
- `pd_flags` 中的 `PD_PAGE_HAS_TPD_SLOT` 标记页面是否使用 TPD

## 第二部分: 9 种 undo 记录

### 2.1 undo 记录类型

zheap 定义了 9 种 undo 记录 (`zheapam_undo.h:27-35`):

```c
typedef enum undorectype
{
    UNDO_ZHEAP_INSERT,           /* 插入 */
    UNDO_ZHEAP_MULTI_INSERT,     /* 多 tuple 插入 */
    UNDO_ZHEAP_DELETE,           /* 删除 */
    UNDO_ZHEAP_INPLACE_UPDATE,   /* in-place 更新 */
    UNDO_ZHEAP_UPDATE,           /* 非 in-place 更新 */
    UNDO_ZHEAP_XID_LOCK_ONLY,    /* 仅锁 */
    UNDO_ZHEAP_XID_LOCK_FOR_UPDATE, /* 锁后更新 */
    UNDO_ZHEAP_XID_MULTI_LOCK_ONLY, /* 多 locker */
    UNDO_ZHEAP_ITEMID_UNUSED     /* itemid 标记为 unused (vacuum) */
} undorectype;
```

**每种记录存储的内容** (`zheap_undo_record.c`):

```c
typedef struct UndoRecordHeader
{
    uint8       urec_info;       /* 标志位:哪些字段存在 */
    Oid         urec_reloid;     /* 关系 OID */
    TransactionId urec_prevxid;   /* 前一个修改事务 */
    TransactionId urec_xid;       /* 当前事务 */
    CommandId   urec_cid;         /* 命令 ID */
} UndoRecordHeader;
```

**可变部分** (根据 `urec_info` 标志):
- `UndoRecordRelationDetails`: fork number (如果不是 MAIN_FORKNUM)
- `UndoRecordBlock`: blkprev + block number + offset (如果涉及数据块)
- `UndoRecordPayload`: payload 长度 + tuple 长度
- payload 数据 + tuple 数据

### 2.2 undo 链:blkprev + xid 双索引

zheap 的 undo 记录通过两个指针链接:

1. **blkprev (block previous)**: 同一个 block 上的上一个 undo 记录
   - 用于 vacuum/prune 快速定位需要处理的 undo
   - 存储在 `UndoRecordBlock.urec_blkprev`

2. **xid 链**: 同一个事务的所有 undo 记录
   - 通过 `urec_xid` 和 `urec_prevxid` 链接
   - 用于事务回滚时快速找到所有 undo

**为什么需要双索引?**
- **blkprev**: vacuum 时只需要处理某个 block 上的 undo
- **xid 链**: 回滚时需要处理事务的所有 undo

### 2.3 undo 记录的生命周期

```
插入 tuple → 写 UNDO_ZHEAP_INSERT → 关联到页面的 TransInfo 槽
    ↓
更新 tuple → 写 UNDO_ZHEAP_UPDATE → 新 TransInfo 槽
    ↓
事务提交 → undo 记录标记为"可丢弃" ( oldestXidWithEpochHavingUndo )
    ↓
vacuum → 清理过期的 undo 记录 + 回收事务槽
```

**关键点**: zheap 的 undo 记录在事务提交后**不会立即清理**,而是保留到:
1. 该 tuple 对所有快照都可见
2. 或者 oldestXidWithUndo 超过该 undo 的 xid

## 第三部分: 与 undam/OrioleDB/zedstore 的对比

### 3.1 zheap vs undam

| 特性 | zheap | undam |
|---|---|---|
| **定位** | PG 补丁集 (fork) | PG extension |
| **PG 版本** | 14.1 | 12 |
| **undo 存储** | PG 主线 undo 子系统 | 自有 undo 链 |
| **TPD** | ✅ 有 | ❌ 无 |
| **事务槽** | 页面级 TransInfo 数组 | UndamRelInfo L1 list |
| **更新策略** | in-place + undo chain | in-place + undo chain |
| **TOAST** | ✅ 有 (zheaptoast.c) | ❌ 无 (fixed-size chunk) |
| **WAL** | PG 标准 WAL | GenericXLog |
| **状态** | 2021 年停滞 | 2020 年停滞 |

**关键差异**:
1. **zheap 使用 PG 主线 undo 子系统**,而 undam 自己实现 undo 链
2. **zheap 有 TPD 溢出机制**,undam 没有
3. **zheap 的 tuple header 更小**(5 字节 vs undam 的固定 header)

### 3.2 zheap vs OrioleDB

| 特性 | zheap | OrioleDB |
|---|---|---|
| **定位** | 行存 undo-based heap | 列存 BTree |
| **PG 版本** | 14.1 (补丁) | 18.6 (extension) |
| **存储引擎** | 修改 page layout | 完全自有 BTree |
| **undo** | PG 主线 undo | 自有 undo (5 种 image) |
| **并发控制** | 事务槽 + undo | 64-bit OXid + COMMITSEQNO |
| **buffer 管理** | PG buffer manager | OBuffer + mmap |
| **状态** | 2021 年停滞 | 2026 年活跃开发 |

**关键差异**:
1. **zheap 是行存**,OrioleDB 是列存 —— 完全不同的定位
2. **zheap 基于 PG buffer manager**,OrioleDB 绕过 PG buffer manager
3. **zheap 用 PG 主线 undo**,OrioleDB 自己实现 undo

### 3.3 zheap vs heap (传统)

| 特性 | zheap | heap |
|---|---|---|
| **tuple header** | 5 字节固定 | 23 字节固定 |
| **MVCC 信息** | undo 日志 | tuple header (xmin/xmax/cmin/cmax) |
| **HOT 更新** | 不需要 (in-place + undo) | 需要 (避免 index 更新) |
| **vacuum** | 清理 undo + 回收槽 | 清理 dead tuples + 重建 FSM |
| **bloat** | 低 (undo 代替 heap tuple) | 高 (dead tuples 占用空间) |
| **clog 写入** | 减少 (事务信息在 undo) | 标准 (每个 tuple 写 xmin/xmax) |
| **TPD** | ✅ 有 | ❌ 无 |
| **事务槽竞争** | 低 (overflow to TPD) | 高 (固定槽数) |

## 第四部分: 为什么 zheap 没有进入 PG 主线

### 4.1 README.zheap 中列出的待办

`README.zheap` 明确列出了 5 个未解决问题:

1. **并行 INSERT 不支持** —— "parallel workers raise ERROR when inserting undo records"
2. **discard worker 缺失** —— "essential for zheap, unlike [3]"
3. **undo 记录序列化需要改进** —— "Improve/rework serialization"
4. **zheap 特定的回归测试缺失** —— "Add zheap specific regression tests from [1]"
5. **与 PG master 分支的合并需要审查** —— "Review if the merge with postgres master is correct"

### 4.2 设计层面的 3 个未解问题

**问题 1: undo 日志的持久化策略**

zheap 依赖 PG 主线 undo 子系统,但 undo 日志的生命周期管理复杂:
- 何时可以安全丢弃 undo 记录?
- 如果 discard worker 不及时,undo 日志会无限增长
- 与 PG 的 `oldestXidWithEpochHavingUndo` 机制如何交互?

**问题 2: TPD 的性能影响**

TPD 溢出页虽然解决了事务槽不足的问题,但带来了新的开销:
- 每次访问 tuple 可能需要额外读取 TPD 页面
- TPD 页面竞争 (多个 heap 页面共享 TPD)
- 跨页更新时需要锁定 2 个 TPD buffer

**问题 3: 与 PG 18+ TableAmRoutine API 的兼容性**

zheap 的 `zheapam_methods` (zheapam_handler.c:2029-2083) 只实现了 PG 14 的 API:

### 4.3 代码层面的 2 个已知缺陷

**缺陷 1: 并行 INSERT 报错**

`README.zheap`:
> "Implement insertion of UNDO records by parallel workers, so that parallel INSERT works (currently it raises ERROR)."

**原因**: zheap 的 undo 记录插入不是线程安全的,并行 worker 无法同时写 undo。

**缺陷 2: 未测试的组合**

`README.zheap`:
> "Untested combinations of autoconf and PostgreSQL versions are not..."

zheap 只在 PG 14.1 上测试过,其他版本未经验证。

### 4.4 与 PG 主线演化的冲突

**冲突 1: undo 子系统的重构**

PG 14 之后,undo 子系统经历了重大重构:
- `UndoRecord` 格式变化
- `UndoLog` 管理机制变化
- zheap 的 `PrepareZHeapUndoRecord` 基于旧版 undo API

**冲突 2: TableAmRoutine API 的快速演化**

从 PG 14 到 PG 18,TableAmRoutine 增加了 14 个新回调:
- zheap 需要逐个适配
- 每个新回调都需要实现 + 测试

**冲突 3: 并行 vacuum 的演进**

PG 18 增强了并行 vacuum 能力,但 zheap 的 vacuum 机制依赖 undo 清理,与主线并行 vacuum 不兼容。

## 五、与 zedstore/OrioleDB/undam 的完整对比

|---|---|---|---|---|
| **zedstore** | PG fork | 13 (2020) | 停滞 | 列存 + 行存混合 |
| **OrioleDB** | PG extension | 18 (2026) | 活跃 | 列存 BTree |
| **undam** | PG extension | 12 (2020) | 停滞 | 行存 undo-based |
| **zheap** | PG patch | 14 (2021) | 停滞 | 行存 undo-based |

| 特性 | zheap | undam | OrioleDB | heap |
|---|---|---|---|---|
| **undo 存储** | PG 主线 undo | 自有 undo 链 | 自有 undo (5 种 image) | 无 |
| **undo 记录类型** | 9 种 | 4 种 (insert/delete/update/lock) | 5 种 (compact/split/merge/diff) | N/A |
| **undo 索引** | blkprev + xid 双链 | 单链 | 页面级 LSN | N/A |
| **in-place 更新** | ✅ 支持 | ✅ 支持 | ✅ 支持 | ❌ 不支持 (HOT 除外) |
| **vacuum** | 清理 undo + 回收槽 | 清理 undo 链 | 清理 old tuples | 清理 dead tuples |

### 5.3 tuple header 对比

| 字段 | heap | zheap | undam | OrioleDB |
|---|---|---|---|---|
| **xmin** | 4 字节 (tuple header) | undo | undo | tuple header |

| **cmin/cmax** | 4 字节 (tuple header) | undo | undo | N/A |

| **固定 header** | 23 字节 | **5 字节** | ~10 字节 | ~15 字节 |
| **节省空间** | - | **78%** | ~60% | ~35% |

### 5.4 页面结构对比

| 特性 | heap | zheap | OrioleDB |
|---|---|---|---|
| **页面大小** | 8KB | 8KB | 可变 (BTree page) |
| **opaque 区域** | pd_lower/pd_upper/PD_VISIBLE | TransInfo[] | BTree page header |
| **事务信息** | tuple header | TransInfo + undo | OXid + COMMITSEQNO |
| **溢出机制** | N/A | TPD 页面 | N/A |
| **空闲空间管理** | FSM | 无 (依赖 undo) | OBuffer |

## 六、zheap 的关键代码路径

### 6.1 插入路径

```c
// zheapam.c:120-145
zheap_prepare_insert() {
    // 1. 分配事务槽 (页面级 TransInfo 或 TPD)
    // 2. 准备 undo 记录 (UNDO_ZHEAP_INSERT)
    // 3. 设置 tuple header (infomask + infomask2)
    // 4. 写 WAL (log_zheap_insert)
    // 5. 插入 tuple 到页面
}
```

**关键步骤**:
1. **分配事务槽**: `GetTransactionSlotInfo()` 获取页面级 TransInfo 槽或 TPD 槽
2. **准备 undo**: `zheap_prepare_undo_insert()` 创建 `UnpackedUndoRecord`
3. **序列化 undo**: `PrepareZHeapUndoRecord()` 将 `UnpackedUndoRecord` 转为 `UndoRecData` 链
4. **写 WAL**: `log_zheap_insert()` 记录 tuple + undo 信息

### 6.2 更新路径

```c
// zheapam.c:zheap_update()
// 1. 检查是否可以 in-place 更新 (事务槽复用 + TPD 槽复用)
// 2. 如果可以 in-place:
//    - 写 UNDO_ZHEAP_INPLACE_UPDATE
//    - 修改 tuple header (设置 ZHEAP_INPLACE_UPDATED)
// 3. 如果不可以 in-place:
//    - 写 UNDO_ZHEAP_UPDATE
//    - 插入新 tuple
//    - 标记旧 tuple 为 ZHEAP_UPDATED
```

**in-place 更新的条件** (`zheap.h:27-28`):
```c
#define NUM_BLOCKS_FOR_NON_INPLACE_UPDATES 200
// 关系大小 < 200 blocks 时才允许 non-inplace 更新
```

### 6.3 vacuum 路径

```c
// prunezheap.c:prune_zheap()
// 1. 扫描页面,找到 dead/unused tuples
// 2. 对 dead tuples:写 UNDO_ZHEAP_ITEMID_UNUSED
// 3. 回收 itemid (标记为 unused)
// 4. 清理过期的 undo 记录
// 5. 回收事务槽 (如果不再需要)
```

**关键创新**: zheap 的 vacuum 不需要重建 FSM,因为:
- dead tuples 的 itemid 被标记为 unused,可以立即重用
- undo 记录代替了 dead tuple 的存储

---

## 七、zheap 的 3 个核心创新

### 7.1 创新 1: 5 字节 tuple header

**传统 heap**: 23 字节固定 header (xmin/xmax/cmin/cmax/infomask/infomask2/hoff)

**zheap**: 5 字节固定 header (infomask2/infomask/hoff) + 事务信息移到 undo

**收益**:
- 每 tuple 节省 18 字节
- 1M 行表节省 18MB
- 减少 page 分裂频率

### 7.2 创新 2: TPD 事务槽溢出

**问题**: 页面级事务槽数量固定 (典型值 8-16),当多个事务同时修改同一页面时槽不够用。

**zheap 解决方案**: TPD 溢出页
- 在 zheap 文件内部存储 TPD 页面
- TPD entry 存储 tuple → 事务槽的映射
- Meta page 跟踪 TPD 页面范围

**收益**:
- 消除事务槽竞争
- 支持高并发单页更新

### 7.3 创新 3: undo-based vacuum

**传统 heap vacuum**:
1. 扫描页面,找到 dead tuples
2. 将 dead tuples 的 itemid 标记为 unused
3. 重建 FSM (Free Space Map)
4. 清理 clog 中的事务状态

**zheap vacuum**:
1. 扫描页面,找到 dead/unused tuples
2. 写 UNDO_ZHEAP_ITEMID_UNUSED (记录 itemid 被回收)
3. 清理过期的 undo 记录
4. 回收事务槽

**收益**:
- 不需要重建 FSM (undo 代替了 dead tuple 的存储)
- 减少 clog 写入 (事务信息在 undo,不需要写 xmin/xmax)

## 九、一句话总结

**zheap 是 EnterpriseDB 对 PostgreSQL heap 表的一次「undo-based MVCC」重构实验 —— 通过 5 字节 tuple header + TPD 事务槽溢出 + 9 种 undo 记录,实现了 78% 的 tuple header 空间节省和更低的 vacuum 开销;但因为它停留在 2021 年的 PG 14.1 补丁集阶段,缺少 discard worker、并行 INSERT 支持、以及与 PG 18+ TableAmRoutine API 的适配,最终没有被主线接受。zheap 的核心创新 (undo-based tuple header、TPD 溢出) 影响了后续的 undo 子系统设计,但其补丁集的形态注定无法在现代 PG 上直接使用。**
