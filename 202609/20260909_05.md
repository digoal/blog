## 一、undo 日志的"内存模型"

### 1.1 undo 段 (Undo Log Segment)

zheap 的 undo 日志按段组织,每个段的大小:

```c
// undolog.h:44-50
#define UNDOSEG_SIZE 128          // 默认: 128 个块 = 1MB
#define UNDOSEG_SIZE 4            // 备选: 4 个块 = 32KB
#define UndoLogSegmentSize ((size_t) BLCKSZ * UNDOSEG_SIZE)
```

**典型配置**: `UNDOSEG_SIZE = 128` → 每个 undo 段 **1MB**。

### 1.2 undo 记录大小

每个 undo 记录由可变长度的链组成:

```c
// 基础头 (所有记录都有)
typedef struct UndoRecordHeader
{
    uint8       urec_info;       // 1 字节:标志位
    Oid         urec_reloid;     // 4 字节:关系 OID
    TransactionId urec_prevxid;   // 4 字节:前一个修改事务
    TransactionId urec_xid;       // 4 字节:当前事务
    CommandId   urec_cid;         // 4 字节:命令 ID
} UndoRecordHeader;
#define SizeOfUndoRecordHeader (offsetof(UndoRecordHeader, urec_cid) + sizeof(CommandId))
// = 1 + 4 + 4 + 4 + 4 = 17 字节 (可能有对齐填充,实际约 20-24 字节)

// 可选:关系详情 (非 MAIN_FORKNUM 时有)
typedef struct UndoRecordRelationDetails
{
    ForkNumber  urec_fork;       // 1 字节
} UndoRecordRelationDetails;
#define SizeOfUndoRecordRelationDetails (offsetof(UndoRecordRelationDetails, urec_fork) + sizeof(uint8))
// = 1-4 字节

// 可选:块信息 (涉及数据块时有)
typedef struct UndoRecordBlock
{
    UndoRecPtr  urec_blkprev;    // 8 字节:同一块的上一个 undo
    BlockNumber urec_block;      // 4 字节:块号
    OffsetNumber urec_offset;    // 2 字节:偏移号
} UndoRecordBlock;
#define SizeOfUndoRecordBlock (offsetof(UndoRecordBlock, urec_offset) + sizeof(OffsetNumber))
// = 8 + 4 + 2 = 14 字节 (可能有对齐填充,实际约 16 字节)

// 可选:payload 信息
typedef struct UndoRecordPayload
{
    uint16      urec_payload_len;  // 2 字节
    uint16      urec_tuple_len;    // 2 字节
} UndoRecordPayload;
#define SizeOfUndoRecordPayload (offsetof(UndoRecordPayload, urec_tuple_len) + sizeof(uint16))
// = 4 字节
```

### 1.3 各类型 undo 记录的大小估算

| 记录类型 | 典型大小 | 说明 |
|---|---|---|
| `UNDO_ZHEAP_INSERT` | 40-100 字节 | header + block + payload (tuple 数据) |
| `UNDO_ZHEAP_MULTI_INSERT` | 80-200 字节 | header + block + payload (多个 tuple) |
| `UNDO_ZHEAP_DELETE` | 40-80 字节 | header + block (无 payload) |
| `UNDO_ZHEAP_INPLACE_UPDATE` | 60-150 字节 | header + block + payload (旧值) |
| `UNDO_ZHEAP_UPDATE` | 100-300 字节 | header + block + payload (旧 tuple + 新 tuple) |
| `UNDO_ZHEAP_XID_LOCK_ONLY` | 30-50 字节 | header + block (最小记录) |
| `UNDO_ZHEAP_XID_LOCK_FOR_UPDATE` | 50-100 字节 | header + block + payload |
| `UNDO_ZHEAP_XID_MULTI_LOCK_ONLY` | 40-80 字节 | header + block |
| `UNDO_ZHEAP_ITEMID_UNUSED` | 30-50 字节 | header + block (vacuum 标记) |

**平均大小估算**: 约 60-80 字节/记录。

## 二、undo 日志增长场景分析

### 场景 1: 高并发更新 (最坏情况)

**假设**: 单表,1M 行,每行每秒更新一次,持续 1 小时。

**计算**:
- 每秒更新次数: 1,000,000 次
- 每次更新产生 1 个 `UNDO_ZHEAP_UPDATE` (约 200 字节)
- 每秒 undo 日志增长: 1,000,000 × 200 字节 = **200 MB/s**
- 1 小时增长: 200 MB/s × 3600 s = **720 GB**

**结论**: 这个场景下 undo 日志会**爆炸式增长**。

**现实限制**: 实际上受限于:
1. undo 段大小 (1MB/段) → 需要 720,000 个段
2. 磁盘空间 → 720 GB 需要大量磁盘
3. 事务提交频率 → 如果事务每秒提交,undo 记录可以立即标记为"可丢弃"

### 场景 2: 长事务 (最危险场景)

**假设**: 一个长事务持续运行 24 小时,期间修改 100万行。

**计算**:
- 总修改次数: 1,000,000 次
- 每次修改产生 1 个 undo 记录 (约 200 字节)
- 总 undo 日志: 1,000,000 × 200 字节 = **200 MB**

**关键点**: 这 200 MB 的 undo 记录在事务提交前**都不能丢弃**!

**影响**:
- undo 日志占用 200 MB 磁盘空间
- 其他事务不能访问这些 tuple (直到长事务提交/回滚)
- 可能导致 undo 日志段无法回收

### 场景 3: 批量更新 (可控场景)

**假设**: 每小时批量更新 10万行,每行更新一次。

**计算**:
- 每小时更新次数: 100,000 次
- 每次更新产生 1 个 undo 记录 (约 200 字节)
- 每小时 undo 日志增长: 100,000 × 200 字节 = **20 MB**
- 每天增长: 20 MB × 24 = **480 MB**

**结论**: 这个场景下 undo 日志增长**可控**,但需要 discard worker 及时清理。

## 三、undo 生命周期管理

### 3.1 undo 记录的生命周期

```
[创建] → [活跃] → [提交/回滚] → [可丢弃] → [丢弃]
```

**关键阶段**:

1. **活跃 (Active)**: 事务执行期间,undo 记录必须保留
2. **提交后 (Committed)**: 事务提交后,undo 记录可以标记为"可丢弃"
3. **可丢弃 (Discardable)**: 当所有快照都看不到该 undo 对应的 tuple 时
4. **丢弃 (Discarded)**: undo 记录被物理删除,空间回收

### 3.2 可丢弃条件

zheap 的 undo 记录可丢弃条件 (从代码推断):

```c
// zheapam.c:5054-5057
// "be discarded. We cannot use any assert for checking is the log
// is actually discarded, since UndoFetchRecord can return NULL
// for the records which are not yet discarded but are about to be
// discarded."
```

**推断的可丢弃条件**:
1. 事务已提交
2. 该 undo 对应的 tuple 对所有活跃快照都可见 ( oldestXidWithEpochHavingUndo )
3. 没有其他事务依赖该 undo 记录

### 3.3 discard worker (缺失!)

`README.zheap` 明确说明:
> "Implement discard worker - unlike [3], it's essential for the zheap."

**这意味着**: zheap **没有后台 discard worker**!

**后果**:
- undo 日志的清理依赖 vacuum
- 如果 vacuum 不及时,undo 日志会无限增长
- 长事务会阻塞 undo 日志回收

### 3.4 undo 日志回收机制

从代码推断,undo 日志回收通过以下方式:

1. **vacuum 时清理**: `lazy_vacuum_zheap_rel` 会清理过期的 undo
2. **事务提交时标记**: 提交的事务的 undo 记录可以标记为"可丢弃"
3. **oldestXidWithUndo 机制**: PG 主线的 `oldestXidWithEpochHavingUndo` 决定哪些 undo 可以丢弃

**问题**: 没有后台 worker 主动清理,只能被动等待 vacuum。

## 四、undo 日志增长控制策略

### 4.1 现有控制机制

从代码推断,zheap 可能有的控制机制:

| 机制 | 说明 | 状态 |
|---|---|---|
| `UNDOSEG_SIZE` | 每个 undo 段大小 (1MB/4MB) | ✅ 有配置 |
| `oldestXidWithUndo` |  oldestXidWithUndo 机制 | ✅ 依赖 PG 主线 |
| vacuum | 清理过期 undo | ✅ 有实现 |
| discard worker | 后台主动清理 | ❌ **缺失** |

### 4.2 建议的增长控制策略

如果要在生产环境使用 zheap,需要:

1. **监控 undo 日志大小**: 定期检查 `pg_stat_undo_chunks` / `pg_stat_undo_records`
2. **调整 `UNDOSEG_SIZE`**: 根据 workload 调整段大小
3. **限制长事务**: 避免长事务阻塞 undo 回收
4. **增加 vacuum 频率**: 更频繁的 vacuum 可以及时清理 undo
5. **实现 discard worker**: 这是 README.zheap 明确指出的缺失功能

## 五、与 heap 的对比

| 特性 | zheap | heap |
|---|---|---|
| **undo 日志增长** | 中-高 (取决于更新频率) | 低 (没有独立 undo 日志) |
| **undo 清理时机** | vacuum / 事务提交 | 自动 (clog + vacuum) |
| **长事务影响** | 高 (undo 不能回收) | 中 (tuple 不能回收) |
| **批量更新影响** | 高 (undo 日志快速增长) | 低 (直接更新 tuple) |
| **vacuum 压力** | 中 (需要清理 undo) | 高 (需要清理 dead tuples) |
| **空间浪费** | 中 (undo 日志) | 高 (dead tuples + bloat) |

## 六、结论

**zheap 的 undo 日志增长是可控的,但需要 discard worker**:

1. **单条 undo 记录**: 40-300 字节 (取决于记录类型)
2. **每秒 1000 次更新**: 约 200 KB/s undo 增长
3. **长事务 (24h)**: 可能导致 200 MB+ undo 无法回收
4. **批量更新 (10万行/小时)**: 约 20 MB/h 增长

**关键风险**:
- 没有 discard worker → undo 日志依赖 vacuum 清理
- 长事务 → 阻塞 undo 回收
- 高并发更新 → undo 日志快速增长

**建议**:
1. 实现 discard worker (README.zheap 已指出)
2. 监控 undo 日志大小
3. 限制长事务运行时间
4. 增加 vacuum 频率
