## 一、vacuum 机制概述

### 1.1 heap vacuum (传统)

传统 heap 的 vacuum 是一个**单阶段过程**:

```
1. 扫描 heap 页面,找到 dead tuples
2. 清理 dead tuples (标记 itemid 为 unused)
3. 重建 FSM (Free Space Map)
4. 清理索引中的 dead 条目
5. 清理 clog 中的事务状态
```

**关键文件**:
- `src/backend/commands/lazyvacuum.c` —— 主逻辑
- `src/backend/access/heap/pruneheap.c` —— page pruning

### 1.2 zheap vacuum (两阶段)

zheap 的 vacuum 是一个**两阶段过程**:

```
第一阶段:
1. 扫描 heap 页面,找到 dead tuples
2. 写 UNDO_ZHEAP_ITEMID_UNUSED (记录 itemid 被回收)
3. 标记 itemid 为 unused
4. 修复页面碎片

第二阶段:
5. 清理索引中的 dead 条目
```

**关键文件**:
- `src/backend/commands/zvacuumlazy.c` —— 主逻辑
- `src/backend/access/zheap/prunezheap.c` —— page pruning
- `src/backend/access/zheap/prunetpd.c` —— TPD pruning

## 二、vacuum 流程对比

### 2.1 heap vacuum 流程

```c
// lazyvacuum.c: lazy_vacuum_heap()
// 1. 扫描 heap 页面
// 2. 对每个页面:
//    a. 找到 dead tuples
//    b. 标记 itemid 为 unused
//    c. 修复页面碎片
//    d. 写 WAL (if needed)
// 3. 清理索引
// 4. 清理 clog
// 5. 更新统计信息
```

**heap vacuum 的关键步骤**:

1. **扫描阶段**: 使用 `heap_page_prune` 识别 dead tuples
2. **清理阶段**: 标记 itemid 为 unused,修复碎片
3. **索引清理**: 删除索引中指向 dead tuples 的条目
4. **clog 清理**: 清理事务状态

**heap vacuum 的瓶颈**:
- 需要扫描整个表 (即使页面是全可见的)
- 需要清理索引 (可能很慢)
- 需要重建 FSM (额外的 I/O)

### 2.2 zheap vacuum 流程

```c
// zvacuumlazy.c: lazy_vacuum_zheap_rel()
// 第一阶段: vacuum heap
// 1. 扫描 zheap 页面
// 2. 对每个页面:
//    a. 找到 dead tuples
//    b. 分配事务槽
//    c. 写 UNDO_ZHEAP_ITEMID_UNUSED
//    d. 标记 itemid 为 unused
//    e. 修复页面碎片
//    f. 写 WAL (包括 undo 信息)

// 第二阶段: vacuum index
// 3. 清理索引中的 dead 条目
```

**zheap vacuum 的关键步骤**:

1. **扫描阶段**: 使用 `zheap_page_prune` 识别 dead tuples
2. **清理阶段**: 
   - 分配事务槽 (页面级或 TPD)
   - 写 UNDO_ZHEAP_ITEMID_UNUSED (记录 itemid 被回收)
   - 标记 itemid 为 unused
   - 修复碎片
3. **索引清理**: 删除索引中指向 dead tuples 的条目

**zheap vacuum 的创新**:
- **写 undo 记录**: 记录 itemid 被回收,支持回滚
- **不需要重建 FSM**: undo 代替了 dead tuple 的存储
- **减少 clog 写入**: 事务信息在 undo,不需要写 xmin/xmax

## 三、vacuum 详细对比

### 3.1 扫描阶段对比

| 特性 | heap | zheap |
|---|---|---|
| **扫描方式** | 顺序扫描 + visibility map 跳过 | 顺序扫描 + visibility map 跳过 |
| **dead tuple 识别** | `heap_page_prune` | `zheap_page_prune` |
| **全可见页面** | 跳过 (VM 标记) | 跳过 (VM 标记) |
| **扫描开销** | 低 | 低 (类似) |

**结论**: 扫描阶段 zheap 和 heap 几乎相同。

### 3.2 清理阶段对比

| 特性 | heap | zheap |
|---|---|---|
| **dead tuple 处理** | 标记 itemid 为 unused | 写 UNDO_ZHEAP_ITEMID_UNUSED + 标记 itemid 为 unused |
| **事务槽分配** | 不需要 | 需要 (页面级 TransInfo 或 TPD) |
| **undo 记录** | 不需要 | 需要 (UNDO_ZHEAP_ITEMID_UNUSED) |
| **WAL 记录** | `xl_heap_clean` | `xl_zheap_unused` + undo 信息 |
| **FSM 重建** | 需要 | 不需要 |
| **碎片修复** | `PageRepairFragmentation` | `ZPageRepairFragmentation` |

**关键差异**:
1. **zheap 需要分配事务槽** —— 每次 vacuum 都需要一个事务槽来记录 undo
2. **zheap 需要写 undo 记录** —— 额外的 I/O 开销
3. **zheap 不需要重建 FSM** —— 节省 I/O,但需要维护 undo 日志

### 3.3 索引清理对比

| 特性 | heap | zheap |
|---|---|---|
| **清理时机** | 第二阶段 (清理 heap 后) | 第二阶段 (清理 heap 后) |
| **清理方式** | 删除索引条目 | 删除索引条目 |
| **依赖** | heap vacuum 已完成 | heap vacuum 已完成 (包括 undo 写入) |
| **失败回滚** | 不支持 | 支持 (通过 undo) |

**关键差异**: zheap 的索引清理可以回滚,heap 的不行。

## 四、vacuum 性能对比

### 4.1 zheap vacuum 的开销

**额外的开销**:
1. **事务槽分配**: 每次 vacuum 需要分配事务槽 (可能阻塞)
2. **undo 记录写入**: 每个 dead tuple 写一个 undo 记录 (额外的 I/O)
3. **undo 日志增长**: vacuum 产生的 undo 记录会占用 undo 日志空间

**节省的开销**:
1. **不需要重建 FSM**: 节省 I/O
2. **减少 clog 写入**: 事务信息在 undo,不需要写 clog

**净效果**: 
- **小表 (few pages)**: zheap 可能更慢 (事务槽分配 + undo 写入开销 > FSM 重建开销)
- **大表 (many pages)**: zheap 可能更快 (FSM 重建开销 > undo 写入开销)

### 4.2 理论性能对比

假设: 1M 行表,10% dead tuples (100K dead tuples)

| 操作 | heap | zheap |
|---|---|---|
| **扫描页面** | 10000 页 | 10000 页 (相同) |
| **标记 dead tuples** | 100K 次 | 100K 次 + 100K undo 记录 |
| **事务槽分配** | 0 次 | 100K 次 (每次 vacuum 一个槽) |
| **undo 写入** | 0 次 | 100K 次 (每次 50-100 字节) |
| **FSM 重建** | 1 次 (全表) | 0 次 |
| **索引清理** | 100K 次 | 100K 次 (相同) |
| **clog 清理** | 100K 次 | 0 次 (事务信息在 undo) |

**估算**:
- heap: 10000 页扫描 + 1 次 FSM 重建 + 100K 索引清理 + 100K clog 清理
- zheap: 10000 页扫描 + 100K 事务槽分配 + 100K undo 写入 + 100K 索引清理

**结论**: zheap 在 vacuum 时**增加了事务槽分配和 undo 写入开销**,但**减少了 FSM 重建和 clog 清理开销**。

## 五、vacuum 的关键代码路径

### 5.1 heap vacuum

```c
// lazyvacuum.c: lazy_vacuum_heap()
// 1. 获取 OldestXmin
// 2. 扫描 heap 页面
// 3. 对每个页面:
//    a. heap_page_prune() 识别 dead tuples
//    b. 标记 itemid 为 unused
//    c. PageRepairFragmentation() 修复碎片
//    d. 写 WAL (xl_heap_clean)
// 4. 清理索引
// 5. 清理 clog
```

### 5.2 zheap vacuum (with undo)

```c
// zvacuumlazy.c: lazy_vacuum_zpage_with_undo()
// 1. 获取 OldestXmin
// 2. 扫描 zheap 页面
// 3. 对每个页面:
//    a. zheap_page_prune() 识别 dead tuples
//    b. PageReserveTransactionSlot() 分配事务槽
//    c. 准备 UNDO_ZHEAP_ITEMID_UNUSED 记录
//    d. PrepareZHeapUndoRecord() 序列化 undo
//    e. InsertXactUndoData() 插入 undo
//    f. ItemIdSetUnusedExtended() 标记 itemid 为 unused
//    g. ZPageRepairFragmentation() 修复碎片
//    h. 写 WAL (xl_zheap_unused + undo 信息)
// 4. 清理索引
// 5. 清理 TPD (如果使用 TPD)
```

**关键差异**:
- zheap vacuum 需要**分配事务槽** (步骤 b)
- zheap vacuum 需要**写 undo 记录** (步骤 c-e)
- zheap vacuum 需要**清理 TPD** (步骤 5)

## 六、TPD pruning (zheap 特有)

### 6.1 TPD 页面的生命周期

```
创建: 当页面事务槽不够用时,创建 TPD 页面
使用: 新 tuple 的事务槽映射到 TPD
清理: 当 TPD 页面的最新事务 < oldestFullXidHavingUndo 时,可以清理
回收: 清理后,TPD 页面可以释放回 meta page 池
```

### 6.2 TPD pruning 机制

```c
// prunetpd.c: TPDPagePrune()
// 1. 检查 TPD 页面的 tpd_latest_fxid
// 2. 如果 tpd_latest_fxid < oldestFullXidHavingUndo:
//    - 可以清理整个 TPD 页面 (TPDPruneEntirePage)
//    - 释放 TPD 页面回 meta page 池
// 3. 否则:
//    - 扫描 TPD 条目,清理 all-visible 的条目
//    - 修复 TPD 页面碎片
```

**关键条件**: `oldestFullXidHavingUndo` 决定 TPD 页面是否可以清理。

## 七、vacuum 的 3 个关键问题

### 7.1 问题 1: 事务槽分配可能阻塞

```c
// zvacuumlazy.c:251-273
trans_slot_id = PageReserveTransactionSlot(...);
if (trans_slot_id == InvalidXactSlotId)
{
    LockBuffer(buffer, BUFFER_LOCK_UNLOCK);
    pgstat_report_wait_start(PG_WAIT_PAGE_TRANS_SLOT);
    pg_usleep(10000L);  // 10ms
    pgstat_report_wait_end();
    LockBuffer(buffer, BUFFER_LOCK_EXCLUSIVE);
    goto reacquire_slot;
}
```

**问题**: 如果页面事务槽全部被占用,vacuum 会等待 10ms 后重试。

**影响**: 高并发场景下,vacuum 可能被阻塞。

### 7.2 问题 2: undo 日志增长

```c
// zvacuumlazy.c:276-287
undorecord.uur_type = UNDO_ZHEAP_ITEMID_UNUSED;
undorecord.uur_payload.len = uncnt * sizeof(OffsetNumber);
undorecord.uur_payload.data = (char *) palloc(uncnt * sizeof(OffsetNumber));
```

**问题**: 每次 vacuum 都会写 undo 记录,增加 undo 日志大小。

**影响**: 频繁 vacuum 会导致 undo 日志快速增长。

### 7.3 问题 3: TPD 页面清理依赖 oldestFullXidHavingUndo

```c
// prunetpd.c:76-84
oldest_fxid_having_undo = FullTransactionIdFromU64(
    pg_atomic_read_u64(&ProcGlobal->oldestFullXidHavingUndo));

if (FullTransactionIdPrecedes(tpdopaque->tpd_latest_fxid,
                              oldest_fxid_having_undo))
{
    prstate.nunused = TPDPruneEntirePage(rel, tpdbuf);
    goto free_tpd_page;
}
```

**问题**: TPD 页面清理依赖 `oldestFullXidHavingUndo`,如果长事务运行,TPD 页面不能清理。

**影响**: 长事务会阻塞 TPD 回收,导致 TPD 页面泄漏。

## 八、结论

**zheap vacuum 的设计更优雅,但实现更复杂**:

| 维度 | heap | zheap |
|---|---|---|
| **vacuum 阶段** | 单阶段 | 两阶段 (heap + index) |
| **事务槽** | 不需要 | 需要 (可能阻塞) |
| **undo 记录** | 不需要 | 需要 (增加 I/O) |
| **FSM 重建** | 需要 | 不需要 |
| **clog 清理** | 需要 | 不需要 |
| **回滚支持** | 不支持 | 支持 (通过 undo) |
| **实现复杂度** | 低 | 高 |

**zheap vacuum 的优势**:
1. **支持回滚** —— vacuum 失败可以回滚 (通过 undo)
2. **不需要重建 FSM** —— 节省 I/O
3. **减少 clog 写入** —— 事务信息在 undo

**zheap vacuum 的劣势**:
1. **需要分配事务槽** —— 可能阻塞
2. **需要写 undo 记录** —— 增加 I/O 和 undo 日志增长
3. **实现复杂** —— 两阶段 + undo + TPD pruning

**实测建议**:
1. 编译 zheap 并运行 pgbench 对比 vacuum 性能
2. 测试高并发场景下的事务槽竞争
3. 测试长事务对 TPD 回收的影响
