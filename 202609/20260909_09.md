## 你写的 AI 技能，为什么总是不触发？
  
### 作者

## 背景  
  
> 龙蜥 SkillHub 上线以来，我看过几十个社区提交的技能。有一个现象很有意思：**90% 的技能文档写得很漂亮，但实测触发率不到 50%。**  

用户明明说了「帮我写月报」，Agent 就是无动于衷。

用户明明说了「诊断一下这台 Anolis 机器」，Agent 给的是通用 Linux 命令，完全没调用那个精心写好的诊断技能。

这不是 Agent 变蠢了。是你的 `description` 写错了。

---

## 先说一个反直觉的事

**Agent 触发技能，看的不是你写得好不好，是看 `description` 够不够像用户真实说话的样子。**

大多数人写 `description` 的逻辑是：精炼、专业、准确。这三个词单独拿出来都是褒义词，但放在 `description` 里，恰恰是触发率低的根因。

为什么？

因为 Agent 在决定调用哪个技能时，做的是语义相似度匹配。用户说「这个月的 PR 统计一下」，Agent 要在 N 个技能里找到最相关的那个。如果你的 `description` 写的是「生成龙蜥社区月度运营报告」——这句话专业、准确，但语义距离太远，Agent 匹配不上来。

如果你写的是：「当用户说『月报』『这个月的 PR』『Issue 汇总』『统计一下本月数据』时立刻触发」——这就直接就是用户的语言，语义距离为零。

**这叫 pushy description，是提升触发率最有效的单一手段。**

---

## 什么是 Skill？给没听说过的人解释一遍

Skill（技能）是 AI Agent 的「工具插件」。

用一个类比：普通的 AI 助手就像一个博学的顾问，你问什么它答什么。加了 Skill 之后，它变成了一个带专用工具箱的顾问——用户说某类话，它自动打开对应工具完成任务，而不是靠通用推理现编答案。

龙蜥社区（OpenAnolis）有一个叫 **SkillHub** 的平台（skillhub.openanolis.cn），专门存放面向 Anolis OS 生态的技能。想象成「App Store，但里面装的是 AI 操作流程」。技能由社区成员贡献，经过审核后上架，任何人都可以在自己的 Agent 里加载使用。

技能的核心文件只有一个：`SKILL.md`。

---

## SKILL.md 的解剖

一个合格的 `SKILL.md` 长这样：

```yaml
---
name: kernel-perf-diagnose
description: 诊断 Anolis OS 内核性能瓶颈。当用户说「内核性能有问题」
  「帮我看看 CPU」「perf 分析」「系统变慢了」「火焰图」时立刻触发。
  即使用户只说「机器跑得慢」而上下文是 Anolis OS，也应触发。
version: 1.0.0
author: 张三
os_support:
  - Anolis OS 8
  - Anolis OS 23
suggested_sig: kernel
contributor_type: enterprise
org_name: 中兴通讯
---

# 内核性能诊断

## 一、准备工作
需要：perf、bcc-tools、flamegraph 已安装。

## 二、执行步骤
1. 采样 CPU 热点：`perf record -g -p <PID> sleep 30`
2. 生成报告：`perf report --stdio`
3. 生成火焰图：...

## 三、Anolis 特殊说明
ANCK 内核支持 eBPF，RHCK 部分工具受限...

## 四、验证
看到火焰图中热点函数即为成功。
```

结构上分两块：

**frontmatter（上半部分，YAML 格式）**：给 Agent 和平台看的元数据。决定技能是否被触发、如何被分类。

**body（下半部分，Markdown 格式）**：给 Agent 执行时读的指令。决定任务做得好不好。

两块的职责严格分离，这个原则非常重要，后面会详细说。

## 触发失败的五种死法

### 死法一：description 太精炼

❌ `「生成 Anolis OS 月度运营报告」`

✅ `「生成龙蜥社区月度运作报告。当用户说『写月报』『龙蜥月报』『生成本月运营数据』『openanolis monthly』时立刻触发。即使用户只说「汇总数据」而上下文是龙蜥社区，也应触发。」`

差别不是文字量，是语义密度。第二个版本里有五个触发短语，Agent 有五次机会命中。

### 死法二：把触发条件写在 body 里

这是高频错误。有人写了很长的 body，第一段就是「当用户说 X、Y、Z 时使用本技能」。

**没用的。**

Agent 决定是否触发技能，只看 frontmatter 的 `description`，根本不读 body。body 只在技能已被触发、Agent 开始执行任务时才会读。把触发条件放在 body 里，等于写在墙背面，Agent 看不到。

### 死法三：name 三处不一致

`SKILL.md` 里的 `name` 字段、ZIP 文件名、ZIP 内顶层目录名，这三处必须完全一致。

```
✅ 正确：
SKILL.md:  name: kernel-perf-diagnose
ZIP 文件名: kernel-perf-diagnose.zip
ZIP 内目录: kernel-perf-diagnose/

❌ 错误（有一处不同就报错）：
name: kernel_perf_diagnose   ← 下划线 vs 连字符
ZIP: kernel-perf.zip         ← 名字不完整
目录: KernelPerfDiagnose/    ← 驼峰
```

三处错位，Claude Code 找不到技能，Copilot Shell 报「skill manifest mismatch」，OpenClaw 显示空白。

### 死法四：打包带 macOS 垃圾文件

Mac 用户一定遇到过这个问题。直接在 Finder 里右键「压缩」，ZIP 里会包含 `__MACOSX/` 目录和 `.DS_Store` 文件。SkillHub 审核会直接拒。

打包前先清理：

```bash
find . -name '.DS_Store' -delete
find . -name '__MACOSX' -exec rm -rf {} +
cd .. && zip -r your-skill-name.zip your-skill-name/
```

### 死法五：body 用伪代码

审核会拒掉无法实际运行的技能。`<your-pid-here>`、`[TODO: 填入 API Key]` 这类占位符会被判定为「未完成」。给出能直接跑的真实命令，包括依赖安装步骤、环境变量声明，这是通过审核的基本条件。

## 高手进阶：触发率怎么量化

发布之前，有一件事很多人跳过了：**测试触发率**。

触发率 = 「应该触发本技能的 prompt，实际被触发的比例」。

怎么测？

**第一步**，建一个 `tests/` 目录，放几个测试 prompt：

```
tests/
├── case-01-happy-path.md        # 标准场景
├── case-02-edge-implicit.md     # 隐式触发（用户没说关键词但语境对）
└── case-03-no-trigger.md        # 不该触发的 prompt（测误触发率）
```

每个 case 写三行：
- `prompt:` 用户会怎么说
- `expected:` 应该/不应该触发
- `reason:` 为什么

**第二步**，带着这个技能跑 Agent，每条 prompt 跑 10 遍（Agent 有随机性，单次不算数）。

**第三步**，统计数字。

| 指标 | 目标 | 怎么改 |
|------|------|--------|
| 触发率 | ≥ 80% | 改 description，增加触发短语，语气更 pushy |
| 正确率 | ≥ 80% | 改 body，步骤拆细，补 pitfalls |
| 误触发率 | ≤ 10% | description 加「不适用于…」限定语 |

**进阶版**：收集 30 条以上真实用户 prompt，算 F1 score（精确率和召回率的调和平均），收敛到 F1 > 0.85 再发布。这是工程级别的质量门槛。

## 为什么要在乎 os_support 字段

很多人觉得 `os_support` 是可选的，填不填都行。

从功能上说确实如此。但有两个理由让你应该填：

**第一，搜索和筛选。** SkillHub 前台支持按 OS 版本筛选，不填的技能在「只看 Anolis OS 23 兼容」的筛选结果里不出现。

**第二，OpenClaw 优先级。** 龙蜥自家的 OpenClaw 客户端会优先推荐 `os_support` 包含当前 OS 版本的技能。同样功能的两个技能，填了的排前面。

`os_support` 可以填多个值：

```yaml
os_support:
  - Anolis OS 8    # RHEL 8 系，兼容 CentOS 8 迁移
  - Anolis OS 23   # 基于 OpenCloudOS，更激进的上游跟踪
  - 通用           # 跨发行版，不依赖龙蜥特定工具
```

如果技能只用了 `systemctl`、`dnf`、通用 Python 库——填「通用」，适用范围最广。如果用了 ANCK 内核特性、`anolis-release` 包、龙蜥镜像源——明确填 Anolis OS 8/23，别让 Ubuntu 用户装了跑不起来。

## 两条发布路径，哪条适合你

### 路径 A：SkillHub Web 上传

适合：个人贡献、快速试水、首次发布。

1. 登录 `skillhub.openanolis.cn`（用龙蜥通行证 SSO，和 Gitee 账号互通）
2. 进「我的技能 → 提交新技能 → 上传 ZIP」
3. 填好 ZIP 路径，可选填企业归属
4. 等三合一审核：AI 评分 + admin 复核，通过即上架

时间成本：上传 5 分钟，等审核通常 1 个工作日内。

### 路径 B：Gitee PR

适合：企业团队、多版本管理、希望有 git 历史的场景。

```bash
# fork openanolis/anolis-skills
git clone https://gitee.com/yourname/anolis-skills
cd anolis-skills
mkdir -p skills/your-skill-name
cp -r /path/to/your-skill-name/* skills/your-skill-name/
git add . && git commit -m "feat: add your-skill-name"
git push
# 然后在 Gitee 上提 PR
```

PR 合并后，Webhook 自动触发入库，通常 10 分钟内在前台可见。

两条路走的是**同一个审核引擎**，结果一样，不会双处理。选哪条取决于你的工作习惯，不影响技能质量。

## 你的技能能兼容几个 Agent？

同一份 `SKILL.md` 可以被以下 Agent 客户端加载：

| 客户端 | 必填字段 | 特殊限制 |
|--------|---------|---------|
| **Claude Code** | name + description | description ≤ 1024 字符 |
| **Copilot Shell** | name + description | ZIP 顶层目录名必须严格匹配 name |
| **OpenClaw（龙蜥）** | name + description + os_support 推荐 | 优先展示 os_support=Anolis OS 的技能 |
| Cursor / Codex CLI / Gemini CLI / Qwen Code / Trae / Cline | name + description | 各产品体验以官方文档为准 |

**最大公约数原则**：按 Copilot Shell 最严格的规范写（三处 name 完全一致），所有客户端都能正常使用。

description 的字符限制值得特别注意——Claude Code 限制 1024 字符。你的触发短语再多，也要在这个额度内压缩完。实测：8-10 个触发短语加两行说明，基本正好用完。

## 安全自检，三分钟扫完

发布前快速过一遍这个清单，省去审核来回：

**高风险，直接拒：**
- `curl`/`wget` 到未在 body 里声明的外部 URL
- 读 `~/.ssh`、`~/.aws`、`/etc/shadow` 等敏感目录，没有合理说明
- `eval` 处理外部输入、base64 解码未知内容、代码混淆

**建议做法：**
- 所有网络目标在「前置条件」里显式列出
- 权限最小化：不需要 root 的步骤不写 sudo
- 高危操作（删除、格式化、修改系统配置）带回滚说明

龙蜥社区的规模决定了安全要求比个人工具更严。一个被广泛使用的技能出了安全问题，影响的不是一个人的机器。

## 发布之后：怎么维护和迭代

发布是起点，不是终点。

**触发率持续下降**？通常是因为 Agent 版本升级改变了语义匹配逻辑。解法：重新收集用户 prompt 样本，重跑触发率测试，针对新的漏网短语更新 description。

**步骤过期了**？比如某个工具改了命令行参数。解法：改 body，注明适用版本，`version` 字段升一个小版本（1.0.0 → 1.0.1）。

**逻辑越来越复杂**？当 body 里的步骤超过 15 条，维护成本会指数上升。解法：把核心逻辑移进 `scripts/` 目录的 Python 或 Shell 脚本，body 只保留调用入口。脚本可以独立测试、独立版本控制，比嵌在 Markdown 里好管理得多。

**想支持多语言**？复制 `SKILL.md` 为 `SKILL.zh.md` 和 `SKILL.en.md`，各自填写对应语言的 description，body 的执行步骤可以共享。国际化用户越来越多，值得花这个时间。

## 给初学者的最小可行路径

如果你现在就想动手，五步上手：

```bash
# 1. 建目录
mkdir my-first-skill && cd my-first-skill

# 2. 写 SKILL.md（至少填 name + description + body 5行）
vim SKILL.md

# 3. 打包
cd .. && zip -r my-first-skill.zip my-first-skill/

# 4. 登录 skillhub.openanolis.cn 上传 ZIP

# 5. 在 Claude Code 或 Copilot Shell 里加载，测试触发率
```

第一版不用追求完美。触发率低就改 description，步骤不清楚就改 body，迭代三轮基本能稳定。

## 给专家的一道思考题

你维护的技能，有没有做过 **false-negative 分析**？

false-negative = 用户说了应该触发的话，但 Agent 没触发。

比用触发率更有价值的问题是：**哪类 prompt 最容易漏？**

从真实用户的对话历史里抽样，人工标注「这条应不应该触发我的技能」，然后对照 Agent 实际行为。漏掉的 prompt 往往有规律：

- 用户用了方言或缩写（「帮我看看这台机器」而不是「诊断 Anolis OS」）
- 用户先问了别的问题，上下文已经偏移
- 用户的需求包含了本技能的一部分，但不完全匹配

这三类漏触发，对应的 description 修法各不相同。把这个分析做完，F1 score 通常能从 0.7 提到 0.9 以上。

龙蜥 SkillHub 现在有 40+ 个技能，覆盖系统运维、AI、内核、安全、文档、CI/CD 六个类目。

但和真正的需求量相比，这个数字还很小。

每个在 Anolis OS 上重复做过三次的事，都值得写成一个技能。每个你教过别人怎么操作的流程，都值得写成一个技能。技能不是给自己用的，是给整个社区用的。

`skillhub.openanolis.cn`，登录就能上传。

`gitee.com/openanolis/anolis-skills`，fork 就能提 PR。

你的工作经验，值得被固化成 AI 能直接使用的工具。
