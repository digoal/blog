## TiDB 圆桌逐题发言稿  
  
> 圆桌主题：如何让 Agent 在企业里严肃落地、稳定发挥？  
> 嘉宾：德哥 / digoal(原阿里云 / 现 PostgreSQL & AI 应用)  
> 核心框架：屠龙刀 + 三层记忆 + 数据库×AI 重构  
  
### 开场定调  
  
> 主持人好，各位嘉宾好。我是德哥，做了20年数据库，现在是 AI 实践者, 几乎扑在用 AI Agent 进行交付上。我自己搞了个"AI 屠龙刀"镜像 — 很多人把 Agent 当工具用，我把它当"活物"用。我的理念是怎么把 AI “屠龙刀” 大变 活"人"。  
  
### 第一题: Agent 从 Demo 到生产，最难的问题是什么?  
  
我的答案: 不是模型、不是工具调用、不是 RAG, 是记忆 + 沉淀 + 可演进  
  
市面上 90% 的 Agent 困死在 Demo，一跑生产就崩。我观察下来，三件事同时没做对：  
  
1. 没有"用进废退"的机制  
  
人类员工干一年会变资深，Agent 干一年还是那个 Agent。市面上大多数 Agent 项目的现状就是：今天你看到的，跟你半年前看到的，是同一个东西。模型升级了、prompt 优化了、工具多了，但 SOP 没沉淀、踩坑没记录、最佳实践没编码。结果就是——同样的坑踩一万次，每次都现去搜 prompt 调教。  
  
2. 把"记忆"当 KV 存储用，不当认知伙伴用  
  
现在做 Agent 记忆的团队，主流方案是 LLM 切 chunks → embed 向量化 → 塞向量数据库做 RAG。这条路在 demo 上"看起来很美"，到生产就翻车。我自己在 cognee 上跑过 benchmark，LoCoMo 上一轮 gpt-5 答案用 6.4% 错题率 + 严格判官 → 0.095；同一份答案换宽判官 → 0.74(差距 40 分)。换 prompt 不换模型，Mem0 v2 OSS 自己家的答案从 0.7413 掉到 0.3427，57/143 答案翻盘。这不是 memory 技术问题，这是测量仪器 + 语料 + 长度的纠缠——把 memory 单独去 SOTA 排序，是个伪命题。  
  
真实企业的记忆需求长这样：上周三上午跟法务开的会里有 3 条合规要点、上个月某次客户投诉的处理路径、上季度王总说过的一句战略转向。这些信息结构化程度低、上下文敏感、跨事件关联、跨时间衰减，纯向量召回根本召不回。必须把记忆分层:  
  
- L1 工作记忆: 当前对话的 short-term 上下文  
- L2 实体记忆: 人、事、物的事实卡片(类似 Notion 的轻量结构)  
- L3 模式记忆: 从多次交互里沉淀的 SOP/最佳实践(屠龙刀里这就是 SKILL)  
- L4 元记忆: Agent 对自己"会不会、记得什么、不确定什么"的自评  
  
四层一起用，才撑得起企业场景。光靠 L1+L2 那种 KV + 向量检索，叫"高级聊天机器人",不叫 Agent。  
  
3. 没有人去维护它  
  
这条最反直觉。我一直强调: Agent 的记忆不是"自动长出来"的,是"边用边养"的。每跑完一个任务, 人(或者上游 Agent)要花 30 秒做三件事: 踩坑 → 写 SKILL；经验 → 升 SKILL；旧 SKILL → 修剪。一个 SKILL 用三次就该被抽成更通用的版本, 这是 Agent 的"成长"。  
  
**SKILL 不在多, 而在精. SKILL 本身也要迭代, 而不是静态的.**。  
  
我的解决方案  
  
我做了一个项目叫屠龙刀,核心就这一句话: LLM + Agent + 联网是载体,核心是越用越好(用进废退)。具体落地的有:  
- SOP/踩坑 → 沉淀成 SKILL(主人手写,人类可读可改)  
- 重复操作 → 沉淀成脚本/工具包(Hermes 脚本库 ~/.hermes/profiles/digoal/scripts/)  
- 定时任务 → 沉淀成 cron job(每天自动跑,7×24 不空转)  
- 工作流 → 沉淀成编排经验(错了改 SKILL,对了也改 SKILL)  
  
案例: 一个 5 人团队的"AI 投资助理"  
  
我们(4 人 + 我)业余做 A 股研究时,用屠龙刀搭了个 AI 投研助理:  
- 日层:每日 15:00 自动跑数据库/AI/金融动态 cron → 解构 → 写日报(异步 fire)  
- 周层:每周日跑跨领域思维碰撞(7 个领域 sub-agent 并行)+ 每周 A 股估值轮动  
- 月层:每月跑投资复盘 cron → 沉淀成月度 SKILL → 入了主库  
  
跑了不到 3 个月,我们产出的研报质量比 2024 年雇佣的两位实习分析师高，成本是他们的 1/10。关键不是模型更强，是我把团队过去的决策 SOP、踩过的坑、看过的财报逻辑,全沉淀进了屠龙刀的 SKILL 库——新人(新会话)进来第一天就能继承所有积累。  
  
这就是用进废退。我现在看待 Agent 跟看待实习生一样——不养不成器。  
  
  
  
### 第二题: 一个 Agent 要长期稳定工作，关键能力到底是什么?  
  
我的答案: 不是更聪明的模型, 是确定性 + 可观测 + 可回滚  
  
"稳定"在企业语境下, 不是 SLA 99.99%,是"什么时候崩你得能告诉我为什么崩，并且崩了能退回去"。  
  
我把"长期稳定"拆成三个支点：  
  
支点 1: 确定性 > 灵活  
  
很多 Demo 喜欢展示"这个 Agent 会自己想办法解决新问题",听着很美,生产最痛。我观察到一个反直觉规律:Agent 在企业里的真实价值,不来自它能解决未知问题,来自它能把已知问题 100% 解决掉。  
  
原因:  
- 已知问题占企业 80% 工作量(报销、客服、合规报表、采购审批)  
- 已知问题每次重答不一致,下游没法接(财务系统对不上账、审批流走不下去)  
- Agent 在已知场景下灵活性大 = 不确定性大 = 风险大  
  
屠龙刀的策略:把已知场景 100% 锁死(SKILL 写死 SOP、tool call 路径写死、prompt 模板写死、参数走配置文件),只对未知场景开 LLM 自由度。我管这叫"确定性地板 + 灵活性天花板":底层稳如狗,顶层敢创新。  
  
支点 2: 可观测 > 不可观测  
  
企业里崩了之后最贵的事不是修 bug,是找 bug。一个 Agent 跑了 1000 次,出 1 次错,你怎么定位?我的屠龙刀三层全链路日志:  
- prompt 层:完整记 prompt + response(进了数据库,带 session_id)  
- tool 层:每个 tool call 入参出参 + latency + token  
- 业务层:SQL 审计类似的语义 — 每个任务做了哪些动作、改了哪些数据、花了多少 token、拿走了什么  
  
这套东西是借鉴数据库的慢查询日志 + pg_stat_statements 做的。换到 Agent 时代,一样成立:没有可观测,就没有稳定。  
  
支点 3: 可回滚 > 不可回滚  
  
这是 my AI 屠龙刀最深的体感。我说一个真实的场景——上个月我用 Agent 自动跑 cron 做数据库 schema 迁移,跑完才发现自己 SKILL 里有个判断条件写反了,把生产表 drop column 写成了 rename column。结果呢? 因为我每个 cron 任务都有 task_id + 写了个回滚 SKILL(rollback_skill:{task_id})，10 秒内我让 Agent 自动回了滚,业务零感知。  
  
为什么我能这么干？因为从第一天设计 SKILL 库的时候，我就把"每个写操作 = 生成反向 SKILL"当成硬约定。  
  
关键能力清单(我从屠龙刀里抽出来的真干货)  
  
| 能力   | 不是                  | 是                                             |  
|--------|-----------------------|------------------------------------------------|  
| 记忆   | KV 存储               | 分层记忆(工作/实体/模式/元) + 自动遗忘         |  
| 技能   | 死在 prompt 里        | SKILL 化(可被检索、被组合、被版本管理)         |  
| 编排   | 堆 tool call          | 状态机 + 任务层级表 + 死信队列                 |  
| 观测   | 跑成功就好            | 全链路可观测(tool 入参出参 + token + 业务影响) |  
| 回滚   | 走 git revert         | 自动生成反向 SKILL                             |  
| 领域化 | 通用 Agent 一个打天下 | 多 profile = 多个垂直领域专家 + 团队作战       |  
  
  
  
### 第三题: 企业级 Agent 怎么做到稳定、可靠、可控?  
  
我的答案: 把数据库的工程纪律搬到 Agent 上  
  
这一点我特别有发言权——十几年数据库内核训练出来的本能,就是任何"看似智能"的东西背后都必须有强约束。  
  
原则 1: Agent 也是"系统",也要走"系统"那条路  
  
我经常跟同行讲一句话:你觉得 LLM 是个黑盒不可控?那是你还没用工程纪律管它。数据库运维怎么管一个不可预测的 workload?就那几招:慢查询日志 + 资源隔离 + 自动 kill + 告警。这套搬到 Agent 上:  
  
| 数据库               | Agent                                            |  
|----------------------|--------------------------------------------------|  
| 慢查询日志           | tool call latency + token cost 监控              |  
| pg_stat_activity     | 实时 agent_state(在跑什么、卡在哪、占多少 token) |  
| pg_terminate_backend | "agent kill switch"(超时就 abort)                |  
| Row-Level Security   | 每个 Agent 的可见数据范围严格限定                |  
| replication + WAL    | agent 任务的事件溯源(每步变更可重放)             |  
| 备份 + PITR          | SKILL 版本管理 + 任意时刻回放                    |  
  
这不是比喻。这是我真在做的——事件溯源 + 操作审计 + RLS,我把它们当 Agent 的"PG 内核"用。  
  
原则 2: 可控 = 边界清晰 + 授权收紧  
  
很多 Agent 失败案例,根因都是边界模糊。给 Agent 一个万能工具箱,等于给它一把没有保险的枪。  
  
我的屠龙刀三层权限模型:  
1. 用户主权: 每个用户有独立的 profile,Agent 不能跨 profile 拿数据  
2. 场景授权: 每个 SKILL 声明它需要哪些权限,运行时校验  
3. 危险操作二次确认: 写操作、跨用户操作、生产 DB 操作,必须叫人  
  
第三条最重要。我自己的 Agent 在生产环境跑 DROP TABLE 之前,会先调我的飞书发一条消息,等我点"放行"才执行。这个流程看似笨,但这是企业落地的关键——人必须留在回路里。  
  
原则 3: 可靠 = 任务可重启 + 失败可重放  
  
企业级 Agent 不能因为网络抖动或 token 限额崩了就停。我现在的做法:  
- 每个长任务先写"任务契约"到数据库(类似数据库的 WAL 概念):任务目标、子任务列表、依赖关系、当前状态  
- Agent 崩了/超时了/被 kill 了,新 Agent 凭任务契约可以接续  
- 这个机制叫"stateless worker + durable state"——同 Kafka / Celery / Sidekiq,但用在 Agent 上  
  
这意味着我把 Agent 当无状态的工人,状态全部外部化在数据库里。我那位在 X 上做 Agent 重启实验的同行说过一句话很对:"Agent 应该像 serverless 函数,而不是像长进程 daemon"。  
  
三句话总结我对这一题的态度  
  
> 稳定 = 确定性地板。  
> 可靠 = 全链路可观测 + 可重放。  
> 可控 = 边界清晰 + 人留回路 + 状态外置数据库。  
  
  
  
### 第四题: Data + AI, 怎么真正从信息走向 Decision & Action?  
  
我的答案: 数据栈正在被 Agent 协作重构 — 从"存数据"到"存 Agent 协作全过程"  
  
**未经整理的数据，只是原始素材，还谈不上信息，更谈不上知识或洞察。** 未能被 Agent 认知的数据也只是原始素材.  
  
这一题是我的主场。十几年做数据库, 我看到了 AI 时代数据栈最大的范式转移: 数据库的本质, 从"存数据",正在演化成"存 Agent 协作的全过程"。  
  
为什么会这样?  
  
LLM 推理大规模生产化之后,数据栈的下游消费者不只是 BI/分析师/APP,最大消费者变成了 Agent。单个 Agent 已经要 RAG + 操作审计了，多 Agent 协作起来，还要:  
- 上下文搜索 (RAG + 元数据过滤的混合检索)  
- 安全隔离 (Row-Level Security + 动态权限 + 操作审计 — 这些原本是 PG 的"高级特性"，Agent 时代会变成"基础需求")  
- 多 Agent 编排 (任务-子任务层级存储 + 状态机 + 任务依赖关系)  
- 任务管理 (任务队列表 + 状态字段 + 重试计数 + 死信队列)  
- 行为可跟踪溯源 (事件溯源)  
  
哪一条不是数据库的老本行？  
  
未来的数据库, 不是"带了点 AI 的数据库", 是"为 Agent 协作重新设计的数据库"。这话我一年前说可能有人觉得激进, 2026 年下半年应该没人反对了——所有大厂都在重新设计自己的数据栈底座。  
  
这件事屠龙刀已经在做了  
  
我部署 cognee/PowerContext 跑在 PostgreSQL 18.4 上(同库装 pgvector + AGE 图数据库 + pg_trgm)。为什么不直接用 LangChain / Mem0 / Zep？因为那些是基于内存+向量 DB 的方案,到企业级根本撑不住多用户 + 跨部门 + 审计 + 权限。我选 PG + pgvector + AGE 的组合,就是把:  
  
- 向量检索 → pgvector(主力)  
- 图关系 → AGE(Apache TinkerPop 协议)  
- 全文+模糊 → pg_trgm + tsvector  
- 结构化元数据 → 标准 PG 表  
- 审计日志 → 标准 PG 表 + pgaudit 插件  
- 权限隔离 → 标准 PG RLS  
  
所有能力全部收在同库里。代价是部署复杂(SQL 调优、扩展编译、连接池),好处是 Agent 协作全数据闭环,不再需要"把记忆从内存搬到 DB"这种损耗。  
  
从"信息"走向"Decision & Action", 中间缺什么?  
  
缺的不是一个更大的 LLM，缺的是 "Decision & Action 的全链路数字化底盘"。我把它拆成 4 层:  
  
```  
┌───────────────────────────────────────────────────────────────┐  
│   Layer 4: Action (执行,SkILL/cron/工具调用)                  │  
├───────────────────────────────────────────────────────────────┤  
│   Layer 3: Decision (决策:SQL + RAG + LLM 综合)               │  
├───────────────────────────────────────────────────────────────┤  
│   Layer 2: Context (上下文: cognee/PowerContext/PG 三层记忆)  │  
├───────────────────────────────────────────────────────────────┤  
│   Layer 1: Data (原始数据:事务库 + 数仓 + 日志)               │  
└───────────────────────────────────────────────────────────────┘  
```
  
  
现在绝大部分企业的 AI 项目卡在 Layer 2 → Layer 3 这一段。他们有数据(BI 有报表),有上下文(RAG 召回了几个文档),但没有 Decision 系统把数据和上下文结构化成"可执行决策"。  
  
怎么把 Decision 做出来? —— 把数据库里三个老工具重新启用来:  
  
1. 用 RLS 做 Action 的安全边界  
  
PG 的 Row-Level Security 本来是合规工具(医疗、金融、电信用得最多)。Agent 时代要重新启用了:每个 Agent 在每个场景下"该看见什么、能改什么",全用 RLS 表达。  
  
我屠龙刀的设计:Agent 的所有数据访问都走同一个 PG 连接,通过 SET app.current_agent_id 切 RLS 上下文。同一个表,A Agent 看到的行和 B Agent 看到的行不一样,而且不能绕过(PG RLS 是强制的)。  
  
这是"可控"的根基。任何 Agent 都不应该"裸奔"。  
  
2. 用事件溯源做 Action 的可审计  
  
每个 Agent 的每个动作(读什么、写什么、调什么工具、花多少 token、产生什么副作用),全记到一个 append-only 事件表,类似数据库的 WAL。  
  
```sql  
CREATE TABLE agent_event_log (  
  event_id      bigserial PRIMARY KEY,  
  task_id       uuid NOT NULL,  
  agent_id      text NOT NULL,  
  event_type    text NOT NULL,  -- read | write | tool_call | decision  
  payload       jsonb NOT NULL,  
  ts            timestamptz DEFAULT now()  
) PARTITION BY RANGE (ts);  
```
  
  
这个表的存在,意味着:  
- 任何 action 出错,能秒级回放找原因(类似 PITR)  
- 监管来了直接交表(不用临时 grep 日志)  
- 可以做"决策反演"——回看 Agent 在某时刻为什么做了某选择  
  
3. 用任务队列表做多 Agent 协作  
  
PG 当 Kafka 用,这事我做了好多年(企业实战里 PG 队列性价比远高于独立 Kafka,数据一致性还好)。Agent 时代更合适:  
  
```sql  
CREATE TABLE agent_task (  
  task_id        uuid PRIMARY KEY DEFAULT gen_random_uuid(),  
  parent_task_id uuid REFERENCES agent_task,  
  agent_id       text NOT NULL,  
  skill_name     text NOT NULL,  -- 用哪个 SKILL  
  payload        jsonb,  
  status         text NOT NULL DEFAULT 'pending',  -- pending/running/done/failed/dlq  
  retry_count    int DEFAULT 0,  
  locked_by      text,           -- 哪个 worker 正在跑  
  locked_at      timestamptz,  
  created_at     timestamptz DEFAULT now()  
);  
```  
  
多 Agent 协作 = 多个 worker `SELECT ... FOR UPDATE SKIP LOCKED + UPDATE` status。这套就是 Celery / Sidekiq / Temporal 的核心,被我用 PG 原生 SQL 实现了,零额外组件,事务一致,审计自带。  
  
我对未来 3 年的判断  
  
1. "Agent + 数据库"会出现一个独立的细分赛道.  
  
不是传统 OLTP/OLAP, 也不是单纯向量库。是"Agent 协作数据库",专门优化: Agent 身份切换(RLS 友好)、事件溯源(append-only 优化)、任务队列(SKIP LOCKED 友好)、混合检索(向量+全文+图+结构化同库)。  
  
2. 所有大厂的数据栈, 接下来 18 个月会重做底层  
  
不是因为炫技,是因为旧数据栈不优化 Agent 协作负载。这是范式转移,不是版本升级。  
  
3. 中国在这条赛道上会走出自己的路  
  
中国企业的 Agent 落地场景(电商、客服、内容审核、投研、政务)跟海外不一样, 数据更密、并发更高、合规更严。谁能把 PG 这种强一致性底座 + Agent 协作原生设计 + 中国场景适配串起来,谁就是下一波赢家。  
  
  
  
### 收尾: 我对整个圆桌的一句话总结  
  
> Agent 不是更聪明的工具, 是"用进废退"的活体。  
> 把它当人养, 它就越来越强。把它当工具用, 它就一直在 Demo。  
  
具体怎么养？四件事:  
1. 每个任务跑完必须沉淀(SKILL / 踩坑 / 经验)  
2. 每个 SKILL 必须可观测可回滚(用 PG 的工程纪律管)  
3. 每个 Action 必须留痕(事件溯源当 AGI 时代的 WAL 用)  
4. 每个 Agent 边界清晰(RLS 当 Agent 时代的权限系统用)  
  
做到这四条，企业里的 Agent 不只能 Demo 漂亮，还能 7×24 稳定生产。
