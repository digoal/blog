## 背景 
   
  
PostgreSQL 19 SQL/PGQ 的功能被回退了, 自己写一个通用的基于 BFS 的属性图功能插件.  
  
该实现在多年之前写过 《PostgreSQL 图式搜索(graph search)实践 - 百亿级图谱，毫秒响应》  
- https://github.com/digoal/blog/blob/master/201801/20180102_04.md  
  
写好已开源: https://github.com/digoal/pg_graph_search/

7、提交, 并在 commit 消息中关联 issue id  
```  
git add .  
git commit -F - <<'EOF'
contrib/pg_graph_search: add property graph search extension, with OpenTenBase support  
  
Add pg_graph_search, a metadata-driven property graph search extension.  
The extension is pure SQL (no shared library, no local files), and the  
platform differences are isolated behind a single build-time placeholder  
plus one runtime probe function, so the same source tree still runs the  
full test suite on upstream PostgreSQL.  
  
A graph is an ordinary table (src, dst, prop).  graph_search.install()  
generates the per-instance API -- search, cursor, shortest_path, subgraph,  
stats -- along with an edge view and a registry row.  graph_search.plan()  
previews the DDL and graph_search.advise() checks the input table first.  
  
OpenTenBase specifics:  
  
  * The registry must be DISTRIBUTE BY REPLICATION.  Without an explicit  
    distribution clause the default is to hash on the first primary key  
    column, so each DN would see only part of the instance list.  Inject  
    the clause through the @DISTRIBUTE_CLAUSE@ placeholder, so that plain  
    "make" and "make portable" produce an OpenTenBase build and a portable  
    one from the same sources.  
  
  * sql_mode = 'all' in the control file, because  
    check_extension_in_right_mode() only accepts 'all' or a value matching  
    the running SQL mode.  
  
  * registry_distribution() reports the current strategy, and  
    set_registry_replication() repairs it idempotently.  
  
Note that this build has ENABLE_ALL_TABLE_TYPE off, so only  
DISTRIBUTE BY shard (col) and DISTRIBUTE BY REPLICATION are accepted.  
DISTRIBUTE BY HASH is rejected with "Cannot support distribute type: Hash",  
and so is omitting the clause entirely, since that also defaults to hash.  
Edge tables therefore have to state their distribution explicitly, and  
DISTRIBUTE BY REPLICATION additionally requires a default node group.  
  
Verified on OpenTenBase 5.21.8 (commit b612d77cb) on a single-host  
1 CN + 2 DN + GTM cluster: CREATE EXTENSION and the registry land on all  
three nodes, registry row counts match between CN and DN, the generated  
functions exist on the DNs with identical signatures, uninstall() drops  
cleanly on every node, 18/18 regression assertions and 15/15 correctness  
checks pass on both OpenTenBase and PostgreSQL 18, and a  
20000-node/199k-edge graph shards 42/58 across the two DNs.  Throughput  
on that graph: 3-degree search 10.2 tps (shard) vs 8.2 tps (replication);  
shortest path 35.6 tps (shard) vs 71.8 tps (replication); storage 25 MB  
vs 50 MB.  
  
doc/opentenbase-port.md records the build and runbook, the per-node  
metadata checks, the measured performance comparison, the SQL constructs  
this version mishandles when a generated function is combined with a local  
temporary table, and the cluster bring-up pitfalls.  
  
Related to #386  
EOF
```
