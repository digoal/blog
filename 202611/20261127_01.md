## 背景  
我是digoal德哥，Agent 本体 (agent-body) 项目创始人。

今天我想聊聊未来数据库的技术核心竞争力会是什么？同样先看终局，然后看GAP，再推理实现。

假设现在是 2029 年，一家大型制造或零售企业里，跑着上万个自主协作的 AI Agent：采购 Agent 盯着全球供应链异常自动改派订单，法务 Agent 实时审阅每一份补充协议里的违约敞口，客服与履约 Agent 直接联动仓库处理客诉赔付。它们不是在聊天框里陪人解闷的玩具，而是 7×24 小时直接读写业务状态、拍板干活的生产级数字员工。

现在你顺着这个画面往下想一个最现实的问题：**当这上万个 Agent 同时上生产、跑出规模效应的时候，系统里最先崩掉的会是什么？**

很多人第一反应是大模型不够聪明、幻觉太高。但真在生产环境摸爬滚打过的人心里都清楚，模型能力每半年都在台阶式暴涨，真正把 Agent 卡死在“Demo 很惊艳、上线就抓瞎”的，其实是底下那层**数据底座**。

沿着“终局倒推”的思路，只要你把 Agent 规模化生产的链条一环扣一环拆开，就会得出一个非常反直觉、但逻辑上几乎无解的结论：**未来数据库的头号瓶颈，将不再是传统意义上的 CPU 计算与事务锁，而是 GPU 算力、嵌入业务场景的专用内置模型，以及数据本体实时刷新带来的极端 IO 压力。**

咱们顺着这条逻辑线，一步步往下推。

## 一、终局倒推：没有 80% 的暗数据，Agent 根本上不了生产

为什么说现有的数据库撑不起规模化的 Agent？

因为过去四十年，关系型数据库和数仓管得极其漂亮的，其实只是企业里最规整的那 **20% 结构化数据**——ERP 里的订单表、CRM 里的客户字段、财务系统里的流水账。而行业里反复被验证的一个冷酷现实是，根据 [IDC 和 Gartner 的估算](https://superkind.ai/blog/unstructured-data)，企业里大约 **80% 到 90% 的数据都是非结构化数据**；[IDC 甚至预计全球数据总量中高达 80% 属于非结构化形态](https://www.forbes.com/councils/forbestechcouncil/2022/02/03/the-unseen-data-conundrum/)。

这些数据长什么样？它们是塞在邮件附件里的 PDF 补充协议、钉钉和 Slack 里的群聊拍板记录、客服电话的语音转写、产线巡检拍的照片、设备报错日志，以及散落在无数共享文档里的 SOP。业界管这些沉睡在角落、很难被 SQL 直接查到的资产叫 **“暗数据（Dark Data）”** 。

你想想，如果一个 Agent 只能看到 ERP 里那张干巴巴的订单表，却看不到销售在邮件里答应客户的“特殊账期”、看不到法务在 PDF 里批注的“免责条款”、也看不到群里刚同步的“港口拥堵预警”，你敢让它自动拍板吗？绝对不敢。

但反过来，把这 80% 的暗数据一股脑塞进向量库做个朴素的 RAG 就能解决吗？早就被证伪了。切碎的文档片段没有业务语义，没有实体间的因果约束，更没有“谁能改什么状态”的操作边界。

所以，Agent 要规模化上生产，中间必须架起一座桥——**数据本体（Data Ontology）的建立与实时维护**。

你看看目前在企业级 AI 落地最扎实的路线之一，比如 [Palantir Foundry 与 AIP 的架构设计](https://flur.ee/blog/palantir-ontology-explained)，它的核心秘密根本不是自研了多强的大模型，而是用 **Ontology（本体）** 把底层的结构化表和海量暗数据映射成业务世界里活生生的对象（人、订单、设备、合同）、关系（隶属、制约、触发）和可执行动作（审批、改派、冻结），让本体同时充当 Agent 的**上下文（Context）** 和**工具集（Toolset）** 。

话说到这儿，第一个关键转折点就来了：建本体听起来很美，可你一旦要把 80% 的暗数据持续喂进本体、再让 Agent 高频去查这个本体， **数据库里跑的“算子”彻底变天了。**

## 二、算子变天：老关系算子卷到头了，Agent 本体需要一整套“吞算力”的新算子

过去几十年，关系型数据库的算子体系（`SELECT`、`PROJECT`、`JOIN`、`GROUP BY`、`AGGREGATE`）已经被人类打磨到了艺术品级别。向量化执行、SIMD 指令集优化、成熟的基于代价的优化器（CBO），让单机 CPU 一秒钟扫几千万行结构化数据跟玩儿一样。

为什么能这么快？因为老算子干的都是**确定性的符号计算**——比较两个整数谁大、比对两个字符串一不一样，在 CPU 上不过是几个时钟周期的事。

可到了数据本体和 Agent 时代，业务问数据库的问题全变味了。Agent 不会只问 `WHERE amount > 10000`，它会问：

* **语义过滤（Semantic Filter）** ：帮我把过去三个月所有“隐含交付延期风险”的供应商邮件和合同条款筛出来。
* **语义连接（Semantic Join）** ：把客服语音转写里的抱怨，和研发侧的缺陷工单、仓储侧的批次记录做跨模态实体对齐。
* **本体抽取与归并（Entity Resolution & Extraction）** ：这份刚收到的扫描版变更函里，提到的“华东大区老王”到底对应本体里的哪个自然人、影响了哪三份在履约的框架协议？
* **语义聚合与推理（Semantic Aggregate / Rank）** ：综合这 50 份现场报告，给各条产线的停机风险打分排序。

这不是拍脑袋的科幻，学术界和工程界已经在把这些东西正式算子化了。比如斯坦福和伯克利团队推出的开源查询引擎 [LOTUS](https://www.arxiv.org/abs/2407.11418v1)，就明确把基于大模型的 `map`、`reduce`、`filter` 等**[语义算子（Semantic Operators）](https://github.com/lotus-data/lotus)** 直接引入到了类 Pandas/SQL 的数据查询引擎里。

你顺着这个逻辑往下算一笔账，就能瞬间感受到寒意：

以前一个 `WHERE` 过滤算子，耗时是**纳秒级**，吃的是 CPU 周期；现在一个语义过滤或者实体消歧算子，本质上是在跑**神经网络前向推理**，耗时直接飙升到**毫秒甚至秒级**，吃的是海量矩阵乘加运算。

一旦数据本体面向成千上万个 Agent 开放这种高频、批量的语义算子，**数据库的算力底座就彻底翻篇了。**

## 三、瓶颈一：算力重心大迁徙——GPU 算力与“内置业务小模型”

有人可能会说：“算子需要推理，那我直接在数据库里调云端大模型 API 不就完了吗？”

真上生产，这条路绝对走不通。你想想，一张千万级的暗数据底表，哪怕只做一次全量语义过滤或本体刷新，调外部通用大模型 API，光是网络 RTT 延迟、Token 账单以及数据出域的合规风险，就能瞬间把任何企业的预算和 SLA 击穿。

于是，顺理成章的工程推演就是：**未来的数据库必须把模型“吞”进引擎内部，在离数据最近的地方，靠 GPU 算力和高度定制的“业务内置小模型”来扛住日常算子开销。**

这里面藏着两层实打实的瓶颈：

1. **第一层是 GPU 算力本身成为数据库的“新 CPU”。**
   不光是语义推理吃 GPU，就连本体底层最基础的向量索引构建与检索，CPU 也已经力不从心了。来看一组硬核实证数据：根据 [Spheron 在 2026 年公布的实测基准](https://www.spheron.network/blog/deploy-nvidia-cuvs-cagra-gpu-vector-search-indexing/)，面对 5000 万条向量，用 32 核 CPU 构建 HNSW 索引需要足足 **8 到 12 个小时**——大半天没了；而换用 H100 GPU 跑 [NVIDIA cuVS 的 CAGRA 索引](https://developer.nvidia.com/blog/optimizing-vector-search-for-indexing-and-real-time-retrieval-with-nvidia-cuvs/)，同样的 5000 万条向量建库时间直接压到 **30 分钟以内**。在 1000 万条 1536 维向量测试中，H100 CAGRA 建库只要约 **45 秒**（P50 延迟 0.6ms），而 32 核 CPU HNSW 要跑约 **22 分钟**（P50 延迟 3.8ms），[NVIDIA cuVS 结合动态批处理还能将高并发在线检索吞吐拉升 8 倍以上](https://developer.nvidia.com/blog/optimizing-vector-search-for-indexing-and-real-time-retrieval-with-nvidia-cuvs/)。
   你想想，这还只是索引构建。如果再加上每天源源不断涌入的暗数据向量化、多模态解析、重排（Rerank），数据库集群里没有成规模的 GPU 算力池，本体根本“转”不起来。

2. **第二层是“处理业务的特殊内置模型”的调度与演进瓶颈。**
   通用大模型太重、太贵、太慢。数据库要扛住高并发本体算子，必须在引擎内部沉淀一批极轻、极专的**内置模型**——专门抽合同实体与条款的 NER 模型、专门做行业黑话同义词对齐的 Embedding 模型、专门判别风控等级的分类小模型、专门做 Top-K 精排的 Cross-Encoder。
   这带来的新难题是：传统数据库只需要管好“数据和 SQL”，未来数据库还得管好“模型权重显存驻留、动态 Batch 调度、异构算子编排（哪一步走 CPU 过滤，哪一步进 GPU 小模型，哪一步才兜底调用大模型）”，以及**业务规则一变，内置小模型怎么低成本热更新、不让旧本体和旧向量大面积失效**。

好，先别松气。假设你财大气粗，买够了 GPU，也把业务内置小模型塞进了数据库里。问题解决了吗？

**远没有。因为真正的第二座大山，正堵在下一秒。**

## 四、瓶颈二：本体实时刷新，直接把老数据结构的 IO 打穿

如果数据本体像图书馆的纸质目录一样，一年只编一次，那其实还好办——晚上离线跑批，白天只读不写。

可 Agent 上生产最要命的要求是：**本体必须实时刷新。**

你想想那个画面：客户刚刚在邮件里发来一份盖章的补充协议，或者工厂里某个传感器刚报了一个异常工单。如果在接下来的 5 分钟里，数据本体没有实时同步这个变化，另一个正在跑的采购或客服 Agent 就会基于**过时的本体状态**做出完全错误的决策——这在生产环境就是 P0 级事故。

现在，请你跟着这“一笔业务变更”，潜入数据库底层看看会发生什么恐怖的连锁反应：

一份新文档进来 → 内置模型抽取实体与属性 → 结构化字段要更新 → 语义向量要重新生成并插入/覆盖旧向量 → 倒排索引要分词写入 → 属性图里的节点和边要重新挂载、甚至修改多跳关联关系。

**前端轻飘飘的一次业务事件，到底层被放大成了 3 到 4 套完全不同索引结构的并发随机写与同步刷新。** 这就是恐怖的**本体刷新写放大与 IO 风暴**。

更扎心的是，我们过去几十年引以为傲的那些经典数据结构，面对这种“高频实时更新 + 多模混合查询”的 Agent 负载，几乎个个都露出了命门：

### 1. 向量索引（HNSW）：内存贵到肉疼，一上盘、一更新就露馅
HNSW（分层可导航小世界图）是目前最火的向量索引，但它本质上是为**偏静态、全内存**场景设计的。[Tiger Data 在对比 HNSW 与 DiskANN 时就一针见血地指出](https://www.tigerdata.com/learn/hnsw-vs-diskann)：HNSW 为了维护多层图结构和大量邻居指针，非常吃内存；一旦数据量爆掉不得不落盘（比如基于磁盘页的 pgvector HNSW），每次图游走都会引发大量离散的随机磁盘读，[VLDB 2025 的研究论文《Turbocharging Vector Databases using Modern SSDs》](https://www.vldb.org/pvldb/vol18/p4710-do.pdf) 专门剖析了这类基于槽页（slotted page）的图索引在 SSD 上面临的严重 I/O 低效问题。
更要命的是**实时删改**：本体属性变了、旧文档作废了，HNSW 很难优雅地原地删除节点，往往只能打“墓碑标记（Tombstone）”，删多了图连通性退化、召回率暴跌，最后只能触发极其消耗 IO 和算力的全量/局部重建。这也是为什么学术界和工业界拼命在卷 DiskANN/Vamana、[`pgvectorscale` 的 Streaming DiskANN](https://www.tigerdata.com/learn/hnsw-vs-diskann)，以及主打十亿级向量原地增量更新的 [SPFresh](https://www.researchgate.net/publication/374920073_SPFresh_Incremental_In-Place_Update_for_Billion-Scale_Vector_Search)。

### 2. 全文检索（BM25）与模糊检索：体量、合并与长尾延迟的三重夹击
千万别以为有了向量检索，BM25 和模糊检索就可以退休了。恰恰相反，Agent 在生产环境查精确的物料编码（SKU）、合同号、错别字客户名、专业缩写时，向量检索经常“差之毫厘谬以千里”，必须死磕 BM25 全文检索和模糊检索（Fuzzy Search）。
但老倒排索引（Inverted Index）在超大体量和实时刷新下同样很吃力。[一篇关于十亿级文档分层 BM25 检索的 arXiv 研究指出](https://arxiv.org/html/2608.00229v1)，单单是十亿篇文档的扁平 BM25 索引，体积就高达约 **400 GB**，要把它稳在内存里需要和语料规模成正比的巨量 DRAM。如果再加上本体实时写入带来的高频 Segment 刷盘与后台 Compaction（段合并），再叠加模糊检索里动辄展开大量词项的编辑距离（Levenshtein）或 N-gram 扫描，磁盘 IO 带宽和 P99 尾延迟瞬间就会被打满。

### 3. 属性图（Property Graph）：本体最核心的“指针追逐”死穴
数据本体的灵魂是关系，关系最自然的表达就是属性图（Property Graph）。Agent 做复杂归因和影响面分析，动辄要做 3 跳、5 跳的图遍历（比如：`订单 -> 涉及物料 -> 对应二级供应商 -> 近期涉诉案件`）。
可传统图数据库在底层跑多跳遍历时，有一个绕不开的物理死穴叫 **“指针追逐（Pointer Chasing）”** 。正如 [arXiv 关于图数据库正则路径查询加速的论文](https://arxiv.org/pdf/2403.10051) 以及[业界对指针遍历与矩阵遍历的性能剖析](https://medium.com/@shekhar.manna83/pointer-traversal-vs-matrix-traversal-the-performance-revolution-b4388573b733)所揭示的：每顺着一条边找下一个邻居，内存或磁盘地址都是不可预测的随机跳转，几乎每一跳都在触发 CPU Cache Miss 和随机 IO，极难做并行化和预取，CPU 大把时间都干等着内存和磁盘把数据送过来。当本体还在后台高频改边、加点时，锁竞争加上随机 IO，吞吐直接腰斩。

### 4. 最致命的隐性成本：多引擎拼凑的“胶水税”
回头看看今天大多数团队是怎么搭 Agent 数据底座的：业务数据放 PostgreSQL/MySQL，向量放 Milvus/Qdrant，全文和模糊查 Elasticsearch，图谱放 Neo4j，暗数据原件扔在对象存储的 Parquet/S3 里。
结果呢？一笔本体刷新要在四个系统间做分布式双写/四写，光是对齐一致性、回放日志、处理某个库写失败的脏数据，就把工程团队和网络/磁盘 IO 折磨得死去活来。

为了把刚才这一连串的范式转移看得更透彻，我们可以直接拉一张表，对比一下“传统关系数据库时代”和“Agent 本体数据库时代”的底层基因差异：

| 对比维度 | 传统关系型数据库时代 | Agent 规模化生产的本体数据库时代 |
| :--- | :--- | :--- |
| **核心纳管对象** | 20% 高度规整的结构化表 | 20% 结构化 + 80% 暗数据映射出的活体“数据本体” |
| **核心查询算子** | 确定性符号算子（`SELECT`、`JOIN`、`GROUP BY`） | 关系算子 + 语义算子（`SEM_FILTER`、`SEM_JOIN`、实体消歧、图推理） |
| **第一算力瓶颈** | CPU 周期与锁竞争 | GPU 推理/建库算力 + 业务内置小模型调度 |
| **第一 IO 瓶颈** | 顺序日志写 + B+ 树页随机读写 | 本体实时刷新引发的多索引写放大 + 图指针追逐 + 跨模态随机读 |
| **索引与存储形态** | 单一 B+ 树 / LSM-Tree + 列存（如 Parquet） | 向量 + BM25 + 模糊 + 属性图 + 多模态原件的融合引擎 |

## 五、破局的方向：下一代数据库长什么样？

把病根和瓶颈聊透了，现在我们再把视角拉回架构演进。既然已经推演出未来卡脖子的就是 **“GPU + 内置模型算力”** 和 **“本体实时刷新下的多模 IO”** ，那下一代真正能扛起 Agent 规模化生产的数据库，必然会沿着下面四条主线长出新骨头：

### 1. 存储格式重构：告别只为“全表扫描”设计的老列存
以前大数据时代大家爱用 Parquet，因为它压缩比高、做离线全表列扫极快。但 AI 和 Agent 工作负载完全相反——它经常需要根据向量或图谱命中几千个分散的 Row ID，然后瞬间把对应的原文段落、图片切片或属性抽出来，这是极其高频的**随机点查（Random Access）** 。
所以行业已经开始向 AI 原生存储格式演进。比如开源多模态湖仓格式 [Lance](https://lance.org/)，通过引入高效的行寻址（Row Addressing）和二级索引，在保留列扫能力的同时，把[随机访问性能做到了比 Parquet 快 100 倍以上](https://datalakehousehub.com/knowledgebase/lance-file-format/)（[在部分实测工作负载中甚至达到数百至数千倍级差距](https://www.dremio.com/blog/exploring-the-evolving-file-format-landscape-in-ai-era-parquet-lance-nimble-and-vortex-and-what-it-means-for-apache-iceberg/)）。未来的暗数据底座，底层文件格式必须天生支持多模态数据的亚毫秒级随机拾取。

### 2. 数据结构与索引大融合：把“四套库”揉成“一颗核”
靠 CDC 同步去粘合关系库、向量库、ES 和图数据库，注定是过渡方案。未来的核心突破，一定在于**统一存储层上的多模索引融合**——在同一份数据布局和事务日志下，原生协同支持结构化列、向量（DiskANN/SPFresh 这类 SSD 友好且支持原地增量更新的图/分区索引）、分层 BM25/模糊检索以及属性图（像 [LatticeDB](https://github.com/jeffhajewski/latticedb) 这类探索单引擎同时编译图遍历、向量和 BM25 的思路，正是早期的风向标）。
同时，底层 IO 引擎必须深度吃透现代 NVMe SSD 的高队列深度特性（如基于 `io_uring` / `liburing` 的全异步 IO 管线，配合缓存感知布局与向量化/矩阵化图遍历），把传统“指针追逐”和“小随机读”的 IO 损耗压到物理极限。

### 3. 优化器升维：从 CPU 代价模型进化到“异构算力 + 模型级联”调度器
传统数据库的查询优化器（CBO）只算磁盘页数和 CPU 行数；下一代数据库的优化器，必须算清楚 **IO 代价、CPU 代价、GPU 显存带宽、内置小模型推理延迟和大模型 Token 成本**这五笔账。
一条 Agent 发来的复杂本体查询进来，聪明的优化器会自动做**算子下推与级联漏斗**：先用微秒级的结构化过滤、BM25 和模糊检索把百万级候选集砍到几千条；再用驻留在 GPU 里的业务内置小模型做批量向量/语义精排，砍到几十条；最后只有那 1% 真正模棱两可、需要深度逻辑推理的硬骨头，才交给大模型算子去拍板。这样才能把 GPU 算力和延迟压在生产级 SLA 之内。

### 4. 本体维护流式化：从“全量重算”走向“增量微扰（Incremental Delta）”
要彻底治好本体实时刷新的 IO 病，就不能每来一条暗数据就大动干戈。数据库需要像现代流计算（Incremental View Maintenance, IVM）一样，把数据本体当成一张**持续增量维护的语义物化视图**：一份合同更新了第三条，系统只重算第三条的 Embedding、只更新受影响的局部子图边权和倒排增量，把写放大精准锁死在最小变更半径里。

---

## 结语：回到起点，看清下一代数据库的真正护城河

聊到这里，我们再回头看开篇那个问题：三年后，上万个 Agent 在企业生产环境里浩浩荡荡跑起来时，谁会是最大的赢家？

大概率不是只会拼参数量的基座模型，也不是只会把四五个开源组件用胶水粘在一起的“套壳 RAG 平台”。

**真正扼住咽喉的，是能够把 80% 暗数据实时炼化成活体“数据本体”的新一代 AI 原生数据库。** 它的护城河非常硬核、非常底层——往上看，它得懂怎么把业务专用小模型和 GPU 算力编排进查询算子里；往下看，它得用全新的存储格式、融合索引和异步 IO 架构，把向量、BM25、模糊检索和属性图在实时刷新下的性能死穴一个个啃下来。

过去四十年，数据库教会了计算机如何精确地记住“人类录入的数字”；接下来十年，数据库要学会的，是如何带着算力和模型，实时理解并维护“整个商业世界正在发生的真相”。这，才是 Agent 时代最激动人心的底层战役。
